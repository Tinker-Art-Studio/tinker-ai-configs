## Findings

**1. Blocker — `addDays` collides with app.js's `addDays`; in the browser `reminderWindow()` returns Date objects and `selectRemindersDue` finds nothing.**
`js/schedule-helpers.js:382` (new) vs `js/app.js:3914` (existing, `addDays(date, n)` → Date in, Date out). Both are classic scripts; index.html loads app.js *after* schedule-helpers.js (lines 1098, 1100), so app.js's function declaration overwrites the global binding — exactly the "later script silently wins" hazard timeoff-schedule.js:20–22 documents. `reminderWindow` resolves `addDays` through the global scope at call time, so even its *internal* call is hijacked.
Concrete: in the browser, `reminderWindow('2026-10-15')` → app.js `addDays('2026-10-15', 1)` → `new Date('2026-10-15')` +1 → returns `[Date, Date]`. Feed that to `selectRemindersDue`: `dayKeyForDate(Date)` builds `new Date('Fri Oct 16 2026 …T12:00:00')` → Invalid → dayKey `undefined`; `isInFutureWindow(future, Date)` compares a Date to `'2026-10-01'` → NaN → false; `hasOwnProperty(overrides, Date)` coerces to `"Fri Oct 16 …"` → false. Result: `[]` for everyone, no error. The Phase 4 view ("computed by the SAME rule the job uses") would show nothing due and the job (Node `require`, module scope) would send — the two disagree, which is the one thing the commit says they can't. Jest can't see it because it `require()`s the module.
Fix: rename the helper (e.g. `addCalendarDays`) and update `reminderWindow`, the exports and the tests. Then replace the hand-kept const list at `schedule-editor-wiring.test.js:1633` with a generic guard: extract every top-level `function|const|let|var` name from schedule-helpers.js and assert none is declared at top level in app.js, firebase-data.js, auth-guard.js or push-notifications.js. The current test checks five consts by name and no functions, so it passed this commit.

**2. Should-fix — the "recurring days never qualify" claim is enforced only by convention, and the test that says it pins it is vacuous.**
`js/schedule-helpers.js:353` only checks `shift.remind === true` on whatever `getShiftForDate` returned; a recurring weekday is returned as a spread copy, so a `remind: true` on `recurring.Mon` *would* be selected. The test at `schedule-helpers.test.js` ("a flag on a weekday is meaningless and ignored") puts `remind: true` on `Mon` and then shadows the only Monday (2026-10-19) with a `null` day-off override — the recurring branch is never reached. Concrete: `selectRemindersDue([{ uid:'g', recurring:{ Mon:{ start:'10:00', end:'14:00', remind:true } }, overrides:{} }], ['2026-10-19'])` → one entry. No app writer puts the key on a weekday today, so this is latent, but the acceptance criterion is stated as a property of the function.
Fix: make the test real (remove the `'2026-10-19': null`, or add a second flagged-weekday date with no override), and add the two-line guard mirroring the resolver's own routing: `const map = isInFutureWindow(schedule.futureSchedule, dateStr) ? ((schedule.futureSchedule||{}).overrides||{}) : (schedule.overrides||{}); if (!Object.prototype.hasOwnProperty.call(map, dateStr)) return;` before trusting `shift.remind`.

**3. Should-fix (needs Christie's call) — a partial-day approval silently unflags the employee's own flagged shift.**
`js/timeoff-schedule.js:97–101`: `value = { start, end, ...PARTIAL_CONSTANTS }` then `withStaleKeysDeleted(value, previousOverride, deleteField)` with no predicate → every surplus key on the previous shift, `remind`/`remindUid` included, gets a delete sentinel. Concrete: Grey's Oct 17 `{10:00–14:00, note:'SDOC', remind:true, remindUid:'grey'}`; a partial day off (leave at 12:00) is approved → stored `{10:00–12:00, tinker, note:'Time off (partial day)'}`, no flag → no reminder for a shift Grey still works; on withdrawal the flag comes back (the round trip is fine — the modern restore path handles both shapes). This is a time change by another writer, and the design review's rule for the AI path was "a time change never silently unflags." The plan's BDDs cover "partial then flagged" and "full-day round trip", not this. Either behaviour is defensible (the reduced shift's note is replaced too); what's wrong is that it's silent and untested.
Fix if preserving: `if (previousOverride && typeof previousOverride === 'object' && previousOverride.remind === true) { value.remind = true; if (typeof previousOverride.remindUid === 'string' && previousOverride.remindUid) value.remindUid = previousOverride.remindUid; }` before line 101 (the record's `wrote` can carry it or not — `sameOverride` ignores it either way). Fix if not: a comment at line 97 saying a partial day drops the flag on purpose. Both: a `timeoff-schedule.test.js` case "ORIGINAL flagged → partial applied → stored value has/lacks the flag → reversed → flag back".

**4. Nit — `partitionRollback` still compares with `sameStructure`, which sees the flag.**
`js/schedule-helpers.js:591–593`. Concrete: tab A confirms sub S (coverage written `remind:true`); a manager unticks it (Phase 4); tab B, modal already open, loads S *after* the untick (`previousOverride` = coverage without flag), writes ours, request write refused `sub-changed`; `same(previousOverride, A.wrote)` false (flag differs), `same(ours.wrote, A.wrote)` true → `leave`, no `mismatch` → S's shift now carries `remind:true` again and the alert says nothing. With a flag-insensitive compare the first test passes → roll back → restore the unflagged value. Narrow (three actors), but it's the second place that compares override values and the commit calls `sameOverride` "the ONE compare". Fix: strip `remind`/`remindUid` from both sides before `sameStructure` here, or export a shared `sameOverrideIgnoringReminder` from schedule-helpers.js and have timeoff-schedule.js use it too, so there is literally one.

**5. Nit — SET mode without a resolvable `remindUid` discards the one already stored.**

## Checked and found sound
- **Untick is a real delete** in both maps, never `false`; day-off ↔ shift transitions replace the whole value; a never-flagged override gets no sentinel (unit + emulator, including one level deeper under `futureSchedule` with the rest of the block untouched).
- **`existing` read from `after`**: safe. The batch only ever mutates `after.overrides[d]` / `after.futureSchedule.overrides[d]`; bounds are never touched, so window membership is invariant across the batch and each date reads a value no earlier iteration touched. Routing uses the same predicate the resolver uses; `futureSchedule: null` routes to base, `{}` (bounds-less) to future — both pre-existing semantics.
- **Model can't set the keys**; `after` mirrors the leaves; the transaction passes `opts` through, writes leaf `FieldPath`s in varargs form, awaited; the AI caller still passes two args (preserve).
- **Sub path**: `ctx.subUid` is always `match.uid` (claimedBy), the write targets that same uid-keyed doc, so `remindUid === docId`; the overwrite-existing-shift path keeps the flag by whole-value replacement and the record's `previousOverride` restores whatever was there.
- **`stillHoldsWhatWeWrote`**: `sameOverride` is its only value compare; legacy branches compare `=== null` or not at all. The two `sameStructure` guards in firebase-data.js (`:659`, `:731`) compare request records with the caller's copy of the same records, never the live schedule. `scheduleSignature` compares two Firestore round-trips; a concurrent flag toggle would (correctly) block the whole-future delete with "someone else changed this".
- **Change email**: `normaliseShift`/`sameShift` never read the flag. **Destructive-save confirm** counts `note` sentinels only, as the comment says.
- **Intl**: `hourCycle:'h23'` + `hour:'2-digit'` + `formatToParts` yields `"00"…"23"` on V8 (Node 18/20/22, Chrome) and JSC (Safari ≥ 13); no `hour12` anywhere, so the en-US h24-at-midnight bug can't apply; the U+202F AM/PM space is irrelevant (h23, parts not joined); `% 24` is belt-and-braces and NaN falls through to `isSendTime → false`. `DENVER_PARTS` at module scope is right (constructed once; a missing tz database would throw at cold start, loudly). No collision on the three new consts (grep clean).
- **Other writers**: `migrateSchedule` copies whole documents → flags survive; the Summer importer's recursive merge keeps a re-imported shift's flag; the in-app CSV writer (`app.js:5780–5789`) wipes every future override — pre-existing, correctly scheduled for Phase 3. The editor's `handleAddOverride` drops the flag on any edit/move of a flagged override (`app.js:3213`) — planned for Phase 3's pre-filled checkbox; between now and then only sub coverage flags exist and nothing reads them, so no production effect if Phases 1–5 deploy together.
- **Firebase invariants**: no new collection; `remindUid` is guarded on every writer (`typeof === 'string' && non-empty`), so no `""`/`undefined`/`null` is ever written; all writes awaited.
