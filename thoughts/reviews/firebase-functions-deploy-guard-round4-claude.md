## Findings

### Blocking

**1. Blocking — F8 step 2 (hash bullet): the retry-after-failed-build path still cannot verify, and F8 contradicts D2-3's own test.** Round-3 Codex #4 / Claude #2 are only half fixed.

F8 keys the conditional on *"the newest **verified** attempt's"* tree id. But the case both reviewers named is a retry after a build **failure**, where the previous attempt is by definition unverified — so the rule falls through to "otherwise it must differ from the before-snapshot's", and that is unsatisfiable. `cloudfunctionsv2.js:291-294` writes the hash label into the function's labels at **create**, and `fabricator.js:309-324` creates the resource and *then* polls the operation, so a build that fails leaves the function present (state `FAILED`) already carrying `hash(T1)`. The retry is an update; the label is deterministic from source + backend env only (`cache/hash.js:21-24`, `applyHash.js:9-20`) and `--only functions:core` re-deploys without changing it (`planner.js:27`). So `hash_after == hash_before` → `deploy_match=no` → `deploy_verified=no`, exactly as F7's "the same sha is re-run under the same approval", D2-1's BDD and D2-5's BDD all require to succeed. D2-3's test list already asserts the opposite of F8 ("**same-sha retry** (equal hash → verified)"), so the plan contradicts itself.

*Fix:* record the per-function hash **and** the tree id in **every** attempt receipt (verified or not), and restate the rule as: if any earlier attempt receipt for this codebase carries this tree id, the live hash must equal that receipt's; otherwise it must differ from the before-snapshot's, with an absent before-hash counting as different. Add a scenario "first build fails for permissions → same sha re-run → verified".

**2. Blocking — F9 `--reverify` is unbounded, so it can mark a superseded attempt verified from a later attempt's production state — and `--diff` then diffs from the wrong base.**

F9 gates `--attest` on "It refuses unless that attempt is the newest" but imposes no such rule on `--reverify`, and `deploy_verified` for an attempt = "its own receipt's, or its newest verify record's". D2-3's ordering test exercises "attempt A unverified, attempt B verified, **then A reverified**" as a legitimate action. After B has shipped, `--reverify A` re-reads and re-probes *current* production and writes `deploy_verified=yes` onto A. `--status` then reports "last verified X" with X = A, and F9 says "`--diff` diffs from X" — i.e. from A's commit while B's bytes are what the CLI last pushed. That is precisely the class of bug the code this guard copies documents at length (`scripts/deploy-rules.sh:79-84`: "The guard could diff against the wrong base … and, worse, print 'nothing to deploy' for a change that never shipped"). The ordering test as written passes while X is wrong, because it only asserts that B is still named the newest *attempt*.

*Fix:* `--reverify` refuses unless the named attempt is the newest attempt (same rule as `--attest`); turn D2-3's "A reverified" case into a **refusal** test and add a positive test that reverifying the newest attempt upgrades only the probe/read-back dimensions. Also record the before-snapshot digest and per-function before-hash in the attempt receipt, so `--reverify` can re-apply F8's hash bullet instead of silently skipping it (today the in-flight file holds the only copy and D2-3 step 11 deletes it).

**3. Blocking — D2-1 / F7: nothing re-checks the Editor grant immediately before the first build, and the Phase D log explicitly asked for that check.**

`my-clay-hub-phase-d-project.html:409` records: "No default Compute service account exists yet (Compute Engine API not enabled) — **Phase D2 must repeat this check right after its first functions deploy**, in case that creates `760301318440-compute@developer.gserviceaccount.com` with Editor." D2-1 step 2 is what creates that account (enabling the Compute Engine API), Google's automatic Editor grant for default service accounts lands asynchronously, and D2-1 step 8's screenshot may be taken before it appears. The next check is D2-5 step 4 — *after* the build has already run. D2-2/D2-3/D2-4 also sit between D2-1 and D2-5, so even without the async race the IAM state at deploy time is unverified. The single window F7 exists to close is left open.

*Fix:* add **D2-5 step 0**: Christie re-reads IAM "View by roles" (Google-provided grants shown) and confirms neither candidate holds Editor or Cloud Build Service Account, recorded immediately before the ask; make it a precondition of `--approved` and add a BDD "Editor reappeared on the Compute account → stop, remove it, re-record".
