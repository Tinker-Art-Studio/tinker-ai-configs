## MEDIUM

**1. `scripts/check-live.sh:36-43` — the propagation gate runs first, so during normal lag *nothing at all* gets verified.** The file, private and function checks are lag-free by construction on `BASE`, yet an exit 2 on the main address returns before any of them runs. Right after a paid deploy — the moment lag is most likely — the script can report INCONCLUSIVE having proved nothing about the bytes, the 65 unpublished paths or the nine functions, and `deploy.sh` then ends. A real leak or a dropped function is deferred to a manual re-run. Sections 2-4 belong first, with the propagation question last.

**2. `scripts/check-live.sh:55-63, 72-81, 85-91` — the per-path retry is gone, so one transient response is now a hard FAILED.** The old code retried each file and private path once after 15 s; now 90 of ~92 requests get a single attempt, while the verdict got stricter (exact content type). A 503 or a slow edge produces `DIFF`/`PUBLIC` → `[check-live] FAILED`, and the plan's failure BDD (plan:163-164) says that means "republish the previous deploy in Netlify's UI" — rolling back a good deploy on a blip. A transport-level failure is handled (exit 2), an HTTP-level one is not.

**3. `scripts/deploy.sh:39` — `refuse` on a missing `deploy_url` discards a working fallback after a paid deploy.** `check-live.sh:17` is `BASE=${2:-$LIVE}`, and `${2:-…}` treats an empty argument as absent — so passing an empty `DEPLOY_URL` would degrade gracefully to checking the main address. Instead the script stops with zero verification of a deploy that is already live. The key is present in today's CLI (verified above), so this only fires on a CLI change — but that is exactly when you'd want the fallback rather than a stop. Dropping lines 39 and letting line 41 run unchanged is the whole fix.

**4. `scripts/deploy.sh:36` — `--json > "$OUT"` makes any CLI prompt invisible and throws away the log URLs.** With `log()` suppressed, the upload is silent and the `logs` / `function_logs` URLs the JSON carries are parsed away and never shown — the first thing you want when check-live complains. Worse, inquirer writes prompts to stdout, which is now a file: if production deploys are ever locked (`deploy.js:253-273` — and "lock to this deploy" is a plausible reaction to a bad deploy, which the plan's own rollback invites), `npm run deploy` hangs with no visible prompt and no explanation. Echoing `logs` alongside the deploy URL covers the common case.

**5. `scripts/check-live.sh:31` — `exit 2` outranks an already-found failure.** A leak found at path 3 followed by a network blip at path 40 ends in `[check-live] INCONCLUSIVE (network) — re-run`, exit 2, even though a `PUBLIC` line was already printed 40 lines up, and both `deploy.sh:9` and `CLAUDE.md:70` teach "exit 2 = just re-run".
