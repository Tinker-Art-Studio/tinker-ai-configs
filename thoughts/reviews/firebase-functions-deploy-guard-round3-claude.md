## Findings

### Blocking

**1. Blocking — F8: "the env *keys* are exactly `FIREBASE_CONFIG` and `GCLOUD_PROJECT`" is false for every real deploy, so `deploy_verified=yes` is unreachable while every fake-CLI test passes.**
K17 is about the *hash input*, which is the **backend-level** env (`applyHash.js:9` → `getEnvironmentVariablesHash(wantBackend)` over `wantBackend.environmentVariables`, `prepare.js:110` — two keys). F8 applies it to the **deployed endpoint** env, which is a different object: `prepare.js:122` copies the two, then `:133` adds `EVENTARC_CLOUD_EVENT_SOURCE = projects/<p>/locations/<r>/services/<id>`; `cloudfunctionsv2.js:82-86` (create) and `:132-136` (update) then add `FUNCTION_TARGET` and `LOG_EXECUTION_ID`. `functions:list` reads all of them back (`:393`). So the live key set is **five**, not two — `deploy_match=no` forever. This is round‑2 finding #2's failure shape re-entering through a new door.
*Fix:* expected key set = `{FIREBASE_CONFIG, GCLOUD_PROJECT, EVENTARC_CLOUD_EVENT_SOURCE, FUNCTION_TARGET, LOG_EXECUTION_ID}`, with `EVENTARC_CLOUD_EVENT_SOURCE` asserted equal to the computed resource string and `FUNCTION_TARGET` to the manifest's entry point; keep "no other key" as the control that catches a hand-injected variable (which `prepare.js:267-272` would otherwise silently preserve). Add a mutation test for one extra live key, and make one D2‑5 step print the observed key set before this check is allowed to gate `deploy_verified`.

**2. Blocking — F8: "the `hash` label … **differs** from the before-snapshot" makes re-running the same approved sha permanently unverifiable — which D2‑5's own BDD and F7 both require.**
`getEndpointHash(sourceHash, envHash, secretsHash)` (`cache/hash.js:22`) covers nothing but source, backend env and secrets. `--only functions:<cb>` sets `targetedByOnly`, so `planner.js:27` never skips and the CLI *does* re-deploy — producing an identical label. So D2‑5's "the same sha is re-run under the same approval" and F7's "re-run the same sha under the same approval" both end `deploy_verified=no` by construction. Round 2 recommended the conditional form ("`hash_after != hash_before` exactly when the tree id changed"); the plan kept only half of it.
*Fix:* compare against the tree id in the newest verified receipt — require `hash_after != hash_before` when the tree id changed and `hash_after == hash_before` when it did not; test both directions.

**3. Blocking — D2‑5 steps 1+3 / F9: the bootstrap turns on a `--reconcile` mode the plan does not define, and which cannot emit `deploy_verified=yes`.**
F9's `--reconcile` is the crash path: it is driven by the in-flight file ("the recorded sha", "names the attempt"). But D2‑5 step 1 *completes* — it writes a receipt and removes the in-flight file (D2‑3 step 11). Step 3 therefore has no `cli_exit`, no `backstop_seen`, no `skip_line_seen`, no before-snapshot and no transcript to re-read, yet `deploy_verified=yes` requires all of them (F9). Under finding 2 there is also nothing to compare the hash against.
*Fix:* define a third, named mode (e.g. `--reverify <receipt-tag>`) that carries the named receipt's `cli_exit`/`backstop_seen`/`skip_line_seen`/tree id/manifest sha256 forward, re-reads and re-probes, and writes a superseding receipt that names the receipt it upgrades; make D2‑5 step 3 use that, and add its own test.

**4. Blocking — F1 contradicts the meta line, and "`deploy-rules.test.sh` passes untouched" is not achievable.**
The meta says "The rules guard `scripts/deploy-rules.sh` is not changed"; F1 says the `receipt_rows … rc_of` block "is moved into `scripts/lib/receipts.sh`, and both guards source it". Both cannot be true. Worse, the rules harness copies exactly two files into the throwaway clone and rewrites `^REPO="…"` in each (`scripts/deploy-rules.test.sh:110,114`), so a sourced `scripts/lib/receipts.sh` is either missing in the clone (every test fails) or read from the real repo (the isolation the harness exists for is gone). And because that file would then decide receipt *ordering*, it must join the rules guard's `CONTROL_FILES` (`scripts/deploy-rules.sh:207`) or an older approved commit can bring older ordering logic — the exact class of bug the comment block at `:78-121` documents.
*Fix:* state plainly that `deploy-rules.sh` gains one `source` line; add `scripts/lib/receipts.sh` to `CONTROL_FILES`; change the harness to copy and pin it; and replace "passes untouched" with a D2‑2 acceptance step that the rules suite passes *after* those three edits, plus a test that the functions guard and the rules guard order an identical tag set identically.

**5. Blocking — F2/F13: nothing declares the approved **invoker**, and no refusal test covers an endpoint that has none.**
`v1alpha1.js:145` makes `invoker` optional in the manifest, and `fabricator.js:345` turns an absent invoker into `["public"]` → `allUsers`. `runtime-accounts.json` pins *identities* but nothing pins *callers*; F13's "with an approved invoker" has no artifact behind it, and neither D2‑2's nor D2‑3's enumerated refusals include "no invoker", "`invoker: ['public']`", or "no `serviceAccount`" (absent → GCF's default, i.e. the broad Compute account). An implementation that checks only trigger kind satisfies every written acceptance criterion and ships a public function — the one outcome this plan exists to prevent.
*Fix:* make `functions/runtime-accounts.json` the single per-function declaration of **both** runtime account and invoker; refuse any endpoint whose invoker is absent, is `['public']`, or differs from the declaration, and any endpoint with no `serviceAccount`; add the three refusals to D2‑2/D2‑3's lists with passing twins, plus a BDD.

**6. Blocking — no choice enforces the D23 invariants the plan lists as "already decided".**
Round‑1 Codex #11 is dispositioned to "D2‑3 step 5 and F8's field match", but D2‑3 step 5 names only F13/F2/F6, and F8 says `maxInstances`, concurrency, timeout and memory are "as declared" — vacuous when the manifest declares none (GCF then applies its own defaults and the read-back agrees with the manifest's silence). A partial implementation can deploy with no instance ceiling, or in the wrong region, and pass.
*Fix:* add a named choice listing the manifest invariants — `platform: gcfv2`, `region` exactly `['us-central1']`, `runtime: nodejs22`, and `maxInstances`, `concurrency`, `timeoutSeconds`, `availableMemoryMb` **present** — each with its own refusal and test, and have F8 compare the live value to the manifest's required value rather than to "as declared".

## Direct answers

**Q2 (security).** The byte-closure is genuinely strong now: F3 + the backstop + the sealed manifest close the post-predeploy code-execution window for real — after `detectFromYaml` succeeds, nothing between the hook and packaging runs user code (`prepare.js:74→183`), which is what round 2 asked for. The remaining ways to ship something public are finding 5 (no declared invoker, no refusal test) and finding 6 (no enforced invariants). F7's ordering is sound; the roles are minimal but may be insufficient (18). The anonymous probe is valid evidence that `allUsers` does not hold `run.invoker` on that service *at that moment*, provided the refusal is genuinely from the platform — which finding 9 says it cannot currently establish. It misses `allAuthenticatedUsers`, any named principal, and project/folder/org-level invoker grants (8), and it is a point-in-time reading that the next `setInvokerCreate` can overwrite wholesale (`gcp/run.js:122-128`).

**Q4 (receipt coherence).** The `complete|partial|unsafe` shape is gone; the dimensioned design is better and is compatible with the rules guard's ordering — `receipt_rows`' three clauses still hold (the stamp is reserved before the CLI and the tag written after, so "stamp ≤ tag date" survives even the 15-minute reconcile), attest tags live in a sibling prefix that `fetch_state`'s `refs/tags/deployed/my-clay-hub/*` already covers, and prefix scoping keeps the namespaces apart. Two mismatches: `--status`/`--diff` now need a *second* selector ("newest verified") that the shared library doesn't provide and that must be **fail-closed**, whereas the rules guard's annotation readers (`receipt_by`, `receipt_note`) are deliberately fail-**soft** — the extracted library will host both kinds and the plan should say so; and nothing says how a reconcile receipt (new stamp, older attempt) is distinguished from a deploy receipt when `--status` names "the newest attempt" and `--diff` banners "Y".

**Q5 (won't work as described).** Findings 1, 2, 3, 4, 10, 11, 12 are the ones that will not work as written. The offline CLI-path test *is* feasible (`lifecycleHooks` needs only a `Config` and `needProjectId`, both offline), `npm ci --prefix` *is* safe against the symlinked root, the hook regex extension is tractable with the existing token rules (note `functions:deletegcfartifacts` contains `functions:delete`, so anchor each alternative), and the sealed-manifest mechanism *does* work exactly as K2 claims.
