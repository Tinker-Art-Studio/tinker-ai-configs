## Review: `firebase-deploy-guard.html` (v1, design only)

### Findings, most severe first

**1. BLOCKER — "Fail closed" is false in Claude Code; a missing or crashing hook lets the deploy through.**
Section: *The hook*; Phase 2 BDD #3; Safety checklist bullet 5. The brief's premise ("a non-zero exit also blocks") is wrong per the hooks docs: **exit 2 is the only exit code that blocks**; exit 1, exit 127 (`No such file or directory`), and a **timeout** are all "non-blocking errors — the call continues through the normal permission flow." Sequence: someone moves/renames `~/.claude/hooks/firebase-deploy-guard.sh` (or `node`/`python3` isn't on the hook's PATH, or the JSON parse throws) → every Bash call, including `cd ~/studio-hub && firebase deploy --only firestore:rules`, proceeds. Exactly the case the plan claims to have closed.
Change: (a) in `settings.json` use `"command": "bash /abs/path/firebase-deploy-guard.sh || exit 2"` — a missing or crashing script then blocks *every* Bash call with the bash error on stderr, which is loud and fixed in one minute; that is the actual price of fail-closed, state it. (b) Inside the script: `set -euo pipefail`; deny by printing the JSON and `exit 0` *or* reason-on-stderr + `exit 2` — both work; never `exit 1`. (c) Keep the script free of anything slow (no git, no network) because a timeout is fail-open; parse with `/usr/bin/jq` (present on this Mac at `/usr/bin/jq`, so the "no jq" constraint is moot and jq is faster than `node -e` under nvm). (d) Phase 2 verification: rename the script, run `true`, expect a block — not a pass.

**2. BLOCKER — TOCTOU: the guard checks HEAD, then deploys whatever is on disk ~30–60 s later. Two ordinary sessions still reproduce the incident, now with a false tag on top.**
Section: *The guard* (checks 1–5, then "runs firebase deploy from --dir"). `npm test` is `firebase emulators:exec …` — tens of seconds. Sequence: Session A commits X, pushes, Christie says "approved to change firebase X". A runs the guard: HEAD==X ✓ clean ✓ on origin ✓, tests start. Session B (cwd Payroll) edits `~/studio-hub/firestore.rules` for its own feature — or runs `git pull`/`git checkout wip/…` in the shared tree. Tests finish (jest read the file at start, so they tested X). `firebase deploy` reads the file *now* → ships X + B's hunk. `live/…` and `deployed/…` are stamped X. Live ≠ X, and the tag now lies.
Change: never deploy the shared working tree. Resolve the sha (`git rev-parse --verify --quiet "$sha^{commit}"`), `git worktree add --detach "$tmp" "$sha"` (or `git archive | tar`), `ln -s "$repo/node_modules" "$tmp/node_modules"`, run `npm test` **and** `firebase deploy --only "$target" --project "$id" --non-interactive` inside `$tmp`, `git worktree remove` on EXIT. The tests read `firestore.rules` from cwd (`rules.test.js:65`), so they test the exported bytes. With this, HEAD is irrelevant and the dirty-tree check (#2 in the plan) should become a printed **warning**, not a refusal — a refusal invites a session to `git stash`/commit *someone else's* edits to get a clean tree, which is worse than the thing it prevents. Add `--project` regardless: `firebase use` stores an active project per-directory in the CLI's configstore and silently overrides `.firebaserc`.

**3. SHOULD-FIX — The plan contradicts the machine: a same-named `firebase-deploy-guard.sh` hook already exists in `~/.claude/settings.local.json`, and it is not user-scope. That is probably how Sep 21 happened.**
Section: *Research → Global settings* ("no hooks today… nothing to merge around"). `~/.claude/settings.local.json` (Aug 15) has `hooks.PreToolUse → bash ~/tinker-ai-configs/scripts/firebase-deploy-guard.sh` plus `autoMode.soft_deny/hard_deny` strings that name the three `--only` forms and the old phrase. The docs list only `~/.claude/settings.json` as user scope; `settings.local.json` is *project-local*, so that file is loaded only by sessions launched in `~`. Verified in this session (cwd `studio-hub`): `cd ~/tinker-ai-configs && echo firebase deploy` ran — the old hook's `cd` check would have denied it. So the `firebase-auto-mode-permissions-hardening` memory ("scoped universal/machine-wide") is wrong, and every session launched in Classbook/Payroll/etc. has had no hook at all.
Change: Phase 2 removes the hook from `settings.local.json` (one gate, one file), rewrites the three `autoMode` strings to name the guard script as the only approved form (Christie runs auto mode — the current `hard_deny` text could make the classifier block the guard itself), fixes that memory, and picks a filename that doesn't collide (`~/tinker-ai-configs/scripts/…` is git-tracked; reference it by absolute path as the old hook does rather than copying to `~/.claude/hooks/`).

**4. SHOULD-FIX — The hook's "invokes the guard → allow" exception is a loophole with no benefit.**
Section: *The hook*. "If it matches AND the command invokes `scripts/deploy-rules.sh` → exit 0." Then `scripts/deploy-rules.sh --status && firebase deploy --only firestore:rules` is allowed. The guard's own command line never contains `firebase deploy`, so it never needs an exception.
Change: delete the exception. Rule is simply: text matches → deny; otherwise exit 0.

**5. SHOULD-FIX — The regex misses forms an ordinary session will actually produce.**
Section: *The hook*, `/(^|[;&|(]\s*|\s)firebase\s+deploy\b/`. Misses: absolute/relative path (`/opt/homebrew/bin/firebase deploy` — three copies of `firebase` are on PATH here; `./node_modules/.bin/firebase deploy`), `npx firebase-tools deploy`, global flags before the subcommand (`firebase --project tinker-hq-apps deploy …`, `firebase -P … deploy`), and — per the plan's own test (f) — `echo "firebase deploy"` doesn't match because `"` isn't in the prefix class. Heredoc / `bash -c` / `eval` / `$(…)` all *do* get caught because the text is in the command string; aliases don't exist in the non-interactive shell. The one that escapes text matching is indirection (a wrapper script or npm script written then run) — see #8.
Change (smallest that covers what matters, BSD-grep safe, no `\b`):
`grep -qE '(^|[^[:alnum:]_.-])firebase(-tools)?[^;&|]*[[:space:]]deploy([[:space:]]|$)'`
— "`firebase`/`firebase-tools` at a token start, then anything up to a separator, then ` deploy`." Accepted false positives: `echo`, `grep`, comments; the deny text should say "if you only meant to read text, use Read/Grep."

**6. SHOULD-FIX — Tag mechanics as written don't work, and the moving tag is the over-engineered part.**
Section: *The guard*, tag block. `git push origin --tags` pushes every local tag (incl. junk) and is *rejected* for a moved tag; bare `--force-with-lease` needs a remote-tracking ref, which tags don't have (→ "stale info"). It only works as `--force-with-lease=refs/tags/live/x:<old-sha>` — and `git fetch` won't move a rewritten tag in any second clone. Also `yyyymmddTHHMMZ` collides on two deploys in one minute (a rollback right after a bad deploy is the likely case) → `git tag` fails *after* a successful deploy.
Change: drop `live/*`. Immutable annotated tags only: `deployed/<project>/<target>/<yyyymmddTHHMMSSZ>`, `-m "sha256=<file hash> file=firestore.rules project=… target=…"` (this also answers the open question about proving the tag honest — no Rules API needed). "Live" = `git tag -l 'deployed/tinker-hq-apps/firestore-rules/*' --sort=-refname | head -1`; `--diff` diffs against that. Push explicit refspecs (`git push origin refs/tags/deployed/…`), never `--tags`, never force. Order: deploy → create local tag → push; a push failure must exit with a *distinct* code and message ("DEPLOYED; tag not pushed; run `git push origin <tag>`") — the local tag is the truth on this one-clone machine.

**7. SHOULD-FIX — "HEAD on origin" should be "sha is an ancestor of origin/main", plus a lock for concurrent guards.**
Section: *The guard* check 3; *Open questions* #1. `git branch -r --contains` accepts any pushed branch (e.g. a `wip/…` preservation branch); a deploy from there means main no longer describes what's live and the next main deploy silently reverts it. Sha-prefix collisions are handled by `rev-parse --verify` (ambiguous → error), so ≥7 chars is fine.
Change: `git fetch origin main` (refuse if it fails — you can't push tags offline anyway) then `git merge-base --is-ancestor "$sha" origin/main`. Hotfix answer for a one-person shop: it's a commit on main; the rules file is one file, so there is no partial deploy to protect anyway. Concurrency: `mkdir "$repo/.git/tinker-deploy.lock"` at start, remove on EXIT, refuse if present (also stops two emulator runs fighting over port 8080).

**8. SHOULD-FIX — Add a CLI-level backstop in `firebase.json` so bypassing the hook doesn't bypass the gate.**
Section: *Why this shape → Not solved here* (Christie's terminal, wrapper scripts). `firebase.json` supports per-target `predeploy` arrays (`"firestore": { "rules": …, "predeploy": ["scripts/predeploy-check.sh"] }`, same for `storage`); a non-zero predeploy aborts before any upload. Have the guard export `TINKER_DEPLOY_SHA=<sha>`; the predeploy script refuses unless that var is set and `git show "$TINKER_DEPLOY_SHA:firestore.rules"` is byte-identical to the file being deployed. That closes `npx`, absolute paths, wrapper scripts, npm scripts, aliases, *and* the terminal in ~10 lines, and gives a human escape hatch (set the var by hand). Caveat, honestly: I could not open the installed firebase-tools source in this session (permission), so confirm the firestore/storage targets run lifecycle hooks — test with a predeploy that `exit 1`s; it aborts before contacting Firebase, so it's a safe live test. (Also check the other ~20 repos for `package.json`/Makefile scripts wrapping `firebase deploy` — I couldn't grep outside the working dirs.)

**9. SHOULD-FIX — Phase 3 rewrites too few documents; the ones it misses actively tell sessions to run the denied command.**
Section: *The words*; Phase 3. Missing from the list: `studio-hub/DEPLOY-SAFETY-CHECKLIST.md` (whole "Scoped deploy commands" table + step list), `studio-hub/CLAUDE.md:30`, `studio-hub/AGENTS.md:8`, `FIREBASE-SETUP.md:33`, the `autoMode` strings (see #3), the `firebase-backend-resilience-plan` memory's phrase line, and whatever the stamped `CLAUDE.md`/`AGENTS.md` in the other repos say about deploying. `RULES-ROLLBACK.md` step 3 as written (`git show … > firestore.rules; npm test; firebase deploy`) will be *denied* by the hook, and its "Tagging before a deploy" section becomes obsolete — delete it. The deny message bridges the gap so this isn't a blocker, but every stale doc is a session that argues with the hook.

**10. SHOULD-FIX — The "committed someone else's edits" case needs a protocol, not just a check.**
Section: *Why this shape → Approve a sha*. `firestore.rules` is one file; two sessions' hunks in it can't be separated by path-scoped commits (`feedback_commit_explicit_paths` doesn't help here). If A commits a+b as X and *summarises* the diff to Christie, b ships approved. The guard can't stop a human approving a diff she didn't read, but the words can shape it.
Change: the guard prints the **full** `--diff` (live→sha, target file), not a stat; CLAUDE.md says the approval request must paste `--diff` output verbatim and "if the diff contains hunks you did not write, stop and say so before asking." Optional, cheap, and worth naming as a v2: the hook receives `transcript_path` on stdin, so it can grep *user* messages for the literal `approved to change firebase <sha>` matching `--approved <sha>` — that makes the phrase mechanical and session-bound (session B cannot ride A's approval). Not needed for the Sep 21 class of incident.

**11. NIT — small inaccuracies and gaps.**
- "Existing sessions need `/hooks` or a restart": docs say settings-file edits to `hooks` are hot-reloaded by the watcher; `/hooks` is read-only. Drop the claim.
- `timeout: 5` — fine, but note a timed-out hook *allows* the call.
- `npm test` for `--target storage` runs the Firestore suite; there are no storage tests. Say so in `--status` output rather than implying storage was tested.
- Seed tag: stamp the real deploy time of `1da12e3`, or put "seeded, console-verified 2026-09-21" in the annotation.
- Make the guard cwd-independent (`cd "$(dirname "$0")/.."`) so `~/studio-hub/scripts/deploy-rules.sh --approved …` works from any repo without the `cd &&` chain the hook can't reason about.
- Lower-case the `--approved` value before comparing.
- Netlify: keep it out. Different shape (per-repo, the gate is a human "yes", no content invariant a script can check). The existing `autoMode.soft_deny` line already covers it.
- Over-engineered: the moving tag + lease (drop, #6), the Rules-API hash fetch (drop, #6's annotation replaces it). Proportionate: the script, the throwaway-repo tests with a fake `firebase`, `--dir`. Under-engineered: #2 and #8.

### Checked and found sound
- The incident diagnosis (per-session/per-command gate vs per-content risk) and the shape: approve a sha, deploy from git, tag after exit 0, user-scope hook because sessions deploy from other cwds — all correct, and #3 confirms the cwd premise empirically.
- Facts vs disk: `firebase.json` names the three files; `.firebaserc` → `tinker-hq-apps`; HEAD `1da12e3` is on `origin/main`, tree clean; exactly one tag `rules-2026-08-12`; no `scripts/`; `~/.claude/settings.json` has no hooks; `package.json` test is `firebase emulators:exec … jest`; tests read `firestore.rules` from cwd (so the worktree approach in #2 works unchanged).
- Hook mechanics: `PreToolUse` + `matcher: "Bash"`, stdin includes `cwd`, `tool_input.command`, `session_id`, `transcript_path`; deny JSON with exit 0 works; subprocesses aren't intercepted, so the guard's inner `firebase deploy` is safe; hooks from user settings apply to subagents and nested `claude` sessions too.
- `firebase deploy --help` as the live proof is harmless and correct.
- Rollback: the dated-tag ladder is strictly better than `git log -- firestore.rules` because it records *deploys*, not commits (several commits deployed at once, or a commit never deployed, both confuse the log). The one hole — an untagged deploy from a terminal — is what #8 closes.
- Not hooking edits (Write/Edit to the rules file) is right; edits aren't the risk, shipping is.
