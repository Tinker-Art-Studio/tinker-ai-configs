## MEDIUM

**M1. The new re-confirm notice can state something false — a failed reversal is not a manager re-confirm.**
v6 adds: *"Saved. Sam was re-confirmed by a manager while you were editing, so Sam stays on this request."* The only mechanism that makes a removed sub reappear is `carryConfirmedSubs` re-appending any sub the fresh read shows confirmed (`schedule-helpers.js:1027–1032`). That set includes **failed reversals**: `reverseConfirmedTimeOffSubs` skips the un-confirm write for a failed index (`app.js:8236`), so the sub is still `confirmed` at the step‑2 read and gets re-appended — and `subs-changed` does *not* catch it (for a removed sub it only fires when the document says confirmed and `openedSubs` said **un**confirmed; here both say confirmed). So the plainly-derivable condition ("re-appended by carry") fires for a stuck reversal, where the truth is already being reported by `failedSubsNote` at `:7460–7471` — the manager would get "…stays marked Confirmed, with the record of what to undo" and then, contradicting it, "was re-confirmed by a manager". One clause: the notice names only re-appended subs **whose reversal landed** (re-appended minus `subsResult.failed`), and it belongs in the wiring-ratchet list, which currently doesn't mention it.
