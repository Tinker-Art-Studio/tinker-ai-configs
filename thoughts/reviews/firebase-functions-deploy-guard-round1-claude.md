## B. Security

4. **A committed symlink inside `functions/<cb>/` ships bytes the approved commit does not contain.** *(blocking, F3 / D2-2)* `packageSource` calls `fsAsync.readdirRecursive` **without** `ignoreSymlinks`, so `filter((n) => !options.ignoreSymlinks || !n.isSymbolicLink())` keeps symlinks; `statSync` then follows them and `archive.file(file.name, …)` archives the *target's* contents under the in-folder name. (The function's own catch text — "Remove links and shortcuts and try again" — is the CLI acknowledging this.) Git stores a symlink as its target *path*, so a tree-id comparison of `functions/<cb>` passes while the uploaded bytes are whatever the target holds at deploy time — including files outside the repo. **Fix:** F3 must refuse any non-regular file (symlink, fifo, socket) under `functions/<cb>/`, in both the guard's walk and the predeploy backstop, with its own BDD scenario.

5. **The diff Christie approves never shows the `firebase.json` functions block, and only `ignore` is pinned.** *(should-fix, F4 / D2-3 step 6)* D2-3 step 6 diffs `-- functions/<cb>` only. `functions/projectConfig.js` `validateSingle` passes every unknown key through (`...rest`), and `prepare.js` honours `configDir` (`proto.convertIfPresent(userEnvOpt, localCfg, "configDir", …)`) to relocate `.env` loading, and `prefix` to rewrite function ids. So a commit could change where env files are read from, or rename every function, without appearing in the approved diff — the control-files check only requires the sha's `firebase.json` to equal the tip's. **Fix:** (a) include the `functions` block of `firebase.json` in `--diff`; (b) have the backstop pin the whole codebase config to an exact allowlist of keys and values (`source`, `codebase`, `runtime`, `ignore`, `predeploy` — nothing else), not just `ignore`; (c) add `"disallowLegacyRuntimeConfig": true` to that pinned set (verified accepted: `projectConfig.js` `shouldUseRuntimeConfig`), so legacy runtime config can never enter the upload or the hash.

6. **The anonymous probe cannot distinguish a platform refusal from the function's own refusal, and F2's stated rationale for the canary is inverted.** *(should-fix, F2 / F8)* F2 says the canary catches "a broken probe … one that reads every reply as 'refused'". It cannot: the canary *is* private, so such a probe passes on it. What the canary actually catches is the opposite bug (a probe that reads every reply as *not* refused), because it returns 204 when reachable. Worse, the pattern does not generalise: `ingestMemberUpdate` is specified (foundation E-2) to answer an unauthenticated caller with 403 *itself*, so a publicly-invokable `ingestMemberUpdate` would pass this probe. **Fix:** correct F2's rationale and name the fake-`curl` "200 → unsafe" case as the real control; pin and assert the *platform* refusal signature (Google front-end 403 body/headers) rather than the status code alone; and require every private HTTP function to be distinguishable when reached.

7. **What the probe misses is understated, and the Console invoker check happens only once.** *(should-fix, "Already decided" / D2-5)* An anonymous request is also refused for `allAuthenticatedUsers` (any Google account), for a stray grant to a specific principal, and for `ingressSettings != ALLOW_ALL` — so a "pass" proves only "not `allUsers`, given ingress is open". The foundation plan's D2 requirement is literally "a post-deploy read-back of each function's revision **and its invoker policy**"; the probe is a narrower substitute. **Fix:** state the substitution as an explicit amendment to the foundation plan's D2 list (and log it there), and make the Console invoker read-back a required, logged step after **every** deploy that creates or updates an HTTP endpoint — not only the first.

8. **`invoker: 'private'` wipes any manually granted `run.invoker` member on every redeploy.** *(should-fix, F2 / A3 / forward to E-2)* On update, `fabricator.js:464-492` calls `run.setInvokerUpdate(project, service, ['private'])`; `proto.getInvokerMembers` returns `[]`, and `gcp/run.js:130-155` then *replaces* the `roles/run.invoker` binding with an empty member list. A3 writes "every HTTP function is `invoker: 'private'`" into CLAUDE.md, and E-2 grants the link's service account `run.invoker` on `ingestMemberUpdate` by hand — that grant will be silently deleted by the next guarded deploy, breaking the link. **Fix:** record this now as a decision, and specify the intended pattern (declare the caller in code — `invoker: ['clayhub-link@…']` — and have the guard's step-4 check accept exactly `private` *or* an explicit allowlist of service accounts, refusing `public`/absent).

9. **Callables and other public-by-default triggers are not refused by the step-4 check.** *(should-fix, D2-3 step 4)* The check refuses "an HTTP function without `invoker: 'private'`". In the build manifest a callable carries `callableTrigger`, not `httpsTrigger` (`discovery/v1alpha1.js`), and `fabricator.js:363` unconditionally does `setInvokerCreate(..., ["public"])` for it — so a callable would pass step 4 and deploy `allUsers`. Task-queue and blocking triggers have their own invoker semantics too. **Fix:** make step 4 an allowlist of trigger kinds (only `httpsTrigger` with an approved invoker, and `scheduleTrigger`), refusing everything else until it has a rule.

10. **F7's ordering is sound; its role set is plausible but one prerequisite is already satisfied and should be stated.** *(nit, F7 / D2-1)* The Phase D plan's log (D-1 step 10) records that the Compute Engine API is **not** enabled and no `…-compute@` account exists, so D2-1 step 1 genuinely creates it and step 2 removes Editor before any build can run — the order is right, and I found nothing in the CLI that re-grants a broad role to it (`deploy/functions/ensure.js` grants only secret access; `checkIam.js` grants nothing for HTTP-only backends). The Console-created cleanup policy also genuinely defuses K8: `functions/artifacts.js` `checkCleanupPolicy` skips a location when `hasOtherPolicies` is true — **any** policy id counts, not just `firebase-functions-cleanup`. Two notes: F7 supersedes C5's "plus Christie's `actAs` on `functions-build@` only" with Owner-wide `actAs`, which should be recorded as the widening it is; and `canary@` with zero roles cannot write logs (no `roles/logging.logWriter`), which is fine for a 204 but will bite D-4.

## C. Gaps against the foundation plan, and partial implementations that would still pass

11. **The functions emulator requirement is dropped without being recorded as a deviation.** *(nit, F10)* Foundation D2 lists "the functions emulator tests run first"; F10 defers it. The reasoning is good — log it as a deviation in the foundation plan's decisions, as C3/C5 were.

12. **No rollback path exists for a functions deploy at all.** *(should-fix, F6 / D2-5)* The rules guard is paired with `RULES-ROLLBACK.md`, referenced from CLAUDE.md. D2 produces no equivalent, and F6 refuses deletion, so a function that turns out to be wrong can be neither reverted nor removed through any sanctioned path. **Fix:** add `FUNCTIONS-ROLLBACK.md` in D2-2 (restore the old `functions/<cb>` tree onto a **new** commit on main, then re-run the guard — the same shape as the rules runbook), say explicitly that deletion has no guarded path yet, and reference it from A3.

13. **A crash or Ctrl-C during the read-back leaves production changed with nothing recorded — contrary to what D2-5 claims.** *(should-fix, F9 / D2-5)* F9 writes the receipt *after* the read-back, and D2-5's "If interrupted" says "the receipt, or the pending-receipt file, says what happened". But in the copied logic `$GIT_DIR/tinker-deploy-pending` is written **only** after a successful `git tag` whose push failed (`deploy-rules.sh:426-430`); a read-back that hangs on `curl` or dies on a missing `jq` leaves neither. **Fix:** write an in-flight marker (`$GIT_DIR/tinker-deploy-inflight`: project, codebase, sha, reserved stamp, "CLI invoked") immediately before the CLI call, remove it when the receipt lands, and have `--status` report it loudly. Add a BDD scenario for "killed between the CLI and the receipt".

14. **Failure paths with no scenario, where a partial implementation still passes every listed test.** *(should-fix, D2-2 / D2-3)* Nothing in the listed assertions exercises: the read-back showing the **Compute** service account, or a wrong/absent `serviceAccount`; an **extra** function in the codebase; a **missing** function; `ingressSettings` not `ALLOW_ALL`; a `functions.yaml` present (there's a `.env` scenario but not this one); `RESOURCE_DIR` not being a codebase `source`; a **missing** vs **extra** entry in the ignore list; a probe that **times out** or 404s. An implementation that checks only `state` and `hash` would pass D2-3's suite as written. **Fix:** one assertion per refusal, as `deploy-rules.test.sh`'s own standing rule requires ("every refusal is a test").

15. **A probe that is inconclusive is labelled `unsafe`.** *(should-fix, F8 / F9)* F8 fails the read-back on "any other reply, including 2xx, 404, 5xx or a timeout", and F9 defines `unsafe` as "a probe wasn't refused" — so a first-deploy URL that hasn't propagated, or a dropped connection, yields `unsafe` and the guard tells Christie to go check the invoker policy. **Fix:** three-way it — 2xx/redirect/any *answered* non-refusal → `unsafe`; DNS failure, timeout, 404, 5xx → `partial` ("inconclusive"), after bounded retries (e.g. 5 × 10 s).

16. **`--status` has no defined answer when the only receipt is partial or unsafe.** *(should-fix, F9)* "The newest *complete* receipt is what shipped" plus "name any newer partial or unsafe one above it" leaves the first-deploy-was-partial case saying "no guarded deploy yet" while a function is actually running. **Fix:** specify that with no complete receipt but a partial/unsafe one present, `--status` says "no complete receipt; production may have changed at `<receipt>`" and `--diff` explains why it shows the whole folder.

17. **`functions:deletegcfartifacts` is missing from F12's deny list.** *(should-fix, F12 / A1)* `commands/` contains `functions-deletegcfartifacts.js` alongside the eight commands A1 names; it deletes container images in production. (The read-only ones — `functions:secrets:get|access|describe`, `functions:config:get|export`, `functions:list|log` — are correctly left out.) **Fix:** add it to A1 and A2.

## D. Receipt design vs the rules guard's ordering logic

18. **`outcome=` is a decision input but would be read by a deliberately fail-soft path.** *(should-fix, F9 / D2-3 step 1)* `receipt_rows` is built from `git for-each-ref '%(objecttype) %(creatordate:unix) %(refname:lstrip=2)'` — no message — so "newest *complete*" needs a second read of each tag's contents. The only existing message reader, `receipt_by`/`receipt_note`, is documented as failing **soft** ("Missing evidence must never block a deploy that is otherwise fine"). If the functions guard reuses that shape, a complete receipt whose annotation can't be read silently becomes not-complete, and the guard diffs from an older base — exactly the class of bug the big `receipt_rows` comment exists to prevent. **Fix:** read `outcome=` through a fail-**closed** helper (`|| return 1` + `die $EX_RECORD`), mirroring `latest_receipt`/`newest_stamp`, and state that in the plan.

19. **Say explicitly that the stamp reservation still orders against *all* receipts.** *(nit, F9 / D2-3 step 1)* Step 7b's monotonicity depends on `newest_stamp()` covering every receipt under the prefix. Now that partial and unsafe receipts exist, if "newest" were narrowed to complete ones a later complete receipt could be stamped below an existing partial and sort under it. It is also worth stating that `$GIT_DIR/tinker-deploy-pending` is shared with the rules guard (safe under the shared lock — either guard's reconcile publishes whatever tag it names — but it is shared state a reader should see), and that the new slug `functions-<codebase>` sits inside `TAG_ROOT`, so `fetch_state` already brings it and `receipt_rows`' prefix filter keeps the namespaces apart. Both are true of the copied code; neither is written down.

20. **The diff base after a partial is a deliberate superset — say so.** *(nit, D2-3 step 6)* `git diff <last complete> <sha>` will re-show changes a partial deploy may already have applied. That's the right choice; the plan should state it so nobody "fixes" it later.

## E. Things that will not work as described

21. **`npm ci` at the root *and* symlinking the root `node_modules` are mutually exclusive.** *(blocking, D2-3 step 3)* Step 3 says both. `deploy-rules.sh:324` does `ln -s "$REPO/node_modules" "$TMP/node_modules"`; `npm ci` begins by removing `node_modules`. Depending on how the removal treats the symlink you get either a wasted multi-minute network install inside the lock, or — the reading that matters — destruction of the shared working tree's `node_modules`, which every other session depends on. **Fix:** pick one. Keep the symlink and run `npm ci` **only** in `functions/<cb>/` (F5's actual intent), and keep `deploy-rules.sh`'s CONTROL_FILES comment about the symlink limitation applying unchanged.

22. **Nothing asserts that `functions/<cb>/node_modules` was actually populated, and the CLI silently falls back to the shared tree.** *(should-fix, F5 / D2-3 step 3)* `runtimes/node/index.js:98-118` `findFunctionsBinary` tries `<sourceDir>/node_modules/.bin/firebase-functions`, then **`<projectDir>/node_modules/.bin/…`** — i.e. the symlinked shared tree — then the SDK path. So if the codebase `npm ci` fails or is skipped, discovery runs the shared tree's SDK with no error, defeating F5's whole reason for existing. **Fix:** after `npm ci`, refuse unless `functions/<cb>/node_modules/.bin/firebase-functions` exists; add it as a refusal with its own test.

23. **The real-CLI test does reach the network, and as described it can pass without proving anything.** *(should-fix, D2-2)* "Nothing reaches the network, because predeploy runs before prepare" is wrong: `commands/deploy.js` runs `.before` hooks first — `requirePermissions` → `requireAuth` (a real token exchange via `google-auth-library`) → `testIamPermissions`, then `checkIam.checkServiceAccountIam(project)`. Those *fail soft* for `demo-my-clay-hub` (both swallow errors), so the predeploy hook is reached — but only with a working login and network, and `npm test` now makes authenticated Google API calls as Christie (and lets the CLI refresh the cached credential). Crucially, if `requireAuth` throws, the CLI exits non-zero *before* the hook, and a test asserting only "exit != 0" passes while proving nothing. **Fix:** assert on the backstop's own `REFUSED: this deploy targets project 'demo-my-clay-hub'` line, and skip loudly (not silently) when unauthenticated or offline. State the credential/network dependency in the plan.

24. **The discovery preview works, with caveats the plan should absorb.** *(nit, D2-3 step 4 / O1)* `commands/internaltesting-functions-discover.js` exists in 15.22.3 and prints `JSON.stringify(wantBuilds)` keyed by codebase — so O1 resolves to "usable". But it calls `needProjectId` and `getProjectAdminSdkConfigOrCached(projectId)`, so it needs `--project my-clay-hub` and the network; it accepts no `--only`, so it runs **every** codebase's user code; and the fields it emits are the *Build* shape, where `region` is a list, `httpsTrigger.invoker` is an array, and the service account may arrive as either `serviceAccount` or `serviceAccountEmail` (`discovery/v1alpha1.js:61-70, 137-150, 297-306`). The same field caveat applies to D2-2's `__endpoint` assertions. Also worth pinning: `FUNCTIONS_DISCOVERY_TIMEOUT` and `FIREBASE_FUNCTIONS_DISCOVERY_OUTPUT_PATH` are read from the guard's own environment and change how discovery runs, and `GOOGLE_APPLICATION_CREDENTIALS` / `GOOGLE_CLOUD_QUOTA_PROJECT` change who deploys — the guard should invoke the CLI with those explicitly unset.

25. **`npm test` cannot run `test:functions` as described, and the new guard's own suite is never wired in.** *(should-fix, F10 / D2-2)* `tests/canary.test.js` needs `firebase-functions` resolvable, i.e. `functions/core/node_modules` — nothing installs it for an ordinary `npm test` (no workspaces, no postinstall). And `package.json:7` (`test` = `test:unit && test:guard && test:rules`) is only extended with `test:functions`; `scripts/deploy-functions.test.sh` is never added, so the new guard's suite would not run in the pre-deploy gate even though D2-3 lists it among the control files. **Fix:** declare `functions/*` as npm workspaces (or add an explicit install step) and make `test` = `test:unit && test:guard && test:functions-guard && test:functions && test:rules`.

26. **The "410 existing tests unchanged" criterion is wrong on both halves.** *(should-fix, D2-2)* The Phase D log records the current count as 94 unit + 178 guard + 194 rules = **466** at `6a0233b` (HEAD). And `tests/unit/firebase-config.test.js:17` asserts `Object.keys(cfg).sort() === ['emulators','firestore','storage']` with the comment "a new target needs its own predeploy" — adding a `functions` key **must** turn it red, and its new form has to handle the array shape (`cfg.functions` is a list; every element needs its own `predeploy`). This is also the D-2 forward note in the Phase D log. Global CLAUDE.md additionally says not to hardcode a count. **Fix:** drop the number; require instead "`npm test` green, and `firebase-config.test.js` updated in the same commit to assert a `predeploy` on every element of `functions`".

27. **Scheduled and other non-`httpsTrigger` endpoints have a `uri` and should be probed too.** *(should-fix, F8 — matters for D-4, the next plan)* `gcp/cloudfunctionsv2.js:441` sets `endpoint.uri` from `gcfFunction.url` for every gen-2 function, and `fabricator.js:383-388` gives a scheduled function its **own service account** as the invoker — so it is reachable and must refuse a stranger. F8 scopes the probe to "every HTTP function". **Fix:** probe every read-back endpoint that has a `uri`, and record the expected invoker shape per trigger kind.

28. **Small preflight gaps.** *(nit, D2-3)* `deploy-rules.sh:266` preflights `git npm firebase shasum`; the functions guard additionally needs `curl` and `jq` (the rules guard calls `/usr/bin/jq` by absolute path — do the same, and add `curl` to the tool loop). `functions/core/package.json` declaring `engines.node: "22"` on a Node 20.20.2 laptop makes `npm ci` emit `EBADENGINE` (and would hard-fail under `engine-strict`); worth a line in O4.

**Two things I want to be explicit about, because they are the strongest parts:** the choice to force `--only functions:<codebase>` is exactly right and verified (K4/K5 both hold, and `getReleventConfigs` really does fan every codebase's predeploy out on an unmatched name), and pre-creating `gcf-artifacts` with any Console cleanup policy really does defuse the K8 exit-1 trap (`hasOtherPolicies`). Neither needed a change.

Verdict: **not ready**
