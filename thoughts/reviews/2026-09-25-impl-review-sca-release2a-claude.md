# Findings

**1. MEDIUM — `e2e/roles-startup.spec.js` runs all five roles as admin; the rules risk it exists to close is untested.**
`login(page, role)` ignores its `role` argument whenever the saved session is in effect. `playwright.config.js:31` sets `use.storageState: 'e2e/.auth/state.json'` — the **admin** session — so `page.goto('/')` resolves `headerPopulated` and `login()` returns at `e2e/helpers/login.js:110` before `credsFor(role)` is ever reached. All five tests at `e2e/roles-startup.spec.js:8-17` therefore sign in as `e2e-admin`, and the claim in the commit message ("admin, manager, prep, staff and team-only accounts sign in … the season loads") is not what runs.
*Failure scenario:* if the `list` on `summerCamps_seasons` were denied for, say, a `team`-only account, this suite would still be green and every team-only user would hit the full-screen red banner on deploy. I checked the rule by hand instead — `firestore.rules:764-770` grants `read` (which is `get` **and** `list`) under a condition that never references `resource`, so the list is permitted for `isManagerOrAbove()`, `summer-camp`, `team`, `classbook`, `classbook-admin`, `curriculum-admin`. The risk is genuinely absent; the assurance is false.
*Fix:* add `test.use({ storageState: { cookies: [], origins: [] } })` to the role loop's describe block so the guard appears and `login()` falls through to the role's credentials — or call `signInViaForm(page, role)` directly.

**2. MEDIUM — when the current season moves under an open tab, two banners appear and one is self-contradictory.**
`showSeasonMovedBanner()` (`js/app.js:4977`) opens with `applySeasonViewState()`, which ends by calling `renderSeasonViewBanner()`. At that moment `viewing === current === '2026'` and only `currentMoved` is true, so the guard at `js/app.js:4962` (`if (Season.isViewingCurrent()) return;`) does not fire and the tab renders *"Viewing **Summer 2026** — read-only. Edits go to Summer 2026, the current season"* with a "Go to Summer 2026" button, directly beneath the red *"Summer 2027 is now the current season"* banner. `e2e/season-read-only.spec.js:162` only asserts the moved banner's text, so it passes.
*Fix:* widen the guard to `if (Season.isViewingCurrent() || Season.viewing() === Season.current()) return;` at `js/app.js:4962`, leaving the moved banner to speak alone.
Not reachable in production today (one season), but it is on the path Phase 2.5 opens.

**3. MEDIUM — a past-season view can permanently delete a Kid Note or a Note for Next Year.**
`Season.writeRef()` returns early for `ALL_SEASONS_KEYS` **before** the read-only gate (`js/season.js:408`), so `handleDeleteKidNote` (`js/app.js:7026`) and `handleDeleteNote` (`js/app.js:6629`) are ungated from any view. Neither `#kid-note-modal-delete-btn` nor the note delete control is in `PAST_SEASON_HIDE`, and the read-only sweep (`e2e/season-read-only.spec.js:125-135`) checks only that the *add* and *import* buttons are hidden — it never opens a note modal.
*Failure scenario:* 2027 is current, a teacher opens a 2026 tab through the switcher under the "read-only" banner, opens a kid note and clicks Delete. The note is gone, irreversibly, from a view the app told them was read-only.
*Fix:* call `Season.assertCanCreate()` at the top of both delete handlers (the existing guard already means "this tab may change the current season's world"), **and** add `#kid-note-modal-delete-btn` plus the Notes-for-Next-Year delete selector to `PAST_SEASON_HIDE`; extend the sweep to open one note modal per tab.

**4. MEDIUM — in a brand-new season the first Open Studio off-site save fails.**
`saveOffSiteOSInline` (`js/app.js:13490`) and `seedCoalCreekToAllWeeks` (`js/app.js:13545`) `update()` the `week_N` document; every other Open Studio write uses `set(..., { merge: true })` (13647, 13777, 13802, 13886). The week document does not exist until the main grid has been saved once, so `update()` fails with NOT_FOUND. Pre-existing — 4ba983d has the same two `update()` calls — and harmless for 2026 where all eleven documents exist, but 2.3 explicitly makes empty summers work and `e2e/season-empty.spec.js` only asserts that tabs render, never that a save lands.
*Fix:* convert both to `set(Season.stamp({ offSiteOS: { sensoryBinFromTinker, activitiesAM, activitiesPM }, updatedAt, updatedBy }), { merge: true })` — nested objects, not the dotted paths, since `set()` treats a dotted key as a literal field name. Add a save to the empty-season spec.

**5. LOW — `_pdDeleteMarkedPhotos()` deletes Storage objects before the gated Firestore write.**
`js/app.js:12439` removes marked photos from Storage; the gated `Season.writeRef('summerCampsProjectDetails')` update follows at 12455. Storage is outside Season's gate entirely (`firebase.storage().ref(path).delete()`, `js/app.js:12258`) and the photo-remove buttons are in neither `PAST_SEASON_HIDE` nor `PAST_SEASON_LOCK`. **Currently unreachable** — `[onclick^="editProjectDetail"]` is hidden and `#project-detail-form input` is disabled in a past view, so the modal can neither be opened nor submitted — so this is a missing second line of defence rather than a live bug. Separately, `_pdStoragePath` (`js/app.js:12198`) is `projectDetailPhotos/<camp>/<project>/…` with no season segment, so two summers' identically-named camps share a folder.
*Fix:* `Season.assertCanCreate()` as the first statement of the form's submit handler (`js/app.js:12417`), before any upload or delete; decide on a season segment in the path before Phase 3's carry-forward copies `photos` arrays.

**6. LOW — the completeness checker cannot see a whole-collection read through `Season.readRef()`.**
`readRef()` returns an unfiltered `CollectionReference` (`js/season.js:385-388`). All eight current call sites correctly do `.doc(id).get()` — I checked each (`js/app.js:10600, 10663, 10954, 11102, 12160, 12174, 12304, 13081`) — but `Season.readRef(key).get()` or `.where(...)` would read every season and no rule catches it, unlike the audited `{ seasons: 'all' }` allow-list.
*Fix:* in `test/season-completeness.test.js`, flag `get`/`where`/`orderBy`/`onSnapshot` called directly on a `Season.readRef()` result — only `.doc()` may follow it.

**7. LOW — dead and misleading read-only scaffolding.**
`css/styles.css:6286` still carries `body.season-read-only [data-requires-writable] { display: none !important; }` and the comment at `js/app.js:4849` says the body class "hides every `[data-requires-writable]` control", but nothing in the repo has that attribute — the mechanism is the injected `PAST_SEASON_HIDE` stylesheet. `canEdit()` (`js/app.js:4854`) is defined and never called. `Season.writeRef()`'s shared-key error (`js/season.js:410-411`) claims "its writers use `db.collection()` and check `Season.isViewingCurrent()` themselves" — none of the six shared-collection writers does, by design (Stock Totals and Team stay editable in every view).
*Fix:* delete the dead CSS rule and `canEdit()`; correct both comments to describe the list-based mechanism and the deliberate ungating of shared collections.

**8. LOW — the read-only MutationObserver rescans a parent's whole subtree per added node.**
`js/app.js:4924` calls `lockPastSeasonFields(n.parentNode || n)`, which runs 30 `querySelectorAll` calls over the *parent* for every added element; a render that appends N rows one at a time is O(N²·30). Past-season views only — I confirmed `applySeasonViewState()` with `readOnly === false` creates no stylesheet, installs no observer, and does nothing but clear the already-empty switcher host, so production cost is zero.
*Fix:* lock `n` and its own subtree (plus `n.matches(sel)` for `n` itself), or coalesce to one document-wide pass per animation frame.

**9. LOW — `npm run deploy` no longer runs any test.** It was `npm run test:e2e && netlify deploy --prod`; `scripts/deploy.sh` now checks clean/pushed, builds and deploys. Pre-push normally covers it, but a commit pushed with `--no-verify`, from another machine, or before `npm run prepare` installed the hook deploys untested.
*Fix:* run the three emulator-free static checks inside `scripts/deploy.sh` before the build — they take about a second.

# What I checked and found correct

**1 — single season, nothing hidden, every save path works.** With `viewing === current === '2026'` and `currentMoved` false, `writeRef` computes `target = opts.season || st.viewing = '2026' === st.current` and returns the collection (`js/season.js:405-416`); no call site passes `opts.season` (the checker's `other-season-write` allow-list is empty and clean). Legacy mode behaves identically. `applySeasonViewState()` with `readOnly === false` creates no stylesheet, no observer, no banner, and `renderSeasonSwitcher()` returns on `seasons.length < 2` leaving `#season-switcher-host` empty — `.season-switcher-host:empty { display: none }` wins on specificity, so there is no layout shift. IDs are byte-identical: `docId(x, '2026')` returns `String(x)` unchanged, so Open Studio's `week_N`, weekly prep's `{camp}_weekN` and lessonData's `encodeLessonKey(...)` all produce exactly what 4ba983d wrote.

**2 — `js/season.js`.** Read scope is `viewing()` (`query`, `readRef`, `readDocId`), write target is `current()` (`writeRef`, `writeDocId`, `stamp`). `load()`'s single forced-server list is permitted by `firestore.rules:764-770` for every role the app admits (admin/manager via `isManagerOrAbove()`, plus `summer-camp`, `team`, `classbook`, `classbook-admin`, `curriculum-admin`) — `read` covers `list`, and the condition never touches `resource`, so the query is not document-dependent. `watchCurrent()` is benign in production: `_current.season === '2026' === state.current`, so the first snapshot sets nothing, and in legacy mode a missing `_current` yields `effective = '2026'`, also a no-op. On `validateSeasonDoc`: the only writer of the 2026 registry document is `ensureSeasonDoc()`, which sets `Object.assign({}, buildSeedFromConfig(APP_CONFIG), { createdAt, createdBy, updatedAt, updatedBy })`, and `buildSeedFromConfig` has carried all twelve fields — `week1Monday`, `breaks`, `timeSlots`, `studios`, `studioCapacities` included — since the first season commit (`5bd80b9`), unchanged through this diff. `config.js`'s values satisfy every check: `numWeeks: 11` with `weekStructure` 1…11 (numeric literal keys become the strings `'1'`…`'11'` through Firestore, which `ws[w] || ws[String(w)]` handles), six studios each with a capacity, unique `AM`/`PM` slot keys, `week1Monday: '2026-05-25'` (a Monday), `breaks: [{ afterWeek: 5 }]`. `test/season.emulator.test.js:507` asserts the real shape loads, and :570 asserts the seed's key set equals the registry fixture's. The residual exposure is a hand edit in the Firebase console — worth one glance at `summerCamps_seasons/2026` before deploying, since a malformed doc now locks out every user with a red banner where 4ba983d would have carried on.

**3 — the 58 conversions.** No read goes through `writeRef`: the only `.get()` within four lines of a `writeRef` is `detailsQuery`'s (`js/app.js:12014`), a `Season.query`, and none of the six `writeRef`-to-variable bindings (511, 7919, 10357, 12011, 12582, 13545) is ever read from. All eight `readRef` sites are `.doc(id).get()`. No write bypasses the gate: the only raw `db.collection(...)` calls in app.js are `users`, `backupStatus`, the shared `summerCamps_team`/`summerCamps_stockItems`, and the data-safety panel's read-only count loop; there are no `runTransaction`, `onSnapshot`, `collectionGroup`, or snapshot-`doc.ref` writes left (`grep '\.ref\b'` finds only the three Storage lines). All seven snapshot rewrites target the collection they were read from — I traced each: materials→materials (9761, 9787, 10294), projectDetails→projectDetails (11628), curriculum→curriculum (10054, 10415, 11640). Storage is the one write path outside the gate (finding 5).

**4 — the CSV import.** `planImport` is pure and matches within the current season only; an update carries only mapped, non-empty, actually-different columns, so a sparse sheet can no longer blank `parentPhone`/`strategies` — the exact regression this fixes. `week` and `campTopic` are match-key fields and are never patched, which is equivalent to the old code writing them back unchanged. Preview equals write: `renderCSVImportPreview` and `executeImport` consume the same `csvImportPlan` object. Retry is idempotent — it re-plans from the server (`js/app.js:7319`, forced `{ source: 'server' }`), so a landed create now matches by name+camp+week and becomes a no-op; create ids come from `.doc().id`, so a merge-less `set` can never overwrite an existing note. The manifest, including a `before` copy of every note it will update, downloads before the first write. `assertCanCreate()` runs once up front and again via `beforeBatch` before every batch, inside the try, so a refusal is reported rather than swallowed. One narrow race remains: a note edited between Review and Import is overwritten by the plan's stale value; the old row-by-row import was strictly worse.

**5 — the sign-in sweep cannot stamp differently today.** `autoSweepStragglers()` already runs in production at 4ba983d; the diff adds only `setSeasonNeedsChoice` and a toast.
