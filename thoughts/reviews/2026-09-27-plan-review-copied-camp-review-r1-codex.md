The core derivation is sound: carry-forward stamps provenance on every copied curriculum doc, fresh-camp creation does not, and existing curriculum edits are partial updates. I found no high-severity data-integrity problem, but the plan still has several implementation gaps.

1. **MED — Successful review writes can leave the card and header count stale.**  
   `loadCurriculum()` stores independent objects in `window.CURRICULUM_CAMPS` and renders from that array ([js/app.js:155](/Users/christiehubley/summer-camp-app/js/app.js:155)). Closing or cancelling the editor only hides the modal; it does not reload or redraw curriculum ([js/app.js:9001](/Users/christiehubley/summer-camp-app/js/app.js:9001)). Therefore updating only Firestore and the editor band will not satisfy “on closing, the card and count update.”  
   **Fix:** after mark/undo succeeds, update the matching cached object and rerender the grid/header, or await `loadCurriculum()` before allowing the modal to close. Disable the review control while its write is pending so rapid Mark/Undo clicks cannot resolve out of order. Extend the BDD assertion to check the header count immediately after both Mark and Undo, without a page reload.

2. **MED — Current-season staff and prep access is not covered by role tests.**  
   Curriculum is a generally visible tab ([index.html:49](/Users/christiehubley/summer-camp-app/index.html:49)); only elements explicitly marked `.admin-manager-only` are hidden from staff/prep ([js/auth.js:181](/Users/christiehubley/summer-camp-app/js/auth.js:181)). Firestore permits those users to read curriculum but only managers/admins to update it ([firestore.rules:827](/Users/christiehubley/studio-hub/firestore.rules:827)). The proposed scenarios cover a manager and a past-season view, but not staff/prep viewing the current season.  
   **Fix:** introduce a single predicate such as `canReviewCamp() = manager/admin && Season.isViewingCurrent()`, use it both when rendering and inside the handler, and add emulator E2E cases for current-season `staff` and `prep`: the band/badge remains visible, Mark/Undo is absent, and a direct handler invocation performs no write.

3. **MED — Lesson Plans’ promised fail-open behavior is not in the stated test set.**  
   Today all Lesson Plans reads are in one `Promise.all`, and any rejected read fails the entire tab ([js/app.js:2827](/Users/christiehubley/summer-camp-app/js/app.js:2827), [js/app.js:2865](/Users/christiehubley/summer-camp-app/js/app.js:2865)). Merely adding curriculum to that array would contradict the plan’s “still loads without badges” requirement. Although the BDD describes the failure, the Phase 2 test list only says badge visible before review and gone after ([plan:97](/Users/christiehubley/tinker-ai-configs/thoughts/plans/summer-camp-copied-camp-review.html:97)).  
   **Fix:** fetch curriculum in a separately caught promise or use an explicit settled result, defaulting the review lookup to empty. Add a Playwright fault-injection case that rejects only the emulator `runQuery` for `summerCamps_curriculum` and verifies the normal Lesson Plans cards still render. This uses the emulator for data rather than mock Firestore.

4. **MED — The header wording is wrong when a season contains copies from multiple source summers.**  
   The copy dialog allows selecting any earlier registered season, not only the immediately preceding one ([js/app.js:12987](/Users/christiehubley/summer-camp-app/js/app.js:12987), [js/app.js:13041](/Users/christiehubley/summer-camp-app/js/app.js:13041)). Thus Summer 2028 can contain copies from both 2026 and 2027. The proposed single line “N camps copied from Summer X” ([plan:68](/Users/christiehubley/tinker-ai-configs/thoughts/plans/summer-camp-copied-camp-review.html:68)) cannot represent that state, so the claim that the feature works unchanged for 2028 is incomplete.  
   **Fix:** either use source-neutral text—“N copied camps · M not yet reviewed”—or group counts by `carriedForwardFrom.season`. Add a mixed-source scenario.

5. **LOW — A renamed Lesson Plans topic does inherit `carriedForwardFrom`, even though the new topic document was created by the rename.**  
   On rename, `CampAdmin.saveCamp()` copies every field from the old topic except `season` into the new topic document ([js/camp-admin.js:206](/Users/christiehubley/summer-camp-app/js/camp-admin.js:206), [js/camp-admin.js:215](/Users/christiehubley/summer-camp-app/js/camp-admin.js:215)). Consequently, provenance on arbitrary collection documents cannot universally mean “this exact document was created by carry-forward.” This does not invalidate the proposed rule because it is based solely on curriculum documents, but it is an important constraint.  
   **Fix:** explicitly document and enforce that `campReviewState()` accepts only curriculum data. Lesson Plans must derive status from its new curriculum query, never from the topic’s own `carriedForwardFrom`.

6. **LOW — The rename/duplicate-name BDD is too weak for the actual joins.**  
   Curriculum and the Lesson Plans topic are renamed together transactionally ([js/camp-admin.js:200](/Users/christiehubley/summer-camp-app/js/camp-admin.js:200)), so the badge can follow a legitimate rename. But materials and project-details records intentionally keep the old camp name ([js/camp-admin.js:344](/Users/christiehubley/summer-camp-app/js/camp-admin.js:344)). Project Details also collapses records into name-based maps/groups ([js/app.js:12571](/Users/christiehubley/summer-camp-app/js/app.js:12571), [js/app.js:12619](/Users/christiehubley/summer-camp-app/js/app.js:12619)). Coal Creek twins remain distinguishable because their exact names differ by a prefix ([js/app.js:4](/Users/christiehubley/summer-camp-app/js/app.js:4)).  
   **Fix:** in Materials and Project Details, attach the badge directly from the curriculum object already being rendered, preferably by curriculum document ID—not by looking up child records. In Lesson Plans, use an exact-name curriculum map and detect/log duplicates instead of silently taking one. Add tests for a Coal Creek pair, a renamed copied camp whose child records retain the old name, and malformed duplicate curriculum names.
