Midnight crossing, traced:
- Into Sunday, retry keyed Sunday at ~00:10. If its export completes, the 09:00 run says "already done" (a real Sunday snapshot, about 9 h earlier than usual; the next week's copy is then about 7 d 9 h newer, inside 7 d 18 h). If it's still running at 09:00, the real run resumes it. If it failed or was cancelled, it's history and the real run exports. The Saturday-keyed export lands in its own folder. Freshness reads `timeCreated` (freshness.js:20), so neither folder's date name affects it.
- Into a weekday: two exports, two prefixes. If Google refuses a second concurrent export, the retry fails (failure email), and a later retry starts it once the first export is done. No data loss either way.
- Scheduler clock skew: a slightly early real delivery (t > now by seconds) keys by now, which is the same UTC date. Only a skew of about 9 h would change it. No tolerance needed. DST plays no part in the code (schedule and keys are UTC).
- Caps: an extra copy adds one folder; 50 per date and 500 overall (56-day lifecycle, about 8 weekly copies) leave a large margin.
- Force run on Sunday before 09:00: keyed Sunday, and the 09:00 run says "already done" or resumes. That's fine, and the copy is genuinely Sunday's. Force run on Sunday after 09:00: header = next Sunday, keyed today = the same key as the real run's series, so it finds "already done" or resumes, with no duplicate. Both are correct.

1. should-fix — functions/vault/export-run.js:54, FUNCTIONS-ROLLBACK.md:215-217. **A Force run whose header is in the PAST (not the future) is still keyed by the header's date.** The fix only covers `t > now`. The header is the job's stored next `scheduleTime`. On a job paused by §10's own "To stop exports at once" step, that value may never be advanced, so a Force run made while the job is still paused could arrive with a scheduleTime days or weeks old. That is unverified: I haven't seen what Scheduler sends for a paused job, and it may refuse to run one. In that case the run takes an old date's key. If that date still has a complete folder, it logs "already done" and makes no copy, so the catch-up silently fails, though the freshness alert keeps firing. If the folder has aged out, it makes a copy under a misleading old date (DATA-RESTORE.md §1 would then mis-date it). A real run and all its retries arrive within about 3 h of their scheduled time. Two cheap fixes, either is enough: (a) code: key by now when `t > now` OR `now - t` exceeds a generous window such as 12 h, plus one test; or (b) runbook: "Resume a paused job before a Force run. After any Force run, check that the log's first line shows `key` = today's UTC date." I'd add the log-line check to the runbook in any case. It's the one direct confirmation that a Force run did what was meant.
