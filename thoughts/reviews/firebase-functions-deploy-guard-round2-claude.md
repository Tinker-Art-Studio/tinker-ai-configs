## Findings

**1. Blocking — F2 / F5 / F10: npm workspaces + `npm ci` inside `functions/<cb>/` + the symlinked root `node_modules` either destroys the shared tree's `node_modules` mid-deploy, or refuses every deploy.** Round-1 Codex #10 / Claude #21 are *not* resolved; moving `npm ci` into the codebase reintroduces the same catastrophe through a new door.

Evidence: npm's config walks up from cwd and, when cwd is a workspace of an ancestor, sets `localPrefix` to the **workspace root** and `workspace=[cwd]` (`/usr/local/lib/node_modules/npm/node_modules/@npmcli/config/lib/index.js:717-743`). `npm ci` then removes `node_modules` **entry by entry** after `fs.readdir` — which follows a symlink — for the root *and every workspace* (`/usr/local/lib/node_modules/npm/lib/commands/ci.js:88-97`; `lib/utils/get-workspaces.js:16-22`: an empty filter returns root + all workspaces). With `ln -s "$REPO/node_modules" "$TMP/node_modules"` (`scripts/deploy-rules.sh:324`, which F5 keeps), the deletion lands inside `/Users/christiehubley/my-clay-hub/node_modules` — the shared install every session, both guards and the pinned CLI depend on. Two branches, both fatal:
- root lockfile regenerated to cover the workspaces (the "correct" setup): validation passes (`ci.js:49-77`), then the rm wipes the shared tree, and because `--workspace` excludes the root's own deps the tree is left holding *only* the codebase's dependencies — no `firebase-tools`, no `firebase`, no `@firebase/rules-unit-testing`;
- per-codebase lockfile kept instead (F2 says each codebase commits one): npm uses the **root** lockfile, `validateLockfile` throws, and no functions deploy ever runs. npm maintains one lockfile at the workspace root, so F2's per-codebase lockfile (which GCF's own build needs) and workspaces are contradictory, and D2-3 step 3 would pin a lockfile that never installs anything.

Also: workspaces hoist, so `functions/<cb>/node_modules/.bin/firebase-functions` won't exist after a root install → F5's check refuses; and the hoisted copy at the root makes K2's `projectDir` fallback a live path rather than a theoretical one.

Fix: drop workspaces. Each codebase keeps its own `package.json` + `package-lock.json`; the guard runs `npm ci --prefix "$TMP/functions/<cb>"` — a CLI `prefix` short-circuits the walk-up (`@npmcli/config/lib/index.js:686-690`) — or `npm ci --workspaces=false` with cwd in the codebase. Give root `npm test` an explicit install step (`npm --prefix functions/<cb> ci`, or `test:functions` skips **loudly** with a named reason when the deps are absent). Add a test asserting the exact argv the guard passes *and* one real-`npm ci` fixture proving a symlinked root `node_modules` is untouched — the current fake-`npm` harness cannot see this class of bug.

**2. Blocking — F8 step 1: the "expected hash" recipe is wrong (the env is not empty), so `verified=yes` is unreachable on a real deploy while every fake-CLI test passes.** `prepare.js:110` sets `wantBackend.environmentVariables = {...userEnvs, ...firebaseEnvs}`; `functions/env.js:247-252` returns `{FIREBASE_CONFIG: JSON.stringify(adminSdkConfig), GCLOUD_PROJECT: projectId}`; `applyHash.js:9` hashes exactly that. So the label is `sha1(sourceHash + sha1('{"FIREBASE_CONFIG":…,"GCLOUD_PROJECT":"my-clay-hub"}') + sha1("{}"))`, and the `FIREBASE_CONFIG` value is a **live** API body (`functionsConfig.js:102-106`, `/v1beta1/projects/…/adminSdkConfig`) whose key order is the server's. A guard computing "empty env" mismatches every time → `deploy_match=no` → `verified=no` forever, and D2-5's acceptance criterion can never be met. This is precisely the failure shape the plan is built to avoid: the fixtures agree with the guard, production doesn't.

Fix (recommended): stop making hash equality the evidence — the bytes are already pinned by F3 + the backstop + the tree id. Instead (a) take a **pre-deploy** `functions:list` snapshot and require `hash_after != hash_before` exactly when the tree id changed (and equality when it didn't), (b) require the CLI output to *not* contain `Skipping the deploy of unchanged functions.` (`planner.js:41`), and (c) keep F8's field-by-field config match as the real check. If you keep the recomputation, spell it out: sourceHash = `sha1` of the C-locale-sorted per-file `sha1`s joined, envHash over the two variables above with `FIREBASE_CONFIG` taken verbatim from the pinned CLI's own fetch, `secretsHash = sha1("{}")` — and make one D2-5 step show expected and live agreeing on a real deploy *before* the check is allowed to gate `verified`.

**3.
