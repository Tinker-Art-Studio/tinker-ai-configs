### The five round-5 fixes — all present, three checked through the code

- **`lastEditId` ownership.** Plan § 2B now reads: generated by `saveDayOffPlan()` itself, *after* allow-list
  validation, applied last with the identity stamp, overriding anything a caller sent; not caller-writable
  (a caller-supplied value throws like any field outside the allow-list) and not clearable; passed as
  `verifyDayOffPlanWrite(ref, editId, written, cleared)`. This resolves Codex M-1 by the other route it
  offered — `lastEditId` stays *out* of the caller allow-list and is stamped like identity, so the
  enumeration at the allow-list bullet is still literally exhaustive for caller payloads. Internally
  consistent; no SDOC caller sends it (`{ planComplete }`, `app.js:2119`; the editor builds from form fields).
- **Model field list.** Plan row 58 now names `lastEditId`, "a per-save id written only by `saveDayOffPlan()`".
- **No-op BDD.** Now "the editor shows its usual '✓ Saved'; no write (spy), no read-back, no 'edited
  since'/rename message, no reload scheduled" — matches the shared, unconditional success block
  (`app.js:11643-11651`). See L-1.
- **`getRandomValues` fallback.** Cites `newDayOffItemId()` at `firebase-data.js:1911-1917` — exact, and that
  function is the guarded pattern (`typeof crypto !== 'undefined' && crypto.getRandomValues`, `Math.random`
  fallback). `crypto.randomUUID()` is gone from the plan.
- **Own-name wording.** "saved again just after — from another window or the Plan complete box" now covers the
  same-window autosave/checkbox interleave that motivated the id.

### The L-3 rejection is correct — code checked

`firebase-data.js:1124-1128`: `dayOffYearKeys()` are loaded and then
`currentLessonData[yearKey] = mergeSummerReload(yearKey, previousSummer?.[yearKey], fresh[yearKey])` — the
same merge summer gets, on every listener reload and every `summerReloadHook` run. It is effective for SDOC,
not just called: `buildDayOffSlots()` (`:2027-2052`) spreads the plan doc onto the slot, so `lastEditedAt` is
present and `lessonEditedAtMs()` (`:1008`) can be non-zero; `SUMMER_SAVED_FIELDS` (`:1016`) is exactly the
SDOC plan's saved shape (CONTENT_FIELDS + photo pair + planComplete + stamp); and `displacedSummerServerCopies`
is keyed `semKey|lessonKey` (`:1028-1029`), so an SDOC year keys and prunes like a season. Round 5's L-3 was
looking at `rebuildDayOffSlots()` (`:2098-2101`), the local post-save install — that one does replace the map
wholesale and parks nothing, but it is not the reload path. **Not adopted was the right call**, and the split
table's wording ("SDOC reloads already run `mergeSummerReload()`") is accurate.

### LOW (non-blocking)

- **L-1 — the no-op prose still says "no message".** The save-path bullet reads "returns before the verifier:
  no message, no reload", while the BDD now correctly keeps "✓ Saved". `saveDayOffPlan()` is a data-layer
  function that shows no messages, so "no message" can only mean the verifier's — but "no read-back message"
  would remove the last chance of an implementer suppressing the editor's success line.
- **L-2 — pin that the id is generated once, before `runTransaction`.** The plan says "after allow-list
  validation" (which precedes the transaction), so the natural reading is right. Worth stating explicitly:
  if generation ever moved inside the transaction callback, an SDK retry would regenerate it and the verifier
  would compare a stale id → a spurious "edited since" (never a false failure, so LOW).
