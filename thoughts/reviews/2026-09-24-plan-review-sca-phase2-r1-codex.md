1. **HIGH — `Season.docId()` uses the wrong season for past-season reads.**  
   The plan makes queries and `Season.doc()` follow `viewing()`, but says `docId()` defaults to `current()` ([plan:264-285](/Users/christiehubley/tinker-ai-configs/thoughts/plans/summer-camp-app-seasons.html:264)). Open Studio performs direct computed-ID reads ([app.js:13675](/Users/christiehubley/summer-camp-app/js/app.js:13675)). If 2027 is current while the tab views 2026, `Season.docId('week_3')` would produce `season-2027|||week_3`, hiding the 2026 record or displaying 2027 data.  
   **Fix:** remove the ambiguous default. Provide `docIdForRead(id)` using `viewing()` and `docIdForWrite(id)` using `current()`, or require every call to pass an explicit season. Add scenarios for viewing 2026 Open Studio while 2027 is current and vice versa.

2. **HIGH — `Season.ref()` cannot both gate writes and continue serving direct reads.**  
   Phase 1 defines `ref()` for direct `.doc(id)` reads and updates ([season.js:290-295](/Users/christiehubley/summer-camp-app/js/season.js:290)); Phase 2 makes it throw whenever the viewing season is read-only ([plan:272-276](/Users/christiehubley/tinker-ai-configs/thoughts/plans/summer-camp-app-seasons.html:272)). Existing direct reads include materials and project details ([app.js:11206](/Users/christiehubley/summer-camp-app/js/app.js:11206), [app.js:12910](/Users/christiehubley/summer-camp-app/js/app.js:12910)) and Open Studio’s week document ([app.js:13675](/Users/christiehubley/summer-camp-app/js/app.js:13675)). Past-season views would therefore throw before `.get()`.  
   **Fix:** split `readRef()` from `writeRef()`, or return guarded proxies whose `.get()` remains legal but `.add/set/update/delete()` checks writability. Batch helpers also need guarded `set/update/delete` APIs. The completeness test should reject writes through read references.

3. **HIGH — the `_current` listener does not make stale-tab writes race-free.**  
   The plan claims that once another admin changes `_current`, “no write can carry the old season” ([plan:279-280](/Users/christiehubley/tinker-ai-configs/thoughts/plans/summer-camp-app-seasons.html:279)). An `onSnapshot` notification is asynchronous. A save—or a batch whose refs and payloads were already built—can commit after `_current` changes but before the callback sets `currentMoved`. The current rules do not compare document season with `_current`; they allow manager writes to the per-season collections ([firestore.rules:827-855](/Users/christiehubley/studio-hub/firestore.rules:827)).  
   **Fix:** weaken the stated guarantee or close the race. For Firestore writes, use a transaction that reads `_current` and performs the write, so a concurrent current-season change retries or aborts. For prepared batches, revalidate `_current` immediately before commit, acknowledging that only rules or transactions provide a hard guarantee. Add an emulator race test that moves `_current` between write preparation and commit.

4. **HIGH — the retained Kid Notes CSV import violates both the snapshot and non-overwrite invariants.**  
   The import performs multiple updates/adds without taking a snapshot ([app.js:7035-7116](/Users/christiehubley/summer-camp-app/js/app.js:7035)). Worse, it constructs every field with `''` when absent and then updates an existing profile with that object ([app.js:7054-7094](/Users/christiehubley/summer-camp-app/js/app.js:7054)); a minimal CSV can blank phone numbers, strategies, notes, and other existing data. Phase 2 changes its de-duplication but does not fix this ([plan:321](/Users/christiehubley/tinker-ai-configs/thoughts/plans/summer-camp-app-seasons.html:321)).  
   **Fix:** add a recoverable, awaited pre-import snapshot; build patches only from columns actually mapped and non-empty; preview creates versus updates; and write through bounded awaited batches. Add failure/resume and “sparse CSV does not erase existing fields” emulator tests.

5. **HIGH — Phase 2’s e2e plan directly violates the emulator-only requirement.**  
   Section 2.9 explicitly calls for “e2e (production, read-only)” ([plan:354](/Users/christiehubley/tinker-ai-configs/thoughts/plans/summer-camp-app-seasons.html:354)). The current Playwright server serves local files, but the app still connects to production Firebase; login uses `.env.test` production credentials ([playwright.config.js:1-23](/Users/christiehubley/summer-camp-app/playwright.config.js:1), [login.js:1-20](/Users/christiehubley/summer-camp-app/e2e/helpers/login.js:1)). New camp/topic, registry, session, note, and team writers also lack the required write-path emulator coverage.  
   **Fix:** make emulatorizing this repo’s entire e2e harness a prerequisite to 2A, modeled on the Classbook’s current emulator-only harness. Then add failing emulator tests for every new create/update/delete path. Do not run the existing e2e suite against production.

6. **HIGH — project-photo saves are not failure-safe, and the existing Storage rule denies deletes.**  
   The current save uploads new photos, attempts old-photo deletion, and only afterward writes Firestore ([app.js:13031-13072](/Users/christiehubley/summer-camp-app/js/app.js:13031)). A Firestore failure can leave new orphan uploads and, if deletion succeeds, references to deleted originals. Today deletion generally cannot succeed because `projectDetailPhotos` uses `allow write` with `request.resource.size`; `request.resource` is null on delete ([storage.rules:38-43](/Users/christiehubley/studio-hub/storage.rules:38)). The helper swallows every delete failure ([app.js:12860-12865](/Users/christiehubley/summer-camp-app/js/app.js:12860)). Phase 2 claims no rules change and calls both upload and deletion sites “uploads” ([plan:278,312](/Users/christiehubley/tinker-ai-configs/thoughts/plans/summer-camp-app-seasons.html:278)).  
   **Fix:** include the gated Storage-rule change that separates create/update from delete. Save in this order: upload new objects → commit Firestore references → delete removed objects; on Firestore failure, best-effort delete only the newly uploaded objects. Never suppress deletion failures without reporting/queuing cleanup. Test injected upload, Firestore, and deletion failures.

8. **MEDIUM — structural season editing has a cross-client race and the write method is underspecified.**  
   A forced-server count followed by a separate registry update does not enforce “only while no documents exist” ([plan:304](/Users/christiehubley/tinker-ai-configs/thoughts/plans/summer-camp-app-seasons.html:304)). The Classbook or another tab can create a document between the scan and update.    **Fix:** simplest safe design: make dates, weeks, breaks, slot keys, and studio removal immutable after the initial create; the create form already allows editing before submission. Explicitly require sanitized `update()`/transaction updates for editable registry fields and `_current`, never full-document `set()`.

10. **MEDIUM — new notes will lack `season` in local caches, and creation from a past view is misleading.**  
    Firestore gets the stamp, but locally inserted Notes for Next Year and Kid Notes use the unstamped pre-write object ([app.js:6350-6353](/Users/christiehubley/summer-camp-app/js/app.js:6350), [app.js:6938-6940](/Users/christiehubley/summer-camp-app/js/app.js:6938), [app.js:7097-7099](/Users/christiehubley/summer-camp-app/js/app.js:7097)). Additionally, while viewing 2026 with 2027 current, Add/CSV uses 2026 camps shown by the UI but stamps 2027, which is an easy mis-stamp.  
    **Fix:** include `season: Season.current()` in optimistic cache entries. Disable Add/CSV while viewing a past season or provide an explicit target-season selector with a conspicuous confirmation; editing existing profiles/observations can remain cross-season. Add immediate-render and past-view tests.

13. **MEDIUM — topic creation/rename is vulnerable to duplicates and chained renames.**  
    The plan uses auto-ID topic documents and a read-before-write name check ([plan:310](/Users/christiehubley/tinker-ai-configs/thoughts/plans/summer-camp-app-seasons.html:310)). Two tabs can both see no topic and create duplicates. A rename must also remember the last successfully stored name; otherwise A→B followed by B→C can keep querying for A. Duplicate curriculum camp names themselves remain allowed, although Classbook lesson keys can then collide by teacher/camp/block/project ([firebase-data.js:1744-1748](/Users/christiehubley/tinker-spring-curriculum/js/firebase-data.js:1744)).  
    **Fix:** enforce unique normalized camp names per season, preferably with deterministic topic IDs or a transactional uniqueness record. Define rename behavior for zero, one, and multiple matching topic docs and add a chained-rename scenario.
