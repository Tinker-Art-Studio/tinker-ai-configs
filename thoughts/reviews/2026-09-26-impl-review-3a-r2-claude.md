**copyCamp's all-destination concurrent reads (Codex 1) — correct and complete.** `js/carry-forward.js:441-456`: every destination ref is built before `runTransaction`, all reads are one `Promise.all` of `tx.get` with no write staged yet, so the reads-before-writes rule holds in both SDKs. Reads = writes = `3 + details + materials`, capped by `MAX_WRITES = 450` at `js/carry-forward.js:394`; Firestore's 500 cap is on *writes* in a transaction, reads are uncapped, so no limit is breached by the extra reads. Semantics in both SDKs give the intended guarantee: in the compat Web SDK a doc read as absent records `SnapshotVersion.min()` and its `tx.set` commits with an `exists:false` precondition, so a doc created in the read→commit window fails the commit, the transaction retries, the re-read finds it and throws `exists`; in firebase-admin the reads join the server-side transaction's read set with the same outcome.
