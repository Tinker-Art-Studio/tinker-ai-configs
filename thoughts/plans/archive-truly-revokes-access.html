Plan: Archiving someone in Tinker HQ truly ends their access

Apps: Tinker HQ (~/studio-hub) plus every staff app on tinker-hq-apps · Drafted: Oct 9 2026 · v1 · execution-ready: false — waiting on Christie's decisions (below) and a second-model design review.

Goal: when Christie archives someone in Tinker HQ, that person can no longer sign in to any Tinker app. Any app already open on a shared computer stops and says "This account has been archived", instead of opening normally and quietly failing every save.

What happened (Oct 9)

The front-desk computer's Roster Manager was signed in as admin@tinkerartstudio.com. That account had been archived because it was tagged to Alexis, a former EA. The app opened as normal. Firestore refused every read and save ("Missing or insufficient permissions"), so the saves failed without anyone being told. Roster Manager was fixed the same day (roster-manager commit c3032a1). admin@ has since been reactivated as a studio account.

What research found

1. Archive only reaches the Firestore rules. It does not reach the sign-in or the apps.

  • Archive (studio-hub/js/app.js:1166, runArchiveTransaction :1183) writes active:false, archivedAt, archivedBy and flips the person's Ticker roster entry in the same step. Un-archive writes only active:true.
  • The Firebase Auth account is never touched. The archived person's password still works, and they can sign in to any app. The confirm dialog promises they will "immediately lose access to every Tinker app", but nothing on the sign-in side does that. An earlier plan (studio-hub-archive-employees.html) chose to enforce archive through the rules only.
  • Each app keeps its own sign-in, separate from HQ's, because each one is its own Netlify site. An old sign-in on a shared computer stays signed in, and nothing on screen shows whose sign-in it is.

2. The apps: only Roster Manager blocks an archived account

There are six different copies of the sign-in check (by file hash), plus two apps with their own code. None except Roster Manager looks at active or at the person's access to that app. Several apps also fall back to saved or default data when Firestore refuses them, which is the same "the data disappeared" look as the May Classbook incident.

3. The rules: data protection mostly works, with five gaps

isActiveUser() (firestore.rules:24) is built into isAdmin, isManager, isManagerOrAbove, hasAppAccess and belongsToStudio, so almost every rule refuses an archived account. That is why Roster Manager failed. The rules audited are at origin/main 92ec15c, which matches what is live (the last receipt is 56c4a59, and firestore.rules has not changed since). The gaps are:

4. Turning off sign-in needs a small server step, which does not exist yet

  • Only the Firebase Admin SDK can disable an Auth account. A browser cannot. tinker-hq-apps has no Cloud Functions and no functions guard yet. A tinker-hq-apps functions guard is already planned as step E-3 of my-clay-hub-phase-e-link.html (marked highest-risk), mirroring my-clay-hub/scripts/deploy-functions.sh.
  • A downloaded service-account key is blocked by a Google Workspace org policy, so Netlify and Render functions cannot use the Admin SDK. A Cloud Function running as its own service account can.
  • tinker-hq-apps has billing linked (PITR and backups are on), so it is very likely on Blaze, which Cloud Functions require. This still needs confirming in the Console.
  • Never: the cached CLI token, raw REST calls, backup.js, or a hand-granted run.invoker.

5. People and shared studio accounts are not told apart

  • A users doc has no field that says "this is a studio account". The known shared or non-person accounts are admin@ (studio mailbox, used by Alexis), kiosk@ / kiosk2@ (Ticker tablets, recognised by hard-coded email or uid in the rules), reminders@ (bot, uid-pinned, no users doc), and test@ / test2@.
  • Archiving a person cannot reach a shared password they know. Alexis still knows admin@'s password. For a shared account, "offboarding" means changing its password, not archiving it.

Phases

The order is chosen so the real risk closes first. Phase 0 is Christie only, with no code. Phase 3 is what actually makes archive "truly" archive. Phase 4 is the visible "this account is archived" screen. It matters less once Phase 3 is live, because a disabled account is signed out within the hour, but it is still the clear message for "no access to this app".

Phase 3: Archive turns off sign-in (the core change)

execution-ready: false — depends on the tinker-hq-apps functions guard

3a. Functions guard for tinker-hq-apps. Build it once here, and step E-3 of the My Clay Hub plan reuses it. Mirror my-clay-hub/scripts/deploy-functions.sh: one codebase per run, --status / --diff / --approved <sha>, a worktree of an origin/main commit, declarations.json, a read-back after deploy, receipt tags under deployed/tinker-hq-apps/functions-<cb>/, --attest, and a FUNCTIONS-ROLLBACK.md. Heed finding F7: anything added to studio-hub's firebase.json or package.json must not break the rules guard. Confirm the Blaze plan first.

3b. The function: account-sync/syncAuthOnArchive.

  • Trigger: a Firestore trigger on users/{uid} update, not a callable. It is not an HTTP endpoint, so there is no invoker or ingress to get wrong. It fires however the archive happens (HQ, Console, a future script), and the archive button stays exactly as it is.
  • Logic: it acts only when active actually changed.
    • false: updateUser(uid, {disabled:true}), then revokeRefreshTokens(uid).
    • true (or the field removed): updateUser(uid, {disabled:false}).
    • Any other change: it does nothing, which also means it never loops on its own write.
  • Never touches the kiosk uid or emails, the reminder-bot uid, or an accountType:'shared' account (Phase 5). It logs a skip instead. A skip list is kept in the function, and the rules keep their own pins.
  • Reports back: it writes authDisabled: true|false and authSyncedAt to the users doc, so HQ can show the status. The trigger ignores this write because active did not change.
  • Runs as its own service account, account-sync@tinker-hq-apps, with only Firebase Authentication Admin plus Firestore write on users. Christie creates it in the Console; creating a service account is allowed, only key downloads are blocked. Retries are on, and every action is idempotent.
  • Tests: run the Auth and Firestore emulators with the function. Archive leads to disabled with tokens revoked; un-archive leads to enabled; a name edit does nothing; a kiosk or shared account is skipped; a repeated event is harmless.

3c. Tinker HQ shows it. Manage Team shows "Sign-in off ✓" or "Sign-in still on, retrying…" from authDisabled, and the archive dialog's wording becomes true. Ship this with HQ's Phase 4 change in one Netlify deploy.

Acceptance: within about a minute of Christie archiving someone, they cannot sign in to any app, and anything they have open stops within the hour. Un-archiving lets them sign in again with the same password.

Happy: Given a staffer is active and signed in to Classbook on their phone, When Christie archives them, Then their account is disabled, their sessions are revoked, and their next sign-in anywhere is refused.
Edge: Given Christie archives a staffer and un-archives them a minute later, When both events run (possibly out of order), Then the function reads the doc's current active, not the event's copy, so the account ends up enabled.
Failure: Given the function errors (an outage), When Christie looks at Manage Team, Then the row says "Sign-in still on". The rules still block all data, and Christie can disable the account by hand in the Console, as in Phase 0.

If this is interrupted

  • Each phase is independently safe. Rules phases only remove access from archived accounts.
  • If Phase 3 is half-built, nothing changes, because no function is deployed. If it is deployed but HQ is not updated yet, sign-in is still turned off; HQ just does not show the status.
  • If Phase 4 is partly rolled out, some apps show the archived screen and the others half-work as today. Nothing gets worse.
