Plan: One-Off Shift Email Reminders

Status: Drafted, not yet reviewed. Trigger keyword rule below was validated against every real override in the live Sept–Dec 2026 schedule before being written down — not guessed.
Goal: Anyone with a genuinely atypical, easy-to-forget shift (SDOCs, break camps, Friday Art Night) gets an automatic email confirmation when it's added to their schedule, and a reminder 48 hours before it happens — without anyone needing to remember to check Ticker or manually send a reminder.
Repo: ~/tinker-timeclock Ticker only — no Firestore rules changes.
Depends on: Plan B Phase 1's shared email helper at netlify/functions/_lib/email.js — import it directly, do not stand up a second Resend integration. Should be built after Plan B's Phase 1 ships, or alongside it if convenient.
Why now: Standing weekly commitments (regular Friday/Saturday slots) don't need this — people already expect those. What's easy to forget is the thing added two months ago in a hallway conversation that only shows up once. Christie was previously trying this in a different app (Schedule Viewer); consolidating it here makes more sense now that Ticker is becoming the source of truth for schedules and already has (via Plan B) the email infrastructure this needs.

How the trigger rule was derived (not guessed)

A read-only audit tool was run against the live production schedule (19 active people, Sept–Dec 2026, 229 dated overrides examined) and every override was shown to Christie, sorted by pattern. Two rounds of correction happened before landing on the final rule:

  • First pass tried a structural signal (is this a weekday the person doesn't normally work). Wrong — Julia Zuniga's recurring Friday/Saturday Clay Hub slot, and Mackenzie Reinhart's and Shelley Rahim's recurring Friday/Saturday birthday-party slots, all showed up as "extra days" even though they're standing weekly commitments, just implemented as weekly overrides instead of a recurring pattern.
  • Second pass moved to content-based keywords, refined against the real data: "camp" alone would have caught nearly everything (SDOC camp, Fall/Thanksgiving/Winter Break camp, Veterans Day camp, Tinker School Day Off Camp) but missed Lauren Burkey's "September 21 SDOC" (no literal "camp" in the text). Erica Podwoiski's recurring monthly "FAN (Friday Art Night)" needed its own keyword. Anika's and Mackenzie's one-off Saturday "Training" entries were confirmed as also excluded.
Final trigger rule (Aug 29, four keywords): an override is a reminder candidate if its note text contains, case-insensitive, the whole word "camp", "SDOC", "FAN", or "Extra Shift" — matched with word boundaries, not as a bare substring, so it can't accidentally fire inside an unrelated word (e.g. "Tiffany" does not match "FAN").
"Extra Shift" replaces the earlier "Private Event" idea — corrected (Aug 29) after Christie clarified what she actually needed. The original idea tried to auto-detect confirmed private events by matching "Private Event" while excluding "Booking Available" — but that was solving the wrong problem. Christie's real need: private events (and potentially other future one-off types) sometimes get added to someone's schedule genuinely outside their normal hours — that's what should trigger a reminder, not whether a Clay Hub slot's note happens to say "booked" vs. "available." Julia Zuniga's recurring Friday/Saturday Clay Hub slot never needs this keyword, no matter what event it's booked with, because it's her standing shift — nobody would type "Extra Shift" on it. A truly extra addition — someone covering a private event outside their regular pattern — gets "Extra Shift" typed into the note deliberately, the same way "SDOC" or "FAN" already work: a human-applied convention, not something inferred from the wording of an existing template. This also generalizes to any future one-off type without needing a new keyword invented each time.

Helper text at note entry

Wherever a shift note is entered or edited (the override editor in Schedule Builder, and anywhere else notes are written), show a short helper line near the note field: "Notes containing 'camp,' 'SDOC,' 'FAN,' or 'Extra Shift' automatically email the scheduled person a reminder 48 hours beforehand." This makes the trigger legible to whoever's typing, instead of a hidden rule they'd have to be told about separately.

Phase 1 — Candidate detection (pure function, no email yet)

Acceptance criteria

A pure, testable function correctly classifies any override note per the rule above, with unit tests covering every example already validated against real data.

Given a note containing "SDOC camp," "Fall Break camp," "Tinker School Day Off Camp," or "Veterans Day camp," when classified, then it's a reminder candidate.
Given a note reading exactly "September 21 SDOC" (no "camp" substring), when classified, then it's still a reminder candidate (via the SDOC keyword).
Given a note reading "Youth Birthday Party — Eden Bat Mitzvah" or any of Julia Zuniga's other recurring Clay Hub slot notes, when classified, then it is NOT a candidate — no keyword match, confirmed correct by Christie even though it's a specifically-named booking, because it's part of a standing shift, not a one-off.
Given a note reading "Birthday party — Fri party 3:45-5:15" or "Training with Anika," when classified, then it is NOT a candidate — no keyword match.
Given a note containing "Tiffany" (contains the substring "fan" but not as a whole word), when classified, then it is NOT a candidate — the FAN keyword requires a word boundary, not a bare substring.
Given a note containing a word like "SDOCument" or "psdoc" (contains the substring "sdoc" but not as a whole word), when classified, then it is NOT a candidate — same word-boundary requirement as FAN, tested explicitly for SDOC too (a second-model review caught that only FAN had this negative test, not SDOC).
Given a note reading "Private Event — covering for Christie (Extra Shift)" or similar, where "Extra Shift" was deliberately typed in, when classified, then it's a reminder candidate — this is the deliberate, human-applied signal for "this is genuinely outside this person's normal hours," regardless of event type.

Firebase safety checklist

  • Pure function, no Firestore access at all in this phase.
  • Lives in js/schedule-helpers.js, this repo's existing dual-loadable (browser global + Jest require()) pure-function file, alongside partitionSchedulesByRosterActive() — not a new file, per this repo's own established pattern. Word-boundary regex matching already has precedent in this codebase (formatNoteTimes()) to follow.
  • Test coverage required before this phase is done: unit tests in this repo's existing schedule-helpers.test.js, no emulator needed — this is a pure function.

Phase 2 — Immediate confirmation email on add

Acceptance criteria

The moment an admin saves an override that matches the trigger rule, the person it's assigned to gets an email confirming the date, time, studio, and what it is. The note-entry UI shows the helper text described above so the trigger isn't a hidden rule.

Given an admin saves a new override matching the trigger rule for someone's schedule, when the save succeeds, then that person receives a confirmation email with the date/time/studio/description.
Given an admin saves an override that does NOT match the trigger rule (a routine recurring-style entry), when saved, then no email is sent.
Given the email send fails, when that happens, then the schedule save itself is unaffected and the failure is logged — same "never let email break the real write" principle as Plan B.
Given the person the shift is assigned to has no resolvable email (an unclaimed roster entry — a real, already-modeled state elsewhere in this app, e.g. the "Contact info available after they sign in" message in the time-off sub picker), when a matching override is saved for them, then no email attempt is made and no error is thrown — same graceful handling this app already uses for that exact state elsewhere.

Firebase safety checklist

  • Read-only trigger check plus an email send — no new Firestore writes beyond the schedule save that already happens today.
  • No rules change.
  • Depends on saveSchedule() (js/firebase-data.js:205-219) actually awaiting its write and surfacing failures — see the shared prerequisite fix noted in Plan 1 (that function is currently synchronous and doesn't await its internal .set() call). Confirm that fix has landed before wiring an email send onto "the save succeeded."

Phase 3 — 48-hour-ahead daily reminder

Acceptance criteria

A scheduled function runs once daily and emails anyone with a trigger-matching one-off shift exactly 2 calendar days out — regardless of how long ago it was added to their schedule.

Resolved (Aug 29) — no dedup tracking, deliberately. A second-model review flagged that a naive dedup flag (writing "already reminded" onto the override itself) would be unsafe — handleAddOverride() (js/app.js:3071-3098) rebuilds override objects from scratch on every save, so any later edit to that date would silently wipe the flag. The fix considered was a separate tracking collection (with its own new Firestore rule). Christie's simpler read, and the one this plan adopts: with a single fixed daily check ("what's exactly 2 days out"), each date only ever matches that condition on one calendar day under normal operation — no tracking should be needed at all. The only way a duplicate happens is a rare edge case (the scheduled function retried after a partial failure, or manually re-run while debugging) — worth accepting as a minor, occasional inconvenience rather than adding a new collection and rule to prevent it. This plan has zero Firestore rules changes, full stop.
Given today is 2026-09-19 and someone has a trigger-matching override dated 2026-09-21, when the daily scheduled function runs, then that person receives a reminder email.
Given the daily function is accidentally run twice on the same day (retry or manual re-trigger), when that happens, then the same person may receive the same reminder twice — a known, accepted tradeoff for keeping this phase simple, not a bug to design around.
Given a trigger-matching shift is added with LESS than 48 hours' notice (e.g., a last-minute SDOC added tomorrow), when the daily function's window has already passed for that date, then Phase 2's immediate confirmation email is still the person's notice — this phase intentionally does not try to retroactively catch shifts that are already inside the 48-hour window, to keep the daily job simple (single fixed lookahead, not a range).
Given the trigger-matching override is deleted before the daily function ever runs for it, when the function runs, then it correctly finds nothing at that date and sends no reminder — no stale scheduled send survives a deletion, since the function re-reads live schedule data each run rather than pre-queuing sends.
Given the scheduled function runs at a fixed UTC time, when "2 days out" is computed, then the comparison uses the studio's local calendar date (America/Denver, matching the timezone convention already used by Schedule Viewer's own reference cron), not raw UTC date math — override dates are timezone-naive YYYY-MM-DD strings, so an off-by-one day is a real risk near midnight if this isn't pinned explicitly.

Firebase safety checklist

  • No rules change — no new collection, no new fields on any rules-guarded document.
  • Runs as a Netlify Scheduled Function — new infrastructure type for this repo (Plan B's functions are all on-demand, not scheduled).

Completeness check

Phase 1 has zero side effects and can be built/tested in isolation. Phase 2 is additive to the existing save flow. Phase 3 is the only phase needing genuinely new infrastructure (a scheduled function) and is fully independent of Phase 2 — either could ship without the other if needed.

Resume instructions

Build after (or alongside) Plan B's Phase 1, since Phase 2 and 3 here both depend on that same Resend integration existing first. The trigger rule itself needs no further confirmation — validated against real data and confirmed by Christie.
