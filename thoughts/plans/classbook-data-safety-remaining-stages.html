⚠️ Abort must restore live state, not just skip the delete (found during second-model review): handleGridAction's move branch mutates currentLessonData[semKey] and re-renders the grid before the Firestore write happens (optimistic UI, app.js:4568-4589, no surrounding try/catch). A read-back-triggered abort that only skips deleteLessonKey leaves Firestore correct but the in-memory model and visible grid still show the move as done — a subsequent action before a reload could persist that wrong state. The fix must also restore lessons[sourceKeyToDelete] into currentLessonData[semKey] and re-render on abort.
🛑 2B introduces a new partial-failure state that must be handled, found during a follow-up second-model review of this plan: both swap branches mutate currentLessonData[semKey] and call renderAdminGrid() before their save completes (app.js:4614-4615 for the occupied branch, 4621-4622 for the empty branch) — same optimistic-UI pattern as move. Today the occupied branch is one atomic saveLessonData write (all-or-nothing); after 2B replaces it with two separate saveSingleLesson calls, a new failure mode becomes possible: the first targeted save succeeds, the second throws, and Firestore ends up half-swapped while the already-rendered grid shows the swap as fully complete. Fix: on a second-save failure, roll currentLessonData[semKey] back to its pre-swap state and re-render, mirroring 2A's abort-restore fix, and surface an alert naming the partial state. The pre-existing empty-branch (saveSingleLesson().then(() => deleteLessonKey())) has the identical exposure if the chained deleteLessonKey throws after the first write succeeds — apply the same restore-on-failure handling there too since Phase 1 is already touching this code.
🛑 Decided, not deferred — saveAdminEdit is in scope, found by reading the actual code: the second-model review initially characterized converting saveAdminEdit() as a smaller, optional benefit, reasoning that it builds a fresh lesson object from the open form (unlike move/swap's stale-snapshot risk). Reading saveAdminEdit() directly shows that reasoning only covers the edited lesson: const lessons = { ...(currentLessonData?.[semKey] || {}) } copies the entire local semester — every other lesson too — and the full copy goes through saveLessonData()'s .set(..., {merge:true}). Firestore's merge is recursive, so every lesson key present in that local copy gets deep-merged (in practice, field-by-field overwritten) into Firestore — any lesson other than the one being edited silently reverts to whatever this browser tab had cached, if it's stale relative to Firestore. A live onSnapshot listener (setupLessonDataListener) keeps currentLessonData in sync in the common case, narrowing the window a lot — but a listener reconnect lag, network hiccup, or long-open tab can still leave a stale sibling lesson in that local copy at save time. Same category of risk 2A/2B close, just partially (not fully) mitigated by the listener. Fix it the same way as swap.

Use writeTestLessonFields (not writeTestLesson) for any assertion that needs to prove a partial write left sibling fields untouched.

Phase 2 — Save-path field safety (Stage 2C + 2D)

✅ Shipped Aug 12, 2026. Implemented exactly as redesigned below: js/firebase-data.js's saveSingleLesson non-summer branch rewritten around per-field dotted-path update() calls with content-field stripping (hoisted contentFields/hasContent to the top of the function, shared by both branches); summer branch's hasContent guard got the planComplete bypass in the same edit. Both Plan Complete checkbox call sites in js/app.js (summer ~1985, non-summer ~2431) narrowed to pass { planComplete } only. Red tests first: Test 5 (existing) rewritten to simulate the actual fixed call-site payload rather than a payload the real handler never sent; two new tests added (non-summer Plan Complete via the real attachCardListeners production listener — not a simulation; non-summer stripping regression mirroring Test 1/2, with extra assertions proving sibling non-content fields and the rest of the lesson survive a per-field write, the exact critical gap this phase's redesign closes). All 3 failed for the expected reason against pre-fix code; all pass after. Full suite re-run: 16/16 green. Not yet committed or deployed to Netlify.
🛑 Critical, found during second-model review: the summer and non-summer save paths have different Firestore write semantics, and this phase's original design ("narrowing a payload is strictly safer") was only true for one of them. Summer's saveSingleLesson (firebase-data.js:672) uses .set(cleanData, { merge: true }) — a document-level merge where omitting a field genuinely leaves it untouched. Non-summer's saveSingleLesson (firebase-data.js:683-685) does curriculumDb.collection('curriculum').doc('lessonData').update({ [fieldPath]: lessonData }) where fieldPath = semesterKey + '.' + lessonKey — Firestore's update() only protects sibling data at dotted-path segments you don't mention; the object value supplied for the path you do mention fully replaces whatever was there. A narrowed or stripped lessonData object at that path deletes every field it omits — the exact failure this whole plan exists to stop. Both 2C and 2D must target the non-summer path with explicit per-field dotted paths, never a partial object assigned to the bare semesterKey.lessonKey path.

What it does

2C (app.js, Plan Complete checkbox — calls at app.js:1985 and app.js:2431): Stop passing the full lesson object to saveSingleLesson. Summer path: pass only { planComplete, lastEditedBy, lastEditedAt } — the existing .set(merge:true) already makes this safe. Non-summer path: write explicit per-field dotted paths instead, e.g. update({ "semKey.lessonKey.planComplete": true, "semKey.lessonKey.lastEditedBy": ..., "semKey.lessonKey.lastEditedAt": ... }) — never a partial object assigned to the bare semKey.lessonKey path. This requires a guard update: saveSingleLesson's hasContent check currently blocks all-empty-content-field saves — add a bypass when the payload explicitly contains planComplete, so this narrower write isn't blocked by a guard meant for a different failure mode.

2D (firebase-data.js, non-summer saveSingleLesson, function firebase-data.js:646-691, non-summer branch 677-690): Apply the same content-field stripping already live on the summer path — strip empty introPitch/processStep1–4/closure/dayOfMaterials before writing. On the non-summer branch, "strip" must mean "omit that field's dotted path from the update() call entirely," not "omit the key from an object that still gets assigned wholesale to the lessonKey path" — same distinction as 2C.

Given: A lesson has a real photoUrl, but the in-memory lesson object is stale (photoUrl blank from a failed load) When: An admin checks the Plan Complete checkbox Then: Only planComplete/lastEditedBy/lastEditedAt are written — as a merge on the summer path, as explicit per-field dotted paths on the non-summer path AND photoUrl in Firestore is untouched regardless of the stale in-memory value, on both paths AND the hasContent guard does not block this write, because it explicitly recognizes a planComplete-only payload Given: A teacher saves real lesson content in the same session When: They separately check Plan Complete afterward (or vice versa) Then: Both saves land correctly — neither write shape clobbers fields the other one owns Given: A Spring/Fall (non-summer) lesson has real content in Firestore in fields not touched by the current save When: A save runs with some content fields empty in memory (stale load) and 2D's stripping applies Then: The non-summer path omits those fields' dotted paths from the update() call — it does not send a stripped-but-still-whole object to the lessonKey path AND existing Firestore content in untouched fields survives unchanged — this is the direct regression test for Test 1/2's logic, applied to the other save path, and the test that would have caught the critical issue above had it existed before this review
✅ Once redesigned around per-field dotted paths for the non-summer branch, both changes are additive/narrowing rather than replacing. Neither changes the target collection or its rules.

Phase 3 — Post-save read-back verification (Stage 2E)

✅ Shipped Aug 12, 2026. New verifySummerLessonWrite(docRef, writtenContentFields) helper in js/firebase-data.js, forcing get({source:'server'}) per the second-model-review finding below, with the exact retry-once/soft-message/hard-message behavior specified. Wired into saveSingleLesson's summer branch right after the write, only when the payload included at least one content field (a planComplete-only save has nothing to verify). No caller-side changes needed — existing catch blocks in the summer modal's saveLesson() and the Plan Complete checkbox handler already display err.message, and both new error messages are worded to read sensibly there. Red tests first: since real Firestore is too reliable to naturally trigger a silent write failure, tested the verification function directly — against a real Firestore doc deliberately missing a field (proves mismatch detection without needing to fabricate a write failure), and against a duck-typed fake docRef whose get() always throws (isolates the retry-twice-then-soft-message logic from real network conditions). Plus a happy-path regression proving a normal save still resolves without throwing. All 3 confirmed red/appropriately-passing against pre-fix code, all pass after. Full suite: 19/19 green. Not yet committed or deployed to Netlify.

What it does

After every summer-path saveSingleLesson write, read the doc back and confirm the content fields that were supposed to change actually landed. If any expected field reads back missing or empty, surface an error to the teacher within seconds — this is the single change that would have caught both original May 2026 wipe incidents immediately instead of days later.

🛑 Must force a server read, found during second-model review: js/firebase-data.js uses the v8-compat Firestore SDK throughout. A default .get() immediately after a write can resolve from local cache, which reflects the pending write optimistically regardless of whether it ever reached the server — a cache read here could report "confirmed" on a write that never actually persisted, defeating the point of this phase. The read-back (and its retry, below) must explicitly use get({ source: 'server' }). This codebase already treats cache-vs-server as a real distinction elsewhere (setupLessonDataListener, firebase-data.js:511-515, explicitly skips cache-only snapshots) — follow that precedent here.
Given: A teacher saves real content to introPitch and processStep1 When: The read-back runs immediately after the write, forcing a server read Then: Both fields are confirmed present and non-empty in the read-back AND the teacher sees the normal "✓ Saved" indicator with no extra friction Given: A write silently fails to persist a field (simulated in test by writing then externally clearing the field before read-back) When: The server-forced read-back detects the mismatch Then: The teacher sees an explicit error naming which field(s) may not have saved, within the same save flow — not a generic "saved" that's actually wrong Given: The write itself succeeded, but the read-back call fails for an unrelated reason (transient network blip immediately after) When: The first server read-back fails Then: Retry once, also forced to the server (a retry that reads from cache verifies nothing) AND if the retry also fails, show a soft "couldn't confirm save, check your connection" message — not a silent success, and not a hard wipe-alarm, since the underlying write most likely did succeed AND log both attempts to console either way
Doubles Firestore reads on every save. Cost is trivial at this app's scale (~100 saves/day per the original plan doc) — explicitly accepted, not a concern to re-litigate during execution.

Phase 4 — Intentional field clear support (Stage 3)

What it does

The Stage 1 stripping fix protects against accidental overwrites but also silently blocks intentional clears — today, deleting all text from a field and saving does nothing; the old content reappears on reload with no explanation. Track which content fields had text when a modal opened (the non-summer modal already does this via teOriginalData; the summer modal needs the same tracking added). At save time, a field that was non-empty at open and is now empty is an intentional clear — use Firestore's FieldValue.delete() for it instead of omitting it from the payload.

Given: A lesson has real content in processStep2 when the modal opens When: A teacher deletes all the text in processStep2 and saves Then: FieldValue.delete() is used for processStep2 (not silent omission) AND a brief confirmation ("processStep2 cleared") appears, so the behavior is visible rather than silent AND on reload, processStep2 is genuinely empty — the old content does not reappear Given: A lesson has an already-empty processStep3 when the modal opens (never filled in) When: A teacher saves without touching processStep3 Then: Nothing is deleted — it was empty at open, so this is not a "clear," just an untouched empty field AND existing Stage-1 stripping behavior for never-filled fields is unchanged
Requires open-state snapshotting in the summer modal, which doesn't exist yet (non-summer modal already has it). This is the most UX-sensitive phase — get the confirmation copy right so a genuine clear reads as confirmed, not alarming.
