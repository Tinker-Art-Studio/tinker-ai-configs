🛑 Critical, found during second-model review: the summer and non-summer save paths have different Firestore write semantics, and this phase's original design ("narrowing a payload is strictly safer") was only true for one of them. Summer's saveSingleLesson (firebase-data.js:672) uses .set(cleanData, { merge: true }) — a document-level merge where omitting a field genuinely leaves it untouched. Non-summer's saveSingleLesson (firebase-data.js:683-685) does curriculumDb.collection('curriculum').doc('lessonData').update({ [fieldPath]: lessonData }) where fieldPath = semesterKey + '.' + lessonKey — Firestore's update() only protects sibling data at dotted-path segments you don't mention; the object value supplied for the path you do mention fully replaces whatever was there. A narrowed or stripped lessonData object at that path deletes every field it omits — the exact failure this whole plan exists to stop. Both 2C and 2D must target the non-summer path with explicit per-field dotted paths, never a partial object assigned to the bare semesterKey.lessonKey path.

What it does

After every summer-path saveSingleLesson write, read the doc back and confirm the content fields that were supposed to change actually landed. If any expected field reads back missing or empty, surface an error to the teacher within seconds — this is the single change that would have caught both original May 2026 wipe incidents immediately instead of days later.

🛑 Must force a server read, found during second-model review: js/firebase-data.js uses the v8-compat Firestore SDK throughout. A default .get() immediately after a write can resolve from local cache, which reflects the pending write optimistically regardless of whether it ever reached the server — a cache read here could report "confirmed" on a write that never actually persisted, defeating the point of this phase. The read-back (and its retry, below) must explicitly use get({ source: 'server' }). This codebase already treats cache-vs-server as a real distinction elsewhere (setupLessonDataListener, firebase-data.js:511-515, explicitly skips cache-only snapshots) — follow that precedent here.

Context — Vulnerability #11 reopened (Phases 7–8, Layer 1)

Both lesson editors (saveTeacherEdit() for non-summer, saveLesson() for summer camp) build their Firestore write payload from every currently non-empty field in the open form, not just the field(s) the user actually typed into this session. Neither modal re-syncs its open form against live Firestore data while it's open — a live re-sync mid-typing would risk clobbering the user's own in-progress edit, so the form is effectively a point-in-time snapshot for as long as it stays open.

Concrete failure: Teacher A and Admin B both open the same lesson. Both load processStep1: "Old step 1". B edits processStep1 → "New step 1" and saves; Firestore now has "New step 1". A, still viewing their now-stale-loaded form, edits only projectTitle — never touching processStep1 — and saves. A's save payload still includes A's stale copy, processStep1: "Old step 1", because the payload is built from "every non-empty field currently in the form," not "every field this user changed." B's edit is silently reverted, even though A never opened that field.

Why this wasn't caught by this plan's own Phase 1–6 reviews: Vulnerability #11 was marked "deferred, not in scope" (see "Not in scope" below) before Phase 1 had even started. Every later second-model-review in Phases 1–6 was scoped to verifying the specific phase under execution. None were asked to re-derive Vuln #11 from the actual code, because it had already been closed as a scoping decision — a review only re-examines what it's pointed at. The "same-instant race" framing that closed it also didn't name the actual mechanism above, so there was no prompt to look again. Worth remembering for future plans: an "out of scope" decision made before the relevant code exists (or before anyone has traced the actual mechanism) can go unexamined by every subsequent review indefinitely.

The non-summer branch has no equivalent blocking check at all — it always writes whatever's in the cleaned payload, empty or not (protected only by field-level stripping, not a whole-save block). Phase 8 — Summer editor: diff-only payload (redesigned after second-model review) + guard widening

🛑 This phase was fundamentally redesigned after a second-model review found the original draft's diff was a no-op — read this box before "What it does" below, which describes the corrected design. // Phase 3's verifySummerLessonWrite() retry-once precedent). Returns

async function adminLessonStillExistsWithRetry(semKey, key) {
  if (!curriculumDb) initCurriculumFirestore();

  1. Generated message ID (Codex's non-blocking note, now applied).   2. Today's shipped code (being replaced by this phase) calls getQaThread(lesson), pushes onto it, and writes the whole resulting array back — so a legacy-only lesson's first message under today's code silently migrates its synthesized legacy thread into a real qaThread array. // Shared by sendTeacherQaMessage (here) and sendQaReply (Phase 11) — both need
// to seed arrayUnion's argument list with the synthesized legacy thread on a
// lesson's first message under this atomic-append pattern, or those legacy
// messages are silently lost the moment qaThread gets its first real entry
// (see the note above). arrayUnion's deep-equality dedup makes repeating this
// migration from two concurrent senders safe: identical legacy entries
// collapse to one, and new entries (each carrying a generated id) never
// collide with each other or with the migrated legacy ones.
function buildQaThreadUnionArgs(existingLesson, newEntry) {
  const needsMigration = !existingLesson?.qaThread || existingLesson.qaThread.length === 0;
  return needsMigration ? [...getQaThread(existingLesson || {}), newEntry] : [newEntry];
}

async function executeCopyPlan(sourceKey) {

  // Fail closed if the initial load failed — same reasoning as Phase 9/14.
  // Found by a second Codex review round: saveSingleLesson()'s own internal
  // check doesn't help here, since this function already reads/mutates local
  // state and reports success before ever calling it.
  if (lessonDataLoadedSuccessfully === false) {
    alert("Lesson data failed to load earlier — refusing to copy to avoid writing over unconfirmed server state. Reload and try again.");
    return;
  }

  const lessons = { ...currentLessonData[semKey] }; // local display/cache only from here — never sent to Firestore as a whole object
  const source = lessons[sourceKey];
  if (!source) return;

  const checkboxes = document.querySelectorAll('.ca-copy-cb:checked');
  const targetKeys = Array.from(checkboxes).map(cb => cb.dataset.key);
  if (targetKeys.length === 0) { alert('No targets selected.'); return; }

  const overwriteTargets = targetKeys.filter(k => lessons[k] && hasLessonContent(lessons[k]));
  if (overwriteTargets.length > 0) {
    const names = overwriteTargets.map(k => {
      const l = lessons[k];
      return `${l.teacher} — ${l.className} (Wk ${l.weekNum})`;
    }).join('\n');
    if (!confirm(`${overwriteTargets.length} target(s) already have lesson plans that will be overwritten:\n\n${names}\n\nContinue?`)) return;
  }

  const fields = getCopyableFields(source);
  const isSummer = semKey.startsWith('summer-');
  const previousContent = {};
  const skippedTargets = [];

  for (const targetKey of targetKeys) {
    if (!lessons[targetKey]) continue;
    const targetExisting = lessons[targetKey];
    if (hasLessonContent(targetExisting)) {
      previousContent[targetKey] = getCopyableFields(targetExisting);
    }

    // A field the source's copyable fields leave empty, but the EXISTING
    // target had real content in — same fieldsToClear treatment Phase 13
    // uses, needed for the same reason (saveSingleLesson strips, doesn't
    // clear, empty payload fields).
    const fieldsToClear = CONTENT_FIELDS.filter(f =>

    // condition (firebase-data.js:712) at this call site, so a target that

    // copyable content is `materials`, which isn't in CONTENT_FIELDS) is

        console.warn(`⚠️ Copy Plan: target ${targetKey} would be blocked by the summer content guard (no CONTENT_FIELDS content, nothing to clear) — skipping, not counting as copied.`);
        skippedTargets.push(targetKey);

      // after N of M") could read as if a skipped target were part of the
      // failure count, when it was deliberately, separately excluded above.

      return;
    }

    // Local display/cache only — mirrors what was actually just saved.
    Object.assign(lessons[targetKey], fields);
    fieldsToClear.forEach(f => { lessons[targetKey][f] = ''; });
    copied++;

    // Log immediately after this target's successful save — not in a
    // separate loop after every target is attempted, so an already-saved

    // already uses (e.g. saveAdminEdit, Phase 9), so a log failure here
    // doesn't abort the loop or leave the admin with an uncaught rejection
    // and no explanation for an otherwise-successful lesson save.
    //
    // Accepted, not fixed — a third Codex review round noted this try/catch
    // only silences the failure, it doesn't undo it: appendChangeLogEntry()
    // (firebase-data.js:606-618, pre-existing shared code, not part of this
    // plan) updates currentChangeLog synchronously BEFORE its own Firestore
    // write, so a rejected write here leaves a phantom local history entry
    // that never actually persisted. Same class of gap exists at every other
    // call site of this shared function throughout the app, not something
    // introduced by this phase — fixing it would mean changing that shared
    // function's own contract (update the cache only after the write
    // succeeds, or have every caller roll back on failure), a bigger change
    // than this plan's scope. Self-corrects on the next real reload

    // doc, applied here to an audit-log entry rather than lesson content.
    const logEntry = {
      action: 'copy',

        projectTitle: source.projectTitle,
        fromTeacher: source.teacher, fromClassName: source.className, fromWeek: source.weekNum,

    } catch (e) { console.warn('Could not write change log entry for', targetKey, e); }
  }

  closeAdminModal();
  renderAdminGrid();
  renderChangeHistory();

    ? ` (${skippedTargets.length} skipped — no content to copy for the summer content guard, see console)`
    : '';

}

New pure helper, no Firestore or cache access:

// A property of the CURRENT roster alone, so it can never depend on cache
// freshness or timing. Catches every case where two DIFFERENT roster rows
// would write to the identical Firestore document, whether or not either one
// already exists there — the existence question is answered separately, per
// key, by the forced-server check already inside createLessonSlotsForRoster.
function validateRosterKeys(roster, numWeeks) {
  const keyOwners = {}; // lessonKey -> Set of JSON.stringify([teacher, className])
  for (const [className, data] of Object.entries(roster)) {
    if (!data.teacher || !className) continue;
    const teacher = data.teacher;
    for (let weekNum = 1; weekNum <= numWeeks; weekNum++) {
      const lessonKey = makeLessonKey(teacher, className, weekNum);
      if (!keyOwners[lessonKey]) keyOwners[lessonKey] = new Set();
      // JSON.stringify of the actual [teacher, className] pair, not a
      // template-literal display string — closes the round-6 Codex finding
      // that a display string like `${teacher} / ${className}` is not
      // injective (two different pairs can render identically).
      keyOwners[lessonKey].add(JSON.stringify([teacher, className]));
    }
  }
  const collisions = Object.entries(keyOwners)
    .filter(([, owners]) => owners.size > 1)
    .map(([key, owners]) => ({
      key,
      sources: [...owners].map(s => { const [t, c] = JSON.parse(s); return `${t} / ${c}`; })
    }));
  return { valid: collisions.length === 0, collisions };
}

async function createLessonSlotsForRoster(semKey, roster, numWeeks) {
  if (!roster || !numWeeks || Object.keys(roster).length === 0) return;

  // Summer skipped entirely — see the danger box above for the full trace of
  // why a roster-keyed existence check can never be meaningful against
  // summer's disjoint key scheme. Summer lesson creation happens exclusively
  // via loadSummerCampData()'s regeneration, unrelated to classRoster.
  if (semKey.startsWith('summer-')) return;

  // Fail closed if the initial load already failed BEFORE this call.
  if (lessonDataLoadedSuccessfully === false) {
    throw new Error('Lesson data failed to load earlier — refusing to create roster slots to avoid writing over unconfirmed server state. Reload and try again.');
  }

  if (!currentLessonData) await loadLessonData();
  // Re-checked after the load attempt above, not just before it — catches a
  // failure from THIS invocation's own loadLessonData() call, not just an
  // earlier one (the flag starts null, not false, until a load has actually
  // been attempted and failed, so the first check alone can't catch this).
  if (lessonDataLoadedSuccessfully === false) {
    throw new Error('Lesson data failed to load — refusing to create roster slots to avoid writing over unconfirmed server state. Reload and try again.');
  }
  if (!currentLessonData[semKey]) currentLessonData[semKey] = {};

  const existingLessons = currentLessonData[semKey];
  // Locally-missing candidates — NOT confirmed new yet. That confirmation
  // happens per-key below, via a forced-server read, before any write.
  // Precondition: the caller (saveSettings()) has already run
  // validateRosterKeys() on this exact roster/numWeeks pair and returned
  // before calling this function at all if any collision was found — this
  // function has exactly one call site and does not re-validate that case.
  // What it DOES still check, per key below: whether a single roster row's
  // key collides with unrelated, already-real content that has nothing to do
  // with THIS roster (e.g. a manually-created lesson elsewhere, or a
  // pre-existing lesson the local cache hasn't synced yet) — a different
  // question from "do two rows in this roster collide with each other."
  const candidates = {};
  for (const [className, data] of Object.entries(roster)) {
    if (!data.teacher || !className) continue;
    const teacher = data.teacher;
    for (let weekNum = 1; weekNum <= numWeeks; weekNum++) {
      const lessonKey = makeLessonKey(teacher, className, weekNum);
      if (!existingLessons[lessonKey]) {
        candidates[lessonKey] = {
          teacher, className, weekNum, weekDate: '', projectTitle: '',
          introPitch: '', processStep1: '', processStep2: '', processStep3: '', processStep4: '',
          closure: '', materials: '', materialsList: [], dayOfMaterials: '',
          qaThread: [], planComplete: false,
          classSize: String(data.enrollment || 0),
          lastEditedBy: '', lastEditedAt: ''
        };
      }
    }
  }

  const candidateKeys = Object.keys(candidates);
  if (candidateKeys.length === 0) return;

  if (!curriculumDb) initCurriculumFirestore();
  let createdCount = 0;
  const failures = [];
  for (const lessonKey of candidateKeys) {
    // Re-checked every iteration, not just twice before the loop — found in
    // round 6: the two pre-loop checks can't catch the flag flipping
    // mid-loop (each iteration does a sequential network round trip), and a
    // write after a mid-loop flip would have silently no-opped via
    // saveSingleLesson()'s own internal gate while still counting here as a
    // success. Cheap to check per-iteration, so fixed outright.
    if (lessonDataLoadedSuccessfully === false) {
      failures.push(`${lessonKey} (lesson data failed to load mid-operation)`);
      continue;
    }
    try {
      // Forced-server existence check FIRST — the actual fix for the
      // "collides with unrelated real content" case (see the precondition
      // note above for how this differs from the "two rows in this roster
      // collide with each other" case, now caught upstream in saveSettings).
      const check = await adminLessonStillExistsWithRetry(semKey, lessonKey);
      if (check.exists) {
        // Locally missing, but genuinely real on the server — nothing to
        // create. Update the local cache with the REAL data (not the
        // scaffold), so this key stops looking "missing" on the next pass
        // too, and isn't shown blank over real content in the meantime.
        currentLessonData[semKey][lessonKey] = check.data;
        continue;
      }

      // Confirmed free — the complete scaffold is now safe to use outright
      // for the LOCAL cache. The Firestore-bound write below is still
      // intentionally sparse for empty CONTENT_FIELDS — saveSingleLesson's
      // own internal stripping — the same "omitting a field already means
      // empty" convention every other save path in this doc uses.
      await saveSingleLesson(semKey, lessonKey, candidates[lessonKey]);
      currentLessonData[semKey][lessonKey] = candidates[lessonKey];
      createdCount++;
    } catch (err) {
      // Independent, unordered creates with no swap/copy-style relationship
      // between them — still attempt every remaining slot rather than
      // stop-on-first-failure, but collect what failed instead of silently
      // swallowing it. A thrown existence check (both server reads failed)
      // lands here too — treated as a failure for this key, not a guess.
      console.error(`❌ Failed to create lesson slot ${lessonKey}, continuing with remaining slots:`, err);
      failures.push(lessonKey);
    }
  }

  if (createdCount > 0) {
    console.log(`✅ Created ${createdCount} lesson slots for roster classes`);

Phase 15 — Semester delete: surface failures, honest summer content-clearing via real server enumeration (deleteSemester / deleteLessonData)

🛑 Brought into scope Aug 14, 2026 at Christie's explicit request ("when all is said and done, I want all things fully wrapped") — previously found via a completeness sweep and deferred as unrelated to Vulnerability #11. deleteSemester(key) (app.js:3898-3925), wired to a real "🗑 Delete" button in the admin Semester selector (any non-active semester), has two real bugs. (2) deleteLessonData() (firebase-data.js:480-485) only clears the semester's key from curriculum/lessonData — for a summer semester, this is a complete no-op for the actual lesson content, which lives entirely in separate summerCamps_lessonData documents this call never touches, so "deleting" a summer semester removes it from config/the grid while every one of its real lesson plan documents stays permanently orphaned in Firestore.
🛑 Reshaped Aug 15, 2026 (round 6) after two independent reviewers found the original design's first-ever pass had two structural gaps, not just polish items — full history in the Decisions Log, summarized here since this box describes the CURRENT design.
  1. [Codex, HIGH] "Deleting" summer-2026 could never actually stick. loadConfig() (firebase-data.js:58-74) unconditionally auto-recreates the summer-2026 config entry on every load if it's missing, and loadLessonData() always regenerates its lessons via loadSummerCampData(). async function deleteSemester(key) {
  const sem = currentConfig?.semesters?.[key];
  if (!sem) return;
  if (key === currentConfig.activeSemester) {
    alert('Cannot delete the active semester.');
    return;
  }

  const isSummer = key.startsWith('summer-');

  if (key === 'summer-2026') {
    // loadConfig() unconditionally auto-recreates exactly this key on every
    // load (firebase-data.js:58-74) — deleting its config entry is
    // unwindable by design, not a bug to route around. Reframed honestly as
    // clearing its saved content instead of pretending to delete a semester
    // that can't actually be removed — found Aug 15, 2026 (round 6).
    if (!confirm(`Clear all saved lesson plans for "${sem.name}"? Summer 2026 is this studio's ongoing summer semester and can't be removed from the semester list — it will remain, and will regenerate its lesson slots from the camp schedule as usual. This only clears its SAVED lesson content (teacher notes, project details, Q&A threads, etc.) so it can be planned fresh. This cannot be undone.`)) return;

    const cleanupErrors = await clearSummerLessonContent(key);
    renderAdminGrid();
    renderHelpQueue();
    if (cleanupErrors.length > 0) {
      alert(`Some of "${sem.name}"'s saved content could not be cleared: ${cleanupErrors.join(', ')}. Check the console for details and consider a manual cleanup.`);
    } else {
      alert(`"${sem.name}"'s saved lesson content has been cleared.`);
    }
    return;
  }

  if (!confirm(`Delete semester "${sem.name}"? This will remove its lesson data. This cannot be undone.`)) return;
  if (!confirm(`Are you sure? Type OK in your head and click OK to confirm.`)) return;

  // original design had no try/catch around saveConfig() at all, so a
  // failure there left the in-memory config mutated (semester looked deleted
  // locally) while Firestore's config doc still had it, with no alert of any
  // kind — the opposite of this phase's own "surface failures" purpose.
  const semesterBackup = currentConfig.semesters[key];
  delete currentConfig.semesters[key];

    await saveConfig(currentConfig);
  } catch (e) {
    currentConfig.semesters[key] = semesterBackup;
    console.error('Could not save config after removing semester', key, e);

    return;

    // (summer-2026 is handled entirely above, before this point). Still
    // routed through the same real-enumeration cleanup, since summer camp

    // pre-existing characteristic, not introduced here. If a second
    // summer-type semester is ever created, its content and summer-2026's
    // are the same shared pool; clearing one clears both. Accepted, the same
    // way other data-model-scope limits are accepted elsewhere in this doc.

    try {
      await deleteLessonData(key);
    } catch (e) {
      console.error('Could not delete lesson data for', key, e);
      cleanupErrors.push('lesson data could not be fully removed');
    }
  }

  // Aug 15, 2026 (round 6, both reviewers): the original design dropped 3 of
  // today's 6 post-delete re-renders (Cut Bank, Idea Bank, Change History),
  // contradicting its own BDD claim that the success path was unchanged.

  renderAdminGrid();
  renderHelpQueue();
  renderCutBank();
  renderIdeaBank();
  renderChangeHistory();

    alert(`"${sem.name}" was removed from the semester list, but ${cleanupErrors.join(', ')} — some content may still exist in Firestore under this semester's old key. Check the console for details and consider a manual cleanup.`);
  }
}

async function clearSummerLessonContent(key) {
  if (!curriculumDb) initCurriculumFirestore();
  const cleanupErrors = [];

  let lessonKeys = [];
  try {
    const snap = await curriculumDb.collection('summerCamps_lessonData').get();
    lessonKeys = snap.docs.map(d => d.id);
  } catch (e) {
    console.error('Could not enumerate summer lesson data for', key, e);
    return ['saved lesson content could not be enumerated — nothing was removed'];
  }

  if (lessonKeys.length > 0) {
    let deletedCount = 0;
    try {
      for (let i = 0; i < lessonKeys.length; i += 500) {
        const batch = curriculumDb.batch();
        const slice = lessonKeys.slice(i, i + 500);
        slice.forEach(docId => batch.delete(curriculumDb.collection('summerCamps_lessonData').doc(docId)));
        await batch.commit();
        deletedCount += slice.length;
      }
    } catch (e) {
      console.error('Could not delete summer lesson data for', key, e);
      // Reports what's actually still undeleted, not the original total —
      // found Aug 15, 2026 (round 6): an earlier committed batch shouldn't
      // be double-counted as a failure if a later batch is what threw.
      cleanupErrors.push(`${lessonKeys.length - deletedCount} of ${lessonKeys.length} summer lesson document(s) could not be removed`);
    }
  }

  // Q&A queue entries share the same document IDs as summerCamps_lessonData
  // (both keyed by encodeFirestoreKey(lessonKey)) — clear the matching ones
  // so a removed lesson doesn't leave a stale unread-message banner behind.
  try {
    const qSnap = await curriculumDb.collection('summerCamps_prepHelpQueue').get();
    const qKeys = qSnap.docs.map(d => d.id).filter(id => lessonKeys.includes(id));
    for (let i = 0; i < qKeys.length; i += 500) {
      const batch = curriculumDb.batch();
      qKeys.slice(i, i + 500).forEach(docId => batch.delete(curriculumDb.collection('summerCamps_prepHelpQueue').doc(docId)));
      await batch.commit();
    }
  } catch (e) {
    console.error('Could not delete summer Q&A queue entries for', key, e);
    cleanupErrors.push('some Q&A queue entries could not be removed');
  }

  return cleanupErrors;
}

Phase 17 — Cut Project: forced-server read before archive-and-delete (cutProject)

🛑 Found Aug 15, 2026 (round 6) by the completeness sweep re-run — a genuinely new, live, unaudited instance of the same vulnerability class this whole plan exists to close, not a dead-code finding like the two already named in "Not in scope." cutProject(key) (app.js:4885-4943), wired to a real "Cut" button inside openDetailModal() (app.js:4351), reads the lesson to archive from currentLessonData[semKey][key] — the local cache, not a forced server read — builds the Cut Bank archive entry from that snapshot, then unconditionally calls deleteLessonKey(semKey, key), a raw dotted-path delete that bypasses both saveLessonData() and saveSingleLesson() entirely. This function's two sibling call sites for the same underlying delete — move and swap-with-empty — both copy content to a new destination FIRST, with read-back verification for move, before ever deleting the source (Phase 1). cutProject() has no equivalent protection at all: nothing verifies the local snapshot matches what's actually in Firestore before it's archived, and nothing verifies the doc still exists before it's deleted.
🛑 Concrete failure scenario, confirmed by tracing the real code, not hypothetical. openDetailModal() is the same long-lived, non-live-refreshing popup that motivated Phase 9's existence check for saveAdminEdit() and Phase 11's for sendHelpResponse()/sendQaReply(), for the identical reason — it stays static once opened, with no listener refreshing it.
