🛑 Critical, found during second-model review: the summer and non-summer save paths have different Firestore write semantics, and this phase's original design ("narrowing a payload is strictly safer") was only true for one of them. Summer's saveSingleLesson (firebase-data.js:672) uses .set(cleanData, { merge: true }) — a document-level merge where omitting a field genuinely leaves it untouched. Non-summer's saveSingleLesson (firebase-data.js:683-685) does curriculumDb.collection('curriculum').doc('lessonData').update({ [fieldPath]: lessonData }) where fieldPath = semesterKey + '.' + lessonKey — Firestore's update() only protects sibling data at dotted-path segments you don't mention; the object value supplied for the path you do mention fully replaces whatever was there. A narrowed or stripped lessonData object at that path deletes every field it omits — the exact failure this whole plan exists to stop. Both 2C and 2D must target the non-summer path with explicit per-field dotted paths, never a partial object assigned to the bare semesterKey.lessonKey path.

What it does

After every summer-path saveSingleLesson write, read the doc back and confirm the content fields that were supposed to change actually landed. If any expected field reads back missing or empty, surface an error to the teacher within seconds — this is the single change that would have caught both original May 2026 wipe incidents immediately instead of days later.

🛑 Must force a server read, found during second-model review: js/firebase-data.js uses the v8-compat Firestore SDK throughout. A default .get() immediately after a write can resolve from local cache, which reflects the pending write optimistically regardless of whether it ever reached the server — a cache read here could report "confirmed" on a write that never actually persisted, defeating the point of this phase. The read-back (and its retry, below) must explicitly use get({ source: 'server' }). This codebase already treats cache-vs-server as a real distinction elsewhere (setupLessonDataListener, firebase-data.js:511-515, explicitly skips cache-only snapshots) — follow that precedent here.
Given: A teacher saves real content to introPitch and processStep1 When: The read-back runs immediately after the write, forcing a server read Then: Both fields are confirmed present and non-empty in the read-back AND the teacher sees the normal "✓ Saved" indicator with no extra friction Given: A write silently fails to persist a field (simulated in test by writing then externally clearing the field before read-back) When: The server-forced read-back detects the mismatch Then: The teacher sees an explicit error naming which field(s) may not have saved, within the same save flow — not a generic "saved" that's actually wrong Given: The write itself succeeded, but the read-back call fails for an unrelated reason (transient network blip immediately after) When: The first server read-back fails Then: Retry once, also forced to the server (a retry that reads from cache verifies nothing) AND if the retry also fails, show a soft "couldn't confirm save, check your connection" message — not a silent success, and not a hard wipe-alarm, since the underlying write most likely did succeed AND log both attempts to console either way

Context — Vulnerability #11 reopened (Phases 7–8, Layer 1)

Both lesson editors (saveTeacherEdit() for non-summer, saveLesson() for summer camp) build their Firestore write payload from every currently non-empty field in the open form, not just the field(s) the user actually typed into this session. Neither modal re-syncs its open form against live Firestore data while it's open — a live re-sync mid-typing would risk clobbering the user's own in-progress edit, so the form is effectively a point-in-time snapshot for as long as it stays open.

Concrete failure: Teacher A and Admin B both open the same lesson. Both load processStep1: "Old step 1". B edits processStep1 → "New step 1" and saves; Firestore now has "New step 1". A, still viewing their now-stale-loaded form, edits only projectTitle — never touching processStep1 — and saves. A's save payload still includes A's stale copy, processStep1: "Old step 1", because the payload is built from "every non-empty field currently in the form," not "every field this user changed." B's edit is silently reverted, even though A never opened that field.

Why this wasn't caught by this plan's own Phase 1–6 reviews: Vulnerability #11 was marked "deferred, not in scope" (see "Not in scope" below) before Phase 1 had even started. Every later second-model-review in Phases 1–6 was scoped to verifying the specific phase under execution. None were asked to re-derive Vuln #11 from the actual code, because it had already been closed as a scoping decision — a review only re-examines what it's pointed at. The "same-instant race" framing that closed it also didn't name the actual mechanism above, so there was no prompt to look again. Worth remembering for future plans: an "out of scope" decision made before the relevant code exists (or before anyone has traced the actual mechanism) can go unexamined by every subsequent review indefinitely.

What it does

Bypass saveSingleLesson() entirely for this save — the same pattern this codebase already uses for photo fields (a direct, targeted dotted-path update() call) — and append the new message via Firestore's arrayUnion() instead of a local read-modify-write, so two concurrent senders can't overwrite each other regardless of timing.

⚠️ Two fixes to this snippet since the last review round, Aug 14, 2026:
  1. Generated message ID (Codex's non-blocking note, now applied). The original draft relied on each message's timestamp alone for uniqueness. arrayUnion() de-duplicates array entries by deep equality — a timestamp string only has millisecond resolution, so two different real messages sent in the same millisecond (plausible on a fast connection, e.g. an admin and a teacher both hitting Send right after a page load race) could theoretically collide if every other field also matched, silently merging into one entry. Each entry now carries an id, generated the same way this codebase's existing Idea Bank feature already does (app.js:5317, Date.now().toString(36) + Math.random().toString(36).substr(2, 5) — matched to house style rather than introducing crypto.randomUUID() as a second, inconsistent convention for the same purpose).
  2. Legacy-thread migration gap — found while designing Phase 11 below, real, not previously caught by any prior review pass. getQaThread(lesson) (app.js:6678) only falls back to the old teacherNotes/adminResponse fields when lesson.qaThread is absent or empty — once qaThread has one real entry, those legacy fields are never read again by anything. Today's shipped code (being replaced by this phase) calls getQaThread(lesson), pushes onto it, and writes the whole resulting array back — so a legacy-only lesson's first message under today's code silently migrates its synthesized legacy thread into a real qaThread array. A bare arrayUnion(newEntry), as originally drafted for this phase, does not do that migration — it just creates a brand-new one-entry array, permanently losing whatever legacy messages getQaThread() was synthesizing for that lesson. Fixed below via a small shared helper, reused by Phase 11.
// Shared by sendTeacherQaMessage (here) and sendQaReply (Phase 11) — both need
// to seed arrayUnion's argument list with the synthesized legacy thread on a
// lesson's first message under this atomic-append pattern, or those legacy
// messages are silently lost the moment qaThread gets its first real entry
// (see the note above). arrayUnion's deep-equality dedup makes repeating this
// migration from two concurrent senders safe: identical legacy entries
// collapse to one, and new entries (each carrying a generated id) never
// collide with each other or with the migrated legacy ones.
function buildQaThreadUnionArgs(existingLesson, newEntry) {
  const needsMigration = !existingLesson?.qaThread || existingLesson.qaThread.length === 0;
  return needsMigration ? [...getQaThread(existingLesson || {}), newEntry] : [newEntry];
}

async function sendTeacherQaMessage(lessonKey, lesson) {
  const input = document.getElementById('te-qa-input');
  if (!input) return;
  const message = input.value.trim();
  if (!message) return;

  const user = getAuthUser();
  const isAdmin = ['admin', 'manager'].includes(user?.role);
  const newEntry = {
    id: Date.now().toString(36) + Math.random().toString(36).substr(2, 5),
    from: isAdmin ? 'admin' : 'teacher',
    name: user?.name || 'Unknown',
    message,
    timestamp: new Date().toISOString()
  };

  const semKey = getTvSemKey();
  // Read-only use of the local cache, just to decide whether legacy migration
  // applies — never spread into the Firestore payload itself, so staleness
  // here can't cause data loss (worst case: an unnecessary but harmless
  // re-migration, deduped by arrayUnion as explained above).
  const currentLesson = currentLessonData?.[semKey]?.[lessonKey] || lesson;

  try {
    // Firestore-bound payload — only the Q&A-related fields, never the full
    // stale `lesson`. qaThread appended via arrayUnion (atomic on Firestore's
    // side), not a local read-modify-write — this is why saveSingleLesson()
    // isn't used here: it JSON-round-trips its payload (firebase-data.js's
    // stripping/cleanData step), which would silently corrupt a FieldValue
    // sentinel like arrayUnion into a plain object. A direct update() call,
    // same as the existing photo-field pattern, avoids that entirely.
    if (!curriculumDb) initCurriculumFirestore();
    const updates = {
      [`${semKey}.${lessonKey}.qaThread`]: firebase.firestore.FieldValue.arrayUnion(...buildQaThreadUnionArgs(currentLesson, newEntry)),
    };
    if (!isAdmin) {
      updates[`${semKey}.${lessonKey}.teacherNotes`] = message;
    } else {
      updates[`${semKey}.${lessonKey}.adminResponse`] = message;
    }
    await curriculumDb.collection('curriculum').doc('lessonData').update(updates);

    input.value = '';
    openTeacherEditModal(lessonKey);
  } catch (err) {
    console.error('Error sending Q&A message:', err);
    alert('Error sending message: ' + err.message);
  }
}
