Phase 1 — Admin grid safety (Stage 2A + 2B)

What it does

2A (app.js, admin grid move, ~line 4578): After saveSingleLesson(semKey, newDestKey, movedLesson) succeeds, read back the destination doc. If the source lesson had real content but the destination read-back shows none, abort — do not delete the source. If the source had no content to begin with, proceed with the delete (not a false-positive block).

2B (app.js, admin grid swap, ~line 4596): Replace the single saveLessonData(semKey, lessons) bulk overwrite with two targeted saveSingleLesson() calls, one per swapped slot.

⚠️ Related finding from this session, not in the original vulnerability table: saveAdminEdit() (app.js, admin grid cell create/edit, ~line 4538) also ends with a full saveLessonData(semKey, lessons) bulk write — the exact same pattern 2B is fixing for swap, just on a different admin action. Decide during this phase whether it should also move to a targeted save, or whether editing one cell's full content genuinely needs the object it already builds in memory. Record the decision either way.
Given: An admin drags a lesson with real content from Week 3 to Week 5 When: The destination write completes and the read-back confirms matching content landed Then: The source lesson is deleted AND if the read-back shows no content at the destination despite the source having content, the move is aborted with an alert, and the source is preserved untouched Given: The lesson being moved is an empty scaffold slot (no content fields) When: The move completes Then: The source is still deleted — this is not a false-positive block, since there was nothing to lose Given: The destination write itself throws (network error, permission) When: saveSingleLesson rejects Then: The delete of the source never executes — verify this explicitly with a test, even though it's already true by control flow today Given: An admin swaps two lessons in the grid, one with real content and one empty When: The swap saves Then: Two targeted saveSingleLesson calls run — not a full-semester saveLessonData overwrite AND a canary lesson written to a third, unrelated slot before the swap is provably unchanged afterward
✅ Both fixes are additive verification/read-back before an existing delete, or a swap from one write shape to a narrower one. No schema change, no new collection.

Phase 2 — Save-path field safety (Stage 2C + 2D)

What it does

2C (app.js, Plan Complete checkbox, lines 2003 & 2449): Stop passing the full lesson object to saveSingleLesson. Pass only { planComplete, lastEditedBy, lastEditedAt }. This requires a guard update: saveSingleLesson's hasContent check currently blocks all-empty-content-field saves — add a bypass when the payload explicitly contains planComplete, so this narrower write isn't blocked by a guard meant for a different failure mode.

2D (firebase-data.js, non-summer saveSingleLesson, lines 558–569): Apply the same content-field stripping already live on the summer path — strip empty introPitch/processStep1–4/closure/dayOfMaterials before the update() call.

Given: A lesson has a real photoUrl, but the in-memory lesson object is stale (photoUrl blank from a failed load) When: An admin checks the Plan Complete checkbox Then: Only { planComplete: true, lastEditedBy, lastEditedAt } is written AND photoUrl in Firestore is untouched regardless of the stale in-memory value AND the hasContent guard does not block this write, because it explicitly recognizes a planComplete-only payload Given: A teacher saves real lesson content in the same session When: They separately check Plan Complete afterward (or vice versa) Then: Both saves land correctly — neither write shape clobbers fields the other one owns Given: A Spring/Fall (non-summer) lesson has real content in Firestore When: A save runs with some content fields empty in memory (stale load) Then: The non-summer path strips those empty fields before writing, exactly like the already-fixed summer path AND existing Firestore content in untouched fields survives unchanged — this is the direct regression test for Test 1/2's logic, applied to the other save path
✅ 2C narrows a write's payload (strictly less data sent). 2D copies an already-shipped, already-tested stripping pattern to a second code path. Neither changes the target collection or its rules.

Phase 3 — Post-save read-back verification (Stage 2E)

What it does

After every summer-path saveSingleLesson write, read the doc back and confirm the content fields that were supposed to change actually landed. If any expected field reads back missing or empty, surface an error to the teacher within seconds — this is the single change that would have caught both original May 2026 wipe incidents immediately instead of days later.

Given: A teacher saves real content to introPitch and processStep1 When: The read-back runs immediately after the write Then: Both fields are confirmed present and non-empty in the read-back AND the teacher sees the normal "✓ Saved" indicator with no extra friction Given: A write silently fails to persist a field (simulated in test by writing then externally clearing the field before read-back) When: The read-back detects the mismatch Then: The teacher sees an explicit error naming which field(s) may not have saved, within the same save flow — not a generic "saved" that's actually wrong Given: The write itself succeeded, but the read-back call fails for an unrelated reason (transient network blip immediately after) When: This is decided during execution Then: [decision needed — do not let a flaky read-back falsely alarm a teacher about a write that actually succeeded; likely resolution: one silent retry of the read-back before surfacing an error, log to console either way]
Doubles Firestore reads on every save. Cost is trivial at this app's scale (~100 saves/day per the original plan doc) — explicitly accepted, not a concern to re-litigate during execution.

Phase 4 — Intentional field clear support (Stage 3)

What it does

The Stage 1 stripping fix protects against accidental overwrites but also silently blocks intentional clears — today, deleting all text from a field and saving does nothing; the old content reappears on reload with no explanation. Track which content fields had text when a modal opened (the non-summer modal already does this via teOriginalData; the summer modal needs the same tracking added). At save time, a field that was non-empty at open and is now empty is an intentional clear — use Firestore's FieldValue.delete() for it instead of omitting it from the payload.

Given: A lesson has real content in processStep2 when the modal opens When: A teacher deletes all the text in processStep2 and saves Then: FieldValue.delete() is used for processStep2 (not silent omission) AND a brief confirmation ("processStep2 cleared") appears, so the behavior is visible rather than silent AND on reload, processStep2 is genuinely empty — the old content does not reappear Given: A lesson has an already-empty processStep3 when the modal opens (never filled in) When: A teacher saves without touching processStep3 Then: Nothing is deleted — it was empty at open, so this is not a "clear," just an untouched empty field AND existing Stage-1 stripping behavior for never-filled fields is unchanged
Requires open-state snapshotting in the summer modal, which doesn't exist yet (non-summer modal already has it). This is the most UX-sensitive phase — get the confirmation copy right so a genuine clear reads as confirmed, not alarming.

Phase 5 — Detection and monitoring (Stage 4)

What it does

4A: Admin dashboard section showing, per teacher, how many lesson docs have content today vs. yesterday's backup count — red highlight on an unexplained drop.

4B: Backup health surfaced in-app. Reconcile with what already exists: the Firebase Backend Resilience plan's Step 1 (completed Aug 11, 2026) already built managed daily cloud backups with the tinker-hq-vault project and email alerting — this phase should read from / link to that instead of re-inventing a local-log-only health check.

4C: Extend logTeacherEdit's existing field-change audit to record character counts ({ field, before, after }), flagging after: 0 && before > 50 as a potential wipe, visible in the admin change-history view.

Given: A save changes introPitch from 250 characters to 0 When: logTeacherEdit records the change Then: The audit entry is flagged as a potential wipe (after:0 && before>50) AND this flag is visible to admins in the existing Change History view, not a separate hidden log Given: The content-count dashboard loads Then: It shows each teacher's today's content count next to yesterday's backup-derived count AND only an unexplained drop is red-highlighted — a drop matching a known curriculum change (e.g. a class was intentionally cut) is not falsely flagged

Phase 6 — Expand test coverage (Stage 5)

What it does

Add Playwright tests for Phases 1–5, extending e2e/data-safety.spec.js:

  • Admin move aborts and preserves source when destination read-back shows no content
  • Admin swap writes correct content to both slots via two targeted saves; unrelated canary lesson is untouched

Firebase Safety Checklist

  • Rules: No new collections introduced by Phases 1–4 or 6. If Phase 5's backup-health display (4B) ends up needing a new Firestore path (rather than reading the resilience plan's existing cloud infra), add its rule in the same commit per this app's CLAUDE.md convention.
  • updateDoc, not setDoc: All phases use saveSingleLesson's existing targeted merge pattern. None introduce a full-document .set() — Phase 1 specifically removes the one remaining bulk-write path in the swap action (and possibly the admin-edit path, per the Phase 1 decision).
  • Empty fields stripped: Phase 2's 2D is exactly this requirement, extended to the second (non-summer) save path.
  • Snapshot before bulk ops: No bulk delete/import in this plan. Phase 1 testing against real semester data should still snapshot first per this app's standing invariant.
  • Emulator/Playwright test before each write-touching phase ships: required by this app's own AGENTS.md and CLAUDE.md — Phases 1, 2, 3, and 4 each need a red test proving the gap before the fix, matching how Stage 1C's Test 6 was rewritten this session after it was found to never actually exercise the bug.

Completeness Check — mid-plan interruption

Each phase is independent and additive — none require a later phase to be functionally complete. If work stops after any phase, the app is left in a fully working, deployable state with strictly fewer known risks than before that phase started. There is no partial-phase state that leaves the app broken; a phase either ships complete (code + test + commit) or hasn't started.

Not in scope

  • Concurrent-session conflict detection (Vulnerability #11, "last write wins"). Explicitly Stage 4 in the original plan doc's own numbering but low-risk (single small team, low collision likelihood) — deferred past this plan; revisit only if reported as an actual incident.
  • Migrating the non-summer semester's single-giant-document lesson storage to per-lesson documents (matching summer's summerCamps_lessonData collection shape). Would reduce blast radius further but is a real data migration outside this plan's scope — the fixes here work within the existing document shape.
