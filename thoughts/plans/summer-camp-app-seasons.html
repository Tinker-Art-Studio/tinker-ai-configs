1.4 Deterministic document IDs — the cross-app contract

Steps, each resumable, progress always recomputed from a server scan (the backfill field on the season doc is advisory):

  1. Dry run (read-only): reads every per-season collection whole from the server, counts docs with and without season, shows the table ("curriculum: 48 to stamp, 0 stamped"; kid notes split by importYear 2025/2026). Nothing proceeds until the counts look right.
  2. Backup gate: reads backupStatus/latest.lastSuccessAt (an ISO string, admin-readable) from the server and refuses unless it is within the last 10 minutes — the scheduled backup already runs every 30 minutes, so a 30-minute window would not prove a deliberate node ~/tinker-backups/backup.js --force ran; no typed timestamp. Re-checked on every run that will stamp (a resume included), not only when the card opens. The seen value is recorded as backfill.backupSeenAt.
  3. Season doc: summerCamps_seasons/2026 created from APP_CONFIG in a transaction. If it already exists (a resumed run), its immutable seed fields (dates, numWeeks, weekStructure, breaks, week1Monday) are compared with the seed: identical → continue without writing; different → stop loudly and show the diff (never overwrite a registry). Creating it does not switch filtering on — only _current does (step 6).
  4. Stamp: per per-season collection, batches of ≤400 awaited update({ season }) ops (kid notes: String(importYear || 2026); all else '2026'), only for docs the server scan classifies as missing. The scan classifies every doc as missing / valid (the exact string '2026', or '2025' on a 2025-imported kid note) / invalid (anything else — a number, null, an unexpected year); invalid docs are listed explicitly and block switch-on until resolved by hand. update() touches nothing else, so lastUpdated/updatedAt don't move. A batch that fails with NOT_FOUND (a doc deleted between scan and commit — a material delete, the Classbook's orphan cleanup) is re-scanned and retried, not surfaced as fatal. A closed tab mid-way loses nothing: each batch is atomic, and the next run's scan finds exactly what's left.
  5. Verify: a fresh server scan; every collection must be 100% valid with zero missing and zero invalid. Counts are compared with the latest dry run: a rise is informational (the Classbook is live — a saved lesson or a kid note is a new, stamped doc), a drop refuses and names the collection.
  6. Switch on: only now, _current = { season: '2026', setAt, setBy } (transaction; abort if present). The button then reads "Done — Summer 2026 is set up".

After switch-on the card keeps one action, permanently: "Re-scan & stamp stragglers". Teachers keep the Classbook open for days and it has no cache-busting or reload prompt (tinker-spring-curriculum/index.html:477-480); a pre-patch tab can still write an unstamped campComplete/prepHelpQueue/lessonData doc after step 6 (and a pre-deploy Summer Camp App tab an unstamped kid note), which the filtered reads would then hide — the same "data disappeared" class this plan exists to prevent. The action is steps 1 + 4 + 5 restricted to missing docs, and it is exempt from the backup gate (it only adds season via update() to docs the scan lists as missing — a fresh --force backup for every sweep would make the sweep less likely to be run); the season is parseDocId(id).season for computed-ID collections and, while 2026 is the only season, '2026' for the rest (once a second season exists an unstamped auto-ID straggler is ambiguous and the sweep lists it for a manual choice instead). Rollout also leaves several days between the Classbook patch deploy and step 6 so open tabs cycle. (Round 2, both reviewers. A stricter alternative — a rules condition denying any unstamped create/update in all 14 collections — is recorded as a possible Phase 2+ hardening, not Phase 1.)
