Plan: Summer Camp App Seasons — start Summer 2027, carry forward select camps

Goal: In the Summer Camp App, Christie can start a new summer the way she starts a semester in the Classbook — create "Summer 2027" with its own dates and week structure, carry forward the camps she chooses from 2026 (now, or one at a time later), plan 2027 while 2026 stays intact as history, and publish 2027 camps to the Classbook when ready.
App: summer-camp-app (Summer Camp 2026) — js/app.js, js/config.js, index.html. Consumer: tinker-spring-curriculum (The Classbook) via classbook-camp-seasons.html.
Context: Created Sep 20, 2026. Christie: "I build all backend summer info in [the Summer Camp App], and then publish it to classbook … I would need to be able to set a new summer in the Summer Camp app, similar to how I do in the classbook with new semesters. But I'd want to be able to copy select Summer Camps into the next year, and/or toggle them into the upcoming year at a later date too." This plan therefore owns the season — its creation, the shared-collection backfill, and carry-forward. The Classbook plan becomes the consumer side and depends on this one.
Risk: MEDIUM-HIGH — 17 collections become season-aware; a backfill of every existing doc; carry-forward copies documents between seasons (the classic place for duplicates or a copy that silently overwrites). Every data-write phase gets the full data-safety process (red test on real Firestore, dual implementation review, Console spot-check).
execution-ready: false — Scoping: research done, decisions open (D1–D7).

Context — what the app is today

  • Single-season by construction. js/config.js APP_CONFIG: appName: 'Summer Camp 2026', startDate: '2026-05-26', endDate: '2026-08-11', numWeeks: 11, and a hard-coded weekStructure (days off, notes, date ranges per week) with 17 consumers in app.js. Date pickers in index.html are bounded to 2026.
  • Camps come from Google Sheets. APP_CONFIG.sheetGIDs (campTopics, campSessions, masterCurriculum, projectDetails, materialsByTopic, needToOrder, prepHelpQueue, teacherHelpQueue) feed imports into Firestore; camp docs are then edited in-app (saveCampOverride() etc.). A "new summer" therefore means: a 2027 sheet (or a season-tagged import) plus in-app editing — not a blank "create camp" form today (D2).
  • 17 summerCamps_* collections, all with Firestore rules already: curriculum, schedule, lessonData (shared with the Classbook), projectDetails, materialsHub, needToOrder, stockItems, prepHelpQueue, weeklyPrep, campComplete, openStudio, kidNotes, notesNextYear, daysOff, team, projectLibrary, settings. None carries a season/year field (verified on real docs Sep 20: curriculum 48 docs, schedule 229 docs — no year anywhere) — except Kid Notes and Notes-for-Next-Year, which already have a 2025/2026/All year toggle in the UI (index.html:603-606), so a per-year concept exists in two places and can be generalized rather than invented.
  • Publish to Classbook sets publishedToClassbook: true (+ publishedToClassbookAt) on camp/project docs (app.js:~12065-12141); the Classbook reads every camp doc and shows the published ones. Without a season, a published 2027 camp would appear inside the Classbook's Summer 2026.
  • What "copy a camp" has to carry: the camp's curriculum doc (campTopic, teacher, blocks with Monday–Friday project titles, age range, bins, notes, preset projects), its project details (per project), its materials (materialsHub entries keyed campTopic|||project). What it must not carry: schedule/sessions and enrollment (2027 has its own schedule), campComplete flags, kid notes, prep-help queue items, needToOrder — and, by default, teachers' 2026 lesson plans (D3b).

Decisions Christie needs to make (D1–D7)

D1 — Season lives as a season field on every doc (recommended; mirrors the Classbook plan's D1 option a). Values '2026', '2027'… Existing docs backfilled to '2026' once. No new collections → no Firestore rules change. Alternatives (per-season collections; archive-and-reuse) are rejected for the reasons in classbook-camp-seasons.html D1. Confirm.
D2 — How is a season created and populated? Proposed: a Seasons panel in Settings: create "Summer 2027" (name, start/end dates, week structure — the same shape as today's hard-coded weekStructure, editable), stored in summerCamps_settings (one doc per season) with a currentSeason pointer. Populating it: (a) carry forward select 2026 camps (D3), and/or (b) import from a 2027 Google Sheet — the import stamps season from the season you're viewing. Do you still want sheet import as a way to bring in new camps, or should 2027 be "carry forward + edit in app" only?
D3 — Carry-forward semantics. Proposed: copy, never move. "Carry forward to 2027" creates a 2027 copy of the camp's curriculum doc + project details + materials; 2026's docs are untouched. Reset on copy: publishedToClassbook (false), publishedAt/By, curriculumStatus, completeOverride, needsAttention; keep: everything curricular. Idempotent: carrying the same camp forward twice is a no-op with a "already in 2027" message (each copy records carriedForwardFrom: <2026 doc id>). Offered in two places: a multi-select "carry forward" step when creating the season, and a per-camp button/toggle in the 2026 view later. Christie's "toggle them into the upcoming year" — is a toggle that performs the copy (and shows "in 2027 ✓") what you mean, or do you want a camp to literally belong to two seasons at once?
D3b — Teachers' 2026 lesson plans on carry-forward? (a) Don't copy — teachers start 2027 plans fresh (recommended default: plans are per-teacher, teachers change, and Classbook's per-season lesson keys keep 2026 plans readable as reference); (b) offer a checkbox "include last year's plans as drafts" that copies summerCamps_lessonData docs for that camp into 2027 keys. (b) is easy to add later; deciding (a) for v1 keeps Phase 3 smaller.
D4 — What does "current season" control, and how do you look at 2026 afterwards? Proposed: currentSeason decides what the app opens to and what new writes are stamped with; a season switcher (like the Kid Notes year toggle, but app-wide) lets admins view/edit any season. Past seasons stay fully editable (no "archive lock") unless you want one — should 2026 become read-only at some point?
D5 — Which collections are per-season vs shared across years? Proposed per-season: curriculum, schedule, lessonData, projectDetails, materialsHub, needToOrder, prepHelpQueue, weeklyPrep, campComplete, openStudio, kidNotes (already has year), notesNextYear (already has year), daysOff. Proposed shared (no season): team, projectLibrary (that's its point — cross-year reuse), stockItems (studio inventory), settings (holds the seasons themselves). Confirm, especially stockItems and team.
D6 — Week structure per season. Today's weekStructure (11 weeks, Memorial Day short week, the Jun 29–Jul 3 break) moves from config.js into the season doc, edited in the Seasons panel. 2027's calendar is entered when the season is created (dates can be edited later). Any other per-season constants you know of — e.g. camp time slots, studios?
D7 — Classbook handoff. Publishing a 2027 camp to the Classbook stamps season: '2027' (it already carries the field from D1); the Classbook's own seasons plan (Phase 3) filters by it. Nothing else changes in the handoff. Sequencing: this plan's Phases 1–2 must land before the Classbook can show 2027 camps; the Classbook's Phase 1 (explicit semester types) can proceed independently.

Full existing e2e suite green; before/after screenshot pass of the main tabs; the Classbook is unaffected (it doesn't filter yet and sees the same docs).

Given: the backfill has run When: a read-only scan groups every per-season doc by season Then: 100% carry season '2026', doc counts per collection are unchanged, and no doc's lastUpdated/updatedAt moved (the backfill sets only the season field via updateDoc) Given: Christie edits a camp, adds a kid note, and marks a camp complete after Phase 1 When: those writes land Then: each new/updated doc carries season '2026' — the app never writes an unstamped doc again Given: the backfill is interrupted part-way When: it is re-run Then: only unstamped docs are touched; the end state equals an uninterrupted run

This is the ONE backfill for both apps — the Classbook plan's former Phase 2 is folded in here, since this app is the writer of record.

Acceptance: when creating 2027 (or any time after, from the 2026 view), Christie can pick camps to carry forward; each gets a 2027 copy of its curriculum doc, project details and materials with the D3 fields reset; 2026's docs are byte-identical before and after; carrying the same camp forward twice does nothing and says so; a carried-forward camp shows where it came from; per-camp "Carry forward to 2027 ✓" state is visible in the 2026 list.

Completeness check — what if this is interrupted?

  • Mid-Phase 1 backfill: unstamped docs are treated as 2026 by both apps; re-run to finish. Safe indefinitely.
  • After Phase 1: the app is identical to today with a season field everywhere. Safe indefinitely.
  • After Phase 2, before 3: 2027 exists but is empty; Christie can start typing camps in by hand (or import) — usable.
  • Mid-Phase 3 (partial copy): designed to be resumable per camp; nothing in 2026 is ever modified by carry-forward, so the worst case is an incomplete 2027 camp that a re-run completes.
