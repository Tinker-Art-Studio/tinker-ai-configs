1.3 One data-access layer — js/season.js

Loaded after config.js, before auth.js/app.js. Written UMD-style with db injected (the pattern wip/step4-data-safety's data-safety.js uses) so the same module runs in the browser and under the emulator tests.

Season.load(db) // forced-server read of _current (+ its season doc); resolves to one of three states, see 1.6 Season.current() // '2026' — throws if load() hasn't completed (never a silent default) Season.doc() // the current season's registry doc (dates, weekStructure, timeSlots, studios, …) Season.query(key) // per-season key → CollectionReference.where('season','==', current) (a Query: get/onSnapshot only) Season.query(key, { seasons: 'all' }) // kidNotes / notesNextYear: unfiltered Season.ref(key) // the CollectionReference itself — for .doc(id) reads/updates and .add() — callers MUST stamp what they create Season.ref(key).doc(Season.docId(legacyId)) // computed IDs go through docId() (1.4) Season.stamp(payload, season?) // sanitize (see below) + { ...payload, season } — REQUIRED for every set()/add()/batch.set() on a per-season ref, merge or not Season.patch(payload) // sanitize + strips `season` — for update()/batch.update() (an edit never moves a doc between seasons) Season.docId(legacyId, season?) / Season.parseDocId(docId) → { season, legacyId } // 1.4 Season.raw(name) // the audited escape hatch: unfiltered CollectionReference for the migration and the Step 4 guard only Season.assertWritable(season) // Phase 2 hook (D4 read-only past seasons) — a no-op in Phase 1

Sanitizer: one function, used by stamp() and patch(): drops undefined; keeps null, false, 0, empty arrays and FieldValue sentinels (schema-significant — e.g. completedBy: '' in weeklyPrep is a real value the UI relies on); empty strings are kept where the existing code writes them deliberately and the review found no reader that breaks on them — this matches today's behaviour and does not attempt to fix the app's pre-existing merge-set() partial edits (Open Studio, app.js:13912-14152), which are named here as out of scope rather than silently inherited.

Every one of the 155 call sites (handoffs/sca-seasons-phase1-sites.txt) is converted: whole-collection and filtered reads → Season.query(...); .doc(id) reads and update()s → Season.ref(...) + Season.patch(); every add() / set() / batch.set() → payload through Season.stamp() whether or not it is a "new" doc and whether or not it merges — this is what protects saveSessions() / saveTopics() (app.js:8430-8454, batch.set on sheet IDs with no merge: a re-import would otherwise strip the stamp from all 229 schedule docs), publishCamp()'s weeklyPrep set (:10639) and the Open Studio merge-sets on first write. Equality-only queries gain the season filter with no new index (Firestore index merging; the review confirmed every where() in the app is equality-only and there are no in/array-contains/range/collectionGroup queries). The only per-season collection queried with orderBy that also gets the filter is daysOff (4 sites) → drop the orderBy('date') and sort client-side, with exact-order tests; kidNotes and notesNextYear keep their orderBy because they are read unfiltered (D8b narrowed).

Completeness is enforced, not hoped for: a static test (an AST walk over every JS file the page loads — app.js, auth.js, any future module — not a regex over one file) fails on: any db.collection(...) / collection('summerCamps_…') naming a per-season collection outside season.js; any .set(/.add(/batch.set( on a Season.ref() whose payload isn't Season.stamp(...); any .update(/batch.update( whose payload isn't Season.patch(...); any onSnapshot or collectionGroup on a per-season name outside Season.query(). In non-production (localhost) Season also wraps db.collection to throw on a raw per-season access, so a missed site fails loudly in development. 1.4 Deterministic document IDs — the cross-app contract

Most per-season docs have auto IDs, so 2027 docs can never collide with 2026 ones. Five collections use computed IDs that would collide the moment a 2027 camp shares a name with a 2026 one (the review confirmed this is the complete set): lessonData (teacher|||camp|||block|||project, written by the Classbook), campComplete (teacher|||campName — corrected; written by the Classbook, firebase-data.js:442-445), prepHelpQueue (the lesson key, Classbook), openStudio (week_{n}, app.js:13347-14152) and weeklyPrep ({campTopic}_week{n}, app.js:10637). Rule, shared by both apps: 2026 keeps every existing ID unchanged; any other season prefixes the entire legacy ID with {season}|||, applied after the legacy ID is fully formed (after encodeLessonKey() / whitespace replacement — e.g. 2027|||Fired_Up!_week3, 2027|||week_3). parseDocId() is the inverse (a doc ID whose first ||| segment is a 4-digit year is prefixed; anything else is a 2026 legacy ID). No 2026 doc is ever renamed. Round-trip tests for all five, including project names containing / and |||-adjacent characters.

Classbook side of the contract (recorded in classbook-camp-seasons.html as hard dependencies): (a) its summer loader uses the decoded doc ID directly as the in-memory lesson key (firebase-data.js:1227-1235) — it must strip the prefix via parseDocId() before matching; (b) it reads campComplete by teacher and prepHelpQueue whole using data fields, not IDs (firebase-data.js:429-435, app.js:3445, 3472), so any 2027 doc of those two types would leak into its 2026 view until its own seasons filter lands — therefore this plan's Phases 3–4 must not write 2027 campComplete/prepHelpQueue/lessonData docs until the Classbook seasons Phase 1 is live. Nothing in the Classbook parses summer doc IDs today (its two split('|||') sites are regular-semester keys), and encodeFirestoreKey() only touches /, so the prefix is safe to introduce.
