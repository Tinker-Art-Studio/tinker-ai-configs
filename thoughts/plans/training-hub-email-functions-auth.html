Goal: only a signed-in, active Training Hub manager (role manager or admin) can make Training Hub send an email. A request from anyone else gets a 401/403, and no mail goes out.
Why: today any request that reaches these endpoints sends mail from training@tinkerartstudio.com to any address, CC'ing Christie, and nothing checks who asked.

Approach: recommended option A (no new secrets)

One shared module, netlify/functions/_lib/requireManager.ts, is called first in each of the three handlers, before the body is parsed or the API key is read. Doing all three in one commit matters: fixing one leaves two open while the work looks finished.

  1. Verify the Firebase ID token from Authorization: Bearer <idToken> using jose (one small dependency with no sub-dependencies; it runs on Netlify's Node runtime).
    • The keys come from Google's public JWKS: https://www.googleapis.com/service_accounts/v1/jwk/securetoken@system.gserviceaccount.com via createRemoteJWKSet, cached by jose.
    • Check algorithms:['RS256'], iss = https://securetoken.google.com/tinker-hq-apps and aud = tinker-hq-apps. jose handles exp and nbf; iat and auth_time are checked explicitly (both numeric and not in the future). sub must be a non-empty string of at most 128 characters and must not be the reminder-bot uid (D3).
    • The project id is a constant in code, not an env var, so a mis-set variable can't point verification at another project.
  2. Check the role against Firestore, rules-enforced.
    • The function makes a GET https://firestore.googleapis.com/v1/projects/tinker-hq-apps/databases/(default)/documents/users/{sub} carrying the caller's own ID token.
    • The existing self-read rule (users: request.auth.uid == userId) allows exactly that one doc. The function can therefore read nothing the signed-in user couldn't already read in the app, and it holds no credential of its own.
    • It requires fields.role.stringValue ∈ {admin, manager} and an active field that is absent or exactly booleanValue: true, the same as the rules' get('active', true) == true. A string "false", a null or any other type is refused (D4). The request uses mask.fieldPaths=role&mask.fieldPaths=active, so no other users-doc field reaches the function, and sub is URL-encoded.
    • A missing doc, a failed read or any other value returns 403.
  3. Client: each of the four fetch calls adds Authorization: Bearer ${await firebase.auth().currentUser.getIdToken()} through one helper authorizedFetch(). On a 401/403 the manager sees "Email not sent — please reload and sign in again" (the publish and share paths already surface failures; the two assignment paths are fire-and-forget today and will log and show a notice).
  4. Close the per-function gaps in the same pass:
    • send-assignment-email: pin trainingUrl as the other two do, and escape every interpolated value.
    • send-observation-email: only CC observerEmail when it equals the verified token's email.
    • Recipient restriction: decision B.

Why not firebase-admin (option B)

  • For the role read, it needs a service-account private key stored as a Netlify env var. That key bypasses Firestore rules for every staff app, up to whatever its IAM role allows (it can be least-privileged, but it is still outside rules). (v2: corrected.) The 4 KB env-var total applies only in Netlify's Lambda-compatibility mode, and the key (~2.3 KB) would fit anyway, so size is not a blocker. verifyIdToken alone, without checkRevoked, needs no key.
  • It adds a large dependency (about 30 MB installed) and slower cold starts.
  • It conflicts with the standing direction: no credential that skips rules (the backup-js-uses-cli-token and firebase-agent-defense-hardening notes).
  • The only thing it buys is verifyIdToken(token, checkRevoked). Option A instead has up to a ~1 hour window in which a token stays valid after an account is disabled. Archiving (active:false) is still enforced immediately, because the role read goes through rules.
Note for Christie: step 2 is a raw Firestore REST call. The CLAUDE.md rule against raw REST calls is about the Firebase CLI's cached token, which bypasses rules. This call carries the signed-in user's own token and is rules-enforced, the same as the app's SDK reads. I believe it is within that rule, but it's your call (decision A).

v2 changes from plan review r1

  • Hardening added to the same pass (D5):
    • Strict type and length validation on every payload field through the existing boundedString pattern. Today memberName.split (assignment:59) and observerName.trim (observation:57) throw on a non-string, outside the try block.
    • Cap items (e.g. 50) and title length. Strip CR/LF from the subject. Bound dueAt to a sane window, cap scheduled reminders per request, and check the reminder send's {error} (assignment:205, never checked today). Write down the reminder timezone.
    • The CC comes from the verified token's email, and observerEmail from the body is ignored. Consider taking sharerName from the verified identity too.
  • Never log event.headers or the token. The Firestore and JWKS hosts are hard-coded constants. No CORS headers are added: a cross-origin request carrying a token fails preflight, which is correct. A JWKS fetch timeout maps to 503. jose's key cache lasts only per warm instance, so a cold start costs one extra fetch.
  • Client (D8): FirebaseCompatAuth.currentUser gains getIdToken() in the type. authorizedFetch() refuses when currentUser is null and passes an AbortSignal through. A 401/403 is not logged as sent.
  • Extra tests: future or missing iat/auth_time; the reminder-bot uid; a malformed REST active (string, null); 404 and 403 from REST both → 403; reminder rejection; recipient-uid binding; payload validation. npm test (Vitest) is run explicitly before deploying, because scripts/deploy.sh runs only the demo Playwright suite.

Testing without production

  1. Unit (Vitest, offline): requireManager takes an injectable key set and fetch.
    • Tests sign tokens with a locally generated RSA key (jose.generateKeyPair + createLocalJWKSet).
    • Cases: no header → 401; bad signature → 401; wrong aud/iss (another Firebase project's real-shaped token) → 401; expired → 401; alg:none → 401; valid token + role staff → 403; archived manager → 403; missing users doc → 403; Firestore 5xx → 403 (fails closed); valid manager → passes.
  2. Handler tests (Vitest): each of the three handlers, with Resend mocked, returns 401/403 and never constructs or calls Resend when requireManager rejects. This is the test that proves all three are wired, not just one.
  3. Rules-path integration (Firestore emulator, studio-hub rules):
    • Start the Firestore emulator with /Users/christiehubley/studio-hub/firestore.rules (project demo-tinker-training) and seed manager, staff and archived users.
    • Point the REST base URL at FIRESTORE_EMULATOR_HOST and use the emulator's unsigned mock tokens, with only the signature step stubbed.
    • This proves the self-read rule allows the role read and refuses it for another uid.
    • The emulator base URL is chosen only from an explicit test-only constructor argument, never from an env var in production code.
  4. Local end-to-end (v2, narrowed; D7): this only proves "no or garbage token → 401" against the bundled function, using netlify dev --offline with RESEND_API_KEY unset. That way the CLI can't pull the real key from the linked site, and nothing can send. An emulator-signed-in manager can't pass locally: emulator tokens are unsigned, and production code has no emulator bypass (D2). The manager-passes path is covered by the unit and handler tests, and by the emulator integration test (test-only constructor overriding the REST base URL and the project id, because a demo- project emulator refuses tinker-hq-apps paths).
  5. After deploy (Christie):
    • One real publish to the test account (test@tinkerartstudio.com) succeeds.
    • A curl -X POST https://tinker-training-hub.netlify.app/.netlify/functions/send-observation-email -d '{}' returns 401 for each of the three functions.

Phase 1: shared guard and tests (execution-ready: false)

Given a request with no or an invalid token when it hits any of the three functions then 401, and Resend is never called.
Given a valid token for a staff user then 403. Given a valid token for an active manager then the email is sent exactly as today.
Failure: Google's key endpoint or Firestore is unreachable → 403/503, no mail (fails closed).
