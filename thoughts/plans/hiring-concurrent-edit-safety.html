Goal

Christie and the GM can have the same candidate open at the same time, and nothing either of them types or changes gets undone by the other person's screen. Interview answers show up on the other person's screen as they're saved, and a change of stage (e.g. to Not Moving Forward) always sticks.

What's wrong today (research, 2026-09-28)

  1. Interview answers get erased. Every open candidate card auto-saves every 5 seconds (app.js:692). The save copies every answer box on that screen, blanks included (app.js:793–807), even if nobody typed. The other person's screen never refreshes its boxes (the live refresh was removed in a13c9b0). So an idle viewer's blank boxes are saved over the typist's answers every 5 seconds. The Firestore merge (firebase-data.js) lets any answer set with keys win, and {'0':'','1':''} has keys. The live listener (app.js:1878–1899) also lets the local copy win, so the idle viewer never picks up the real answers and keeps re-saving blanks until they close the card. Last to close wins.
  2. Every save rewrites the whole pipeline. Each save (saveDataToFirestore) writes candidateData for every candidate from that browser's memory. The transaction only merges interview answers, and the data is computed before the transaction runs. If one person changes a stage and another person's open card auto-saves before the first change reaches them, the stage change is reverted. That can happen every 5 s while any card is open. This may explain the GM's "can't move people to Not Moving Forward." (Not confirmed; Christie is asking her what she sees.)
  3. A failed save looks like a successful one. Errors go only to console.error. The button still says "Saved!" and the autosave line still says "✓ Auto-saved".
  4. Smaller issues found on the same path: saveNotes rebuilds the record and drops declineDismissed. dismissAllDeclineAlerts re-links cards using the old email-only key, so cards don't update until a reload. Settings → "Push Data to Firestore" (seedDataToFirestore) overwrites the whole document from one browser's local copy.

Design

  • Write only what changed, one field at a time. New data-layer functions write single field paths inside a transaction: candidateData.<key>.<field> and candidateData.<key>.interviewAnswers.<position>.<n>. They use FieldPath segments because candidate keys contain ., |, @, / and spaces, and transaction.update leaves every other candidate and field alone. This keeps the repo's "all writes in transactions" invariant.
  • Remember what this person typed. Interview boxes are marked "dirty" on input. The 5-second autosave (kept, per the repo invariant) writes only dirty boxes, and a tick with nothing dirty writes nothing. Blur and closing the card flush immediately. A box stops being dirty only once its write succeeds and its value hasn't changed since the flush began.
  • Incoming wins, except for what I'm typing. The live listener takes Firestore's version of candidateData and overlays only this browser's still-unsaved dirty answers. If the card is open, every interview box that isn't dirty is refilled from the incoming data, so the other person's typing appears.
  • Save Changes (Notes tab) writes only the fields you changed. When the card opens, it captures a baseline of stage, considering, notes, actions, declineEmailSent, futureCandidate and hireDate. Save writes only the fields whose form value differs from that baseline, so fields you didn't touch never overwrite someone else's change.
  • Other writers become field writes: reference notes, the "Considering for" change, Dismiss All (declineDismissed per candidate, one transaction), and job templates (jobTemplates only). The whole-document saveDataToFirestore is deleted once nothing calls it.
  • First save for a new applicant. A candidate who exists only in the Google Sheet has no Firestore record yet. Their defaults (stage, notes, considering) come from the sheet. If the transaction finds no record for that key, it writes the full local record for that one candidate, not a single field, so the sheet-derived defaults aren't lost.
  • Empty values: clearing an answer or a text field writes FieldValue.delete(), never an empty string (repo invariant). Readers already treat missing as ''. Empty keys are refused before any write.
  • Saves that fail say so. Every save function returns success or failure. The autosave line shows "✓ Saved" only after the write lands, and on failure shows "⚠ Not saved — check your connection", which stays up until a later save succeeds. The Save buttons do the same.
  • Testability: firebase-data.js gets initHiringDataLayer({db, FieldPath, FieldValue}) and a module.exports guard, the same pattern as clay-hub-membership's initDataLayer. The pure decision logic (which fields changed, how to merge incoming data with dirty answers) goes in a new js/sync-logic.js, a plain script that is also requireable in Node.
  • Cache busting: bump app.js?v=8→9 and add ?v=2 to firebase-data.js and sync-logic.js, so no browser runs new app.js with an old data layer.

Design additions from review round 1 (2026-09-28, verified against the code)

  • R1. Sheet-only applicants must survive the live listener. Today the listener replaces the whole map (candidateData = data.candidateData, app.js:1897), so any applicant not yet in Firestore disappears from candidateData on the first snapshot. After that, interview answers (app.js:802) and the Considering change (app.js:1691) throw, and reference notes silently don't save. Fix: extract defaultRecordFor(candidate) from mergeCandidateData into sync-logic.js. The listener rebuilds defaults for every sheet candidate missing from the incoming data. The first-save path takes its record from that helper, stripped of empty values, with only the dirty answers.
  • R2. Unsaved answers outlive the card. Pending writes live in a queue keyed by candidateKey + position + index, holding the values in memory, and are captured synchronously when the card closes or the position changes. The queue retries on its own timer, independent of the modal, and a beforeunload warning shows while it is non-empty. Flushes are single-flight, so a tick never overlaps an in-flight save. DOM ids (iq-N) are never used as keys.
  • R3. The whole-document import runs only when the document provably doesn't exist. loadDataFromFirestore returns {exists:false} vs {error}. On an error the app shows "Couldn't load — reload", and nothing that writes is enabled. Settings → "Re-import from Sheet" is listed as a whole-document writer (see open question 2).
  • R4. Never refill the box with focus. Keep a "last value written" per box until a snapshot confirms it. Transaction writes show up in the listener only after commit, so an older snapshot must not overwrite fresher local text.
  • R5. Fix the Save Answers button. Today it's wired as addEventListener('click', saveInterviewAnswers) (app.js:1673), so the click event arrives as the position and the save throws. Wrap it: () => saveInterviewAnswers().
  • R6. No position selected. The answer boxes are disabled and show "Pick a position under 'Considering for' first" (AGENTS.md invariant), so there is never a dirty box stuck under an empty key.
  • R7. Save Changes baseline rules. The baseline comes from localData, not the form, because hireDate auto-fills today (app.js:648). '', null and missing count as equal. The baseline resets after a successful save and after a Considering change. Fields the old code dropped (declineDismissed, interviewNotes) are no longer touched.
  • R8. Dismiss All goes through the first-save path, so sheet-only rejected candidates stop alerting.
  • R9. Mechanics: use the varargs transaction.update(ref, fieldPath, value, …) form, because the object form splits dotted keys. The existence check for a candidate happens inside the same transaction. The merge logic skips the legacy flat {'0':'text'} string values and never deletes them. No new top-level fields are added during the rollout: old tabs' whole-document set would drop them. lastUpdated is still written. sanitizeCandidateData is deleted once it has no callers.
  • R10. Push-button removal: the HTML section and the JS listener are removed in the same commit. A leftover getElementById(...).addEventListener would throw during start-up and the app would never load.

Design changes from review round 2 (2026-09-28) — these supersede R4 and R7 where they differ

  • B1 (replaces R7's baseline): the Notes-tab fields work like the answer boxes. Stage, considering, notes, actions, the checkboxes and hireDate are each marked dirty on change. Save Changes writes only dirty fields. Each snapshot refills the non-dirty fields, so the form always shows current data and a later save can never write a stale value. No baseline object. hireDate's auto-fill with today counts as a change once Save is clicked (same as today).
  • S1: distinct names. The data-layer functions are writeCandidateFields, writeInterviewAnswers and writeJobTemplates. Nothing may share a top-level name with app.js, which is a classic script in the same global scope. A Phase 1 test loads config.js, sync-logic.js, firebase-data.js and app.js in index.html order into one context and fails on any clash.
  • S2 (replaces R4's "last value written"): one local overlay. An overlay entry is {candidateKey, field-or-answer path, value | DELETE, state: queued | in-flight | awaiting-confirm}. It is applied to both candidateData and the on-screen refill, whether or not the box has focus. An awaiting-confirm entry clears when a snapshot's value matches it, or after 2 later snapshots or 10 s, whichever is first, so another person's later edit is never hidden forever. A refill held back for a focused box applies on blur. sync-logic.js unit tests cover each transition.
  • S3 (tightens R3): one import rule. The full-document import runs only when the Firestore read succeeded and the document doesn't exist. If it exists, nothing is ever rebuilt from the sheet, whatever importDone or localStorage say. On a load error the board shows a red "Couldn't reach the database — reload" banner, with no board and no saving. A later successful listener snapshot does not quietly enable saving: the banner asks for a reload.
  • S4 (R1 helper and legacy keys): data check on the 2026-09-28 nightly backup: 232 candidates; 88 email-only legacy keys, all 88 already have an email|timestamp twin; 0 legacy flat answer sets; document ≈108 KB (far from the 1 MiB limit, which rules out the "document full" theory). The helper still includes the migrate-legacy branch with its first-applicant-wins set, for correctness. With today's data it never fires.
  • S6: order and branch. The ?emulator=1 switch moves to the start of Phase 2, reviewed with it. Phases 1–3 happen on branch fix/concurrent-edits, merged to main only at Phase 4, so no unrelated deploy from main can ship unverified wiring. sync-logic.js is new, so it gets no ?v=.
  • S5: old tabs during rollout. An old tab with a card open still does the old 5-second whole-document save, so it can still blank answers and drop brand-new applicants' records. Choice for Christie (open question 3).
Known limit: job templates stay last-write-wins on the whole list (rarely edited).
Known limit: if both people edit the same answer box at the same time, the last write wins for that box. Different boxes, different fields, and different candidates never collide.
Rollout hazard: a tab still running the old code keeps rewriting the whole document every 5 s while a card is open. After deploying, Christie and the GM must reload every open Hiring tab. Phase 4 includes a "reload now" step for both of them.

Completeness — what if this stops halfway?

  • Phase 1 only adds code, and the app behaves exactly as today.
  • Phase 2 is one commit, and nothing is live until Phase 4's deploy. Stopping between phases leaves production on the old code.

  • After the deploy, the remaining risk is an old tab left open (see the rollout hazard above).
