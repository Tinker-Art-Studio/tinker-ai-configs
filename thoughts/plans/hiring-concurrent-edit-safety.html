Goal

Christie and the GM can have the same candidate open at the same time, and nothing either of them types or changes gets undone by the other person's screen. Interview answers show up on the other person's screen as they're saved, and a change of stage (e.g. to Not Moving Forward) always sticks.

What's wrong today (research, 2026-09-28)

  1. Interview answers get erased. Every open candidate card auto-saves every 5 seconds (app.js:692). The save copies every answer box on that screen, blanks included (app.js:793–807), even if nobody typed. The other person's screen never refreshes its boxes (the live refresh was removed in a13c9b0). So an idle viewer's blank boxes are saved over the typist's answers every 5 seconds. The Firestore merge (firebase-data.js) lets any answer set with keys win, and {'0':'','1':''} has keys. The live listener (app.js:1878–1899) also lets the local copy win, so the idle viewer never picks up the real answers and keeps re-saving blanks until they close the card. Last to close wins.
  2. Every save rewrites the whole pipeline. Each save (saveDataToFirestore) writes candidateData for every candidate from that browser's memory. The transaction only merges interview answers, and the data is computed before the transaction runs. If one person changes a stage and another person's open card auto-saves before the first change reaches them, the stage change is reverted. That can happen every 5 s while any card is open. This may explain the GM's "can't move people to Not Moving Forward." (Not confirmed; Christie is asking her what she sees.)
  3. A failed save looks like a successful one. Errors go only to console.error. The button still says "Saved!" and the autosave line still says "✓ Auto-saved".
  4. Smaller issues found on the same path: saveNotes rebuilds the record and drops declineDismissed. dismissAllDeclineAlerts re-links cards using the old email-only key, so cards don't update until a reload. Settings → "Push Data to Firestore" (seedDataToFirestore) overwrites the whole document from one browser's local copy.

Design

  • Write only what changed, one field at a time. New data-layer functions write single field paths inside a transaction: candidateData.<key>.<field> and candidateData.<key>.interviewAnswers.<position>.<n>. They use FieldPath segments because candidate keys contain ., |, @, / and spaces, and transaction.update leaves every other candidate and field alone. This keeps the repo's "all writes in transactions" invariant.
  • Remember what this person typed. Interview boxes are marked "dirty" on input. The 5-second autosave (kept, per the repo invariant) writes only dirty boxes, and a tick with nothing dirty writes nothing. Blur and closing the card flush immediately. A box stops being dirty only once its write succeeds and its value hasn't changed since the flush began.
  • Incoming wins, except for what I'm typing. The live listener takes Firestore's version of candidateData and overlays only this browser's still-unsaved dirty answers. If the card is open, every interview box that isn't dirty is refilled from the incoming data, so the other person's typing appears.
  • Save Changes (Notes tab) writes only the fields you changed. When the card opens, it captures a baseline of stage, considering, notes, actions, declineEmailSent, futureCandidate and hireDate. Save writes only the fields whose form value differs from that baseline, so fields you didn't touch never overwrite someone else's change.
  • Other writers become field writes: reference notes, the "Considering for" change, Dismiss All (declineDismissed per candidate, one transaction), and job templates (jobTemplates only). The whole-document saveDataToFirestore is deleted once nothing calls it.
  • First save for a new applicant. A candidate who exists only in the Google Sheet has no Firestore record yet. Their defaults (stage, notes, considering) come from the sheet. If the transaction finds no record for that key, it writes the full local record for that one candidate, not a single field, so the sheet-derived defaults aren't lost.
  • Empty values: clearing an answer or a text field writes FieldValue.delete(), never an empty string (repo invariant). Readers already treat missing as ''. Empty keys are refused before any write.
  • Saves that fail say so. Every save function returns success or failure. The autosave line shows "✓ Saved" only after the write lands, and on failure shows "⚠ Not saved — check your connection", which stays up until a later save succeeds. The Save buttons do the same.
  • Testability: firebase-data.js gets initHiringDataLayer({db, FieldPath, FieldValue}) and a module.exports guard, the same pattern as clay-hub-membership's initDataLayer. The pure decision logic (which fields changed, how to merge incoming data with dirty answers) goes in a new js/sync-logic.js, a plain script that is also requireable in Node.
  • Cache busting: bump app.js?v=8→9 and add ?v=2 to firebase-data.js and sync-logic.js, so no browser runs new app.js with an old data layer.
Known limit: if both people edit the same answer box at the same time, the last write wins for that box. Different boxes, different fields, and different candidates never collide.
Rollout hazard: a tab still running the old code keeps rewriting the whole document every 5 s while a card is open. After deploying, Christie and the GM must reload every open Hiring tab. Phase 4 includes a "reload now" step for both of them.

Completeness — what if this stops halfway?

  • Phase 1 only adds code, and the app behaves exactly as today.
  • Phase 2 is one commit, and nothing is live until Phase 4's deploy. Stopping between phases leaves production on the old code.
  • Each save is one transaction, so it either fully lands or doesn't. A dirty box that failed to save stays dirty and retries on the next tick.
  • After the deploy, the remaining risk is an old tab left open (see the rollout hazard above).
