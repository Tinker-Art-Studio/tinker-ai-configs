Plan: Ticker — A Failed Schedule Write Is Reported As Success

Status: execution-ready: false — v2, revised after review round 1. One product decision is outstanding (staff withdrawal, below) and blocks Phase 3. Written Sep 9, 2026.

This is a LIVE bug. Found Sep 9 2026 by both reviewers during the time-off fix, and deliberately not bundled into that change: it is broad, affects many paths, and needs its own scoped fix and review.

Review round 1 (Claude + Codex) rejected v1 of this plan. Both independently found that its Phase 1 — the phase labelled "inert" — would have written {ok, applied} into the live appliedOverrides field, which removeTimeOffOverrides() would then read as two date keys. That would have caused the unrecoverable state this plan exists to prevent. Codex additionally found three blocking issues v1 missed entirely: the second write in each flow is unchecked too, staff cannot write schedules at all (so the fix would break a currently-advertised action), and this repo has no way to force a write failure in a test today. All verified against the code before this revision. The v1 phase plan is superseded; do not execute it.

Review round 2 (Claude + Codex) ALSO rejected the plan. Both independently reached the same three conclusions: Phase 0's approach does not unblock anything (the real blocker is that app.js cannot be require()d at all, not that failures cannot be forced); Phase 2's rollback is best-effort, not a correctness guarantee, and can destroy a concurrent writer's data; and the staff-withdrawal design has no manager-side completion action, so it would strand requests. Claude additionally found that the offline threat model in this plan is backwards and that a live, failure-independent bug exists today. See "Round 2 findings" below. v3 is required before execution.

Round 2 findings — all verified, all still open

LIVE BUG, independent of this plan — approveTimeOff has no re-entrancy guard. (Claude, round 2.)
approveTimeOff() (app.js:7333) does not disable its button and never checks data.status before acting. Two admins, or one impatient double-click, run applyTimeOffOverrides twice. The second run captures the day-off marker the first run wrote and stores { had: true, previousOverride: null } — so the eventual reversal restores a phantom Day Off instead of the real shift. For a partial day it permanently restores the request's own reduced shift.

This needs no write failure at all. It is reachable today by double-clicking Approve. It is arguably more likely to fire than the bug this plan was written about, and the fix is small: disable the button, and bail if data.status === 'approved'. Compare submitConfirmSub (:7167), which already disables its button.
HIGH — the offline threat model here is backwards. (Claude, round 2.)
Offline persistence is enabled (firebase-config.js, enablePersistence({synchronizeTabs:true}), awaited at firebase-data.js:17). With it on, await set() does not reject when offline — it stays pending until the server acknowledges. So saveSchedule never returns false offline; approveTimeOff simply hangs, with no toast and no error, and this plan's guard never runs. Likewise get() falls back to cache, so loadSchedule returns stale data, not null.

Consequence #4 above is therefore wrong on its offline half: rules denial is the real trigger, not offline. And offline combines with the re-entrancy bug above — a manager who sees nothing happen clicks Approve again, both writes flush on reconnect, and the double-apply corruption lands with no failure ever reported.
HIGH — "absent schedule document = success" is right for apply and WRONG for reverse. (Claude, round 2.)
v2 made this a blanket rule. For reverse with a non-empty appliedOverrides map, an absent document means the overrides' document is gone or has moved — and reporting success lets Phase 3 clear the record, producing exactly the unrecoverable state this plan exists to prevent.

It is reachable, not theoretical: a seeded request stores uid = claimedBy || id (:5516), so an unclaimed employee's approved request carries an emp_… id; when they later claim their name, migrateSchedule moves the document to their auth uid; then removeTimeOffOverrides('emp_…', map) finds nothing and "succeeds". Note removeTimeOffOverrides takes a raw uid and does not go through resolveScheduleTarget() — the resolver this repo added for precisely this identity split.
Phase 0 is aimed at the wrong blocker — both reviewers, independently.
Pointing firebase.json at the shared rules file would not break the existing 338 tests (they use the Admin SDK, which the emulator grants owner access, so rules are bypassed either way) — but it would not make a single Phase 2–4 scenario executable either. Those scenarios require calling approveTimeOff(), and js/app.js has no module.exports and cannot be require()d. Every existing emulator test re-implements the write shape rather than executing the function, which is exactly why they cannot tell a guard placed before updateTimeOffRequest from one placed after.

Phase 0 must be EXTRACT, not authorize: move applyTimeOffOverrides, removeTimeOffOverrides and the approve-and-record orchestration into a require()able module — schedule-helpers.js is the established precedent — taking { loadSchedule, saveSchedule, updateTimeOffRequest } as injected dependencies. Forcing a failure then costs one line, needs no rules change and no cross-repo coupling, and the tests execute the real code. It also sidesteps the "no mock Firestore" tension: the data layer is injected, Firestore is not mocked.

Claude also warned against the rules-file route on its own terms: the path is outside the repo, so it breaks any non-sibling checkout and CI; an unrelated studio-hub edit would fail Ticker's whole suite; and it would create pressure to edit the shared production rules file to make Ticker's tests green — the file whose regression breaks all eight apps at once.
HIGH — Phase 2's rollback is best-effort, not a correctness guarantee. (Codex, round 2.)
Two concrete states where compensating with the in-memory applied map makes things worse:
  1. Concurrent edit. Apply captures shift A and writes Day Off; another operation writes a legitimate shift B on that date; the request update fails; rollback restores A and destroys B.
  2. Overlapping approvals. Request A captures shift X and writes Day Off; request B approves the same date, captures the Day Off and writes its own; A's request update fails; A's rollback restores X, silently undoing B's successful approval while B still reads as approved.
And the double-failure case (schedule write lands, request update fails, rollback also fails) leaves a live override with no durable provenance — so "retrying after the cause is fixed works normally" is false there, because retrying invokes the non-idempotent apply. Claude's cheap mitigation: on rollback failure, persist the map under a different field name (pendingReversal, never appliedOverrides, so no existing reader misparses it). Losing the map is strictly worse than an odd field on a non-approved request.

Codex's position is that a real fix needs one of: a transaction across both documents, provenance on each override plus conditional compensation, or a durable recovery record written atomically with the schedule change. This is the open architectural question for v3.

  • Needs Action would not show it (:6289 filters to submitted/under_review), and the dashboard query has the same restriction (firebase-data.js:460).
  • isOwner and isAdmin are not exclusive (:6793) — Christie both owns and administers her own requests, so "branch on role" would tell her to wait for a manager to action her own time off. Branch on capability, admin winning.

Goal

When a schedule write fails, the manager is told it failed — and the app does not record the change as having happened. Today the opposite is true: approving time off can tell the manager "Request approved — schedule updated", notify the employee that they are approved, and store a record of overrides that were never written.

Repo: ~/tinker-timeclock Ticker only — no Firestore rules changes, no new collections, no migration.
Collections touched: timeclock_schedules/{uid} (writes), timeclock_timeoff/{docId} (writes). Both already have rules (firestore.rules:320 and :338, manager+ read/write).
Blast radius: every time-off approval, un-approval, denial, withdrawal, edit-reopen and sub confirm/un-confirm. Schedules drive Who's Working, My Schedule, kiosk late/grace/streak logic and the scheduled-vs-actual comparison.
Why it matters more now: schedule removals actually remove as of 66dcbc8 (Sep 8). The gap between "the UI says it worked" and "the data changed" has real consequences it did not have when the writes were no-ops anyway.

Root cause

Two functions in js/firebase-data.js turn failure into an ordinary-looking return value:

  • saveSchedule() (:205) catches its own errors and returns false.
  • loadSchedule() (:183) catches its own errors and returns null — the same value it returns for an employee who legitimately has no schedule document. A failed read and an absent document are indistinguishable.

Two callers then discard that signal entirely, and every path downstream of them assumes the schedule changed.

The four concrete consequences

1. HIGH An approval can be recorded against a write that never landed.
approveTimeOff() (:7332) calls applyTimeOffOverrides(), then unconditionally writes status: 'approved' and appliedOverrides, toasts "Request approved — schedule updated", and pushes "Your time off request has been approved" to the employee. If the schedule write failed, the employee is still scheduled to work, believes they are approved, and the request now carries a record of overrides that do not exist. (Correction from v1: this path sends a push notification only. The time-off email is tied to sub confirmation, not approval.)
2. HIGH A failed reversal can destroy the rollback metadata — unrecoverable.
unapproveTimeOff() (:7452) calls removeTimeOffOverrides(), then writes appliedOverrides: null. On a failed removal the schedule still holds the time-off overrides and the record of what to restore is gone. Nothing in the app can recover it. The edit-reopen path (:6709, then formData.appliedOverrides = {} at :6711) has the identical shape, as does reverseConfirmedTimeOffSubs() (:7311), which clears each sub's appliedOverrides through the transaction regardless of whether the schedule write landed.

withdrawTimeOff() (:7420) and denyTimeOff() are less severe — they change status but leave appliedOverrides intact, so the data needed to reverse survives. Do not refactor them into clearing it.
3. HIGH The second write in each flow is unchecked too. (Missed in v1; found by Codex, verified.)
updateTimeOffRequest() (firebase-data.js:474) catches its own errors and returns false, and none of these flows check it. So the mirror-image failure is equally reachable: the schedule write succeeds, the request update fails, and the app still toasts success and pushes the notification. That leaves a live override with no durable record that it exists — arguably worse than the failure this plan was written to fix, because appliedOverrides was never stored at all.

A fix that only checks saveSchedule converts one silent failure into a louder version of the other. Both writes in every touched flow must be checked.
4. MEDIUM A failed read is a silent no-op that reports success.
Both override functions open with const schedule = await loadSchedule(uid); if (!schedule) return. A permission error or offline moment therefore does nothing at all and tells the caller it succeeded — and is indistinguishable from an employee who genuinely has no schedule document, which is a legitimate case that should succeed. Given this repo's failure history is rules regressions, and rules regressions deny reads too, this may be the likelier trigger of the two.

The asymmetry that decides the failure rule

Reversal is idempotent. Application is not. This is the single most important thing to understand before writing any of the code below, and v1 of this plan got the rule wrong because it missed this.
  • Reverse is safe to retry. resolveOverrideRestore() (schedule-helpers.js:574) either restores a fixed captured value or emits FieldValue.delete(). Running it twice converges on the same state.
  • Apply is NOT safe to retry. applyTimeOffOverrides() recaptures had/previousOverride from current state on every run. Re-applying over an already-applied override records had: true, previousOverride: null — the day-off marker it wrote itself — so the next reversal restores a phantom Day Off instead of deleting it. This is the same class of bug the before snapshot at :7511 fixed within a single call, reappearing across calls.
So the two directions get two different failure rules:
DirectionOrderOn failure
Apply (approve, seed)schedule write → verify → then touch the request doc Abort, persist nothing. Re-applying is corrupting, so a half-recorded apply must not exist.
Reverse (unapprove, withdraw, deny, edit-reopen, un-confirm sub, bulk sub reversal) schedule write → verify → then clear appliedOverrides Never clear appliedOverrides for a reversal that did not land. Do not abort the status change — see the decision below. Report loudly, keep the record, stay retryable.
DECIDED Sep 9, 2026 by Christie — staff withdrawal of an approved request becomes a request a manager completes.

The problem: firestore.rules:321 grants timeclock_schedules writes to manager+ only; staff are read-only. But app.js:6949 offers Withdraw Request to the request's owner — a staff member — including when the request is approved and therefore has overrides to remove. Today that silently fails and tells them it worked. Simply honouring the failure would block staff from withdrawing at all.

The decision: staff keep direct one-click withdrawal for submitted and under_review requests — those have no appliedOverrides, so no schedule write is needed and nothing changes for them. Withdrawing an approved request instead sets a withdrawalRequested flag on the request and notifies a manager, who completes the actual reversal through the existing manager path. Rejected: a privileged Netlify endpoint (new attack surface) and widening the schedule rule for staff (schedules feed payroll comparison and kiosk logic).

Verified: this needs no rules change. The staff update rule (firestore.rules:345) is allow update: if hasAppAccess('timeclock') && resource.data.uid == request.auth.uid — no hasOnly() field allowlisting — so a staff member can already write a new field to their own request. The hasOnly caveat raised in the safety checklist was checked and does not apply here.

Phases 3 and 4 are unblocked. Phase 3 gains the withdrawal-request path as part of its scope.

NEW BUG found Sep 10, 2026 while verifying the re-entry guard — reverting a partial day leaves the time-off note behind. MEDIUM
saveSchedule() writes with set(..., { merge: true }), which merges nested maps recursively. Restoring an override whose value has FEWER keys than the value currently stored therefore leaves the extra keys behind. Concretely: a date carries a real override with no note, a partial-day time-off is approved (writing note: "Time off (partial day)"), and reverting it restores the real shift — with the time-off note still attached. The employee sees their normal hours labelled as time off.

Why nothing caught it: the existing coverage in remove-timeoff-overrides.emulator.test.js restores over a null day-off marker, and null is not a map, so nothing can leak through it. The case only appears when the restored value is a map with fewer fields than what is currently stored.

Pinned as test.failing in timeoff-status-guard.emulator.test.js (872f674) — it passes while the bug exists and starts failing the moment it is fixed, so it documents the defect without enshrining it. Not fixed there: the fix changes saveSchedule's merge semantics for every schedule write in the app. Belongs to this plan.

The likely fix is a dotted-path update() for the restore branch (update({ ['overrides.' + dateStr]: value }) replaces the whole nested value rather than merging into it) rather than changing saveSchedule globally — but that needs its own review, because update() fails on a non-existent document where set(merge) creates one, and confirm-sub relies on the creating behaviour.

THE LOAD HAZARD — this would have taken the whole app down. APPROVABLE_FROM is a top-level const (app.js:7341). A second top-level const of the same name in another classic script is SyntaxError: Identifier 'APPROVABLE_FROM' has already been declared, thrown at parse of the second script. app.js never executes — white screen, whole app dead, not a handler-level error.

A second, quieter version: schedule-helpers.js exports bare top-level functions, not a namespace. Follow that precedent literally and the new file's global applyTimeOffOverrides collides with app.js's same-named wrapper. Function declarations do not throw on redeclaration — the later script silently wins, app.js loads second, its wrapper wins, and the wrapper calls TimeOffSchedule.applyTimeOffOverrides, which does not exist. Silent TypeError on click.

Both are killed by one decision: wrap the new file in an IIFE assigning a single TimeOffSchedule global, plus module.exports. This is a deliberate divergence from schedule-helpers.js, not a copy of it — the file header must say so and say why.

How the dependencies are injected

  • Per-function deps, not one shared object. Each extracted function receives only what it uses: apply needs { loadSchedule, saveSchedule }; remove needs { loadSchedule, saveSchedule, deleteField }; the orchestration needs the rest. A single shared builder that eagerly evaluates firebase.firestore.FieldValue.delete() would give applyTimeOffOverrides — which today never touches firebase at all — a throw path it does not currently have. That is a self-inflicted behaviour change in a phase claiming neutrality.
  • Built lazily, per call. Never at parse time. _ready flips false→true after initAppFirestore(), currentUser is reassigned at sign-in, and the sentinel needs firebase loaded. A factory called once at load is strictly worse — it is the parse-time capture this is trying to avoid.
  • currentUser and new Date() pass as thunks, not values. Today reviewedBy and reviewedAt (:7401) are evaluated after the schedule write. Passing values would move that earlier: with a null currentUser, today the schedule write lands and then throws (leaving a live override with no record); after an eager move it would throw first and write nothing. Strictly better — and still a behaviour change in a phase claiming neutrality. Preserve the timing exactly; fix it in a later phase where it is visible.
  • resolveOverrideRestore is NOT injected. It was missing from v3.1's deps list entirely, and removeTimeOffOverrides calls it (:7666) — under Node that is a ReferenceError. require() it in the module's Node branch and read the browser global otherwise. The reviewers split here: Codex preferred injecting it. Injection wins on explicitness, but it would let a test stub the exact restore-versus-delete decision these tests exist to exercise, and the function is pure and already properly covered. Requiring it is the call.
  • deleteField is the FieldValue.delete() sentinel. This repo already injects that exact sentinel as DELETE_FIELD (app.js:3209), so the pattern is established, not invented here. It is also what makes the emulator-backed test below possible.
  • Destructure at the top of each moved function (const { loadSchedule, saveSchedule } = deps;) so the body underneath stays byte-for-byte identical. That is what makes the byte-identical review criterion mean anything.
  • Stub shapes must match production. updateTimeOffRequestIfStatus returns { success, reason, status } with reason ∈ {not-ready, not-found, status-changed, error}, and the rollback branch reads result.status. A stub omitting status silently exercises a path production never takes. Build stubs from one shared factory returning the real shapes — note loadSchedule returns { uid, ...data }, not a bare { overrides }.
app.js keeps thin wrappers with the SAME names and signatures, so none of the ten call sites changes. Verified: applyTimeOffOverrides at :5560, :7388; removeTimeOffOverrides at :6713, :6732, :7235, :7275, :7307, :7432, :7515, :7575. All ten await; two use the return value, eight discard it; a wrapper returning the inner promise preserves both.

They must stay async function declarations, not const — the inline onclick handlers require global function declarations, which is the load-bearing reason (hoisting is the lesser one). Do not add try/catch to any wrapper: the rollback call at :7432 runs inside approveTimeOff's own try, so a wrapper that caught would convert the abort-specific alert into the generic "Failed to approve request."

The "no mock Firestore tests" rule — the bright line, in the plan rather than in an argument. Injecting the data layer is not mocking Firestore: these tests assert control flow, not write shape. Characterization tests — as test.failing, asserting the DESIRED behaviour

v3.1 said these should "describe today's behaviour including the bugs" and "FAIL when the fixing phase lands". Both reviewers rejected that: a permanently red suite is a broken build, and the first person to see red will "fix" the test. A test asserting today's wrong value is also precisely the shape this repo has been burned by four times.

Use test.failing, asserting the CORRECT contract — the pattern already in this repo at timeoff-status-guard.emulator.test.js (872f674). It passes while the defect exists, and Jest treats an unexpected pass as a FAILURE, so the moment a later phase fixes the bug the suite goes red and forces the test to be promoted to an ordinary one. It cannot enshrine the defect, because it never asserts the defective value. 
test.failing('KNOWN DEFECT (Phase 2 promotes this): a rejected schedule save must not yield an applied record', async () => {
  const result = await applyTimeOffOverrides(uid, dates, {
    loadSchedule: async () => schedule,
    saveSchedule: async () => false,
  });
  expect(result).toEqual({ success: false, reason: 'schedule-write-failed' });
});
Rules: own file, header naming the phase that promotes each one; title starts KNOWN DEFECT; never a bare negative assertion (a too-loose one matches both old and new behaviour, so it does not fail when the fix lands and the signal evaporates).

One target was mis-placed in v3.1: "a failed read is indistinguishable from an absent document" is not a property of applyTimeOffOverrides — it belongs to loadSchedule (firebase-data.js:184, which returns null for !_ready, for a thrown read, AND for a genuinely absent doc). Characterize it where it lives, or the test pins the wrong function and a later phase fixes the other one.

Firebase safety checklist

  • Rules updated? Not needed for manager paths. No new collection; timeclock_schedules (:321) and timeclock_timeoff (:338) both already have manager+ read/write. Two caveats: (a) the staff-withdrawal decision above may require a rules or architecture change depending on which option is chosen; (b) if any phase adds a new field to timeclock_timeoff — a reversalPending marker is the obvious design — check that collection's update rule for field allowlisting first, or the write recording a failure would itself be denied.
  • Snapshot before bulk ops? Not applicable — no bulk operation, no migration, no delete of existing data. This change only declines to write in cases where it currently writes wrongly.
  • updateDoc not setDoc? This plan changes no write payload. Noting honestly that saveSchedule uses set(..., { merge: true }) rather than .update(), which sits in tension with the repo's stated invariant — it is deliberate, because confirm-sub may legitimately create a schedule document that does not exist yet. Changing it is out of scope here and should not be smuggled into this fix.
  • Empty fields stripped? Unchanged. omitEmptyMaps and the provenance rules from 5ec9eb7/66dcbc8 stay exactly as they are — this plan must not alter what gets written, only whether the caller believes it happened.
  • Emulator test before each write phase? NOT YET POSSIBLE — see Phase 0. The existing suites named here (remove-timeoff-overrides.emulator.test.js, timeoff-sub-confirm.emulator.test.js) re-implement the write shape with the Admin SDK rather than executing the orchestration functions in app.js, and firebase.json loads no rules file at all. They therefore cannot catch a guard placed after the request update, an unchecked false, or a success toast after a failure. v1 of this plan assumed this coverage existed; it does not.
  • Console spot-check per write phase? Yes — required by the workflow and not substitutable by a green suite. Per phase: approve a real request, confirm the overrides appear on timeclock_schedules/{uid}, then un-approve and confirm they are gone.
Testing the failure path is the hard part of this plan. Every phase's most important scenario is "the write fails", and the emulator succeeds by default. The suite needs a way to force a rejection — a stubbed saveSchedule/loadSchedule for the pure-logic paths, or an emulator rules-denied write for the end-to-end ones. Decide the mechanism in Phase 1, because if forcing failure is awkward, every later phase will be tempted to skip its most valuable test. A phase whose failure path is untested has not actually been verified.

Completeness check — what if this is interrupted mid-way?

Safe to interrupt between any two phases. Phase 0 touches only test infrastructure. Phase 1 is genuinely additive because it adds new function names rather than changing existing ones — stopping after it leaves the app behaving exactly as it does today. Phases 2 and 5 are independent. Phases 3 and 4 are not as independent as v1 claimed: denial reaches schedule removal only through Phase 4's sub helper, and withdrawal and edit-reopen use both the requester and the sub reversal paths. Treat 3 and 4 as one unit that can be interrupted between them only if the interim state is checked.

Phase order is by severity and dependency. Phase 0 blocks everything, because without a way to force a failure no phase can verify its most important scenario. Phase 2 is the case Christie hits most often; Phases 3 and 4 are the unrecoverable ones but are blocked on the staff-withdrawal decision. If only one phase ever ships after 0 and 1, Phase 2 is the most valuable.
