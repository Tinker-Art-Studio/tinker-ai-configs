Plan: Classbook check-live retries CDN lag

App: The Classbook (~/tinker-spring-curriculum) · Branch: claude/check-live-retry (worktree .claude/worktrees/check-live-retry, from origin/main 5360e6d) · Drafted: Oct 9 2026 (Christie away) · execution-ready: false until review · No Firestore, no deploy.

Goal: after npm run deploy, [check-live] FAILED means something is really wrong, not that Netlify's CDN hadn't caught up yet. The script keeps re-checking for about 30 seconds before it gives up.

Current state

  • scripts/check-live.sh makes three passes and exits non-zero on any failure.
    1. Completeness (local only): every file dist/index.html, the JS or the CSS references exists in dist/.
    2. Faithful: each dist/ file's sha1 equals the live file's, fetched with a ?nocache= query.
    3. Private: 16 dev paths must 404 live.
  • It runs once, right after netlify deploy in scripts/deploy.sh, and it also runs on its own via npm run check-live. Christie's note: an immediate FAILED is usually CDN lag.
  • There are no tests for the script.

Design

  1. Completeness stays a one-shot pass. A MISSING ref is a build problem, so retrying can't fix it, and it fails immediately.
  2. The faithful and private passes become one function. It checks the list it is given and returns the items still failing.
  3. Retry loop: re-check only the items still failing every CHECK_LIVE_INTERVAL seconds (default 5) until CHECK_LIVE_TIMEOUT (default 30) has passed. Each round prints [check-live] N still differ — CDN lag? retrying in 5s (12s/30s).
  4. An item that matches stays matched and isn't fetched again. The final verdict lists exactly the items that never came right.
  5. The output keeps its current shape (MATCH, DIFF, 404, [check-live] ok/FAILED), and the exit code is unchanged (0 or 1), so deploy.sh is untouched.
  6. CHECK_LIVE_BASE (default https://tinker-classbook.netlify.app) exists only so the test can point at a local server. Production use never sets it.
  7. POSIX sh, as today (the script is run with sh), so no bash-only syntax.

Phase 1: test first, then the retry (execution-ready: false)

scripts/check-live.test.sh builds a throwaway dist/ and a served copy in a temp directory. It serves them with python3 -m http.server on a free local port, runs the real script against it with short timeouts, and asserts the exit codes and output. Its four cases:

Happy: live already matches → exit 0, "ok", and no retry message.
CDN lag: one file differs at first and is corrected 2 s later (timeout 8 s, interval 1 s) → exit 0, with at least one retry line.
Real failure: a file differs for good → exit 1 after about the timeout, and FAILED names only that file. A must-be-404 path served live → exit 1, after retrying too, because a stale cached deploy can also lag.
Build failure: a referenced file missing from dist/ → exit 1 immediately, with no retry.

It's run by hand (sh scripts/check-live.test.sh), because npm test is the emulator/Playwright suite. It needs no network beyond localhost.

Phase 2: review

Claude and Codex review the implementation; then a PR, not merged. It first takes effect the next time Christie deploys Classbook.

Safety

  • No Firestore and no deploy. The script only reads (GET/HEAD) the live site.
  • The worst case is a deploy taking about 30 s longer when it really did fail.
