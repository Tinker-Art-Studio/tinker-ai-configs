Phase 1 — A: a locked period's hours can't be changed (execution-ready: false)

Acceptance criteria (user outcomes)

  1. A manager who edits, deletes or adds a clock entry on a day inside a locked period gets "<Day> is in the locked pay period <Sep 1 – Sep 15> (locked by <name>). Nothing was changed. Unlock the period first, then lock it again after editing." and the entry is unchanged in Firestore.
  2. Approving a time correction or missed-punch request for a locked day is refused the same way, and the request stays pending. Denying it still works, because a denial doesn't change hours.
  3. The check runs against the database at the moment of the save, not against what the screen loaded. A period locked in another tab after the editor opened is still respected.
  4. If the lock can't be confirmed (offline, read denied, any error), the save is refused with "Could not confirm whether this pay period is locked, so nothing was changed. Check your connection and try again." It fails closed.
  5. The admin entry editor shows a "🔒 This day is in a locked pay period: read-only" note and disables Save/Delete/Add when the editor opens on a locked day. That's a courtesy only. Criterion 1 is the real protection.
  6. Nothing changes for an unlocked period: same toasts, same re-render.

Design

  • Pure helper lockedPeriodForDate(lockedMap, dateStr) in js/schedule-helpers.js (already shared with tests via module.exports). It returns {key, lockedBy, lockedAt} or null, with inclusive start/end and a strict YYYY-MM-DD check on both the date and each key (a malformed key is skipped, never treated as locking everything). isDateInLockedPeriod becomes a one-line call to it, so the screens and the write share one rule.
  • Data layer, a new function in js/firebase-data.js:
    writeClockEntryIfUnlocked({ op: 'update'|'delete'|'add', entryId, updates, entry }) → { ok, reason, id?, period? }.
    It runs one _db.runTransaction:
    1. tx.get(lockedPeriods)
    2. for update/delete: tx.get(entry). If it's missing → {ok:false, reason:'not-found'}. The date checked is the stored date, never the caller's copy. For update, if updates.date is present and differs, both dates are checked (no admin path changes date today; this is defence against a future one).
    3. for add: the date checked is entry.date. If it isn't a valid YYYY-MM-DD → {ok:false, reason:'bad-date'}
    4. if lockedPeriodForDate matches → {ok:false, reason:'locked', period} and nothing is written
    5. otherwise tx.update / tx.delete / tx.set(newRef, entry) (a new id from .doc(), the same shape addClockEntry writes today)
    Any thrown error → {ok:false, reason:'error'}, logged. A transaction can't commit without the server, so an offline device fails closed by construction. A lock committed by another tab between our read and our commit makes Firestore retry the transaction, and the retry sees the lock.
  • Callers in js/app.js: the three adminEdit* functions and the status === 'approved' branch of handleChangeRequest call the new function instead of updateClockEntry/deleteClockEntry/addClockEntry. A shared lockRefusalMessage(result) turns locked/error/not-found/bad-date into the messages above. On a locked refusal the caller also refreshes the in-memory lockedPeriods and re-renders, so the screen catches up with the truth. The denial branch keeps updateClockEntry. adminEditDeleteEntry gains the same in-flight guard adminEditSaveEntry already has (_aeeSaveInFlight), and adminEditAddEntry disables its button while saving.
  • Editor courtesy note: openAdminEntryEditor reads getLockedPeriods() fresh when it opens. If the day is locked, it shows the note and disables the three controls. If that read fails, the editor stays enabled, since the write still fails closed.

BDD

Happy: Given Sep 1–15 is unlocked, when a manager changes Kaitlyn's Sep 3 clock-out to 5:00 PM with a reason, then the entry's timestamp updates, the toast says "Saved", and the timesheet re-renders as today.
Locked edit: Given Sep 1–15 is locked by Anika, when a manager saves, deletes or adds an entry dated Sep 1, Sep 8 or Sep 15, then each is refused with the locked message naming Anika and the entry docs are byte-identical before and after.
Boundary: Given Sep 1–15 is locked, when a manager adds an entry dated Sep 16 (or Aug 31), then it saves.
Locked after opening: Given the editor was opened on an unlocked Sep 8, when another manager locks Sep 1–15 and this manager then presses Save, then it's refused (the transaction reads the lock at save time).
Stale date: Given the screen's copy of an entry says Sep 16 but the stored doc says Sep 15 (locked), when it's edited, then it's refused (the stored date decides).
Approval: Given a pending missed-shift request on a locked day, when a manager presses Approve, then it's refused, the request stays pending and no push is sent. When the manager presses Deny, the denial is saved and the push sent.
Failure: Given the device is offline or the lock read is denied, when a manager saves an edit on any day, then it's refused with "Could not confirm whether this pay period is locked…" and nothing is written. The editor's Save is usable again afterwards.
Gone: Given the entry was deleted elsewhere, when a manager saves an edit to it, then "That entry no longer exists — refresh" is shown and nothing is created.
Malformed lock key: Given lockedPeriods holds a key "oops" alongside a real one, then only the real period locks anything.
No lock doc: Given timeclock_settings/lockedPeriods doesn't exist (a fresh studio), then every edit saves (a missing doc means nothing is locked; it isn't an error).

Firebase safety checklist

  • Rules change? No. Manager+ already writes timeclock_entries and reads timeclock_settings. New collection? No.
  • Partial updates stay update (tx.update); the add is a new doc. No set without merge is introduced.
  • Empty fields: the add writes the same object adminEditAddEntry builds today (no empty strings). The edit writes the same updates as today.
  • Bulk delete/import? No. No snapshot needed.
  • Emulator tests first, red before green (Phase 1 data layer); wiring tests for app.js.
  • Payroll Tool: no field or format change. A refusal leaves raw entries unchanged, which is exactly what the Payroll Tool's discrepancy check assumes.
  • Console spot-check after release: one locked period's lockedPeriods entry unchanged, and one entry Christie tried to edit (if any) unchanged.

Accepted residuals (disclosed, not fixed here)

  • Rules don't enforce the lock (E). Anyone with manager access could still change a locked day via the console or SDK. App-layer only, as the August proposal said.
  • An edit that lands between the manager's lock read and their confirm isn't in the snapshot they confirm. That's pre-existing and rare (two managers acting within seconds), and the Payroll Tool flags the hour discrepancy. Closing it would need the lock to re-read entries inside its transaction; noted for E/D.
  • Kiosk punches aren't lock-checked. They always write "now", and a period is locked only after it ends. If a manager locks the current period early, a later kiosk punch would land in it. Not something the app offers (the lock button is per past period), so this is noted rather than handled.
  • Staff screens keep their existing in-memory lock check. Their requests count for nothing until a manager approves, and approval is now checked.

Completeness: if interrupted midway

  • Each phase is one commit (or a few) on main, pushed. Nothing is deployed until Phase 3, so a half-done phase changes nothing for staff.
  • Phase 1 is safe to ship alone. Phase 2 doesn't depend on Phase 1.
  • No data migration and no data written by this plan's code except through the normal app actions.
