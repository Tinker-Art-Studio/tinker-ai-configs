Phase 1 — A: a locked period's clock hours can't be changed from Ticker (execution-ready: false)

Acceptance criteria (user outcomes)

  1. A manager who edits, deletes or adds a clock entry on a day inside a locked period gets "<Day> is in the locked pay period <Sep 1 – Sep 15> (locked by <name>). Nothing was changed. Unlock the period first, then lock it again after editing.", and the entry is unchanged in Firestore.
  2. A staff member who reports a missing punch for a locked day gets "<Day> is in a pay period that's already been locked for payroll. Nothing was submitted. Please tell your manager directly.", and nothing is saved.
  3. Approving a correction or missing punch for a locked day is refused the same way, and the request stays pending. Denying a pending request is still allowed in a locked period, because a pending request adds no approved hours.
  4. Approve and Deny only act on a request that is still pending in the database. If someone else already reviewed it, the manager sees "This request was already <approved/denied> by <name>. Nothing was changed." and the list refreshes. (No more approved→denied flips from a stale tab, and no second approval overwriting originalTimestamp.)
  5. The check happens in the database at the moment of the save. A period locked after the screen loaded is still respected.
  6. If the lock can't be confirmed (offline, read denied, any error): "Could not confirm whether this pay period is locked, so nothing was changed. Check your connection and try again." It fails closed.
  7. Save, Delete, Add, Approve, Deny and Submit are disabled while their save is in flight, so a double click can't send two.
  8. When the entry editor opens on a locked day, it shows "🔒 This day is in a locked pay period" and disables Save and Delete on the listed entries. Add is checked against the date chosen in its own date picker when pressed (it isn't disabled up front). The courtesy note is just a display; the database check in criterion 1 is what protects the data.
  9. For an unlocked period everything works exactly as today.

Design

  • Pure helper lockedPeriodForDate(lockedMap, dateStr) in js/schedule-helpers.js returns {key, start, end, lockedBy, lockedAt} or null. Start and end are inclusive. The date and each key's two halves must pass the existing isRealDate (904); a malformed key is skipped, never treated as locking everything. isDateInLockedPeriod becomes a one-line call to it. The helper is injected into every vm test context that loads firebase-data.js.
  • Data layer (js/firebase-data.js), each returning { ok, reason, … } and never throwing:
    • writeClockEntryIfUnlocked({ op, entryId, updates, entry, expectDate }) with op = 'update'|'delete'|'add'. For add, the new doc ref is allocated before the transaction (so a retry can't create a second one) and entry.date must pass isRealDate (bad-date otherwise). Inside one runTransaction, all reads come before any write: tx.get(lockedPeriods), plus for update/delete tx.get(entry). Missing → not-found. If expectDate is given and the stored date differs → changed (the caller built its timestamp for a date the entry no longer has). The date checked is the stored one (plus updates.date if one is ever sent). Locked → {reason:'locked', period}. Otherwise the write. The callback has no side effects besides tx.*, so a retry is safe.
    • reviewChangeRequest(entryId, decision, buildUpdates) for decision = 'approved'|'denied'. In one transaction it reads the lock doc and the entry. Missing → not-found. changeRequest.status !== 'pending' → {reason:'already-reviewed', status, reviewedBy}. For approve, a locked date → locked. Deny of a pending request is allowed even when locked. buildUpdates(storedEntry) builds the updates from the copy read inside the transaction (not the earlier, possibly cached read) and may return {error:'bad-time'} → {reason:'bad-time'} with nothing written.
    Any thrown error → {ok:false, reason:'error'}, logged. A transaction can't commit offline, so this fails closed.
  • Callers (js/app.js):
    • The three adminEdit* functions use writeClockEntryIfUnlocked. Save passes expectDate: entry.date.
    • handleChangeRequest uses reviewChangeRequest for both decisions. Its update-building moves into the buildUpdates callback. An empty time box now returns bad-time ("Enter a time before approving") instead of throwing with no message. The time conversion itself (browser-local new Date(date+'T'+time)) is left unchanged on purpose: it must match the Payroll Tool's identical parsing, and Ticker's managers are in Mountain Time. Recorded as a residual.
    • submitMissingPunch (both the single punch and the whole-shift branch) uses writeClockEntryIfUnlocked({op:'add'}).
    • One describeWriteRefusal(result, context) turns each reason into the messages above. On locked or already-reviewed the caller refreshes lockedPeriods / the list and re-renders.
    • In-flight guards: Delete reuses _aeeSaveInFlight; Add, Approve/Deny (per entry id) and Submit disable their button until the result comes back.
  • Editor courtesy note: openAdminEntryEditor (2428) reads getLockedPeriods() when it opens. A failed read leaves controls enabled, since the write still fails closed.

BDD

Happy: Given Sep 1–15 is unlocked, when a manager changes Kaitlyn's Sep 3 clock-out to 5:00 PM with a reason, then the entry updates, "Saved" shows, and the timesheet re-renders as today.
Locked edit: Given Sep 1–15 is locked by Anika, when a manager saves, deletes or adds an entry dated Sep 1, Sep 8 or Sep 15, then each is refused naming Anika, and the docs are identical before and after.
Boundary: Given Sep 1–15 is locked, an add dated Sep 16 or Aug 31 saves.
Locked mid-save (concurrency): Given the entry transaction has read lockedPeriods (unlocked) and is paused, when a lock commits, then the transaction retries and refuses. (This is the one property a read-then-write would fail.)
Stale date: Given the screen's copy says Sep 16 but the stored doc says Sep 17, when Save is pressed, then it's refused with "This entry changed since you opened it — reopen the day", and nothing is written.
Staff missing punch: Given Sep 1–15 is locked, when a staff member reports a missing clock-out (or a whole missed shift) for Sep 10, then it's refused and nothing is saved. Sep 16 saves as today.
Approve locked: Given a pending correction on a locked day, when Approve is pressed, then it's refused, the request stays pending and no push is sent.
Deny pending, locked: Given a pending request on a locked day, when Deny is pressed, then the denial saves and the push is sent.
Stale tab: Given a missed shift was approved (and the period then locked), when a stale tab presses Deny (or Approve again), then "already approved by …" shows and the stored request, timestamp and originalTimestamp are unchanged.
Empty time: Given the correction's time box is cleared, when Approve is pressed, then "Enter a time before approving" shows and nothing is written.
Failure: Given the lock read fails or the device is offline, when any of these saves runs, then it's refused with "Could not confirm…" and nothing is written. The button is usable again.
Gone: Given the entry was deleted elsewhere, an edit or review shows "That entry no longer exists — refresh" and creates nothing.
Malformed key / no lock doc: A key "oops" or "2026-02-30_2026-03-05" locks nothing. A missing lockedPeriods doc means nothing is locked.
Double click: Given Delete (or Add, Approve) is pressed twice quickly, then one write happens.

Accepted residuals (disclosed, not fixed here)

  • HIGH: anyone can bypass this from the browser console until item E. The rules let any staff member with Ticker access create their own entries and change any field of their own entries, and managers can write everything (firestore.rules:462). This plan protects Ticker's screens only.
  • HIGH (separate bug, D3): a single missing punch counts as paid even while pending or after it's denied. Fix next session with C (Christie, Oct 9). Workaround: delete a wrong missing punch in the entry editor instead of only denying it.
  • Sick leave (HFWA) isn't frozen by a lock. Christie's Sep 28 decision; payroll re-reads it live. Staff can still submit HFWA for a locked date.
  • Roster changes after a lock change attribution. A claim, merge or assign changes which uid an emp_* kiosk entry's hours belong to, in both Ticker's calcPeriodTotals and the Payroll Tool's pull (around index.html:3046). Recalculated totals can then differ from the locked ones, and the Payroll Tool's discrepancy warning shows. A lasting fix (freezing the mapping in the snapshot) belongs with D.
  • Several roster writers save the whole roster from the page's in-memory copy (e.g. setStaffPin, 6469), so two managers editing the roster at once can undo each other. Pre-existing; for the rules-hardening/roster follow-up.
  • An edit that lands between a manager's lock read and their confirm isn't in the snapshot they confirm. Rare; the Payroll Tool flags the discrepancy.
  • Kiosk punches aren't lock-checked (D1). Their date is today's, and a period is locked after it ends. Note that a late kiosk clock-out can carry a chosen earlier time (around 10346), but still on today's date.
  • Approval times are parsed in the browser's local time zone, the same way the Payroll Tool parses them. Correct for managers in Mountain Time; not changed here so the two apps stay identical.
  • Offline plain writes (Phase 2's rows) queue and resolve on reconnect, so offline they hang rather than show a message.
