Plan: Time Off Email Routing + Auto Sub-Assignment

Status: Drafted, not yet reviewed. Several open decisions below need Christie's answer before this is execution-ready — flagged inline, not guessed at.
Goal: Every time-off request is submitted through Ticker (not email), automatically notifies the right studio's coordinator by email, and confirming a sub writes their shift directly onto their schedule while removing it from the original requester — with zero manual re-entry either way.
Repo: ~/tinker-timeclock Ticker only — no Firestore rules changes. New external dependency: an email-sending service (see Phase 1).
Why now: Staff still request time off by email out of habit; Christie wants Ticker to be the single real channel, with automatic routing to the two people who actually act on these requests (Clay Hub → Maryssa, Tinker Art → Lauren, both cc'd to Anika) instead of relying on staff remembering who to email.
Risk: Low-medium. No rules changes, but this introduces the app's first real email integration (new API key, new failure mode: emails can silently fail to send in a way push notifications' existing fire-and-forget pattern already tolerates but a coordinator missing a real request cannot).

Current state (confirmed by reading the code, not assumed)

  • Neither Ticker nor Studio Hub has any email-sending code today — only web push (netlify/functions/send-notification.js, VAPID/web-push). A working reference pattern exists in a different Tinker app, Schedule Viewer (netlify/functions/send-reminders.mjs): Resend SDK, API key via RESEND_API_KEY env var, resend.emails.send({from, to, subject, html}). That file's own recipient map is unpopulated in practice — the pattern is real, the data isn't — so it's a reference, not something to literally reuse as-is.
  • Time off requests live in timeclock_timeoff, submitted via handleSubmitTimeOff() (js/app.js:6571-6676). On submit, it already calls sendPushToAllAdmins('New Time Off Request', ...) (js/app.js:6671) — this plan adds an email alongside that, it does not replace it.
  • No studio field exists anywhere on a time-off request or on a roster entry. Studio membership lives on the person's own users/{uid}.studios array (set in Studio Hub), and per-shift studio tags ('tinker'/'clayhub') live inside each day's shift object on their timeclock_schedules doc. See open decision below — routing has to be built from one of these, it doesn't already exist as a field to just read.
  • Sub proposals exist today only as free text. proposedSubs[] (js/app.js:6614) is {name, email, dates, confirmed} — plain strings a requester types in, not a resolved roster id. toggleSubConfirm() (js/app.js:6929-6948) only flips a confirmed flag and recomputes coverageStatus — it never touches anyone's actual schedule. There is no existing confirmSub-style function that writes a shift. This is genuinely new logic.
  • Removing the requester's shift on approval already exists and already works. approveTimeOff() (js/app.js:6963-6991) calls applyTimeOffOverrides(data.uid, data.dates) (js/app.js:7124-7153), which writes a null (day off) or partial-shift override into the requester's own schedule for each requested date, and removeTimeOffOverrides() reverses it on withdraw/deny/un-approve. Phase 3 below does not need to build this — it already ships. The only new work is the mirror-image write: putting the confirmed sub's shift onto their schedule.

Phase 1 — Email infrastructure

Acceptance criteria

Ticker can send a real email from a Netlify function, proven with one test send before anything is wired to real user actions.

Corrected after second-model review — commit to a concrete shared file, not just a "pattern." This plan originally described Phase 1 as "mirroring Schedule Viewer's test-reminder.mjs pattern" — checked directly, and that file (and its sibling send-reminders.mjs) each inline their own new Resend(...) call and their own non-exported HTML-template function. There is no actual shared, importable helper to reuse, even in the app being cited as the reference — it's a pattern to imitate, not code to import. Since the One-Off Shift Reminders plan explicitly depends on this phase producing something it can reuse (rather than standing up a second Resend integration), Phase 1 must produce one concrete, exported, shared function at netlify/functions/_lib/email.js (e.g. sendEmail({to, cc, subject, html})), that both this plan's later phases AND the One-Off Shift Reminders plan import directly — not each write their own.
Given a Resend API key is set as a Netlify env var, when a manual test function is invoked, calling the shared netlify/functions/_lib/email.js helper, then a real email arrives at a real test address.
Given the Resend API call fails (bad key, rate limit, network error), when the send function runs, then the failure is logged clearly (not swallowed silently like push notifications' fire-and-forget pattern) — a missed time-off email is a real operational miss, not a cosmetic one.

Firebase safety checklist

  • No Firestore writes in this phase — infrastructure only.
  • New secret: RESEND_API_KEY as a Netlify env var, never committed to the repo.
  • Deliverable is a real file at a fixed path (netlify/functions/_lib/email.js) — the One-Off Shift Reminders plan cites this exact path once it exists.

Phase 2 — Route submission emails to the right coordinator

Acceptance criteria

The moment someone submits a time-off request in Ticker, the correct coordinator gets a real email with the request details, cc'd to Anika — no one has to remember who to email or check the app.

Given a Clay Hub shift is requested off, when the request is submitted, then Maryssa receives an email with the requester's name, dates, and reason, cc'd to Anika.
Given a Tinker Art shift is requested off, when submitted, then Lauren receives the same, cc'd to Anika.
Given none of the requested dates have a resolvable shift (all already days off, so per-date studio lookup falls back to the requester's users.studios), AND that person belongs to zero or both studios, when submitted, then the fallback-of-fallback is explicit, not silently dropped: zero studios sends to neither coordinator but still visibly logs a warning (this should be rare enough to investigate, not silently swallowed); both studios sends to both coordinators, same as the multi-studio case above.
Given a request spans dates in both studios, when submitted, then both Maryssa and Lauren receive it, Anika cc'd once.
Given the email send fails for any reason, when that happens, then the request is still saved successfully in Firestore (existing behavior unaffected) and the failure is visibly logged — a broken mail integration must never block or lose a real time-off request.

Firebase safety checklist

  • New field on the timeoff request doc (requestStudios) — additive, no schema break for existing requests that predate this field.
  • No rules change — email sending happens in a Netlify function, not a Firestore rule.
  • await the email send but never let its failure roll back or block the already-working Firestore write.

Phase 3 — Auto-assign confirmed sub's shift

Acceptance criteria

When an admin confirms a specific sub for a time-off request and picks full-shift or custom times, that shift is written directly onto the sub's own schedule — no manual schedule editing needed. Removing it from the original requester already works today via the existing approve flow and needs no changes.

Pending Christie's answer to the ordering decision above — this BDD depends on it: if (a) [confirm works before or after approval]: given a time-off request has already been approved, when an admin confirms a proposed sub, then the schedule write still succeeds — canToggle was expanded to include the 'approved' status. If (b) [pre-approval only, unchanged]: given a request has already been approved, when anyone looks for a way to confirm a sub, then there correctly is none — matching today's actual behavior, not a bug.
Given a sub who matches exactly one active roster entry is confirmed, choosing "full shift," when confirmed, then the sub's schedule gets an override for that date matching the original requester's normal shift time for that day exactly.
Given an admin instead enters custom start/end times for the sub, when confirmed, then the sub's schedule override uses those custom times, not the requester's original ones.
Given the typed sub name has no matching active roster entry at all (state 2 of the three-state fallback above), when an admin tries to confirm, then they can still mark it confirmed, but see an explicit "no roster match — add their shift manually" note, and no schedule write is attempted.
Given the typed sub name matches a real roster entry that has never been claimed (claimedBy: null — state 3, distinct from state 2 above), when an admin tries to confirm, then the same "add their shift manually" outcome applies — no schedule write (no uid to write to) — but the note shown is specific to this case, e.g. "This person hasn't signed in yet — add their shift manually once they do," not the generic no-match message, so it's clear the roster entry exists and just isn't usable yet.
Given a sub is un-confirmed after being confirmed, when that happens, then the override written onto their schedule for that date is removed, mirroring how removeTimeOffOverrides() already reverses the requester-side write on withdraw/deny.
Given the sub already has their own shift scheduled that day (a genuine double-booking), when an admin tries to confirm them for the same date, then they see a conflict warning before the override overwrites their existing shift — never a silent overwrite.
Given a sub was confirmed (schedule write done) and then the underlying time-off request is withdrawn, denied, or edited back open, when that happens, then the sub-side override is also reversed — not just the requester-side one. withdrawTimeOff()/the edit-reopen path today only reverses the requester's own overrides via removeTimeOffOverrides(); this phase must extend that same reversal to also cover a confirmed sub's schedule write, or a sub can be left on a schedule for time off that no longer exists.
Given a sub declines after already being marked confirmed, when an admin un-confirms them, then in addition to reversing the schedule write (already covered above), a cancellation note is available — the confirmation email already sent to that sub is not retroactively unsendable, so the un-confirm flow should make it obvious to the admin that a follow-up message may be needed.
Given two admins act on the same request's proposedSubs[] at nearly the same time (e.g. one confirms sub A while another edits coverage notes), when both writes land, then neither is silently lost — proposedSubs updates must go through a transaction (read-modify-write), not a bare updateDoc, since this phase adds a real schedule write and an email send on top of what was previously a low-stakes flag toggle.

Firebase safety checklist

  • Writes to the sub's schedule are scoped overrides for the specific requested date(s) only — never a wholesale schedule replace.
  • Un-confirming must cleanly reverse the write, same pattern as the existing removeTimeOffOverrides() — and per the BDD above, withdrawal/denial/re-edit of the underlying request must also trigger this same reversal on the sub's side, not just the requester's.
  • proposedSubs[] updates in this phase must use a transaction, not a bare field update — see the concurrent-edit BDD above.
  • No rules change — this is a normal, already-permitted timeclock_schedules write.
  • Older, migrated time-off docs store proposedSubs[].dates as free-text strings, not the live form's array of ISO dates — this phase's date-handling logic must defend against both shapes rather than assume the array format everywhere.
  • Depends on updateTimeOffRequest() (js/firebase-data.js:465-477) actually awaiting and surfacing failures — like saveSchedule() (see Plan 1's shared prerequisite fix), this function is currently synchronous internally. Confirm that fix has landed before this phase ships, since it now carries a real schedule write and an email send on its result.

Phase 4 — Confirmation emails to sub and requester

Acceptance criteria

The moment a sub is confirmed (Phase 3), both the sub and the original requester get an email confirming the arrangement — through Ticker's own email integration, not a manually-sent Gmail message. Cross-reference: if the copied shift note still contains a One-Off Shift Reminders keyword (camp/SDOC/ FAN/Extra Shift), the sub will also get a separate 48-hour reminder from that plan later — confirmed with Christie as intentional, not a bug (see that plan's Decisions Log). No suppression needed between the two.

Given an admin confirms a sub with a schedule write that succeeds, when that happens, then the sub receives an email stating the date, time, and studio they're covering, noting it's already on their Tinker Ticker schedule.
Given the same confirmation, when it happens, then the original requester receives an email naming who is covering their shift and for which date(s).
Given a sub is confirmed with NO roster match (per the fallback in the decision above, no schedule write happens), when that happens, then the requester still gets a confirmation email naming the sub, but the sub themselves gets no auto-email (they're not a Ticker user — no address to send to from this system) and the admin is shown the same "add their shift manually" note as before.
Given a request needs two subs (e.g. Kayleigh covering mornings, Shelley covering afternoons) and they confirm on different days, when each one confirms, then that sub's pair of emails (to them and to the requester) fires immediately — per-sub, not held until the whole request reaches full coverage.

Firebase safety checklist

  • Email failure here must not roll back or undo the already-succeeded schedule write from Phase 3 — same "never let email failure break the real action" principle as Phase 2.
  • No rules change.

Completeness check

Phases are ordered by dependency: Phase 2 needs Phase 1's working send function; Phase 3 is fully independent of both and could ship first if useful on its own. If interrupted mid-Phase-2, the existing push-to-admins behavior and the Firestore write both keep working unaffected — email is strictly additive, never a required step for the request itself to succeed.
