The change (one phase, one commit)

Phase 1: publish an allowlisted dist/, delete the four admin tools, check the live site after every deploy

Acceptance (user outcomes):

  • After the deploy, the app works exactly as before: sign-in, clock in/out, schedules, time off, reminders view, offline (service worker), install icons. The Netlify functions still run (the hourly reminder job, emails, the preview endpoint).
  • The four admin pages, the notes, tests, logs, package.json, function sources and the worktree copy no longer serve their content on the live site. With the single-page fallback (/* → /index.html 200) they return the app's own index.html. This is checked on every deploy.
  • A file added to the repo root later is not published unless it is deliberately added to the allowlist.
  • Deploying is one command, npm run deploy. It refuses on a dirty or unpushed tree and uses the full sha as the deploy message, as the deploy rules require.

Changes:

  • Delete user-import.html, grant-timeclock-access.html, schedule-import.html, summer-camp-sync.html (Christie, Sep 30: "these were things written to get info into the app, now done"). They stay in git history; summer-camp-sync.html (built May 17, fixed May 27 f53788d) is the one worth recovering for Summer 2027.
  • scripts/build-dist.sh: rm -rf dist, then a pure copy of an explicit allowlist: index.html, manifest.json, sw.js, css/, js/, assets/. No transformation, so every deployed byte is a committed byte. sw.js stays at the root (a service worker's scope is its own folder).
  • netlify.toml: publish = "dist". functions = "netlify/functions", node_bundler and included_files = ["js/schedule-helpers.js"] are unchanged: functions are bundled from the source tree, not from the publish folder, so require('../../js/schedule-helpers.js') is unaffected.
  • scripts/deploy.sh + "deploy": "sh scripts/deploy.sh" in package.json, modelled on the Classbook's proven script. It refuses unless git status --porcelain is empty and git rev-list @{u}..HEAD is empty, then builds, runs netlify deploy --prod --dir dist --message "$SHA", then check-live.sh. It does not ask; Claude asks Christie before running it, as today.
  • scripts/check-live.sh, adapted to Ticker's single-page fallback:
    • Complete: every local src/href in index.html, every path in sw.js's APP_SHELL, and every icon in manifest.json exists in dist/.
    • Faithful: every file in dist/ is byte-identical live (cache-busting query).
    • Private: for each must-not-be-public path, the live body must equal dist/index.html (the fallback) or be a 404. If it equals the local file, or anything else, it FAILS. This is not a status check: the fallback makes everything 200.
    • Functions still deployed: /.netlify/functions/preview-shift-reminders answers (a refusal without the secret is expected; a 404 is a failure). Read-only; it never sends.
  • .gitignore gains dist/. .netlifyignore is deleted (it never worked, and a file that looks like protection is worse than none).
  • Docs: CLAUDE.md and AGENTS.md "Deployment" say npm run deploy (after Christie's "okay to deploy?"), not netlify deploy --prod.
  • Tests (wiring, no writes): the build allowlist covers every APP_SHELL entry, every local index.html reference and every manifest icon; the four pages are gone from the repo; netlify.toml publishes dist; check-live.sh treats "equals the fallback" as private and a 200 alone as nothing; deploy.sh refuses a dirty/unpushed tree and passes the sha.
Happy: Given the merged branch, when npm run deploy runs, then the app loads and signs in, check-live prints ok, /user-import.html returns the app shell, and /CLAUDE.md returns the app shell.
Edge: Given a new file notes.md dropped at the repo root, when deploying, then it is not in dist/ and is not published.
Edge (offline): Given an installed app with the v24 cache, when it next loads after the deploy, then sw.js v25 installs and caches every APP_SHELL file (none 404, because the build is complete).
Failure: Given an uncommitted change or an unpushed commit, when npm run deploy runs, then it refuses before building or uploading anything.
Failure: Given check-live finds a mismatch or a leaked path, then it exits non-zero and says which. The deploy has already happened, so the fix is a follow-up deploy or a rollback in the Netlify UI to the previous deploy.

Firebase safety checklist

  • No Firestore reads/writes, rules, collections or indexes change. No data migration.
  • Functions: unchanged source, and the same bundler config. The check confirms they're still deployed.

Completeness check

One commit. Before the deploy nothing is live, so an interrupted change is just an unmerged branch. A deploy that goes wrong is rolled back by republishing the previous deploy in Netlify's UI (instant, no build). The page deletions are reversible from git history.
