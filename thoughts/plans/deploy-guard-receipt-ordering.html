The bug, and the measured baseline

deploy-rules.sh:76 orders receipts by --sort=-refname. Names are …/<UTC yyyymmddTHHMMSSZ>-<sha7>; the stamp has second resolution, so two deploys in one second tie and the tie breaks on the sha7 — which carries no order at all. Nine baseline runs of the guard suite on this branch, before any change:

90/0  90/0  87/3  89/1  90/0  90/0  89/1  90/0  90/0      → 3 of 9 failed

Mechanism, independently re-verified by a reviewer: at deploy-rules.test.sh:127 the third deploy reads the record at :218 before writing its own receipt, sees two receipts tied on stamp, and picks by sha7. When it picks the SHA2 one the diff is SHA2 → SHA2 — empty.

Two harms, not one. A wrong diff — and worse, a mis-picked receipt that points at origin/main makes --status print “nothing to deploy” (:125–126), so the operator walks away from a change that never shipped. Silent, with no diff to contradict it.
Current real-world exposure is nil, and the flake is the actual blocker. The repo holds exactly one receipt, so there is nothing to mis-order. But the guard runs npm test at :236, which includes the flaky guard suite, so roughly 1 deploy in 3 aborts on a flake unrelated to the rules being shipped. Fixing the bug fixes the flake.

What ships

1. The order: (name stamp, tag date, refname), descending

KeyJustification
1. name stampThe stamp is not a time this script observes — it is one the script writes, and that hand-recovery transcribes (:258 prints the tag name for the operator to copy). A receipt written 49 minutes late still carries deploy time; the tag date cannot survive that transcription. That asymmetry is the whole argument, and it is why ordering by tag date was tried, reviewed and reverted (d43a171). Permanently off the table.
2. tag dateBreaks exact stamp ties only — where it is the only evidence there is.
3. refnameDeterminism only; carries no chronology.
Pinned, because a single-timezone test harness cannot catch this (found and verified in review round 3): 
%(creatordate:format:%Y%m%dT%H%M%SZ)             → 20260921T165412Z   WRONG — tagger-LOCAL time wearing a fake "Z"
TZ=UTC %(creatordate:format-local:…)             → 20260921T225412Z   correct
%(creatordate:unix)                              → 1790031252         correct, timezone-free
%(creatordate:iso)  (the truth)                  → 2026-09-21 16:54:12 -0600
The tie-break key is %(creatordate:unix), compared numerically. Any human-readable UTC display uses TZ=UTC + format-local. Using format: would print a false time to Christie and invert the ordering between clones in different timezones, while every fixture in a single-timezone harness still passed.

2. One receipt predicate — used by the reader AND the writer

A receipt is a ref under this target's namespace that is:

  1. an annotated tag — step 9 writes nothing else, and a lightweight tag has no date of its own (git reports the pointed-to commit's date, which for a rollback is not deploy time at all);
  2. named with a stamp that is a real UTC date-time (full calendar validation, leap years included — arithmetic in the same awk pass, so no subprocess per ref and no BSD/GNU strptime divergence); and
  3. stamped no later than its own tag object was written (stamp ≤ creatordate).

Rule 3 in v5 is time-independent, and that is the point. The script reserves the stamp before the release and tags after it, so a genuine receipt always satisfies stamp ≤ its own tag date — including one written by a clone whose clock is wrong, because both values come from that same clock. A tag naming a time after it was itself written was fabricated.

Crucially this compares two values frozen in the tag object, never against now. v4's rule compared the stamp to now and both reviewers broke it: a legitimate receipt from a 2-seconds-fast clone was excluded, a later deploy wrote a lower stamp, and then the excluded receipt aged into validity and won permanently. Nothing can age in or out under v5's rule.

Verified on four fixtures:

seeded receipt (faithful late recovery)   stamp 22:05, tagged 22:54     → RECEIPT
script-written                            stamp 10:00, tagged 10:00:30  → RECEIPT
clock-skewed clone (+2s)                  stamp == tagdate              → RECEIPT   ← v4's rule broke this
planted year-2999 junk                    stamp ≫ tagdate               → excluded  ← permanently

3. Reads fail closed

A failed git for-each-ref must never read as “no receipt yet” — d43a171 put it inside a command substitution feeding a here-string, discarding its exit status, and the guard printed “the whole file is new to the record” with no diff and carried on. Four rules, all verified on this machine (bash 3.2.57):

  • local x on its own line, then x="$(…)" || return 1. Verified: local y="$(exit 7)" → status 0 (masked); separate → status 7.
  • Every call site uses an explicit || die $EX_RECORD "…" — bare set -e exits with no message.
  • Every fallible command inside those functions carries its own || return 1: set -e is suppressed inside a function invoked in a || die context.
  • No | head -1 under pipefail (head exits early, sort takes SIGPIPE, and a healthy read becomes a refusal) — use awk 'NR==1'. LC_ALL=C on any shell-side sort, because BSD sort under en_US.UTF-8 does not give byte order for - and /.

EX_RECORD=19 is the one new refusal, and it fires only when the record genuinely cannot be read — strictly better than today's silent wrong answer, and unreachable on a healthy repo.

4. The monotonic stamp reservation moves BEFORE the release

A new receipt must be strictly newer by stamp than every receipt recorded for this target — not merely not-a-duplicate. That is what makes the key monotonic and the flaky test deterministic by construction.

Before the release, never after. :253's existing dedup loop moves here — it is not duplicated and it does not stay. Today it can sleep 1 after production changed, widening the window between “production changed” and “a receipt exists”; a Ctrl-C there leaves production changed with no record. The release takes far longer than the wait, so this costs nothing.

Two conditions — stale stamp, and name already taken — evaluated independently, never chained on || (chaining is how d43a171's capped path silently skipped the collision check). If the wait cannot succeed within a small bound, the guard prints a fact naming the blocking receipt and proceeds. It does not refuse: a refusal here would let one stray tag brick the only sanctioned deploy path for all 21 apps, which is precisely the failure that got v3's design rejected. Consequence documented: at= becomes the instant the stamp was reserved, immediately before the release.

5. The answer carries its evidence

--status and the replaces: line print the winning receipt's tag date (true UTC) and its by= provenance beside its stamp. No threshold, no alarm, no refusal — facts, so a human can see at a glance that a receipt was hand-written rather than having the guard guess about it.

Deferred to its own plan — with reasons

  • R1 (refuse when a tag's at= contradicts its name). Sound in principle and cheap, but round 3 showed the missing-at= case bricks under the natural implementation, and the field needs anchored parsing. Needs specifying, not guessing.
  • F2/F3 (report same-stamp ties and excluded refs) and making --status's conclusion line conditional. Wording-level and safe, but each needs its own tests; not required to fix the bug.
  • Phase 2 — the unrecorded deploy (:257's failed git tag -a writes no marker). Round 3 found the marker is never cleared on the success path, the pre-release guard emits a post-release message, and the idempotency comparison is undefined. A real bug worth fixing, in a plan that specifies the state machine.
  • Cross-clone serialization. Out of scope; cross-clone misordering is undetectable from local git evidence and is stated as a limit in the script header.

Phase 1 — the only phase

Acceptance criteria (user outcomes):

  • A receipt written by hand after a later deploy does not become “what shipped last”.
  • A tag in the namespace that is not a receipt is never named as what shipped last.
  • If the record cannot be read, the guard refuses and says so — never “no receipt yet”.
  • Every answer shows when the receipt's tag was written and who wrote it.
  • The guard suite passes every run, because the guard is deterministic — not because a test sleeps.
  • Nothing that deploys successfully today is refused after this change.
Happy: Given receipts A (stamp 08:00, hand-tagged 11:00) and B (stamp 09:00, tagged 10:00) When --status Then B is named, with its true UTC tag date and by= shown.
Edge: Given a lightweight tag, an annotated tag with an unparseable name, an impossible calendar stamp, and a planted year-2999 tag all in the namespace When --status Then none is ever named.
Edge: Given a receipt from a clone whose clock is 2s fast When a deploy runs Then it IS a receipt, the writer waits past it, and the new stamp is strictly greater.
Failure: Given git for-each-ref fails When --status Then EX_RECORD and a sentence saying the record could not be read — not “no receipt yet”, no empty diff.

Tests

Four vacuous assertions have now been caught — one shipped, three proposed. All passed while the bug was present: d43a171's “name order and date order agree” (any tie degenerates both sorts to refname); v1's “4th deploy's replaces: names the 3rd receipt” (:253's dedup loop already sleeps on a name collision); v3's “recover A, assert B still wins” (today A leaves no receipt at all, so B wins trivially); and v4's F1 display, which a single-timezone harness cannot distinguish from the wrong format: spelling.
Standing rule, written into the test file's header: never assert that two orderings agree, and never assert distinctness where you mean order. Assert on values — stamps, receipt names, the text of replaces:, diff content, exit codes.
  • Stamps strictly increasing (an ordered comparison, never sort -u | wc -l) across three back-to-back deploys with three distinct shas — with a repeated sha the old writer's dedup loop yields C, C, C+1 instead of C, C, C and the test would pass for the wrong reason.
  • Every predicate exclusion: lightweight; unparseable name; impossible calendar stamp (20260931T120000Z, 20260229 in a non-leap year, 20260921T990000Z); stamped-after-written. Each sorts above the real receipt under -refname, so today's reader names each of them.
  • The clock-skew case: a receipt stamped 2s ahead but consistent with its own tag date is still a receipt and still constrains the writer. This is the case v4's rule broke.
  • Timezone: two receipts at the same name stamp whose tag objects carry different UTC offsets; assert both the resulting order and the printed time. A single-offset fixture cannot catch the format: trap.
  • Failed ref read → EX_RECORD, via a transparent git wrapper on the harness PATH, inert unless a switch is set, and scoped to the guard invocation (FAIL_GIT=… run …) rather than exported, or it corrupts the harness's own fixture setup.
  • Synthesized real-receipt shape (annotated, by=seeded, 49-minute skew) → still named. Labelled as a regression pin, not a forced case — it passes today too.
  • Negative assertions: a healthy record prints no exclusion notice and no blocking-receipt notice. Without these, an implementation that reports unconditionally passes the whole battery. run() captures stderr into $OUT, so an over-eager message is otherwise invisible.
