Plan: Deploy guard — receipt ordering (“what shipped last”)

Repo: ~/studio-hub · scripts/deploy-rules.sh, scripts/deploy-rules.test.sh only · Drafted Sep 22 2026 · v4 — after two two-model plan reviews (Claude + Codex), both rounds request-changes · execution-ready: false · Under the Firebase deploy guard plan. No rules change, no data change, no deploy.

Goal. The guard never presents a guess as a fact. It names the receipt it used, states what else it could have used, and refuses only when a tag's own contents contradict themselves. It does not claim to always know what shipped last, because it cannot.

The bug, and the measured baseline

deploy-rules.sh:76 orders receipts with --sort=-refname. Names are …/<UTC yyyymmddTHHMMSSZ>-<sha7>; the stamp has second resolution, so two deploys in one second tie and the tie breaks on the sha7 — no order at all. Nine baseline runs of the guard suite on this branch, before any change:

90/0  90/0  87/3  89/1  90/0  90/0  89/1  90/0  90/0      → 3 of 9 failed

Mechanism, verified and independently re-verified by a reviewer: at deploy-rules.test.sh:127 the third deploy reads the record at deploy-rules.sh:218 before writing its own receipt, sees two receipts tied on stamp, and picks by sha7. When it picks the SHA2 one the diff is SHA2 → SHA2 — empty.

The harm is not only a wrong diff. A mis-picked receipt that points at origin/main makes --status print “nothing to deploy” (:125–126) and the operator walks away from a change that never shipped — silent, with no diff to contradict it.
d43a171's approach stays permanently off the table. It ordered by tag creation date. The one real receipt was hand-written 49m12s after the deploy it records (by=seeded), and the script's own EX_RECEIPT path instructs operators to hand-write receipts.

Part 1 — The ordering model (endorsed 4/4; unchanged)

The order: (name stamp, tag date, refname), descending

KeyJustification
1. name stampThe stamp is not a timestamp the script observes — it is a value the script writes and that hand-recovery transcribes (:258 prints the recovery command with $TAG already interpolated). A receipt written 49 minutes late still carries deploy time. The tag date is the only field that cannot survive that transcription. That asymmetry is the whole argument.
2. tag dateConsulted only inside an exact stamp tie. Honest about its worth: after the write-side reservation, a same-clone same-second tie cannot be produced by the script at all. It exists to make --status deterministic, so two sessions comparing notes get the same string — not to establish history.
3. refnameDeterminism only. Carries no chronology.

Verified on a hand-built fixture (explicit GIT_COMMITTER_DATE; far-future dates need the epoch form @32503680000 +0000, because git rejects 2999-01-01T00:00:00 +0000 outright):

ReaderPicks
today's -refnamenot-a-stamp-xxxxxxxa malformed tag — not a receipt at all
reverted -creatordate29990101T000000Z-lighta lightweight tag
this plan20260922T090000Z-bbbbbbbthe receipt that genuinely shipped last

The receipt predicate — one definition, used by reader AND writer

A receipt is a ref under refs/tags/<TAG_PREFIX> that is:

  1. an annotated tag (objecttype == tag) — a lightweight tag has no date of its own; and
  2. named with a stamp that is a real UTC instant, and
  3. whose stamp is not in the future.

Rule 3 is the one structural change in v4, and it is the highest-risk new idea here — reviewers should attack it first. A receipt's stamp asserts “I shipped at time T”. If T is in the future that assertion is false, so the tag is corrupt by definition — exactly like a malformed stamp. Treating it as a non-receipt rather than as evidence collapses four separate v3 problems at once:

  • A far-future tag can no longer dominate the ordering, so the reader is never poisoned by one (v3 left the bogus tag winning forever even after the override — Claude 1g).
  • It can no longer trap the writer, so v3's three-way clock split, its cap, and its --accept-out-of-order-receipt override all become unnecessary and are deleted.
  • The wait now terminates in ≤1 s by construction: a valid stamp is ≤ now, so now exceeds it unless they are equal, and one second fixes that. A wait that doesn't terminate now means a genuinely stopped or backwards clock — a real, reportable fault rather than a guess.
  • Impossible-but-well-shaped stamps (20269999T999999Z, 20260921T990000Z) are handled by the same rule rather than by luck.

Cost, stated honestly: if a future-stamped tag does record a real deploy (a clone with a fast clock), the guard reports an older receipt as what shipped last. That is why exclusion is never silent — see F3.

Validation is arithmetic, not date parsing: range-check the fields in the same awk pass (month 1–12, day 1–31, hour ≤23, min/sec ≤59) and compare the stamp against a single “now” stamp taken once. No subprocess per ref, no BSD/GNU strptime divergence, no set -e abort on a parse error. Verified: this rejects 20260921T990000Z and 20261332T100000Z and accepts valid stamps. Accepted limit: it admits 20260229 in a non-leap year — harmless for ordering, and noted rather than hidden.

Do not tighten the predicate to require by=deploy-rules.sh. The real receipt says by=seeded and would vanish from the record.

Reads fail closed

A failed git for-each-ref must never read as “no receipt yet” — d43a171 put it inside a command substitution feeding a here-string, discarding its exit status, and the guard then printed “the whole file is new to the record” with no diff and carried on. Three rules, all verified on this machine (bash 3.2.57):

RuleWhy
local x on its own line, then x="$(…)" || return 1 Verified: local y="$(exit 7)" → status 0 (masked); separate → status 7.
Every call site uses an explicit || die $EX_RECORD_READ "…" Bare set -e would exit with no message at all.
Every fallible command inside those functions carries its own || return 1 New, from review round 2. set -e is suppressed inside a function invoked in a || die context, so failures inside it are otherwise ignored. The outer rule alone is not enough.

Shell traps that must not be dropped again (they are the same class that killed the first attempt): no | head -1 under pipefail (head exits early, sort takes SIGPIPE, and a healthy read becomes a refusal) — use awk 'NR==1'; and LC_ALL=C on any shell-side sort, because BSD sort under en_US.UTF-8 does not give byte order for - and /, and byte order is what fixed-width stamp comparison assumes.

Part 2 — Facts, not warnings (this replaces v3's H1–H4)

Three of these are statements printed with the answer, not alarms. One is a refusal. Nothing here has a threshold, and nothing can brick the deploy path.

ConditionBehaviour
F1 always Print the winning receipt's provenance and tag date beside its stamp — in --status, in the --diff header, and on the replaces: line (:227). e.g. replaces: …/20260921T220500Z-1da12e3 (1da12e3dbb3c) — tag written 22:54:12Z, by=seeded. This is what v3 tried to achieve with a skew alarm: it turns an invisible model assumption into something a human can check, with no threshold to get wrong and no day-one noise.
F2 more than one receipt shares the maximum stamp and they point at different commits Say so with the answer, naming every candidate and its commit, and proceed. If the tied candidates resolve to the same commit the answer is forced for every purpose the guard has, so nothing is printed. No refusal: v3 refused here and both reviewers showed it deadlocks — a tie never resolves with time, and the only way to add a newer receipt is a deploy, which the refusal blocks.
F3 refs under the namespace excluded by the predicate (lightweight, malformed, or future-stamped) Say so, naming them and why. Never silent: an excluded ref may be the record of a real deploy. A future-stamped one is called out specifically, because rule 3 is what excluded it.
R1 the winner's at= field disagrees with its own name stamp REFUSE (EX_RECORD_CORRUPT) on --approved and --diff.
Why R1 is the one check worth keeping, and why it cannot misfire. The script writes the name stamp and at= from the same shell variable, so a script-written receipt can never trip it. A human editing the printed git tag -a command will change the stamp in the tag name and is very likely to leave at= at its original value — which is precisely the improvised-recovery case that every other detector misses. A tag whose own body contradicts its own name is unambiguously corrupt, so refusing needs no threshold and no judgement. Verified on the real receipt: name stamp and at= both 20260921T220500Z — it passes.
Stated plainly in the plan and in the script header, because it is the honest limit: a hand-written receipt whose name stamp, at= and tag date are all consistently improvised is undetectable from local git evidence. No check in this plan catches it. Phase 2 is the mitigation — it removes the human from the timestamp — which is what makes Phase 2 load-bearing rather than a bonus. Likewise, cross-clone misordering (A reserves 10:00:00 and finishes last; B reserves 10:00:01 and finishes first) produces two valid, unique-stamped receipts and is completely undetectable, not merely unknowable.

All of F1–F3 print via say() to stdout, not warn() to stderr. “Above the diff” is a stream-ordering claim that does not survive a piped or captured transcript, and the workflow is that Claude runs --diff and Christie reads that output.

Part 3 — The write side

A new receipt must be strictly newer by stamp than every receipt recorded for this target — not merely not-a-duplicate. That is what makes the primary key monotonic and the flaky test deterministic by construction.

Before the release, never after — and this is now a stated constraint, not a happy consequence. d43a171 waited after firebase deploy returned, opening up to ten seconds in which production had changed and neither a receipt nor a marker existed. Nothing new may be able to fail between :243 and :260; the reservation must not cd into or touch $TMP or anything the predeploy hook hashes.

Sequencing, pinned (v3 left this ambiguous and one reading defeated the argument):

WhereWhat
after step 1's reconcile, before the teststhe record health pass (F1–F3, R1). It needs only the ref list, so an R1 refusal costs one second instead of a full rules suite.
immediately before step 8the reservation loop: take a stamp, test monotonicity (over receipts) and name collision (over all refs) — evaluated independently, never chained on ||, which is how d43a171's capped path skipped the collision check. Also compute HASH here ($TMP/$FILE is immutable from :208), so Phase 2's marker is complete before the release.
—:253's existing post-release dedup loop MOVES here. It does not stay and it is not duplicated. Today it can sleep 1 after production changed; that is removed.

If the loop cannot get a strictly-newer stamp within a few seconds, that now means a stopped or backwards clock (see rule 3), so it refuses pre-release with EX_CLOCK — free, because nothing has shipped. Consequence documented: at= becomes the instant the stamp was reserved, immediately before the release.

Phases

Phase 1 — reader, writer and tests, as ONE atomic change

Reader and writer land together. Reader-alone reduces the same-clone flake by zero (both keys have one-second resolution, so a same-second pair ties on both and still falls through to sha7), and shipping a phase whose known effect is “the gate stays flaky” trains operators to re-run until green.

Acceptance criteria (user outcomes):

  • A receipt written by hand after a later deploy does not become “what shipped last”.
  • Every answer carries its evidence — which receipt, when its tag was written, who wrote it.
  • When two receipts are equally recent and disagree about the commit, the guard says so and names both, instead of picking one silently.
  • A tag whose own body contradicts its own name stops the deploy.
  • A tag in the namespace that is not a receipt is never named as what shipped last, and never silently ignored.
  • If the record cannot be read, the guard refuses and says so — never “no receipt yet”.
  • The guard suite passes every run, because the guard is deterministic — not because a test sleeps.
Happy: Given receipts A (stamp 08:00, hand-tagged 11:00) and B (stamp 09:00, tagged 10:00) When --status Then B is named, with its tag date and by= shown, and nothing warns.
Edge: Given two receipts sharing the max stamp but pointing at different commits When --approved Then both are named with their commits, the deploy proceeds, and the chosen base is stated explicitly.
Edge: Given a stray future-stamped annotated tag When a deploy runs Then it is not a receipt, F3 names it and says why, the deploy is not stalled or refused, and it completes at normal speed.
Failure: Given a receipt whose at= says 22:05 but whose name says 23:10 When --approved Then EX_RECORD_CORRUPT, the message names the contradiction, and firebase was never called.
Failure: Given git for-each-ref fails When --status Then EX_RECORD_READ and a sentence saying the record could not be read — not “no receipt yet”, no empty diff.

Phase 2 — the unrecorded deploy: a failed git tag -a must leave a marker

Separate commit, after Phase 1. Load-bearing, not a bonus — it is the only mitigation for the undetectable improvised-timestamp case above.

The bug (pre-existing). Step 9 treats its two failure paths differently: a failed git push (:262) writes $PENDING and the next run reconciles; a failed git tag -a (:257) writes nothing, so production has changed, nothing records it, and the next deploy proceeds as if nothing happened.

Design — recover faithfully. The human typing a timestamp is the corruptor, so remove the human from the timestamp. Everything needed is computed before the release (sha, reserved stamp, target, sha256, the exact message), so the post-release step is a single atomic publish. The next run rebuilds the receipt with its original stamp. Two marker files, not one overloaded format — a $PENDING entry naming a tag that does not exist would fail [ "$LOCAL_O" = "$PO" ] at :178 and produce a misleading refusal.

Defect found in reviewv4

bare printf > marker aborts silently under set -e — and a full/read-only disk is the most likely cause of both the tag failure and the marker failure guarded: || { print the full hand-write instructions; exit $EX_RECEIPT; } — never a bare redirect

Precedence if both markers exist: $PENDING first.

Happy: Given a deploy succeeded but git tag -a failed When the guard runs again Then it rebuilds that receipt with its original stamp, pushes it, says what it did, clears the marker, and proceeds.
Edge: Given the marker exists AND the operator already hand-wrote the tag When the guard runs Then it recognises the tag as matching, clears the marker, and proceeds — no deadlock.
Edge: Given a marker in the OLD $PENDING format When the guard runs Then it behaves exactly as today; deploy-rules.test.sh:170–191 stays green, unmodified.
Failure: Given the marker exists and the rebuild also fails When the guard runs Then it refuses with the new code, names the live-but-unrecorded commit, prints the literal commands, and firebase is never called.

Tests

Three vacuous assertions have now been caught — one shipped, two proposed. All three passed while the bug was present:
  1. d43a171's “name order and date order agree” — under any tie both sorts degenerate to refname.
  2. v1's “a 4th deploy's replaces: names the 3rd receipt” — :253's dedup loop already sleeps when names collide, so the 3rd receipt lands a second later with or without the fix.
  3. v3's “deploy A with the tag write failing, deploy B, recover A; assert --status names B” — today A leaves no receipt at all, so B is trivially named. Fixed: assert A's receipt exists with A's original stamp and sorts before B's. That is the part that fails today.
Standing rule, written into the test file's header: never assert that two orderings agree. Assert on values — stamps, receipt names, the text of replaces:, diff content, exit codes.

Determinism by controlled time

A fake date on the harness PATH serves the stamp from a counter file; a fake sleep advances it. Two traps pinned, both from review:

  • The fake intercepts only date -u +%Y%m%dT%H%M%SZ with no other flags and delegates every -v/-j/-f/-r form to the real date. (The guard also uses date for the lock owner line.)
  • The counter holds real epoch seconds, formatted through the real date — otherwise it breaks at the 59→60 boundary and the guard's comparison starts failing on a clock that “advanced”.

Tag dates stay deterministic via explicit GIT_COMMITTER_DATE on git tag -a (verified). The transparent git wrapper (for the failed-ref-read case) takes its switch scoped to the guard invocation — FAIL_GIT=… run --status — never exported, or it corrupts the harness's own fixture setup.

The battery — every case forced, none hoped for

  • Stamps strictly increasing across three back-to-back deploys, each captured from that run's own receipt: line. Use three DISTINCT shas — with a repeated sha the old writer's dedup loop produces C, C, C+1 rather than C, C, C, so the fixture must avoid the name collision for the test to fail for the right reason.
  • Delayed hand-recovery (08:00 tagged 11:00 vs 09:00 tagged 10:00) — labelled as an F1 test, not an ordering test: today's -refname already picks the same winner, so the ordering half passes while the bug is present.
  • R1: annotated receipt, name stamp now, at= an hour earlier → refused, firebase never called.
  • Predicate, all three exclusions: a lightweight future tag; an annotated not-a-stamp-abc1234 (which sorts above every real receipt under refname); an annotated 20269999T999999Z and a 20260921T990000Z → none is ever named, each appears in F3.
  • Predicate parity, both directions in one test: a future lightweight tag → the writer must not wait or refuse; this is d43a171's asymmetry exactly.
  • F2: two receipts at the max stamp pointing at different commits → both named, deploy proceeds; and pointing at the same commit → nothing printed.
  • Failed ref read → EX_RECORD_READ.
  • Synthesized real-receipt shape (annotated, by=seeded, 49-minute skew, at= matching the name) → still named as what shipped last, and nothing warns. The harness builds a throwaway repo, so this is synthesized, not read from the real one.
  • Negative assertions — every check gets a “stays silent on a healthy record” test. Without these an implementation that reports unconditionally passes the whole battery. run() captures stderr into $OUT, so an over-eager message is otherwise invisible.
  • Phase 2: marker written on tag failure (fails today); faithful rebuild uses the original stamp (asserted equal to the one captured from the first run, which catches a “recovery” that silently re-stamps); rebuild when the tag already exists → no deadlock; legacy $PENDING untouched.
