Plan: Deploy guard — receipt ordering (“what shipped last”)

Repo: ~/studio-hub · scripts/deploy-rules.sh, scripts/deploy-rules.test.sh only · Drafted: Sep 22 2026 · execution-ready: false · Under the Firebase deploy guard plan (this is a correctness fix to its step 9 and its reader). No rules change, no data change, no deploy.

Goal. When the guard says replaces: <receipt> and prints a diff, that diff is against what actually shipped last — including when receipts were written by hand, landed in the same second, or came from another clone. And when the record is genuinely ambiguous, the guard says so rather than picking silently.

Why this plan exists (read this first)

The diff the guard prints at step 6 is the thing Christie reads before saying the approval phrase. Its base is whatever latest_receipt() calls “what shipped last”. If that is the wrong receipt, the approval is given against a diff that does not describe the change — in the worst case an empty diff, when the wrongly-chosen base happens to be the commit being deployed.

The bug, precisely

scripts/deploy-rules.sh:76 today:

latest_receipt() { git for-each-ref --count=1 --sort=-refname --format='%(refname:short)' "refs/tags/${TAG_PREFIX}"; }

Receipt names are deployed/<project>/<slug>/<UTC yyyymmddTHHMMSSZ>-<sha7>. The stamp has second resolution, so two deploys inside one second tie on the name, and -refname breaks that tie on the trailing sha7 — which carries no order at all. Measured on this branch, before any change, nine consecutive runs of npm run test:guard:

run 1: 90 passed, 0 failed     run 4: 89 passed, 1 failed     run 7: 89 passed, 1 failed
run 2: 90 passed, 0 failed     run 5: 90 passed, 0 failed     run 8: 90 passed, 0 failed
run 3: 87 passed, 3 failed     run 6: 90 passed, 0 failed     run 9: 90 passed, 0 failed

Three of nine. The failing assertions are the rollback case at scripts/deploy-rules.test.sh:127 and the --status/--diff block — exactly the places that read the record.

The first attempt (d43a171) was reverted, and its approach is off the table. It ordered by the tag object’s creation date (--sort=-creatordate). A tag’s creation date is not deploy time in this repo. The only real receipt, deployed/tinker-hq-apps/firestore-rules/20260921T220500Z-1da12e3, was written by hand 49 minutes after the deploy it records — verified again for this plan: name stamp 22:05:00Z, tag date 2026-09-21 22:54:12Z, body says by=seeded. Hand-writing receipts is not an accident here: the script’s own EX_RECEIPT path instructs the operator to do it. Date ordering reads a hand-written receipt as newest even when a genuinely later receipt exists, which is a worse failure than the one it fixed — reachable by ordinary recovery practice rather than by a same-second race. Both reviewers (Claude and Codex, Sep 22) independently said the same thing.

The ordering model — this is the part to review

Everything else here is mechanics. If this model is wrong, the code will be wrong however clean it looks — which is precisely how the first attempt passed fifteen green runs and was still incorrect.

1. One receipt predicate

A receipt is a ref under refs/tags/<TAG_PREFIX> that is (a) an annotated tag (objecttype == tag), and (b) named with a well-formed stamp: the text before the first - after the prefix matches ^[0-9]{8}T[0-9]{6}Z$.

The same predicate is used by the reader and by the writer’s monotonicity lookup. The previous attempt filtered lightweight tags when reading but counted them when ordering, so a stray lightweight tag was “not a receipt” for --status yet still able to stall every deploy for ten seconds.

Why annotated: step 9 writes nothing else, and a lightweight tag has no date of its own — git reports the pointed-to commit’s date, which for a rollback receipt is not deploy time at all. Why well-formed name: an unparseable name cannot be placed in the order, and the alternative (treating it as the smallest or the largest) invents an answer.

2. The order: (name stamp, tag date, refname), all descending

KeyWhy it is where it is
1. name stamp The name stamp IS deploy time. The guard writes it from date -u at the moment of the release, and a hand-written recovery receipt is told to reproduce the stamp of the deploy it records. It is the only field that means “when did this ship” under both ways receipts get created.
2. tag date Breaks same-stamp ties only. Within one second, two guard-written receipts really were created in the order their tag objects were created, so here the tag date is meaningful. Across different stamps it is not, which is why it is second and not first.
3. refname Last, for determinism alone. It carries no chronology (it ends in a sha7). Its only job is that two runs of the guard over the same refs give the same answer.

git for-each-ref cannot sort on a substring of a refname, so the stamp has to be parsed out. One awk pass over a --format line does the filtering and the max-tracking together, which keeps the predicate and the order in one place. Verified against a hand-built fixture (scratch repo, explicit GIT_COMMITTER_DATE on each tag — four refs: a correctly-ordered receipt pair where the older-named one was tagged an hour later, one lightweight tag with a year-2999 name, one annotated tag with an unparseable name):

ReaderPicks
today’s -refnamenot-a-stamp-xxxxxxxthe malformed tag — not a receipt at all

this plan20260922T090000Z-bbbbbbbthe receipt that genuinely shipped last

3. Ambiguity is reported, not resolved

Neither key is total once receipts can come from a second clone or a human’s hand. So the reader computes the winner twice — once by (stamp, date, refname), once by (date, stamp, refname) — and warns when they differ, naming both and saying which one it used and why.

This warning is self-clearing, which is what makes it tolerable. It fires only while the disagreement sits at the top of the record — i.e. only while it could actually change the answer. The next ordinary guarded deploy writes a receipt that is newest under both keys, and the warning stops. On the real repo today (one receipt) it does not fire at all.

This is the only measure that covers the two-clone case, where neither key is total and no local rule can be.

4. Reads fail closed

A failed git for-each-ref must not read as “no receipt yet”. In the reverted attempt the call sat inside a command substitution feeding a here-string, which discards its exit status: a failed read returned '' and the guard printed “no receipt yet — the whole file is new to the record” with no diff, then carried on. So: capture into a variable with || return 1, declare local on a separate line from the assignment (local x="$(cmd)" masks the substitution’s status), and let callers die with a distinct code. Verified: the capture form returns status 1 when git cannot read refs.

5. The write side reserves a strictly-newer stamp BEFORE the release

The reader’s primary key is only as good as the writer’s guarantee. A new receipt must be strictly newer by stamp than every receipt already recorded for this target — not merely not-a-duplicate. That is what makes the primary key total and monotonic, and it is what makes the flaky rollback test deterministic by construction.

Before the release, never after. The reverted attempt waited after firebase deploy returned, opening a window of up to ten seconds in which production had changed and no receipt and no pending marker existed — a Ctrl-C there leaves the next --status confidently naming the wrong receipt. Reserving the stamp first costs nothing (the release takes far longer than the wait) and the window goes back to what it was. Consequence to document: at= in the tag body becomes the instant the stamp was reserved — immediately before the release rather than immediately after it.

Two checks, evaluated independently rather than chained on || (chaining is how the reverted version let the capped path skip the duplicate-name check):

  • Monotonicity — over receipts only. A stray lightweight or malformed tag must not be able to trap a deploy.
  • Name collision — over all refs, because git tag -a fails on any existing name, receipt or not.

6. At the cap, refuse — because nothing has shipped yet

If this machine’s clock cannot produce a stamp newer than the record, waiting forever is not an option. The reverted version waited 10s and then wrote an out-of-order receipt anyway, because by then the deploy had already happened. Moving the wait before the release turns that into a free refusal. Nothing has shipped, so the guard can stop, name the offending receipt, and let the operator fix the clock or remove the bogus tag.

Whatever wording survives review, it must not repeat the reverted version’s claim that “the guard reads them by tag date, which is still right”. A fast clock produces a future name and a future date; both orderings are wrong together, and saying otherwise is confidently wrong in exactly the case that triggers the message.

Open questions for review

Q1 — cap: refuse, or write anyway with a warning? This plan says refuse (new exit code), on the grounds that nothing has shipped at that point and a >10s clock skew against the record is a genuinely broken record worth stopping for. The cost: a stray future-named annotated tag in the namespace blocks deploys until a human removes it, which during an incident is friction. The counter-argument (and the existing plan’s stated philosophy on the dirty-tree check) is that refusals tempt workarounds. This is the decision I most want challenged.

Q2 — should an ambiguous record refuse --approved, not just warn? Recommendation: warn only. The guard still picks the right receipt under the model above, and the ambiguity is a historical artefact that clears itself on the next deploy. Refusing would block deploys on something already resolved correctly.

Q3 — the ambiguity warning goes to stderr, like every other warn in this script. In the deploy path it is emitted just before the ═══ guarded deploy ═══ block, so in a combined transcript it sits directly above the diff Christie reads. Is stderr right, or should this one line be on stdout so it survives someone pasting stdout alone?

Q4 — two new exit codes (EX_RECORD=19 unreadable record, EX_CLOCK=20 cannot stamp newer than the record), consistent with the file’s “distinct codes” convention. Or fold both into one?

Phases

Phase 1 — The read side: one predicate, the right order, fail closed

scripts/deploy-rules.sh (reader only) + scripts/deploy-rules.test.sh. No change to how receipts are written, so the same-second flake is reduced but not gone after this phase — that is Phase 2’s job, and this plan does not pretend otherwise.

Acceptance criteria (user outcomes):

  • When a receipt was written by hand after a later deploy, the guard still names the later deploy’s receipt as what shipped last, and prints the diff against it.
  • When the record is ambiguous, the guard says so in words that name both candidates — and stops saying so once an ordinary deploy resolves it.
  • A tag in the namespace that is not a receipt (lightweight, or an unparseable name) is never named as what shipped last.
  • If the guard cannot read the receipt record, it refuses and says that — it never reports “no receipt yet”.
Happy: Given receipts A (stamp 08:00, tagged 11:00 by hand) and B (stamp 09:00, tagged 10:00 by the guard) When --status Then B is “last receipt”, and a warning names A as the by-date candidate.
Edge: Given a lightweight tag named 29990101T000000Z-… and an annotated tag named not-a-stamp-… in the namespace When --status Then neither is named; the newest real receipt is.
Edge: Given two receipts with the SAME stamp and different tag dates When --status Then the later-tagged one wins, and no ambiguity warning fires (both orders agree).
Failure: Given git for-each-ref fails When --status Then the guard refuses with EX_RECORD and a sentence saying the record could not be read — not “no receipt yet”, and no empty diff.

Phase 2 — The write side: a strictly-newer stamp, reserved before the release

scripts/deploy-rules.sh step 9 (the stamp moves ahead of step 8) + tests.

Acceptance criteria (user outcomes):

  • Two deploys in quick succession leave two receipts the guard can order — the second’s diff is against the first, not against whichever sha7 sorts higher.
  • The rollback case in the test suite passes every run, because the guard is deterministic — not because the test sleeps.
  • The window between “production changed” and “a receipt exists” is no larger than it is today.
  • If this machine’s clock cannot stamp a receipt newer than the record, the guard stops before deploying and names the receipt that is in the way.
Happy: Given a receipt exists for this target When a second deploy runs in the same second Then it waits out the second, deploys, and writes a receipt with a strictly greater stamp.
Edge: Given a stray lightweight tag named with a year-2999 stamp When a deploy runs Then it is ignored (not a receipt), the deploy is not stalled, and it completes at normal speed.
Failure: Given an annotated receipt stamped in the year 2999 When a deploy runs Then after the cap the guard refuses with EX_CLOCK, names that receipt, and firebase was never called — asserted against the fake CLI’s log.

Tests — what the previous attempt got wrong here

The vacuous assertion. d43a171 asserted “ordering by name and ordering by tag date give the same answer”. Under the old writer all three receipts are written inside one second, so their creatordates are equal, both sorts degenerate to refname, and the assertion passes while the bug is present. It could only fail by luck. Nothing in this plan asserts “two orderings agree”.

Assertions that cannot degenerate, used instead:

  • Distinct stamps: after three back-to-back deploys, the three receipt names carry three different seconds. Fails against today’s writer; cannot pass by luck.
  • End-to-end, not a re-implementation of the sort: a fourth deploy’s printed replaces: line names the third deploy’s receipt. This exercises the real read path rather than re-running the comparison the code under test just ran.
  • Deterministic by construction: fixtures set GIT_COMMITTER_DATE explicitly on git tag -a (verified: it controls the tagger date), so no test depends on wall-clock timing and no unexplained sleep is load-bearing.

Coverage the previous attempt lacked, added here: delayed hand-recovery; clock rollback / future-dated receipt; the capped path; and a failed ref read (a transparent git wrapper on the harness’s PATH, inert unless an env var is set — the same shape as the existing fake firebase and fake npm).

Firebase safety checklist

  • No Firestore data change. No rules change. No deploy of any kind. firestore.rules is not touched by this plan.
  • Files changed: scripts/deploy-rules.sh and scripts/deploy-rules.test.sh. Nothing else.
  • No new Firestore collection, so no new rule is required.
  • The guard’s deploy path (steps 5, 7, 8 — worktree, tests, byte-level predeploy re-check) is not touched. This change can only affect the record and the printed diff, never which bytes ship. Each review must confirm that independently.
  • Never reads ~/.config/configstore/firebase-tools.json; no raw Firestore REST call anywhere.
  • npm test (rules suite + guard suite) run repeatedly, with the counts actually seen reported — not a hardcoded number.
  • studio-hub is a shared working tree: commit only these two files, never git add -A.

Completeness check — interrupted mid-way

  • After Phase 1, before Phase 2: the reader is correct and fail-closed; the writer still stamps at second resolution, so two same-second receipts can still tie on stamp and tag date and fall through to the arbitrary refname tiebreak. The suite may still flake on the rollback case. Strictly better than today, not yet done.
  • Interrupted inside a phase: nothing is deployed and no production state exists to unwind. The working tree is the only thing changed; git checkout of the two files is a complete undo.
  • The existing real receipt is untouched. The tag name format does not change, so 20260921T220500Z-1da12e3 stays discoverable and keeps meaning what it means.
