Plan: Deploy guard — receipt ordering (“what shipped last”)

Repo: ~/studio-hub · scripts/deploy-rules.sh, scripts/deploy-rules.test.sh only · Drafted Sep 22 2026 · v2 after a two-model plan review (Claude + Codex) — both said request changes · execution-ready: false · Under the Firebase deploy guard plan. No rules change, no data change, no deploy.

Goal. When the guard names what shipped last and prints a diff from it, that diff is either right or the guard refuses to present it as authoritative. It never converts incomplete evidence into a confident answer.
Narrowed in v2 (both reviewers). v1 claimed this would be correct “including … another clone”. That was an overclaim and is withdrawn. Two clones deploying concurrently cannot be ordered from local git evidence: the lock is per-GIT_DIR, the stamp is a local variable that reserves nothing globally, and stamps record release start while production reflects release completion. This plan makes the single-clone record sound and makes ambiguity visible; it does not make cross-clone history knowable. That limit is now stated in the script's header comment, next to the existing “receipts of GUARDED deploys, not proof of production” sentence.

The bug, and the measured baseline

scripts/deploy-rules.sh:76:

latest_receipt() { git for-each-ref --count=1 --sort=-refname --format='%(refname:short)' "refs/tags/${TAG_PREFIX}"; }

Receipt names are …/<UTC yyyymmddTHHMMSSZ>-<sha7>. The stamp has second resolution, so two deploys inside one second tie and -refname breaks the tie on the sha7 — no order at all. Nine consecutive baseline runs of the guard suite on this branch, before any change:

90/0  90/0  87/3  89/1  90/0  90/0  89/1  90/0  90/0      → 3 of 9 failed

The mechanism, confirmed: at deploy-rules.test.sh:127 the third deploy reads the record at deploy-rules.sh:218 before writing its own receipt, so it sees two receipts tied on stamp and picks between them by sha7. When it picks the SHA2 one, the printed diff is SHA2 → SHA2 — empty — and assert_has "-// v3" fails.

The harm is not only a wrong diff. A mis-picked receipt that happens to point at origin/main makes --status print “nothing to deploy” (deploy-rules.sh:125–126) and the operator walks away from a change that never shipped. Silent, with no diff displayed to contradict it. (Claude, finding 6.)
The reverted approach (d43a171) stays off the table. It ordered by tag creation date. The one real receipt, 20260921T220500Z-1da12e3, was hand-written 49m12s after the deploy it records — re-verified for this plan by both reviewers independently. The script's own EX_RECEIPT path instructs operators to hand-write receipts, so this is ordinary practice, not an accident.

Part 1 — The ordering model (unchanged from v1; both reviewers endorsed it)

The receipt predicate — one definition, used everywhere

A receipt is a ref under refs/tags/<TAG_PREFIX> that is (a) an annotated tag (objecttype == tag) and (b) named with a stamp matching ^[0-9]{8}T[0-9]{6}Z$ before the first -. The reader and the writer's monotonicity lookup use the same predicate — d43a171 filtered lightweight tags when reading but counted them when ordering, so a stray tag was “not a receipt” for --status yet could still stall every deploy.

Do not tighten the predicate to require by=deploy-rules.sh in the tag body. The real receipt says by=seeded and would vanish from the record. (Claude.)

The order: (name stamp, tag date, refname), descending

KeyJustification
1. name stampThe stamp is not a timestamp the script observes — it is a value the script writes, and that hand-recovery transcribes (deploy-rules.sh:258 prints the recovery command with $TAG already interpolated). So a receipt written 49 minutes late still carries deploy time. The tag date is the only field that cannot survive that transcription. That asymmetry is the entire argument.
2. tag dateConsulted only when two stamps are byte-identical. Honest about its worth: after the write-side reservation, a same-clone same-second tie cannot be produced by the script at all, so this key only ever fires for two clones or hand-made tags — where the dates come from different clocks and are no more trustworthy than the stamps. It is a deterministic guess, not evidence. Which is why a tie is now reported (Part 2), not silently resolved.
3. refnameDeterminism only. Carries no chronology.

Verified on a hand-built fixture (scratch repo, explicit GIT_COMMITTER_DATE): a receipt pair where the older-named one was tagged an hour later, plus a lightweight year-2999 tag and an annotated tag with an unparseable name.

ReaderPicksVerdict

Part 2 — Record health (NEW in v2; this replaces the two-argmax detector)

Why v1's detector had to go — all three reproduced in a scratch repo:
Casev1 detectorResult
Receipt with an old stamp and a year-2999 tag date; 3 later ordinary deploys follow warns on every run, forever“self-clearing” is false
Two receipts, same stamp and same tagger second no warning; both argmaxes agree on the arbitrary sha7 winnersilent wrong answer
Fast clock: future name and future date (correlated) no warning; both agree on the bogus receipttreated as production truth
Two proxies that share a failure mode cannot detect that failure mode. The dominant real error — a receipt written late — moves both in the same direction by the same amount.

So the guard stops asking “do two sorts agree?” and instead asks one question: “is this answer forced by the evidence, or did I have to guess?” One pass over the receipts yields four independent findings, each catching a class the others miss:

FindingMeans--status/--diff--approved
H1 — more than one receipt at the maximum stamp The winner was decided by tag date or by sha7, not by deploy-time evidence. name every candidate with its tag dateREFUSE (EX_RECORD)
H2 — the winner's own skew: tag date − name stamp > 10 min Probably hand-written. For a script-written receipt this skew is exactly the release duration. warn, naming both timeswarn, above the diff
H3 — any receipt's stamp is in the future A clock ran fast, or a tag was planted. No ordering can be trusted, and the writer cannot stamp past it. warn, naming the tagREFUSE (EX_CLOCK) unless overridden
H4 — refs under the namespace excluded by the predicate Someone wrote a recovery receipt without -a, or mistyped the stamp — a real deploy record that is silently invisible. warn, naming themwarn

H2 is the one that earns its place. It is the only check that catches the failure both reviewers identified as most likely, and which the v1 detector was structurally blind to:

Deploy A ships at 22:05 → git tag -a fails → exit 17. Deploy B ships at 22:15 and gets a normal receipt. At 22:54 the operator hand-writes A's receipt but improvises a fresh date -u instead of copying the printed command. A now has a later stamp and a later tag date than B. It wins under both keys. H2 catches it — A's own stamp-to-date skew is 49 minutes.

Wording it must produce, in Christie's terms:

WARNING: this receipt's stamp says 22:05:00Z but its tag object was written at
22:54:12Z — 49 minutes later. It was probably written by hand. Confirm it is
really what shipped last before approving the diff below.

Two cheap additions that turn an invisible model assumption into something a human can check (Claude): print the winner's tag date next to its stamp in --status and in the replaces: line (deploy-rules.sh:227); and cross-check the at= field in %(contents) against the name stamp — they agree on the real receipt, and if they ever disagree the tag was edited and nothing about it should be trusted.

Reads fail closed

A failed git for-each-ref must never read as “no receipt yet” — d43a171 put it inside a command substitution feeding a here-string, which discards its exit status, and the guard then printed “the whole file is new to the record” with no diff and carried on. Capture into a variable with || return 1, declaring local on a separate line from the assignment. Verified on this machine's bash 3.2.57:

local y="$(exit 7)"   → status seen = 0     # masked
local y; y="$(exit 7)" → status 7, set -e fires  # propagates

Because bare set -e would exit with no message, every call site uses an explicit || die $EX_RECORD "…".

Part 3 — The write side

Reserve a strictly newer stamp, before the release

The reader's primary key is only as good as the writer's guarantee, so a new receipt must be strictly newer by stamp than every receipt recorded for this target — not merely not-a-duplicate.

Before the release, never after. d43a171 waited after firebase deploy returned, opening up to ten seconds in which production had changed and neither a receipt nor a pending marker existed. This is now a stated constraint, not a happy consequence (Claude, finding 6): nothing new may be able to fail between deploy-rules.sh:243 and :260. set -euo pipefail is on, so an unguarded failure there aborts after production changed, with no receipt, no $PENDING and no printed instructions. The reservation must also not touch $TMP or anything the predeploy hook hashes.

Check early, reserve late (Claude): do the feasibility check right after step 3 (~:200) so a refusal costs one second instead of a full rules suite; take the actual stamp immediately before step 8 so it stays close to the release. Consequence, documented: at= becomes “when the receipt was reserved”, which is also what makes H2's 10-minute threshold defensible — the expected skew becomes exactly the release duration.

Two checks, evaluated independently, never chained on || (chaining is how d43a171's capped path skipped the duplicate-name check): monotonicity over receipts only (a stray lightweight tag must not trap a deploy), and name collision over all refs (because git tag -a fails on any existing name).

The three-way split, decided by the size of the gap

v1's single 10-second cap conflated two unrelated faults: “this clock will not advance in ten seconds” (broken hardware) and “there is a tag stamped three years out” (corrupt data). Same path, same message, same remedy — and neither remedy fits both.

newest recorded stampaction
≤ nowproceed immediately — the normal case, no wait at all
now < stamp ≤ now + 10 swait it out, then proceed. Pre-release; costs seconds.
> now + 10 srefuse immediately — do not sleep first — EX_CLOCK, naming the offending tag, whether it is annotated, its by= field, and the recovery steps
Why an override is mandatory, not a nicety. One annotated tag with a far-future well-formed stamp would otherwise brick the only sanctioned deploy path for all 21 apps, permanently — and the guard is exactly what Christie must reach for during an emergency rules rollback. Receipts are documented as immutable and never deleted, and the tag may be a genuine receipt from a fast clock, so “just delete it” can erase real history. So: --accept-out-of-order-receipt, non-default, which proceeds and writes a receipt at the current (older) stamp with a loud warning that persists in --status until the record is repaired. The alternative some would reach for — “just use max(prev, now)+1s” — is a Lamport clock, and under a stray 2999 tag it poisons every future receipt name with a year-2999 stamp. Rejected.
Whatever the final wording, it must not repeat d43a171's claim that “the guard reads them by tag date, which is still right”. A fast clock produces a future name and a future date; both orderings are wrong together. Because the runbook is outside this change's scope, the recovery steps live in the refusal message itself — which is where an operator under pressure will actually see them.

New exit codes — new, never reused

EX_RECEIPT (17) currently means “production changed, the receipt did not publish” and deploy-rules.test.sh:172 pins that meaning. A pre-release refusal and a post-release one must never be confusable in a transcript. So: EX_RECORD=19 (the record cannot be read, or cannot honestly name what shipped last) and EX_CLOCK=20 (this machine cannot stamp a receipt newer than the record).

Phases

Phase 1 — reader, writer and tests, as ONE atomic change

Both reviewers rejected the v1 split. Reader-only reduces the same-clone flake by zero: both keys have one-second resolution, so a same-second pair ties on stamp and on tag date and still falls through to sha7. Shipping a phase whose known effect is “the gate stays flaky for a while” trains operators to re-run until green, which is the habit that gets a real failure waved through — and npm test is the gate on every rules deploy.

Acceptance criteria (user outcomes):

  • A receipt written by hand after a later deploy does not become “what shipped last”.
  • When the guard cannot tell which receipt shipped last, --approved refuses rather than printing a diff that might have the wrong base.
  • A receipt that looks hand-written is flagged in words, with both times, above the diff.
  • A tag in the namespace that is not a receipt is never named as what shipped last — and is never silently ignored either.
  • If the record cannot be read, the guard refuses and says so — never “no receipt yet”.
  • A machine whose clock is behind a far-future receipt is told so in one second, not after a full test run, and is given a documented way through.
  • The guard suite passes every run, because the guard is deterministic — not because a test sleeps.
Happy: Given receipts A (stamp 08:00, hand-tagged 11:00) and B (stamp 09:00, tagged 10:00) When --status Then B is named, with its tag date shown, and H2 warns about A's skew.
Edge: Given two receipts sharing a stamp When --approved Then H1 refuses with EX_RECORD, names both candidates with their tag dates, and firebase is never called.
Edge: Given a stray lightweight year-2999 tag When a deploy runs Then it is not a receipt, the deploy is not stalled or refused, H4 warns it exists, and the deploy completes at normal speed.
Failure: Given an annotated receipt stamped an hour ahead When --approved Then the guard refuses in about one second with EX_CLOCK, the message names the tag and the recovery steps, and firebase was never called. And with --accept-out-of-order-receipt Then it proceeds, warns loudly, and the warning persists in later --status.
Failure: Given git for-each-ref fails When --status Then EX_RECORD and a sentence saying the record could not be read — not “no receipt yet”, and no empty diff.

Tests

The assertion I nearly shipped. v1 proposed: “a fourth deploy's replaces: line names the third deploy's receipt.” Claude traced it and I confirmed: the third deploy re-deploys SHA2, so its candidate tag name is byte-identical to the happy-path receipt's — the existing dedup loop at deploy-rules.sh:253 fires and sleeps a second. So the third receipt ends at T+1 with or without this change, and any stamp-major reader names it. -refname is stamp-major (fixed-width stamps in the same position). The assertion's bug-detection is itself a coin flip — the worst possible property for a regression test, and the same defect the last attempt shipped, in a new costume.
Standing rule for this file, written into its header: never assert that two orderings agree. Under any tie both for-each-ref sorts degenerate to refname and return identical output, so such an assertion passes precisely while the bug is present. Assert on values — stamps, receipt names, the text of replaces:, the content of the printed diff, exit codes.

Determinism by controlled time, not by sleeping

Codex's design, adopted: a fake date on the harness PATH answers the stamp format from a counter file and delegates every other invocation to the real date; a fake sleep advances that counter by one second. Then the writer test is deterministic in both directions: under the old writer no sleep occurs, all stamps stay equal, and the test fails every run; under the new writer the monotonicity loop sleeps and the stamps differ every run. Same shape as the existing fake firebase and fake npm.

Tag dates stay deterministic via explicit GIT_COMMITTER_DATE on git tag -a (verified: it controls the tagger date). Far-future dates need the epoch form — @32503680000 +0000; git rejects 2999-01-01T00:00:00 +0000 as an invalid date format.

The planted-tag battery — every case forced, none hoped for

  • Stamps strictly increasing across three back-to-back deploys (not merely distinct — distinctness passes for T+1, T, T+2 under a rollback), each captured from that run's own receipt: line.
  • Malformed name: an annotated …/not-a-stamp-abc1234, which sorts above every real receipt under refname → must be ignored, and H4 must mention it.
  • Future lightweight: 29990101T000000Z-handmade → ignored. (Note deploy-rules.test.sh:177's existing hand-made tag is 19990101T…, which sorts below everything and proves nothing about ordering.)
  • Predicate parity, both directions in one test: a future lightweight tag → the writer must not wait or refuse; a future annotated one → it must. This is d43a171's asymmetry exactly.
  • Delayed hand-recovery (stamp 08:00 tagged 11:00 vs stamp 09:00 tagged 10:00) → the stamp-09:00 receipt wins; H2 warns.
  • H1: two receipts sharing a stamp → --approved refuses EX_RECORD, names both, firebase never called.
  • H1 worst case: same stamp and same tagger second → still refuses (v1 would have answered arbitrarily).
  • H3 correlated fast clock: future name and future date → refused, not silently trusted.
  • H3 override: --accept-out-of-order-receipt proceeds, warns, and the warning persists.
  • Failed ref read: a transparent git wrapper on the harness PATH, inert unless an env var is set, failing only for-each-ref → EX_RECORD.
  • Regression pin: the existing real receipt's shape (annotated, by=seeded, stamp parses) stays discoverable.

Named follow-ups — deliberately NOT in this change

  • (Found by review, pre-existing.) deploy-rules.sh:257's git tag -a failure path does not write $PENDING — only the push failure at :262 does. So a failed tag write leaves production changed with no marker, and the next deploy does not refuse. This is the exact precondition for the improvised hand-recovery that H2 exists to catch. It is excluded here because $PENDING records name + tag object id and no tag object exists on that path — fixing it changes the reconcile protocol, which is its own plan.
  • RULES-ROLLBACK.md needs “a bogus receipt is blocking deploys”. Outside this change's scripts-only scope; the recovery steps are carried in the refusal message meanwhile.
  • Real cross-clone serialization (a remote ref lock). Large, and the goal statement is narrowed instead.
