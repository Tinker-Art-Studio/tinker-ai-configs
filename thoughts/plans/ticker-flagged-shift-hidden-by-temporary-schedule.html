Plan: A flagged shift hidden by a temporary schedule

App: Tinker Ticker (~/tinker-timeclock) · Drafted: Sep 22 2026 · execution-ready: false · Status: DRAFT — awaiting review · Found by the Claude half of the Sep 22 sub-tabs implementation review (finding #3, 2026-09-22-impl-review-subtabs-claude.md). Follows the “48-hour shift reminders” plan, which shipped Sep 21 (62db9a2) and the sub-tabs, which shipped Sep 22 (6cc4732).

Goal: when a manager has ticked “remind” on a shift that the app will never show — because a temporary schedule covers that date, or because the flag landed on a temporary schedule that does not — she is told, in the Reminders view and on its badge, instead of the reminder silently never going out.

What this is NOT: the reminder job is behaving correctly and does not change. A shift the app does not show should not send — that is the design. The whole defect is that nobody is told. No rules change, no new collection, no change to the job, and (in Phase 1) no Firestore write at all.

The mechanism, exactly

Two lines. First, listReminderRows (js/schedule-helpers.js:584) marks a row hidden when the layer it lives on is not the layer that serves its date:

hidden: (layer === 'future') !== inFuture

Then reminderRowStatus (:661) checks hidden before it checks remind (:662):

if (row.hidden) return { code: 'hidden' };
if (!row.remind) return { code: 'none' };

So a flagged hidden row and an unflagged hidden row produce a byte-identical status. Everything downstream — the row's rendering (cls: 'muted', grey), and the attention badge added Sep 22 — is blind to the difference, because the information has already been discarded.

The two ways in

#How it happensResult
1 The temporary schedule arrives after the flag. A base-layer override is flagged for Oct 15. Later a temporary schedule is created covering Oct 12–20 (by the editor, the AI tool, or a CSV import). Oct 15 is now served by the future layer; the flag sits on base → hidden.
2 The flag lands on the wrong layer. A temporary schedule runs Nov 1–30. On Nov 10, with it active, the editor is used to add a Dec 5 shift and tick remind. The editor writes to the layer active today, which is future. Dec 5 is outside Nov 1–30 → the flag sits on future, which does not serve it → hidden.

Way 2 is the reminder-shaped face of an already-known follow-up: the schedule editor and the time-off/sub writers still write whichever layer is active today; only the AI path routes per date. Fixing that routing is its own plan and is NOT in scope here — but it is the upstream cause of way 2, and closing it would remove that half of this bug at the source.

Edge case that makes this worse than it looks. isInFutureWindow (:296) is !!future && (!validFrom || d >= validFrom) && (!validUntil || d <= validUntil). A futureSchedule that exists with no bounds at all therefore swallows every date — so every base override on that person becomes hidden at once, and today every one of them is silently grey.

Why it is easy to miss

The row is present and does say “(not shown — inside/outside the temporary schedule’s dates)”. But it renders grey, alongside every override on the non-active layer — for a month-long temporary schedule, that is every base override in that month. The one that matters looks exactly like the dozens that do not.

And the irony worth naming: too-late is counted by the badge, and it also means “will never send”. The badge flags the harmless version of this failure and misses the dangerous one.

One decision for Christie

Should the manager be able to untick a hidden flag from the Reminders view (Phase 2), or is being told enough (Phase 1 only)?

This is not a free addition. planReminderToggles (:754) computes the layer that serves the date and refuses any toggle whose layer differs:
const layer = isInFutureWindow(d.futureSchedule, dateStr) ? 'future' : 'base';
if (t.layer !== layer) { skipped.push({ date: dateStr, reason: 'moved' }); return; }

A hidden row is by definition one where those differ, so the transaction would always skip it as moved. That guard is deliberate — it is what stops a row whose date has moved layers from being written blind. Phase 2 therefore means loosening a safety guard that was added on purpose, which is why it is a separate, reviewed phase and not part of Phase 1.

Worth knowing before choosing: unticking does not deliver the reminder. The flag is on a shift that is not happening. If she still wants the person reminded she must add the shift on the layer that actually serves the date — and if that date is served by the temporary schedule’s recurring pattern rather than an override, there is no row to flag at all, because the flag only ever lives on overrides. So Phase 2 buys tidiness, not delivery.

Recommendation: Phase 1 first, then decide. Phase 1 carries nearly all the value (she finds out), costs no write path, and after a week of seeing how often this actually fires she will know whether Phase 2 is worth loosening the guard for.

Phases

Phase 1 — the status tells the truth (no Firestore write)

Acceptance criteria, as user outcomes:

  • A shift Christie ticked “remind” on that the app will never show is called out in the Reminders list in amber, saying plainly that it will not send and why.
  • The Reminders sub-tab badge counts it, so she finds out without opening the tab.
  • An unflagged hidden shift still renders exactly as it does today — grey, uncounted. There are many of these and they are not problems.
  • Nothing about what does or does not get emailed changes.

Changes: reminderRowStatus returns { code: 'hidden', flagged: row.remind }; describeReminderStatus renders flagged ones warn with their own text and title; reminderAttentionSummary counts them under a new label, date-gated with the rest of the amber family.

Tests that must change (they assert today's behaviour exactly): schedule-helpers.test.js:2341 and :2342 both toEqual({ code: 'hidden' }). They become the two halves of the new contract.

Given a base override on Oct 15 with remind: true, and a temporary schedule covering Oct 12–20, when Christie opens Schedule Builder, then the Reminders badge counts that shift and its row reads amber, naming the temporary schedule as the reason it cannot send.
Given the same shift but without remind, when she opens Schedule Builder, then the row is grey “hidden” as today and the badge does not count it.
Given a flagged hidden shift whose date has already passed, when the badge is drawn, then it is not counted — a past shift cannot be fixed (the same date gate the amber family got on Sep 22).
Given a futureSchedule with no validFrom and no validUntil, so every base override is hidden, when three of them are flagged, then the badge counts exactly three, not the whole map.
Given both a hidden base row and a live future row for the same date, both flagged, when the badge is drawn, then the live one is counted by its own status and the hidden one is counted once as not-sending — the manager is not shown a contradiction.
Given an orphan log row (hidden: true, remind: false, carrying a log), when its status is computed, then the log still decides it (“sent — shift since removed”) and the hidden branch is never reached.

Phase 2 — the manager can clear a stale flag (Firestore write — gated on the decision above)

Acceptance criteria:

  • Christie can untick a flagged hidden shift from the Reminders view and the flag is actually removed.
  • She can never tick a hidden shift — that would create a flag that cannot send, which is the bug this plan exists to remove.
  • Every other toggle behaves exactly as it does today; the moved guard still protects them.

Shape: the toggle carries an explicit opt-in (for example shadowed: true) meaning “I am deliberately acting on the layer this row was shown from, which is not the serving layer”. The guard becomes: layers must match unless the caller said shadowed and the toggle is an untick. Leaf-delete only, same-shape guard unchanged.

Required before coding (AGENTS.md, non-negotiable): a failing Firestore emulator test first, then the fix, then green. Then a second-model implementation review of the diff before Phase 3.

Given a flagged hidden base override, when Christie unticks it, then remind and remindUid are deleted from that base override only, and the temporary schedule and every other date are untouched.
Given a hidden row, when a tick (not an untick) is attempted, then it is refused and reported — no write.
Given a row shown as hidden, when the temporary schedule's bounds are edited between the view loading and the untick so the row is no longer shadowed, then the transaction re-reads and skips it rather than writing where she did not look.
Given the shift was rewritten by someone else since the view loaded, when she unticks, then the existing sameShift guard still skips it as changed.

Firebase safety checklist

  • New collection? No. Nothing beyond timeclock_schedules, which has had a rule since before this feature (firestore.rules:381, manager read/write). No rules change, so nothing to deploy to Firebase.
  • Partial updates? Phase 2 writes leaf deletes through the existing toggleShiftRemindersTransaction — never setDoc, never a whole map.
  • Empty fields stripped? Unchanged: remind is true or absent, never false/null/"".
  • Awaited writes? Unchanged — the existing toggle path already awaits and surfaces failures.
  • Bulk delete/import? None. Every write is one human untick.
  • Emulator test before code? Required for Phase 2. Phase 1 is pure functions and is covered by schedule-helpers.test.js.
  • Console spot-check? Required after Phase 2 — one real document, confirming the base override lost its two keys and the futureSchedule is untouched.

Completeness check — what if this stops part-way?

  • After Phase 1: Christie is told about shadowed flags but can only clear them through the schedule editor. That is strictly better than today and is a sensible permanent stopping point.
  • After Phase 2: she can also clear them in place. Docs would lag; nothing behaves wrongly.
  • Mid-Phase 1: the helper and the renderer are one commit. Split across a deploy, the worst case is a status the renderer does not recognise, which falls through to default: { cls: 'muted', text: s.code } — today's behaviour. Safe either way.
