Plan: A flagged shift hidden by a temporary schedule

App: Tinker Ticker (~/tinker-timeclock) · Drafted: Sep 22 2026 · v2 after a two-model design review (Claude + Codex, Sep 22 — every finding folded in; see the Decisions log) · execution-ready: true — both design reviews passed; Christie approved Phase 1.5 and gave written approval to edit the repo, Sep 22. · Found as finding #3 of the Sep 22 sub-tabs implementation review.

Goal: when a manager has ticked “remind” on a shift the app will never show — because a temporary schedule covers that date, or because the flag landed on a temporary schedule that does not — she is told, and she can clear it without leaving the app.

What this is NOT: the reminder job is correct and does not change. Both reviewers confirmed it independently: selectRemindersDue resolves through getShiftForDate, so a shadowed flag is invisible to the job by construction, and sending it would email hours the person is not working. No rules change, no new collection, no change to the job.

The mechanism, exactly

listReminderRows (js/schedule-helpers.js:584) marks a row hidden when the layer it lives on is not the layer that serves its date: hidden: (layer === 'future') !== inFuture. Then reminderRowStatus (:661) checks hidden before remind (:662), so a flagged hidden row and an unflagged one produce a byte-identical status. The information is gone before anything downstream can use it.

#How it happensResult
1The temporary schedule arrives after the flag. A base override is flagged for Oct 15; later a temporary schedule covering Oct 12–20 is created (editor, AI tool, or CSV import). Oct 15 is served by the future layer; the flag sits on base → hidden.
2The flag lands on the wrong layer. A temporary schedule runs Nov 1–30. On Nov 10, with it active, the editor adds a Dec 5 shift and ticks remind — the editor writes the layer active today. Dec 5 is outside the window; the flag sits on future, which does not serve it → hidden.

Way 2 is the reminder-shaped face of a known follow-up (the editor and the time-off/sub writers write whichever layer is active today; only the AI path routes per date). Fixing that routing is its own plan and is NOT in scope — this plan detects its consequences, it does not prevent new wrong-layer flags.

The edge case that makes this worst. isInFutureWindow (:296) has no bounds requirement, so a futureSchedule with no validFrom and no validUntil swallows every date — every base override for that person goes hidden at once. And because a bounds-less window is by definition active today, it always lands in the unreachable case below.
Two different “is the temporary schedule active” tests exist. isInFutureWindow (:296) does not require future.recurring; the editor's futureActive (app.js:3339) and getNormalRecurringShift (:859) do. A futureSchedule with overrides but no recurring therefore shadows base overrides in the resolver while the editor still edits base. Whoever implements this must not assume one test.

Why Phases 1 and 2 must ship together

v1 recommended shipping the display fix alone and deciding on unticking later. Both reviewers rejected that, and they were right. openScheduleEditor (app.js:3338-3347) loads future.overrides whenever the temporary schedule covers today, and the base map is then never rendered:

The window covers…Reminders viewCan she clear it?
the date, but not todayhidden Yes — the editor loads base, the row is listed, Remove works.
the date and todayhidden No. The editor loads future; the base override is invisible. The AI tool routes per date to the future map; reminderRowToggleable refuses hidden rows; “Clear all shown” filters on that same predicate; the schedule-view modal is read-only. Only the Firebase console.

So Phase 1 alone would put a permanent amber count on the badge that nothing in the app can clear — the exact failure the Sep 22 date gate was added to prevent (“a red badge nobody can clear is one people learn to ignore”). Phase 1 and Phase 2 are separate commits and separate review gates, but one release.

Decided: Phase 1.5 is IN (Christie, Sep 22)

Phase 1.5 — catch this at the moment it is created. APPROVED.

handleSaveSchedule already stops and confirms when a temporary schedule will hide the regular one — twice (app.js:3741 “their regular schedule stays hidden until this temporary schedule ends”, and :3752 for a missing end date). That confirm is the precise moment way 1 is created and the last cheap moment to act.

Counting base overrides inside the new window that carry remind: true and naming them in that existing prompt (“3 of the dates this covers have a reminder set — those reminders will stop sending”) prevents the bug rather than reporting it, for a fraction of Phase 2's cost. It is not a substitute — CSV imports and bounds edits bypass that path entirely — but it is the highest-value line in the plan per unit of risk.

Recommendation: yes, include it. It is a read-only count added to a prompt that already exists.

Phases

Phase 1 — the status tells the truth (no Firestore write)

Acceptance criteria, as user outcomes:

  • A shift Christie ticked “remind” on that the app will never show is called out in amber in the Reminders list, saying plainly that it will not send and why — and the row does not also render grey and italic.
  • The Reminders sub-tab badge counts it, so she finds out without opening the tab.
  • An unflagged hidden shift renders exactly as today — grey, uncounted. There are many and they are not problems.
  • If the shift the app does show for that date is itself flagged, the shadowed row says so and is NOT counted — the person is getting their reminder.
  • After a future-schedule CSV import, the badge is right immediately, without pressing Refresh.
  • Nothing about what does or does not get emailed changes.

Change sites — all five (v1 named three):

  1. reminderRowStatus (helpers:661) — return a distinct code, hidden-flagged, not { code: 'hidden', flagged }. Both reviewers asked for this independently: reminderAttentionSummary is a pure code → label lookup (:708) and cannot express “only when flagged” without a special case, whereas a distinct code drops straight into REMINDER_ATTENTION_LABELS and leaves the existing hidden contract byte-identical.
  2. describeReminderStatus (app.js:3176) — cls: 'warn' with text and title that name which way it happened (it already branches on row.layer for the title).
  3. reminderAttentionSummary (helpers:708) — one label entry; date-gated with the rest of the amber family; explicitly NOT in REMINDER_ATTENTION_SEVERE.
  4. renderRemindersView (app.js:3213) — cls = r.hidden ? 'hidden-row' : … paints the row grey italic (css/styles.css:2303). A flagged hidden row must not get that class, or “called out in amber” is a coloured pill inside a row the app's own visual language says to ignore.
  5. listReminderRows (helpers:562) — set servingRemind: true on a hidden row when the serving layer holds a flagged shift for the same date. This is the only place with the whole schedule in hand; reminderRowStatus only ever sees one row.

Plus wiring: runFutureScheduleWrite (app.js:6258) currently ends at renderFutureCsvTable + showToast with no reload, so an import that creates shadowed flags leaves the badge stale. Add await loadSchedulesData(); await loadRemindersView(); — reads only.

Tests that must change (three sites — v1 named two): schedule-helpers.test.js:2341 and :2342 (toEqual({ code: 'hidden' })), and :2629 (the Sep 22 “job working normally is never counted” case, which pins a 'hidden' row as uncounted). With a distinct code, :2629 stays true unchanged — which is itself the argument for the distinct code.

Way 1. Given a base override on Oct 15 with remind: true, and a temporary schedule covering Oct 12–20, when Christie opens Schedule Builder, then the badge counts it and its row reads amber, naming the temporary schedule as the reason.
Way 2 (v1 had no BDD for this direction at all). Given a future-layer override for Dec 5 with remind: true and a window of Nov 1–30, when the view renders, then that row is amber and counted, with a title naming the outside-the-window reason — an implementation that handles only the base direction must fail here.
Given the same shift without remind, then the row is grey “hidden” exactly as today and is not counted.
Given a flagged hidden shift whose date has passed, then it is not counted — unfixable and unclearable; the Sep 22 date gate applies unchanged. And hidden-flagged is never severe: it can never produce a log, so it can never be evidence of a send that went wrong.
Boundary. Given validFrom/validUntil are inclusive, a row dated exactly on each bound, and one-sided windows (missing validFrom; missing validUntil) in both layer directions, then each row's hidden-ness matches getShiftForDate for that date.
Given a bounds-less futureSchedule, so every base override is hidden, and three of them are flagged, then the badge counts exactly three, not the whole map.
Corrected from v1 (which asserted the wrong total). Given a hidden flagged base row and a live flagged future row for the same date, with no log, then the live row is sends and is NOT counted (sends is deliberately uncounted), the hidden row reports “the shift shown for this date is flagged and will send” via servingRemind, and the badge total is 0.
Given the same pair but the live row has its own amber problem (no-account), then the total is 1 — the live row's — and the shadowed row is still benign.
Given a hidden flagged row and a log recording a send for that date, then the log still decides the status (if (log) precedes the hidden branch) and the table never shows “sent ✓” and “will never send” for the same person and date.
Given an orphan log row (hidden: true, remind: false, with a log), then the log decides it and the hidden branch is never reached.
Given a flagged hidden row that is also valid: false (no start/end), then it is counted (it is a real stale flag) but offers no checkbox even after Phase 2 — planReminderToggles:758 refuses it — and its title says to fix it in the editor.

Phase 1.5 — prevent way 1 at the save confirm (gated on the decision above; no new write)

  • When a save is about to create or widen a temporary schedule that will hide dates carrying reminders, the existing confirm names how many, so Christie can cancel instead of discovering it later.
Given a save that creates a window covering three flagged base overrides, when the existing “regular schedule stays hidden” confirm appears, then it also says three reminders will stop sending; and cancelling writes nothing.
Given a window covering no flagged overrides, then the prompt is unchanged from today.

Phase 2 — the manager can clear a stale flag (Firestore write)

  • Christie can untick a flagged hidden shift from the Reminders view and the flag is actually removed.
  • She can never tick a hidden shift — that would create a flag that cannot send.
  • Every other toggle behaves exactly as today.

The guard, as an assertion rather than a bypass (Claude's shape; it makes the write surface move rather than widen, and Phase 2's “bounds edited between load and untick” case falls out of it for free):

const serving = isInFutureWindow(d.futureSchedule, dateStr) ? 'future' : 'base';
const wantShadowed = t.shadowed === true;
if ((t.layer !== serving) !== wantShadowed) { skipped.push({ date: dateStr, reason: 'moved' }); return; }
if (wantShadowed && t.remind) { skipped.push({ date: dateStr, reason: 'shadowed-tick' }); return; }
const layer = t.layer;   // ← everything below MUST use this
The trap both reviewers named, and the most likely partial implementation. Today layer is both the guard's subject and the map/path selector (:756, :760). Loosening the guard without repointing layer to t.layer reads and deletes from the serving map — precisely the blind write the guard exists to stop — and it passes any test that only asserts “the untick succeeded”. Every Phase 2 test must assert the stored document on BOTH layers.

Correction carried from the review: v1 credited the moved guard with preventing the phantom-shift / bounds-less-futureSchedule hazard. It does not — the changed guard does (:758 requires the date to exist in the chosen map with start and end; :759 requires sameShift). What moved uniquely prevents is a tick landing on a layer that can never send, which the untick-only rule covers.

UI sites (v1 named none): reminderRowToggleable (app.js:3155) categorically rejects hidden rows; the renderer (:3218) emits no checkbox for them; describeSkipped (:3258) needs a shadowed-tick case. And decide explicitly whether “Clear all shown” includes them — it filters on the same reminderRowToggleable (:3294), so it would sweep them in by default, while its confirmation text currently says hidden rows are excluded.

Required before coding (AGENTS.md, non-negotiable): a failing Firestore emulator test first, then the fix, then green. Then a second-model implementation review of the diff before Phase 3.

Given a flagged hidden base override, when Christie unticks it, then remind and remindUid are deleted from that base override only, and the futureSchedule and every other date are byte-identical afterwards.
The mirror. Given a flagged hidden future override, when she unticks it, then the future override loses its two keys and the base map is untouched.
Given a hidden row, when a tick is attempted, then it is skipped shadowed-tick and reported — no write.
Given an ordinary stale toggle whose layer no longer matches and which does NOT carry shadowed, then it is still skipped moved — the exception cannot be exploited by a stale normal row.
Given a row shown as hidden whose window bounds changed since the view loaded so it is no longer shadowed, then the assertion fails and it is skipped moved — never written where she did not look.
Given the requested hidden map or value was deleted, set to null, or made incomplete since the view loaded, then it is skipped changed and no parent is recreated.
Given the shift was rewritten by another manager since the view loaded, then sameShift still skips it as changed.
Given another manager already removed the hidden flag, then the untick is an idempotent success with no write (matching today's “a toggle that already holds is counted as applied with no write”), and the row refreshes.

Completeness check — what if this stops part-way?

  • After Phase 1 alone: Christie is told, but in the window-covers-today case she cannot clear it anywhere except the Firebase console. Acceptable only as a brief intermediate state — not a permanent stopping point (this is what v1 got wrong). If it must ship alone, the amber title has to name the console.

  • After Phase 2: feature complete; only docs lag.
  • Mid-Phase 1: an unrecognised status code falls through to default: { cls: 'muted', text: s.code } — today's behaviour. Safe either way.
