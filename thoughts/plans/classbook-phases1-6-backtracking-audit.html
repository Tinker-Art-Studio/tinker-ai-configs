Context — the audit, and one architectural insight it led to

How the audit was run: two independent instances (one Codex CLI, one separate Claude Code instance), each given read-only access to the real app repo, instructed to verify the REAL current code against the same classes of bug the companion plan's Vulnerability #11 work has repeatedly found.

What they found, combined: 13 real issues. The two most severe were verified a third time — directly, by reading the cited code — before being written up here.

The architectural insight that started this plan: three of the most severe findings share one root cause — saveSingleLesson() silently returns undefined instead of throwing when the global lessonDataLoadedSuccessfully guard is tripped. Fixing this one function to throw instead of silently returning closes several downstream findings as a side effect. Phase 1 below is that fix.

A second, larger architectural insight, found in round 3: saveSingleLesson()'s non-summer branch and deleteLessonKey() both operate on dotted-path fields within the SAME single Firestore document, curriculum/lessonData — confirmed by reading both functions directly (js/firebase-data.js:692-760, 371-379). Firestore guarantees a single .update() call on one document is atomic: either every field in that call lands, or none do. Round 2's occupied-swap/move logic did two or three SEPARATE saveSingleLesson()/deleteLessonKey() calls and then tried to detect and compensate for partial failure after the fact — an entire class of bug (and an entire class of fix, and an entire class of bug IN that fix, which is what rounds 2 and 3 kept finding) that simply doesn't exist if the multiple writes are combined into one atomic call in the first place. Phase 9 below replaces the compensating-write design with a new shared helper, saveMultipleLessonFields(), built exactly this way.

Round 4 update (Aug 15, 2026): that atomic write genuinely eliminates the PARTIAL-FAILURE race — both reviewers confirmed this holds under hostile re-tracing. But Codex found it doesn't and can't eliminate a DIFFERENT race: movedLesson/swappedSource/swappedDest are still built from a local cache snapshot taken at click time, so an atomic write can faithfully apply STALE data. This is not a regression this plan introduced — the exact same exposure existed in the original shipped code before any of Phases 1-11 changed anything — but it's real, and Christie decided it deserves proper tracking rather than either a rushed fix or being silently forgotten. // Pure helper — computes the dotted-path update object for ONE lesson within
// the shared curriculum/lessonData document, given an already-finalized
// lessonData object. Extracted from saveSingleLesson()'s non-summer branch
// (round-3 refactor) so it can be reused by saveMultipleLessonFields() below
// without duplicating the stripping/clearing logic.
function buildLessonFieldUpdates(semesterKey, lessonKey, lessonData, fieldsToClear = []) {
  const clearedContentFields = fieldsToClear.filter(f => CONTENT_FIELDS.includes(f));
  const stripped = { ...lessonData };
  CONTENT_FIELDS.forEach(f => { if (!stripped[f] || !String(stripped[f]).trim()) delete stripped[f]; });
  const cleanData = JSON.parse(JSON.stringify(stripped));
  clearedContentFields.forEach(f => { cleanData[f] = firebase.firestore.FieldValue.delete(); });
  const updates = {};
  for (const [field, value] of Object.entries(cleanData)) {
    updates[`${semesterKey}.${lessonKey}.${field}`] = value;
  }
  return updates;
}

    }

  }
}
