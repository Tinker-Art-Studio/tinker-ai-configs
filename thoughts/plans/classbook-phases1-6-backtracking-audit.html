Context — the audit, and one architectural insight it led to

How the audit was run: two independent instances (one Codex CLI, one separate Claude Code instance), each given read-only access to the real app repo plus the two reference documents describing what Phases 1-6 were SUPPOSED to implement (CLASSBOOK-DATA-SAFETY-PLAN.md and the companion plan's Phase 1-6 sections), instructed to verify the REAL current code against that intent and against the same classes of bug the companion plan's Vulnerability #11 work has repeatedly found — not to trust either reference document's own "shipped and deployed, all clean" framing.

What they found, combined: 13 real issues (some independently corroborated by both reviewers, several found by only one). The two most severe were verified a third time — directly, by reading the cited code myself — before being written up here, given how disruptive it would be to report something this severe if it were wrong.

The architectural insight, found while designing Phase 1 below: three of the most severe findings (Phase 2, Phase 3, Phase 4 below) share one root cause — saveSingleLesson() silently returns undefined (just a console.error) instead of throwing when the global lessonDataLoadedSuccessfully guard is tripped. Every caller that chains a .then() or sits inside a try block assumes a resolved promise means the write happened — so the guard, which exists specifically to make writes fail safely when local state can't be trusted, currently makes them fail UNSAFELY instead: callers proceed as if the save succeeded, and several of them then take a DESTRUCTIVE follow-on action (deleting a source lesson after a "move" or "swap") on that false assumption. Fixing this one function to throw instead of silently returning closes three of the four HIGH findings below as a side effect, since each affected call site already has error-handling machinery (a catch block) that currently only engages on a genuine exception — once the guard failure IS a genuine exception, that existing machinery engages correctly, automatically, with no separate patch needed at each site. This is the same kind of root-cause-over-patch preference the companion plan repeatedly converged on (Phase 14's redesign, Phase 18's block-at-source decision) — Phase 1 below is that fix, and it should very likely be designed, reviewed, and shipped first, since it changes what the OTHER phases even need to do.

Cross-plan coordination note, important: saveSingleLesson(), readAdminLessonDoc(), and saveAdminEdit() are all used or directly modified by multiple NOT-YET-EXECUTED phases in the companion plan (classbook-data-safety-remaining-stages.html, Phases 7-18) — most notably Phase 9, which already plans to add an opts param to readAdminLessonDoc() for its own purposes while explicitly preserving the OLD cache-permitting default for the move read-back (this plan's Phase 6 changes that same default). Christie's explicit sequencing decision: execute this plan first, then re-verify/redo the companion plan's review, since several of its phases' pseudocode was written assuming the CURRENT (buggy) behavior of these shared functions and will need re-examination once this plan changes them. Each phase below names its specific known coordination point.

Phase 1 — saveSingleLesson() fails loudly instead of silently, when the load-guard is tripped

🛑 Root cause of Phases 2, 3, and 4 below — found while designing a fix for those, not a separate audit finding on its own. saveSingleLesson() (js/firebase-data.js:692-695) checks lessonDataLoadedSuccessfully === false at its own top and, if tripped, does console.error(...); return; — a normally-resolving undefined, not a thrown error. Every caller across the app either awaits this with no return-value check at all, or chains a .then() assuming resolution means success. The guard's entire purpose is to make writes fail safely when the app can't trust its own local state — as implemented, it does the opposite: it makes them fail invisibly, and several callers then take an irreversible follow-on action (deleting a lesson) believing the preceding write succeeded.

What it does

File: js/firebase-data.js, saveSingleLesson(semesterKey, lessonKey, lessonData, fieldsToClear = []). No ordering dependency on Phases 2-8 below — but Phases 2-4 should be designed/reviewed AFTER this phase, since this phase changes what error-handling they actually need to add.

⚠️ Coordination with the companion plan, to check when that plan's review is redone: every phase in classbook-data-safety-remaining-stages.html that calls saveSingleLesson() (Phases 1, 7, 8, 9, 11, 12, 13, 14, 17 either directly or via a helper) was designed against the CURRENT silent-return behavior. Most of them already wrap the call in their own try/catch expecting a possible throw for OTHER reasons (network, permission) — this change likely makes their existing error handling correctly cover the guard case too, the same way it does for this plan's Phase 2-4 callers, but each should be re-checked, not assumed, when that plan's review resumes.
async function saveSingleLesson(semesterKey, lessonKey, lessonData, fieldsToClear = []) {
  if (lessonDataLoadedSuccessfully === false) {
    // Was: console.error(...); return; — a silently-resolving no-op that every
    // caller mistook for success. Now matches how every OTHER load-guard check
    // in this codebase already behaves (e.g. every "if
    // (lessonDataLoadedSuccessfully === false) throw ..." in the companion
    // plan's own proposed phases) — fail loudly, let the caller's existing
    // error handling engage, rather than silently no-op and let the caller
    // proceed on a false assumption.
    throw new Error('Lesson data failed to load — refusing to save to avoid writing over unconfirmed server state. Reload and try again.');
  }
  // ... rest of the function unchanged ...
}

Phase 2 — Move's read-back verification: force a server read, and check the content actually matches, not just that content exists

🛑 Two independent, compounding gaps — found by both reviewers, verified directly against the real code. readAdminLessonDoc() (js/app.js:4571-4575) does a bare .get() — no {source:'server'} — despite existing specifically to verify a write actually landed before deleting the source (the read-back step in handleGridAction()'s move branch, app.js:4658-4669). This is the EXACT risk Phase 3 (Stage 2E)'s verifySummerLessonWrite() was built to close elsewhere in this same codebase, with an explicit comment explaining why a cache read is unsafe immediately after a write — that reasoning was never applied to this sibling code path. Separately, the check itself only asks "does the destination have ANY content" (lessonHasContent(destReadBack)), not "does it match what was just moved there." Move already supports targeting an already-occupied destination (confirmed directly: app.js:4609-4613 warns "This will overwrite it" and proceeds) — so when the destination already had real content BEFORE the move, and the write to it silently fails or doesn't fully land, the read-back finds the destination's OLD content still sitting there, misreads that as "the move succeeded," and the source gets deleted. Net effect: the moved lesson is gone from both its old and new locations; the destination's original occupant is untouched.

async function readAdminLessonDoc(semKey, lessonKey, opts = {}) {
  if (!curriculumDb) initCurriculumFirestore();
  // Round-1 fix: adopt the companion plan's opts.source==='server' shape,
  // not this draft's original opts.forceServer — they're the same function,
  // and only one convention can win once both plans have shipped.
  const getOpts = opts.source === 'server' ? { source: 'server' } : undefined;
  const snap = await curriculumDb.collection('curriculum').doc('lessonData').get(getOpts);
  return snap.exists ? (snap.data()?.[semKey]?.[lessonKey] || null) : null;
}

Phase 3 — Occupied-swap: a genuine second-write failure leaves Firestore half-swapped with a false "restored" claim

🛑 Found by Codex, verified against the real code — a distinct problem from Phase 1's guard-bypass fix, since it's about a genuinely thrown error, not a silent no-op. handleGridAction()'s occupied-swap branch (app.js:4692-4710) does two sequential await saveSingleLesson() calls inside one try block. If the FIRST succeeds and the SECOND genuinely throws (network drop, permission change, quota — a real failure, not the Phase 1 guard case, which after Phase 1 ships would ALSO throw here and hit this same catch), the catch block calls restoreGridActionState(), which only reverts the in-memory model and re-renders — it performs no compensating Firestore write. The alert claims both lessons "have been restored to their original slots," but that's only true in the browser; Firestore still has the first write's result live, with no second write to complete or revert it.

What it does

File: js/app.js, handleGridAction()'s occupied-swap branch. Depends on Phase 1 shipping first, since Phase 1 changes what actually reaches this catch block (the guard case now arrives here too, in addition to genuine network/permission failures) — this phase's fix needs to handle both origins correctly, not just the pre-existing genuine-failure case.       // half-swapped now. Do not claim restoration; tell the admin the

Phase 4 — Move and swap never compute fieldsToClear, silently creating hybrid lesson content

🛑 Found by Codex, verified against the real code — reachable with no network failure or concurrency required, the most easily-triggered finding in this audit. Move and swap are meant to be full-replacement operations, but they call saveSingleLesson() with no fieldsToClear argument. saveSingleLesson()'s stripping logic omits empty content fields from the write entirely, rather than clearing them — so any content field that's empty in the INCOMING (moved/swapped) lesson but non-empty in the lesson ALREADY at that destination survives untouched. Concrete swap example: lesson A has real introPitch text and an empty processStep1; lesson B has the reverse. After swapping A and B, BOTH slots end up with the same hybrid A/B content instead of genuinely exchanging places — this is exactly the "Stage 1 stripping blocks intentional clears" problem Phase 4 (Stage 3) in the companion plan's Phases 1-6 was built to solve, but that fix (fieldsToClear support) was only ever wired into the two teacher-facing edit modals, never into the admin grid's move/swap actions.

What it does

File: js/app.js, handleGridAction()'s move and both swap branches. No dependency on Phases 1-3 above — this is an independent bug in the same function, fixable in any order relative to those. Round 1 finding (R1-11, Codex + Claude, HIGH, independently corroborated by both reviewers): the first draft's occupied-swap formulas compared the wrong baseline objects — destLesson vs swappedSource and sourceLesson vs swappedDest — both of which are identical-by-construction for every content field (since swappedSource IS a spread of destLesson, and swappedDest IS a spread of sourceLesson, with only non-content fields overridden). That makes both filters mathematically always empty — the fix did not fix its own headline BDD example. The move-side formula (comparing genuinely different objects, destLesson vs movedLesson) was correct as originally written and is unchanged below. Round 1 finding (R1-12, Codex, HIGH): even corrected, the fix's scope of CONTENT_FIELDS only (7 fields) misses other optional fields that can also survive as hybrid leftovers on an occupied move/swap — see the open note below. Phase 5 — Photo replacement deletes the newly-uploaded photo, not the old one

🛑 Found by Codex, independently re-verified by reading the code directly before including it here, given how severe and surprising the claim is. getPhotoPath(semesterKey, lessonKey, filename) (js/firebase-data.js:775-779) always computes the SAME path for a given lesson — curriculum/{semester}/{lessonKey}/demo.jpg (summer: summerCamps/{lessonKey}/demo.jpg) — there is no unique filename or version suffix per upload. All three photo-editing call sites (saveTeacherEdit() app.js:3050-3057, saveAdminEdit() app.js:4519-4522, the summer modal's saveLesson() app.js:9772-9776) follow the identical sequence: upload the new file to that deterministic path (overwriting whatever was there), THEN unconditionally delete existing.photoPath if one was recorded. For any lesson that already has a photo — a genuine REPLACEMENT, not a first-time upload — existing.photoPath is exactly the path that was just overwritten, since it was computed by this same function on a prior save. deleteLessonPhoto() (firebase-data.js:813-819) genuinely deletes the object (it only swallows "already gone" errors, nothing else) — so the sequence is: overwrite the photo with the new image, then immediately delete that same object, then save a Firestore download URL pointing at nothing. Only triggers on replacement (not first-ever upload for a lesson), which likely explains why this hasn't been reported yet — but every teacher or admin who replaces an existing demo photo today gets a broken image.
