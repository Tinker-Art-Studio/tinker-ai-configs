Plan: Training Hub data-loss check panel

App: Training Hub (~/Documents/New project, project tinker-hq-apps) · Parent: Firebase Backend Resilience Plan, Step 4 (firebase-backend-resilience-report.html, plan_QTCn4wTWpk-h) · Drafted: Oct 9 2026 · v2 after design review r1 (in-session Claude agent: READY WITH CHANGES, all applied) · execution-ready: true (Christie decided D1/D2 Oct 9 and said "let's get going")

Goal: a manager can open the Training Hub Dashboard and, in one click, see whether any of the four irreplaceable record sets (onboarding checklists, observations, training assignments, onboarding people) has shrunk sharply or become unreadable since a known-good moment, and so tell "data was lost" apart from "a rules change hid it" before anyone panics or "fixes" anything.
Why: the tripwire engine (src/lib/dataLossIncidentCheck.ts, committed Sep 10 in 6db527b) is built and unit-tested but nothing calls it, so it monitors nothing. This is the last Training Hub item in Step 4.

Current state (researched Oct 9)

  • Engine: checkForDataLossIncident() reads the four collections with Promise.allSettled (plain .get(), which can silently answer from the offline cache), so a denied read shows up as its own anomaly instead of hiding the whole check. Thresholds: any drop at all in onboardingChecklists (no delete path exists for it); a drop of 25% or more in the other three. The baseline is stored as counts in this browser's localStorage; the record time isn't saved, and a failed save is silently ignored.
  • Rules (origin/main studio-hub/firestore.rules): all four collections allow read for isManagerOrAbove(), so a manager can count all four. No rules change, no new collection.
  • UI: the Dashboard (src/components/training/Dashboard.tsx) already has a manager-only card (Canonical Sync), so a second manager-only card fits beside it. canManageTraining is also true in demo mode, so the new card must also require firebaseConfigured.
  • Tests: vitest, 144/144 at 7de92fe. 16 of those are the engine's own tests (two assert today's merge-on-record and void-return behaviour and will change deliberately in Phase 1), run against the in-memory fake (testSupport/fakeFirebaseCompat.ts). There's no Firestore emulator setup in this repo. That's acceptable here because nothing in this plan writes to Firestore.
  • Read cost: one check reads every document in the four collections once. Today that's tens to low hundreds of documents, and the Dashboard already loads all assignments for managers.

Decisions for Christie

D1 — Where the baseline lives. DECIDED Oct 9 (Christie): this browser. The baseline is "how many records were here at a moment I trusted". Keeping it in the browser means no new collection, no rules change and no guard deploy. Downside: it exists only in the browser where it was recorded. A different computer or a cleared browser shows "No baseline yet" until someone presses Record baseline there. The panel says this in plain words and shows when and where the baseline was recorded. Alternative: one shared Firestore doc that every manager sees. That needs a new rule and a sha-approved rules release, so it's a reasonable later upgrade if one browser turns out to be too limiting.
D2 — Manual only, or also check automatically? DECIDED Oct 9 (Christie): also automatic, quietly. If the check runs only when someone clicks it, nobody will click it until data already looks missing. Recommended: when a manager opens the Dashboard and this browser has a baseline, run the check once per page load. Stay silent when everything looks fine; show a red banner at the top of the card when something has dropped or can't be read. Cost is one extra read of the four collections per Dashboard open, by managers only. Alternative: button only (the parent plan's minimum).

Phases

Phase 1 — Engine fit-out (no UI)

Acceptance (user terms): the engine can tell the panel when a baseline was recorded, refuse to record one from a check with a failed read, list which collections a new baseline would lower, and report whether the baseline actually saved.

  • Server reads only: read with .get({ source: 'server' }) so an offline device can't report cached or empty counts as a drop (review r1 #1). The test fake learns to accept the option and to simulate an offline failure.
  • Why a read failed: keep the Firestore error.code next to readError. permission-denied is "rules"; unavailable and anything else is "couldn't reach Firebase" (review r1 #1).
  • Save recordedAt with the counts. A new loadDataLossBaselineInfo() returns {counts, recordedAt} (review r1 #5). Older stored baselines without the date still load, with recordedAt null.
  • Recording replaces the baseline (all four counts plus the date) instead of merging, which could keep one stale count (review r1 #4). It returns whether it saved, so blocked browser storage says so instead of failing silently.
  • Ratchet up: after a check where every read succeeded and nothing is anomalous, raise each stored count to max(baseline, now). Without this, a baseline of 100 that grew to 200 would miss a loss of 120 records (review r1 #3). The ratchet never lowers a count; lowering needs Record baseline with confirmation. recordedAt stays the manual record date, and a separate raisedAt notes the last automatic raise.
  • New pure helpers: baselineFromCheck(result) returns counts only when every read succeeded, otherwise null. collectionsLoweredBy(result) lists collections whose current count is below the stored baseline.
  • Unit tests for each. The merge test and the "doesn't throw" test are rewritten on purpose (replace semantics; returns false); the other 14 stay as they are.
Happy: Given a check where all four reads succeed, when a baseline is built from it, then it holds all four counts plus a timestamp, and loading it back returns the same.
Edge: Given a baseline stored by the Sep 10 code (counts only), when it is loaded, then the counts come back and recordedAt is null.
Edge: Given baseline observations 100 and a clean check reads 200, then the stored baseline becomes 200. A later check reading 80 is flagged Dropped.
Failure (offline): Given the device is offline, when the check runs, then every read is a "couldn't reach Firebase" failure, not a count of 0. Nothing is ratcheted and nothing can be recorded.
Failure: Given a check where onboardingChecklists was denied, when a baseline is built from it, then the result is null (nothing to record). Given localStorage throws on write, when recording, then it returns false.

Phase 2 — Manager-only "Data safety check" card on the Dashboard

Acceptance (user terms): a manager sees a card with Check now and Record baseline, plus one row per record set showing the baseline count, the count now, and a status: OK, Dropped, Couldn't read, or No baseline. Non-managers and demo mode never see the card.

  • Plain names: Onboarding checklists · Observations · Training assignments · Onboarding people.
  • Couldn't read wording, chosen by error code. permission-denied: "Training Hub couldn't read this, which usually means a permissions (rules) change, not deleted data. Don't change or re-enter anything. Tell Christie." Anything else: "Couldn't reach Firebase. Check the connection and press Check now again." Dropped wording: "Fewer records than the baseline. Don't re-enter anything yet. Tell Christie."
  • Record baseline runs a fresh check first. If any read failed, it refuses and says why. If any count is lower than the current baseline, it asks for confirmation and names those sets ("This accepts the lower counts as the new normal"), because recording a baseline after a loss would hide that loss.
  • Footer line: "Baseline recorded in this browser only." Or: "No baseline in this browser yet. Press Record baseline when you know the data is right."
  • Automatic check (D2): runs at most once per page load per signed-in user, with a baseline present. The run-once guard and the last result live outside Dashboard, because Dashboard unmounts on every view switch (App.tsx renders it conditionally) and StrictMode double-runs effects in dev (review r1 #2). A result that arrives after sign-out or a viewer change is dropped. The banner shows only on an anomaly.
  • Read-only: the card performs no Firestore writes.
  • Tests: unit-test the pure row/status/message builder; tsc + vitest green. The live click-through is Christie's (Claude can't sign in as her).
Happy: Given a manager whose browser has a baseline and unchanged data, when they press Check now, then four rows show OK and the counts match the baseline.
Edge: Given a browser with no baseline, when the manager opens the Dashboard, then no automatic check runs, every row reads "No baseline", and the card explains how to record one.
Edge: Given the automatic check ran, when the manager goes Dashboard → Library → Dashboard, then no second set of reads happens and the last result is still shown.
Failure: Given a rules regression denying trainingObservations, when the check runs, then that row reads Couldn't read with the rules wording, the banner is red, and Record baseline refuses.
Failure: Given onboardingChecklists went from 40 to 39, when the check runs, then that row reads Dropped (any drop counts for checklists), while observations going 100→90 stays OK (under 25%).

Completeness: what if this is interrupted?

  • Accepted (review r1 #6): the baseline is studio-wide headcounts, not personal data, so another manager on the same browser using it is fine. Anyone using that browser could see four document counts in localStorage. That's acceptable; nothing is cleared on sign-out.
  • Known LOW (review r1): an admin user doc with active: false passes the app's manager check but not the rules, so they'd see "Couldn't read". Their whole Dashboard load would already fail before that, so nothing extra is done for it.
  • Work is on branch claude/step4-data-loss-panel, one commit per phase. An unfinished branch changes nothing live.
  • Phase 1 alone is harmless (engine only, still unwired). Phase 2 merged but not deployed is harmless. Nothing reaches users before Phase 3's deploy.
  • If deployed but no baseline is recorded yet, the card shows "No baseline". That's harmless, and the next manager visit can record one.
