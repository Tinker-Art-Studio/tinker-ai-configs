Plan: Recap Open Tasks — grouping, hand-back, topics, reassign

App: Recap (~/recap) · Drafted: Sep 22 2026 · execution-ready: false — awaiting second-model design review.

Goal: the Open Tasks list reads as organised work instead of one long list (grouped by meeting and topic, with the meeting viewable in place), and no task can silently fall through the cracks when someone says it isn't theirs.

Scope limits: no Firestore rules change and no new collection in any phase. Every new field (topic, passedBy) lives inside summary.beforeNextMeeting, the one field a shared non-manager is already allowed to write. Roles are never changed (see CLAUDE.md, "Roles are GLOBAL").

Current state (researched Sep 22)

  • tasks.html + renderOpenTasks() (js/app.js ~5196) group by assignee only. Each row carries its meeting title, date and series as small meta text.
  • The meeting link calls openMeetingById(), which navigates away to meetings.html#meeting=.
  • "Not mine" only hides. It appends taskKey to the viewer's users/{uid}.dismissedTaskKeys. The meeting still lists the task under the same assignee, so a task someone has disowned still looks owned. This is the silent-drop problem.
  • Data shape: summary.beforeNextMeeting = [{ assignee, items: [string | {text, done}] }]. One assignee can already have several groups; applyTaskDone() walks all of them.
  • Writes from Open Tasks: setTaskDone(), a transaction that finds the item by assignee + text and writes summary.beforeNextMeeting only. That is the only update a shared non-manager's rule branch (onlyActionItemsChanged()) accepts.
  • The detail view (meetings.html) renders action groups at ~3387 and allows drag between groups, renaming an assignee and "+ Add person". The new-meeting summary renders them at ~1818, and the copy-as-text/HTML formatters at ~4311 / ~4392.
  • The summarize prompts in server/server.js emit {assignee, items}. Personal/logistics prompts already use assignee as a life category.
  • Tests: task-helpers.test.js (pure helpers) and task-write.emulator.test.js (firebase-admin, behaviour only). Meetings rules are covered in studio-hub/rules.test.js.
Trap to respect (CLAUDE.md): the detail view's concurrency protocol (one object per meeting via canonicalMeeting(), one write queue per meeting, a _savedSummary baseline). The Open Tasks popup must not reuse showMeetingDetail() or create a meeting object that reaches it. The popup is a separate, read-only render. Its only write is the existing setTaskDone() transaction.

Phases

Phase 1 — Group by meeting + view-only meeting popup (display only, no data writes beyond the existing tick)

Acceptance (user outcomes):

  • Everyone's view nests Person → Meeting (title · date) → tasks; My tasks nests Meeting → tasks. Meetings are newest first. Unknown speaker / Unassigned stay last.
  • Clicking a meeting header (or a task's meeting link) opens a popup over the list showing the meeting's summary, including its action items with checkboxes for tasks the viewer can tick (canEditTaskMeeting). Closing it returns to the same scroll position.
  • The popup has an "Open full meeting" button that goes to meetings.html#meeting= for editing.
  • Ticking in the popup removes the task from the list behind it without a reload.

Implementation notes: add a pure groupTasksForDisplay(tasks, {byPerson}) to task-helpers.js (unit-tested) that returns the nested structure. The popup reads the meeting from the meetings array loadOpenTasks() already fetched (keep it in a module-level map; no extra read). Build a task object per item and tick through setTaskDone(). Close on Esc, the backdrop and the ×.

Happy: Given Anika has 6 open tasks from 2 meetings, when she opens My tasks, then she sees 2 meeting headers with 4 and 2 tasks under them, newest meeting first.
Edge: Given a meeting whose summary is malformed, when its header is clicked, then the popup shows what it can and "some items couldn't be read", and the list behind it is unaffected.
Failure: Given the meeting was unshared from Anika after the page loaded, when she ticks a task in the popup, then she sees the existing "no longer shared" message, the checkbox reverts, and nothing else changes.

Phase 2 — "Not mine" hands the task back + Needs attention (data write: beforeNextMeeting only)

Acceptance:

  • Assigned solely to the viewer (the trimmed assignee equals one of their name variants, case-insensitive): "Not mine" asks for confirmation ("This goes back to Unassigned on the meeting so someone can reassign it"), then moves the item into the meeting's Unassigned group (creating the group if needed) with passedBy: "<first name>" and passedAt (ISO date string).
  • Shared assignee ("Anika or Christie", "Carey/Christie"): "Not mine" keeps today's hide-only behaviour, because someone else still owns the task. The confirm text says so.
  • The Open Tasks page gets a third tab, Needs attention, listing every Unassigned and Unknown speaker task across readable meetings, grouped by meeting, with "passed on by Anika · Sep 22" where it applies.
  • For managers, the Open Tasks nav link shows a count ("Open Tasks · 3") on every Recap page, so handed-back tasks aren't missed.
  • The detail view shows "passed on by Anika" next to such an item. Dragging it to a person clears passedBy/passedAt.

Implementation notes: add a pure moveTaskToAssignee(rawGroups, task, newAssignee, extraFields) to task-helpers.js and use it in Phases 2 and 4. It follows the same invariant as applyTaskDone: locate by assignee + text, touch nothing else byte-for-byte, and append to the first group with the target assignee (and the same topic, once Phase 3 lands) or push a new group. Write through a new moveTask() transaction mirroring setTaskDone(), with summary.beforeNextMeeting as the only field. If the source group becomes empty, leave it (removing groups is the owner's call in the detail view).

Happy: Given "Order clay" is assigned to "Anika" on a meeting shared with her, when she clicks Not mine and confirms, then the meeting shows it under Unassigned with "passed on by Anika", her list drops it, and Christie's nav reads "Open Tasks · 1".
Edge: Given "Book the kiln tech" is assigned to "Anika or Christie", when Anika clicks Not mine, then it only hides from Anika's list (existing dismissedTaskKeys) and stays on Christie's.
Failure: Given Christie renamed the item in the detail view after Anika's list loaded, when Anika clicks Not mine, then the transaction can't find it, she sees "That item has changed — reload and try again", and nothing is written.
Accepted limit (existing, same-section last-save-wins): if Christie has the same meeting open in the detail view and edits its action items after Anika hands one back, Christie's save can put it back under Anika. carryRemoteDoneFlags carries ticks, not moves. This is rare, and the item is never lost, just un-handed-back. A per-item merge is the fix if it ever bites.
Nav count cost: the count needs queryReadableMeetings() on pages that don't already run it (index, meetings, settings). That's one extra query per page load, for managers only, run after the page renders so it never blocks it.

Phase 3 — Topic headers (data write: new optional topic on groups; prompt change)

Acceptance:

  • New summaries of work meetings group each person's items by topic: a group is {assignee, topic, items}, with several groups per person when there are distinct topics. Personal/logistics prompts are unchanged (they already use assignee as the category).
  • The detail view shows each group as "Person · Topic". The topic is click-to-edit like the assignee, a "+ Add topic" button under a person creates a new group for them, and drag between groups moves items between topics.
  • Open Tasks nests … → Meeting → Topic → tasks, in both My tasks and Everyone's. Groups without a topic (every existing meeting) render with no topic header, exactly as today.
  • Copy-as-text/HTML includes the topic as a subheading.

Implementation notes: topic is on the group, so every existing identity rule (assignee + text in applyTaskDone, carryRemoteDoneFlags, taskKey) is unchanged. Renaming a topic never breaks a tick or a dismissal. collectOpenTasks adds topic: asText(group.topic). Strip an empty topic before any write (never store ""). Update all four renderers (new-meeting summary, detail, text, HTML) plus the server.js prompts and schema examples. The prompts must not use topic to infer an assignee, so the evidence-only attribution rules stay as they are.

Happy: Given a leadership meeting where Maryssa takes 9 items about camp, hiring and supplies, when it's summarized, then her tasks appear under 3 topic headers in both the detail view and her task list.
Edge: Given a meeting summarized before this change, when it's viewed, then it looks exactly as it does today (no "undefined" or empty headers).
Failure: Given the model returns a group with a non-string topic, when rendered, then it is treated as no topic, and nothing throws out of the rollup.

Phase 4 — Reassign from the task list (data write: beforeNextMeeting; optionally sharedWith by a manager)

Acceptance:

  • For the meeting's creator and managers (canEditMeetingDetail), "Not mine" and each Needs attention row get a Reassign… menu listing: people the meeting is shared with, then the meeting's participants (from meeting.participants), de-duplicated by first name. Participants the meeting isn't shared with are marked "not shared".
  • Picking a "not shared" person asks every time: "Share this meeting with Maryssa too?" with the choices Share & assign, Assign only or Cancel. Share & assign is offered to managers only, because a staff creator can't change sharedWith under the rules. Staff see "Assign only — they won't see it until a manager shares the meeting".
  • Reassigning clears passedBy/passedAt and lands the item in the new person's group with the same topic.
  • Shared staff never see Reassign. They keep Not mine (Phase 2).

Implementation notes: reuse moveTaskToAssignee. Share & assign is ONE transaction writing summary.beforeNextMeeting + sharedWith (a union of the current list read in the transaction, never a list rebuilt from the UI; see CLAUDE.md "Sharing — two traps"). Participants map to users by name through the same list loadRecapUsers() uses (active users only). A participant with no matching user can be assigned but not shared.

Happy: Given a handed-back task on a meeting Maryssa attended but isn't shared on, when Christie picks Maryssa → Share & assign, then the meeting is shared with Maryssa and the task is in her My tasks.
Edge: Given the participants list says "Julia, Christie" and Julia has no Recap user, when Christie reassigns to Julia, then only Assign only is offered.
Failure: Given someone else unshared Maryssa while the menu was open, when Christie confirms Share & assign, then the transaction re-reads sharedWith, unions Maryssa back in (Christie explicitly chose to share), and writes both fields atomically. Nothing is half-written.

Completeness — if interrupted

  • Each phase is independently shippable and committed separately. Phase 1 has no data effect.
  • Every data write is a single transaction, so there is no half-moved item.
  • Phase 3 fields are optional. Code from Phases 1–2 ignores topic, and older clients render topic-less. A half-deployed Phase 3 at worst shows groups without headers.
