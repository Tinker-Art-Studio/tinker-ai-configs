Plan: Recap Open Tasks — grouping, hand-back, topics, reassign

App: Recap (~/recap) · Drafted: Sep 22 2026 · v2 after a two-model design review (Claude + Codex, Sep 22; every finding verified against the code and folded in, see the Decisions log) · execution-ready: true — design review passed; Christie approved both decisions Sep 22.

Goal: the Open Tasks list reads as organised work instead of one long list (grouped by meeting and topic, with the meeting viewable in place), and no task can silently fall through the cracks when someone says it isn't theirs.

Scope limits: no Firestore rules change and no new collection in any phase (both reviewers verified this against onlyActionItemsChanged(), the staff sharedWith pin and the manager branch). Every new item/group field (topic, passedBy*, assignedAt) lives inside summary.beforeNextMeeting. Roles are never changed.
Decisions — RESOLVED Sep 22 (Christie: "yes, agreed" to both recommendations):
  1. What the nav count counts. "Unknown speaker" is a designed, frequent AI output, so counting every Unassigned + Unknown task would show a big number on day one that never reaches zero, and it would stop being read. Recommended: the badge counts only tasks someone handed back (not yet reassigned), and the Needs attention tab lists all of them.
  2. Reassign is managers only (narrower than "creator + managers"). Staff can't read the user list under the rules, so a staff creator's menu couldn't tell who the meeting is shared with. Staff creators can still reassign by dragging in the full meeting view, as today. Recommended: managers only.

Current state (researched Sep 22)

  • tasks.html + renderOpenTasks() (js/app.js ~5196) group by assignee only. The meeting link calls openMeetingById(), which navigates away to meetings.html#meeting=.
  • "Not mine" only hides: it appends taskKey (meetingId::assignee::text) to the viewer's users/{uid}.dismissedTaskKeys. The meeting still lists the task under the same assignee.
  • Data: summary.beforeNextMeeting = [{ assignee, items: [string | {text, done}] }]. One assignee can already have several groups.
  • setTaskDone() is a transaction writing summary.beforeNextMeeting only, which is the whole surface of a shared non-manager's rule branch.
  • Assignee-group renderers: the new-meeting summary (~1818), the detail view (~3387), copy-as-text (~4311), copy-as-HTML (~4392) and the series rollup (~4809, fed the raw summary JSON by server.js ~1143).
  • Field-dropping writes today: the detail-view and new-meeting text-edit handlers (app.js ~3629, ~1860) replace an item with normalizeActionItem()'s {text, done}, which drops any other key. applyTaskDone, carryRemoteDoneFlags and drag use {...raw} and preserve extra keys.
  • loadRecapUsers() is manager-only by construction (the users-list query is provable only via the manager branch) and excludes the viewer.
  • The existing Share write sets sharedWith, sharedByUid, sharedByName and sharedAt. The recipient's "new shared meeting" banner keys on sharedAt.
  • Tests: task-helpers.test.js and task-write.emulator.test.js (firebase-admin, behaviour). Rules are covered in studio-hub/rules.test.js.
Traps to respect (CLAUDE.md):
  • The detail view's concurrency protocol (one object per meeting via canonicalMeeting()). The popup must NOT reuse showMeetingDetail(). Its meeting map is populated only under isTasksPage and holds only the fields the popup renders. The nav count keeps a number only: it maps meeting docs to a count and drops them in the same expression, so no second meeting object ever exists on meetings.html.
  • Any write a shared non-manager can make must have exactly one top-level field, summary.beforeNextMeeting. moveTask() must never gain a second field, such as a document-level updatedAt/passedAt, or every shared user's hand-back is denied.

Shared foundation (lands with the phase that first needs it)

  • Item identity becomes topic-aware (Phase 3): applyTaskDone, moveTaskToAssignee and carryRemoteDoneFlags PREFER a group whose asText(group.topic) === task.topic, then fall back to today's assignee + text behaviour, so topicless data and renamed topics work as now. taskKey appends ::topic only when the topic is non-empty, so every existing dismissal key stays valid. With topics, "the same text under two topics" becomes routine, and without this a tick or move could hit the wrong twin.
  • Edits preserve item fields (Phase 2): fix the two text-edit handlers to write {...raw, text} (a string item becomes {text, done:false}). Otherwise renaming a handed-back item silently erases "passed on by".
  • collectOpenTasks carries raw fields (passedByName, passedAt, assignedAt, and group topic), all guarded with asText.

Phases

Phase 1 — Group by meeting + view-only meeting popup (display only; the only write is the existing tick)

Acceptance (user outcomes):

  • Everyone's view nests Person → Meeting (title · date) → tasks; My tasks nests Meeting → tasks. Meetings are newest first, and Unknown speaker / Unassigned stay last.
  • Clicking a meeting header (or a task's meeting link) opens a popup over the list: the meeting's summary plus its action items. Items the viewer can tick (canEditTaskMeeting) have live checkboxes; the rest are shown disabled. Esc, the backdrop or × closes it, keeping the scroll position.
  • An "Open full meeting" button goes to meetings.html#meeting= for editing.
  • Ticking in the popup removes exactly that task from the list behind it, with no reload. Re-opening the popup shows it ticked.

Implementation notes:

  • Add a pure groupTasksForDisplay(tasks, {byPerson}) to task-helpers.js, unit-tested.
  • Build the popup with document.createElement, the way showRollupModal() does, and reuse formatSummaryAsHTML() for the body, since it already guards malformed groups.
  • Popup rows are built from the same task objects as the list, collected with includeDone: true and split by done for the list. This keeps removal by object identity working when two items have identical text.
  • After a successful tick, apply applyTaskDone() to the cached meeting's summary.beforeNextMeeting and to the task object, then re-render both the list and the popup.
Happy: Given Anika has 6 open tasks from 2 meetings, when she opens My tasks, then she sees 2 meeting headers with 4 and 2 tasks under them, newest meeting first.
Edge: Given two open items with identical text in one meeting, when one is ticked in the popup, then exactly one row leaves the list, and re-opening the popup shows one ticked and one open.
Edge: Given a meeting whose summary is malformed, when its header is clicked, then the popup shows what it can, and the list is unaffected.
Edge: Given a shared staff user opens a meeting that is readable but not tickable, then the popup's checkboxes are disabled.
Failure: Given the meeting was unshared after load, when a task is ticked in the popup, then the existing "no longer shared" message appears, the checkbox reverts, and neither the cache nor the list changes.

Phase 2 — "Not mine" hands the task back + Needs attention (data write: beforeNextMeeting only)

Acceptance:

  • Solely assigned to the viewer: the assignee is normalised (trimmed, trailing : . , stripped, case-insensitive) and equals one of the viewer's name variants, with no separator (and, or, /, &, ",", +, with). "Not mine" confirms, naming the task, the meeting and the assignee exactly as written: "This goes back to Unassigned on Leadership · Sep 18 so someone can reassign it". It then moves the item into that meeting's Unassigned group (same topic; the group is created if needed), stamped passedByUid, passedByName and passedAt.
  • Anything else ("Anika or Christie", "Anika (lead)" and so on): today's hide-only behaviour, with confirm text saying someone else still owns it. This is the conservative direction: an ambiguous string is never moved.
  • The success toast has Undo, which moves the item back to the original assignee string and clears passedBy*, because shared staff otherwise can't reverse a mis-click.
  • The hand-back also arrayRemoves the viewer's own dismissal key for that item (a self-write, already permitted), so it can't re-arm later.
  • The Open Tasks page gets a third tab, Needs attention: every Unassigned and Unknown speaker task across readable meetings, grouped by meeting, with "passed on by Anika · Sep 22" where it applies. It ignores dismissedTaskKeys, so nobody can hide a task from triage, and it respects the mailbox filter.
  • After a hand-back the task shows under Unassigned in Everyone's and Needs attention without a reload, because the local task object is updated, not dropped.
  • Nav count (managers only; counts handed-back tasks not yet reassigned — Decision 1): "Open Tasks · N" on every Recap page. On tasks.html it is computed from allTasks with no extra query. On other pages it uses one query bounded to the last 90 days, runs after the page renders, is cached in sessionStorage for 5 minutes, and is skipped on index.html while recording or uploading. Staff never run the query.
  • The detail view shows "passed on by Anika" next to such an item. Moving it to a real person, by drag there or by Reassign in Phase 4, clears passedBy*.
  • CLAUDE.md's Open Tasks section is updated in the same commit ("Not mine" semantics changed).

Implementation notes:

  • Add a pure moveTaskToAssignee(rawGroups, task, newAssignee, {set, clear}) to task-helpers.js. It follows the same invariant as applyTaskDone: clone and change only the moved item and the destination group, and leave everything else byte-for-byte.
  • For duplicate texts it prefers the match whose done equals task.done, so it never moves the finished twin.
  • It appends to the first group matching the destination assignee and the same topic, or pushes a new group. The source group is left in place even if it becomes empty.
  • The moveTask() transaction mirrors setTaskDone(): exactly one top-level field.
Happy: Given "Order clay" is assigned to "Anika" on a meeting shared with her, when she clicks Not mine and confirms, then the meeting shows it under Unassigned with "passed on by Anika", her list drops it, Everyone's shows it under Unassigned immediately, and Christie's badge increments.
Edge: Given "Book the kiln tech" is assigned to "Anika or Christie", when Anika clicks Not mine, then it only hides from her list and stays on Christie's.
Edge: Given "Anika" has two identical "Email parents" items, one done and one open, when she hands back the open one, then the open one moves and the done one stays.
Edge: Given a handed-back item, when Christie edits its wording in the detail view, then "passed on by Anika" survives.
Edge: Given Anika hands one back by mistake, when she clicks Undo, then it is back under "Anika" with no passedBy*.
Failure: Given Christie renamed the item after Anika's list loaded, when Anika clicks Not mine, then she sees "That item has changed — reload and try again" and nothing is written.
Conservation (emulator): after any move, the total item count is unchanged, and string items, extra fields and malformed siblings are byte-for-byte preserved.
Accepted limit (same-section last-save-wins, existing): if Christie has that meeting open in the detail view and edits its action items after Anika hands one back, Christie's save can put it back under Anika. The item is never lost, just un-handed-back. An emulator test documents both commit orders: no loss and no duplication. A per-item merge is the fix if this ever happens in practice.

Phase 3 — Topic headers (data write: optional topic on groups; prompt change)

Acceptance:

  • New summaries of work meeting types that use beforeNextMeeting with named people (enumerated from server.js during implementation) group each person's items by topic as {assignee, topic, items}, with several groups per person when there are distinct topics. Excluded: personal/logistics (assignee is already the category), Work Reflection ("Self"), and the Julia flat actionItems format. Topic never influences attribution; the evidence-only rules are unchanged.
  • The detail view shows each group as "Person · Topic", still one DOM element per raw group (the drag handlers map DOM index to array index). The topic is click-to-edit, "+ Add topic" creates a new group for that person, and dragging moves items between topics.
  • Open Tasks nests … → Meeting → Topic → tasks. Groups without a topic (every existing meeting) render with no topic header, exactly as today. The mixed case (one person with one topicless group and two topic groups) renders the topicless items first.
  • Copy-as-text/HTML includes the topic as a subheading. The series-rollup prompt gets one line: ignore completed and handed-back items, and treat topic as context only.
  • Topic-aware identity (Shared foundation) lands in this phase.

Implementation notes: never store topic: ""; delete the key instead. A non-string topic is treated as none.

Happy: Given a leadership meeting where Maryssa takes 9 items about camp, hiring and supplies, when it's summarized, then her tasks appear under 3 topic headers in the detail view and her task list.
Edge: Given "Follow up with vendor" under both Camp and Supplies for Maryssa, when she ticks the Camp one, then only that one is ticked; the same holds for hand-back and dismissal.
Edge: Given a meeting summarized before this change, when it's viewed, then it looks exactly as today.
Failure: Given someone renames a topic while another person ticks an item under it, then the tick falls back to assignee + text and still lands on the right item (or fails with "item changed"). It never silently hits a different topic's twin when one with a matching done-state exists in the preferred topic.

Phase 4 — Reassign from the task list (data write: beforeNextMeeting; managers may also share)

Acceptance (Decision 2: managers only):

  • Managers get a Reassign… menu on their own rows and on every Needs attention row. It lists: Me (pinned first), people the meeting is shared with, then the meeting's participants, with participants not shared on the meeting marked "not shared".
  • Picking a "not shared" person asks every time: Share & assign, Assign only or Cancel.
  • Reassigning clears passedBy*, stamps assignedAt, and lands the item in the person's existing group (the same topic, matched by assigneeMatchesPerson and solely that person). Otherwise it creates a new group named by first name, matching how the AI writes assignees, so nobody shows up as two people.
  • A reassigned task always shows in the new person's My tasks: collectOpenTasks ignores a dismissal made before the item's assignedAt. This closes the stale-dismissal hole without writing to anyone else's user doc.
  • Staff never see Reassign. They keep Not mine and Undo.

Implementation notes:

  • Participant → user mapping fails closed:
    • An exact normalised full-name match wins.
    • A first-name match counts only if exactly one active Recap user has that first name.
    • If there's no match or more than one, the person can be assigned but not shared.
    • Distinct user IDs are never merged just because they share a first name.
  • Share & assign is ONE transaction writing summary.beforeNextMeeting, sharedWith (a union with the list read inside the transaction, never rebuilt from the UI), sharedByUid, sharedByName and sharedAt. That gives the recipient the new-share banner and the "Shared by" chip. It only ever runs for managers.
Happy: Given a handed-back task on a meeting Maryssa attended but isn't shared on, when Christie picks Maryssa → Share & assign, then the meeting is shared (and Maryssa sees the new-share banner), and the task is in her My tasks under "Maryssa", not "Maryssa Lastname".
Edge: Given Maryssa once dismissed that same text on that meeting, when it's reassigned to her, then it still appears in her My tasks.
Edge: Given two active users named Carey, when a participant "Carey" is picked, then only Assign only is offered.
Edge: Given Christie picks Me, then the task moves to "Christie" and appears in her My tasks.
Failure: Given someone unshared Maryssa while the menu was open, when Christie confirms Share & assign, then the transaction re-reads sharedWith, unions Maryssa in, and writes every field at once.
