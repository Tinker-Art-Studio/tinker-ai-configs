Plan: Classbook Concurrent-Edit Safety — Vulnerability #11 (Layer 1)

Goal: When two people have the same lesson open at once, saving your own edits never silently reverts someone else's concurrent edits to a different field, for the two teacher-facing lesson editors (saveTeacherEdit, saveLesson). A second-model review found a third editing surface, the admin's own edit popup (saveAdminEdit), has the identical vulnerability and is not closed by this plan — see "Not in scope."
App: tinker-spring-curriculum (The Classbook) — js/app.js (saveTeacherEdit, saveLesson), js/firebase-data.js (saveSingleLesson), e2e/data-safety.spec.js
Context: The Classbook Data Safety Plan (CLASSBOOK-DATA-SAFETY-PLAN.md) and its execution plan (classbook-data-safety-remaining-stages.html, plan_jrhp-GpcSGph) are both complete and deployed as of Aug 13, 2026. That plan's "Not in scope" section deferred Vulnerability #11 ("last write wins" on concurrent sessions) as low-risk, on the strength of a plan-reviewer comment resolution that characterized it narrowly as "the same-lesson-same-instant race" and concluded Christie's actual May 2026 incident was a different, already-fixed bug (the stale-load bulk-overwrite case). Both of those specific claims are true. What they missed: there's a third, broader mechanism neither the original vulnerability table nor that resolution named — see Context below. This plan exists because Christie asked directly what happens today if two people edit the same lesson concurrently, and the honest investigation surfaced this gap.
Scope decision: Christie chose Layer 1 only — stop resending untouched fields on every save. Layer 2 (detecting and warning on a true same-field collision) is explicitly deferred; see Not in Scope.
Risk: Medium — touches the core save payload construction for both lesson editors, the exact surface the whole prior plan was built to make safer. Both phases are additive/narrowing (send less, not more) and every existing safety mechanism (stripping, read-back verification, intentional-clear support) is left in place underneath.
execution-ready: false — awaiting review. Christie asked for a second-model-review before any execution starts, matching how every phase of the prior plan was handled.

Context — the mechanism that was missed, and why

Both lesson editors (saveTeacherEdit() for non-summer, saveLesson() for summer camp) build their Firestore write payload from every currently non-empty field in the open form, not just the field(s) the user actually typed into this session. Neither modal re-syncs its open form against live Firestore data while it's open — a live re-sync mid-typing would risk clobbering the user's own in-progress edit, so the form is effectively a point-in-time snapshot for as long as it stays open.

Concrete failure: Teacher A and Admin B both open the same lesson. Both load processStep1: "Old step 1". B edits processStep1 → "New step 1" and saves; Firestore now has "New step 1". A, still viewing their now-stale-loaded form, edits only projectTitle — never touching processStep1 — and saves. A's save payload still includes A's stale copy, processStep1: "Old step 1", because the payload is built from "every non-empty field currently in the form," not "every field this user changed." B's edit is silently reverted, even though A never opened that field.

Why this wasn't caught by the prior plan's reviews: Vulnerability #11 was marked "deferred, not in scope" early — plan_jrhp-GpcSGph's Aug 12 comment thread, resolved same-day — before Phase 1 of that plan had even started. Every later second-model-review in that plan was scoped to verifying the specific phase under execution (Phase 2's merge-vs-update semantics, Phase 3's cache-read bug, etc.). None were asked to re-derive Vuln #11 from the actual code, because it had already been closed as a scoping decision — a review only re-examines what it's pointed at. The resolution's own framing ("same-instant race") also didn't name the actual mechanism above, so there was no prompt to look again. This is a process gap worth remembering for future plans: an "out of scope" decision made before the relevant code exists (or before anyone has traced the actual mechanism) can go unexamined by every subsequent review indefinitely.

⚠️ The blocking guard is asymmetric between the two save paths, found while tracing this — not a new issue, unrelated to this plan's fix, noted for awareness: saveSingleLesson()'s "block if all content fields are empty" guard (firebase-data.js:712) exists only inside the summer branch. The non-summer branch has no equivalent blocking check at all — it always writes whatever's in the cleaned payload, empty or not (protected only by field-level stripping, not a whole-save block). This predates this plan and isn't something Layer 1 introduces or worsens on either path — flagging it here so it isn't mistaken for something this plan should also fix. Worth a look in a future session if it ever seems relevant.

Phase 1 — Non-summer editor: diff-only payload

What it does

File: js/app.js, saveTeacherEdit(lessonKey, originalLesson), around the line building updatedLesson (currently const updatedLesson = { ...originalLesson, ...formData };).

Build the Firestore-bound payload from only the fields getTeChangedFields() already reports as changed, not the full formData snapshot. getTeChangedFields() already covers every field this modal lets a teacher edit — projectTitle, shortDetails, inspoLink, the content fields, materials, materialsList, planComplete — not just the 7 content fields, so this closes the gap for all of them uniformly, not only introPitch/processStep1-4/closure/dayOfMaterials.

const changedFormData = {};
changedFields.forEach(f => {
  if (f === 'photo') return; // handled separately via photoUrl/photoPath below
  changedFormData[f] = formData[f];
});
const updatedLesson = { ...originalLesson, ...changedFormData };

Everything downstream is unaffected: fieldsToClear is computed independently and still works identically (a field that was non-empty at open and is now empty is still detected the same way, regardless of what else is in the payload); the audit-trail entries built from changedFields (Phase 5/4C, before/after char counts) are untouched since changedFields itself isn't changing, only what gets sent to Firestore is narrower now.

✅ No guard interaction to worry about here — the non-summer branch of saveSingleLesson has no "block if empty" check at all (see Context note above), so a narrower payload can't trip a guard that doesn't exist on this path.
⚠️ Corrected during second-model review — why this is actually safe: the original draft of this section claimed the local cache is unaffected because "originalLesson's copy of an untouched field and the DOM's copy are identical." That's false during an actual concurrent edit — it's exactly the case this whole plan exists for. The real reason this phase is safe: originalLesson is a function parameter to saveTeacherEdit(lessonKey, originalLesson), and every call site re-reads it fresh from the live-synced currentLessonData at call time (app.js:2837/2843/2862) rather than passing a value frozen at modal-open time — this is Stage 1B's Cmd+S stale-closure fix (already shipped), doing double duty here. So by the time a save actually fires, originalLesson already reflects any concurrent edit the live listener has delivered by then, and {...originalLesson, ...changedFormData} correctly carries that forward for untouched fields. This does still depend on the listener having delivered the update before this save fires — not an absolute guarantee, but a real, already-existing freshness mechanism, not the false "always identical" claim the original draft made.
Given: Teacher A and Admin B both open the same non-summer lesson, both loading processStep1="Old step 1" When: B edits processStep1 to "New step 1" and saves, then A (still on the stale load) edits only projectTitle and saves Then: Firestore's processStep1 remains "New step 1" — A's stale, untouched copy of processStep1 is never sent AND A's projectTitle edit lands correctly Given: A teacher edits the lesson title (projectTitle) only, touching no content field When: They save Then: The save succeeds and only projectTitle is written — no content field's dotted path appears in the update() call at all, touched or not Given: A teacher clears a content field that had real text (an intentional clear, Stage 3 behavior) When: They save Then: FieldValue.delete() is still used for that field exactly as before — fieldsToClear's computation doesn't depend on what's in changedFormData Given: The admin grid moves/swaps/edits a lesson — a different caller of saveSingleLesson that still sends a full lesson object, not a diffed one When: That full object arrives with stale-empty content fields from a stale grid load Then: The existing stripping/read-back protections from the prior plan are completely unaffected — this phase only changes what saveTeacherEdit sends, not saveSingleLesson itself or any other caller

Phase 2 — Summer editor: diff-only payload (redesigned after second-model review) + guard widening

🛑 This phase was fundamentally redesigned after a second-model review found the original draft's diff was a no-op — read this box before the "What it does" section below, which describes the corrected design. The original draft computed contentUpdates correctly (only touched, non-empty fields) but then built the Firestore-bound payload as updatedLesson = {...lesson, ...contentUpdates, ...} and savedLesson = {...lesson, ...updatedLesson} — both re-spread the full lesson closure variable underneath the diff. lesson is captured once when the modal opens (app.js:9486-9491) and is never refreshed while the modal stays open — there is no live listener on summerCamps_lessonData the way curriculum/lessonData has one; loadSummerCampData() is a one-shot fetch. So for any untouched field, rawContentFields[f] === lesson[f] always, the diff correctly excludes it from contentUpdates, and it rides right back in via the ...lesson spread anyway — the actual Firestore write (app.js:9797, await saveSingleLesson(semKey, lessonKey, savedLesson, fieldsToClear)) always sends the full stale snapshot regardless of the diff. Replaying this plan's own original BDD scenario against that code: A's stale processStep2 would still overwrite B's newer edit. The fix below closes that gap by never spreading lesson into the Firestore-bound object at all.

What it does

File: js/app.js, saveLesson() inside the summer lesson modal.

Step 1 — diff, same as originally drafted: compute contentUpdates from only the fields that actually changed since summerLessonOriginalData (the existing open-time/last-save snapshot, already used for Stage 3's clear detection):

const touchedContentFields = Object.keys(rawContentFields).filter(
  f => rawContentFields[f] !== summerLessonOriginalData[f]
);
const contentUpdates = Object.fromEntries(
  Object.entries(rawContentFields).filter(([f, v]) => v !== '' && touchedContentFields.includes(f))
);

Step 2 — the actual fix: split what's written to Firestore from what's kept for local display. Build the Firestore-bound object only from contentUpdates plus metadata and photo fields — never spread the stale lesson object into it. This is safe with no listener or freshness fix needed at all, because saveSingleLesson's summer branch already writes via .set(cleanData, {merge:true}) — omitting a field from the payload already means "leave whatever's on the server exactly as it is," so there's no need for lesson to be fresh in order to correctly leave an untouched field alone.

⚠️ Ordering, corrected after a second review pass: the first draft of this snippet referenced photoUrl/photoPath as if already set, without showing where — today's code assigns updatedLesson.photoUrl/updatedLesson.photoPath directly inside the photo-handling branches, and updatedLesson is exactly what this redesign removes. The corrected snippet below makes the full ordering explicit: declare bare photoUrl/photoPath locals, have the existing photo-handling branches (including the await uploadSummerCampPhoto(...) call) assign those locals instead of a lesson-object property, complete that await first, and only then build firestorePayload — so a photo upload can never be silently dropped by running the payload build before the upload resolves.
// Handle photo upload — photoUrl/photoPath stay bare local variables (not
// attached to any lesson object) so they can be merged into whichever
// payload needs them, built further down, after this upload has resolved.
const photoInput = document.getElementById('summer-photo-input');
const hasNewPhoto = photoInput?.files?.length > 0;
const pendingRemove = photoInput?.dataset?.pendingRemove === 'true';
let photoUrl = null, photoPath = null;

if (hasNewPhoto) {
  if (showStatus) autoSaveStatus.textContent = 'Uploading photo...';
  const result = await uploadSummerCampPhoto(lessonKey, photoInput.files[0]);
  if (lesson.photoPath) {
    await deleteLessonPhoto(lesson.photoPath);
  }
  photoUrl = result.url;
  photoPath = result.path;
  if (showStatus) autoSaveStatus.textContent = 'Saving...';
} else if (pendingRemove && lesson.photoUrl) {
  if (lesson.photoPath) {
    await deleteLessonPhoto(lesson.photoPath);
  }
  photoUrl = '';
  photoPath = '';
}

// Firestore-bound payload — built ONLY from what actually changed this save,
// now that the photo upload (if any) has already resolved above.
const firestorePayload = {
  ...contentUpdates,
  lastEditedBy: getAuthUser()?.name || 'Unknown',
  lastEditedAt: new Date().toISOString(),
};
if (photoUrl !== null) {
  firestorePayload.photoUrl = photoUrl;
  firestorePayload.photoPath = photoPath;
}
await saveSingleLesson(semKey, lessonKey, firestorePayload, fieldsToClear);

// Local display/cache only — never sent to Firestore, so staleness here is
// cosmetic, not a correctness risk (see the note on local/server divergence
// below). Keeps the full merge so the open modal and currentLessonData
// continue showing untouched fields as whatever they were, not blanked.
const savedLesson = { ...lesson, ...contentUpdates, lastEditedBy: firestorePayload.lastEditedBy, lastEditedAt: firestorePayload.lastEditedAt };
if (photoUrl !== null) { savedLesson.photoUrl = photoUrl; savedLesson.photoPath = photoPath; }
fieldsToClear.forEach(f => { savedLesson[f] = ''; });
if (currentLessonData[semKey]) currentLessonData[semKey][lessonKey] = savedLesson;
lesson = savedLesson;

This is the same fix pattern Stage 2D already established for the non-summer path in the prior plan ("never a whole-object assignment to the bare path — explicit per-field, only for what's actually changing") — applied here to summer's merge-based write instead of non-summer's dotted-path write.

⚠️ Local/server divergence, found during the second review pass — cosmetic, not a data-safety risk, but worth stating plainly: because savedLesson still spreads the full stale lesson, after this save the local currentLessonData can show a different value than what's actually in Firestore for any field someone else changed concurrently — e.g. if B changed processStep2 and A never touched it, A's local cache keeps showing A's stale copy even though Firestore now correctly holds B's edit. This cannot leak into a future write (the next save's diff is computed from the live DOM vs. summerLessonOriginalData, never from lesson/savedLesson), and it self-corrects on reload — but there's no guarantee of self-correction otherwise, since summerCamps_lessonData has no live listener to refresh it sooner. Accepted tradeoff, not a defect: the alternative (blanking the untouched field locally) would be worse UX for no safety benefit.
⚠️ Minor Stage 2E interaction, found during the second review pass: a genuinely photo-only or planComplete-only save now has zero content fields in writtenContentFields, so verifySummerLessonWrite (Stage 2E's post-save read-back check) is skipped entirely for that save, same as it already is for a pure planComplete save today. It previously ran anyway on a photo-only save, incidentally re-verifying whatever pre-existing, unrelated content fields happened to be in the old (broken) payload — that was never actually confirming the photo saved correctly either way, so this is a loss of incidental, misleading reassurance, not a loss of real coverage.
⚠️ Guard interaction, corrected framing: the original draft argued the diff-only payload would incorrectly trip the "block if all content empty" guard on a photo-only save, and proposed a guard rewrite to fix it. With the corrected design above, that interaction is real and the guard rewrite is still needed — a photo-only save now genuinely produces a firestorePayload with zero CONTENT_FIELDS keys (previously it accidentally didn't, because the payload was never actually narrowed). The guard rewrite itself is unchanged from the original draft:

// Before:
if (!hasContent && !('planComplete' in lessonData) && clearedContentFields.length === 0) { return; }

// After:
const contentFieldsInPayload = CONTENT_FIELDS.filter(f => f in lessonData);
if (contentFieldsInPayload.length > 0 && !hasContent && clearedContentFields.length === 0) { return; }

This also folds away the now-redundant !('planComplete' in lessonData) special case from Stage 2C — a planComplete-only payload already has zero CONTENT_FIELDS keys, so the general "no content keys touched" condition covers it for free.

🛑 Caller audit, corrected — the first draft's claim here was wrong: the summer branch of saveSingleLesson is reached from more than just saveLesson() and the Plan Complete checkboxes (app.js:1988, 2435, which already send zero CONTENT_FIELDS keys and are unaffected either way). The admin grid's own move/swap paths (app.js:4651, 4703-4717) are correctly unreachable for summer — renderAdminGrid() routes summer semesters to renderSummerCA() instead. But saveAdminEdit() (app.js:4486) is reachable: renderSummerCA()'s own admin popup (buildSummerScheduleGridHtml → openSummerCampPopup, and buildSummerByWeekHtml) calls showAdminEdit(...) on summer lessons too, which saves via saveAdminEdit() → saveSingleLesson(semKey, key, lessons[key]) with semKey = 'summer-2026' — a real, current caller, not a hypothetical one. saveAdminEdit() builds its payload fresh from DOM form fields every time with no diffing at all (no open-time snapshot to compare against, unlike teOriginalData/summerLessonOriginalData) — so an admin editing a lesson through this popup, whether summer or non-summer, can still silently overwrite a teacher's concurrent edit to an untouched field, the exact mechanism this plan exists to close. Neither Phase 1 nor Phase 2 touches saveAdminEdit() — see "Not in scope" below. The BDD scenario about a stale full-empty object below is real, not hypothetical, given this caller exists.
Given: Two teachers/admins both open the same summer lesson, both loading processStep2="Old step 2" When: One edits and saves processStep2, then the other (whose local `lesson` variable is now stale, and stays stale — there is no listener to eventually correct it) edits only introPitch and saves Then: Firestore's processStep2 keeps the first person's edit — the second person's stale, untouched copy is never sent at all, because the Firestore-bound payload never includes lesson's fields to begin with Given: A teacher uploads a new photo without touching any text field, on a lesson that already has real content in Firestore When: They save Then: The save is NOT blocked by the hasContent guard AND no content field's dotted path/merge key is sent at all — read back Firestore afterward and confirm all existing content fields are byte-for-byte unchanged Given: saveAdminEdit() sends saveSingleLesson's summer branch a full lesson object where a content field is genuinely empty (a real, current caller pattern — see the caller audit above, not hypothetical) When: saveSingleLesson runs Then: The save is still blocked exactly as before if ALL content fields are empty with nothing else justifying it — the guard's widened condition only changes behavior when content keys are absent from the payload entirely, not when they're present-but-empty Given: A teacher clears a content field that had real text (Stage 3 intentional clear) When: They save Then: FieldValue.delete() is still used for that field exactly as before — clearedContentFields.length > 0 still bypasses the guard as it always did AND the local savedLesson still reflects the clear correctly (savedLesson intentionally keeps the full merge-for-display pattern, unaffected by the Firestore-payload split above)

Firebase Safety Checklist

  • Rules: No new collections, no rule changes — both phases only narrow what's already being written to summerCamps_lessonData and curriculum/lessonData, both already covered.
  • updateDoc, not setDoc: Unaffected — summer keeps its existing .set(merge:true), non-summer keeps its existing per-field dotted-path update(). Neither phase changes the write mechanism, only which fields make it into the payload.
  • Empty fields stripped: Still true, and more so — saveSingleLesson's existing CONTENT_FIELDS.forEach stripping stays completely unchanged as a second, independent layer of protection under both callers' new narrower payloads.
  • Test coverage — this is the whole point of the plan, so it needs real Firestore coverage, not mocks — but the two phases need different test designs, per a second-model-review finding:
    • Phase 1 (non-summer): a real-Firestore-write-then-save design has a genuine timing race here, because Phase 1's safety depends on the live currentLessonData listener having delivered the concurrent write before the second save fires — if the test's own write and the listener's delivery race, the test could flake red for reasons unrelated to the code under test. Mirror the existing, already-proven pattern instead: e2e/data-safety.spec.js's Test 7 (Stage 1B) simulates "the concurrent state already landed" by directly mutating currentLessonData in the page context via page.evaluate(), deterministically, no timing dependency. Use that same direct-injection technique here.
    • Phase 2 (summer): the corrected design has no listener to race against at all — the Firestore-bound payload never includes lesson's fields regardless of timing — so the originally-proposed design is fine and actually simpler here: write an initial value via the test helpers, open the modal (establishing that as the page's stale baseline), overwrite the same field in Firestore again via the test helpers (simulating a concurrent save), edit a different field via the real UI and save, then read back and confirm the field changed via the test helper still holds its value. No listener-timing dependency to worry about.
  • Emulator/Playwright test before each phase ships: required by this app's own AGENTS.md/CLAUDE.md and this project's own established pattern — write the test first, confirm it fails against pre-fix code for the right reason, implement, confirm green, run the full suite.

Completeness Check — mid-plan interruption

Phase 1 (non-summer) is fully independent and self-contained — it can ship, be tested, and deploy on its own with no guard interaction at all. Phase 2 (summer) depends on nothing from Phase 1 either, but its three parts — the diff, the Firestore-payload/local-cache split, and the guard fix — must ship together in the same commit: the diff alone (without the payload split) is a no-op, per the second-model-review finding that drove this phase's redesign; the payload split without the guard fix would incorrectly block legitimate photo-only saves. If work stops after Phase 1 only, the app is left fully working with the non-summer editor's concurrent-edit gap closed and the summer editor's gap still open exactly as it is today — not worse.

Not in scope

  • Layer 2 — optimistic same-field collision detection. Christie's explicit choice: Layer 1 (this plan) closes the broader, more damaging mechanism (stale untouched fields silently reverting someone else's concurrent edits to those fields). What remains after Layer 1 is the narrower case — two people editing the literal same field at the literal same moment — where whoever saves last still silently wins for that one field. Closing that fully would mean reading each field's current server value before writing and warning the user if it's changed since their form loaded, which needs its own UX design (what does the warning look like, what does the user do next) and adds a Firestore read per save. Deferred, not abandoned — revisit if this narrower case is ever reported as an actual incident, same standard this project has used for every other deferred item.
  • The non-summer branch's missing "block if all-empty" guard (see Context note). Pre-existing, unrelated to concurrent-edit safety, not touched by either phase here.
  • saveAdminEdit() — found by the second-model review, genuinely open, not fixed by this plan. The admin's own edit popup (reachable for both summer and non-summer lessons) has the identical vulnerability this whole plan exists to close — it resends every form field on every save, with no open-time snapshot to diff against at all, unlike the two teacher editors this plan does fix. Closing it needs its own snapshot-and-diff mechanism added to a third modal (showAdminEdit/saveAdminEdit), which is real, separate work, not a small addition to Phase 1 or 2 — deliberately not folded in here without Christie's explicit go-ahead on the added scope. This means the plan's Goal is achieved only for the two teacher-facing editors, not for admin-initiated edits — flagged here plainly rather than left implicit, since it changes what "done" means for Vulnerability #11 as a whole.
