Plan: Classbook Concurrent-Edit Safety — Vulnerability #11 (Layer 1)

Goal: When two people have the same lesson open at once, saving your own edits never silently reverts someone else's concurrent edits to a different field.
App: tinker-spring-curriculum (The Classbook) — js/app.js (saveTeacherEdit, saveLesson), js/firebase-data.js (saveSingleLesson), e2e/data-safety.spec.js
Context: The Classbook Data Safety Plan (CLASSBOOK-DATA-SAFETY-PLAN.md) and its execution plan (classbook-data-safety-remaining-stages.html, plan_jrhp-GpcSGph) are both complete and deployed as of Aug 13, 2026. That plan's "Not in scope" section deferred Vulnerability #11 ("last write wins" on concurrent sessions) as low-risk, on the strength of a plan-reviewer comment resolution that characterized it narrowly as "the same-lesson-same-instant race" and concluded Christie's actual May 2026 incident was a different, already-fixed bug (the stale-load bulk-overwrite case). Both of those specific claims are true. What they missed: there's a third, broader mechanism neither the original vulnerability table nor that resolution named — see Context below. This plan exists because Christie asked directly what happens today if two people edit the same lesson concurrently, and the honest investigation surfaced this gap.
Scope decision: Christie chose Layer 1 only — stop resending untouched fields on every save. Layer 2 (detecting and warning on a true same-field collision) is explicitly deferred; see Not in Scope.
Risk: Medium — touches the core save payload construction for both lesson editors, the exact surface the whole prior plan was built to make safer. Both phases are additive/narrowing (send less, not more) and every existing safety mechanism (stripping, read-back verification, intentional-clear support) is left in place underneath.
execution-ready: false — awaiting review. Christie asked for a second-model-review before any execution starts, matching how every phase of the prior plan was handled.

Context — the mechanism that was missed, and why

Both lesson editors (saveTeacherEdit() for non-summer, saveLesson() for summer camp) build their Firestore write payload from every currently non-empty field in the open form, not just the field(s) the user actually typed into this session. Neither modal re-syncs its open form against live Firestore data while it's open — a live re-sync mid-typing would risk clobbering the user's own in-progress edit, so the form is effectively a point-in-time snapshot for as long as it stays open.

Concrete failure: Teacher A and Admin B both open the same lesson. Both load processStep1: "Old step 1". B edits processStep1 → "New step 1" and saves; Firestore now has "New step 1". A, still viewing their now-stale-loaded form, edits only projectTitle — never touching processStep1 — and saves. A's save payload still includes A's stale copy, processStep1: "Old step 1", because the payload is built from "every non-empty field currently in the form," not "every field this user changed." B's edit is silently reverted, even though A never opened that field.

Why this wasn't caught by the prior plan's reviews: Vulnerability #11 was marked "deferred, not in scope" early — plan_jrhp-GpcSGph's Aug 12 comment thread, resolved same-day — before Phase 1 of that plan had even started. Every later second-model-review in that plan was scoped to verifying the specific phase under execution (Phase 2's merge-vs-update semantics, Phase 3's cache-read bug, etc.). None were asked to re-derive Vuln #11 from the actual code, because it had already been closed as a scoping decision — a review only re-examines what it's pointed at. The resolution's own framing ("same-instant race") also didn't name the actual mechanism above, so there was no prompt to look again. This is a process gap worth remembering for future plans: an "out of scope" decision made before the relevant code exists (or before anyone has traced the actual mechanism) can go unexamined by every subsequent review indefinitely.

⚠️ The blocking guard is asymmetric between the two save paths, found while tracing this — not a new issue, unrelated to this plan's fix, noted for awareness: saveSingleLesson()'s "block if all content fields are empty" guard (firebase-data.js:712) exists only inside the summer branch. The non-summer branch has no equivalent blocking check at all — it always writes whatever's in the cleaned payload, empty or not (protected only by field-level stripping, not a whole-save block). This predates this plan and isn't something Layer 1 introduces or worsens on either path — flagging it here so it isn't mistaken for something this plan should also fix. Worth a look in a future session if it ever seems relevant.

Phase 1 — Non-summer editor: diff-only payload

What it does

File: js/app.js, saveTeacherEdit(lessonKey, originalLesson), around the line building updatedLesson (currently const updatedLesson = { ...originalLesson, ...formData };).

Build the Firestore-bound payload from only the fields getTeChangedFields() already reports as changed, not the full formData snapshot. getTeChangedFields() already covers every field this modal lets a teacher edit — projectTitle, shortDetails, inspoLink, the content fields, materials, materialsList, planComplete — not just the 7 content fields, so this closes the gap for all of them uniformly, not only introPitch/processStep1-4/closure/dayOfMaterials.

const changedFormData = {};
changedFields.forEach(f => {
  if (f === 'photo') return; // handled separately via photoUrl/photoPath below
  changedFormData[f] = formData[f];
});
const updatedLesson = { ...originalLesson, ...changedFormData };

Everything downstream is unaffected: fieldsToClear is computed independently and still works identically (a field that was non-empty at open and is now empty is still detected the same way, regardless of what else is in the payload); the audit-trail entries built from changedFields (Phase 5/4C, before/after char counts) are untouched since changedFields itself isn't changing, only what gets sent to Firestore is narrower now; the local currentLessonData[semKey][lessonKey] = updatedLesson cache is unaffected for untouched fields, since originalLesson's copy of an untouched field and the DOM's copy of that same untouched field are identical (the user never changed it) — same cached value either way, just reached without resending it to Firestore.

✅ No guard interaction to worry about here — the non-summer branch of saveSingleLesson has no "block if empty" check at all (see Context note above), so a narrower payload can't trip a guard that doesn't exist on this path.
Given: Teacher A and Admin B both open the same non-summer lesson, both loading processStep1="Old step 1" When: B edits processStep1 to "New step 1" and saves, then A (still on the stale load) edits only projectTitle and saves Then: Firestore's processStep1 remains "New step 1" — A's stale, untouched copy of processStep1 is never sent AND A's projectTitle edit lands correctly Given: A teacher edits the lesson title (projectTitle) only, touching no content field When: They save Then: The save succeeds and only projectTitle is written — no content field's dotted path appears in the update() call at all, touched or not Given: A teacher clears a content field that had real text (an intentional clear, Stage 3 behavior) When: They save Then: FieldValue.delete() is still used for that field exactly as before — fieldsToClear's computation doesn't depend on what's in changedFormData Given: The admin grid moves/swaps/edits a lesson — a different caller of saveSingleLesson that still sends a full lesson object, not a diffed one When: That full object arrives with stale-empty content fields from a stale grid load Then: The existing stripping/read-back protections from the prior plan are completely unaffected — this phase only changes what saveTeacherEdit sends, not saveSingleLesson itself or any other caller

Phase 2 — Summer editor: diff-only payload + guard widening

What it does

File: js/app.js, saveLesson() inside the summer lesson modal (currently builds contentUpdates from every non-empty rawContentFields entry, filtered only by non-emptiness, not by whether it changed).

Diff rawContentFields against summerLessonOriginalData (the existing open-time/last-save snapshot, already used for Stage 3's clear detection) and only include a field in contentUpdates if it's both non-empty and different from the baseline:

const touchedContentFields = Object.keys(rawContentFields).filter(
  f => rawContentFields[f] !== summerLessonOriginalData[f]
);
const contentUpdates = Object.fromEntries(
  Object.entries(rawContentFields).filter(([f, v]) => v !== '' && touchedContentFields.includes(f))
);
🛑 This phase's payload change directly triggers a real interaction with the existing "block if all content empty" guard — must ship together with the guard fix, not as a separate follow-up: today, a photo-only save (no text field touched) still passes hasContent in practice, because the OLD payload resends whatever's currently non-empty in the form — if the lesson already has real content, hasContent comes back true purely as a side effect, even though the user only uploaded a photo. Once Phase 2 ships the diff-only payload, a photo-only save produces a contentUpdates with zero content-field keys at all. saveSingleLesson()'s guard (firebase-data.js:712, if (!hasContent && !('planComplete' in lessonData) && clearedContentFields.length === 0) return;) would then incorrectly block the save — hasContent is false, there's no planComplete key, and nothing's being cleared, so the photo-only save gets silently refused.

Fix, in the same phase: change the guard from "is there real content anywhere in the payload" to "does the payload attempt to touch any content field at all" — block only when content-field keys are present but empty, not when they're simply absent from an intentionally narrow save:

// Before:
if (!hasContent && !('planComplete' in lessonData) && clearedContentFields.length === 0) { return; }

// After:
const contentFieldsInPayload = CONTENT_FIELDS.filter(f => f in lessonData);
if (contentFieldsInPayload.length > 0 && !hasContent && clearedContentFields.length === 0) { return; }

This also lets the now-redundant !('planComplete' in lessonData) special case (added for Stage 2C) fold away — a planComplete-only payload already has zero CONTENT_FIELDS keys in it, so the general "no content keys touched" condition covers that case for free. Net effect: an admin-grid or bulk caller sending a full, stale, all-empty lesson object is still blocked exactly as before (content keys ARE present, just empty); a narrow, intentional save that never touches content at all — photo-only, planComplete-only, title-only-on-non-summer's future equivalent — is never blocked.

Given: Two teachers/admins both open the same summer lesson, both loading processStep2="Old step 2" When: One edits and saves processStep2, then the other (still on the stale load) edits only introPitch and saves Then: Firestore's processStep2 keeps the first person's edit — the second person's stale, untouched copy is never resent Given: A teacher uploads a new photo without touching any text field, on a lesson that already has real content in Firestore When: They save Then: The save is NOT blocked by the hasContent guard AND no content field's dotted path/merge key is sent at all — read back Firestore afterward and confirm all existing content fields are byte-for-byte unchanged Given: An admin-grid caller sends a full lesson object with all content fields genuinely empty (stale grid load, not this phase's diff logic) When: saveSingleLesson runs Then: The save is still blocked exactly as before — the guard's widened condition only changes behavior when content keys are absent, not when they're present-but-empty Given: A teacher clears a content field that had real text (Stage 3 intentional clear) When: They save Then: FieldValue.delete() is still used for that field exactly as before — clearedContentFields.length > 0 still bypasses the guard as it always did

Firebase Safety Checklist

  • Rules: No new collections, no rule changes — both phases only narrow what's already being written to summerCamps_lessonData and curriculum/lessonData, both already covered.
  • updateDoc, not setDoc: Unaffected — summer keeps its existing .set(merge:true), non-summer keeps its existing per-field dotted-path update(). Neither phase changes the write mechanism, only which fields make it into the payload.
  • Empty fields stripped: Still true, and more so — saveSingleLesson's existing CONTENT_FIELDS.forEach stripping stays completely unchanged as a second, independent layer of protection under both callers' new narrower payloads.
  • Test coverage — this is the whole point of the plan, so it needs real Firestore coverage, not mocks: each phase's first BDD scenario (the two-overlapping-sessions case) is testable without two real simultaneous browser sessions — write an initial value via the existing test helpers (simulating "B's earlier state"), open the modal in one page (simulating "A's session," loading that state as A's baseline), then directly overwrite that same field in Firestore via the test helpers (simulating "B's concurrent save landing after A's load," bypassing A's page entirely so A's in-page state goes stale relative to the server), then have A's page edit a different field and save, then read back and assert the field B "changed" still holds B's value. This exercises the real mechanism without needing two live sessions or real timing coordination.
  • Emulator/Playwright test before each phase ships: required by this app's own AGENTS.md/CLAUDE.md and this project's own established pattern — write the test first, confirm it fails against pre-fix code for the right reason, implement, confirm green, run the full suite.

Completeness Check — mid-plan interruption

Phase 1 (non-summer) is fully independent and self-contained — it can ship, be tested, and deploy on its own with no guard interaction at all. Phase 2 (summer) depends on nothing from Phase 1 either, but its payload change and its guard fix must ship together in the same commit — shipping the payload change without the guard fix would incorrectly block legitimate photo-only (and any future non-content-only) summer saves. If work stops after Phase 1 only, the app is left fully working with the non-summer editor's concurrent-edit gap closed and the summer editor's gap still open exactly as it is today — not worse.

Not in scope

  • Layer 2 — optimistic same-field collision detection. Christie's explicit choice: Layer 1 (this plan) closes the broader, more damaging mechanism (stale untouched fields silently reverting someone else's concurrent edits to those fields). What remains after Layer 1 is the narrower case — two people editing the literal same field at the literal same moment — where whoever saves last still silently wins for that one field. Closing that fully would mean reading each field's current server value before writing and warning the user if it's changed since their form loaded, which needs its own UX design (what does the warning look like, what does the user do next) and adds a Firestore read per save. Deferred, not abandoned — revisit if this narrower case is ever reported as an actual incident, same standard this project has used for every other deferred item.
  • The non-summer branch's missing "block if all-empty" guard (see Context note). Pre-existing, unrelated to concurrent-edit safety, not touched by either phase here.
