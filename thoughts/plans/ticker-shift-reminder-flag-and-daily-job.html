Plan: 48-hour shift reminders — a per-shift flag and a daily job

App: Tinker Ticker (~/tinker-timeclock) + rules in ~/studio-hub/firestore.rules · Drafted: Sep 20 2026 · execution-ready: false · v2 after a two-model design review (Claude + Codex, Sep 20; every finding folded in — see the Decisions log). Awaiting Christie's read and one decision (recipient resolution, below).

Goal: a manager can mark any dated shift "remind", and the person working it gets one email in the morning (Denver) two days before — or one day before, if it was flagged late — without anyone remembering to send it. Nothing is ever inferred from note text: a reminder goes out because a human ticked a box, and every tick is reviewable in one place.
Christie's decisions (Sep 20): Option A — a dedicated "reminder bot" Firebase Auth user read through the security rules from a Netlify Scheduled Function (no service account, no key). The reminder is an explicit per-shift checkbox, not a keyword. Batch entry (AI tool, imports) defaults the flag OFF; time-off sub-coverage shifts default ON. Send from 9:00 AM Denver, two calendar days before the shift. A Reminders view lets her tick/untick any upcoming shift, with "tick all" / "clear all" scoped to the active filter. The old "Extra Shift" keyword code was deleted the same day (b44e281, not yet deployed).
One decision for Christie (v2): both reviewers flagged that the plan's bot would read the roster document (timeclock_settings/employees), which holds every staff member's plaintext kiosk PIN, and would list every users document (push-notification keys, roles, emails). v2 avoids both: each flag writer also stamps remindUid — the auth uid to email, which the manager's browser already knows — and the bot only ever gets that one users document. The cost is one extra stored field. The alternative is to accept the kiosk-level exposure and let the bot read the roster. v2 assumes the least-privilege design; say so if you would rather keep it simpler.

Why this shape

  • Why not a keyword: the one-off-shift-reminders plan tried camp/SDOC/FAN, then "Extra Shift" alone, and Christie's reaction to a term's worth of data was "I do not like the idea of email blasting 73 times." A rule inferred from wording decides for her. A flag she ticks does not.
  • Why the flag lives on the shift, not in a UI: overrides get written by four tools today (editor, AI tool, CSV importers, time-off sub coverage) and a fifth is coming (the future schedule builder). If the reminder is a stored field, every tool is just a way of setting it, at whatever grain fits that tool — and the future builder does not need to exist before the reminder works.
  • Why a Reminders view: bulk paths do not have to get the flag right at entry time. It is also the only way to flag this fall's ~55 SDOCs that are already in the schedule, and it doubles as the preview of what the job will send and the record of what it did.
  • Why Option A over a Cloud Function: a Firebase Cloud Function needs Blaze billing and a new deploy surface, and reads with the admin SDK (bypassing rules). A bot user reads through the rules, which is exactly what the standing credential rule asks for, costs nothing, and matches the kiosk precedent already in firestore.rules (isKiosk(), pinned by uid).
  • Why the reminder follows the resolver: the job resolves each date with getShiftForDate() — the ONE resolver the app and the change email use — so a flagged override the app would never show is never reminded either. This is not theoretical: sub coverage is always written to the base overrides map (app.js ~7353), so a sub on a temporary schedule is exactly this case, and the Reminders view says "hidden" rather than offering a toggle that cannot fire.
  • Why claim-before-send: the only real duplicate exposure is same-day — a manual "Run now", a run cut off at Netlify's 30-second scheduled-function limit and re-run, two overlapping ticks. A log written after the send cannot stop that; a claim written atomically before it can. A crash between claim and send costs at most one late reminder; a crash between send and mark is covered by Resend's idempotency key. Never a blast.
  • Why an hourly tick from 9 AM, not one tick at 9: with claim-based dedupe the extra ticks are free, and they are the recovery mechanism — a tick lost to a deploy or a timeout is picked up by the next one. A one-shot "hour == 9" job that misses its tick sends nothing that day, and by design nothing tomorrow either.

Research (read-only, Sep 20; corrected in v2)

  • Where overrides are written: editor handleAddOverride() (app.js ~3184) builds the object from form fields (start, end, studio, note, _type) — a stored field the form does not know is dropped on edit; editOverride() pre-fills from the stored object; the save goes through buildOverridesWrite(current, original, DELETE) (schedule-helpers.js ~657), which writes each value as-is and special-cases a CLEARED note with a delete sentinel because set(..., {merge:true}) leaves absent keys untouched. The AI tool: handleAiSaveEdits() (app.js ~5240) → applyScheduleEditsTransaction(uid, edits) (firebase-data.js ~248, a transaction whose own comment records why: a plain read-then-leaf-update once recreated a bounds-less futureSchedule after another manager removed it) → applyScheduleEdits() (schedule-helpers.js ~354), which REPLACES each dated leaf with { start, end, studio, note? }. Sub coverage: buildSubScheduleOverride() (schedule-helpers.js ~222), written to base overrides, later reversed by removeTimeOffOverrides() (timeoff-schedule.js ~159) which skips any date that no longer holds what the request wrote — the compare is sameOverride() (~259), shared with the partial-day path.
  • The two importers differ: schedule-import.html (Summer) writes set({ futureSchedule }, { merge: true }) — recursive merge, so unchanged dates keep their fields. The in-app Future Schedule CSV writer (app.js ~5778) writes set({ futureSchedule: { recurring, overrides: {}, validFrom, validUntil } }, { mergeFields: ['futureSchedule'] }) — which REPLACES the whole block, wiping every existing future override (a pre-existing hazard this plan now makes worse, since it would also wipe flags). Phase 3 fixes it.
  • How a date resolves: getShiftForDate(schedule, dateStr, dayKey) — inside an active future window ONLY the future maps are consulted; otherwise a base override applies regardless of base bounds. An override returns the stored object as-is, so extra fields flow through it; recurring days return a spread copy of the weekday and never carry them.
  • Identity: a schedule document's id is an auth uid OR a roster emp_ id (resolveScheduleTarget, ~593); the email for an emp_-keyed document of a claimed person is under the roster entry's claimedBy (resolveReminderRecipient, ~611). The roster (timeclock_settings/employees) holds plaintext kiosk PINs (setStaffPin, app.js ~5806); users documents hold push-subscription keys (push-notifications.js ~93). partitionSchedulesByRosterActive() (~15) is how the app skips archived people.
  • Rules today: timeclock_schedules read/write isManagerOrAbove(), read for hasAppAccess('timeclock') and isKiosk(), each as its own allow; users self-create requires appAccess absent or empty (rules ~106–110); isKiosk() = uid pin OR token.email == 'kiosk@…'. No timeclock_reminder_log exists. rules.test.js in studio-hub has fixed uids per role.
  • Auth guard: requireAuth() (auth-guard.js ~52–90) does NOT refuse an account with no users doc — it tries to CREATE one with appAccess: ['timeclock']; the self-create rule refuses that (appAccess non-empty), the guard catches, builds an in-memory staff identity and shows the app (with no data, since the bot has no access rules). Phase 2 adds an explicit refusal.
  • Netlify functions: CommonJS, _lib/ shared code, Resend via _lib/email.js (SDK 6.26 supports idempotencyKey). Scheduled functions have a 30-second limit and run only on the published deploy; the Netlify UI has a "Run now" button. No @netlify/functions or client firebase package yet (both needed). js/firebase-config.js is a browser global, not a module — the function needs its own copy of the public web config. schedule-helpers.js is dual-loadable, so the job can require it.
  • Existing tests: 666 in Ticker, rules suite in studio-hub. Gaps: no override-write path is tested for a boolean child key; no test exercises the bot's reads under the real rules; no scheduled function has been tested here. buildSubScheduleOverride's output shape is pinned by schedule-helpers.test.js, timeoff-schedule.test.js and the sub-confirm emulator suite — Phase 1 budgets for updating them.

Data model

timeclock_schedules/{docId}.overrides['2026-10-12']        = { start, end, studio, note?, remind: true, remindUid: '<auth uid>' }
timeclock_schedules/{docId}.futureSchedule.overrides['…']  = same shape — the flag lives wherever the override lives

timeclock_reminder_log/{docId}_{date}   (NEW collection; one document per person-date; the dedupe and the audit trail)
  = { uid: docId, date, to, shift: { start, end, studio, note }, claimedAt, sentAt: null | ts, attempts: n, lastAttemptAt?, error? }
  • remind is written as true when ticked and DELETED (sentinel) when unticked — never false. remindUid is written alongside it (the auth uid the email belongs to: the roster entry's claimedBy if the document is emp_-keyed, else the document id; for sub coverage, subUid) and deleted with it. A person with no linked account gets remind: true and no remindUid; the view shows "no linked account — no email will be sent".
  • A day-off override (null) cannot carry the flag; the checkbox is hidden for type "Day Off".
  • The log key is the schedule document id (which can be an emp_ id), so the view and the job agree. Created by the bot as a CLAIM before sending; updated by the bot only to mark the outcome; read by managers; never deleted.

Phase 1 — The flag, as data and pure functions data-write change → emulator test first

Outcome: an override can carry remind/remindUid; ticking and unticking both persist; nothing that writes, rebuilds or reverses overrides drops, misreads, or trips over it.

  • Status, computed by the SAME rule the job uses (reminderWindow): hidden (the resolver would not read this override for its date — no checkbox, tooltip explains) · no linked account (flagged, no remindUid) · archived (roster inactive — flagged but the job skips; "Clear all shown" is the fix) · sends <date> from 9 AM · too late — no reminder (flagged on the day) · claimed, sending… / sent ✓ <when> / failed ✗ <error> from the log · sent — shift changed since when the log's shift snapshot differs from the current one · — (not flagged).
  • Writes are transactions, one per schedule document, modelled on applyScheduleEditsTransaction: read the document → route each toggled date with isInFutureWindow on the document AS READ → require the value at that path to be a non-null map with start and end → tx.update the leaves (remind/remindUid set or FieldValue.delete()), stamping updatedAt/updatedBy. Any date that fails the guard (removed, made a day off, future block gone, moved maps) is SKIPPED and reported ("this shift changed — reload"), never recreated. Bulk = the same transaction with all that document's toggled dates; the result names the stale rows and commits the valid ones. A failed transaction reverts the checkboxes and toasts.

  • New collection → rule in the same phase: timeclock_reminder_log, Phase 2 (rules live in studio-hub; Ticker's docs updated in the same phase).
  • Partial updates: every flag write is a transactional leaf update with a same-shape guard, or a merge write carrying key/sentinel — never a whole-object set(), never an unguarded leaf that could create a phantom shift or a bare futureSchedule. The log is create + bounded update, never delete.
  • Empty fields stripped: remind is true or absent; remindUid is a uid or absent; never false/null/"".
  • Awaited writes: every toggle and every log write; failures surface (toast / function log ERROR).
  • No bulk delete/import: the retro flagging is human toggles through the view. The job never writes to a schedule document. The in-app CSV writer STOPS wiping future overrides (Phase 3).
  • Emulator tests before code: Phase 1's untick-is-a-delete; Phase 4's stale-row guards; Phase 5's core against seeded documents with the real resolver, including concurrency.
  • A denied read is an error, never empty data: Phase 5 adapters return { ok } and abort.
  • Credentials: the bot's password lives only in Netlify env; Claude never reads or types it. No service account, no CLI token, no raw REST. Blast radius if leaked: read every schedule, get the users documents of people being emailed (email, name, role, push keys), create/mark log documents. NOT the roster, NOT PINs. Rotate the password to end it.
  • Spot-check per data-write phase: one real document in the Firebase console after Phases 3, 4 and 5.
