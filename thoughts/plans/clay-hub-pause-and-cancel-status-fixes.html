Clay Hub Membership — pause & cancellation status fixes

Repo: clay-hub-membership · Collection: clayHub_members (rule exists, firestore.rules ~L920) · Sep 25 2026

Goal

A member who has paused more than once is resumed (or not) based on their current pause, and removing a scheduled cancellation puts the member back in Active (or Paused if they are mid-pause) instead of leaving them stuck in Off-Boarding.

Research findings

  • checkExpiredPauses (js/app.js ~L599) reads pauseHistory[0]; completeWorkflow appends with push (~L3062). Every other reader (pause eligibility ~L2433, paused list ~L1242, ~L4652) already uses the last element. The premature-pause correction also removes shift() — the wrong entry for multi-pause members.
  • The auto-resume log text uses currentPause.end, which is undefined for entries written by completeWorkflow (they use endDate) — logs "pause ended undefined". Fixed alongside since it is the same lines.
  • cancelScheduledCancellation (~L2862) nulls scheduledCancellation but leaves stage:'offboarding'. checkExpiredOffboarding then returns early (no final date), so the member is stuck forever. Prior stage is not stored.
  • No test suite exists in this repo (gap). app.js touches document at load, so it cannot be required in Node.

Phase 1 — Pure status helpers + tests execution-ready: false

New js/member-status.js (classic script, loaded before app.js; also module.exports for Node): getLatestPauseIndex, evaluatePausedMember, stageAfterCancellationRemoved. Tests in tests/member-status.test.js run with node --test tests/ (no new dependencies, no root package.json so Render's build is untouched).

Acceptance: tests fail against the old logic's behaviour and pass against the helpers.

Phase 2 — Wire into app.js

  • checkExpiredPauses uses evaluatePausedMember; premature correction removes the entry by index (splice), not shift.
  • cancelScheduledCancellation: if stage is offboarding, set stage to stageAfterCancellationRemoved(member) (paused if today falls inside the latest pause window, else active), and log "Scheduled cancellation removed — moved from Off-Boarding back to Active/Paused". Other stages are left alone.
Acceptance: in the local app (port 8083), a two-pause member whose newest pause ended is auto-resumed; removing a cancellation moves the card out of Off-Boarding.

BDD scenarios

Resume, happy: Given a paused member with pauses [Jan 2025 (ended), Sep 1–20 2026] and today Sep 25 2026, when the page loads, then they move to Active and the log says the pause ended 2026-09-20.

Resume, bug case: Given pauses [Jan 2025 (ended), Sep 1–Oct 31 2026], when the page loads, then they stay Paused (old code wrongly resumed them).

Premature, edge: Given pauses [Jan 2025, Nov 1–30 2026] and stage paused, then they return to Active, the Nov pause becomes scheduledPause, and the Jan 2025 entry stays in history.

Legacy fields / out-of-order array: entries using start/end are handled; the latest is chosen by date, not position; missing/invalid start dates fall back to array order.

Remove cancellation, happy: Given an Off-Boarding member with no current pause, when admin clicks Remove, then stage = active and an action is logged.

Remove cancellation, mid-pause: Given today inside their latest pause window, then stage = paused.

Failure path: Given the Firestore write fails, the existing saveMemberToFirestore logs the error; localStorage still holds the change and the next page-load bulk save re-writes it (existing behaviour, unchanged).

Firebase safety checklist

  • Rules change: none — no new collection. No deploy of any kind.
  • Bulk delete/import: none, so no snapshot needed.
  • Write path: unchanged — uses existing saveMemberChanges → saveMemberToFirestore, which does a full-document .set() of the in-memory member. This is a pre-existing deviation from the "updateDoc for partial edits" invariant; flagged, not changed (along with the bulk .set() on every page load) pending Christie.
  • No fields written as undefined: stage is always 'active' or 'paused'.
  • Emulator test: not applicable — no rules or write-shape change; logic is covered by Node unit tests.

Out of scope — flagged for Christie

  • Future-dated pauses only set scheduledPause; nothing flips stage to 'paused' when the start date arrives.
  • saveAllMembersToFirestore rewrites every member doc with .set() (no merge) on every page load.
  • Date-only strings are parsed as UTC midnight across the app, so in Colorado every pause/cancel date is treated as one day early (resume happens on the end date, "PAUSE TODAY" shows the day before). Consistent, so harmless-ish; fixing it must be app-wide in one change.
  • Members already stuck in Off-Boarding with no scheduledCancellation are not auto-repaired.
  • After removing a cancellation, any saved in-progress cancel checklist (workflows.cancel) remains, so the card still shows a "pending action" highlight.
