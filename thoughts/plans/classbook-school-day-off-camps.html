Context — what exists to build on, and what doesn't

  • Semesters live in curriculum/appData.semesters[key] with name, startDate, numWeeks, breakWeeks, closureDates, published, classRoster, teacherNames (+ semesterType for summer). Teachers see only published !== false (app.js:58-61, :662-668); admins see all. Publish is a per-semester toggle in the selector. This container/publish/gating machinery is exactly what an SDOC school year needs — the proposal is to make an SDOC year a third semester type rather than a parallel system.
  • Summer camp plans are the closest existing shape to an SDOC plan: one plan per (teacher × camp × block × project) in summerCamps_lessonData, with intro pitch, four process steps, closure, materials list, day-of materials, photo, Q&A thread, plan-complete flag — edited in the summer modal, saved through saveSingleLesson()'s summer branch (targeted write, empty-field stripping, explicit clears, forced read-back verification, load guard). SDOC plans should be the same document shape and go through the same save path — every data-safety fix of the last four months then applies for free.
  • What doesn't exist: any notion of a date-based unit (a day, not a week or a camp-week), any way to attach a camp to a date, any teacher assignment that isn't "roster row → teacher" or "camp doc → teacher string", and any collection for it. closureDates on a semester is the opposite concept (studio closed) and shouldn't be reused.
  • Where SDOC dates come from: school-district calendars (Christie enters them). Whether a date has one camp or several (AM/PM, age groups, two studios) is D2 — the Summer Camp App's schedule has timeSlot and studio, which suggests the answer may be "several".

Decisions Christie needs to make (D1–D6)

D1 — Is "a third semester type" the right container? Recommended yes: reuses the selector, publish toggle, teacher gating, and the mental model ("switch to the SDOC year like switching to Summer"). Alternative: a separate top-level tab/section — more UI to build, no reuse, and teachers learn a second navigation. Any reason SDOCs should NOT sit in the semester selector?
D2 — What is one "unit" of an SDOC day? Is a day-off date usually one camp with one or two teachers, or several camps (AM/PM, age bands, Main vs Coal Creek)? This decides whether the session layer is visible or hidden in v1. Also: does a teacher plan one project for the day, or a sequence of projects (like a summer camp's Monday–Friday blocks compressed into a day: e.g. morning project / afternoon project)? Recommended v1: one plan per session, with the plan's four process steps covering the day's arc; multi-project days come later if needed.
D3 — Where do the dates come from, and which calendars? Manual entry by Christie (recommended v1: a date picker + label + optional district tag) vs. importing a district calendar file. Which districts matter (BVSD? SVVSD? Jeffco?) — only for the label/tag, no logic depends on it.
D4 — What do teachers see? (a) Only teachers assigned to at least one date see the SDOC year at all; (b) every teacher sees the year but only their own dates inside; (c) every teacher sees every date read-only (so they can see who's teaching what) and edits their own. Recommended: (b) for v1 — simplest gating that still keeps other teachers' plans out of the way; (c) is a small follow-up if you want visibility.
D5 — Prep and materials integration in v1? Summer plans feed the Materials Hub and prep dashboard. For SDOCs the equivalent is "what does the prep team need ready for Oct 12?" Recommended: out of v1 — the plan's day-of materials field captures it; a "next SDOC" card on the prep dashboard is a natural Phase 4 once the model is real.
D6 — Enrollment / kids? Roster Manager and the Summer Camp App carry enrollment and Kid Notes for summer. Does an SDOC session need capacity/enrollment in the Classbook, or is that tracked elsewhere (Sawyer? Roster Manager)? Recommended v1: an optional capacity number on the session for planning, nothing more — no roster, no kid data in the Classbook.

Completeness check — what if this is interrupted?

  • After Phase 1: Christie has a private, fully usable planning list for the year; nothing is visible to teachers; nothing else in the app changed. This is a perfectly good stopping point for weeks if needed.
  • After Phase 2: teachers can plan; admins read via Phase 1's list but edit only through the teacher path until Phase 3 — acceptable.
  • Rules deployed before UI, or UI before rules: rules must land first (or same deploy) — without them every write is a silent permission error that looks like "data disappeared" (the May 2026 lesson). Phase 1's order is therefore: rules commit + deploy → then the UI deploy.
