Goal: Christie can plan the whole 2026-27 school year of School Day Off Camps in the Classbook — every day-off date, what camp runs that day, and which teacher runs it — and assigned teachers can build their plans for those days the same way they build summer camp plans, with the year invisible to teachers until she publishes it.

Context — what exists to build on, and what doesn't

  • Semesters live in curriculum/appData.semesters[key] with name, startDate, numWeeks, breakWeeks, closureDates, published, classRoster, teacherNames (+ semesterType for summer). Teachers see only published !== false (app.js:58-61, :662-668); admins see all. Publish is a per-semester toggle in the selector. This container/publish/gating machinery is exactly what an SDOC school year needs — the proposal is to make an SDOC year a third semester type rather than a parallel system.
  • Summer camp plans are the closest existing shape to an SDOC plan: one plan per (teacher × camp × block × project) in summerCamps_lessonData, with intro pitch, four process steps, closure, materials list, day-of materials, photo, Q&A thread, plan-complete flag — edited in the summer modal, saved through saveSingleLesson()'s summer branch (targeted write, empty-field stripping, explicit clears, forced read-back verification, load guard). SDOC plans should be the same document shape and go through the same save path — every data-safety fix of the last four months then applies for free.
  • What doesn't exist: any notion of a date-based unit (a day, not a week or a camp-week), any way to attach a camp to a date, any teacher assignment that isn't "roster row → teacher" or "camp doc → teacher string", and any collection for it. closureDates on a semester is the opposite concept (studio closed) and shouldn't be reused.
  • Where SDOC dates come from: school-district calendars (Christie enters them). Whether a date has one camp or several (AM/PM, age groups, two studios) is D2 — the Summer Camp App's schedule has timeSlot and studio, which suggests the answer may be "several".

The model — redrawn Sep 21, 2026 for multi-day, multi-camp SDOCs (D2) and shared plans (D4)

Four things, three of them Firestore documents. The unit Christie plans is an event (one or more consecutive day-off dates); an event hosts several camps (a topic in a time slot at a location, split across studios/age bands, run by one or more teachers, with 1–2 projects + Open Studio per day); each camp-project has one plan shared by all of that camp's teachers. The vocabulary deliberately mirrors the summer side (camp, project, block, plan, headcount) so the summer editor, progress dashboard and Help Queue can be reused with small deltas rather than rebuilt.

Decisions Christie needs to make (D1–D6)

D1 — Is "a third semester type" the right container? Recommended yes: reuses the selector, publish toggle, teacher gating, and the mental model ("switch to the SDOC year like switching to Summer"). Alternative: a separate top-level tab/section — more UI to build, no reuse, and teachers learn a second navigation. Any reason SDOCs should NOT sit in the semester selector?
D2 — What is one "unit" of an SDOC day? Is a day-off date usually one camp with one or two teachers, or several camps (AM/PM, age bands, Main vs Coal Creek)? This decides whether the session layer is visible or hidden in v1. Also: does a teacher plan one project for the day, or a sequence of projects (like a summer camp's Monday–Friday blocks compressed into a day: e.g. morning project / afternoon project)? Recommended v1: one plan per session, with the plan's four process steps covering the day's arc; multi-project days come later if needed.
D3 — Where do the dates come from, and which calendars? Manual entry by Christie (recommended v1: a date picker + label + optional district tag) vs. importing a district calendar file. Which districts matter (BVSD? SVVSD? Jeffco?) — only for the label/tag, no logic depends on it.
D4 — What do teachers see? (a) Only teachers assigned to at least one date see the SDOC year at all; (b) every teacher sees the year but only their own dates inside; (c) every teacher sees every date read-only (so they can see who's teaching what) and edits their own. Recommended: (b) for v1 — simplest gating that still keeps other teachers' plans out of the way; (c) is a small follow-up if you want visibility.
D5 — Prep and materials integration in v1? Summer plans feed the Materials Hub and prep dashboard. For SDOCs the equivalent is "what does the prep team need ready for Oct 12?" Recommended: out of v1 — the plan's day-of materials field captures it; a "next SDOC" card on the prep dashboard is a natural Phase 4 once the model is real.
D6 — Enrollment / kids? Roster Manager and the Summer Camp App carry enrollment and Kid Notes for summer. Does an SDOC session need capacity/enrollment in the Classbook, or is that tracked elsewhere (Sawyer? Roster Manager)? Recommended v1: an optional capacity number on the session for planning, nothing more — no roster, no kid data in the Classbook.

1.3 Data layer (js/firebase-data.js, one section "Day Off Camps", every function behind the same load guard the lesson writers use — lessonDataLoadedSuccessfully === false refuses, :360, :835):

  • loadDayOffCampData({ yearKey, isCurrent }): three equality queries — dayOffCamps_events, dayOffCamps_camps, dayOffCamps_lessonData, each .where('yearKey','==', yearKey) (single-field, no index) — builds the slot map described in the model (empty map for a year with no camps; a permission error throws so the guard trips, exactly like loadSummerCampData()), and installs currentDayOffEvents[yearKey] / currentDayOffCamps[yearKey] (per-year, like the seasons plan's per-semester sessions) only if isCurrent(). Called from loadLessonData() (:326-349) and the listener's reload (:617-642) for every semester with semesterTypeOf(key) === 'day-off-camps', merged with mergeSummerReload() per year (it is shape-agnostic: it keeps the newer saved-doc fields by lastEditedAt).
  • saveDayOffEvent(yearKey, event): validates (label non-empty; dates ISO, unique, sorted, all within the year's startDate..endDate; no date already used by another event of the year — forced-server read of the year's events; district from a short list or blank). Create: collection.doc() for the ID, one set() of the stripped payload + createdAt/createdBy; update: one update() of only the fields that changed (dirty-diff against the open-state snapshot, the summer editor's pattern) + updatedAt/updatedBy. Strip = JSON round-trip, drop undefined and empty strings, keep [], false, 0. Awaited; a create is followed by a forced-server read-back of the new doc (the Stage 2E discipline).
  • saveDayOffCamp(yearKey, camp): validates (title non-empty; eventId exists in the loaded year; timeSlot ∈ AM/PM/FULL; dates ⊆ the event's dates and non-empty; every projects[date] key ∈ dates, titles trimmed and non-empty, ≤ 3 per day; placements non-empty with integer capacity ≥ 0; teachers ⊆ the year's teacherNames, may be empty while planning). Same create/update/strip/read-back rules. Rename/removal guard: when an update drops or renames a title that has a plan with content (countDayOffPlansWithContent(yearKey, campId, [titles]) — forced-server query where('campId','==',campId) filtered in memory with lessonHasContent()), the editor lists the affected plans and offers Keep the old title or Continue (the plan stays in Firestore under the old title; nothing is deleted) — an orphan can be re-attached by renaming back. No automatic re-keying in Phase 1 (a reassign/Cut Bank flow for SDOC is a Phase 3 item, mirroring the Summer Camp App's). In Phase 1 the guard can never fire (no plans exist yet) — it is written and tested now, with a seeded TEST plan doc, so Phase 2 inherits it.
  • deleteDayOffEvent(yearKey, eventId): forced-server count of camps with that eventId — any → refuse ("Remove its {n} camps first"); none → one delete(). deleteDayOffCamp(yearKey, campId): forced-server query of plans by campId — any with content → refuse naming the project(s); otherwise one batch: delete the camp and its content-less plan docs (scaffold-only docs a teacher opened and closed). Both confirm first; both update the in-memory model only after the write resolves (R4-12).
