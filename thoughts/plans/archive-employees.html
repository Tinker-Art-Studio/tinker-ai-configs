Plan: Archive Employees

Status: NOT execution-ready. This plan supersedes and merges two prior separate plans — tinker-ticker-archive-employees.html (plan_6kGOCdKV7jBv) and studio-hub-archive-employees.html (plan__ArypVn99fHf) — into one, per Christie's direct request after finding two coordinated plans more confusing than helpful. Both originals stay on disk with a superseded banner pointing here; nothing from either was discarded. Both plans' second-model reviews (run independently, before the merge) found real, confirmed bugs — every fix from both is folded into the phases below. Both open questions from the merge were resolved, then a second review round (Claude + Codex again, independently) was run specifically against the merged document and found the merge itself introduced real gaps — not polish — including a non-atomic two-document write, an underspecified race fix, and a genuine hole in the single-trigger premise for people who don't originate in Studio Hub. All directly-fixable findings are already corrected below (see "Second-Model Review, Round 2"). Two new open questions from that round still need Christie's decision before this can be marked execution-ready — see "Real scope decisions" under Round 2.
Goal: One click, in one place — Studio Hub's Manage Team — archives a person completely: they immediately lose access to all 21 Tinker apps, and their Tinker Ticker schedule disappears from Who's Working, Schedule Builder, the roster picker, kiosk PIN entry, and self-service clock-in. Nothing is deleted. "Reactivate" restores everything exactly as it was, in every app, with zero reconfiguration.
Repos: ~/studio-hub writes — rules, Manage Team UI, and the single write action (including reaching into Ticker's roster document). ~/tinker-timeclock reads — no write action of its own; just correctly respecting the flag everywhere it currently doesn't.
Why now: Christie has several seasonal summer employees who've left (some may return next summer) and other past employees to clean up. Both apps' only current offboarding action is a permanent delete with no undo — too destructive for routine cleanup, and (in Studio Hub's case) doesn't even fully revoke access, since a deleted users doc silently gets recreated blank on next login.
Risk: Medium. Phase 1 edits firestore.rules, shared by all 21 apps — a mistake in the helper functions breaks access everywhere, mitigated by emulator tests before deploy. Phase 2 adds a cross-repo write (Studio Hub writing into Ticker's roster document) — must resolve the right person by Firebase Auth uid, not fuzzy name matching, to avoid repeating the "ericapodwoiski" duplicate-roster-entry problem found and cleaned up earlier this session.
Reversible: Yes, by design, on both sides — Reactivate restores role/appAccess/studios in Studio Hub and re-shows the schedule in Ticker, with zero data loss either way.

Why one plan instead of two (context for anyone reading this later)

The original split — one plan per repo, coordinated by cross-referencing each other and answering each other's comment threads — was defensible when it looked like two independent features that happened to share a word. It stopped being that the moment both plans converged on a single trigger (see below): once Studio Hub's Manage Team is the only place anyone clicks "Archive," there's no longer a second, independent feature to plan separately — just one feature whose implementation happens to touch two repos, which is normal for any full-stack change and doesn't need two plan documents any more than a typical frontend+backend feature would.

Concretely, the two-plan structure was the direct cause of several problems found along the way: a "cross-app coordination" section that existed purely to reason about non-overlap between two documents, a wording mismatch ("Unarchive" vs "Reactivate") that only existed because two people/sessions independently named the same button, and — the one with real consequences — a race condition that was hard to see specifically because two independently-built features wrote to the same document from two different repos without either one being aware of the other's write pattern. One plan, ordered by dependency, avoids all of that.

The single-trigger design

Two genuinely different pieces of state remain — merging the plan doesn't merge the data:

  • users/{uid}.active Studio Hub — gated into the five Firestore rule helper functions every one of the 21 apps shares. Controls authentication/authorization — can this person read or write anything, anywhere, at all.
  • timeclock_settings/employees.roster[].active Tinker Ticker — an existing field, already checked in a few places, about to be checked in a few more. Controls schedule/kiosk visibility inside Ticker specifically, independent of whether the person can still log in anywhere.

One trigger writes both. Studio Hub's Manage Team "Archive" button (a) sets users/{uid}.active = false, and (b) resolves and flips the matching Ticker roster entry's active field in the same action — extending code that already reaches into that exact roster document today (addToTinkerTickerRoster/syncTimeclockRoster, studio-hub/js/app.js:804-865), rather than inventing a new cross-repo pattern. Tinker Ticker gets no archive/reactivate button or write function of its own — it only needs to correctly display and respect the flag, which several of its views don't do today.

Resolve by uid, not name — required, not optional. addToTinkerTickerRoster today matches people by name (roster.some(e => e.id === id || (e.name||'').toLowerCase() === name.toLowerCase())) — the exact fuzzy mechanism that produced the "ericapodwoiski" duplicate roster entry cleaned up earlier this session. The archive/reactivate write must resolve the target roster entry by claimedBy === uid first (Studio Hub already has the person's real Firebase Auth uid as the users/{uid} doc's own key — a strictly better match than name), falling back to name-matching only for someone who hasn't claimed their Ticker account yet.

Studio Hub findings studio-hub

FindingFix
Admin self-archive had no recovery path. The blanket admin-write rule (firestore.rules:128, allow write: if isAdmin();) sits completely outside the self-update rule's fieldUnchanged('active') pin, because Firestore ORs sibling allow rules together. An admin could write active:false to their own doc through this rule; the instant it commits, isAdmin() requires isActiveUser() and fails for them on every future request — including their own attempt to undo it. No client-side recovery; only another active admin or a manual Console edit fixes it. Identical bug shape to a loophole already found and fixed in this same file for managers (firestore.rules:114-122, regression tests at rules.test.js:448-468). Extend the admin-write rule so an admin can do anything to other users' docs (unchanged) but can never touch their own active field — an admin can only be archived/reactivated by a different admin. Added to Phase 1.
belongsToStudio() needed its own explicit active check. Its non-admin branch (studio in getUserData().studios) doesn't route through isAdmin()/isManager()/etc. at all, so gating those four functions on isActiveUser() would not have touched this one — an archived staff member with a studios array would keep access to every belongsToStudio()-gated collection: Roster Manager, Clay Hub members/waitlist/appData, Clay Inventory. belongsToStudio() gets its own explicit isActiveUser() check rather than inheriting one. Phase 2 shipping before Phase 3 is actually unsafe (both reviewers independently found this). The completeness check claimed "interrupted after Phase 2: safe but incomplete... not dangerous" — false. Phase 2 is the first time active:false ever gets written to a real roster entry. The instant that happens, renderOrphanedSchedules() (app.js:5861, already documented above) treats that person as orphaned and surfaces the permanent-delete button — before Phase 3's fix (which was scoped as a separate, later phase) ever lands. The two archive writes aren't atomic. The plan sequenced "update users/{uid}, then separately transact the roster write." If the second step fails, access is revoked but the Ticker roster still shows them active — silently inconsistent, and it contradicts the plan's own BDD claim that a failed archive leaves the card unchanged with an inline error. Redesigned as one Firestore transaction spanning both documents — users/{uid} and timeclock_settings/employees are both read/written inside a single runTransaction callback. Either both succeed or neither does. See Phase 2.
The transaction retrofit instructions had a real implementation gap. "Wrap syncTimeclockRoster() in runTransaction" is satisfiable by a plausible-but-wrong implementation that still reads the roster doc via a plain .get() outside transaction.get() — which looks transactional but gets none of Firestore's conflict-detection/retry guarantee. Phase 2's work item now says explicitly: the roster-doc read must be transaction.get(rosterRef) inside the callback; the unrelated users collection scan in syncTimeclockRoster() can stay outside it, since it isn't the contested resource.

A plain name match can hit an ambiguous duplicate — exactly the "ericapodwoiski"-style pattern found and cleaned up earlier this session — and silently flip the wrong person's roster entry. Real scope decisions — need Christie's call, not something to decide unilaterally

3. How much of the roster-write race to actually close. Codex found the race is much bigger than the 3 functions this plan named: saveEmployeeRoster() itself, plus every Ticker function that calls it from a locally-cached array — auto-claim, manual claim, seeding, Add Employee, Remove, Merge, Assign, and PIN changes (app.js:5169, 5771, and others) — all read-modify-write the same document from an in-memory snapshot with no fresh re-read. Any one of them can race the same way the two Studio Hub functions can. Fully closing this means transactionalizing every one of those — a substantially bigger undertaking than "Phase 2's small retrofit," closer to a refactor of Ticker's entire roster-write layer. Recommendation: scope this round to the two Studio Hub sync functions plus the new archive transaction (already planned) — those are the automated writers that fire on unrelated actions (granting access, a periodic sync) and are the realistic source of an accidental collision. Ticker's other roster writers are deliberate, single-admin, one-at-a-time actions (adding one employee, setting one PIN) — a genuine collision there requires two admins editing the roster in the same instant, a much narrower window. Treat full transactionalization of every Ticker roster writer as a separate, tracked follow-up, not a blocker for this plan — but this is a real scope tradeoff, not a technical fact, so it needs your explicit sign-off rather than my assumption.
4. People who exist only in Ticker's roster, with no Studio Hub users doc. Confirmed directly: Ticker's own "Add Employee" flow (handleAddEmployee, app.js:5738) creates a roster entry with claimedBy: null and no corresponding users/{uid} document at all. Such a person never appears in Studio Hub's Manage Team and can never be archived by the sole trigger this plan builds — a real hole in the single-trigger premise for anyone added this way rather than through Studio Hub's createTeamMember (which already auto-adds to the Ticker roster today). Two ways to close it, needs a decision: (a) restrict/redirect Ticker's "Add Employee" button so everyone originates in Studio Hub going forward (a policy fix, not a code one, other than maybe a button label change pointing to Studio Hub), or (b) keep a narrow, Ticker-local archive path only for roster entries with no claimedBy and no matching users doc — reintroducing a small piece of exactly the Ticker-side write action this plan just removed, scoped tightly to this one edge case. Recommendation: (a) — it's simpler, and matches how new hires are already handled in practice via createTeamMember.
Noted, not fixed — accepted as a pre-existing, out-of-scope condition: timeclock_settings/{docId}'s Firestore rule (confirmed: allow write: if hasAppAccess('timeclock') && docId == 'employees';) lets any staff member with timeclock access — the default for nearly every account — write anything to the entire roster document, not just their own name-claim. "Ticker never writes active" is therefore a code convention this plan follows, not a rule the database actually enforces. Tightening that rule is a meaningfully separate security-hardening project (risking breaking the legitimate name-claim flow if done carelessly) and is out of scope for this plan — flagged here so it's a known, accepted residual risk rather than a silent gap.
Also noted — test-first ordering. Phase 2 introduces real new data-write logic (the cross-document transaction) before Phase 4 builds the test harness. Per this repo's own convention (failing emulator test first, then implement), Phase 2's work list now includes writing its own targeted emulator tests for the transaction itself, rather than waiting for Phase 4's broader harness.

Original framing, for context: Phase 2 wraps the new archive/reactivate roster write in a Firestore transaction — this protects the archive action itself (it'll safely retry if something else writes to the roster mid-transaction). Fully closing this requires also converting those two pre-existing functions to runTransaction. That's a small, well-scoped change, now confirmed as part of Phase 2 rather than tracked separately.
