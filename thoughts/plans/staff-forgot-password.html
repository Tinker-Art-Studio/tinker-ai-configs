Plan: Staff can reset their own password from the Tinker HQ sign-in screen

App: Tinker HQ (Studio Hub, ~/studio-hub) only · Drafted: Oct 1 2026 · v2 (scoped to Tinker HQ only, per Christie) · execution-ready: false — waiting on second-model design review.

Goal: a staff member who forgot their password taps Forgot password? on the Tinker HQ sign-in screen and gets Firebase's reset email. Christie no longer sends resets one at a time from the console.

What research found

  • All staff apps use one Firebase Auth user list (project tinker-hq-apps). A password reset done from any app changes the password for every staff app. So the link does not need to be on every sign-in screen. It needs to be wherever staff actually sign in.
  • The sign-in code is copied into each app, not shared. js/auth-guard.js exists as a separate copy in 19 app repos (bookkeeping, payroll-tool, roster-manager, schedule-viewer, tinker-kpi, … , tinker-timeclock). Studio Hub does not use one: its sign-in is its own #login-form in studio-hub/index.html plus login() in studio-hub/js/app.js:178. studio-hub/shared/auth-guard.js is the template other apps were copied from. No page loads it, and it is older than Ticker's copy.
  • Because the Auth user list is shared, the reset only needs to be in one place: the Tinker HQ sign-in, which every staff member already uses as the front door.
  • No Firestore data or rules change. sendPasswordResetEmail is Firebase Auth only. No collection is read or written, so firestore.rules is not touched and no rules deploy is needed.
  • Tests: Studio Hub has rules tests only and no front-end tests. That gap is flagged. The new logic is a small pure message function plus a click handler, and it is verified in the browser (see the scenarios below).

Scope

One place only: the Tinker HQ sign-in (studio-hub/index.html #login-form + studio-hub/js/app.js + css/styles.css). Because every staff app shares one Auth user list, the new password works in every app. No change to Tinker Ticker, the kiosk, the other 18 apps or the shared/auth-guard.js template. No signed-in "Change password" option.

After a reset: Firebase signs out that person's existing sessions, so other apps and devices (for example Ticker on their phone) ask them to sign in again with the new password. That is expected.

Design

  • Add a small Forgot password? text button under Sign In. It is type="button", so pressing Enter in the form still signs in.
  • The button uses the email already typed in the Email box, trimmed. If the box is empty or not an email, it shows "Type your email above, then tap Forgot password?". This avoids a second screen and a second email box.
  • The call is firebase.auth().sendPasswordResetEmail(email) with no continue URL. With no continue URL, it does not depend on the Authorized-domains list. The link opens Firebase's own reset page, the person picks a new password, then comes back and signs in.
  • A pure helper, passwordResetMessage(errCode), decides what the screen says:
    ResultShown (normal text, not red)
    success, auth/user-not-found, auth/user-disabled "If that email has an account, a reset link is on its way. Check your inbox (and spam)." This is the same string in every case, so the screen never shows whether an account exists.
    auth/invalid-email, auth/missing-email"Please enter a valid email." This depends only on the format, not on whether an account exists.
    auth/too-many-requests"Too many reset requests. Please wait a few minutes and try again."
    auth/network-request-failed"Couldn't reach the server. Check your connection and try again."
    anything else"Couldn't send a reset email right now. Please try again, or ask a manager." The code is logged to the console. An unexpected error does not depend on whether the account exists, so it reveals nothing.
  • While the request is in flight, the button is disabled and reads "Sending…". After a result it stays disabled for 30 s, so repeated taps don't trip Firebase's rate limit and lock out sign-in attempts from the same browser.
  • The message clears when the person starts signing in, so a stale "link on its way" doesn't sit next to a sign-in error.
  • Studio Hub demo mode (firebaseInitialized === false) shows "Password reset isn't available in demo mode."
Before Phase 1 ships, Christie checks a console setting (one time). In Firebase console → Authentication → Templates → Password reset, check that the project's public-facing name reads like "Tinker HQ" and not "project-12345…". Optionally customize the subject line too. The default sender is noreply@tinker-hq-apps.firebaseapp.com, which may land in spam, so the on-screen message says "(and spam)". Claude does not change console settings.
Staff without a real email. A reset only helps if the Auth account's email is an inbox the person reads. Any staff account created with a placeholder address still needs Christie. Nothing in this plan changes that.

Acceptance (user outcomes):

  • On tinker-hq.netlify.app, a staff member types their email, taps Forgot password?, and gets Firebase's reset email.
  • Typing an address that has no account shows exactly the same message as a real one.
  • Enter in the password box still signs in. It does not send a reset.
  • No Firestore read or write happens. In the network tab, the only call is to identitytoolkit.googleapis.com.
Happy: Given Christie's own email typed in, When she taps Forgot password?, Then she sees the neutral message, and the email arrives (Christie is the one who triggers a real send; Claude does not).
Edge: Given the email box is empty, When they tap Forgot password?, Then they see "Type your email above…" and no request is sent.
Edge: Given nobody-xyz@example.com, When they tap it, Then they see the identical neutral message (Claude verifies this locally; no email is sent to anyone).
Failure: Given Firebase answers auth/too-many-requests (simulated by stubbing the call in the browser console), When they tap it, Then they see the polite wait message and the button re-enables after 30 s.
Failure: Given the browser is offline, When they tap it, Then they see the connection message, not the success message.
