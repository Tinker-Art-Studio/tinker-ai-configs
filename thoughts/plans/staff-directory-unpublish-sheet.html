Plan: The staff sheet stops being public

App: Staff Directory (~/tinker-staff-directory) + Firestore rules (~/studio-hub/firestore.rules, project tinker-hq-apps) · Drafted: Oct 1 2026 · v2 (Q1–Q4 answered) · execution-ready: false (design review round 1 next)

Goal: the Staff Info Google Sheet is no longer "published to web". Nobody can open staff addresses, emergency contacts, medical notes, background-check or I-9 columns without being signed in and allowed. Staff who use the Staff Directory keep seeing it, with a trimmed set of fields. Managers keep seeing everything they see today.
Why: today the app reads a public CSV link. Anyone who has it (any staff member can find it in their browser) can download the whole sheet with no sign-in.
Approach (option 2, Christie's choice): a manager's browser reads the sheet with their own Google sign-in, then saves two copies to Firestore: a full copy only managers can read, and a trimmed copy staff can read. The Staff Directory then loads from Firestore, never from the sheet's public link, and the link is switched off.

What is wrong today

  • js/config.js holds the sheet's published CSV URL. fetchStaffData() downloads it for every signed-in user. "Read-only" staff mode only hides buttons, so the full sheet is in every staff browser.
  • The sheet has 36 columns, including "Passed Background Check?", "Checked on National Sex Offender Website", "Completed i9, W4, Direct Deposit?", "Eligible for rehire", COVID vaccine status, and Notes. The app doesn't even display most of these, but the public CSV contains them all.
  • The link works with no sign-in at all. Anyone it was ever shared with, or anyone who saw it in a browser, has permanent access until it's unpublished.

Design

How the data flows

StepWhat happens
1. Admin/manager opens the Staff DirectoryAs today, they sign in to the app (Firebase). If they're admin/manager (Christie, Anika), the app asks Google (Google Identity Services) for a short-lived token with the drive.file permission. That covers only files this person has handed to the app: no other Sheets, Docs, Drive or Gmail (Q3, Christie).
1b. First time only, per personThe app opens the Google Picker filtered to spreadsheets, and the person picks the Staff Info sheet. That grants the app access to that one file, for that person, from then on. The app checks the picked file's id equals the known Staff Info sheet id, so picking the wrong file is refused with a clear message.
2. Read the sheetThe browser calls the Google Sheets API (spreadsheets.values.get) for the Staff Info tab with that token. Google also enforces the sheet's normal sharing, so the person must be able to open the sheet anyway.
3. Save two copiesSame parsing as today (detectColumns → staff objects). Then save:
  • staffRoster/full: every field the app uses today, managers only;
  • staffRoster/team: the trimmed fields (Q2), readable by staff.
The same sanity gate as the celebrations plan: no rows, a missing required column, or a big unconfirmed drop in staff count → save nothing.
4. Everyone elseStaff open the Staff Directory and it loads staffRoster/team from Firestore. Managers load staffRoster/full (and refresh it from the sheet when they can).
5. Switch off the linkOnce Firestore matches the sheet (verified), remove the CSV URL from the code. Then Christie unpublishes the sheet in Google Sheets (File → Share → Publish to web → Stop publishing).

Why this is the secure option

  • No permanent key anywhere. The Google token lives in the manager's browser, expires within an hour, and is never saved (not in localStorage, Firestore or code).
  • Least privilege: drive.file + Picker means the app can only ever reach the one sheet each person picked. Even a bug or a malicious script on the page couldn't read anything else in their Google account.
  • Not secrets, and stored in config.js: the OAuth client id, the Picker's browser API key (restricted in Google Cloud to the Picker API and the Directory's web addresses), the project number, and the sheet id. None of them grant access on their own.
  • Firestore rules decide who sees what, not the page. A staff account physically can't download the full copy, even from the browser's developer tools.
  • The sheet's own sharing stays the gatekeeper for the source data. Only Google accounts it's shared with can refresh the copy.

Freshness

  • The Firestore copy updates whenever a manager opens the Staff Directory. A new hire who fills in the Google Form appears after the next manager visit, not instantly.
  • The Directory shows "Staff list synced from the sheet N hours ago" for managers. If the Google sign-in is declined or fails, managers still see the last saved copy, with a "Sync now" button.
  • The celebrations summary (plan hq-celebrations-card, phase 2a) is built from the same sync, so there's one sheet read, not two.

New Firestore rules (sketch; finalized in the rules phase)

// staffRoster/full: the whole staff list as the Directory uses it. Admin/manager only.
// staffRoster/team: the staff-safe fields. Any active, signed-in staff account (not the kiosk).
match /staffRoster/{docId} {
  allow get: if docId == 'team' && !isKiosk() && isActiveUser();
  allow get: if docId == 'full' && !isKiosk() && isManagerOrAbove();
  allow create, update: if !isKiosk() && isManagerOrAbove()
    && docId in ['full', 'team'] && /* shape checks per Q2 */ true;
  // no list, no delete
}

Size: about 80 sheet rows × ~1.5 KB is roughly 120 KB, well under Firestore's 1 MiB per document. That's fine for years at this size. The rules phase adds a size check, and the plan notes when to split into per-person docs (past ~500 rows).

The mandatory data-source check (CLAUDE.md)

This plan changes the Directory's data source from the public CSV to Firestore, and then switches the CSV off. Before the switch, a manager verification step compares, for every row, the CSV, the Sheets API read, and the saved staffRoster/full: same row count, and the same value in every column the app uses. The CSV is removed only after that comparison passes and Christie confirms. Nothing in the sheet itself is touched; the sheet remains the source of truth.

Phases

Order: Setup (Christie) → A rules (guard) → B sync, built alongside the CSV → C verify + switch (Netlify) → D unpublish (Christie) → E retire the CSV path. Celebrations 2a is built on B's sync.

Setup — Google Cloud (Christie, about 10 minutes; Claude gives exact clicks)

In the Google Cloud console for project tinker-hq-apps:

  • enable the Google Sheets API and the Google Picker API;
  • OAuth consent screen: Internal (tinkerartstudio.com accounts only, so no Google verification); scope drive.file only;
  • create an OAuth client ID (Web) with authorized JavaScript origins https://tinker-staff-directory.netlify.app and http://localhost:8081;
  • create a browser API key restricted to the Picker API and those two origins;
  • copy the client id, API key and project number into chat. They aren't secrets.

If the Workspace admin settings block third-party app access, the Internal app may need allowing in the Workspace admin console. The steps cover checking that.

A — Rules: staffRoster (studio-hub, via the guard)

  • staffRoster/team: GET by any active non-kiosk user. staffRoster/full: GET by admin/manager (non-kiosk). Create/update: admin/manager only. No list, no delete.
  • Shape checks: team = {staff: list ≤ 300, updatedAt, updatedBy}, and full the same with its own list. List items can't be inspected by rules, so the builders' tests pin each row's exact key set. team rows have an allow-list without address, medical or emergency keys, enforced by test.
  • Tests in the same style as staffCelebrations, incl. a kiosk with a manager doc, the override staff, archived, bot, signed-out, and a size near the cap.

B — Sync (managers), alongside the CSV

  • js/google-sheet.js: load GIS + Picker; get a drive.file token for admin/manager only; Picker on first use (check the picked id equals the Staff Info id); values.get on the Staff Info tab; return rows in the same shape the CSV parser produces, so detectColumns and the staff-object builder are reused unchanged.
  • js/roster-sync.js (pure, tested): buildRosterDocs(rows, columnMap) → {full, team}, plus the sanity gate (zero rows / missing required column / >40% swing needs a confirm; first run exempt from the swing check), and "write only when changed".
  • Save with explicit refs staffRoster/full + staffRoster/team; awaited; one notice on failure; never appData.
  • Display still comes from the CSV in this phase, so B can ship and be compared side by side without any staff-visible change.
  • The token is held in memory only. If the Google sign-in is declined or fails, the Directory works exactly as before; managers see "Couldn't sync from the sheet" with a Sync button.
  • Tests (node --test):
    • exact key sets for full and team rows; team never contains address, medical, emergency, T-shirt, or past staff;
    • never-copied columns (background check etc.) never appear in either;
    • the "preferred" mapping no longer binds the coffee question;
    • the sanity gate cases;
    • Sheets API row shape → the same staff objects as the CSV for a fixture.

C — Verify, then switch the Directory to Firestore

  • A manager-only "Compare sources" panel: CSV vs the Sheets API read vs the saved staffRoster/full, row count and every displayed column per row, with differences listed. It must show zero differences, and Christie confirms (the CLAUDE.md data-source rule).
  • Then: staff load staffRoster/team; managers load staffRoster/full and sync from the sheet in the background. The CSV is no longer fetched by anyone.
  • Staff Directory deploy (Christie's OK; archive-only deploy, as in the celebrations plan).

D — Unpublish (Christie, in Google Sheets)

File → Share → Publish to web → Stop publishing. Then check:

  • the old CSV URL no longer returns data;
  • a staff account sees the Directory with the trimmed fields;
  • Christie and Anika can each sync.

E — Retire the CSV path

Remove the CSV URL, parseCSV fetch path and the "Setup Required / publish your sheet" notice from the code. Update the help text.

A — Rules: staffRoster

The block above, plus shape checks for both docs (field allow-lists from Q2, sizes). Tests: staff can get team only; managers get both; kiosk, bot, archived and signed-out are refused; no list, no delete; staff can't write; an extra or forbidden field in team (e.g. address) is refused. Deploy through the guard with your sha phrase.

B — Google sign-in + sync (managers)

Load Google Identity Services; request spreadsheets.readonly for admin/manager only; read the tab via the Sheets API; reuse detectColumns and the parser; build full and team with tested builders; the sanity gate; save. Nothing changes for staff yet, and the CSV is still the display source in this phase, so it can be verified side by side.

C — Verify, then switch the Directory to Firestore

The comparison tool (CSV vs Sheets API vs full, every row and column). After it passes and Christie confirms, staff load team and managers load full. The CSV URL is removed from config.js. Staff Directory deploy (your OK).

D — Unpublish the sheet (Christie, in Google Sheets)

Stop publishing. Then check that the old CSV URL returns an error, and that the Directory still works for a staff account and a manager account.
