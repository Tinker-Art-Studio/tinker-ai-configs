Plan: The staff sheet stops being public

App: Staff Directory (~/tinker-staff-directory) + Firestore rules (~/studio-hub/firestore.rules, project tinker-hq-apps) · Drafted: Oct 1 2026 · v10 after design review rounds 1–7 (Codex + Claude) · execution-ready: false (Christie: stop design rounds here? see Decisions log)

Goal: the Staff Info Google Sheet is no longer "published to web". Nobody can open staff addresses, emergency contacts, medical notes, background-check or I-9 columns without being signed in and allowed. Staff who use the Staff Directory keep seeing it, with a trimmed set of fields. Managers keep seeing everything they see today.
Why: today the app reads a public CSV link. Anyone who has it (any staff member can find it in their browser) can download the whole sheet with no sign-in.
Approach (option 2, Christie's choice): a manager's browser reads the sheet with their own Google sign-in, then saves two copies to Firestore: a full copy only managers can read, and a trimmed copy staff can read. The Staff Directory then loads from Firestore, never from the sheet's public link, and the link is switched off.

What is wrong today

  • Offboarding notes are open to checkbox staff. staffDirectory/appData (exit-interview notes, checklist state, past staff's names and emails) is readable and overwritable by any staff member with the Staff Directory checkbox, and every Directory session downloads it and copies it into the browser's storage (R2 both, blocking).
  • Any signed-in account sees everything in the Directory today, including home addresses, emergency contacts and medical notes in each profile ("read-only" mode only hides buttons). And anyone can create a Tinker account: the sign-in key is public, and new accounts get a staff record automatically (R1 Claude-B1).
  • Sheet text goes into the page as HTML (names, pronouns, favorites…). A form answer containing HTML/script would run in a manager's browser. That matters much more once a Google token and the full roster are on the page (R1 Codex-B3).
  • js/config.js holds the sheet's published CSV URL. fetchStaffData() downloads it for every signed-in user. "Read-only" staff mode only hides buttons, so the full sheet is in every staff browser.
  • The sheet has 36 columns, including "Passed Background Check?", "Checked on National Sex Offender Website", "Completed i9, W4, Direct Deposit?", "Eligible for rehire", COVID vaccine status, and Notes. The app doesn't even display most of these, but the public CSV contains them all.
  • The link works with no sign-in at all. Anyone it was ever shared with, or anyone who saw it in a browser, has permanent access until it's unpublished.

Design

How the data flows

StepWhat happens
1. Admin/manager opens the Staff DirectoryAs today, they sign in to the app (Firebase). If they're admin/manager (Christie, Anika), the app asks Google (Google Identity Services) for a short-lived token with the drive.file permission. That covers only files this person has handed to the app: no other Sheets, Docs, Drive or Gmail (Q3, Christie).
1b. First time only, per personThe app opens the Google Picker filtered to spreadsheets, and the person picks the Staff Info sheet. That grants the app access to that one file, for that person, from then on. The app checks the picked file's id equals the known Staff Info sheet id, so picking the wrong file is refused with a clear message.
2. Read the sheetThe browser calls the Google Sheets API (spreadsheets.values.get) for the Staff Info tab with that token. Google also enforces the sheet's normal sharing, so the person must be able to open the sheet anyway.
3. Save two copiesSame parsing as today (detectColumns → staff objects). Then save:
  • staffRosterRevisions/{rev}/full/{id}: every field the app uses today, one doc per sheet row, managers only;
  • staffRosterRevisions/{rev}/team/{id}: the trimmed fields (Q2), one doc per current staff member, readable by managers and by staff with the Staff Directory checkbox.
See "Storage and rules" below: one document per person, so the database rules can check every field (R1 Codex-B1). See "Sync safety" for when nothing is saved.
4. Everyone elseStaff open the Staff Directory and it loads the current revision's team docs (via staffRosterMeta/current). Managers load its full docs, and refresh it with a Sync from sheet button (R1 both: Google can't hand out a token silently on page load).
5. Switch off the linkOnce Firestore matches the sheet (verified), remove the CSV URL from the code. Then Christie unpublishes the sheet in Google Sheets (File → Share → Publish to web → Stop publishing).

Why this is the secure option

  • No permanent key anywhere. The Google token lives in the manager's browser, expires within an hour, and is never saved (not in localStorage, Firestore or code).
  • Least privilege: drive.file + Picker means the app can only ever reach the one sheet each person picked. Honest caveat: drive.file isn't read-only. It technically allows editing the picked file, though the app only ever calls the read endpoint (R1 Codex-B4). It's also Google's non-sensitive tier, so no Google review. Even a bug or a malicious script on the page couldn't read anything else in their Google account.
  • Not secrets, and stored in config.js: the OAuth client id, the Picker's browser API key (restricted in Google Cloud to the Picker API and the Directory's web addresses), the project number, and the sheet id. None of them grant access on their own.
  • Firestore rules decide who sees what, down to the field. Each person's staff-copy doc may contain only the allowed fields: the rules check every doc's exact key list, so even a buggy or tampered sync can't put an address or medical note where staff can read it. (Picking a wrong file in the Picker does add that file to the app's access before the id check refuses it, so the honest claim is "only files you pick", not "only ever this one" (R2 Codex-M1).) (v2's single-list design couldn't do this, because rules can't look inside list items. Changed after R1 Codex-B1, Claude-M12.)
  • The sheet's own sharing stays the gatekeeper for the source data. Only Google accounts it's shared with can refresh the copy.

Freshness

  • The copy updates when Christie or Anika clicks Sync from sheet. A click is needed because Google only issues the short-lived token in response to one. After the first time it's usually one click with no extra prompts (R1 Claude-B4, Codex-M1).
  • Everyone sees "Staff list updated N days ago". Managers see it amber after 7 days, with the Sync button right there.
  • The celebrations summary (plan hq-celebrations-card, phase 2a) is built in the same sync, so there's one sheet read.

Storage and rules (v5: staged revisions)

A sync never edits the live copy in place. It writes a complete new revision alongside the old one, checks it, then flips one pointer. Readers always see one whole, finished revision: never half old and half new (R2 both, blocking).

staffRosterRevisions/{rev}                  // header: {status: 'staging'|'complete', counts {full, team}, createdBy, createdAt (server time), previous}
staffRosterRevisions/{rev}/full/{id}        // one doc per sheet row, every field the Directory uses          — admin/manager only
staffRosterRevisions/{rev}/team/{id}        // one doc per CURRENT staff member, staff-safe fields only       — + staff with the checkbox
staffRosterMeta/current                     // pointer: {revision, previous, updatedAt (server time), updatedBy} — readers start here
  • Sync: create the header as staging → write all full and team docs in chunks of 5 → read them back and check the counts and key sets → mark the header complete → in one transaction, flip staffRosterMeta/current to the new revision. Any failure before the flip leaves the live copy exactly as it was.
  • Two managers at once: the flip is compare-and-swap. The rule requires the new pointer's previous to equal the current revision, and the new revision's header to exist and be complete. A second sync that started from the old pointer is refused and told to re-run.
  • Readers: read the pointer, then that revision's team (staff) or full (managers). Rules let checkbox staff read only team under the revision the pointer names (and its header). Staging revisions are invisible to staff.
  • Rollback: the previous revision stays, so a manager can point back to it.
  • Retention: revisions are kept; nothing is deleted (R3 Claude-M8, Codex-M5). A new revision is only created when the sheet actually changed, so it's a handful a year (~100 small docs each).
  • The rules enforce the staging lifecycle (R3 Claude-M2, Codex-B2). The literal rules below are authoritative where wording differs:
    • a header is created only as staging, by the caller as createdBy, under a new random revision id (create fails if the id exists);
    • counts are set when the header is created (the builder knows every doc before the first write); only its creator moves it once to complete, with counts, createdBy, createdAt and previous unchanged; after that it's immutable. A revision a sync abandons stays as an inert staging revision (cleanup from the Console only) (R6 Claude-L5);
    • row docs may only be created, only by the header's creator, and only while the header is staging. No row updates, ever. So nothing can touch the live revision.
  • First publish (R3 Claude-M1, Codex-B3): staffRosterMeta/current has a separate create rule (no existing doc, no previous, target header complete). Every later flip is an update with compare-and-swap. Manager reads of a revision's full never depend on the pointer, so read-back works before the first publish.
  • Reader race (R3 Claude-M9): if a manager publishes between a staff member's pointer read and their list query, the query is refused. The Directory re-reads the pointer and retries once; a failed read shows "Couldn't load the staff list, reload", never "hasn't been synced yet".
  • Rules check every doc's exact shape (hasOnly + hasAll), with separate schemas for: a current team row, a current full row, the header, and the pointer. Past staff are simply absent from team; team rows carry no status field at all, so there are no tombstones to get wrong (R5 Claude-M2). Optional strings may be '' or match their pattern/cap (e.g. birthday '' || M/D), so a blank birthday doesn't make a sync fail (R2 Claude-B2, Codex-M3).
  • Full rows have an exact allow-list too: background check, I-9, rehire, notes and the other never-copied columns have no key in either schema, so the rules refuse them in full as well as team. Tested per field (R2 Codex-M3).
  • Per-field UTF-8 caps in the builder, with headroom under the rules' caps; an aggregate per-doc size check before writing (R2 Codex-M3).
  • Doc ids: a hash of the normalized email (or of the normalized name when there's no email), so they're path-safe for names with "/" or accents (R2 Codex-L1).
  • Duplicate rows (R3 Claude-B2). The sheet is a Form response tab, and today 3 emails appear twice (counted Oct 2: 81 rows, 0 without an email, 0 blank). For duplicate emails, the later row in the sheet wins (Form responses are appended in order, so row order has no locale or time-of-day ambiguity) (R5 Claude-M1, Codex-M1). A newer P row correctly makes someone past. If a duplicate group's timestamps don't appear to increase with row order, the preview shows a warning (advisory only, since formatted timestamps are locale-dependent and row order already decides) (R7 Claude-M3). If a person's rows disagree on status, or the same email carries clearly different names, the sync needs an explicit confirm, and the preview prints the winning row per person. Two email-less rows with the same name stop the sync: they could be two different people (R4 Codex-M2). Every dropped row is listed in the preview and as an intended difference in Compare. The same id function is applied to the CSV rows, so Compare lines up by person.
  • Timestamps are server time (request.time); createdBy/updatedBy must equal the caller.
  • Each row's id must equal its doc id, and its revision must equal the {rev} in its path (R4 Codex-M5).
  • The pointer flip also requires the target header's counts to be non-zero (team > 0, full ≥ team) and revision != previous (R4 Claude-L3).
  • Reads are one-shot gets, never live listeners on revision data. The only listener is on staffRosterMeta/current; a pointer change triggers a fresh read (R4 Claude-M5).

Literal rules for phase A (R5 Claude-M6), reviewed against the test list before asking for the sha

// ── STAFF ROSTER (revisions) ── plan: staff-directory-unpublish-sheet.html
match /staffRosterRevisions/{rev} {
  function hdr() { return get(/databases/$(database)/documents/staffRosterRevisions/$(rev)).data; }
  function ownStaging() { let h = hdr(); return h.status == 'staging' && h.createdBy == request.auth.uid; }   // one header lookup
  function isHeader(d) {
    return d.keys().hasOnly(['status','counts','createdBy','createdAt','previous'])
      && d.keys().hasAll(['status','counts','createdBy','createdAt','previous'])
      && d.status in ['staging','complete'] && d.previous is string     // '' on the first revision (R5 Claude-B3)
      && d.counts is map && d.counts.keys().hasOnly(['full','team']) && d.counts.full is int && d.counts.team is int;
  }
  allow get, list: if !isKiosk() && isManagerOrAbove();
  allow get: if !isKiosk() && hasAppAccess('staff-directory') && rev == currentRev();
  allow create: if !isKiosk() && isManagerOrAbove() && isHeader(request.resource.data)
    && request.resource.data.status == 'staging' && request.resource.data.createdBy == request.auth.uid
    && request.resource.data.createdAt == request.time
    && request.resource.data.counts.team > 0 && request.resource.data.counts.full >= request.resource.data.counts.team;  // counts set at create (R6 Claude-M3)
  allow update: if !isKiosk() && isManagerOrAbove() && isHeader(request.resource.data)
    && resource.data.status == 'staging' && request.resource.data.status == 'complete'
    && resource.data.createdBy == request.auth.uid
    && fieldUnchanged('createdBy') && fieldUnchanged('createdAt') && fieldUnchanged('previous') && fieldUnchanged('counts');

  match /full/{id} {
    allow get, list: if !isKiosk() && isManagerOrAbove();
    allow create: if !isKiosk() && isManagerOrAbove() && ownStaging()
      && isFullRow(request.resource.data) && request.resource.data.id == id && request.resource.data.revision == rev;
  }
  match /team/{id} {
    allow get, list: if !isKiosk() && (isManagerOrAbove() || (hasAppAccess('staff-directory') && rev == currentRev()));
    allow create: if !isKiosk() && isManagerOrAbove() && ownStaging()
      && isTeamRow(request.resource.data) && request.resource.data.id == id && request.resource.data.revision == rev;
  }
  // no update of rows, no delete anywhere
}
match /staffRosterMeta/{docId} {
  function isPointer(d) {
    return d.keys().hasOnly(['revision','previous','updatedAt','updatedBy']) && d.keys().hasAll(['revision','previous','updatedAt','updatedBy'])
      && d.revision is string && d.previous is string && d.revision != d.previous
      && d.updatedAt == request.time && d.updatedBy == request.auth.uid;
  }
  function target(d) { return get(/databases/$(database)/documents/staffRosterRevisions/$(d.revision)).data; }
  function targetOk(d) { let h = target(d); return h.status == 'complete' && h.counts.team > 0 && h.counts.full >= h.counts.team; }
  allow get: if !isKiosk() && (isManagerOrAbove() || hasAppAccess('staff-directory'));
  allow create: if docId == 'current' && !isKiosk() && isManagerOrAbove() && isPointer(request.resource.data)
    && request.resource.data.previous == '' && targetOk(request.resource.data) && target(request.resource.data).previous == '';
  allow update: if docId == 'current' && !isKiosk() && isManagerOrAbove() && isPointer(request.resource.data)
    && request.resource.data.previous == resource.data.revision && targetOk(request.resource.data)
    && (target(request.resource.data).previous == resource.data.revision          // forward: built on the live revision
        || request.resource.data.revision == resource.data.previous);              // rollback: only to the immediate previous
  // A sync staged on an older revision is refused even if retried (R6 Codex-M1).
}
// ── Top-level helpers (next to the existing ones) ──
function currentRev() {
  return get(/databases/$(database)/documents/staffRosterMeta/current).data.revision;
}
function capStr(d, k, n) { return d[k] is string && d[k].size() <= n; }
function isRosterId(v)   { return v is string && v.matches('^[a-f0-9]{32}$'); }        // hex hash of the normalized email/name
function isRevId(v)      { return v is string && v.matches('^[A-Za-z0-9]{20}$'); }      // Firestore auto-id
function isTeamFields(d) {
  return isRosterId(d.id) && isRevId(d.revision)
    && capStr(d,'name',120) && d.name.size() > 0
    && capStr(d,'pronouns',40)
    && d.studioId in ['tinker','clayhub','both']
    && capStr(d,'email',120) && (d.email == '' || d.email.matches('^[^@ ]+@[^@ ]+$'))   // no backslash escapes (none in this file; R7 both)
    && capStr(d,'phone',40)
    && d.birthday is string && (d.birthday == '' || d.birthday.matches('^[0-9]{1,2}/[0-9]{1,2}$'))
    && d.birthdayMonthOnly is bool
    && capStr(d,'startDate',40)
    && capStr(d,'favoriteCoffee',200) && capStr(d,'favoriteCandy',200)
    && capStr(d,'favoriteSnack',200) && capStr(d,'favoriteSalty',200)
    && capStr(d,'dietary',300);
}
function teamKeys() {
  return ['id','revision','name','pronouns','studioId','email','phone','birthday','birthdayMonthOnly',
          'startDate','favoriteCoffee','favoriteCandy','favoriteSnack','favoriteSalty','dietary'];
}
function isTeamRow(d) { return d.keys().hasOnly(teamKeys()) && d.keys().hasAll(teamKeys()) && isTeamFields(d); }
function fullKeys() {
  return teamKeys().concat(['status','birthdayRaw','address','emergencyContact1Name','emergencyContact1Phone',
                            'emergencyContact2Name','emergencyContact2Phone','medical']);
}
function isFullRow(d) {
  return d.keys().hasOnly(fullKeys()) && d.keys().hasAll(fullKeys()) && isTeamFields(d)
    && d.status in ['current','past'] && capStr(d,'birthdayRaw',40) && capStr(d,'address',300)
    && capStr(d,'emergencyContact1Name',120) && capStr(d,'emergencyContact1Phone',40)
    && capStr(d,'emergencyContact2Name',120) && capStr(d,'emergencyContact2Phone',40)
    && capStr(d,'medical',500);
}
// Every key is always present ('' when blank), so hasAll + hasOnly pins the exact set. The builder mirrors these caps
// with UTF-8 headroom and the same patterns; a shared test fixture runs builder output through a JS copy of these checks.
// Lookups per row create: users (≤2) + header (1, bound once) = ≤3. A batch is at most 5 documents total,
// counting full and team together (≤15 of 20). (R6 Claude-M4, Codex-B2)
// Legacy collection, tightened in the same rules deploy (R2 both, blocking):
match /staffDirectory/{docId} {
  allow read, create, update: if !isKiosk() && isManagerOrAbove();   // was: || hasAppAccess('staff-directory')
  allow delete: if !isKiosk() && isManagerOrAbove();                 // kiosk excluded on delete too (R6 both)
}

Sync safety (R1 Codex-B2, Claude-B2, M1–M4, M11)

  • Exact header contract, not fuzzy matching: the sync uses a pinned list of the sheet's exact column headers for every column it reads (copied fields plus Timestamp and status) (R4 Claude-M1). A missing, renamed, duplicated or ambiguous header stops the sync and names the column. No "save anyway" for structural problems. This also fixes the "preferred name" bug and the risk of "phone" matching "Emergency Contact 1 - Phone". Fixture test: the real 36 headers → the full expected map; no two fields share a column.
  • Every built doc is validated before the first write against one shared schema object (the JS mirror of the rules). A violation names the person, field and cell text in the preview and stops the sync: e.g. an email cell like "a@b.com (personal)" or "n/a", or a row with a blank Name but other answers. Over-cap free text (medical, address, dietary, favorites) is never silently truncated; it's listed for an explicit confirm, then capped (R7 Claude-B2).
  • Status must be C or P (or a known variant). Blank or unknown stops the sync for that row and lists it, so it can never default to "current" and leak into the staff copy.
  • Sheets API call pinned: the tab found by gid 119449978 (currently "Form Responses 1"; the title is quoted in the range, with any apostrophe doubled, and unit-tested) (R6 Claude-L3), majorDimension=ROWS, valueRenderOption=FORMATTED_VALUE (R5 Claude-L1). Rows are padded to header width (the API trims trailing empties) and cells trimmed, like the CSV parser.
  • Every sync shows a "what changed" preview before publishing, and any removal, current→past change, id change, or loss of a previously filled field needs an explicit confirm (R2 Codex-M2). Hard stops with no confirm, all measured on the team (current staff) set versus the live revision: zero rows; current staff down by more than 10% or more than 3 people; more than 3 people flipping current→past in one sync; readable birthdays or start dates down by more than 10% or more than 3. Also on the full set: past rows down by more than 10% or 3, or any previously filled field (address, medical, emergency contacts, phone, email…) emptied for more than 10% or 3 people. Affected names are printed (R6 Claude-M6, R7 Codex-M1).
    • The first sync has no live revision to compare against, so it keeps only the absolute gates (zero rows, header contract, status), and Compare sources is the gate (R4 Claude-L1).
  • Every row carries every allow-listed key as a string ('' when blank), so the Directory's existing code (e.g. staff.email.toLowerCase()) never crashes on a missing field.
  • Writes go in chunks of 5 (same 20-lookups-per-batch limit as the celebrations plan) into the staging revision. Publishing is the single pointer flip described above.
  • The manual CSV-file escape hatch feeds the same pipeline: header contract, validator, preview, staging, flip. There's no second, looser import path (R2 Codex-M2).
  • The full roster is never written to localStorage (a shared manager browser keeps no medical data at rest) (R1 Claude-L7).

The mandatory data-source check (CLAUDE.md)

This plan changes the Directory's data source from the public CSV to Firestore, and then switches the CSV off. Before the switch, a manager verification step compares, for every row, the CSV, the Sheets API read, and the saved Firestore copies: same people (by stable id), and the same canonical value for every key in FULL_KEYS/TEAM_KEYS, not just what's on screen (e.g. favoriteSalty is only used by Generate Order) (R3 Codex-M4). Exact key sets and counts are asserted too. Values are normalized the way the Directory displays them (e.g. the birthday as "October 4"), with a short printed list of intended differences (birth year dropped, never-copied columns absent, past staff absent from the staff copy). It also checks that the staff copy holds current staff only and no forbidden field (R1 Claude-M1, Codex-B2). The CSV is removed only after that comparison passes and Christie confirms. Nothing in the sheet itself is touched; the sheet remains the source of truth.
