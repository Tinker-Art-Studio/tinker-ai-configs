What is actually broken

All of the following share one root cause: saveSchedule() (js/firebase-data.js:205) writes with set(..., {merge:true}), and Firestore recursively merges nested map fields. A key that is absent from the written map is left untouched remotely rather than removed. The editor rebuilds the whole map every save and assumes absence means deletion. It does not.

Every symptom above is silent. The editor shows the change, Save reports success, and the data is unchanged. There is no error and no warning. That is what makes this worth doing carefully: the failure mode is someone turning up for a shift that was supposed to be gone.

Measured, not assumed

Emulator probe (recurring-note-merge.emulator.test.js, untracked) against a real doc:

days present after clearing Sat:            Mon, Sat
override dates after removing 2026-11-11:  2026-11-11, 2026-11-23

Corroborating evidence already in the repo: js/app.js:7340-7346 contains a prose comment describing this exact trap, and removeTimeOffOverrides() works around it with FieldValue.delete(). The time-off flow was fixed; the main editor never was.

Firestore nuance that makes this worse, not better: an explicitly written empty map does overwrite the target. So removing the last weekday or the last override appears to work, while removing one of several silently fails. Anyone spot-checking the fix could easily test the working case and conclude it is fine.

The reviewer disagreement — and why it matters

Both reviewers confirmed the diagnosis and both independently caught bug #3 in the attempted fix. They split on the remedy:

RecommendedRationale
CodexReplace recurring/overrides wholesale (update() or mergeFields)The editor already builds the complete map, so there is nothing to preserve by merging. One change fixes all cases.
ClaudePer-key FieldValue.delete()Wholesale replacement would cause real data loss via a second code path.
Claude is right, and this was verified directly rather than taken on trust. aiEditInBuilder() (js/app.js:4791-4808) renders its own duplicate copy of the weekday grid with no note inputs — start, end and studio only. Both grids feed the same handleSaveSchedule(). Under wholesale replacement, saving from that path would wipe the recurring notes of all 16 affected staff.

The recursive merge that causes bugs #1–#6 is currently the only thing preventing that. Adopting the simpler-sounding fix would have shipped exactly the data loss this work originally (and wrongly) claimed to be fixing.

Claude also flagged that diff-based deletes are safer under concurrency: they will not clobber a key another manager added while the editor sat open.

Proposed phases

Ordering is not arbitrary — Phase 1 is a prerequisite, not a cleanup.

Phase 1 — Reset stale editor state in aiEditInBuilder() prerequisite

scheduleEditOriginalOverrides is assigned in exactly one place (js/app.js:2981, inside openScheduleEditor()). aiEditInBuilder() sets editingScheduleUid and resets editingOverrides, but leaves that snapshot stale from whoever was edited last.

Today that is harmless. Once deletions are derived from a diff against that snapshot, it means emitting deletions for the previous employee's dates against this employee's document. This must land before Phase 3, or the fix introduces worse data loss than the bug it repairs.

Given an admin edits Kathy's schedule, closes it, then opens the AI builder on Leah
When they save Leah from the AI-populated grid
Then no override belonging to Kathy's dates is touched on Leah's document

Phase 2 — Make notes clearable (fixes #3, #4)

A day or override that survives but whose note was cleared must emit FieldValue.delete() for that nested note key. The pure helper must stay pure — take the sentinel as a parameter, or have the caller apply it.

Given Ivy's Thursday has the note "14:30 Thursday Huddle"
When an admin clears that note field and saves
Then reloading shows no note on Thursday, and her hours are unchanged

Phase 3 — Make removals real (fixes #1, #2, #5)

  • Weekdays: derive from DAYS — the grid always renders all 7 columns, so emit FieldValue.delete() whenever a column has no hours. No remote read needed.
  • Overrides: diff against scheduleEditOriginalOverrides (correct only once Phase 1 lands). Compute the delete set with Object.keys/in, never truthiness — a day-off override is null, which is falsy but must be preserved, not deleted.
  • Validity bounds: write explicit null when cleared. getShiftForDate() already treats null as unbounded.
  • Keep two payloads. The sentinel-laden map is for the write only. The clean map is what sendOneOffReminderConfirmations() reads — do not let sentinels reach it.
Given Kayleigh works a standing Saturday
When an admin clears Saturday in the editor and saves
Then she no longer appears on Saturdays in Who's Working, and her other days are unchanged
Given Leah has a day-off override on 2026-11-23 (stored as null)
When an admin removes a different override and saves
Then 2026-11-23 is still a day off — the null was not mistaken for a deletion

Phase 4 — futureSchedule, depth 2 (fixes #6)

Measure first. No test covers removal at depth 2. Probe whether FieldValue.delete() resolves correctly at futureSchedule.recurring.Sat before assuming it does — this repo's own convention, and the reason the original premise here was caught as wrong.

Note the existing inconsistency: the CSV importer (js/app.js:5602) writes futureSchedule with {mergeFields:['futureSchedule']}, which replaces it wholesale (proven by future-schedule-write.emulator.test.js:80), while the editor's future branch deep-merges. Same field, two different removal semantics. Worth resolving deliberately rather than adding a third behaviour.

Phase 5 — Test wiring and honest comments

  • recurring-note-merge.emulator.test.js is untracked and absent from package.json's explicit jest file list, so npm test never runs it. Wire it in.
  • Its tests currently assert the broken behaviour, so they would keep passing after a fix. Flip them to assert the corrected write shape, and keep only the parts not already covered by remove-timeoff-overrides.emulator.test.js:41.
  • Add per-test document cleanup, matching the other emulator suites.
  • Correct the buildRecurringDay() comment and the test name that still assert the retracted data-loss claim.

Open decisions — needed before execution

1. Edit-then-save becomes a real deletion. editOverride() (js/app.js:3081-3103) removes the key so that "Add Override" re-adds it. Today, editing an override and saving without re-adding silently does nothing. After Phase 3 it becomes a real deletion. Recommendation: accept it — it is what the UI implies, and the current no-op is the more surprising behaviour. Needs Christie's explicit sign-off since it changes what an existing gesture does.
2. Scope of bug #8 (aiEditInBuilder never sets _editingFutureSchedule, so an AI-builder save can land in futureSchedule instead of the live schedule for anyone with an active future schedule). Recommendation: log it separately rather than widen this plan — it is a distinct bug with a distinct fix. Christie's call.
3. Should the AI builder's duplicate grid be deduplicated? The two grid renderers have now diverged (one has a note column, one does not). That divergence is both the reason wholesale replacement is unsafe and a standing trap for future edits. Merging them into one renderer would remove a whole class of future bug, but widens this change.

Completeness check

Phase 1 is independent and must ship first. Phase 2 is independent of 3. Phase 3 depends on 1. Phase 4 depends on a measurement not yet taken. Phase 5 is cleanup that should ship with whatever lands. No phase requires a Firestore rules change, and no new collection is introduced.
