What is actually broken

All of the following share one root cause: saveSchedule() (js/firebase-data.js:205) writes with set(..., {merge:true}), and Firestore recursively merges nested map fields. A key that is absent from the written map is left untouched remotely rather than removed. The editor rebuilds the whole map every save and assumes absence means deletion. It does not.

🚨 Symptom #10 — the AI builder's "Save All Schedules" destroys dated overrides

This is live in production right now and does not require any of this plan's changes to be dangerous. It is the most serious finding in this work.

handleAiSaveAll() (js/app.js:4824-4829) does not go through handleSaveSchedule() at all. It writes, for each matched employee: 
await saveSchedule(uid, {
  name: matchedEmp.name,
  earlyClockInMinutes: sched.earlyClockInMinutes || 15,
  recurring: sched.recurring || {},
  overrides: {}          // <-- this
});

Measured against the emulator, Sep 5:

overrides AFTER writing `overrides: {}` with merge:true -> []
VERDICT: ERASED (empty map overwrites)

Firestore's recursive merge has a documented exception: an explicitly written empty map replaces the target map rather than merging into it. So every use of "Save All Schedules" in AI build mode wipes all dated overrides for every person it saves — camp days, day-offs, one-off shifts, approved time-off markers, everything.

The UI gives no warning. Its help text (js/app.js:4588) reads: "Create or replace a permanent recurring schedule (no date range). Use this for new hires or changing someone's year-round base schedule." Nothing there suggests dated overrides are affected, and "changing someone's year-round base schedule" is exactly the case where they would already have overrides worth keeping.

Concrete exposure: running AI build mode on Ivy, Kaitlyn, Kayleigh or Leah today would erase the 74 dated entries written on Sep 4.

Immediate mitigation, before any code changes: do not use "Save All Schedules" in AI build mode on anyone who already has a schedule. AI edit mode is a different code path (handleAiSaveEdits, js/app.js:4842+) which merges overrides rather than replacing them, and is not implicated.

Two corollaries for this plan:

  • Any fix confined to handleSaveSchedule() does not reach this path. Phase 3 as originally written would not have fixed recurring removals here either.
  • The "never send an empty patch map" rule is not just a concurrency nicety — it is load-bearing. A write payload whose override patch is empty must omit the field, never send {}.

Every symptom above is silent. The editor shows the change, Save reports success, and the data is unchanged. There is no error and no warning. That is what makes this worth doing carefully: the failure mode is someone turning up for a shift that was supposed to be gone.

Measured, not assumed

Emulator probe (recurring-note-merge.emulator.test.js, untracked) against a real doc:

days present after clearing Sat:            Mon, Sat

Corroborating evidence already in the repo: js/app.js:7327-7332 contains a prose comment describing this exact trap, and removeTimeOffOverrides() works around it with FieldValue.delete(). The time-off flow was fixed; the main editor never was.

Firestore nuance that makes this worse, not better: an explicitly written empty map does overwrite the target. So removing the last weekday or the last override appears to work, while removing one of several silently fails. Anyone spot-checking the fix could easily test the working case and conclude it is fine.

Proposed phases

Ordering is not arbitrary — Phase 1 is a prerequisite, not a cleanup.

Phase 1 — Reset stale editor state in aiEditInBuilder() prerequisite · shippable alone

Scope widened Sep 5 after review question 2 — see open decision 3. There are five pieces of state openScheduleEditor() sets that aiEditInBuilder() does not reset, not two:

  • scheduleEditOriginalOverrides (symptom #7) — assigned in exactly one place, js/app.js:2981. Latent today; becomes destructive the moment Phase 3 derives deletions from it, since it would emit deletions for the previous employee's dates against this employee's document.
  • window._editingFutureSchedule (symptom #8) — assigned only at js/app.js:2975, never cleared. Sends an AI-builder save into futureSchedule instead of the live schedule.
  • The validFrom/validUntil inputs (symptom #9) — an ACTIVE bug today. handleSaveSchedule() reads them from the DOM (js/app.js:3165-3166) and writes them when truthy, so the previously-opened employee's date range is written onto this one.
  • Also fold in the template dedup: the two grid renderers (:2991, :4777) are identical apart from two placeholder attributes. Extract one renderWeekGrid() so the note column cannot be added to one and not the other. Low risk; this phase already touches the function.

Symptom #9 alone justifies shipping this phase on its own, ahead of the rest of the plan — it is corrupting date ranges today and its fix does not depend on anything else here.

Phase 2b — Make abandoning an override edit safe must ship WITH Phase 3

Added Sep 5 in response to review question 1 — see open decision 1 for the worked example. editOverride() (js/app.js:3068) currently does delete editingOverrides[dateStr] so that "Add Override" re-adds the edited value. That is byte-identical to what Remove does (js/app.js:3064), so the save path cannot distinguish "removed this" from "started editing this and walked away."

Today that ambiguity is harmless, because neither one actually deletes anything. Phase 3 removes that safety net. Shipping Phase 3 without this turns a harmless mis-click into a destructive one on the most-used editing gesture in the editor.

  • Stop deleting the key on edit. Track the date being edited instead, and have handleAddOverride() replace that entry.
  • Side benefit: the row stops vanishing from the list while you edit it.
  • After this, Remove and Edit are genuinely distinguishable, and open decision 1 needs no behaviour trade-off at all.

Phase 3 — Make removals real (fixes #1, #2, #5)

  • Weekdays: derive from DAYS — the grid always renders all 7 columns, so emit FieldValue.delete() whenever a column has no hours. No remote read needed.
  • Overrides: diff against scheduleEditOriginalOverrides (correct only once Phase 1 lands). Compute the delete set with Object.keys/in, never truthiness — a day-off override is null, which is falsy but must be preserved, not deleted.
  • Validity bounds: write explicit null when cleared. getShiftForDate() already treats null as unbounded.
  • Keep two payloads. The sentinel-laden map is for the write only. The clean map is what sendOneOffReminderConfirmations() reads — do not let sentinels reach it.

Open decisions — needed before execution

1. Edit-then-save becomes a real deletion. Answered Sep 5 in response to Christie's review comment ("explain this more clearly with a specific example"). The recommendation has CHANGED as a result — see below.

How the Edit button actually works

In the override list, each row has Edit and Remove. Clicking Edit (editOverride(), js/app.js:3068) does two things: it copies that date's values down into the form, and then —

// Remove the old override so "Add Override" saves the edit
delete editingOverrides[dateStr];

— it deletes the row. The row disappears from the list. It only comes back when you press Add Override, which re-adds it with your edited values.

The worked example

Leah has an override on Wed Nov 11: 8:30am–6:30pm, Clay Hub, note "SDOC / Break camp (AM) · regular shift".

  1. Admin opens Leah's schedule and clicks Edit on Nov 11, meaning to change the end time. The Nov 11 row vanishes from the list; its values appear in the form below.
  2. The admin gets interrupted, or changes their mind, or simply doesn't realise "Add Override" is required to commit the edit — and clicks Save Schedule.
What happens to Leah's Nov 11
TodayNothing. The date was absent from the write, and merge:true leaves it untouched. It reappears on reload. The vanishing row was a lie, but nothing was lost.
After Phase 3Deleted. Leah is no longer scheduled for the Nov 11 camp day at all.

Why this is sharper than it first looked

Remove and abandoned-Edit leave editingOverrides in the identical state. Both do exactly delete editingOverrides[dateStr] (js/app.js:3064 and :3095). The save path cannot tell them apart. So Phase 3 necessarily makes "clicked Edit and walked away" behave exactly like "clicked Remove."

Revised recommendation — do NOT simply accept this

The original recommendation here was "accept it; the current no-op is the more surprising behaviour." Working the example through changes that. Accepting it turns a harmless mis-click into a destructive one, on the single most-used editing gesture, in the same change that removes the merge behaviour currently absorbing the mistake.

Instead, fix editOverride() so abandoning an edit is safe. Rather than deleting the key up front, keep it and track which date is being edited, so that handleAddOverride() replaces it and abandoning the edit leaves the override untouched. The row also stops vanishing while you edit it, which is better UI regardless.

This is small, and it removes the need for Christie to sign off on a behaviour change at all — Remove deletes, Edit edits, and neither surprises anyone. Proposed as a new Phase 2b, and it must ship with Phase 3, not after.

Round 2 review — the plan is NOT execution-ready

Two independent reviews (Claude + Codex) ran against this plan on Sep 5 and independently converged on the same headline finding. Both say do not execute yet. The phase structure below is now known to be wrong in specific ways and needs restructuring before any code is written.

🔴 Headline: Phase 1's "low risk" dedup makes Phase 2 destructive

Both reviewers found this independently. The chain:
  1. aiEditInBuilder() builds its grid from aiParsedSchedules[idx].recurring (js/app.js:4765-4769) — not from the stored document.
  2. That AI data never has a note: the build-mode schema at netlify/functions/schedule-builder.js:93-97 specifies exactly {start, end, studio}.
  3. Phase 1 dedups the two grids; Phase 2 adds the note column to the shared renderer.
  4. Opening the AI builder therefore renders note inputs that are empty because the AI never produced one — not because anyone cleared them.
  5. Phase 2's rule ("a day that survives but whose note was cleared emits FieldValue.delete()") then fires on every AI-populated day.
Result: note deletion for every affected staff member — the exact data loss this plan claims to have avoided by rejecting wholesale replacement. Per-key deletion moved the hazard from the write shape to the input state; it did not remove it.

Root cause, stated properly: aiEditInBuilder() seeds the editor from AI output rather than from the stored document. Wholesale-vs-per-key only changes how that manifests.

Consequence for this plan: the claim "the template dedup is genuinely low risk" is true today and false the moment a note column exists. The two call sites feed the shared renderer from different data sources with different authority. This is a Phase 2 design decision, not a Phase 1 cleanup, and must be resolved before dedup ships.

  • The "move" gesture breaks under Phase 2b. Today: Edit Nov 11 → change the date to Nov 12 → Add = a move, because the original key was already deleted. After Phase 2b, unless the tracked key is explicitly deleted when it differs from the submitted date, you get a duplicate — Nov 11 kept and Nov 12 added.

  • sendOneOffReminderConfirmations is not awaited (js/app.js:3204). A note-level sentinel reaching it is a truthy non-string handed to isReminderCandidate() → throws inside an un-awaited async call → unhandled rejection with no user-visible error, after the save succeeded. Keep the payloads separate and make the call defensive.
  • Future-branch validity bounds can't be cleared either. That branch keeps ...(validFrom ? {validFrom} : {}) and spreads ...existingFuture from the allSchedules cache, so a cleared future range is un-clearable and the stale cached range is rewritten on every future-branch save. Phase 4's scope must widen beyond "probe depth-2 delete".
  • Timezone. Future-schedule activation compares UTC dates (js/app.js:2970, and again at 4931) while the studio runs on Mountain Time, so in the evening it can switch a calendar day early — changing which branch is edited. Include or log deliberately.
  • Tests are sequenced wrong. AGENTS.md requires a failing emulator test before each Firestore-writing fix. Phase 5 currently holds all regression coverage; it must move into the phase it guards.
