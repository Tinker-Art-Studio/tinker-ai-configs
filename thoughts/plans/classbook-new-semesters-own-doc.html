Plan: Classbook — every new semester gets its own document

Goal: When Christie creates Spring 2027 (and every semester after it), its lessons are stored in their own Firestore document, so the shared, size-capped curriculum/lessonData never grows again and lesson saves never hit the 1 MB wall.
Why now: Christie wants to build Spring 2027 the week of Oct 5, 2026. Today, "+ New Semester → Copy from Fall 2026" would write Spring 2027 into lessonData (44% → about 85%).
Parent plan: classbook-per-semester-lesson-storage.html (Phases A–C DONE: Spring 2026 lives in curriculum/lessons_spring-2026, verified). This plan is its required "Follow-up".
Scope for Oct 5 (revision 4): new weekly semesters are created — atomically, with their config entry — in their own document; one generic rule for new lessons_* documents; lessonData closed to new semester keys; reading, editing, live updates, counts and the gauge for any number of own-doc semesters; a production-shaped test seed. Trails it (before Spring 2027 is published): Studio Hub alerts. Deferred: deleting a semester that has its own document (Phase E), moving Fall (Phase D).

Design (revision 4)

  • Flip the default. LEGACY_LESSONDATA_SEMESTERS = ['fall-2026'] replaces OWN_DOC_SEMESTERS. isOwnDocSemester(k) = isWeeklySemester(k) && !LEGACY_LESSONDATA_SEMESTERS.includes(k). Every new semester is own-doc with no flag and no per-semester code. The rules carry the same literal list.
  • Born own-doc vs moved. A semester has an edit pause only if storageMigrations has a record for it (Spring 2026: verified; Fall later). No record → editable as soon as its document exists. The pause/"missing" messages name the semester.
  • Create is one transaction (both reviewers). After updateAppData's two guards (config-load failure, registry error) and an empty-key refusal: the key must match the rules regex ^[a-z0-9]+(-[a-z0-9]+)*$ (one shared literal, pinned by a ratchet test) and not be in the legacy list. One transaction reads appData and lessons_<key>; refuses if the key is already a semester; refuses if the document exists at all (revision 3: no "adopt" path — round 2 found its tx.set would replace the adopted lessons; Phase 0 found no such documents, and atomic create can never leave one); then tx.sets the new document (copied slots, or stamps only) and writes semesters.<key> + stamps to appData — tx.update; if appData is absent the transaction refuses (revision 4, Codex r3-1: creating a partial appData would replace the defaults and hide Spring 2026 from every selector). After commit, the creating tab sets the new semester's source to ownDoc and installs the written map before reconciling listeners, so it can edit and add roster classes immediately (Fable r3-3). No compensation, no orphan, no read-to-update window. The rules check the pair with getAfter(appData).
  • lessonData is closed to new keys. A create or update may not add a top-level key outside ['fall-2026', 'lastUpdated', 'lastUpdatedBy'] (qaData already exists, so it stays editable without being listed; Fable 6). Existing keys change and disappear as today. The fence is added to the lessonData create and the shared update statement only; the manager-only Spring removal/rollback statement stays un-fenced (its affectedKeys().hasOnly(['spring-2026']) already limits what it can add, and the existing rollback test re-adds spring-2026).
  • One generic rule block for new lessons_* documents: docId.matches('^lessons_[a-z0-9]+(-[a-z0-9]+)*$') && docId != 'lessons_spring-2026'. Spring 2026's literal rules stay as deployed except for two edits: isStorageMoveDoc() also covers new lessons_* docs, and the two fenced lessonData statements above (Fable: saves the ~60-test rewrite; fold at Phase D). Create: manager+, only when getAfter(appData) lists the key as a semester. Update: manager+ or classbook roles, gated on a migration record if one exists (guarded exists first), and only while the semester is still in config (semesterInConfigAfter; revision 4, Codex r2-5/r3-2 — a stale pre-deploy tab can remove a new semester's config entry, and then its document must not be editable out of sight; it stays on the server, recoverable by restoring the entry). Delete: manager+, only when the key is gone from the projected config or an unverified migration record exists (Phase D's undo). No routed delete in the app for Oct 5.
  • Deleting an own-doc semester stays disabled (Codex: stale-tab edits between backup and delete could be lost; Fable: two writes can strand a semester). No exception (revision 3): a semester whose document is missing (only possible from a stale pre-deploy tab) gets a manager-only "Create its storage" button instead — a transaction that reads lessons_<key>, refuses if it exists, else sets the stamps (the create rule allows it because config already holds the key). Nothing is ever removed, so no document can be orphaned. Proper delete is Phase E.
  • Listeners by name. Map<semKey, unsubscribe> with a reconcileOwnDocListeners() that starts missing ones and stops removed ones; the lessonData listener carries every own-doc semester's map across each snapshot. createNewSemester calls reconcile only (no full listener re-setup, no generation bump). A vanished document for a semester without a migration record = "missing — deleted or changed elsewhere, reload", never writable. Initial load reads own docs in parallel.
  • Storage state per own-doc semester (Codex r2-4). A failed or not-yet-arrived storageMigrations read is unknown, never "no record"; every own-doc semester is read-only until it arrives, and the state is re-evaluated when it does.

  • Slot template stays as today — an explicit exception, approved by Christie Oct 1, to the "strip empty fields before any write" invariant: the blanks go only into a document the same transaction confirmed absent, and ordinary saves strip empty content fields before writing. See Decisions Log.

Why a legacy list and not a per-semester flag in config: a literal list can't flip under a bad or missing config read, and the rules use the same literal list without an extra get(appData) on every lessonData write.

  • Growth: each tab listens to every own-doc semester (about 0.5 MB each, two more a year). Fine now; later, past semesters can be read once instead of listened to. A single semester near 1 MB: Spring 2026, the largest, is 54%; the gauge warns per semester at 85%.

Firebase safety checklist

  • Rules: no new collection — lessons_* are documents in curriculum. The generic rule is tested for every role and shipped through the guard with the sha phrase before any code relies on it.
  • Partial updates: lesson edits stay per-field dotted update()s; whole-semester writes stay set(…, {merge:true}); creation is a transaction set on a document just read inside the same transaction as absent, plus a dotted update of appData (refused if appData is absent); roster slots are dotted tx.updates of absent keys only.
  • Empty fields: explicit exception approved by Christie (Oct 1) for the slot template's blank defaults, written only into absent documents/keys; ordinary saves keep stripping empty content fields; undefined is never written.
  • Awaited: the one create transaction is awaited before any UI change.
  • Snapshot before delete: no own-doc delete ships in this plan (Phase E). Backups: backup.js covers every lessons_* document.
  • Spot check: Phase C, in the Console.

If interrupted

  • After Phase A: apps behave as today; "Copy from" creation is refused (loud, nothing written). Don't create a semester until Phase B.
  • After Phase B: ready; Spring 2027 can be created. Its alerts reach Studio Hub only after Phase B′.
  • Mid-create: the transaction committed both writes or neither.
