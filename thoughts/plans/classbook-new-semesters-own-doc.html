Plan: Classbook — every new semester gets its own document

Goal: When Christie creates Spring 2027 (and every semester after it), its lessons are stored in their own Firestore document, so the shared, size-capped curriculum/lessonData never grows again and lesson saves never hit the 1 MB wall.
Why now: Christie wants to build Spring 2027 the week of Oct 5, 2026. Today, "+ New Semester → Copy from Fall 2026" would write Spring 2027 into lessonData (44% → about 85%). Decision logged Sep 30 as 🔴 PRIORITY in the parent plan.
Parent plan: classbook-per-semester-lesson-storage.html (Phases A–C DONE: Spring 2026 lives in curriculum/lessons_spring-2026, verified). This plan is its required "Follow-up".
Scope: new semesters created in their own document; one generic rule for lessons_* documents; the lessonData fence generalised; routed semester delete; Studio Hub alerts and the storage gauge cover any number of own-doc semesters. Out of scope (Phase D, later): moving Fall 2026 out of lessonData at the end of its term.
Touches: the Classbook (js/firebase-data.js, js/app.js, e2e), studio-hub/firestore.rules + studio-hub/rules.test.js (sha phrase + guard), studio-hub/js/alerts.js (Studio Hub deploy). tinker-backups/backup.js needs no change (it already tallies every curriculum/lessons_* document and backs up the whole collection).
Line numbers at Classbook 1532121, studio-hub a254b15. Status: DRAFT, revision 1 — awaiting review.
Requirement (Christie, Oct 1): every past semester stays in the app. Own documents are storage only — every semester, past and present, stays selectable and readable in the Classbook, loaded the same way Spring 2026 is today. Nothing in this plan (or Phase D, or the future Archive feature) may make a semester's lessons unreachable from the app; only an explicit manager Delete removes them. Planned future feature: project history search — find a project by name and see when it was last taught (semester, date, classes) to re-use projects on about a 3-year cycle. Per-semester documents make that feasible: the search reads every lessons_* document plus the legacy lessonData keys (and camp lessons), with no single-document size limit.
Until this plan is live, do not create Spring 2027. If the deadline slips, the fallback is to wait — not to create it the old way. Creating it the old way puts ~420 KB into lessonData, and then moving it out again is another Phase-C-sized production move.

Design

  • Flip the default. Replace "own-doc if listed" with "own-doc unless listed": one literal list, LEGACY_LESSONDATA_SEMESTERS (expected ['fall-2026']; confirmed in Phase 0), names the weekly semesters that still live inside lessonData. isOwnDocSemester(k) = isWeeklySemester(k) && !LEGACY_LESSONDATA_SEMESTERS.includes(k). Every new semester is own-doc with no flag, no config field and no per-semester code change. The same literal list is in the rules, so app and rules can't disagree about a key.
  • Born own-doc vs moved. A semester only has an edit pause if storageMigrations has a record for it (Spring 2026: verified; Fall later). A semester with no record — every new one — is editable as soon as its document exists. weeklyLessonTarget / weeklySemesterPausedMessage become: refuse if the document is missing/errored, or if a migration record exists and isn't verified.
  • The document is created with the semester, before its config. createNewSemester (weekly) runs: server config check → one transaction on lessons_<key> (refuse if it exists with real content; adopt it if it exists template-empty or the no-copy path finds leftovers, as today) that sets the empty slots (copy path) or just the stamp (blank path) → config write. If the config write fails, the compensating delete removes the document only if this call created it. This fixes the "not-found on the first write" problem at the source: a semester never exists in config without its document — except one created by a stale pre-deploy tab (see Edge cases).
  • lessonData is closed to new semesters (the generalised fence). Rules: a create or update of lessonData may not add a top-level key unless it's in the legacy list or is lastUpdated/lastUpdatedBy/qaData. Existing keys (Fall, the TEST_DATA_SAFETY leftovers) can be changed and removed as today. This replaces all four Spring-specific lessonData statements: Spring's re-add is refused by the same rule, and its rollback allowance is dead (verified is one-way). A stale tab running old code that tries to write Spring 2027 into lessonData is refused.
  • One rule block for every lessons_* document (docId.matches('^lessons_[a-z0-9-]+$'), semester key = docId.replace('^lessons_', '')): read as today; create: manager+ only (semester creation and moves); update: manager+ or classbook roles, and if storageMigrations has a record for the key it must be verified (one get() per write, same as Spring today); delete: manager+ only, and only when the key is no longer a semester in appData (getAfter, so a batch that removes both is allowed) — a semester's lessons can't vanish while the semester still shows. classbook-admin/curriculum-admin can no longer delete lesson documents (they can't delete semesters in the UI anyway).
  • Routed delete. deleteSemester for an own-doc semester: same two confirms as today → JSON download of its lessons (forced-server, transactional read) → remove the config entry → delete lessons_<key>. A failed document delete leaves an orphan that re-creating the same name adopts (today's legacy behaviour). This also re-enables deleting Spring 2026.
  • Listeners and readers follow config. The own-doc set at runtime = weekly semesters in currentConfig.semesters that aren't legacy. loadOwnDocSemesters, the listener carry-over and per-doc listeners, the content count and the gauge loop that set. createNewSemester starts the new semester's listener in the creating tab. The gauge shows lessonData plus an approx. size per own-doc semester (warn above 85%).
  • Studio Hub alerts stop using a literal list: one listener on the curriculum collection range lessons_ … lessons_ (by document ID), so new semesters' Q&A alerts appear with no Studio Hub change ever again.
Why a legacy list and not a per-semester flag in config: config can silently fall back to defaults on a permission error (the May 2026 incident), and it has no live listener; a literal list can't flip under a bad read, and the rules can use the same literal list without a get(appData) on every lesson write.

Edge cases

  • Stale tabs (pre-Phase-B code) after Phase A: they keep working for Fall and Spring 2026. If one creates a semester with "Copy from", its lessonData write is refused → nothing created. Without "Copy from" it creates a config-only semester → Phase B code shows "storage is missing". Christie is the only semester creator; Phase C starts with a hard refresh.
  • Tabs open while Spring 2027 is created don't see it until they reload (config has no listener) — same as today for any new semester.
  • Config falls back to defaults (permission error): own-doc listeners start only for semesters it lists; a semester missing from config isn't shown at all — loud through the existing load-failure guard, never written.
  • A single semester outgrowing 1 MB: Spring 2026, the largest so far, is 551 KB (54%). The gauge shows each semester's size and warns at 85%.

Firebase safety checklist

  • Rules: no new collection — lessons_* are documents in curriculum, which has its rule block; the generic rule is added in Phase A, tested for all roles, deployed through the guard with the sha phrase, before any code relies on it.
  • Partial updates: lesson edits stay per-field dotted update()s; whole-semester writes stay set(..., {merge:true}); the creation write is a transaction-guarded set on a document that was just confirmed not to exist (or to be template-empty).
  • Empty fields: slot templates are the same as today; no undefined is written (strip before write as today).
  • Awaited: every write in create/delete is awaited and checked before the next step.
  • Snapshot before delete: deleting an own-doc semester downloads its lessons first and refuses if that fails. Backups: backup.js already covers every lessons_* document.
  • Spot check: Phase C, in the Console.

If interrupted

  • After Phase 0: nothing changed.
  • After Phase A: apps behave as today; creating a semester with "Copy from" is refused by the rules (loud, nothing written). Don't create a semester until Phase B.
  • After Phase B: ready; Spring 2027 can be created at any time.
  • Mid-create (Phase C): either the document exists without config (harmless orphan; re-creating the same name adopts it) or both exist. Never config without a document from Phase B code.
