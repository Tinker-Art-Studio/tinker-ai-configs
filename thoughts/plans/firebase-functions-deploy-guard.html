Choices made here (Christie can overrule any)

#ChoiceWhy
F1A separate script, scripts/deploy-functions.sh, with the same CLI shape (--status, --diff, --approved <sha>, plus --codebase <name>). It uses the same lock (.git/tinker-deploy.lock), so a rules deploy and a functions deploy never overlap, and the same receipt rules. Receipts: deployed/my-clay-hub/functions-<codebase>/<UTC stamp>-<sha7>.deploy-rules.sh was reviewed line by line and just proved itself. Mixing functions logic into it would put that at risk for no gain. Its record logic (receipt_rows, the pending-receipt reconcile, stamp reservation) is copied with its comments and tests, not rewritten.
F2Codebases live at functions/<codebase>/, each with its own package.json, committed package-lock.json and "engines": {"node": "22"}. firebase.json gets the array form. D2 creates one codebase, core, holding one function, canary: onRequest({ invoker: 'private', region: 'us-central1', serviceAccount: 'canary@', maxInstances: 1 }). It returns 204 and does nothing else.The guard needs a real, harmless function to prove itself on before D-4's vault export ships. The canary stays for good: every deploy probes it, so a broken probe (say, one that reads every reply as "refused") shows up on the one function known to be private.
F3"The folder matches the commit" means: under functions/<cb>/, every file on disk, excluding only node_modules/, is tracked in the approved commit and byte-identical to it, and every tracked file is on disk. The receipt's folder hash is git's tree id for <sha>:functions/<cb>. Both the guard (before the CLI) and the predeploy backstop (inside it) check this.K1: whatever is in the folder ships. A git tree id changes when any byte of any tracked file changes; the on-disk walk catches the untracked extras a tree id can't see.
F4The ignore list is pinned to exactly ["node_modules", ".git", "firebase-debug.log", "firebase-debug.*.log", "*.local"], and the backstop refuses any other list. The source folder may not contain functions.yaml or any .env* file, tracked or not.K1–K3. A short, fixed list is easy to review. Forbidding the files beats ignoring them: an ignored .env is still read by discovery.
F5The CLI call is always firebase deploy --only functions:<cb> --project my-clay-hub --non-interactive, run in the worktree with TINKER_DEPLOY_SHA set. Never --force. The dependencies are installed fresh in the worktree with npm ci in functions/<cb>/, not symlinked.K4, K5, K7. Discovery runs node_modules/.bin/firebase-functions from that folder (K2), so it must come from this commit's lockfile, not whatever the shared tree has installed.
F6The guard never deletes a function. Before deploying, it compares the functions the commit defines (from the CLI's discovery output) with what functions:list shows in that codebase. If the commit removes one, it refuses and says so, before anything is uploaded. Deleting gets its own guarded mode in a later plan, when something first needs removing.K6. The CLI would refuse anyway, but only after uploading, and with a message that's easy to misread. A deletion is a different kind of change and deserves its own approval.
F7C5 is replaced. Builds run as the Compute default account (K12), so that account gets C5's narrow build roles: Logs Writer on the project; Artifact Registry Writer on the gcf-artifacts repository only; Storage Object Viewer with a condition limited to the gcf-v2-sources-*, gcf-v2-uploads-* and run-sources-* buckets. Editor is removed from it before the first build ever runs (D2-1 enables the Compute API first, on purpose). No function ever runs as it: each function names its own runtime account (serviceAccount), and the read-back refuses the Compute account. functions-build@ (D-1, no roles) is deleted as unused.The Firebase CLI offers no other way; only gcloud's --build-service-account can choose, and there is no gcloud (Christie, Sep 29). Doing it in this order means no build runs with Editor, even for a moment.
F8The read-back runs after every deploy, whatever the CLI's exit code. functions:list --json, filtered through jq so env values are never printed or stored, must show: every function the commit defines, and no others, in that codebase; each ACTIVE; each with the hash label the CLI computed for this deploy; each running as its declared account, never the Compute one; ingress "all". Then the anonymous probe: a plain HTTPS request with no credentials to every HTTP function's uri must get 401 or 403. Any other reply, including 2xx, 404, 5xx or a timeout, fails the read-back.K9–K11. The probe checks the one property that matters, "strangers can't call it", end to end, without new credentials on the laptop. Cloud Run refuses an unauthenticated request before any of our code runs, so the probe can't trigger work.
F9The receipt is an annotated tag written after the read-back, whatever the outcome, because production may have changed either way. Its message holds: project, codebase, commit, folder tree id, the CLI's exit code, each function's state and hash, the probe results, and outcome=complete|partial|unsafe. partial: the read-back doesn't match the commit. unsafe: a probe wasn't refused. The guard exits non-zero for both, with a plain-English next step. --status treats the newest complete receipt as "what shipped", and names any newer partial or unsafe one above it in red."A clear record when a deploy only partly succeeds" (foundation). The rules guard writes no receipt on failure, because a rules release is all-or-nothing. A functions release isn't (K9).
F10Tests first: the guard runs the repo's full npm test in the worktree, extended with test:functions (each codebase's own tests, run with node --test, no emulator needed for the canary). The Functions emulator is added when a codebase first needs Firestore triggers, on its own pinned port, through scripts/emulator-safety.js.The canary has nothing to emulate. Adding an emulator now would be untested machinery.
F11The cleanup policy is set before the first deploy, on a gcf-artifacts repository Christie pre-creates in us-central1 (Docker format), with the policy "delete untagged images older than 1 day, keep the 2 most recent" set in the Console. The read-back also treats the K8 message as a failure that needs attention, never as success.K8. Pre-creating the repository also lets F7 scope Artifact Registry Writer to it.
F12The global hook also denies the CLI's other function-changing commands: functions:delete, functions:secrets:set|destroy|prune, functions:artifacts:setpolicy, functions:config:set|unset|clone. Its message names both guards and the new functions guard (Appendix A, for Christie's approval).The hook exists to catch habits. These commands change production as surely as deploy does.
