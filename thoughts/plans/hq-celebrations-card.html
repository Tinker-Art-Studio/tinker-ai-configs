Plan: Tinker HQ shows admins and managers what's coming up

Apps: Staff Directory (~/tinker-staff-directory) + Studio Hub / Tinker HQ (~/studio-hub) · Drafted: Oct 1 2026 · v9 after design review rounds 1–6 (round 1: Codex full, Claude sandboxed out; rounds 2–3: Codex + Claude full; round 4: Claude only, because Codex was out of credits; round 5: both (Codex: no blocking); round 6: Claude "execution-ready: yes" after text fixes, Codex one blocking contradiction in the text. All folded in. Every finding verified against the code and folded in. See the Decisions log) · execution-ready: true (Christie, Oct 1 2026)

Goal: when an admin or manager opens Tinker HQ, a "Coming up" card lists every staff birthday and work anniversary in the next 60 days, with 5-year milestones (5, 10, 15…) highlighted.
Staff see only their own celebration in HQ: "Happy Birthday!" on their birthday, and "Happy 5-year / 10-year anniversary!" on milestone anniversaries. It shows on the day, or on their first HQ sign-in within 7 days after, once. In HQ they never see anyone else's, and the database rules mean a staff account can read only its own record.
Scope of the privacy promise: Tinker HQ only. In the Staff Directory, staff may see coworkers' dates (D4).
Why: Christie missed Anika's 10th anniversary (Aug 20 2026). HQ is the app she opens every day.
Starting point: Phase 1 (Staff Directory Celebrations page) is live on main @ 6463ec3.

What is wrong today

  • HQ's birthday alert has never worked. checkCelebrations() in studio-hub/js/app.js reads staffDirectory/appData→staff. The Staff Directory never writes a staff field. It writes only {offboardingData, lastUpdated} with a whole-doc set(). Nothing was lost: staff data has always lived in the Google Sheet.
  • That code knew only MM/DD birthdays, looked 7 days ahead, and had no work anniversaries.
  • HQ can't read the Google Sheet directly. The "published to web" link is going away (separate work).

Design

One new collection, staffCelebrations, written only by admins/managers from the Staff Directory

Two kinds of doc in it, both whole-doc set()s, never deleted:

DocContentsWho reads it
staffCelebrations/_summary { staff: [ {id, uid?, name, birthday?, birthdayMonthOnly?, startDate?, status:'current'}, … ], updatedAt, checkedAt, updatedBy }, current staff only. Each row has exactly these keys, pinned by a unit test, because rules can't inspect list items (R3 Claude-B2). Nothing else from the sheet row (address, medical, phone…) can get in.
  • id is always row-<trimmed lowercased email> (lossless, not slugged, so sam.one@ and sam-one@ stay distinct), or row-name-<lowercased name> when there's no email. A collision gets -2, -3… in sheet order (R6 Codex-M2, Claude-L3). It's independent of whether the row is linked, so it doesn't change when someone gets an account (R5 Codex-L1). uid is carried separately when linked. It's never the sheet's staff-<index> id, which shifts when rows are inserted; a test pins the format (R5 Claude-L1). id drives once-keys; dedupe uses uid when present (R3 Codex-5, Claude-L2).
  • birthday is month/day only ("8/3"). A month-only sheet birthday is kept as "7/1" plus birthdayMonthOnly:true, so the card still lists it with "≈ month only" (R3 Claude-M1, Codex-2). getCelebrations() treats parsed.monthOnly || staff.birthdayMonthOnly as month-only.
  • startDate keeps the sheet's wording. status:'current' lets the shared getCelebrations() work on rows as-is (R2-B3).
  • Summary rows use the same caps as records: name truncated, and an over-long startDate dropped (and listed in Needs attention), so one huge cell can't push _summary past Firestore's doc-size limit (R6 Codex-L4).
  • updatedAt = when the content last changed. checkedAt = when a manager's load last confirmed it (R3 Claude-M2, Codex-3). updatedBy = who last wrote the doc, including a checkedAt-only refresh, not who last changed content (R5 Claude-L9).

  • Why not staffDirectory/celebrations (v4): that collection's existing rule also lets staff-directory-override staff and a manager-role kiosk read it, so "in HQ staff only see their own" couldn't be rule-enforced (R2 Codex-4, Claude-M4). Inside staffCelebrations, the new block's !isKiosk() && isManagerOrAbove() covers the summary too, and _summary can never equal a real uid.
  • Written only by admins/managers, when they load or refresh the Staff Directory. The gate is a separate, role-only canWriteCelebrations(user), deliberately not the Directory's canWrite (which includes override staff). It also gates the users read, so override staff never trigger denied reads or a notice on every load (R3 Claude-M5).
  • Validated as a set, committed in small chunks (R4-B1): rules allow only 20 document-access calls per batched write, summed across its writes, and each manager write costs 1–2 users lookups. So one big batch would be refused outright. The full write set (changed records, leavers, summary) is built and checked against the rule shapes first. It's then committed with compat db.batch() in chunks of a fixed CELEBRATION_CHUNK = 5 docs (5 writes × up to 2 lookups = 10, half the quota), records first and _summary last (R4-L8). The emulator isn't trusted to measure a production quota (R5 Claude-M1, Codex-M1). The commit loop awaits each chunk in sequence. A failed chunk stops the run: no summary is written (so neither is checkedAt), one notice is shown, and the next load reconciles. Records may briefly be newer than the summary, never the reverse.
  • 2a lists the whole collection once (_summary plus every record; managers have list). _summary is used for change detection, carrying updatedAt forward, and the checkedAt heartbeat. It's excluded by doc id from all record, leaver and vanished-row logic (R4-M2).
  • Written only when something changed: compare canonical domain fields only, staff sorted by id, ignoring updatedAt/checkedAt/updatedBy. A plain reload writes nothing, except the summary's checkedAt, refreshed at most once a day (R2-M8, R3).
  • Sanity gate before any write (R2-B5, R3 Codex-1). Write nothing (summary, records or leavers) and show a notice if:
    • the sheet produced zero staff rows;
    • (records and leavers only) zero rows matched an account. The summary is still written; it needs no accounts. The card works even if no greetings can be linked (R5 Claude-B1);
    • any required column wasn't found by header (name, email, status, startDate, birthday, from detectColumns()), so a renamed form question can't blank out everyone's dates or make past staff current. name may instead be satisfied by first + last name, as fetchStaffData() already falls back;
    • the number of current rows swings by more than 40% against the existing summary (Supply Low List shape). Skipped on the first run, when no summary exists yet (R5 Claude-M4). The manager sees "Staff count changed from 24 to 9: save anyway?" and must confirm (R4-M4).
    Because detectColumns() matches headers by substring, the Celebrations page (managers) shows which sheet header each required field bound to, e.g. Name ← "Name", Status ← "Employment Status - Current (C) or Past". A wrong binding (e.g. "Emergency Contact 1 - Name") is visible (R4-M4). A broken or unpublished sheet must never look like "everyone left". This is the same failure shape as the Supply Low List incident.
  • Going stale is mild. Dates repeat yearly, so an old summary still predicts correctly; it misses only hires and leavers since the last manager load. The card shows the row count and checkedAt, e.g. "24 staff · checked 2 days ago" (amber past 30 days, with a link to the Directory). The writer never saves an empty summary (the gate blocks zero rows), but the card still handles staff: [] as "Staff list is empty", tested, so a future writer change can't produce a cheerful empty card (R3 Claude-L8, R6 Claude-L4). A leaver marked P disappears on the next manager load. new Date(updatedAt) is safe because it's a full ISO instant; there's a code comment so nobody "fixes" it (R2-L11).

Matching sheet rows to accounts

  • The Directory reads users (managers can read all) and matches each current sheet row by trimmed, lowercased email. Both sides must be non-empty and contain @. Emailless rows go to "Needs attention", and emailless user docs are ignored, so two blanks can never "match" (R5 Claude-M2).
  • Match rate is shown: "Linked 18 of 20 current staff to their HQ account" at the top of "Needs attention", with the unlinked names. This is how Christie sees whether the sheet email and the sign-in email line up (R5 Claude-B1). Christie believes staff sign in with the same email as the sheet (D7), so there's no manual-link feature. Anyone unlinked is named here, and the fix is to correct their email in the sheet (or the account).
  • Duplicates on either side (two rows or two accounts with one email) → that email is skipped and shown in a separate "Needs attention" section of the Celebrations page (managers only). Also listed there: rows with no account, rows whose start date or name couldn't be saved, and existing current records whose sheet row has vanished (R2-L3, R3).
  • Leavers come only from a positive match (R2-B5): a uid gets the leaver write only when a sheet row that matches it has the existing status === 'past' (P, past, former, inactive, outdated) (R3 Claude-L1) and its existing record is current:true. So the first run doesn't create dozens of leaver docs for long-gone staff (R4-M3). A uid that's merely unmatched or skipped is left untouched. Never derive leavers by subtraction.
  • Operational rule: keep leavers in the sheet, marked P. If a row is deleted instead, or an account is recreated under a new uid, the old record can't be safely cleared. It's listed under "Needs attention" on the Celebrations page (managers) for a manual fix: mark the row P, or archive the old account (R3 Codex-8, Claude-L1).
  • Accepted risk (D5, Christie): a user can change the email on their own users doc (the self-update rule doesn't pin it), or create an account with a coworker's unused email. Either way they could be matched to a coworker who has no account and receive that coworker's greeting record. It takes deliberate use of the browser console and exposes one person, so it's too unlikely to justify editing the shared users rule. Not fixed.

New rules block (the only rules change)

// ── staffCelebrations: birthdays + work anniversaries for Tinker HQ ──
// _summary = everyone's dates for the admin/manager card. {uid} = one person's own record.
// Written only by admins/managers from the Staff Directory. Never deleted.
match /staffCelebrations/{docId} {
  function isIsoInstant(v) {
    return v is string && v.matches('^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9:.]+Z$') && v.size() <= 30;
  }
  function isCelebrationRecord(d) {
    return ('current' in d && d.current == false)
      ? (d.keys().hasOnly(['current', 'updatedAt']) && d.keys().hasAll(['current', 'updatedAt']) && isIsoInstant(d.updatedAt))
      : ('current' in d && d.current == true
         && d.keys().hasOnly(['name', 'birthday', 'startDate', 'current', 'updatedAt'])
         && d.keys().hasAll(['name', 'current', 'updatedAt'])
         && isIsoInstant(d.updatedAt)
         && d.name is string && d.name.size() > 0 && d.name.size() <= 120
         && (!('birthday' in d)  || (d.birthday is string && d.birthday.matches('^[0-9]{1,2}/[0-9]{1,2}$')))
         && (!('startDate' in d) || (d.startDate is string && d.startDate.size() <= 40)));
  }
  function isCelebrationSummary(d) {
    return d.keys().hasOnly(['staff', 'updatedAt', 'checkedAt', 'updatedBy'])
      && d.keys().hasAll(['staff', 'updatedAt', 'checkedAt', 'updatedBy'])
      && d.staff is list && d.staff.size() <= 300
      && isIsoInstant(d.updatedAt) && isIsoInstant(d.checkedAt)
      && d.updatedBy == request.auth.uid;
  }
  allow get: if !isKiosk() && isActiveUser() && docId != '_summary' && request.auth.uid == docId;
  allow get, list: if !isKiosk() && isManagerOrAbove();
  allow create, update: if !isKiosk() && isManagerOrAbove()
    && (docId == '_summary' ? isCelebrationSummary(request.resource.data)
                            : isCelebrationRecord(request.resource.data));
  // no delete
}
  • Block-local helpers follow the /curriculum precedent (R2-L8). !isKiosk() is on every grant. The self-get excludes _summary explicitly instead of relying on no uid ever being "_summary" (R3 Codex-10).
  • The record shape is conditional (R3 Codex-7): a leaver must be exactly {current:false, updatedAt}; a current record needs a name, and its birthday must be M/D, so no year can sneak in. Timestamps must look like ISO instants.
  • Summary rows aren't field-checked by the rules (lists can't be iterated). The writer's unit tests pin the row shape instead.
  • No delete, ever. A wrong record can only be overwritten (with the leaver shape), never removed outside the Console. That's deliberate, like timeclock_reminder_log (R2-L10).

HQ: what people see

  • Everyone (rules refuse the kiosk; no client kiosk check needed, R2-L4): GET staffCelebrations/<firebase.auth().currentUser.uid> (R2-B2). Missing doc, permission-denied or current:false → nothing shown, no visible error.
  • Admin/manager also: GET _summary → the "🎉 Coming up" card, and day-of confetti for anyone's celebration (D1). The card has:
    • Just passed (last 7 days) at the top, from recentOccurrence(). If Christie misses the day, she still sees "⭐ Anika: 10 years at Tinker · 2 days ago". This closes the gap that started this work (R3 Claude-M4).
    • Next 60 days, with milestones striped; month-only items get "≈ month only". The marker comes from e.type === 'birthday' ? e.staff.birthdayMonthOnly : e.monthOnly, or from the shared getCelebrations() change above.
    • Footer: "24 staff · checked 2 days ago" (amber past 30 days) and "See all →".
    _summary missing → "Staff list not loaded yet. Open the Staff Directory once to fill it" with a link. Permission-denied or malformed (no staff list) → "Couldn't load the staff list", never a cheerful "nothing coming up" (R3 Claude-M3, Codex-6). The summary read is gated on currentUser.role being admin or manager, and tested. Staff-role HQ never attempts it, so staff never see a permission error or "Couldn't load" (R4-M7). If someone edits their role in the console, the server still refuses.
  • The card gets its own container in index.html, directly above #departments-container, so neither the async read nor a studio-filter click (handleFilterClick() → renderDepartments() clears that container) can wipe it (R3 Claude-L4, R5 Claude-M5). It's hidden for staff and in demo mode (!firebaseInitialized) (R5 Claude-L6). New CSS goes in css/.
  • The viewer's own-record event uses id/uid = the viewer's uid, so it dedupes against their summary row (R5 Claude-L2).
  • One pop-up, built from everything (R2 Codex-8): gather all qualifying events first: the Tinker / Clay Hub studio birthdays, the person's own birthday or milestone (today or last 7 days), and (admin/manager) anyone's celebration today. Deduplicate by id+type, so an admin's own birthday isn't listed twice and same-named people don't collide. Show one pop-up: own greeting first, then studio birthdays, then others. Each line is its own element set with textContent (never innerHTML). Studio birthdays still work in demo mode, as today (R3 Claude-L3).
  • "Once" (R2-M1): one localStorage key per celebration actually shown, keyed by its occurrence date (the observed date, so Feb 28 for a Feb 29 birthday in a non-leap year): celebrated:<viewer uid>:<celebrated person's id>:<birthday|anniv-10y|…>:<YYYY-MM-DD>. Two coworkers with birthdays on the same day get separate keys (R3 Codex-5). Sunday's birthday shown on Wednesday doesn't show again on Thursday. A birthday shown today doesn't suppress a milestone three days later.
  • "Today" means the device's local date, same as the rest of HQ (R1-8, declined Denver-zone).
  • The card's names go through a new escapeHtml() (copied from the Directory; HQ has none) (R2-L2). The pop-up already uses textContent.
  • Demo mode (no Firebase) keeps the existing if (!firebaseInitialized || !currentUser) return; guard.

Shared date logic

js/celebrations.js gains recentOccurrence(parsed, startYear, today, days), returning {date, years} (years counted from the occurrence's own year, which avoids the Dec→Jan trap) or null. Anniversaries require years ≥ 1, and milestones a positive multiple of 5. A start date this year or in the future yields nothing, matching getCelebrations() (R3 Claude-L6, R5 Codex-M2). celebrations-ui.js must not redeclare any top-level const from celebrations.js (they share one global scope) (R5 Claude-L7). Neither app ever uses a collectionGroup query on this collection; the rules don't allow one, even for managers (R5 Claude-L4). It's added in 2a, in the Directory repo with tests, along with the birthdayMonthOnly handling in getCelebrations(). module.exports is updated (R2-L1). 2b copies the file to studio-hub/js/celebrations.js unchanged, with a header naming the source. The writer builders (buildSummary, buildRecords, planCelebrationWrites, canWriteCelebrations) live in a separate Directory-only js/celebrations-sync.js, so HQ doesn't carry dead code (R4-L11). HQ's pure UI helpers (planCelebrationPopup, planCelebrationCard) go in a new studio-hub/js/celebrations-ui.js with the typeof module !== 'undefined' exports guard, the same as archive-helpers.js (R4-M6). Its <script> tag comes after celebrations.js. The tests are jest files at the studio-hub repo root, never under js/, which build-dist.sh publishes. They're added to the npm test list (R2-M2, R4-M6).
