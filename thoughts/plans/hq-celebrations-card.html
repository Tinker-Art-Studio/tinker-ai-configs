Plan: Tinker HQ shows admins and managers what's coming up

Apps: Staff Directory (~/tinker-staff-directory) + Studio Hub / Tinker HQ (~/studio-hub) · Drafted: Oct 1 2026 · v5 after design review rounds 1–2 (round 1: Codex full, Claude sandboxed out; round 2: Codex + Claude full. Every finding verified against the code and folded in. See the Decisions log) · execution-ready: false (D5 decided; design review round 3 running)

Goal: when an admin or manager opens Tinker HQ, a "Coming up" card lists every staff birthday and work anniversary in the next 60 days, with 5-year milestones (5, 10, 15…) highlighted.
Staff see only their own celebration in HQ: "Happy Birthday!" on their birthday, and "Happy 5-year / 10-year anniversary!" on milestone anniversaries. It shows on the day, or on their first HQ sign-in within 7 days after, once. In HQ they never see anyone else's, and the database rules mean a staff account can read only its own record.
Scope of the privacy promise: Tinker HQ only. In the Staff Directory, staff may see coworkers' dates (D4).
Why: Christie missed Anika's 10th anniversary (Aug 20 2026). HQ is the app she opens every day.
Starting point: Phase 1 (Staff Directory Celebrations page) is live on main @ 6463ec3.

What is wrong today

  • HQ's birthday alert has never worked. checkCelebrations() in studio-hub/js/app.js reads staffDirectory/appData→staff. The Staff Directory never writes a staff field. It writes only {offboardingData, lastUpdated} with a whole-doc set(). Nothing was lost: staff data has always lived in the Google Sheet.
  • That code knew only MM/DD birthdays, looked 7 days ahead, and had no work anniversaries.
  • HQ can't read the Google Sheet directly. The "published to web" link is going away (separate work).

Design

One new collection, staffCelebrations, written only by admins/managers from the Staff Directory

Two kinds of doc in it, both whole-doc set()s, never deleted:

DocContentsWho reads it
staffCelebrations/_summary { staff: [ {name, birthday, startDate, status:'current'}, … ], updatedAt, updatedBy }, current staff only. birthday is month/day only ("8/3"), or omitted when the sheet has a month-only birthday. A row then carries birthdayMonthOnly: true, shown as "≈ month only", like the Directory (R2-M6). startDate keeps the sheet's wording. status:'current' is written so the shared getCelebrations() works on the rows as-is (R2-B3). Admins/managers (the HQ card)
staffCelebrations/{uid} { name, birthday, startDate, current:true, updatedAt } for each current staff member matched to an account. No birth year. Month-only birthdays are left out, so nobody gets "Happy Birthday" on a guessed day (R2-M6). Leaver: { current:false, updatedAt }, which drops their name and dates (R2-B4). That person (self only) + admins/managers
  • Why not staffDirectory/celebrations (v4): that collection's existing rule also lets staff-directory-override staff and a manager-role kiosk read it, so "in HQ staff only see their own" couldn't be rule-enforced (R2 Codex-4, Claude-M4). Inside staffCelebrations, the new block's !isKiosk() && isManagerOrAbove() covers the summary too, and _summary can never equal a real uid.
  • Written only by admins/managers, when they load or refresh the Staff Directory. Staff with the staff-directory override skip it.
  • Written only when something changed: compare canonical domain fields only, staff sorted by name, ignoring updatedAt/updatedBy. A plain reload writes nothing (R2-M8).
  • Sanity gate before any write (R2-B5): if the sheet produced zero staff rows, or zero rows matched an account, write nothing (summary and records) and show a notice. A broken or unpublished sheet must never look like "everyone left". This is the same failure shape as the Supply Low List incident.
  • Going stale is mild. Dates repeat yearly, so an old summary still predicts correctly; it misses only hires and leavers since the last manager load. The card shows "Staff list updated N days ago" (amber past 30 days, with a link to the Directory). A leaver can linger on the card until the next manager load (accepted). new Date(updatedAt) is safe because it's a full ISO instant; there's a code comment so nobody "fixes" it (R2-L11).

Matching sheet rows to accounts

  • The Directory reads users (managers can read all) and matches each current sheet row by trimmed, lowercased email.
  • Duplicates on either side (two rows or two accounts with one email) → that email is skipped and shown in a separate "Couldn't link to an account" section of the Celebrations page (managers only). Rows with no account are listed there too (R2-L3).
  • Leavers come only from a positive match (R2-B5): a uid gets the leaver write only when a sheet row that matches it is marked P (or OUTDATED). A uid that's merely unmatched or skipped is left untouched, never flipped. Never derive leavers by subtraction.
  • Accepted risk (D5, Christie): a user can change the email on their own users doc (the self-update rule doesn't pin it), or create an account with a coworker's unused email. Either way they could be matched to a coworker who has no account and receive that coworker's greeting record. It takes deliberate use of the browser console and exposes one person, so it's too unlikely to justify editing the shared users rule. Not fixed.

New rules block (the only rules change)

// ── staffCelebrations: birthdays + work anniversaries for Tinker HQ ──
// _summary = everyone's dates for the admin/manager card. {uid} = one person's own record.
// Written only by admins/managers from the Staff Directory. Never deleted.
match /staffCelebrations/{docId} {
  function isCelebrationRecord(d) {
    return d.keys().hasOnly(['name', 'birthday', 'startDate', 'current', 'updatedAt'])
      && d.keys().hasAll(['current', 'updatedAt'])
      && d.current is bool
      && d.updatedAt is string && d.updatedAt.size() <= 30
      && (!('name' in d)      || (d.name is string      && d.name.size() <= 120))
      && (!('birthday' in d)  || (d.birthday is string  && d.birthday.size() <= 10))
      && (!('startDate' in d) || (d.startDate is string && d.startDate.size() <= 40));
  }
  function isCelebrationSummary(d) {
    return d.keys().hasOnly(['staff', 'updatedAt', 'updatedBy'])
      && d.keys().hasAll(['staff', 'updatedAt', 'updatedBy'])
      && d.staff is list && d.staff.size() <= 300
      && d.updatedAt is string && d.updatedAt.size() <= 30
      && d.updatedBy == request.auth.uid;
  }
  allow get: if !isKiosk() && isActiveUser() && request.auth.uid == docId;
  allow get, list: if !isKiosk() && isManagerOrAbove();
  allow create, update: if !isKiosk() && isManagerOrAbove()
    && (docId == '_summary' ? isCelebrationSummary(request.resource.data)
                            : isCelebrationRecord(request.resource.data));
  // no delete
}
  • Block-local helpers follow the /curriculum precedent (R2-L8). !isKiosk() is on every grant.
  • Summary rows aren't field-checked by the rules (lists can't be iterated). The writer's unit tests pin the row shape instead.
  • No delete, ever. A wrong record can only be overwritten (with the leaver shape), never removed outside the Console. That's deliberate, like timeclock_reminder_log (R2-L10).

HQ: what people see

  • Everyone (rules refuse the kiosk; no client kiosk check needed, R2-L4): GET staffCelebrations/<firebase.auth().currentUser.uid> (R2-B2). Missing doc, permission-denied or current:false → nothing shown, no visible error.
  • Admin/manager also: GET _summary → the "🎉 Coming up" card (next 60 days, milestones striped), and day-of confetti for anyone's celebration (D1).
  • One pop-up, built from everything (R2 Codex-8): gather all qualifying events first: the Tinker / Clay Hub studio birthdays, the person's own birthday or milestone (today or last 7 days), and (admin/manager) anyone's celebration today. Then deduplicate, so an admin's own birthday isn't listed twice. Show one pop-up: own greeting first, then studio birthdays, then others.
  • "Once" (R2-M1): one localStorage key per celebration actually shown, keyed by its occurrence date (the observed date, so Feb 28 for a Feb 29 birthday in a non-leap year): celebrated:<uid>:<birthday|anniv-10y|…>:<YYYY-MM-DD>. Sunday's birthday shown on Wednesday doesn't show again on Thursday. A birthday shown today doesn't suppress a milestone three days later.
  • "Today" means the device's local date, same as the rest of HQ (R1-8, declined Denver-zone).
  • The card's names go through a new escapeHtml() (copied from the Directory; HQ has none) (R2-L2). The pop-up already uses textContent.
  • Demo mode (no Firebase) keeps the existing if (!firebaseInitialized || !currentUser) return; guard.

Firebase safety checklist

  • New collection staffCelebrations: rule added, tested and deployed through the studio-hub guard (sha phrase) before any code writes to it.
  • tinker-hq-apps rules affect every staff app. The change only adds one new match block; no existing block or helper is edited.
  • Writes: whole-doc set()s on docs owned solely by this feature, awaited, empty fields stripped, only when changed, behind the sanity gate. Never appData.
  • No deletes. No bulk import. Nothing to snapshot first; the first write creates the collection.
  • Full studio-hub npm test passes before the rules deploy and before the HQ deploy.
  • Netlify deploys (Christie's OK each, clean pushed tree, sha as message): Staff Directory once, HQ once.

Not in this plan (tracked separately)

  • Unpublishing the Staff Info sheet (option 2 recommended). It also decides what staff see in the Staff Directory (addresses, emergency, medical).
  • Old Staff Directory cards don't escape sheet text.
  • Tinker Ticker: out of scope.
