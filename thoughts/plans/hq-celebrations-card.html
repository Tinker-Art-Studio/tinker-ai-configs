Plan: Tinker HQ shows admins and managers what's coming up

Apps: Staff Directory (~/tinker-staff-directory) + Studio Hub / Tinker HQ (~/studio-hub) · Drafted: Oct 1 2026 · v1 · execution-ready: false (waiting on Christie's review and decisions D1–D3)

Goal: when an admin or manager opens Tinker HQ, a "Coming up" card lists every staff birthday and work anniversary in the next 60 days, with 5- and 10-year (every 5th) anniversaries highlighted. Staff accounts never see it, and the database rules stop them from reading the data even if the page had a bug.
Why: Christie missed Anika's 10th anniversary (Aug 20 2026). HQ is the app she opens every day, so the reminder belongs there, not only in the Staff Directory.
Depends on: Phase 1 (Staff Directory Celebrations page, branch claude/celebrations @ 53d5c17): it provides js/celebrations.js, the date logic this plan reuses.

What is wrong today

  • HQ's birthday alert has never worked. checkCelebrations() in studio-hub/js/app.js reads staffDirectory/appData→staff. The Staff Directory never writes a staff field. It writes only {offboardingData, lastUpdated}, using set(), which replaces the whole doc on every offboarding save. So HQ always finds an empty list and shows nothing. (Nothing was lost: staff data has always lived in the Google Sheet.)
  • That code also only knew MM/DD birthdays, looked only 7 days ahead, and had no work anniversaries.
  • HQ can't read the Google Sheet directly. The sheet's "published to web" link is going away (separate work, see below), and pointing a second app at it would make that harder.

Design

Data path: a small summary in Firestore, written by the Staff Directory

When someone who can write (admin, manager, or staff with appAccess: staff-directory) loads or refreshes the Staff Directory, it saves a summary to a new doc in the existing staffDirectory collection: staffDirectory/celebrations.

{
  staff: [ { name: "Anika …", birthday: "8/3", startDate: "8/20/2016" }, … ],   // current staff only
  updatedAt: "2026-10-01T15:00:00.000Z",
  updatedBy: "<uid>"
}
  • Only what the card needs: name, birthday as month/day (no birth year), and start date. No emails, phones, addresses or anything else from the sheet. Start dates stay in the sheet's own wording (e.g. "July 2022") so the shared date logic reads them identically in both apps.
  • Written only when it changes: the app compares against what it last read and skips the write if nothing changed, so opening the Directory doesn't write every time.
  • A whole-doc set() is correct here. The summary replaces itself entirely each time. It's a separate doc from appData, so it can never clobber offboarding progress (and vice versa).
  • Going stale is mild. Birthdays and anniversaries repeat yearly, so an old summary still predicts correctly. It only misses people hired or offboarded since the last time a manager opened the Directory. The card shows "Staff list updated N days ago", and goes amber past 30 days with a link to open the Directory.

Who can see it: rules first, page second

LayerWhat enforces "not staff"
Firestore rules (unchanged)match /staffDirectory/{docId}: read only if isManagerOrAbove() || hasAppAccess('staff-directory'). A plain staff account gets permission-denied on the summary. No rules change; no guard deploy.
HQ pageThe card is built only inside renderAdminDashboard(), which runs only for role === 'admin' || 'manager'. renderStaffDashboard() never builds it or fetches the summary.

Staff who hold the staff-directory app-access override can read the summary (they can already read and edit all of staffDirectory), but they get the staff dashboard, so they don't see the card.

HQ card

  • Title "🎉 Coming up". Rows: date · name · "🎂 Birthday" / "🎉 3 years" / "⭐ 10 years" · "in 12 days". Milestone rows get the same orange stripe as the Directory.
  • Empty state: "No birthdays or anniversaries in the next 60 days." No summary yet: "Open the Staff Directory once to load the staff list" (with link).
  • "See all →" opens the Staff Directory.
  • Placement: right after the quick-stats row and before Priority Alerts. Collapsible, like the alert feed (state kept in localStorage).

Shared date logic

Copy tinker-staff-directory/js/celebrations.js to studio-hub/js/celebrations.js unchanged, with a header line naming the source file. Two copies of ~200 lines are simpler than a shared package for two static sites. Both copies carry the same tests, so drift shows up as a failing test.

Decisions for Christie

D1 — Birthday-day pop-up in HQ. HQ has an old "It's X's birthday! 🎂" confetti pop-up that never fired, because of the bug above. Repointing HQ at the summary would switch it on for admins and managers on the day itself. Recommend: keep the pop-up for milestone anniversaries only, and show birthdays on the card only. Alternatives: keep it for birthdays too, or remove it. The Tinker / Clay Hub studio-birthday pop-ups are unchanged either way.
D2 — What the card lists. Recommend: birthdays + every anniversary for 60 days, milestones highlighted (matches the Directory). Alternative: anniversaries only, since birthdays are already on the shared calendar.
D3 — Ship Phase 1 now or with 2a. Each Netlify deploy costs credits. Recommend: ship Phase 1 + 2a in one Staff Directory deploy. Alternative: deploy Phase 1 now so the Celebrations page is live today (one extra deploy).

Phases

2a — Staff Directory writes the summary

  • firebase-data.js: loadCelebrationsSummary() and saveCelebrationsSummary(summary) on staffDirectory/celebrations. The save is awaited; errors are logged and shown as a small non-blocking notice, never a silent pass.
  • app.js: after fetchStaffData(), if the user can write, build the summary (current staff; drop blank fields; birthday reduced to month/day). Write only if it differs from the stored one.
  • Never written by read-only staff (the rules would refuse anyway).
  • Tests: summary builder (no birth year, no extra fields, blanks dropped, past/OUTDATED excluded) in tests/.
Given a manager opens the Directory → the summary exists with only name/birthday(M/D)/startDate for current staff.
Given nothing changed since the last open → no write happens.
Given a read-only staff user opens the Directory → no write is attempted.

2b — Tinker HQ card

  • Add js/celebrations.js (copy) and load it in index.html; add it to scripts/build-dist.sh (otherwise the deploy ships without it, and check-live should catch that).
  • renderAdminDashboard(): build the card and fetch staffDirectory/celebrations. Escape every name (HTML-escape helper; names come from a Google Form).
  • checkCelebrations(): read the summary instead of appData.staff, per D1. Skip the read entirely for non-admin/manager users (today it fires and fails with permission-denied for plain staff).
  • Tests: copy the date-logic tests; add a rules test pinning that a plain staff user cannot read staffDirectory/celebrations and a manager can (tests only, no rules change).
Given an admin/manager opens HQ → "Coming up" card lists the next 60 days; milestones highlighted.
Given a staff user opens HQ → no card, and no request for staffDirectory/celebrations in the network log.
Given the summary is 31+ days old → card shows an amber "updated 31 days ago" with a link to the Directory.

Firebase safety checklist

  • New collection? No: a new doc in staffDirectory, covered by the existing rule. No rules edit, no guard deploy.
  • Writes: one whole-doc set() on a doc owned solely by this feature; awaited; empty fields stripped; never touches appData.
  • No deletes, no bulk import. Nothing to snapshot first.
  • Studio Hub's npm test (rules suite) passes before the HQ deploy, even though rules are unchanged.
  • Deploys (each needs Christie's OK, from a clean pushed tree with the sha as the message): Staff Directory once (D3) → HQ once.

Not in this plan (tracked separately)

  • Unpublishing the Staff Info sheet. The published CSV link exposes addresses, emergency contacts, medical and background-check columns to anyone who has the link. This plan doesn't depend on that link, so the fix can go either way.
  • Old Staff Directory cards don't escape sheet text. Names and positions go into the page as HTML; Celebrations code escapes, the old cards don't.
  • Staff Directory deploy publishes the whole repo folder (incl. tests/, PROJECT-SUMMARY.md). Moving it to a dist/-only deploy like Classbook/Ticker/HQ is a small follow-up.
