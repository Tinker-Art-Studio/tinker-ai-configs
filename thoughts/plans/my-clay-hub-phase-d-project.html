Choices made here (Christie can overrule any)

#ChoiceWhy
C1Storage bucket in us-central1, versioning on, noncurrent versions deleted after 90 days.Same region as the functions and the vault bucket; a no-cost-tier location; the lifecycle rule mirrors tinker-hq-apps' bucket.
C2Vault export goes to its own bucket, my-clay-hub-vault-exports, in the existing tinker-hq-vault project — not a folder inside tinker-hq-vault-backups.Bucket-level permissions: a folder would let my-clay-hub's export identity write next to (and potentially over) staff-app backups. A separate bucket keeps the two apart, as the two projects are.
C3Vault export runs on Google's side: a weekly Cloud Scheduler job starts a Firestore managed export, as a dedicated vault-export@ service account. Keeps 8 weeks (lifecycle: delete after 56 days). A Cloud Monitoring alert emails Christie if the job fails.D13 forbids backup.js (it depends on Christie's personal login, the cause of the invalid_rapt outages). Scheduler calls Google's API with its own identity: no code, no key files. Weekly and 8 kept matches tinker-hq-apps' vault.
C4The new guard is adapted from studio-hub's by copying it and changing its pinned values, then running its own copy of the test suite — not by making studio-hub's script serve both repos."Pinned to this repo and project" (parent plan D-3). A shared script would put both projects' deploys behind one file and one set of control-file checks; a mistake there hits both.

D-2 — Repo setup: deny-all rules, a predeploy check, and emulator tests execution-ready: false

Acceptance criteria

  • npm test in my-clay-hub starts the Firestore and Storage emulators under the project demo-my-clay-hub and runs the rules suite. It refuses to run if the project ID doesn't start with demo- or if an emulator host variable is missing (so a test can never reach production).
  • The first tests: a signed-in stranger can do nothing — can't read, list, create, update or delete in members, bookings, settings or an arbitrary collection, and can't read or write any Storage path. The same for a signed-out visitor. Each "denied" test has a positive pair proving the harness can see an allowed action (an admin-context seed write succeeds), so a broken harness can't pass by denying everything.
  • firebase.json wires a predeploy check for firestore and storage that refuses any deploy not started by this repo's guard with a matching approved commit (adapted from studio-hub's predeploy-check.sh; it names this repo's guard).

Files: package.json (devDeps @firebase/rules-unit-testing, a test runner — node --test to match the Membership Manager repo, no Jest), package-lock.json, firebase.json, .firebaserc (default <PROJECT_ID>), firestore.rules and storage.rules (both allow read, write: if false on everything), firestore.indexes.json (empty), scripts/predeploy-check.sh, tests/rules/*.test.js.

D-4 — The weekly vault export (C2, C3) execution-ready: false

Acceptance criteria

  • Once a week, a full Firestore export of <PROJECT_ID> lands in gs://my-clay-hub-vault-exports/weekly/… in the tinker-hq-vault project, with no laptop and no personal login involved.
  • Exports older than 56 days are removed automatically, so about 8 are kept.
  • If the weekly job fails, Christie gets an email.
  • The export identity can start exports and nothing else; it cannot read or delete anything in the vault, and nothing in my-clay-hub can touch tinker-hq-vault-backups.

Christie's Console steps (Claude writes the exact values live, then records them):

  2. On that bucket only: grant the my-clay-hub Firestore service agent (service-<number>@gcp-sa-firestore.iam.gserviceaccount.com) the minimum role Google's export docs require — confirmed at execution time; nothing on tinker-hq-vault-backups.
  3. <PROJECT_ID> → IAM → create vault-export@<PROJECT_ID> with only Cloud Datastore Import Export Admin on this project.
  4. Cloud Scheduler (region us-central1) → job "weekly vault export", Sundays 2:00 AM America/Denver, HTTP POST to the Firestore Admin exportDocuments method for (default), output gs://my-clay-hub-vault-exports/weekly, auth as vault-export@ (OAuth). This is Google's scheduler calling Google's API under that identity — set up in the Console by Christie, never a request sent from this laptop.
  5. Cloud Monitoring → alert policy on that job's failed runs → email Christie.
  6. Run the job once now; confirm a dated export folder appears.
