B3 — Permanent member ID (memberId) execution-ready: false (after B1, B0)

Acceptance criteria:

  • Every member doc has a memberId: m_ plus a random UUID. It's never derived from the email, and it's never changed once set (enforced by B0 and by the app).
  • New members get one when they're created.
  • Existing members get one from a one-time "Assign member IDs" tool, which:
    • reads the raw clayHub_members docs;
    • downloads a snapshot of {docId, data} for every doc first;
    • assigns each ID in a transaction against that exact doc ID, which re-reads and skips the doc if an ID is already there;
    • reports how many were assigned, how many were already set, and any failures;
    • is safe to run again.
  • Nothing assigns an ID on page load.
  • The tool refuses to run unless members loaded from Firestore. It's shown only to admins; that's a UI courtesy, and B0 is the real protection.
  • The in-app id is unchanged. The in-memory variables that were called memberId are renamed to recordId, so the two meanings can't be confused.
  1. Tests first:
    • Unit: newMemberId() has the right format, gives two different values on two calls, falls back to crypto.getRandomValues, and throws if neither source exists (it must never quietly give undefined).
    • Unit: planMemberIdBackfill(rawDocs) picks only docs without a memberId; a malformed or duplicate existing ID is reported, not overwritten.
    • Unit: planDocWrite(snapshot, current, del, {protectedFields:['memberId']}) never deletes or changes a protected field, and warns when one is dropped. Waitlist saves pass no protected fields.
    • Emulator, real functions: two concurrent backfills end with one ID per member; an ordinary save from a record that lacks memberId leaves it untouched; the not-found fallback preserves it; a returning member keeps it; both imports and a console-script-style save keep it.
  2. Code:
    • memberId is added on both creation paths. A returning member keeps theirs.
    • protectedFields for members lands in the same commit as the tool, because it's what holds the design together.
    • After each transaction, update members[i].memberId, storedCopies and localStorage, and count results outside the retryable callback.
    • The recordId rename is a mechanical pass.
  3. After the backfill: creating or re-creating a member doc without a valid memberId is refused by the app.

B4 — Change a member's email (redesigned) execution-ready: false (after B3)

Acceptance criteria:

  • "Change email" on the member card asks for the new address (checked for format), confirms, and then runs one Firestore transaction that:
    1. reads the old doc (the server copy) and the target doc (docIdForEmail(new));
    2. aborts if:
      • the old doc is missing, retired, or has no memberId;
      • the target doc exists in any state (live, retired, or a ./_ collision);
      • the target ID equals the old ID;
    3. writes the new doc built from the server copy, with the new email, the same memberId, and no retirement fields;
    4. updates the old doc with {retired:true, retiredAt, replacedBy};
    5. updates the member's matching clayHub_waitlist doc's email if one exists, so they don't reappear on the waitlist.
  • If it aborts, nothing changes and staff see why ("That email already belongs to name", "Try again", and so on).
  • Retired docs are dropped in loadCollection before they reach records and docIdByEmail, and their doc IDs go into retiredDocIds. saveRecordChanges refuses any write to a retired doc ID (reportSaveProblem('retired')), so a stale tab can't quietly save into it. Because lists, counts, alerts and the shelf map all read members, dropping retired docs there covers all of them.
  • After a successful commit, update the in-memory member, currentMember, any open workflow, storedCopies (new doc from what was written; old ID removed), docIdByEmail, retiredDocIds and localStorage. If it fails, change none of them.
  • An action-log entry records "Email changed from X to Y by staff".
  1. Before B4 ships: confirm in the Console (or with a read-only query from the tool) that no doc already has retired set. Then land the loader filter and the retiredDocIds guard, in the same commit as the change-email flow.
  2. Tests first:
    • Unit: planEmailChange refuses a bad format, the same address, a known duplicate, and a missing memberId.
    • Emulator, real functions: two staff moving two different members to the same new email at once → exactly one wins, and the other aborts with no damage; the target exists retired → abort; a.b@ → a_b@ (same doc ID) → abort; the target is a ./_ collision with another member → abort; a stale tab saving the old record after the change → refused; the waitlist email is updated; a failure part-way → no doc and no cache changed; the new doc carries the server copy's latest fields.

B2 — Editable, tidy phone (Q2) execution-ready: false

Acceptance criteria:
