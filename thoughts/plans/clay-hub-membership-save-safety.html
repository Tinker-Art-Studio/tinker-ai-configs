What exists today (verified in code at b0f4180)

  • The data layer is sound.
    • saveRecordChanges (js/firebase-data.js:81-122) diffs each record against storedCopies, using planDocWrite (js/member-status.js). It writes with update(), or set(…,{merge:true}) for a new doc.
    • It refuses to write a collection that didn't load (:83-86).
    • It returns true or false, and raises a red banner on failure (reportSaveProblem).
  • Callers don't wait for the result.
    • saveMemberChanges (js/app.js:912-918) fires and forgets, and so do the page-load saveLocalData() (:697, :701-712) and about 30 other callers.
    • The success messages don't depend on the result:
      • "Saved!" on the member card (:2437, and the waitlist card at :2405);
      • workflow "Save Progress" (:3150);
      • "…completed" (:3277);
      • "…logged" (quick log, around :3375).
  • The Refresh gap: "↻ Refresh Waitlist" re-runs loadData. collectionLoaded is only reset after a successful get() (firebase-data.js:59), so a failed reload leaves the old "loaded" flag in place, and the page-load save can then write the localStorage copy.
  • No permanent ID.
    • The in-app id is member-${Date.now()} for new members (:2156, :2227), or backfilled from the email for legacy docs (:658, :687).
    • The doc ID is the email, lowercased, with . and / → _ (firebase-data.js:41-43).
    • id is used everywhere as the in-app lookup key (members.find(m => m.id === …)), and in workflows.*.memberId.
  • Email can't be changed. The card shows it read-only (:1709). There's no doc-delete path anywhere. docIdByEmail (firebase-data.js:38, :65-78) maps emails to real doc IDs and warns on duplicates.
  • Phone is entered once, in Add Member (:2207), or copied from the waitlist or sheet. It's read-only afterwards (:1710) and never tidied. The door keypad code is the "last 4 of cell" (keypadCode).
  • Tests: node --test tests/ runs 72 unit tests. tests/emulator/member-saves.emulator.cjs runs 4 emulator tests against studio-hub's real rules (the command is in the repo's CLAUDE.md).

Phases

B1 — Honest saves execution-ready: false

Acceptance criteria:

  • Every button that says a save worked ("Saved!", "…completed", "…logged", Save Progress) says so only after Firestore confirms it.
  • If a save fails, the button shows "Not saved — try again", the red banner appears, and the change stays on screen so staff can retry.
  • Automatic page-load transitions are awaited too, so a failure shows up.
  • The Refresh gap is closed: a failed reload marks the collection "not loaded" before anything can save.
  1. Tests first (emulator, extending member-saves.emulator.cjs):
    • a save rejected by the rules returns false;
    • after a failed reload, a save of that collection is refused and nothing is written;
    • a successful save returns true.
    Unit tests: a small saveOutcomeLabel(ok) helper, so the button text can't drift.
  2. saveMemberChanges becomes async and returns the result of saveMemberToFirestore. saveLocalData returns Promise.all of both saves.
  3. The five user-facing success paths await the save and set their text from the result. The page-load saveLocalData() is awaited.
  4. The other callers (auto-transitions, checklists, alerts) keep going on failure, because the banner already reports it. await is added where the next step depends on the save.
  5. In loadCollection (firebase-data.js), set collectionLoaded[collection] = false before the get().

B2 — Editable, tidy phone execution-ready: false (needs Q2)

Acceptance criteria:

  • Staff can edit a member's phone in Member Details.
  • A phone with fewer or more than 10 digits (or 11 starting with 1) is refused, with a clear message.
  • Phones display as (303) 555-1234.
  • A "Phones missing" filter or count shows who still needs one. Christie fills these in (parent plan D5).
  1. Tests first: phoneDigits() and formatPhone() (valid, 11-digit, too short, letters, blank).
  2. A phone input on the Member Details section, saved through the normal change-only save. A blank phone is allowed and means "none on file", but it's counted as missing.
  3. Existing phones are not rewritten in bulk. They're tidied only when staff next edit them. The display formats them without saving.

B3 — Permanent member ID (memberId) execution-ready: false

Acceptance criteria:

  • Every member doc has a memberId: random (crypto.randomUUID(), prefixed m_), never changed once set, and never derived from the email.
  • New members get one when they're created.
  • Existing members get one from a one-time "Assign member IDs" tool, run by Christie. It downloads a JSON snapshot of every member doc first.
  • Nothing assigns a memberId on page load. Two open browsers must never give one member two different IDs.
  • The existing in-app id stays as it is. It's the app's internal lookup key, and memberId is the cross-app identity.
  1. Tests first:
    • newMemberId() has the right format, and two calls give two different values.
    • planMemberIdBackfill(members) lists only members without a memberId, and never includes one that already has one.
    • Emulator: the backfill writes each doc in a transaction that re-reads the doc and skips it if a memberId appeared meanwhile, so two concurrent runs end with one ID per member.
    • Emulator: a normal change-only save never changes or deletes an existing memberId, even when the in-memory record lacks it.
  2. memberId is added to both creation paths (Add Member, Move to Onboarding). A returning member keeps theirs; returningMemberRecord already keeps stored fields.
  3. Guard: planDocWrite never deletes or changes memberId. That's written as an explicit rule in the helper, with its own test.
  4. The tool:
    • Admin-only, under Settings or Tools, alongside "Import Member Since".
    • It shows the count, downloads the snapshot, runs the transactions, and reports how many IDs were assigned, how many were skipped as already set, and any failures.
    • It's safe to run again: a second run assigns nothing.
Scenario: backfill runs twice at once Given two staff run "Assign member IDs" in two browsers at the same moment When both finish Then every member has exactly one memberId, and the second run reports "already set" Scenario: an ordinary save Given Jane has memberId m_7Q… in Firestore but an older in-memory copy lacks it When staff edit her notes and save Then m_7Q… is untouched

B4 — Change a member's email execution-ready: false (needs B3, Q3)

Acceptance criteria:

  • On the member card, "Change email" asks for the new address (checked for format) and confirms.
  • It then, in one atomic batch:
    • writes the member's full record under the new email's doc ID, with the same memberId;
    • marks the old doc retired: true, with retiredAt and replacedBy: <new email>. It isn't deleted.
  • It refuses if a live (not retired) doc already exists for the new email, or if the member has no memberId yet.
  • After it runs, Membership Manager shows the member once, under the new email. Retired docs are skipped on load everywhere: lists, counts, alerts and the shelf map.
  • An action-log entry records "Email changed from X to Y". localStorage is updated to match.
  1. Tests first:
    • Unit: planEmailChange(member, newEmail, liveEmails) refuses a duplicate, a bad format, a missing memberId, and "same as current".
    • Emulator: the batch creates the new doc and retires the old one, or does neither; a retired doc is skipped by the loader; after a change, the old email's doc can't come back live through a later save.
  2. The loader skips retired === true (loadMembersFromFirestore) and keeps retired docs out of docIdByEmail's duplicate warnings. This lands first, on its own, because it's harmless while no doc is retired.
  3. The batch write uses the web SDK's db.batch() with set(newRef, fullRecord) and update(oldRef, {retired:true, retiredAt, replacedBy}). Afterwards, storedCopies and docIdByEmail are updated from the result.
Scenario: change email Given Jane (memberId m_7Q…) at jane@old.com When staff change her email to jane@new.com Then one batch leaves jane@new.com live with m_7Q… and jane@old.com retired; the list shows Jane once Scenario: duplicate Given a live member already uses bob@x.com When staff try to change Jane's email to bob@x.com Then nothing is written and the message names the other member Scenario: failure mid-way Given the batch fails (network) Then neither doc changes and staff see "Email not changed — try again"

Order, and what My Clay Hub needs

  • Order: B1 → B2 → B3 → B4, one commit per step, each deployed by push and tested in the live app before the next. B4's "skip retired docs" loader change can ship early.
  • For the parent plan's Phase E link: it needs B3 (memberId) and B4 (retired). It already has: calendar-day dates, memberSince, and change-only saves (which fire far fewer triggers).
  • Fields the link must never copy, noted in My Clay Hub's DATA-MODEL.md allowlist: keypadCode and keypadUserId (the door code), staffNotes, notes, application, actions, the full phone, the shelf fields, and any leftover billing fields.
