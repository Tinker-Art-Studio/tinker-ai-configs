Plan: A sub is confirmed only by a manager, on the request's real dates

App: Tinker Ticker (~/tinker-timeclock) · Drafted: Sep 29 2026 · v1 · execution-ready: false — awaiting design review, then Christie's written approval to edit the repo.

Goal: when a manager approves time off, a sub is never shown as "Confirmed" unless their shift is on their schedule and they have been emailed. The one button that does both, Mark Confirmed, is always there for the manager and always works.

Scope, per Christie (Sep 29): from here on only. There is no backfill and no change to existing request documents. No rules change, no new collection, no change to the Payroll Tool or the reminder job.

What went wrong (Ivy's request, Sep 29)

This reverses an Aug 29 decision. The ticker-timeoff-email-and-sub-assignment plan's log records that "either the requester or an admin can set" confirmed, and that "one shared flag is sufficient" (a separate requesterPreConfirmed flag was dropped). Today showed that the shared flag lets a requester produce a "Confirmed" that has no shift and no email. Christie chose (Sep 29) to remove the requester's checkbox entirely. A requester who has lined up a sub can say so in the existing Coverage Notes box. No new field is added.

Phases

Phase 1: Only a manager can confirm a sub

Acceptance (user outcomes):

  • A staff member filling in a time-off request can add or remove proposed subs, but there is no way to mark one confirmed. The checkbox is gone. The Coverage Notes box already invites "I texted Sam… she can cover Tuesday" (index.html:722), so no new wording is needed there.
  • Every sub on a NEW request is saved un-confirmed, and a manager sees Not confirmed · Mark Confirmed on it.
  • Editing an existing request never changes a sub's confirmed state. A sub that was confirmed stays confirmed with its record, and one that wasn't stays unconfirmed. Removing a sub with × still reverses its coverage as today.
  • On their own request, the requester sees no Mark Confirmed button. An unconfirmed sub reads "Not confirmed · a manager confirms coverage". Undo on an already-confirmed sub stays as it is today (record-less subs clear, recorded ones go to a manager via handOffSubRemovalToManager).

Changes:

  • Delete toggleFormSubConfirmed and the checkbox label in renderTimeOffSubs.
  • addTimeOffSub keeps confirmed: false. The edit-load mapping (:7068) keeps carrying the document's confirmed unchanged. With nothing able to flip it, the save (:7372) carries it through, and reconcileEditedProposedSubs / carryConfirmedSubs behave as before (they only react to a confirmed→unconfirmed change or a removal, and now only removal can cause one).
  • Detail view: for a sub that is NOT confirmed, only isAdmin gets the Mark Confirmed button. The owner keeps Undo for a confirmed sub.
  • handleSubConfirmToggle: refuse the confirm branch for a non-manager, with a clear message (defence against a stale tab / old service-worker copy that still renders the button). Un-confirm stays open to the owner.
Happy: Given Ivy submits a request naming Sam as sub, when a manager opens it, then Sam shows "Not confirmed" with a Mark Confirmed button, and after Confirm & Add to Schedule Sam's schedule has the shift and both emails send (unchanged path).
Edge: Given an existing request whose sub was ticked "They agreed" before this ships (confirmed, no subUid), when Ivy edits the reason and saves, then the sub is still confirmed, with no change to it and no reversal attempted (no backfill, per scope).
Edge: Given a manager-confirmed sub with a schedule record, when Ivy edits the request (status submitted/under_review) and saves, then the sub keeps confirmed, subUid and appliedOverrides (reconcile's "linked" carry). When she removes that sub with ×, the reversal runs as today.
Failure: Given a stale tab that still shows Mark Confirmed to the requester, when they click it, then they get "Only a manager can confirm a sub" and nothing is written.

Phase 2: A sub always covers the request's real dates

Acceptance:

  • However the requester orders things (sub first, date later, or dates edited afterwards), a saved sub's dates are the request's dates at the moment of saving.
  • Mark Confirmed never stops with "no covered dates" because the stored dates drifted. If a sub's stored dates overlap none of the request's dates, the confirm dialog lists the request's own dates, and the manager can see them before writing anything.

Changes:

  • Save (:7372): each sub's dates = the request's valid dates being saved, not the add-time copy. The form offers no per-sub date choice today (every sub gets all dates when added), so no choice is lost. The Kayleigh-mornings / Shelley-afternoons split is handled by times in the confirm dialog, not by dates.
  • getSubCoverageDates: an array whose overlap with the request's dates is EMPTY falls back to the request's full dates, like the string/missing case already does. A partial overlap is still honoured. The no-roster-match path at :7876 already uses this fallback, and this change makes it the rule everywhere.
Side effect to know about (not a backfill): the fallback is a code change, not a data change, but it also makes Mark Confirmed work on existing requests whose sub dates had drifted. Ivy's is one of them: once shipped, a manager could Undo → Mark Confirmed there instead of adding the shift by hand. If the shift was already added by hand, Mark Confirmed will see it and ask "already has a shift… Overwrite?" (:7988), and the answer is Cancel.
Happy: Given Ivy adds Sam as sub and THEN picks Oct 3, when she submits, then Sam's dates is ["2026-10-03"] and Mark Confirmed writes Oct 3.
Edge: Given a request edited from Oct 3 to Oct 4 while un-approved, when saved, then the sub's dates become ["2026-10-04"]. A sub already confirmed on Oct 3 keeps its appliedOverrides record for Oct 3, and the reversal uses that record, not dates (unchanged).
Edge: Given an old request whose sub has dates: [], when a manager clicks Mark Confirmed, then the dialog lists the request's dates and the write proceeds only on Confirm.
Failure: Given a request with no valid dates at all, then the existing "no covered dates" refusal still fires (the fallback of an empty list is empty) and nothing is written.

Phase 3: "Coverage: Secured" warns while a sub is unconfirmed

Acceptance:

  • When a manager picks "Coverage: Secured" and any proposed sub is not confirmed, they see: "Sam isn't confirmed yet, so nothing has been added to their schedule and they haven't been emailed. To do that, use Mark Confirmed next to their name. Mark coverage Secured anyway?"
  • Cancel leaves the status unchanged and the dropdown shows the old value. OK saves the label as today.
  • No warning when every sub is confirmed, when there are no proposed subs (coverage arranged some other way), or for Pending / Partial / Not Needed.

Changes: updateCoverageStatus reads the request from allTimeoffRequests (the list the detail view was drawn from). On Cancel it re-renders the detail so the select snaps back.

Happy: Given a request with Sam unconfirmed, when the GM picks Secured and clicks Cancel, then nothing is written and the dropdown still reads Pending.
Edge: Given two subs, one confirmed, when Secured is picked, then the warning names only the unconfirmed one.
Failure: Given the request isn't in the in-memory list (stale view), then no warning can be computed, and the label is saved as today. The warning is advisory only; it never blocks a manager.

Firebase safety checklist

  • Rules: no change. timeclock_timeoff and timeclock_schedules rules are untouched. Note: rules let a staff member update any field of their own request, so this fix is a UI guarantee, not a rules guarantee. Tightening that is out of scope (it would need a rules release through the guard).
  • New collection: none. Bulk write/delete/import: none, so no snapshot needed.
  • Write shape: the request save is unchanged apart from each sub's dates value. No undefined is introduced (dates is always an array). The confirm path's transaction is unchanged.
  • Spot-check after deploy: one new request's proposedSubs[0] in the console shows confirmed: false and dates equal to the request's dates.

Completeness check: what if this stops part-way?

Each phase is a UI-only change in its own commit and is safe alone. Phase 1 without 2 still hits the "no covered dates" stop on drifted requests (today's behaviour). Phase 2 without 1 still lets requesters mark subs Confirmed (today's behaviour). Nothing ships until all three are committed, tested and reviewed.
