Plan: A sub is confirmed only by a manager, on the request's real dates

App: Tinker Ticker (~/tinker-timeclock) · Drafted: Sep 29 2026 · v2 after design review round 1 (Claude + Codex, Sep 29: both "not ready"; every finding is folded in or answered in the Decisions Log) · execution-ready: false — D1–D3 answered by Christie (Sep 29); waiting on design review round 2, then her written approval to edit the repo.

Goal: a sub shows as Confirmed only after a manager used Mark Confirmed. That step writes the shift to the sub's schedule and sends the confirmation email, or, for a name the roster can't match, confirms with the amber "add their shift manually" note. A requester can't produce a "Confirmed" of any kind. When a manager confirms, they choose from the request's real dates.

What "Confirmed" does NOT promise (review round 1, Codex): that the email arrived. The email is sent after the confirmation lands and is fire-and-forget (js/app.js:9274), exactly as today. A sub with no email address on file gets none. Making delivery part of confirmation is a bigger redesign and is out of scope.

Scope, per Christie (Sep 29): from here on only. Nothing rewrites existing request documents. No rules change, no new collection, no change to the Payroll Tool or the reminder job.

Decisions for Christie — ANSWERED Sep 29: D1 = (a) refuse, D2 = yes, D3 = yes

D1. A requester changes the dates after a manager has confirmed the sub. Today (pre-existing), on a request that isn't approved yet, the sub stays "Confirmed" with a shift on the OLD date (round 1, Codex). Options:

  1. (Recommended) Refuse the save: "Sam is confirmed to cover Oct 3. Ask a manager to Undo Sam first, then change the dates." This is simple, and nothing moves on anyone's schedule without a manager.
  2. Save it, and automatically take Sam's Oct 3 shift off and un-confirm Sam (a manager then re-confirms for Oct 4).

(Approved requests aren't affected: editing one already sends it back to review and takes every confirmed sub's shift off.)

D2. Pick dates when confirming. (Recommended) The confirm box lists the request's dates as checkboxes, pre-ticked with the dates the sub was proposed for (or all of them, if those don't line up, which was Ivy's case). The manager unticks any date the sub isn't covering. This replaces v1's "overwrite every sub's dates on save", which both reviewers flagged: it would erase real "she can cover Tuesday but not Wednesday" splits, and it would leave no way to decline one conflicting date without abandoning the rest.

D3. Flag the "Confirmed but nothing on their schedule" state where it already exists. (Recommended) A display-only amber line under such a sub: "Confirmed, but no shift was added to their schedule. Add it by hand, or Undo and use Mark Confirmed." No data is changed. It would show on old requests like Ivy's, which is the point: otherwise they stay a bare green badge forever (round 1, Claude). Say no if you'd rather old requests stay exactly as they look now.

Phases

Phase 1: Only a manager can confirm a sub, and a save can't bring a confirmation back

Acceptance:

  • The request form has no way to mark a sub confirmed. A sub that IS confirmed shows a read-only chip in the form ("Confirmed by a manager"), and removing it with × asks first: "Sam is confirmed and has this shift on their schedule. Removing Sam takes it off and tells a manager. Remove?" (round 1, Claude: the checkbox was the form's only cue).
  • Every sub on a new request is saved unconfirmed.
  • On the non-reset edit path (submitted / under_review), the saved confirmed of each sub is whatever the document says at save time, in both directions. The form can't set it and can't bring it back.
  • The reset path (editing an approved / completed / denied request) is unchanged. It reverses every confirmed sub's shift and un-confirms those whose reversal landed. v1 wrongly said "editing never changes confirmed state" (round 1, Codex).
  • On their own request, the requester sees no Mark Confirmed. An unconfirmed sub reads "Not confirmed · a manager confirms coverage". Undo on a confirmed sub is unchanged (record-less subs clear; recorded ones hand off to a manager).
  • Per D1 (refuse): on the non-reset path, a save whose dates differ from the document's is refused while ANY sub is confirmed on the document: "Sam is confirmed to cover this request. Ask a manager to Undo Sam first, then change the dates." "Differ" means the set of {date, type, partialStart, partialEnd} changes (added, removed, full↔partial, or new partial times), compared against the fresh existingData read that branch already takes. The flexible flag, reason, notes and subs are not dates. This applies to managers editing too (they Undo first). The refusal happens before any reversal runs, so nothing is half-done.

Changes:

  • Delete toggleFormSubConfirmed and the checkbox. Render the read-only chip + the remove confirm.
  • carryConfirmedSubs (js/schedule-helpers.js:1024, called via carryCurrentSubs, js/app.js:8720): drop the hasLink(s) condition so that a form entry claiming confirmed the document doesn't have is always un-confirmed and stripped. reconcileEditedProposedSubs is left alone (its un-tick → reverse branch stays as a guard against an old cached page). Do NOT hard-code confirmed: false at :7372: reconcile would then read every confirmed sub as un-ticked and reverse real coverage on an unrelated edit (round 1, Claude).
  • canToggle becomes isAdmin for Mark Confirmed. The owner keeps Undo on a confirmed sub.
  • Manager checks at the top of the confirm branch of handleSubConfirmToggle, right after the status check (:7850), before the roster match (:7857) so it covers the unmatched branch too, and at the top of submitConfirmSub (round 1, both reviewers).
  • D1 check in handleSubmitTimeOff's non-reset branch, before reconcileEditedProposedSubs's reversals: a small pure helper requestDatesChanged(oldDates, newDates) in schedule-helpers.js with unit tests.
  • D3 (yes): add a matched entry to the amber-note map at :7615 for a confirmed sub with no subUid and no appliedOverrides.
Honest limit. These are app-level guarantees. Rules let a staff member update any field of their own request (firestore.rules:446), and a page running an old cached app.js (the service worker is cache-first, sw.js) has none of these checks until it refreshes. The sw version bump on deploy retires those copies, and D3's amber line is the net for anything that slips through. A rules-level guarantee would need a rules release through the guard and is out of scope.
Happy: Given Ivy submits naming Sam, when a manager opens it, then Sam shows "Not confirmed · Mark Confirmed". After Confirm & Add to Schedule, Sam's schedule has the shift and one confirmation email goes to Sam and Ivy (the endpoint sends a single combined email; round 1, Codex).
Edge (the Claude round-1 race): Given Ivy's edit form is open with Sam confirmed, when a manager Undoes Sam in another tab and Ivy then saves a new reason, then Sam is saved unconfirmed.
Edge: Given a manager-confirmed sub with a record, when Ivy edits only the reason, then confirmed, subUid and appliedOverrides are unchanged. When she removes Sam with × and accepts the prompt, the reversal and hand-off run as today.
Edge: Given an old request whose sub was ticked by the requester (confirmed, no link), when Ivy edits the reason, then it stays as the document has it (no backfill). With D3, a manager sees the amber line.
Edge: Given an approved request with a confirmed sub, when Ivy edits it, then the request goes back to review, a landed reversal un-confirms the sub, and a failed one keeps the confirmation and its record (unchanged behaviour, now asserted).
Failure (D1): Given Sam is confirmed on an under-review Oct 3 request, when Ivy changes it to Oct 4 and saves, then she sees the "ask a manager to Undo Sam first" message, nothing is saved or reversed, and her form stays open with her edits. Changing only the reason saves normally.
Failure: Given a non-manager calls handleSubConfirmToggle (either branch of the roster match) or submitConfirmSub, then they see "Only a manager can confirm a sub": no modal, no schedule write, no transaction, no email.

Phase 2: The manager chooses the dates when confirming (D2)

Acceptance:

  • The confirm box lists each of the request's dates with a checkbox, ticked where the sub was proposed for it. If the sub's saved dates match none of the request's dates, all of them are ticked.
  • Unticking a date means nothing is written for it. The "already has a shift… Overwrite?" prompt still covers the ticked dates. Cancelling it still writes nothing, and the manager can untick the conflicting date and try again.
  • Nothing on the saved request changes. getSubCoverageDates keeps its current meaning, and its "empty array = no dates" test stays green: the "all dates" fallback lives in the box's pre-tick, not in the helper.
  • No ticked dates → "Tick at least one date", and nothing is written.

Changes: openConfirmSubModal renders checkboxes into #confirm-sub-dates (index.html, confirm-sub modal) from the request's dates, pre-ticked from getSubCoverageDates with an empty result → all. submitConfirmSub reads the ticked dates into ctx.dates before its existing "no covered dates" check. The no-roster-match branch (:7881–:7885) keeps its own fallback, unchanged.

Happy (Ivy's case): Given a sub whose saved dates are [] on an Oct 3 request, when a manager clicks Mark Confirmed, then Oct 3 is listed and ticked, and Confirm writes Oct 3.
Edge: Given Kayleigh proposed for Oct 3 only on an Oct 3–4 request, then only Oct 3 is pre-ticked. The manager can tick Oct 4 too.
Edge: Given Oct 4 already holds the sub's own shift, when the manager unticks Oct 4, then there's no overwrite prompt and only Oct 3 is written.
Failure: Given every date is unticked, then Confirm refuses and nothing is written.

Phase 3: "Coverage: Secured" warns while a sub is unconfirmed

Acceptance:

  • Picking Secured while any proposed sub is unconfirmed shows: "Sam isn't confirmed yet, so nothing has been added to their schedule and they haven't been emailed. Use Mark Confirmed next to their name to do that. Mark coverage Secured anyway?", naming only the unconfirmed subs.
  • Cancel writes nothing and the dropdown snaps back. OK saves the label as today.
  • No warning with no proposed subs, all subs confirmed, or any other status.
  • The request is read fresh (getTimeOffRequestResult), not from allTimeoffRequests. That cache can be hours old, skips documents without submittedAt, and returns [] on error (round 1, both reviewers; same precedent as js/app.js:8274). A failed read says "Couldn't check the subs" and asks whether to save anyway.
  • A failed label write says so instead of always toasting "Coverage updated" (round 1, Codex). The duplicate renderAdminAllTimeOff() is dropped.
The label isn't sticky, which is unchanged and worth knowing: every Mark Confirmed / Undo recomputes it (all confirmed → Secured, some → Partial, none → Pending; js/firebase-data.js:805). A manual "Secured" can therefore change by itself on the next confirm or undo. That's expected, not a new bug.
Happy: Sam unconfirmed → GM picks Secured → Cancel → no write, the dropdown still reads Pending.
Edge: Two subs, one confirmed → the warning names only the other.
Failure: Fresh read fails → "Couldn't check the subs. Save Secured anyway?" A failed write → an error, not "Coverage updated".
