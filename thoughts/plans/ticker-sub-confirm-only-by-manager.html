Plan: A sub is confirmed only by a manager, on the request's real dates

App: Tinker Ticker (~/tinker-timeclock) · Drafted: Sep 29 2026 · v6 after design review rounds 1–5 (round 5 checked only the v5 edits: both reviewers, no BLOCKING, no wrong schedule write or false confirmation; four plan-text MEDIUMs, folded in here) · execution-ready: true (design) — round 4 Codex passed outright; rounds 5–6 found no BLOCKING and no wrong write in any edit, and every later finding is folded in. Execution still waits for Christie's written approval to edit the repo, per the Tinker Ticker rule.

Goal: a sub shows as Confirmed only after a manager used Mark Confirmed. For a sub on the roster, that step writes the shift to their schedule for the dates the manager ticks and sends the confirmation email. For a name the roster can't match, it confirms with the amber "add their shift manually" note, as today. A requester can't produce a "Confirmed" of any kind, and nothing an edit form, a stale confirm box, or a second tab does can create or remove a confirmation behind anyone's back.

Not promised: that the email arrived. It is sent after the confirmation lands, fire-and-forget (js/app.js:9274), as today, and a sub with no email on file gets none.

Scope, per Christie (Sep 29): from here on only. Nothing rewrites existing request documents. No rules change, no new collection, no change to the Payroll Tool or the reminder job.

The one rule behind Phase 1

Once the checkbox is gone, the edit form has no say over confirmed. The form remembers each sub's state as it was when the form opened (openedSubs: name → { confirmed, hasRecord, entry }, where entry is a deep copy of the form-shaped object built at :7068 ({name, email, dates, confirmed}), reset at the top of openTimeOffForm beside timeoffFormSubs (js/app.js:7021), filled only in the edit branch), and the request's dates as loaded (openedDates = normalizeRequestDates(existingRequest.dates): a fresh array computed from the document, never from, or aliasing, timeoffFormDates, whose rows the inline handlers mutate in place (:7120–7122). Otherwise every legitimate date edit would look like "someone else changed the dates" and D1 would never fire (round 5, Claude M3 / Codex M1). It is reset to null with openedSubs. That way a skipped fill reaches the helper as a missing value and throws, rather than as []. The throw guards against a wiring bug, which the ratchet already pins; it isn't a runtime path users meet (round 6, Claude L1).) Re-adding a removed name that openedSubs says was confirmed restores the original entry (confirmed: true, so reconcile carries its link and nothing reverses): removing then re-adding is an undo, not an un-confirm (round 3, both reviewers). At save, if the document disagrees with that memory for any sub still in the form, the save is refused: "A manager confirmed or un-confirmed a sub while you were editing, so nothing was saved. Close this form, reopen the request, and try again." A form that is out of date can't decide anything, in either direction. The one deliberate exception (round 4, Claude L7): if Ivy removes a confirmed Sam, the reversal lands, and a manager re-confirms Sam before the save, the manager's newer confirmation wins and Sam stays. That's consistent data, and the manager acted last. The save then says so rather than reporting plain success: "Saved. Sam was re-confirmed by a manager while you were editing, so Sam stays on this request." (round 5, Claude L8). The names come from reversedNames ∩ the names confirmed in carried.current; a non-empty set replaces the plain "Request saved" toast, and a ratchet pins it (round 6, Codex L1). This closes the round-1 race (stale "confirmed"), the round-2 race (stale "unconfirmed" → reversal) and the "removed a sub that just got confirmed without seeing the × prompt" race in one check. carryConfirmedSubs also loses its hasLink exemption, as defence in depth.

The check is a pure helper, checkEditAgainstDocument({ openedSubs, openedDates, formSubs, formDates, docSubs, docDates, reversedNames }) in js/schedule-helpers.js (reversedNames optional, step 2 only), returning { ok: true } or { ok: false, reason: 'subs-changed' | 'dates-changed-elsewhere' | 'dates-while-confirmed', names }. The reasons are evaluated in that order (round 5, Claude L4), so the sub-race BDDs (dates untouched) resolve to subs-changed, and a date move by someone else is reported before D1 can give Undo advice. A missing openedDates argument throws rather than defaulting to [], because a default would false-refuse every dated request (round 5, Codex M1). It is the real exported function, so its unit tests exercise production code (round 2, Claude M4: the emulator harness re-implements app logic and can't test the orchestration itself).

  • subs-changed: for each sub name in formSubs, the document's confirmed ≠ openedSubs' confirmed (absent on either side counts as unconfirmed). For each sub the form removed: the document now says confirmed but openedSubs said unconfirmed (it was confirmed after the form opened, so the × prompt never showed). An optional reversedNames set is skipped entirely (step 2 only).
  • dates-changed-elsewhere (checked after subs-changed and before D1; round 4, Claude M1): normalizeRequestDates(docDates) ≠ normalizeRequestDates(openedDates). Someone else moved the dates since the form opened, so this user can't be told they changed them. Message: "This request's dates were changed by someone else while you were editing, so nothing was saved. Close this form and reopen the request." It never tells anyone to Undo a sub. This fires whether or not any sub is confirmed, which is a deliberate small scope widening: today such a save silently writes the old dates back over the other person's change (:7363) (round 5, Claude L1).
  • dates-while-confirmed (D1): the document's dates still equal openedDates, any sub is confirmed on the document, AND normalizeRequestDates(formDates) ≠ normalizeRequestDates(docDates), so this user did change them. Message: "Sam is confirmed to cover this request. Sam has to be un-confirmed (Undo, by a manager if Sam's shift is on their schedule) before the dates can change." The wording works for a manager editing too (round 4, Claude L9).
  • normalizeRequestDates (round 2, Claude B1 + Codex): sort by date; type missing → 'full'; partialStart/partialEnd kept only when type === 'partial', with ''/undefined → null; flexible dropped. Precisely type: d.type || 'full', so stored undefined, null and '' all mean full, matching the load (round 3, Codex). Known limit (round 3, Claude L2): a hand-edited type: 'partial' with no times can't round-trip, because the form forces times in, so D1 refuses its edits while a sub is confirmed. The same goes for a stored date: '' row or a request with no dates, which validDates (:7331) drops. No app path writes these shapes (round 4, Claude L9). Every other stored shape, i.e. every shape the app writes plus legacy missing/falsy type and empty-string partialStart/partialEnd on a full or missing-type row, compares equal to itself after the form's load (:7063: || 'full', || '') and save (:7366: null when not partial).
