What the research found (why this plan exists)

1. The shared project isn't safe to let members sign in yet. Letting members in means creating Firebase Auth accounts for people who aren't staff. Today several rules trust any signed-in account:
  • Storage, every path (storage.rules): any signed-in account can read, overwrite and delete Classbook, Summer Camp, Social Media, project-detail and Training files.
  • clayMembers create (firestore.rules:979-980): any signed-in account can write clayMembers/{own uid} with isAdmin:true. It then reads, edits and deletes every Clay Hub Booking record. Booking's own add-admin.html bootstraps admins exactly this way.
  • timeclock_settings/adminSubscriptions (:449): any signed-in account can read managers' Web Push subscriptions. tinker-timeclock/netlify/functions/send-notification.js has no auth check, so a member could send fake push notices to managers.
  • isKiosk() (:40-46): it trusts token.email without email_verified. If either kiosk address has no Auth account, anyone could register it and get kiosk reads of every users doc and timeclock data.
  • Tinker HQ auto-creates a users doc (role:'staff', both studios) for anyone who signs in (studio-hub/js/app.js:146-159; the rule allows self-create at :127-132). It grants nothing today, but members would show up in Manage Team, where one checkbox gives them apps.
These holes exist today, because anyone with the public API key can already sign up with email and password. Magic-link sign-in requires open account creation, so it can't be switched off. From here on the rule is "signed in ≠ trusted", and everything in Phase B follows from it.
2. Membership Manager's data isn't shaped the way DATA-MODEL.md assumed (clay-hub-membership/js/app.js, js/firebase-data.js):
  • Collection and doc ID: the collection is clayHub_members. The doc ID is the email, lowercased, with . and / replaced by _ (firebase-data.js:54). The stored email field keeps its original case.
  • Status is stage: onboarding | touring | active | paused | offboarding | cancelled, with a boolean isActive alongside it.
  • stage is only correct right after someone opens Membership Manager. Pause start and end, and offboarding → cancelled, are flipped by code that runs on page load (app.js:599-759). A pause set with a future start never becomes paused on its own.
  • Pause dates live in scheduledPause.{startDate,endDate} and pauseHistory[]. Last day is scheduledCancellation.finalAccessDate. All dates are YYYY-MM-DD strings; there are no Timestamps.
  • Name is one name string. There's no first/last split.
  • No member-since field exists. termStart rolls forward every term.
  • phone is free text and not normalized. It's blank for everyone imported from Sawyer, and Sawyer re-imports also wipe it.
  • Every Membership Manager page load re-writes every member doc in full with .set() and no merge (saveAllMembersToFirestore, app.js:902). Any field another app writes onto these docs is wiped. It also means any trigger on the collection fires for every member on every page load.
  • Two existing Manager bugs matter here:
    • The resume check reads pauseHistory[0], but new pauses are added at the end (:617 vs :3062).
    • "Remove scheduled cancellation" leaves stage:'offboarding' for good (:2862-2889).
3. The infrastructure the spec assumes doesn't exist yet.
  • No Cloud Functions anywhere in tinker-hq-apps. firebase.json has only firestore and storage. The project is on Blaze (since May 28, with a $20 budget alert).
  • The deploy guard only ships rules, storage and indexes (scripts/deploy-rules.sh).
  • Staff only sign in with email and password. No app uses email-link or Google sign-in, so both providers need to be switched on in the console.
  • The spec's beforeSignIn blocking function needs a paid upgrade to Firebase Auth with Identity Platform.
  • Tinker HQ doesn't host other apps' screens. Every app is its own site with a tile and an appAccess key.
4. Clay Hub Booking's footprint is small.
  • Never deployed, linked from nowhere, 12 commits (all feature work Feb 26–28).
  • It left behind:
    • a rules block (firestore.rules:956-1003) for 5 collections: clayMembers, clayBookings, claySpots, clayBlockedSlots, claySettings
    • one composite index on clayBookings (firestore.indexes.json:2-20)
    • a registry row and a palette mention in product-principles.md (:177, :102)
    • a memory file (~/.claude/projects/-Users-christiehubley/memory/clay-hub-booking.md) plus its index lines
    • mentions in two audit docs
  • Production may hold 15–34 seeded claySpots docs, a clayMembers doc for Christie's uid, and Firebase Auth accounts that Booking created for any test members.
