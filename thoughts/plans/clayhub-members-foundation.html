The shape: two projects, one narrow one-way link

tinker-hq-apps (staff only · email/password) members project (members · magic link + Google) ──────────────────────────────────────────── ─────────────────────────────────────────────────────── Membership Manager ──writes──▶ clayHub_members ingestMemberUpdate ◀── the ONLY way in (Phase B: awaited, only changed docs, permanent memberId) (validates a strict payload, orders by source Manage Team ─────────────────▶ users version, writes members/* and staffRoster/* only) │ members/{memberId} projection (keyed by memberId) │ clayhub-link functions staffRoster/{uid} explicitly granted staff only │ (own service account: bookings, activityLog, inbox, settings, … │ READ-ONLY on tinker-hq-apps, other functions: sign-in claim, status recompute, │ may only CALL one function) reminders/release, staff exchange, kiosk, CSVs └──── HTTPS call, signed ─────▶ The link can't write to the members project's database. It can only call one function, which checks every field. The members project has no access of any kind to tinker-hq-apps. Members never get an account in tinker-hq-apps.

This replaces the first design, which had the link write straight into the members database with a broad "Cloud Datastore User" grant. Both reviewers flagged that grant: it includes delete, it can't be limited to one collection, and on the default service account every future function would inherit it. With the new design, "the link can only touch member and staff projections, and can never delete" is enforced by permissions and by the receiving function, not just by tests. See D22.

What the research and the review found

1. Membership Manager's saves aren't reliable enough to feed a live link. Confirmed in code:
  • Save errors are caught and only logged to the browser console (firebase-data.js:50-77), so staff can see "Saved!" when nothing saved.
  • The page-load save isn't awaited (app.js:899-919).
  • If the Firestore load fails or comes back empty, the app falls back to the browser's old localStorage copy and immediately saves it over Firestore (app.js:825-876 → saveLocalData). That's the "data disappeared" pattern, but with an overwrite.
A live link would carry any of these to members within a minute. That's why Phase B comes before Phase E.
2. Members have no permanent identity.
  • The doc ID is derived from the email (lowercased, . and / → _, firebase-data.js:54). That rule isn't unique: a.b@x.com and a_b@x.com collide.
  • There's no delete path, so changing a member's email creates a second doc and leaves the old one live forever. The old email could then still sign in with whatever status it last had.
  • The stored id is also email-derived (app.js:836).
Fix: a permanent, random memberId on every record (Phase B, D21), and an explicit "change email" flow.
3. The rest of Membership Manager's data (clay-hub-membership/js/app.js):
  • Status is stage: onboarding | touring | active | paused | offboarding | cancelled. It's only brought up to date when someone opens Membership Manager (app.js:599-759).
  • Pause dates are in scheduledPause and pauseHistory[], under two spellings (startDate/endDate and legacy start/end, app.js:620-672).
  • Last day is scheduledCancellation.finalAccessDate. A cancelled member whose last day is still ahead is moved back to offboarding (app.js:700-711).
  • Dates are YYYY-MM-DD strings, parsed inconsistently (UTC vs local).
  • Name is one string, there's no member-since field, phone is free text, and phone is blank for Sawyer imports. The Sawyer import drops fields it doesn't know.
4. Existing holes in tinker-hq-apps: real, but not blocking this app, because members never get accounts there. They're handed to the resilience plan's P2 item (A6):
  • Storage rules trust any signed-in account.
  • adminSubscriptions is readable by any account, and send-notification.js has no auth (payroll gate).
  • isKiosk() trusts an unverified email, so pin the uids.
  • Tinker HQ auto-creates a users doc for anyone who signs in.
One of these now matters here: staffRoster is built from users. So the self-create rule's pins (role:'staff' and an empty appAccess, firestore.rules:127-140) become a Clay Hub Members security control. The link will therefore only project people with an explicit grant, and a comment on that rule records the dependency (E-0).
5. The current backup.js reads the Firebase CLI login token (tinker-backups/backup.js:170-172) and calls Firestore's REST API with it. ~/.claude/CLAUDE.md forbids exactly that. It's an existing issue, outside this plan's scope, and belongs with the resilience plan's parked "stop depending on Christie's login" rework. It means:
  • (a) the members project must not be added to backup.js;
  • (b) Claude sessions don't edit or run it;
  • (c) it already backs up the five Booking collections every 30 minutes (:63-64) but keeps only about 2 days of copies (MAX_BACKUPS = 96), which matters for A2.
6. The infrastructure the spec assumes doesn't exist yet.
  • No Cloud Functions anywhere.
  • The deploy guard is built around one file per target, so it can't safely ship a functions folder as it stands: there's no byte-check for a source tree, no untracked-file check, and no record of a deploy that only partly succeeds.
  • The raw-deploy hook blocks every project, but ~/.claude/settings.json's approval rules and the hook's messages name only the studio-hub guard.
7. Clay Hub Booking's footprint.
  • The rules block (firestore.rules, from the "CLAY HUB BOOKING — SEPARATE AUTH SYSTEM" banner through the end of match /claySettings, currently lines 956–1004). Its three helpers are used nowhere else, and no existing test references it.
  • One index.
  • Five names in backup.js's collection list.
  • A registry row and a palette mention in product-principles.md.
  • A memory file.
  • Four other docs: the resilience report, reviews/2026-09-21-impl-review-p2-claude.md, archive-employees.html, studio-hub-archive-employees.html.
  • The latest backup holds 1 clayBookings doc and 19 claySpots (Codex, count only).
