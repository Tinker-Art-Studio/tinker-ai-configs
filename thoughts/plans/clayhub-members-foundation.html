  • The link never forwards an event as it arrives. What the research and reviews found (verified in code)

1. Clay Hub Booking has a live privilege escalation today. firestore.rules (match /clayMembers, allow create: if isClayAdmin() || (isAuthenticated() && memberId == request.auth.uid)) pins no fields. So any account in tinker-hq-apps can create clayMembers/{own uid} = {isAdmin:true, active:true} through the normal client SDK. It then reads, edits and deletes every Booking record. That's why Phase A goes first.
2. Membership Manager's saves aren't safe to feed a live link (clay-hub-membership):
  • Save errors are only logged to the browser console (js/firebase-data.js:50-77).
  • The page-load save isn't awaited (js/app.js:899-919).
  • A failed or empty Firestore load falls back to the browser's old localStorage copy and saves it over Firestore (app.js:825-876).
  • The automatic pause-end and offboarding changes (app.js:664-679, :742-761) change a member only in memory. They rely on that blanket page-load save to persist.
3. Membership Manager's dates are off by one day in Denver. new Date('YYYY-MM-DD') is parsed as UTC midnight, and setHours(0,0,0,0) then lands on the previous local day (app.js:655-665, :738-742). So:
  • a pause entered as Jan 2 – Feb 1 ends on Feb 1, not Feb 2 (and starts a day early);
  • an offboarding member becomes cancelled on their last day.
It's an existing bug. It's fixed in Phase B, and My Clay Hub computes dates correctly on its own side (D4).
4. Members have no permanent identity.
  • The doc ID is the email, lowercased, with . and / → _ (firebase-data.js:54). That isn't unique: a.b@x.com and a_b@x.com collide.
  • There's no delete path, so changing a member's email leaves the old doc live forever.
  • The Sawyer import rebuilds records and drops fields it doesn't know (app.js:503-567).
5. The rest of Membership Manager's data.
  • Status is stage: onboarding | touring | active | paused | offboarding | cancelled. It's only brought up to date when someone opens Membership Manager.
  • Pause dates are in scheduledPause and pauseHistory[], under two spellings (startDate/endDate and legacy start/end).
  • Last day is scheduledCancellation.finalAccessDate. A cancelled member whose last day is still ahead is moved back to offboarding (app.js:700-711).
  • Name is one string. There's no member-since field. Phone is free text, and blank for Sawyer imports.
6. Other holes in tinker-hq-apps: real, but not blocking, since members never get accounts there. They're handed to the resilience plan's P2 item (A6):
  • Storage rules trust any signed-in account.
  • adminSubscriptions is readable by any account, and send-notification.js has no auth (payroll gate).
  • isKiosk() trusts an unverified email.
  • Tinker HQ auto-creates a users doc for anyone who signs in.
Dependency: staffRoster is built from users. So the self-create pins in the users rules (firestore.rules:127-145: role:'staff', empty appAccess, both unchanged on self-update) become a My Clay Hub security control. E-0 records this, and the link only projects explicit grants.
7. backup.js uses the Firebase CLI login token (tinker-backups/backup.js:171-173) and calls Firestore's REST API with it. ~/.claude/CLAUDE.md forbids that pattern. It's an existing issue for the resilience plan.
  • Claude never edits or runs it.
  • My Clay Hub isn't added to it (D13).
  • clayHub_members and users are in COLLECTIONS but not in TIER1_COLLECTIONS (:30-45), so nothing alarms if their doc count drops. Christie adds them (A6).
8. Infrastructure gaps.
  • No Cloud Functions exist anywhere.
  • The deploy guard assumes one file per target (deploy-rules.sh:65-69), and predeploy-check.sh accepts only firestore and storage.
  • The raw-deploy hook blocks every project, but its message (firebase-deploy-hook.sh:35-38) and four autoMode entries in ~/.claude/settings.json (lines 33, 39, 46, 47) name only the studio-hub guard.
9. Clay Hub Booking's footprint.
  • The rules block: from the "CLAY HUB BOOKING — SEPARATE AUTH SYSTEM" banner through the end of match /claySettings, currently lines 956–1004. Its three helpers are used nowhere else, and no test references any of it.
  • One clayBookings index.
  • Five names in backup.js's COLLECTIONS.
  • product-principles.md:102 and :177.
  • The memory file clay-hub-booking.md.
  • Four docs: the resilience report, reviews/2026-09-21-impl-review-p2-claude.md, archive-employees.html, studio-hub-archive-employees.html.

D22How the link delivers changesApproved (Christie, Sep 27). "Re-read, then send a snapshot."
  • A trigger on clayHub_members/{id} collects the memberId from both the before and after versions.
  • For each one, it reads all source docs with that memberId in a single query, filtering on memberId only. "Live" is decided in memory as retired !== true, because live docs usually have no retired field. The query's QuerySnapshot.readTime is the snapshot time.
  • It works out the member's current truth:
    • exactly one live doc → that doc's fields;
    • no live doc → a tombstone;
    • more than one live doc → a conflict: nothing is sent, and it alerts.
  • It POSTs {memberId, snapshot, readTime} to ingestMemberUpdate.
  • That function, in a transaction, drops anything whose readTime isn't later than the stored sourceReadTime. A member with no stored time accepts any snapshot. It checks the payload strictly, runs deriveStatus, and writes. It never deletes.
  • sourceReadTime is a tinker-hq-apps timestamp, kept in its own field. It's only ever compared with other tinker-hq-apps read times, never with my-clay-hub clocks or updatedAt.
  • The reconcile uses the same envelope and the same gate. It reads the whole source in one read-only transaction pinned to a single readTime, and stamps every member (and tombstone) with that time. So a trigger snapshot taken during a reconcile can never be overwritten by older reconcile data.
Because every message is the whole truth as of its read time, arrival order, retries, deletes and email changes (the new doc and the retired old doc in one batch) all end in the right state. users/{uid} works the same way, into staffRoster/staff_{uid}, using that document read's DocumentSnapshot.readTime. There's no memberId and no conflict case on that path. Docs without a memberId are skipped with an alert (Phase E requires Phase B). Phone (keeps SPEC DECISIONS #24): the snapshot carries only phoneLast4, worked out in tinker-hq-apps. The full phone number never leaves that project. No client can read members/* at all. Members read only their own memberProfiles/{memberId}, an allowlist without phoneLast4, also written by ingestMemberUpdate (Phase C verification finding). Phase A — Retire Clay Hub Booking and close its escalation hole ✅ DONE Sep 27, 2026

Acceptance criteria:

  • An ordinary signed-in account can no longer make itself a Booking admin. Every get, list, create, update and delete on all five collections is denied, for every kind of account.
  • isClayAdmin, isActiveMember and isBookingOwner no longer exist in the rules file.
  • A kept snapshot of all five collections, taken after they're sealed (so nothing can change underneath it), exists outside the backup rotation. Its doc IDs are compared with what Christie listed in A1 before anything is deleted.
  • Every other app works as before, and the full rules suite passes.
  • Nothing still presents Clay Hub Booking as live, and the repo is archived.
  • Findings 6 and 7 are recorded in the resilience plan.

Order (round 3): seal first, then snapshot. Removing the rules deletes nothing; it only stops anyone changing the data. While the hole is open, anyone could change the data, so a snapshot taken before sealing wouldn't be the final state.
