Plan: Classbook Shared Document/Array Concurrency Safety

Goal: Find and close every shared-document/array "last write wins" race in the Classbook app — a document multiple admins can read into a local variable, mutate a copy of, and overwrite wholesale — the sibling vulnerability class to the companion plan's Vulnerability #11, but for shared config/utility data (Settings, Cut Bank, Idea Bank, Prep Dashboard, Prep Cycle config) instead of lesson content.
App: tinker-spring-curriculum (The Classbook) — js/app.js, js/firebase-data.js
Context: Companion to classbook-data-safety-remaining-stages.html (plan_jrhp-GpcSGph) — that plan's rounds 9-10 discovered this vulnerability class while fixing Cut Bank/Idea Bank races (Vulnerability #11's Phase 13/17), and Christie chose to split it into its own dedicated plan rather than keep expanding that document indefinitely.
Risk: Varies by instance — Settings/appData is likely highest (could silently lose an entire semester's config), utility banks (Idea Bank) next, Prep Dashboard/Prep Cycle after that, diagnostics lowest (self-healing).
execution-ready: false — Scoping only. No phases have been designed yet. Six concrete vulnerable functions are already known (found incidentally while working the companion plan, not from a deliberate sweep — see "What's already known" below), but this document's own premise is that a comprehensive, deliberate sweep of the whole Classbook app will very likely find more. Do not treat the six below as the final list. No app code has been touched — this document, like its companion, is pure investigation and planning until phases are designed, reviewed, and explicitly approved for execution.

Context — why this plan exists

The vulnerability class: a shared Firestore document (or a field within one) that multiple admins can read into a local JS variable, mutate a copy of, and write back via a full .set() — not a targeted, atomic Firestore transform (arrayUnion(), arrayRemove(), a dotted-path update(), or a transaction). When two admins do this concurrently, whichever write lands last silently wins in full, discarding the other admin's change even if it touched a completely different field or array entry. This is structurally the same root cause as Vulnerability #11 in the companion plan (trusting a stale local snapshot as the basis for a write to shared state) — but Vulnerability #11 is specifically about lesson content (curriculum/lessonData, summerCamps_lessonData); this vulnerability class is about everything else shared — config documents, admin utility arrays (Cut Bank, Idea Bank), weekly prep data, and similar.

How this was found: the companion plan's Phase 17 (Aug 15, 2026, round 8) fixed a concurrent-writer race on the Cut Bank's append side using FieldValue.arrayUnion(). Round 9 found the identical race still open on the Cut Bank/Idea Bank removal side (three call sites, fixed with FieldValue.arrayRemove()). Round 10, verifying that fix, found two things: (1) the Idea Bank fix was itself incomplete — five other live functions still race against it; (2) the same underlying pattern — read a shared document, mutate a local copy, overwrite the whole thing — exists in at least three completely unrelated features (Settings/semester config, Prep Dashboard, Prep Cycle config), found by one reviewer doing a semi-directed search, not a deliberate sweep. Two rounds of only incidental attention found six instances — a genuinely comprehensive, deliberate sweep of the whole app (not triggered by investigating something else) is very likely to find more, which is exactly why Christie chose to give this its own plan instead of continuing to grow the companion doc indefinitely.

Scope boundary — Classbook (tinker-spring-curriculum) only, for now. This exact anti-pattern (local read-modify-write, then full-document overwrite) is a common enough JS/Firestore habit that it plausibly exists in other Tinker HQ apps too (Roster Manager, Payroll Tool, Tinker Ticker, etc.) — but that has not been checked, and doing so is explicitly out of scope for this document unless Christie asks to expand it. Said honestly here rather than silently assumed either way.

What's already known — six instances, found incidentally, not from a sweep

These are documented here so the eventual comprehensive sweep has a known-correct baseline to check against (and so nothing already found gets rediscovered from scratch) — none of these have design work, BDD scenarios, or review done yet. They are almost certainly a subset of what actually exists.

1. Idea Bank's five remaining writers (HIGH — the most directly actionable, since it's the same collection/pattern round 9-10 already partially fixed)

File: js/app.js. Functions: saveNewIdea() (~5305-5330, write ~5327), saveIdeaEdit() (~5340-5357, write ~5354), deleteIdeaProject() (~5359-5369, write ~5367), archiveIdeaProject() (~5371-5376, write ~5374), unarchiveIdeaProject() (~5378-5383, write ~5381). All call saveFutureProjects(projects) (firebase-data.js:581-589), which does a plain .set({projects, lastUpdated, lastUpdatedBy}) on the whole curriculum/futureProjects document — no arrayUnion/arrayRemove, no merge-at-the-element-level. There is no onSnapshot listener on this document (confirmed — the only listeners in firebase-data.js are on curriculum/lessonData and curriculum/appData), so a tab's cached currentFutureProjects can go stale indefinitely with no self-correction.

Concrete failure: Admin A pastes (correctly removes, via the companion plan's already-fixed arrayRemove()) idea X from the bank. Admin B, in a separate tab with a snapshot loaded before A's removal propagated, archives, edits, deletes, or adds a different idea moments later — B's full-array overwrite silently resurrects X. deleteIdeaProject() is the direct sibling of the companion plan's already-fixed deleteCutProject() — same shape, same fix (FieldValue.arrayRemove()). saveNewIdea()/saveIdeaEdit() would need care: an "edit" mutates an existing array element in place, so the fix isn't a simple append/remove — it likely needs the element's stable identity (an id field, if one exists — check app.js:5317's id-generation convention, already referenced elsewhere in the companion plan) to target a transaction or a keyed sub-collection instead of an in-array edit, since Firestore's array transforms can't update one element by identity — only add or remove whole elements.

Reachability note (open question, not yet checked): is Idea Bank reachable for summer semesters, the way Cut Bank/Copy Plan were checked and found NOT reachable in the companion plan? Verify before assuming these five fixes need the same "non-summer only" framing.

2. curriculum/appData — Settings, semester create/delete/publish (HIGH — likely the most consequential, since it's admin-facing config, not a utility bank)

File: js/firebase-data.js, saveConfig(config) (79-85) — an unconditional .set(config) of the ENTIRE config document. Live callers: saveSettings() (app.js:9249-9286 — deep-copies the whole cached config, replaces one semester's fields including array fields like breakWeeks/closureDates/teacherNames, overwrites the whole document), plus semester creation, deletion, and publish-toggling (all touched by the companion plan's Phases 15/18, which did NOT address this underlying overwrite pattern — those phases fixed different bugs in the same functions). setupConfigListener() exists in the codebase but is never called anywhere — confirmed via grep — so the local config cache has no live-refresh mechanism at all.

Concrete failure: Admin A opens Settings and changes one semester's roster or teacher list. Admin B, concurrently, creates a new semester, deletes a different one, or toggles a publish flag. Both save whole locally-derived config objects. Whichever .set(config) lands last silently erases the other admin's change — potentially an entire newly-created semester, vanishing with no error, no trace, and no admin ever told anything went wrong.

Relationship to companion plan: Phase 15 (semester delete) and Phase 18 (block ambiguous semester keys) both touch deleteSemester()/createNewSemester(), which both go through this same saveConfig() path — but neither phase addresses THIS race (they fix different, narrower bugs in the same functions). Worth checking during design whether a fix here needs to be coordinated with those phases' pseudocode rather than designed in isolation.

3. Prep Dashboard weekly autosave (MEDIUM)

File: js/app.js, savePrepDataNow() (~7128-7139), passing the whole currentWeekPrepData to savePrepWeekData() (firebase-data.js:145-162), which replaces the complete ${semesterKey}.${weekKey} map. Includes a classAssociations[project] array locally mutated via push()/filter() (app.js:8418-8444).

Concrete failure: User A adds a class association to a project. User B, from a snapshot that hasn't received A's change, marks a different material complete and autosaves. Each autosave replaces the entire week map — B's later write can silently remove A's association; A's later write can revert B's material update. A live listener on this data narrows the window but doesn't make the read-modify-write atomic.

4. Prep Cycle configuration (MEDIUM)

File: js/app.js, openPrepCycleEditModal() captures config.phases (~7634-7647), builds a complete newPhases array (~7734-7743), then savePrepCycleConfig() (firebase-data.js:313-321) replaces the whole document via .set(toSave).

Concrete failure: two admins with this modal open concurrently, editing different phases or goal/day arrays — the later full-array write discards the earlier admin's edit entirely.

5. Diagnostic dismissals (LOW — self-healing, lowest priority)

File: js/firebase-data.js, saveDiagDismissals() (636-648), called from three sites in app.js (~8799, 8821, 8868). Same pattern: loadDiagDismissals() → mutate a local nested map → saveDiagDismissals(dismissals), plain .set(). A nested map keyed by semester/fingerprint, not a literal array, so it falls slightly outside the exact "array field" framing of the others. Worst case if two admins dismiss different diagnostics concurrently: one dismissal silently reappears — annoying, not data loss, self-corrects the next time someone dismisses it again.

6. (Already fixed, in the companion plan) Cut Bank — curriculum/cutProjects

Named here only for completeness of the pattern's known instances. Genuinely, completely closed as of the companion plan's Phase 13/17 (round 9, verified round 10) — cutProject() uses arrayUnion(), pasteFromCutBank() and deleteCutProject() use arrayRemove(), and both round-10 reviewers independently confirmed via exhaustive grep that these three are the ONLY functions that ever touch currentCutProjects. No further work needed here — do not re-open.

Not in scope / open questions

  • Other Tinker HQ apps (Roster Manager, Payroll Tool, Tinker Ticker, Studio Hub, etc.) — not checked. This plan is Classbook-only unless Christie asks to expand it.
  • Whether the six known instances above are exhaustive — they are not assumed to be. The comprehensive sweep (see Resume Instructions) needs to check every .set( call across js/app.js and js/firebase-data.js for this shape, not just extend the list found incidentally so far.
  • Idea Bank's edit-in-place functions (saveIdeaEdit(), and to a lesser extent archiveIdeaProject()/unarchiveIdeaProject(), which likely toggle a field on an existing element) — noted above as needing a different fix shape than simple append/remove, since Firestore array transforms can't target one element by identity for a field-level edit. This needs real design work (transaction? stable per-idea document instead of one shared array? — a bigger shape question), not assumed to be a simple arrayUnion/arrayRemove swap like the rest.

Resume Instructions

Status: scoping only. Nothing has been designed, phased, or reviewed. Six instances are known; more almost certainly exist.

Exact next step: run a comprehensive, deliberate sweep of the whole Classbook app for this pattern — NOT triggered by investigating something else, unlike how all six known instances were found. Concretely: grep every .set( call (not .set(..., {merge:true}) on a single targeted field — the full-document or full-array-field ones) in js/firebase-data.js and every helper it exposes, then trace each one's caller(s) in js/app.js to check whether the caller does a local read-modify-write of cached state before calling it. A fork or general-purpose agent doing this systematically (not the reviewer-style Codex+Claude dual instances used for adversarial review — this is a discovery/inventory task first) is probably the right tool, producing a structured list: function name, file:line, what document/field it overwrites, whether a live listener exists on that data (narrows but doesn't close the window), concrete reachability (is this admin-only, teacher-facing, how many people realistically edit it concurrently), and a severity estimate.

After the sweep: rank findings by real-world severity — appData/Settings is probably highest (admin-facing, could lose an entire semester), the Idea Bank's five writers are probably next (same collection as work already partially done, most directly actionable), Prep Dashboard/Prep Cycle after that, diagnostics last (self-healing, lowest stakes). Design phases the same way the companion plan does — one phase per logical fix (or a small combined group where the shape is nearly identical, the way the companion plan's Phase 12/13 or Phase 15's summer-2026 special-case were combined) — with BDD scenarios, a Firebase Safety Checklist entry, and the same "trace the real code, don't assume" discipline the companion plan established. Run the same iterative Codex+Claude review loop from round one — the companion plan needed 5-10 rounds per phase group before converging; there's no reason to expect this one converges faster, and starting with the dual-loop (rather than a single second-model-review pass, the way the companion plan's Phases 1-6 did) avoids needing a retroactive audit later the way Phases 1-6 now do.
