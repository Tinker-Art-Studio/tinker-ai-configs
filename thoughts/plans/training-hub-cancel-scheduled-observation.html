Goal: a manager who scheduled an observation that isn't going to happen can cancel it from the Observations tab, and it leaves the Upcoming list without deleting anything.

Current state (researched Oct 9 against 2e969a1)

  • handleCancelScheduledObservation(id) (src/App.tsx:1121) writes {status:'cancelled'} through updateScheduledObservation. That's a merge write that only touches status. Then it patches local state. It is passed to ObservationsWorkspace, where void onCancelScheduledObservation (l.141) only silences an unused-prop warning. Nothing in the UI calls it. Its write is an unconditional merge-set.
  • The Upcoming card already hides anything except upcoming/started (l.210), so a cancelled entry disappears from it with no extra filtering needed.
  • Each Upcoming entry has an Edit button that opens ScheduleObservationModal in edit mode.
  • Collection trainingObservationSchedule: rules allow read, write: if isManagerOrAbove() (studio-hub firestore.rules:400). Managers can already write status. No rules change.
  • For a started entry (a draft exists), deleting the draft tries to put the schedule back to upcoming and unlink it (handleDeleteObservation, App.tsx:807). That is best-effort: an unlink failure is logged. It also resets every linked schedule, whatever its status, so it would revive a cancelled one (r1).
  • Tests: Vitest for pure logic and the adapter (in-memory fake testSupport/fakeFirebaseCompat.ts: get/set/delete only, no update or transaction). There's no emulator harness in this repo, and no component tests (no jsdom/testing-library). The Playwright suite runs in demo mode, where getScheduledObservations returns [] and save/update throw, so there is no browser path to this card.

Design (v2)

  1. Where: a "Remove from schedule…" button on the left of the Edit modal's footer. The modal already has two "Cancel" buttons that mean "close", so this one is not called Cancel (r1). The confirm reads "Remove Name · Class on date from the schedule? Press OK to remove it. The record is kept." OK is the destructive choice.
  2. Which entries: upcoming with no linked draft. For started, the modal says to delete the draft first, which returns the schedule to Upcoming. Helper: canCancelScheduledObservation(s).
  3. Conditional write (D4). A new adapter method cancelScheduledObservation(id) runs a Firestore transaction. It reads the doc. If it doesn't exist, it throws "This observation no longer exists — reload". If its status isn't upcoming or it has an observationId, it throws "This observation has since been started — reload". Otherwise it calls transaction.update({status:'cancelled', cancelledAt}). Using update rather than merge-set means a missing doc is never recreated as a ghost.
  4. Draft delete no longer revives (D5, amended D11): handleDeleteObservation unlinks every linked schedule except a cancelled one. That is a pure helper schedulesToUnlink(list, observationId), tested.
  5. Success handling (D6): on success the row is marked cancelled locally first and the modal closes, then the list is refetched as best-effort. On failure the modal stays open with "Couldn't remove: …".
  6. In-flight guard: Save and Remove share one busy state, and both are disabled while either runs.
  7. Upcoming filter: l.210 is changed to call the helper activeScheduledObservations(list) (filter and sort), so its test covers the code that actually renders.
  8. Soft cancel; no email (scheduling sends none).
