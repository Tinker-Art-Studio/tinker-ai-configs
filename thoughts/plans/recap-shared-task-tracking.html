The read-access bug (why Phase 1 exists)

Christie's expectation: "Others are not supposed to be able to read other people's [meetings] unless it's shared with them, except a manager/admin can see [more broadly]." The live rule in /Users/christiehubley/studio-hub/firestore.rules today (lines 388-404) does not do this:

match /meetings/{docId} {
  allow create: if (isManagerOrAbove() || hasAppAccess('recap'))
    && request.resource.data.createdBy == request.auth.uid;
  allow read: if (isManagerOrAbove() || hasAppAccess('recap'))
    && (
      resource.data.createdBy == request.auth.uid
      || resource.data.business != 'personal'
    );
  allow update, delete: if (isManagerOrAbove() || hasAppAccess('recap'))
    && (
      resource.data.createdBy == request.auth.uid
      || (resource.data.business != 'personal' && isManagerOrAbove())
    );
}

What it actually does: the business != 'personal' clause was written to distinguish Christie's private reflection memos (business: 'personal') from ordinary work meetings — it was never wired to sharedWith at all. The practical effect: any user with Recap access (any role, any appAccess grant) can already read any non-personal meeting, whether or not it was ever shared with them via the Share button. sharedWith (written by saveShareSettings(), js/app.js:5530) only drives the "Shared with me" notification list (js/app.js:5338-5341) — it has never been an access-control gate.

What already works correctly and must not regress: business: 'personal' meetings ARE already creator-only today — even a manager/admin cannot read someone else's personal meeting, since the rule's || business != 'personal' branch simply doesn't apply to them. Phase 1 must preserve this exactly. This holds regardless of who created it — if any user ever created a personal meeting, only that user could read it back, so "never seen by anyone else" is already structurally true today.

Resolved (Sep 4, 2026, from Christie's plan-reviewer comment) — "personal" should be Christie/admin -only, enforced, not just hidden in the UI. Checked directly: today, "Personal" only appears as an option in the UI for admins (js/app.js:182, if (!isCurrentUserAdmin()) hides the business-type option, the two personal meeting-type options, and the Personal scope toggle from anyone else). But that's a client-side-only restriction — the current allow create rule (added to the quote above; not previously shown in this plan) checks nothing about business at all, so nothing at the database level actually stops a non-admin from writing business: 'personal' directly if they bypassed the UI. Since this plan is already touching this exact rule block, Phase 1 now also adds: && (request.resource.data.business != 'personal' || isAdmin()) to allow create — closing the gap at the layer that actually matters, not just the UI layer. This does not change the already-correct read behavior described above; it makes the "who can even create one" question match Christie's stated intent as well as the "who can read it back" question already did.

Decision: use the only lever the current data model actually supports — any manager/admin can read any non-personal meeting, not scoped to "their people." There is no direct-report/hierarchy concept anywhere in the data model today (checked: no reportsTo, no manager-uid field, no hierarchy of any kind on users docs — roles are flat admin/manager/staff plus a per-app appAccess allowlist, confirmed across every rules block in firestore.rules and Studio Hub's own CLAUDE.md), so scoping to "reports only" isn't buildable without a new field on every user plus new rules logic to match it — real, but separate, larger work, not bundled into this plan. If reports-only scoping is ever wanted, it's a follow-up plan, not a Phase 1 rewrite.
Dependency checked, confirmed safe at the code level (not just design intent). Studio Hub's Mission Control alert engine (studio-hub/js/alerts.js:497-554, listenToRecap()) also queries the meetings collection with no sharedWith filtering (.where('business', 'in', ['tinker', 'clay']), no creator/shared scoping). This matters more than it first looks: Firestore evaluates a list/query's security rule against the query's entire provable result set, not per document — if the rule's condition can't be proven true purely from the query's own where clauses, Firestore rejects the whole query, it does not silently filter results. Today's rule's inner clause (business != 'personal') is structurally provable from this exact query's where clause, so it succeeds for anyone who passes the outer gate today, manager or not. After Phase 1, a non-manager's inner clause adds sharedWith contains uid, which is not provable from this query's where clause — so if a non-manager, non-admin user's client ever actually called listenToRecap(), that query would newly start failing outright post-Phase-1. The question is whether that can happen. First pass at this claim only cited Studio Hub's CLAUDE.md prose ("used exclusively by admin and manager roles") — a documented intent, not verified enforcement, which is exactly the kind of prose-vs-code gap this plan exists to close for Recap's own sharedWith field. Went back and checked the actual code: AlertEngine.init(currentUser, db) is called at studio-hub/js/app.js:258, inside if (currentUser && (currentUser.role === 'admin' || currentUser.role === 'manager')) — a real code-level gate, not a hidden button. currentUser is populated from the authenticated user's own Firestore users/{uid} doc (handleAuthStateChange, studio-hub/js/app.js:134) — the same source of truth the security rules themselves read via getUserData() — so a staff-role user cannot spoof this client-side check into passing while also having the rules' own isManagerOrAbove() evaluate true, since rules read the authoritative Firestore doc directly, independent of any client claim. One honest caveat, orthogonal to this plan: app.js:127 restores a cached currentUser from localStorage before the fresh Firestore-sourced check settles, so there's a theoretical brief-window race on Studio Hub's own page load, unrelated to and unchanged by this plan (today's outer gate — isManagerOrAbove() || hasAppAccess('recap') — already governs that same window identically before and after Phase 1, since Phase 1 only changes the inner clause). Conclusion stands: under normal, settled-state operation, nothing but a manager/admin ever reaches listenToRecap(), so Phase 1's rule change is safe for this dependency. Separately noticed, out of scope for this plan: that listener reads meeting.actionItems, a field that doesn't exist in Recap's actual schema (real data uses meeting.summary.beforeNextMeeting[].items[]) — so it currently produces zero real alerts regardless of this rule change. Pre-existing, unrelated dead code. Phase 1 — Fix the meetings read/write rule to actually gate on sharing

Acceptance criteria

A non-personal meeting is readable only by its creator, anyone in its sharedWith list, or a manager/admin — not by every Recap user by default. A personal meeting remains creator-only, unchanged. Only an admin can create a business: 'personal' meeting — enforced by rules now, not just hidden in the UI. Write access (update/delete) on existing documents is unchanged in this phase — see Phase 3 for the new shared-write case.

Given a non-personal meeting created by User A, never shared with User B, when User B (a regular staff member with Recap access, not manager/admin) tries to read it, then the read is denied. (This is the regression test proving the bug is actually fixed — it currently passes today, incorrectly.)
Given the same meeting, now with User B's uid added to sharedWith, when User B tries to read it, then the read succeeds.
Given the same never-shared meeting, when a manager or admin (User C) tries to read it, then the read succeeds — manager/admin oversight preserved per the open decision above.
Given a business: 'personal' meeting created by User A, when a manager/admin who is not the creator tries to read it, then the read is denied — personal stays creator-only, no manager override, exactly today's behavior.
Given a non-admin user (manager or staff) attempts to create a meeting with business: 'personal' by writing directly (bypassing the UI, which already hides this option from them), when the write is attempted, then it is denied — new in this phase, per Christie's plan-reviewer comment confirming "personal" must be exclusively hers to create, not just hidden in the UI.
Given Christie (admin) creates a meeting with business: 'personal', when the write is attempted, then it succeeds, unchanged from today.
Given a meeting document created before this feature existed, with no sharedWith field at all, when any read is evaluated, then the rule does not error — must use resource.data.get('sharedWith', []), not a bare field reference, since Firestore rules throw on referencing a genuinely missing map/array field. Second-model review confirmed .get(key, default) only substitutes the default when the key is absent, not when it's explicitly null — uid in null still throws. Low risk given this repo's own invariant to strip null/undefined fields before every write (AGENTS.md), but noted here as an explicit assumption rather than left implicit: no code path in this app ever writes sharedWith: null.

Firebase safety checklist

  • Rule change only, in /Users/christiehubley/studio-hub/firestore.rules, the match /meetings/{docId} block (lines 388-404) — allow read gets the sharedWith fix, allow create gets the admin-only-personal addition, allow update, delete unchanged in this phase.
  • New emulator test cases added to the existing studio-hub/rules.test.js suite (currently 29/29 passing) — write the failing tests first (they should fail against today's rule, proving the bug is real), then apply the fix, then green.
  • Deploy: firebase deploy --only firestore:rules from studio-hub/ — per standing project policy, do not deploy until Christie says the literal phrase "approved to change firebase," separate from and in addition to tests passing.
  • No new collection, no schema change — existing sharedWith field just becomes load-bearing.

Phase 2 — Retroactive meeting-to-thread linking

Acceptance criteria

From an already-saved meeting's detail view (showMeetingDetail, meetings.html flow), Christie can link it to a previous meeting into a thread — the same outcome as the "Link to previous meeting" picker on the pre-processing screen, just usable after the fact.

Low-risk by construction: the actual linking logic already exists, fully general, and is not tied to "new meeting" in any way — linkMeetingToThread(newMeetingId, meetingData, threadLink) (js/app.js:1299-1360) takes two meeting IDs and a thread-link description, batches the writes (new thread creation or append-to-existing-chain, plus threadPrevMeetingId/threadNextMeetingId pointers on both meetings), and commits atomically. This phase reuses it unchanged — it only needs a new UI entry point, not new write logic.
Given two saved, unlinked meetings, viewing the newer one's detail page, when Christie picks the older one as "this follows," then both meetings get linked into a new thread (or the older meeting's existing thread, if it already has one), identically to what happens today when linking at creation time.
Given a candidate "previous meeting" that is already linked forward to a different next meeting (i.e. it already has threadNextMeetingId set), when Christie tries to pick it as the link target, then it is not offered as a valid choice — carries forward the same constraint the existing creation-time picker already enforces (selectThreadForLink, js/app.js:1218-1241, queries for the thread's last meeting specifically), so retroactive linking cannot silently overwrite/corrupt an existing chain.
Given a meeting that is already part of a thread, viewed from its detail page, when Christie opens the linking control, then it's clear this meeting already belongs to a thread (shows which one) rather than presenting a confusing "link" action that would create a conflicting second link.
Given the batched write partially fails (network drop mid-commit), when that happens, then nothing is left half-linked — batch.commit() is already atomic (existing behavior, unchanged), and the UI surfaces the failure via the existing catch/showToast pattern at js/app.js:1356-1360.

Firebase safety checklist

  • updateDoc-equivalent batch updates only (existing batch.update() calls, unchanged) — no setDoc overwrite of either meeting document.
  • No new collection, no rules change — threads already has a rule (allow read, write: if isManagerOrAbove() || hasAppAccess('recap')) and this phase writes to it exactly the way the existing creation-time flow already does.
  • No emulator test needed beyond what already exists for linkMeetingToThread's write shape (none currently exist — note this as a real gap: there is no existing test coverage of linkMeetingToThread today, retroactive or not; adding this phase is a reasonable place to add the first one).

Phase 3 — Interactive sharing (shared users can check things off, live)

Acceptance criteria

Someone a meeting is shared with can toggle action-item completion themselves, and both sides see the change without reloading the page.

Resolved (Sep 4, 2026) — how far write access extends for a shared user. Christie delegated this call. Decision: (a) any shared user can toggle any item's done state — not restricted to only items assigned to them. Simplest to build and explain, and matches how the summary screen already works for the owner (anyone editing it can already check off anyone's item, per the drag-and-drop reassignment work shipped the previous session, commit 2c7f0f4, Sep 3, 2026). The alternative (restrict each shared user to only their own assigned items) was rejected for v1: it requires resolving assignee identity (Phase 4's own open decision, resolved below) and Firestore rules cannot cheaply enforce "only your own array entry changed" inside a nested array of maps — it would end up UI-enforced only, not rules-enforced, unless paired with a Cloud Function (this project has no Cloud Functions infrastructure today — confirmed, everything here is a direct client SDK write gated by rules). Revisit only if (a) turns out to matter in practice.
Resolved (Sep 4, 2026) — honest limit of rules-based write scoping, accepted. Christie delegated this call. Decision: ship with the cheap rules-only version, accept the documented residual risk below rather than building a Cloud Function to close it. The rule: allow update if request.auth.uid in resource.data.get('sharedWith', []) AND the only top-level field that changed is summary (i.e. title, createdBy, sharedWith, business, date etc. are all untouched) — enforceable via request.resource.data.diff(resource.data).affectedKeys(). This stops a shared user from reassigning ownership, changing who it's shared with, or deleting the meeting. It does not stop a shared user from rewriting the entire summary object client-side (e.g. deleting someone else's item, not just toggling done) — Firestore rules cannot cheaply diff inside a nested array of maps. The UI will only ever send a done-toggle, but a technically savvy shared user could call the SDK directly and write more than that. Accepted as a real residual risk for v1 — the alternative (a Cloud Function-mediated toggle for true field-level enforcement) is real infrastructure this project doesn't have today, and this risk only matters if a shared user is both technically capable and motivated to bypass the UI, on a document they were already trusted enough to be shared with. Revisit only if that stops being a safe assumption.
Given User A shares a meeting with User B, when User B opens it and checks off an item, then the write succeeds, and User A's already-open view of the same meeting updates without a manual reload (requires a real-time listener — onSnapshot is not used anywhere in Recap today; every read is currently a one-time .get(), confirmed by grep. This phase introduces the app's first live listener).
Given User B is not in sharedWith for a given meeting and is not its creator or a manager/admin, when User B attempts to write to it directly (bypassing the UI), then the write is denied by rules — the UI not offering the control is not the only guard.
Given User B is validly in sharedWith, when User B's write (bypassing the UI) touches any top-level field other than summary in the same request — e.g. also setting sharedWith or createdBy, then the whole write is denied — affectedKeys().hasOnly(['summary']) is an all-or-nothing gate on the request, not a partial-accept. (Named explicitly here per second-model review — this exact case was already promised in the Firebase safety checklist's emulator test list but had no matching BDD scenario.)
Given User B has the shared view open and User A deletes the meeting or revokes B's share, when that happens, then User B's live listener reflects it (the doc disappears from their view or a permission-denied is handled gracefully) rather than erroring visibly or leaving stale UI.
Given two people with the meeting open at once both toggle different items within a second of each other, when both writes land, then neither overwrites the other. Second-model review flagged that "recompute from the latest live snapshot before writing" is necessary but not sufficient — that's still a classic read-modify-write race if both toggles happen inside the same window, and only genuinely prevented by wrapping the toggle in runTransaction() (re-reading the doc inside the transaction and retrying on conflict) or a surgical field-path update targeting just that one item's done flag, not a whole-array rewrite. This is not yet a solved implementation detail — it's the actual requirement Phase 3's implementation must satisfy; do not implement this toggle as a plain read-then-updateDoc pair and assume the "recompute from latest snapshot" framing alone covers it.

Firebase safety checklist

  • Rules change (second one in this plan): a new allow update branch on match /meetings/{docId} for shared, non-manager users, scoped as described above. Same deploy gate as Phase 1 — needs "approved to change firebase" separately, even if Phase 1 already got approval.
  • New emulator tests: shared user can toggle when only summary changes; shared user's write denied when any other top-level field is touched in the same request; non-shared user's write still denied.
  • updateDoc, not setDoc — the client should send a minimal update, not the full document.
  • First use of onSnapshot in this codebase — needs explicit listener cleanup (unsubscribe on navigating away) to avoid leaks, following whatever pattern is established when this is actually designed in detail (not yet — no existing precedent in this repo to point to).

Phase 4 — Per-person "My Open Tasks" cross-meeting view

Acceptance criteria

Any logged-in user can see every action item assigned to them, across every meeting and thread they have access to, in one place — not per-meeting, and not dependent on remembering which meeting it came from.

Resolved (Sep 4, 2026) — assignee identity is currently just a text label, not a user reference. Christie delegated this call. Decision: (a) name-string matching against the logged-in user's name field from their users doc — cheap, no schema change — paired with a visible "not mine" dismiss affordance so a mismatch is a one-tap fix, not a silent miss. beforeNextMeeting[].assignee is free text, generated by the AI from the transcript (e.g. "Christie", "Julia", or "Unassigned (needs assignment)" per the server prompt rules) or typed/edited by a human — it is never a user uid, so exact matching will miss nicknames/typos/AI misspellings ("Christie" vs "Christy" vs "Chris"). The alternative — a real uid-backed assignee field, added alongside or replacing the text label — is reliable but a genuine schema change touching every place assignee is read or written (rendering, editing, the drag-and-drop reassignment shipped this same session, the AI summarization prompt, sharing/display): a bigger phase than a one-line query filter. Treated as a real follow-up if name-matching proves too unreliable in practice, not built now.
Given User A is assigned items across three different meetings, some in threads, some not, some already checked off, when User A opens "My Open Tasks," then every still-open item assigned to them appears, each identifiable back to its source meeting (title, date, and thread if any).
Given an item is checked off from this view, when that happens, then it writes back to that item's actual meeting document (same underlying data as Phase 3's toggle, not a separate copy) and disappears from this rollup.
Given a meeting the user has no read access to (per Phase 1's fixed rule — not their own, not shared with them, and they're not manager/admin), when this view queries for their items, then nothing from that meeting appears — this view must respect the same access rules, not bypass them via a broader query.
Given the assignee text is "Unassigned (needs assignment)", when this view is built, then those items never match anyone's "my tasks" — they need their own separate visibility (out of scope for this phase, worth a future "Unassigned" admin view, not building it here).
Given a name-string match false positive (e.g. an item genuinely meant for a different "Chris" incorrectly matched to this user), when the user taps "not mine" on it, then it's removed from their "My Open Tasks" view only — the underlying item and its assignee text on the source meeting are untouched, and it does not reappear for this user on a later reload of this view. (Second-model review flagged this as the load-bearing mitigation for the chosen name-matching approach — Phase 4 has no BDD coverage without this scenario.)

Firebase safety checklist

  • Mostly read-only — one small new write: the "not mine" dismiss needs to persist per-user (the BDD above requires it survive a reload), most naturally as a self-writable array field (e.g. dismissedTaskKeys) on the user's own users/{uid} doc — a user writing only their own dismiss list onto their own document is a low-risk, narrowly-scoped write, but it's still a new field this phase introduces and needs its own updateDoc (not setDoc) and a corresponding allow to self-write that one field, not full self-write access to the whole users doc.
  • No new collection if approach (a) is chosen. If (b) is chosen, no new collection either, but a migration question appears (backfilling existing meetings' assignee text into uids) — flag as its own sub-decision if (b) is picked.
  • Depends on Phase 1 being live — without the rule fix, this view's query would either over-expose (if run with elevated access) or under-return (if naively scoped) other people's meetings.

Phase 5 — "Review open tasks" rollup across a set of meetings

Acceptance criteria

Christie can select a set of meetings — first version: a single thread — and see one consolidated, deduplicated-by-person list of everything still open across all of them, to answer "what's still standing after a few sessions."

Scoped to one thread at a time for v1 — a thread is already a natural, existing grouping (a bounded, ordered chain of meetings), versus an arbitrary multi-select across any meetings which is a fuzzier UI problem (what's the selection model? date range? checkboxes across a long list?) with no clear existing precedent in this app. Generalizing beyond "one thread" is a reasonable v2 if v1 proves useful.
Given a thread with 4 linked meetings, each with its own open and closed action items, when Christie opens "Review open tasks" for that thread, then she sees one list, grouped by assignee, of every item still open across all 4 meetings — each item still traceable to which specific meeting it came from.
Given the same person appears as assignee across multiple meetings in the thread with different open items each time, when the rollup renders, then their items are grouped together under their name once, not repeated per-meeting under separate headers.
Given a meeting in the thread hasn't been retroactively linked yet (Phase 2 not run on it, or run after this thread's rollup was last viewed), when the rollup is generated, then it only reflects meetings actually in the thread at generation time — it's a live query against current thread membership, not a cached/stale list.
Given Christie doesn't have read access to one meeting nominally in the thread (edge case — e.g. a personal-business meeting somehow linked in, or an access change mid-thread), when the rollup runs, then it silently omits what it can't read rather than erroring the whole view.

Firebase safety checklist

  • Read-only phase, same access-rule dependency as Phase 4.
  • Reuses Phase 4's assignee-identity decision — do not re-litigate it separately here.
  • No new collection, no rules change.

Completeness check

Phase 1 is fully independent and should ship first regardless of the rest — it's a correctness fix, not a feature. Phase 2 is independent of everything else (reuses existing, unchanged write logic) and could ship any time. Phase 3's dependency on Phase 1 is conceptual/UX, not a hard technical blocker — second-model review confirmed Phase 3's new write-rule branch would function correctly on its own regardless of whether Phase 1 has shipped, since today's over-broad read rule doesn't interfere with Phase 3's write gate. The real reason to sequence Phase 1 first is that shared write only makes sense once shared read actually means something — building Phase 3 first would let a shared user edit a meeting that (pre-Phase-1) everyone with Recap access could already read anyway, which defeats the point. Phases 4 and 5 depend on Phase 1 for correct scoping and share one open decision (assignee identity) that should be resolved once, not separately per phase. Phase 5 benefits from Phase 2 (retroactive linking) actually being used, but isn't blocked by it — a thread with only forward-linked meetings still works.
