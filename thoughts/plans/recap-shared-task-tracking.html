    && request.resource.data.createdBy == request.auth.uid;

      resource.data.createdBy == request.auth.uid

    );
  allow update, delete: if (isManagerOrAbove() || hasAppAccess('recap'))

}

The above is what's live in production today (unchanged). Acceptance criteria

Resolved (Sep 4, 2026, second review round — real bug, found independently by both a fresh Claude pass and Codex) — the update rule had a bypass that fully defeated the create restriction above. The existing (unchanged-until-now) allow update branch never checked the new value of business at all — only who's making the request. That meant: (1) any non-admin could create an ordinary meeting, then immediately update it to business: 'personal', since the creator branch doesn't care what fields changed; (2) worse, a manager who isn't even the creator could flip someone else's non-personal meeting to personal (the manager branch only required the OLD value to be non-personal), which would then lock even other managers out of reading it under the unchanged read rule. Fixed by splitting update and delete into separate rules (required anyway — request.resource.data doesn't exist on a delete, so it can't safely share a combined rule with an update-time field check) and adding the same business != 'personal' || isAdmin() guard to allow update, plus pinning createdBy so a creator can't reassign ownership via update either (a related gap Codex separately flagged).     && request.resource.data.createdBy == request.auth.uid
    && (request.resource.data.business != 'personal' || isAdmin());

  allow read: if (isManagerOrAbove() || hasAppAccess('recap'))
    && (
      resource.data.createdBy == request.auth.uid
      || (resource.data.business != 'personal' && (
           request.auth.uid in resource.data.get('sharedWith', [])
           || isManagerOrAbove()

    );

    && (resource.data.business == 'personal' || request.resource.data.business != 'personal' || isAdmin())
    && request.resource.data.createdBy == resource.data.createdBy
    && (
      resource.data.createdBy == request.auth.uid

    && (

Refined in fourth review round — the update-rule personal guard was punishing an unintended case. The original condition, request.resource.data.business != 'personal' || isAdmin(), applies on every update whose resulting document is personal — not just conversions into personal. Combined with the read/delete rules (which never require isAdmin() for a creator acting on their own document), this meant a non-admin creator of an already-personal meeting could read and delete it forever, but could never update it again — not even an unrelated field like the title — unless they happened to currently be admin. Two real (if narrow) ways this would bite: a legacy personal meeting created by a non-admin before this rule ships (exactly the pre-existing gap this plan documents as currently live and un-enforced), or an admin who creates a personal meeting and is later demoted. Christie confirmed separately that only she has ever created a personal meeting through the app's actual UI (it's always been admin-only there) — so this isn't a live risk to her today, but it's a real, previously undocumented rule-design flaw worth closing since the fix is free. Refined to: resource.data.business == 'personal' || request.resource.data.business != 'personal' || isAdmin() — only requires isAdmin() when a document is actually transitioning into 'personal'; a document that's already personal and staying personal can be edited by its own creator regardless of their current role, matching how read/delete already worked.
