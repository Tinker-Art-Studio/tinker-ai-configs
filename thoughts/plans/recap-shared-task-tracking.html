Phase 1 — Fix the meetings read/write rule to actually gate on sharing

Acceptance criteria

A non-personal meeting is readable only by its creator, anyone in its sharedWith list, or a manager/admin — not by every Recap user by default. A personal meeting remains creator-only, unchanged. Only an admin can create a business: 'personal' meeting, and a non-admin cannot get around that by creating a normal meeting and then updating it to personal afterward — closed at both the create and update rule, not just create. Existing Recap queries against meetings keep working for the population they're meant to serve — this phase is not just a rules edit, it requires auditing and fixing every query that would otherwise be silently rejected outright once the rule actually checks sharedWith (see the query audit below). Everything in this Acceptance Criteria section is now backed by an actual passing/failing run against a live Firestore emulator, not just rules-text reasoning — see "Empirically verified" below.

Resolved (Sep 4, 2026, second review round — real bug, found independently by both a fresh Claude pass and Codex) — the update rule had a bypass that fully defeated the create restriction above. The existing (unchanged-until-now) allow update branch never checked the new value of business at all — only who's making the request. That meant: (1) any non-admin could create an ordinary meeting, then immediately update it to business: 'personal', since the creator branch doesn't care what fields changed; (2) worse, a manager who isn't even the creator could flip someone else's non-personal meeting to personal (the manager branch only required the OLD value to be non-personal), which would then lock even other managers out of reading it under the unchanged read rule. Fixed by splitting update and delete into separate rules (required anyway — request.resource.data doesn't exist on a delete, so it can't safely share a combined rule with an update-time field check) and adding the same business != 'personal' || isAdmin() guard to allow update, plus pinning createdBy so a creator can't reassign ownership via update either (a related gap Codex separately flagged). See the full corrected rule block below. 
match /meetings/{docId} {
  allow create: if (isManagerOrAbove() || hasAppAccess('recap'))
    && request.resource.data.createdBy == request.auth.uid
    && (request.resource.data.business != 'personal' || isAdmin());

  allow read: if (isManagerOrAbove() || hasAppAccess('recap'))
    && (
      resource.data.createdBy == request.auth.uid
      || (resource.data.business != 'personal' && (
           request.auth.uid in resource.data.get('sharedWith', [])
           || isManagerOrAbove()
         ))
    );

  allow update: if (isManagerOrAbove() || hasAppAccess('recap'))
    && (request.resource.data.business != 'personal' || isAdmin())
    && request.resource.data.createdBy == resource.data.createdBy
    && (
      resource.data.createdBy == request.auth.uid
      || (resource.data.business != 'personal' && isManagerOrAbove())
    );

  allow delete: if (isManagerOrAbove() || hasAppAccess('recap'))
    && (
      resource.data.createdBy == request.auth.uid
      || (resource.data.business != 'personal' && isManagerOrAbove())
    );
}

  2. The same query with a business filter added → succeeds, confirming the fix works.
  3. A non-admin creator updating their own non-personal meeting to business: 'personal' (the bypass) → correctly denied.
  4. A manager updating someone else's non-personal meeting to business: 'personal' → correctly denied.
  5. A non-admin attempting to create a business: 'personal' meeting → correctly denied.
  6. An admin creating a business: 'personal' meeting → correctly succeeds.
  7. A creator attempting to reassign createdBy via update → correctly denied.
  8. An ordinary, legitimate edit (creator updating their own non-personal meeting's title) → correctly succeeds — confirms the fix doesn't regress normal editing.
All 8 passed as intended. This satisfies this repo's own AGENTS.md requirement ("write a failing emulator test first, then fix, then green") in spirit — the throwaway script IS that failing-then-passing proof; the equivalent permanent test cases still need to be written into studio-hub/rules.test.js itself during execution (this was a planning-phase verification, not the actual implementation).

Phase 2 — Retroactive meeting-to-thread linking

Acceptance criteria

From an already-saved meeting's detail view (showMeetingDetail, meetings.html flow), Christie can link it to a previous meeting into a thread — the same outcome as the "Link to previous meeting" picker on the pre-processing screen, just usable after the fact — without being able to corrupt an existing thread chain by picking a target that's already linked forward to something else.

Corrected (Sep 4, 2026, second review round) — the claimed existing chain-safety protection does not actually exist; verified directly, this plan's first draft was wrong. The first draft claimed selectThreadForLink "queries for the thread's last meeting specifically" and that this phase could safely reuse that existing constraint. Read the actual function (js/app.js:1218-1243) directly: its query is where('threadId','==',thread.id).orderBy('createdAt','desc').limit(1) — it returns the most recently created meeting in the thread, and never checks threadNextMeetingId at all, despite its own code comment claiming otherwise ("Find the last meeting in this thread (the one with no threadNextMeetingId)"). The comment describes intent that was never actually implemented. This phase cannot just add a new UI entry point to unchanged logic — the underlying picker function itself needs a real fix, which benefits the existing creation-time flow too, not just this new retroactive path.
Real fix, verified against the data model: every meeting is written with threadNextMeetingId: null explicitly set at creation (js/app.js:1446) — never left absent — so .where('threadNextMeetingId', '==', null) is a reliable, correct Firestore filter for "not yet linked forward" (this would NOT work if the field were sometimes simply missing instead of explicitly null; confirmed it never is). The corrected query: 
db.collection('meetings')
  .where('threadId', '==', thread.id)
  .where('threadNextMeetingId', '==', null)
  .where('business', 'in', ['tinker', 'clayhub', 'both'])  // Phase 1 provability fix, same query
  .limit(1)
  .get();
This single change fixes both problems at once: it's now rule-provable (closing this query's entry in Phase 1's audit table) AND it actually implements the "last meeting in thread" guarantee the original code comment only claimed. A well-formed chain has exactly one meeting per thread with threadNextMeetingId == null; if this query ever returns more than one, that's a sign of an existing data problem (see BDD below), not something to silently paper over by picking one arbitrarily.
Time-of-check/time-of-write race, flagged by Codex — real, needs a transaction. Even with the corrected query above, there's a window between "UI shows this meeting as a valid, unlinked target" and "the link write actually commits" where a second linking action (this feature being used twice concurrently, unlikely but not impossible) could slip in. linkMeetingToThread() (js/app.js:1299-1362) needs to change from a plain batch.commit() to runTransaction(), re-reading the target meeting's threadNextMeetingId inside the transaction immediately before writing and aborting (surfacing a "someone else just linked this, please retry" toast) if it's no longer null. This changes existing, shipped behavior for the creation-time linking flow too (both paths call the same function) — not purely additive, worth Christie knowing this touches already-working code, not just new code.
Self-link and same-thread prevention — scoped for v1. The picker must exclude the meeting currently being viewed from its own candidate list (trivial). Full cycle detection across arbitrarily deep chains is out of scope for v1 — the accepted, low-consequence failure mode is a confusing thread structure, not data loss or a security issue, and building general cycle detection for a feature this narrow is disproportionate. What v1 does guard: the transaction re-check above already prevents the concurrent-double-link case, and self-link is a simple exclusion, not a graph-walk.
Given two saved, unlinked meetings, viewing the newer one's detail page, when Christie picks the older one as "this follows," then both meetings get linked into a new thread (or the older meeting's existing thread, if it already has one), identically to what happens today when linking at creation time.
Given a candidate "previous meeting" that is already linked forward to a different next meeting (i.e. it already has threadNextMeetingId set to something other than null), when Christie opens the picker, then it is not offered as a valid choice — via the corrected query above, not the previously-claimed-but-nonexistent protection.
Given the corrected query returns more than one candidate "last meeting" for a single thread (a sign of existing chain corruption, however it happened), when that's detected, then the picker surfaces this as an error rather than silently picking one — do not mask a real data problem.
Given two people (or two tabs) attempt to link something to the same target meeting at nearly the same time, when the second transaction's re-check finds threadNextMeetingId is no longer null, then the second attempt is aborted with a clear "someone else just linked this" message — no corrupted chain, no silent overwrite.
Given a meeting that is already part of a thread, viewed from its detail page, when Christie opens the linking control, then it's clear this meeting already belongs to a thread (shows which one) rather than presenting a confusing "link" action that would create a conflicting second link.
Given the current meeting is offered in its own "link to" candidate list, when the picker is built, then it's excluded — a meeting cannot be linked to itself.
Given the transaction fails for any other reason (network drop mid-commit), when that happens, then nothing is left half-linked — runTransaction() guarantees atomicity, and the UI surfaces the failure via the existing catch/showToast pattern (js/app.js:1358-1360), adapted for the transaction wrapper.

Firebase safety checklist

  • runTransaction(), not a plain batch.commit() — a real behavior change to existing, shipped code (linkMeetingToThread), not purely additive.
  • Query fix (threadNextMeetingId == null + business filter) lands as part of this phase, shared with Phase 1's query audit for this same function — don't fix it twice in two different phases.
  • No new collection, no rules change — threads already has a rule (allow read, write: if isManagerOrAbove() || hasAppAccess('recap')) and this phase writes to it exactly the way the existing creation-time flow already does.
  • New emulator/unit test coverage needed: there is no existing test coverage of linkMeetingToThread or selectThreadForLink today — this phase is a reasonable place to add the first tests for both, including the corrected query and the transaction re-check.

Phase 3 — Interactive sharing (shared users can check things off, live)

Acceptance criteria

Someone a meeting is shared with can toggle action-item completion themselves, and both sides see the change without reloading the page.

Resolved (Sep 4, 2026) — how far write access extends for a shared user. Christie delegated this call. Decision: (a) any shared user can toggle any item's done state — not restricted to only items assigned to them. Simplest to build and explain, and matches how the summary screen already works for the owner (anyone editing it can already check off anyone's item, per the drag-and-drop reassignment work shipped the previous session, commit 2c7f0f4, Sep 3, 2026). The alternative (restrict each shared user to only their own assigned items) was rejected for v1: it requires resolving assignee identity (Phase 4's own open decision, resolved below) and Firestore rules cannot cheaply enforce "only your own array entry changed" inside a nested array of maps — it would end up UI-enforced only, not rules-enforced, unless paired with a Cloud Function (this project has no Cloud Functions infrastructure today — confirmed, everything here is a direct client SDK write gated by rules). Revisit only if (a) turns out to matter in practice.
Resolved (Sep 4, 2026) — honest limit of rules-based write scoping, accepted. Christie delegated this call. Decision: ship with the cheap rules-only version, accept the documented residual risk below rather than building a Cloud Function to close it. The rule: allow update if resource.data.business != 'personal' AND request.auth.uid in resource.data.get('sharedWith', []) AND the only top-level field that changed is summary (i.e. title, createdBy, sharedWith, business, date etc. are all untouched) — enforceable via request.resource.data.diff(resource.data).affectedKeys(). The business != 'personal' clause was added in second review round — Codex correctly pointed out the first draft's shared-write branch didn't explicitly exclude personal meetings, so a malformed or legacy document with both business: 'personal' and a populated sharedWith could have been blindly writable by a listed user even though the read rule already denies them access to it — an independent gap from the read side, not automatically closed by it, since Firestore evaluates write rules on their own terms regardless of whether a prior read would have succeeded. This stops a shared user from reassigning ownership, changing who it's shared with, or deleting the meeting. It does not stop a shared user from rewriting the entire summary object client-side (e.g. deleting someone else's item, not just toggling done) — Firestore rules cannot cheaply diff inside a nested array of maps. The UI will only ever send a done-toggle, but a technically savvy shared user could call the SDK directly and write more than that. Accepted as a real residual risk for v1 — the alternative (a Cloud Function-mediated toggle for true field-level enforcement) is real infrastructure this project doesn't have today, and this risk only matters if a shared user is both technically capable and motivated to bypass the UI, on a document they were already trusted enough to be shared with. Revisit only if that stops being a safe assumption.
Given User A shares a meeting with User B, when User B opens it and checks off an item, then the write succeeds, and User A's already-open view of the same meeting updates without a manual reload (requires a real-time listener — onSnapshot is not used anywhere in Recap today; every read is currently a one-time .get(), confirmed by grep. This phase introduces the app's first live listener).
Given User B is not in sharedWith for a given meeting and is not its creator or a manager/admin, when User B attempts to write to it directly (bypassing the UI), then the write is denied by rules — the UI not offering the control is not the only guard.
Given User B is validly in sharedWith, when User B's write (bypassing the UI) touches any top-level field other than summary in the same request — e.g. also setting sharedWith or createdBy, then the whole write is denied — affectedKeys().hasOnly(['summary']) is an all-or-nothing gate on the request, not a partial-accept. (Named explicitly here per second-model review — this exact case was already promised in the Firebase safety checklist's emulator test list but had no matching BDD scenario.)
Given User B has the shared view open and User A deletes the meeting or revokes B's share, when that happens, then User B's live listener reflects it (the doc disappears from their view or a permission-denied is handled gracefully) rather than erroring visibly or leaving stale UI.
Given two people with the meeting open at once both toggle different items within a second of each other, when both writes land, then neither overwrites the other. First review round flagged that "recompute from the latest live snapshot before writing" is necessary but not sufficient — that's still a classic read-modify-write race if both toggles happen inside the same window. Second review round (Codex) corrected the fix itself, not just the diagnosis: a "surgical field-path update targeting just that one item's done flag" is not actually available under the current data shape — beforeNextMeeting[].items[] is an array of maps, and Firestore field paths cannot address an array element by numeric index, so there is no such surgical update to reach for. Given this schema, runTransaction() (re-reading the doc inside the transaction and retrying on conflict) is the only viable mechanism, not one of two options. This is not yet a solved implementation detail — it's the actual requirement Phase 3's implementation must satisfy; do not implement this toggle as a plain read-then-updateDoc pair. (An ID-keyed map or subcollection instead of an array would make true field-path updates possible, but that's a real schema change, out of scope for this plan.)

  • Rules change (another change to the same match /meetings/{docId} block Phase 1 already revised): a new allow update branch for shared, non-manager users, scoped as described above, including the business != 'personal' guard added in second review round. Same deploy gate as Phase 1 — needs "approved to change firebase" separately, even if Phase 1 already got approval.

Phase 4 — Per-person "My Open Tasks" cross-meeting view

Acceptance criteria

Any logged-in user can see every action item assigned to them, across every meeting and thread they have access to, in one place — not per-meeting, and not dependent on remembering which meeting it came from.

Resolved (Sep 4, 2026) — assignee identity is currently just a text label, not a user reference. Christie delegated this call. Decision: (a) name-string matching against the logged-in user's name field from their users doc — cheap, no schema change — paired with a visible "not mine" dismiss affordance so a mismatch is a one-tap fix, not a silent miss. beforeNextMeeting[].assignee is free text, generated by the AI from the transcript (e.g. "Christie", "Julia", or "Unassigned (needs assignment)" per the server prompt rules) or typed/edited by a human — it is never a user uid, so exact matching will miss nicknames/typos/AI misspellings ("Christie" vs "Christy" vs "Chris"). The alternative — a real uid-backed assignee field, added alongside or replacing the text label — is reliable but a genuine schema change touching every place assignee is read or written (rendering, editing, the drag-and-drop reassignment shipped this same session, the AI summarization prompt, sharing/display): a bigger phase than a one-line query filter. Treated as a real follow-up if name-matching proves too unreliable in practice, not built now.
Given User A is assigned items across three different meetings, some in threads, some not, some already checked off, when User A opens "My Open Tasks," then every still-open item assigned to them appears, each identifiable back to its source meeting (title, date, and thread if any).
Given an item is checked off from this view, when that happens, then it writes back to that item's actual meeting document (same underlying data as Phase 3's toggle, not a separate copy) and disappears from this rollup.
Given a meeting the user has no read access to (per Phase 1's fixed rule — not their own, not shared with them, and they're not manager/admin), when this view queries for their items, then nothing from that meeting appears — this view must respect the same access rules, not bypass them via a broader query.
Given the assignee text is "Unassigned (needs assignment)", when this view is built, then those items never match anyone's "my tasks" — they need their own separate visibility (out of scope for this phase, worth a future "Unassigned" admin view, not building it here).
Given a name-string match false positive (e.g. an item genuinely meant for a different "Chris" incorrectly matched to this user), when the user taps "not mine" on it, then it's removed from their "My Open Tasks" view only — the underlying item and its assignee text on the source meeting are untouched, and it does not reappear for this user on a later reload of this view. (Second-model review flagged this as the load-bearing mitigation for the chosen name-matching approach — Phase 4 has no BDD coverage without this scenario.)

Firebase safety checklist

  • Mostly read-only — one small new write: the "not mine" dismiss needs to persist per-user (the BDD above requires it survive a reload), most naturally as a self-writable array field (e.g. dismissedTaskKeys) on the user's own users/{uid} doc. Corrected in second review round: no rules change needed for this at all. First draft assumed a new sibling allow update rule would be required, scoped to just this one field — checked the actual existing self-update rule (studio-hub/firestore.rules:117-121) directly and it already permits this: it only pins specific fields from changing (role, appAccess, studios, active, via fieldUnchanged()) — it does not restrict what else may change, so a user writing a new dismissedTaskKeys field onto their own doc already works today, no rule edit required. Codex separately flagged that adding an unnecessary sibling allow update rule here would have been actively risky, not just redundant — Firestore ORs sibling allow rules together, so a second, less-careful rule on users could accidentally widen what every one of the 21 apps sharing this file's self-update path allows. Use the existing rule as-is; add nothing.
  • No new collection if approach (a) is chosen. If (b) is chosen, no new collection either, but a migration question appears (backfilling existing meetings' assignee text into uids) — flag as its own sub-decision if (b) is picked.
  • Depends on Phase 1 being live — without the rule fix, this view's query would either over-expose (if run with elevated access) or under-return (if naively scoped) other people's meetings.

Phase 5 — "Review open tasks" rollup across a set of meetings

Acceptance criteria

Christie can select a set of meetings — first version: a single thread — and see one consolidated, deduplicated-by-person list of everything still open across all of them, to answer "what's still standing after a few sessions."

Scoped to one thread at a time for v1 — a thread is already a natural, existing grouping (a bounded, ordered chain of meetings), versus an arbitrary multi-select across any meetings which is a fuzzier UI problem (what's the selection model? date range? checkboxes across a long list?) with no clear existing precedent in this app. Generalizing beyond "one thread" is a reasonable v2 if v1 proves useful.
Given a thread with 4 linked meetings, each with its own open and closed action items, when Christie opens "Review open tasks" for that thread, then she sees one list, grouped by assignee, of every item still open across all 4 meetings — each item still traceable to which specific meeting it came from.
Given the same person appears as assignee across multiple meetings in the thread with different open items each time, when the rollup renders, then their items are grouped together under their name once, not repeated per-meeting under separate headers.
Given a meeting in the thread hasn't been retroactively linked yet (Phase 2 not run on it, or run after this thread's rollup was last viewed), when the rollup is generated, then it only reflects meetings actually in the thread at generation time — it's a live query against current thread membership, not a cached/stale list.
Corrected in second review round — the "silently omits what it can't read" scenario was false for the actual query this phase would use. A query like where('threadId', '==', threadId) does not return a partial, readable-only subset when some matching documents are outside the requester's access — the same rules-are-not-filters behavior from Phase 1's query audit applies here too: Firestore rejects the whole query outright unless every possible result is provably readable from the query's own where clauses. This phase's query needs the same treatment as Phase 1's fixes — either a business filter (for the manager/admin case) or the two-query own-plus-shared merge pattern (for a staff viewer), reusing the same queryReadableMeetings()-style helper recommended in Phase 1, not a bespoke "catch the permission error per document" approach, which isn't how Firestore list queries actually fail.
Given a thread contains a meeting the viewer cannot read (e.g. never shared with them, and they're not manager/admin), when the rollup query is built using the same readable-scoping pattern as Phase 1/4, then that meeting is excluded from the results by construction — the query itself never asks for documents the viewer can't read, rather than asking for everything and hoping Firestore filters down to what's allowed.
