Plan: Notify an employee of a schedule change

App: Tinker Ticker (~/tinker-timeclock) · Registered: Sep 17 2026 · execution-ready: true · Status: BUILT + DEPLOYED Sep 18 2026 (499d8ea + d6c16cb, 681 tests, sw.js v18; a real send verified through the deployed endpoint) · v3 after two two-model design reviews and two implementation reviews (all findings folded in; see the Decisions log). Open follow-ups: the editor routes overrides by the mode it opened in, not per date; the five email endpoints are unauthenticated.

Goal: when a manager changes someone's schedule for specific dates — through the AI Schedule Changes tool or the schedule editor — they can tick "Notify employee of this change" (on by default), type a short reason, and the employee gets ONE email listing what changed on which dates, including removals, with the reason. The manager is told whether it went out.

Christie's decisions (Sep 17): checkbox defaults to CHECKED; removals (a date set to day off) are included and email too.

Research (read-only)

  • What exists: send-oneoff-shift-confirmation-email (Resend, one date per email, "Shift Confirmed" template in _lib/oneoff-reminder.js) fires only when a schedule-editor save adds an override whose note contains "Extra Shift" (sendOneOffReminderConfirmations, app.js ~8670). Recipient resolution: resolveReminderRecipient(uid, allUsers, employeeRoster) (schedule-helpers.js). Outcome toasts: toastEmailOutcome(outcome, label). Shift lookup for any date: getShiftForDate(schedule, dateStr, dayKey) (app.js ~3839).
  • AI path: renderAiEditResults renders one card per employee; handleAiSaveEdits merges each employee's overrides into the base schedule (or an active futureSchedule) and saves with saveSchedule(uid, { ...existing, overrides: merged }) — the whole-document spread + whole map from the in-memory list, the same write shape closed elsewhere on Sep 16 (note-leak fix). No email is sent from this path today.
  • Editor path: handleSaveSchedule saves the whole edited document (recurring + overrides + bounds, via omitEmptyMaps), then the Extra-Shift confirmation. A frozen pre-edit snapshot scheduleEditOriginalOverrides already exists for diffing.
  • Firestore: no new collection, no new field, no rules change. The only writes are the schedule saves that already happen. The email endpoint is a new Netlify function; like the four existing email functions it is unauthenticated (wishlist item — this plan does not widen the class, it adds one more of the same shape, and should be included when that item is done).
  • Tests: Netlify libs are unit-tested (_lib/*.test.js, enumerated in package.json); app.js wiring is source-pinned in schedule-editor-wiring.test.js; pure helpers go in schedule-helpers.js + schedule-helpers.test.js.

Phases

Phase 1 — The change list and the email, as pure functions

Acceptance (user outcome): given a schedule before and after a save and the dates that were touched, the app can say exactly what changed for a person, in words they'd understand, and render it as one email.

  • ONE resolver. getShiftForDate(schedule, dateStr, dayKey) MOVES from app.js into schedule-helpers.js (classic scripts share globals; every app.js caller is unchanged) and gets direct tests for the cases the review named: a date inside an active futureSchedule window resolves ONLY inside the future object (future override → future recurring → null, never the base); a base override applies regardless of base validFrom/validUntil while base recurring is bounded by them; a stored null is a day off, not fall-through; a window with a missing bound is open on that side.
  • diffScheduleDates(before, after, dates) in schedule-helpers.js — for each touched date, { date, before, after } via that resolver on the two full documents. Shifts are NORMALISED before comparison (studio defaults to 'tinker'; absent note ≡ ''), so a re-save of the same shift is dropped; a note-only change COUNTS and the row shows the note. Dates whose before and after are the same are dropped; output sorted by date, deduplicated.
  • applyScheduleEdits(doc, edits, today) in schedule-helpers.js — validates each edit (date key YYYY-MM-DD; a value is null or has both start and end as HH:MM, studio ∈ {tinker, clayhub}; anything else is REJECTED with a reason), routes EACH DATE to the map the resolver reads for that date (inside the future window → futureSchedule.overrides, else base overrides) — the current AI save routes the whole batch by whether the future is active TODAY, a latent bug the review found — and returns { after, fields, rejected } where fields is a list of [pathSegments, value] leaf updates (e.g. [['overrides','2026-09-29'], {…}]). Empty fields → nothing to write.
  • _lib/schedule-change.js: buildScheduleChangeEmail({ personName, adminName, changes, note }) → { subject, html, text }. One row per date: "Tue Sep 29 — now 5:50 PM–9:00 PM at Tinker (was 4:00 PM–9:00 PM)"; a removal: "now: day off (was 9:00 AM–3:00 PM at Clay Hub)"; an addition: "now … (you weren't scheduled)"; a shift note is shown on its row. The note, if any, under "Note from {adminName}". Everything escaped. The shared sendEmail gains an optional text (additive).

Phase 2 — The email endpoint

Acceptance: a POST with the person's email, the changes and the note sends one email via the shared Resend helper and answers { sent, reason } the way the other email functions do.

  • netlify/functions/send-schedule-change-email.js: validates the body (changes: a non-empty array of the Phase 1 shape, capped at 120 rows (the client truncates beyond that and passes `omitted`); note capped at 1000 chars; names capped) — a body outside those bounds is 400; no personEmail → { sent: false, reason: 'no-recipients' } with 200 (the reason string toastEmailOutcome already understands — the client resolves the recipient and should never POST without one, so this is defensive); Resend failure → { sent: false, reason: 'send-failed' }. No Firestore access.
  • Authentication: this endpoint is unauthenticated like the four existing email functions. Verifying a Firebase ID token server-side needs firebase-admin in the function (public-key verification needs no service account; a ROLE check would need Firestore, which is the blocked item). That is the wishlist's "unauthenticated email endpoints" work and is the NEXT queue item after this plan — it must cover all five functions in one change. Until then the caps above bound abuse.
Given a valid body When POSTed Then one email, { sent: true }
Given an empty changes array When POSTed Then 400, nothing sent — the client should never have called
Given Resend rejects When POSTed Then { sent: false, reason: 'send-failed' }, logged; the schedule save (already done client-side) is unaffected

Phase 3 — AI Schedule Changes: checkbox, note, touched-only save, email, outcome

Acceptance: on the AI results screen the manager sees "Notify employee(s) of these changes by email" (checked) and a "Reason / note" box; Apply saves the edits and, per employee, sends one email listing their changed dates; a toast per employee says sent / no email on file / did not send.

  • 3a — the write (emulator-tested): a new data-layer function applyScheduleEditsTransaction(uid, edits) does the read, the per-date routing (applyScheduleEdits) and the write in ONE transaction (implementation review: a plain read-then-update let another manager remove the future schedule in between, after which the leaf update recreated a bare futureSchedule.overrides that masked the base schedule), the write being ONE update() with FieldPath leaves (overrides.<date> / futureSchedule.overrides.<date>, plus updatedAt/By) — leaf replacement, so no stale key can leak and no map is ever written (the empty-map hazard cannot arise); the repo's own "updateDoc for a partial edit" rule. Emulator test proves unrelated dates, base/future siblings and bounds survive, and that a date inside an upcoming future window lands in the future map. handleAiSaveEdits: group the model's edits by resolved uid (it can name one person twice); per employee read FRESH via loadScheduleResult — ok:false → skipped "could not read" (never the in-memory copy), schedule:null → skipped as today; applyScheduleEdits; rejected edits are named in the status; write. Today's date is Denver-local, not UTC. Added to the "guard is wired into production" describe block of empty-map-guard.emulator.test.js.
  • 3b — the feature: markup in index.html above the Apply button: checkbox (checked) labelled "Notify employee(s) of these changes by email" and a note field labelled "Note to include (sent to everyone listed above)". After a successful write, if ticked and diffScheduleDates is non-empty: resolve the recipient; POST; collect the outcome. Recipient lookup FAILURE (the users read failed — a Result-shaped read replaces the [] fallback for this purpose) is its own outcome, "could not look up their email", distinct from "no email on file". The status line names everyone: "Applied: A, B. Emailed: A. NOT emailed: B (no email on file)." — ONE toast at most (toasts replace each other, so per-employee toasts would hide failures). Past dates are included (the manager chose to notify; untick to suppress).

Phase 4 — Schedule editor: the same checkbox and note on Save

Acceptance: when a manager saves a schedule after adding, editing or removing dated overrides, the same checkbox (checked) and note sit next to Save; the employee gets one email for the dates that actually changed versus when the editor was opened.

  • The editor edits EITHER the base maps or, when a future schedule is active today, the future's maps (openScheduleEditor swaps them in; the save's future branch writes them back). A frozen full pre-edit document snapshot (scheduleEditOriginalDoc) is taken at open; after a successful save the "after" document is the snapshot with the saved maps swapped into the same place the save wrote them. Diff = diffScheduleDates(originalDoc, afterDoc, touchedDates) where touched = keys in the union of the original and saved override maps whose values differ. Changes to recurring weekly hours are NOT emailed by this feature (the label says "date changes"); a removed override whose date falls back to a changed recurring shift shows the NEW recurring as "now" — correct, and stated here.
  • Replaces the Extra-Shift confirmation on editor saves. With the box checked by default, the old one-date "Shift Confirmed" email AND the new consolidated one would both go out on every Extra Shift; and unticking the box would still send the old one. So on editor saves the consolidated email is the ONLY schedule-change email; an Extra Shift date is a row like any other, with its note. Unticked → no email of either kind. sendOneOffReminderConfirmations is no longer called from the editor (retained, unreferenced-by-app, for the plan history — or deleted; decide at implementation).
  • The move gesture (Nov 11 → Nov 12) yields two rows: removed, added.
Given the editor is opened, one override is added and one existing one removed, box ticked When Save Then one email with two rows (added; removed → back to recurring or "not scheduled")
Given only recurring hours were changed When Save with the box ticked Then no email, toast "No date changes to notify about"

Given the employee has no email on file / the send fails When Save with the box ticked Then saved; the toast says which

Firebase safety checklist

  • Rules updated? Not needed — no new collection or field; the schedule saves are the existing ones under the existing timeclock_schedules manager rule.
  • Snapshot before bulk ops? N/A.
  • updateDoc not setDoc? YES for the AI path now: updateScheduleDates is an update() with FieldPath leaves — the repo's rule, literally. The editor path is unchanged.
  • Empty fields stripped? No map is written by the AI path at all (leaf updates); an edit with no valid dates is skipped before the write. Pinned by test.
  • Emulator test? Phase 3a has a real one (the leaf update against a document with unrelated dates, base/future siblings and bounds; a date inside an upcoming future window lands in the future map), plus the "wired into production" pin. The resolver, diff, apply and the email lib are unit-tested.
  • Console spot-check? After Phase 3 deploys: apply one AI edit to a real schedule, confirm only that date changed on the document and the email arrived.

Completeness check

Every phase is independently shippable. Interrupted after Phase 1 or 2: nothing user-visible changes. Interrupted after Phase 3: the AI tool notifies; the editor does not yet (it still sends the Extra-Shift confirmation as before). No data migration, so nothing is left half-done on any document.

Decisions log

  • Sep 17: checkbox defaults to checked; removals email too (Christie).
  • Sep 17: one note per batch on the AI screen, not per employee — the narrative is one request; per-employee notes can be added later if asked.
  • Sep 17: one email per employee per save, listing every changed date — not one per date like the Extra-Shift confirmation.
  • Sep 17: the AI path's save becomes touched-only (a sibling of the Sep 16 note-leak fix) rather than being left as a whole-document spread while adding a feature on top of it.
  • Sep 17 (implementation review, both models): the AI save is one TRANSACTION (read → route → leaf update on the version read); "nothing changed" is its own outcome, not an email failure; the editor's change email describes the PERSISTED document (re-read after the save), falling back to the synthetic one; the endpoint bounds every field (null body, real dates, HH:MM, studio/note/email lengths); the dead Extra-Shift endpoint, template, test and client functions were DELETED (an unauthenticated sender nothing calls); grid days keep stored fields the grid does not render. Follow-up queued: the EDITOR still routes every override to the map it opened in (base or future) rather than per date — a pre-existing gap the new diff now makes visible as "no date changes to notify about" when an override lands where the app never reads it.
  • Sep 18 (implementation review, pass 2 — applied in the amended phases 2–4 commit): (1) HM_RE in _lib/schedule-change.js is a real clock time (hours 0–23, minutes 00–59) — the earlier shape-only pattern let "99:99" through and formatTime rendered it as "3:99 PM"; anything that is not a real time is shown as stored. (2) The endpoint's shift sides (before/after) are TYPE-checked only and their string fields are CLIPPED to the caps by a new boundChanges(), not rejected — those fields carry the employee's stored document, and a legacy value the app never validated (an odd time string, a missing end, a long note) was turning a change that did happen into "email did not send". The manager's own fields (note, names, email), the count and the dates stay reject-on-invalid. (3) Reverses the pass-1 decision above: the editor's change email now diffs against the SYNTHETIC after-document (what this save did to the open-time snapshot), not the persisted re-read — a re-read can carry another manager's concurrent change on a touched date, and "<manager> changed your schedule" would attribute it to the wrong person. Only the bounds (validFrom/validUntil; the future's in future mode; none when the future was wiped) are taken from the persisted read, since a bound the provenance rule left in force is the one thing the synthetic document cannot know. 681 tests.
  • Sep 17 (design review, both models — v2): (1) one resolver: getShiftForDate moves to schedule-helpers.js and the diff uses it — the plan's own rule got future windows and bounds wrong; (2) the AI save routes EACH DATE by that date's future-window membership — the existing code routed the whole batch by whether the future is active TODAY, a latent bug that would have made a correct diff report "no change" for an edit the app cannot see; (3) the editor DOES edit future overrides, so Phase 4 diffs both modes; (4) the consolidated email REPLACES the Extra-Shift confirmation on editor saves, and the checkbox governs all of it (unticked = no schedule-change email of any kind) — this narrows the Sep 4 "Extra Shift" behaviour: the automatic confirmation now depends on the default-checked box; (5) the AI write is an atomic FieldPath update() per employee, not a merge payload; (6) model output is validated before any write; (7) "could not look up email" is distinguished from "no email on file"; (8) one status line names everyone, at most one toast; (9) the note is labelled as going to everyone listed; (10) past dates are included; (11) the endpoint stays unauthenticated with payload caps — authenticating all five email functions is the next queue item.
