Context — what the app is today (verified in code Sep 21, 2026)

  • One shared config, saved on every change. saveConfig() (index.html:1616) is wired to ~40 onchange/oninput handlers plus the "Save Changes" buttons. Each call writes localStorage then db.doc('payroll/appData').set({settings}, {merge:true}). On load, Firestore wins over localStorage (loadConfigFromFirestore, :1577). So any manager's edit is immediately everyone's edit; there is no draft or personal sandbox.
  • Cloud save failures are invisible. saveSettingsToFirestore (:1670) is fire-and-forget with console.warn only; showSaveConfirmation() shows "✔ Settings saved!" regardless. A failed write leaves localStorage and Firestore diverged with no signal.
  • No history, undo, export, or import. "Reset Rules" and "Remove employee" have a confirm(); "Remove" on a QB class (renderClassList, :4640) has none and does not check whether employees still reference the class.
  • "Seed to Firestore" (Data tab, :1759) overwrites the cloud doc — settings and the in-progress pay-period session — with whatever is in the current browser's localStorage. Visible to every manager.
  • Accounts tab edits are lost (bug). renderAccountMapping (:4389) writes CONFIG.classAccountMap and calls saveConfig(), but saveConfig's fullConfig (:1632-1646) omits classAccountMap and neither loader restores it. Every account-mapping change evaporates on reload, and a class added via "+ Add Class" can never be given an account. Likely a direct cause of "classes are not accurate".
  • Season toggle exists — for split rules only. CONFIG.splitSeason ('schoolYear' | 'summer'), buttons on the Split Percentages tab (:783-788), per-employee splitRules vs. summerSplitRules with "Copy from School Year" / "Build from Scratch" (seedSummerRules, initSplitRules). getActiveSplitRules(emp) (:4866) falls back to school-year rules when no summer rules exist. The toggle is a global, shared setting read at Pull Hours time (processHours, :2632) — nothing ties it to the pay period's dates. It also gates the Camp Pay step (updateCampPayNavVisibility, :1801).
  • What the toggle does not switch: rates (per-class pay rates), salaryAllocations (Christie 40/60, Anika 90/10), scheduleNotes, campTeacher/campRate.
  • Salaried percentages are display-only. The "Salaried — Percentage" card (:4938-4952) renders salaryAllocations as text; the employee modal (editEmployee, :4503) has no field for them. Editable only in code.
  • directMappingOverrides is dormant. The Tinker Ticker pull sets jobHours: {} and forces Total Hours Mode (:2363); the override lookup (:2808, :2856) only runs over job columns, which no longer exist. Legacy from the detailed-timesheet .xlsx flow. Not made editable by this plan.
  • Settings changes do not retroactively alter an in-progress period. Review/Summary read APP_STATE.reviewData computed at Pull Hours time; new settings apply on the next pull. (Good — the GM cannot break the period she is mid-way through by editing Settings.)
  • No AI anywhere. @anthropic-ai/sdk sits unused in package.json; there are no Netlify functions and no references in index.html.
  • Tests: none in this repo. Firestore rules tests live in /Users/christiehubley/studio-hub/rules.test.js (a "Finance — payroll + bookkeeping" block covers payroll/{docId}). Rule for a subcollection does not exist — match /payroll/{docId} does not cascade.

Phases

Phase 1 — Settings safety net (do before the next payroll round)

execution-ready: true

Outcome: Nothing the GM can do in Settings is unrecoverable, nothing fails silently, two people cannot silently overwrite each other, the Accounts tab actually saves, and fixing settings then re-pulling hours actually takes effect.

Acceptance criteria (user outcomes)

  1. Accounts tab persists — exactly. Change a QB class's payroll account, reload on another device → the change is there. Choosing "(none)" stays "(none)" after reload (it is not silently put back to the code default). A class added via "+ Add Class" can be given an account and it sticks.
  2. Every cloud save is recorded, atomically. A settings change and its history entry are written together or not at all. The Data tab shows "Settings history": when, who (email), a one-line summary ("Kaitlyn: split rules changed", "QB classes: +1 (Tinker Camp:Teen Camp)", "Accounts: 2 mappings changed"), newest first, 25 at a time with "Load more". Rapid edits within ~1.5 s collapse into one entry.
  3. The pre-session state is always restorable. The first cloud save of a session also records a "baseline" entry of the settings as they were when loaded — unless the newest history entry already matches (canonical hash), in which case no duplicate is written.
  4. One-click restore, exact. Any entry has "Restore" → confirm (shows the summary of what will change vs. current) → settings become exactly that snapshot (keys that did not exist then are gone) and the restore itself appears as a new entry. Nothing is ever deleted from history.
  5. Export / Import. "Export settings" downloads payroll-settings-YYYY-MM-DD.json (no history entry — it is a read). "Import settings" shows a preview (employee count, class count, split-rule count, change summary vs. current, and which integration fields will be ignored), then applies on confirm as one atomic write with a "before-import" snapshot and an "import" entry. Malformed or suspicious files are rejected with a specific message and nothing changes.
  6. Cloud-save failures are loud. If the cloud write fails, no green toast; a sticky red banner says "Saved in this browser only — cloud save failed. [Retry]". The status always reflects the latest save attempt. The toast reads "Saving…" until the write resolves.
  7. Nobody overwrites anyone. If someone else saved settings since this tab loaded them, this tab's save is refused with "Settings were changed by X at HH:MM — Reload to see their changes; your last change was not saved" (never auto-merged). When another manager saves and this tab has no pending edit, the Settings page refreshes itself with a small "Updated by X" note.
  8. Settings are read-only when the cloud copy could not be loaded. If the initial Firestore load fails, Settings show a red banner "Couldn't load settings from the cloud — Settings are read-only until reload succeeds" and every edit control is disabled; nothing from the browser cache can be pushed to the cloud.
  9. A closed tab cannot lose an edit. If the tab is closed inside the save window, the next load offers the unsaved change back: silently discarded if the cloud already holds it, applied automatically when nothing else changed in the cloud meanwhile, otherwise "Discard / Export" with the conflict named.
  10. Drive / tip-log / accountant settings can no longer be wiped by accident. Exporting from Summary (or any save made before the Settings page was opened) leaves the integration settings exactly as they were. (Pre-existing bug: saveConfig() reads those inputs from the DOM, which are empty until Settings is rendered — :1617-1630, :4431.)
  11. An open edit dialog is protected. While the employee modal (or any edit prompt) is open, a remote change does not silently replace what is being edited; Save is refused with the "changed by X — Reload" message if someone else saved meanwhile.
  12. Seed is gone (D4). The Data tab no longer offers "Seed to Firestore"; seedToFirestore() is removed from the code. The Data tab holds Settings history, Export and Import only.
  13. Class removal and rename are safe. Removing a QB class still referenced anywhere (rates, split allocations, remainder class/splits, salary allocations, camp class, account mapping — for active and archived employees) is blocked with a message naming the references. Removing an unreferenced class asks for confirmation. Renaming a class shows "Rename everywhere (N references)?" and cascades to every reference on confirm — no dangling names.
  14. Re-pull applies new settings. On Pull Hours, if allocations already exist, the app asks "Re-pulling recomputes allocations from current settings and discards manual Review adjustments (tips, HFWA, Camp Pay and private-event toggles are kept). Continue?" — "No" leaves everything untouched; "Yes" recomputes from fresh timeclock data. Review and Summary show "Settings changed since hours were pulled (by X at HH:MM) — Re-pull to apply" whenever a config change (not an integration-field change) has been saved since the pull, including after a reload. Camp Pay entries now survive a reload (pre-existing bug: campPay is not in saveAppState, :1681).

Implementation notes

  • Settings write = partial doc update that replaces the settings field wholesale (review finding B1/B2 — set(…,{merge:true}) deep-merges maps, so keys could never be removed): tx.update(appDataRef, { settings: fullConfig, settingsRev: rev+1, settingsUpdatedAt: serverTimestamp(), settingsUpdatedBy: email }). Compliant with the invariant (partial update of the doc; session untouched). lastExport leaves the settings map: written via update({ lastExport }) on the doc, outside rev/history.
  • Revision bootstrap: CONFIG.loadedRev = data.settingsRev ?? 0 at load (pre-Phase-1 docs have no field). In the transaction: cur = snap.exists ? (snap.data().settingsRev ?? 0) : 0; if (!snap.exists) tx.set(ref, { settings, settingsRev: 1, lastHistoryHash, … }) (intentional full write of a doc that does not exist — nothing to preserve) else tx.update(...). "Doc missing" (exists === false) is writable at rev 0; "load failed" (thrown) is read-only — the two are distinguished.
  • Concurrency: settingsRev (integer, always client-computed as cur + 1 — never FieldValue.increment, so the rule's getAfter tie and rev is int hold) on payroll/appData. Every cloud save is a Firestore transaction: read doc → if cur !== loadedRev abort with stale (UI: refusal message + Reload; no merge) → else update settings/settingsRev/settingsUpdatedAt/settingsUpdatedBy/lastHistoryHash and create the history entry (plus the baseline entry when lastHistoryHash !== hash(loadedSettings) — checked from the parent doc inside the transaction; the web SDK cannot run queries in a transaction) in the same transaction. On commit, loadedRev = cur + 1. onSnapshot(appDataRef): when a newer rev arrives and this tab has nothing pending (no queued payload, no in-flight transaction, no open employee modal / prompt), replace CONFIG, update loadedRev, re-render Settings, show "Updated by X". If something is pending, the refresh is deferred; the pending save's transaction then sees the newer rev and is refused with the message — which is the intended protection. Snapshot hydration never calls saveConfig() (explicit invariant; no render path may save). Initial load failure → SETTINGS_READONLY = true; saveConfig() no-ops with the banner; all Settings inputs disabled.
  • One serialized save pipeline: saveConfig() writes localStorage immediately, rewrites the pending marker, and schedules the cloud write 1.5 s trailing. Exactly one pending payload (latest wins) and at most one in-flight transaction per tab. An edit during an in-flight transaction sets dirty; when the transaction commits, the pipeline runs again with the committed rev as loadedRev — so a tab never refuses its own earlier save. pagehide cancels the timer and flushes once; single-flight guarantees no double write.
  • Pending marker + recovery: one marker per tab — localStorage['tinkerPayrollPendingSave.' + tabId] (tabId from sessionStorage), { fullConfig, hash, baseRev, at }. A tab only ever writes or clears its own key; it never touches a foreign marker. Rewritten on every edit; cleared when a commit's hash equals the marker's hash. After a commit whose hash differs from the surviving marker (an edit arrived during the in-flight save), the marker is re-based: baseRev = committed rev, so a later recovery is not a false conflict against the tab's own save. On load, after a successful cloud load only, iterate every marker key: a foreign marker younger than 10 s is left alone and re-checked 15 s later (its tab may still be flushing); otherwise if hash === hash(cloud settings) → delete silently (already saved); else if cloud rev === baseRev → apply via the normal transaction with kind: 'edit', recovered: true and delete the marker; else → Discard / Export dialog naming the conflicting save, deleting the marker on either choice. A refused save (stale rev) drops its pending payload, keeps its marker for the Export path, and then applies the deferred snapshot refresh. Under SETTINGS_READONLY no recovery runs and no marker is created.
  • History subcollection: payroll/appData/settingsHistory/{autoId} = { settings (map), hash (string), rev (int, the parent's new settingsRev), savedAt: serverTimestamp, savedBy: email, kind: 'baseline'|'edit'|'restore'|'import'|'before-import', recovered?: bool, summary (string), configVersion (int) }. Created inside the settings transaction. Listed with orderBy('savedAt','desc').limit(25) + load more. History is an application recovery log, not a security-enforced audit trail: the parent doc stays manager+ writable, and atomicity is guaranteed by the app's transaction (plus the getAfter tie in the rule below).
  • Canonical hash: settingsHash(obj) = SHA-256 (via crypto.subtle) of JSON with recursively sorted keys, after stripEmpty, over the config sections only (employees, qbClasses, classAccountMap, birthdayPartyStaff, splitSeason, summerWindow) — never integration strings or lastExport. Computed identically for the loaded Firestore map and the outgoing map. Also stored as APP_STATE.configHashAtPull at Pull Hours (persisted in the session) and compared to the current config hash for the "settings changed since pull" banner — so integration-field edits never trigger it.
  • Accounts persistence: classAccountMap joins the config sections. Loaders: if the saved settings have a classAccountMap key, it is authoritative (no default overlay); if absent (pre-Phase-1 doc), overlay code defaults once and the first save persists the full map. "(none)" = key absent. classAccountMap is exempt from empty-object stripping — an all-"(none)" map is persisted as {} so it stays authoritative.
  • Edit dialogs pre-check synchronously: saveEmployee() today mutates CONFIG, calls saveConfig() and closes the modal in one synchronous step (:4602-4636); the transaction's refusal would arrive ≥1.5 s later. So every dialog Save (employee modal, schedule-note prompt, class rename confirm) first checks deferredRemoteRev > CONFIG.loadedRev (set by the deferred snapshot) and, if true, refuses before mutating CONFIG or closing the dialog, showing the "changed by X — Reload" message. The transaction remains the backstop when no snapshot has arrived yet.
  • lastExport under read-only: the two export-time saves (:4129, :4257) become update({ lastExport }) and no-op quietly under SETTINGS_READONLY (they must not trip the red banner).
  • Integration inputs: saveConfig() no longer reads any DOM input. The Drive / tip-log / accountant inputs write their own CONFIG field in their oninput/onchange handlers (then call saveConfig()); renderSettings() keeps populating them from CONFIG. This closes the pre-existing wipe path (:1617-1630 vs :4431).
  • Restore / Import rebuild CONFIG as getDefaultConfig() (non-config fields) + the snapshot's config sections — never patched in place — so "keys that did not exist then are gone" holds immediately, not only after reload. Both run through the same transaction (kind before-import/import or restore). If a pay period is in progress, the confirm adds "hours were pulled at an older configuration — Re-pull after restoring".
  • stripEmpty everywhere (no exceptions — the earlier "leave blank integration strings" exception is withdrawn): recursively drop undefined, '', and empty objects from fullConfig and history payloads before write; loaders already treat absence as default. Also fixes the existing synchronous throw when scheduleNotes = undefined reaches the compat SDK. The write is wrapped so a synchronous throw reaches the banner path.
  • Pure helpers → new file js/settings-helpers.js (plain script defining globals, with a module.exports guard so node --test can import it): stripEmpty (with the classAccountMap exemption), canonicalJson, summarizeSettingsChange(prev, next), validateSettingsImport(obj, currentConfigVersion) (shape; unique numeric employee ids; unique tickerId/tickerUid; unique class names; pct in [0,1]; rates ≥ 0; splitSeason ∈ set; configVersion ≤ app; returns which integration fields will be ignored), classReferences(config, className) (every site: rates, splitRules/summerSplitRules allocations/splits/remainderClass/remainderSplits, salaryAllocations/summerSalaryAllocations, salarySchedule allocations and salaryRemainderClass (:2566-2604), campQbClass, directMappingOverrides values (dormant but real class names, :1310), classAccountMap keys; includes archived employees), renameClassEverywhere(config, from, to) (same sites), mergeClassAccountMap(defaults, saved).
  • Re-pull semantics: pullFromTimeclock — if APP_STATE.reviewData exists, confirm before any fetch; "No" returns with nothing touched. "Yes": reset reviewData, summaryData, unprocessedAcknowledged, and the derived inputs actualDayCounts, actualDayHours, actualWeeklyData (today they accumulate by name across pulls, :2309), then fetch and repopulate. Kept: tips, hfwa, campPay (manual, keyed by config id — and now added to saveAppState/loadAppState), privateEvents (manual, re-applied by processHours). Store APP_STATE.configHashAtPull (persisted). Note for the guide: resolveAccount and Camp Pay read live CONFIG at Summary time regardless.
