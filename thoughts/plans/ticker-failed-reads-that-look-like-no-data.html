Plan: Failed reads that look like no data

App: Tinker Ticker (~/tinker-timeclock) · Drafted: Sep 23 2026 · execution-ready: false — awaiting review and Christie's scope decision. · Found by both models while reviewing the Sep 23 HFWA index fix, then re-inventoried from source.

Goal: when the app cannot read something, it says so — instead of drawing an empty list, a zero, or a default that looks exactly like real data. Today a permission error, an offline moment, a missing index or a slow network is indistinguishable from “there is nothing here” in ten places, two of which feed payroll.

Not a hypothetical. This exact pattern hid a real employee's sick-leave submission from her on Sep 22–23: a missing index made the query throw, the catch returned [], and her card said “No submissions yet”. It is also the pattern the global CLAUDE.md names by name (“apps with loadConfig() silently fall back to defaults on permission errors”).

The inventory

Every read in js/firebase-data.js whose catch returns an empty-looking value. Writes that return false are excluded — false is an honest failure signal the caller can act on. These are reads where failure is indistinguishable from emptiness.

The { ok } idiom is already half-applied across this file; this plan finishes it.

The worst one, and it is worse than “a confusing screen”. getLockedPeriods failing makes isLocked false (app.js:2055), which re-enables the Lock Period button on a period that is already locked. lockPayPeriod writes with set(..., { merge: true }), so locking again overwrites the existing lockedAt, lockedBy and employeeTotals — the immutable snapshot of what was actually paid, which the Payroll Tool reads. A read failure can therefore destroy the record of a completed payroll run. Nothing about this is visible at the time.

One decision for Christie

How far do we go — Tier 1 only, or all three?

Tier 1 (3 reads) is where money is. It is small, and it removes the one case that can destroy a payroll record. Tiers 2–3 (8 more) are the same mechanical change and mostly prevent confusion and duplicate data entry rather than wrong numbers.

Recommendation: Tier 1 now as its own release, then Tiers 2 and 3 together when convenient. Tier 1 is worth interrupting other work for. The rest is worth doing, but not urgently, and shipping it separately keeps the payroll-critical change small enough to review properly.

The shape of the fix

The repo has already settled this, twice: a xxxResult() that returns { ok, … }, plus a thin same-name wrapper preserving the old contract for callers not yet converted. Then the render site distinguishes three states rather than two: loaded-and-empty, loaded-with-data, and could not load.

The failure message follows the one shipped on Sep 23, which says the two things a person actually needs: that it could not be loaded, and that the data is not lost.

Phases

Phase 1 — the payroll tier (no Firestore write; one write path gains a guard)

Acceptance criteria, as user outcomes:

  • If the lock status cannot be read, the timesheet says so and the Lock Period button is disabled — never enabled on a period that might already be locked.
  • If timesheet entries cannot be read, the period shows “could not be loaded” rather than “No timesheet data for this period” and zero hours.
  • If settings cannot be read, the app says so rather than silently running on default grace rules.
  • Nothing changes when the reads succeed, including a genuinely empty period.
Given the lock-status read fails, when a manager opens Timesheets, then the lock area says the status could not be read, the Lock button is disabled, and no lock can be written — so an existing employeeTotals snapshot cannot be overwritten.
Given the lock read fails, when a staff member views their entries, then change requests on possibly-locked dates are refused rather than allowed by a default-open isDateInLockedPeriod.
Given the entries read fails for a pay period, then the timesheet reports the failure and shows no totals at all — never 0.00 hours, which a manager could reasonably act on.
Given a pay period that genuinely has no entries, then it still says “no entries” exactly as today.
Given the settings read fails, then the app reports it and does not silently apply DEFAULT_SETTINGS grace rules to hour calculations.

Phase 2 — the operational tier

  • A failed schedules read says so instead of “No schedules created yet” — and the editor refuses to save while the list is unknown, so it cannot create a duplicate document.
  • A failed today's-entries read never tells someone they are not clocked in when they are.
  • Who's Working says the read failed rather than “No one is clocked in”.
Given loadAllSchedules fails, when a manager opens the schedule editor for someone, then saving is blocked with a clear reason — the known duplicate-document hazard when an existing schedule is invisible.
Given the today read fails for a clocked-in person, then the clock buttons do not offer a second clock-in.

Phase 3 — the time-off and streak tier

  • Employee-facing: a failed time-off read says so, like the sick-leave card now does.
  • Manager-facing: the pending list distinguishes “nothing pending” from “could not load”.
  • A failed streak read does not render as a zero streak.
Given the pending time-off read fails, then the dashboard says so rather than showing an empty, reassuring “No pending requests”.

Firebase safety checklist

  • New collection? No. No rules change; nothing to deploy to Firebase.
  • Writes? Phase 1 adds no write. It removes one: a lock cannot be written while the lock status is unknown. That is the point of the phase.
  • Partial updates / stripped fields / awaited writes: unchanged — no write paths are modified beyond guarding entry to one.
  • Bulk delete/import: none.
  • Tests: pure-function and structural, as for the Sep 23 HFWA fix — each converted read asserts it uses the Result variant, and each render site asserts the failure branch exists AND precedes the empty branch. That ordering is load-bearing: an empty-on-failure read still lies if the branches are reversed.
  • Downstream: the Payroll Tool reads employeeTotals from locked periods. This plan does not change that shape — it protects it from being overwritten.

Completeness check — what if this stops part-way?

  • After Phase 1: the money-critical reads are honest; the rest behave as today. A clean, defensible stopping point — and the intended first release.
  • After Phase 2: add operational clarity. Still coherent.
  • Mid-phase: each function is converted with its back-compat wrapper intact, so a half-done conversion leaves unconverted callers behaving exactly as they do now. No intermediate state is worse than today.
