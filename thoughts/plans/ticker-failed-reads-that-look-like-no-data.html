Plan: Failed reads that look like no data

App: Tinker Ticker (~/tinker-timeclock) · Drafted: Sep 23 2026 · execution-ready: false — awaiting review and Christie's scope decision. · Found by both models while reviewing the Sep 23 HFWA index fix, then re-inventoried from source.

Goal: when the app cannot read something, it says so — instead of drawing an empty list, a zero, or a default that looks exactly like real data. Today a permission error, an offline moment, a missing index or a slow network is indistinguishable from “there is nothing here” in ten places, two of which feed payroll.

Not a hypothetical. This exact pattern hid a real employee's sick-leave submission from her on Sep 22–23: a missing index made the query throw, the catch returned [], and her card said “No submissions yet”. It is also the pattern the global CLAUDE.md names by name (“apps with loadConfig() silently fall back to defaults on permission errors”).

The inventory

Every read in js/firebase-data.js whose catch returns an empty-looking value. Writes that return false are excluded — false is an honest failure signal the caller can act on. These are reads where failure is indistinguishable from emptiness.

The worst one, and it is worse than “a confusing screen”. getLockedPeriods failing makes isLocked false (app.js:2055), which re-enables the Lock Period button on a period that is already locked. lockPayPeriod writes with set(..., { merge: true }), so locking again overwrites the existing lockedAt, lockedBy and employeeTotals — the immutable snapshot of what was actually paid, which the Payroll Tool reads. A read failure can therefore destroy the record of a completed payroll run. Nothing about this is visible at the time.

REVISED after the two-model plan review (Sep 28) — the money fix is smaller than Tier 1

Path A: locking a period can store the WRONG totals, with every read on screen perfectly healthy. Both reviewers found this independently and it is more reachable than this plan's original headline.

handleLockPeriod (app.js:2811) does its OWN second read of the period's entries — separate from the one that drew the screen — and never checks whether it succeeded:
const allEntries = await getEntriesByDateRange(…);
const employeeTotals = calcPeriodTotals(allEntries, employeeRoster);

On failure that read returns [], calcPeriodTotals returns {}, lockPayPeriod writes it, returns true, and the UI re-renders as “Locked”. What the manager sees is not what gets locked, and the Payroll Tool reads the stored totals as authoritative hours.

The merge behaviour makes it worse, and this repo has already measured it (empty-map-guard.emulator.test.js): a merge-set unions nested maps, except that an explicitly-written EMPTY map replaces the target. So a non-empty bad snapshot deep-merges — uids present overwrite, uids absent survive with stale values, producing a hybrid that looks entirely plausible — while an empty one erases the stored snapshot outright. And lockPayPeriod writes employeeTotals: employeeTotals || {} raw, without omitEmptyMaps — this repo's own guard for exactly this hazard, applied to schedule writes (app.js:3865) and not to the payroll snapshot.
The fix is now SMALLER than the original Tier 1, and stronger. Both reviewers independently rejected this plan's first instinct — gating the write on a successful read. That makes the manager's ability to lock payroll depend on a read that can fail, and it does not close Path A anyway.

Instead, make the write itself safe: a transaction that reads lockedPeriods inside itself and REFUSES when the period is already locked, plus a guard that refuses an empty employeeTotals unless the manager confirms a genuinely empty period. Then a failed read never blocks a lock, and no read failure can silently overwrite or erase a snapshot. This is the idiom the repo already uses for this exact class of race — updateTimeOffRequestIfStatus, confirmTimeOffSub, applyScheduleEditsTransaction, toggleShiftRemindersTransaction.

It does change a write path, so it needs an emulator test first and an implementation review — but it needs no rules change, and it is perhaps a third of the original Phase 1.

The shape of the fix

The repo has already settled this, twice: a xxxResult() that returns { ok, … }, plus a thin same-name wrapper preserving the old contract for callers not yet converted. Then the render site distinguishes three states rather than two: loaded-and-empty, loaded-with-data, and could not load.

The failure message follows the one shipped on Sep 23, which says the two things a person actually needs: that it could not be loaded, and that the data is not lost.

Phases

Phase 1 — the lock cannot store totals nobody saw (Firestore write: one transaction)

Acceptance criteria, as user outcomes:

  • Locking a period either stores the totals the manager was looking at, or refuses and says why. It can never store empty or partial ones silently.
  • Locking a period that is already locked is refused, naming who locked it and when — the existing Unlock button stays the only way to redo it.
  • A failed lock-status read never blocks a manager from locking; the transaction decides, not the screen.
  • Nothing changes on the happy path, including locking a genuinely empty period after confirming it.

Also in Phase 1 (both reviewers): the roster read at app.js:2856 uses the swallowing loadEmployeeRoster(), and a failed roster read makes calcPeriodTotals skip the deliberate emp_→claimedBy merge — locking a snapshot that splits one person into two rows. It is a third read feeding employeeTotals.

Path A. Given the timesheet rendered real hours but the lock-time entries read fails, when the manager clicks Lock Period, then no lock document is written and the failure is reported — never a lock whose employeeTotals is {}.
Path B. Given a period already locked with totals for 9 people, when a second lock is attempted, then lockedAt, lockedBy and employeeTotals are byte-identical afterwards, and the manager is told it is already locked. Assert the stored document, not the UI.
The measured merge hazard. Given a stored snapshot and a write carrying an empty employeeTotals, then the stored one is NOT erased — an emulator test shaped like empty-map-guard.emulator.test.js, which already measures this exact behaviour.
Given a write carrying a PARTIAL snapshot (some uids missing), then it is refused rather than deep-merged into a hybrid where absent uids survive with stale values.
Given the roster read failed, then no lock is written — its totals would not carry the emp_ merge.
The negative control. Given a period that genuinely has no entries, when the manager confirms that, then it locks normally — the guard must not be a blanket refusal.
Given a good lock-status read followed by a failed one (the shared lockedPeriods global is reassigned unconditionally at app.js:1074 and :2055), then isDateInLockedPeriod still reports the known locks rather than defaulting open for the rest of the session.

Phase 1b — the three reads themselves (no write)

  • A failed timesheet read says so instead of showing zero hours.
  • A failed settings read says so instead of silently applying defaults — and the Settings modal cannot then SAVE those defaults over the real configuration (app.js:5487, :5798).
  • A failed lock-status read says the status is unknown rather than showing the period as unlocked.

Check before building: every settings consumer reads (appSettings && appSettings.X) || <the same default>, so a failed read is byte-identical to a successful read of a config holding the defaults. loadSettings is only payroll-critical if the stored timeclock_settings/appConfig actually differs from DEFAULT_SETTINGS on overtimeWeeklyThreshold / overtimeMultiplier / breakAutoEndMinutes. One look in the Firebase console decides whether it is in scope at all.

The branch-order problem gets a better fix than a test (Claude): extract the decision into a pure readState({ ok, items }) → 'failed' | 'empty' | 'loaded', unit-test that, and have every render site call it. Order then cannot be reversed because there is ONE branch site instead of eleven — the idiom reminderRowStatus already uses.

Phase 2 — the operational tier

  • A failed schedules read says so instead of “No schedules created yet” — and the editor refuses to save while the list is unknown, so it cannot create a duplicate document.
  • A failed today's-entries read never tells someone they are not clocked in when they are.
  • Who's Working says the read failed rather than “No one is clocked in”.
Given loadAllSchedules fails, when a manager opens the schedule editor for someone, then saving is blocked with a clear reason — the known duplicate-document hazard when an existing schedule is invisible.
Given the today read fails for a clocked-in person, then the clock buttons do not offer a second clock-in.

Phase 3 — the time-off and streak tier

  • Employee-facing: a failed time-off read says so, like the sick-leave card now does.
  • Manager-facing: the pending list distinguishes “nothing pending” from “could not load”.
  • A failed streak read does not render as a zero streak.
Given the pending time-off read fails, then the dashboard says so rather than showing an empty, reassuring “No pending requests”.

Firebase safety checklist

  • New collection? No. No rules change; nothing to deploy to Firebase.
  • Writes? Phase 1 adds no write. It removes one: a lock cannot be written while the lock status is unknown. That is the point of the phase.
  • Partial updates / stripped fields / awaited writes: unchanged — no write paths are modified beyond guarding entry to one.
  • Bulk delete/import: none.
  • Tests: pure-function and structural, as for the Sep 23 HFWA fix — each converted read asserts it uses the Result variant, and each render site asserts the failure branch exists AND precedes the empty branch. That ordering is load-bearing: an empty-on-failure read still lies if the branches are reversed.
  • Downstream: the Payroll Tool reads employeeTotals from locked periods. This plan does not change that shape — it protects it from being overwritten.

Completeness check — what if this stops part-way?

  • After Phase 1: the money-critical reads are honest; the rest behave as today. A clean, defensible stopping point — and the intended first release.
  • After Phase 2: add operational clarity. Still coherent.
  • Mid-phase: each function is converted with its back-compat wrapper intact, so a half-done conversion leaves unconverted callers behaving exactly as they do now. No intermediate state is worse than today.
