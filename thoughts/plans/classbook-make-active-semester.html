Christie's decisions (Sep 29)

Making a camp season active has to be checked everywhere "active" is read (see the Phase 1 camp-season scenarios).

Phases

Two phases, committed separately and deployed once (one Netlify credit) after both are reviewed.

Phase 1: "Make active" in Settings execution-ready: false

Acceptance (user outcomes):

  • In Settings, when the "Editing Semester" dropdown is on a non-active Fall/Spring class semester or Summer camp season (Q1 — not an SDOC year), a manager sees "Make this the active semester" next to the Published toggle.
  • Clicking it asks one confirmation that names both semesters: "Make Fall 2026 the active semester? Spring 2026 stops being active." It adds a line when that matters:
    • If the new semester is a draft: "It's a draft — it will be published so teachers can see it." Making it active also publishes it, in the same single write.
    • If the old semester is a draft (published === false): "Spring 2026 is a draft, so teachers will stop seeing it."
  • After confirming, the "(active)" label, the Active Semester badge, and the Publish toggle and Delete button all move to reflect the new state, in Settings, the header dropdown and Curriculum Admin, without a reload.
  • If the write fails, nothing changes on screen, an alert says why, and "Nothing was changed."
  • Nobody below manager ever sees the control (Settings is already hidden, and the rules refuse the write anyway).

Shape: new makeSemesterActive(key) in app.js beside toggleSemesterPublish. It checks eligibility and that the key exists and isn't already active, confirms, then calls updateAppData({ activeSemester: key, [semesters.key.published]: true (only if it was a draft) }). It updates currentConfig optimistically, restores it exactly on failure, then re-renders the header selector, renderSemesterSelector() and loadSettingsForm(). The button lives in the Settings publish group (app.js:10700-10712). The Curriculum Admin bar stays read-only for "active", because non-managers use it and can't write appData.

Phase 2: "Switch everyone to it" execution-ready: false

Acceptance (user outcomes):

  • The Phase 1 confirmation has a checkbox, "Also switch everyone to Fall 2026 the next time they open the Classbook", ticked by default (Q2).
  • With it ticked, every user who can see the new active semester lands on it the next time they load the Classbook, once. After that they can pick any semester and it sticks as usual.
  • With it unticked, nobody's remembered semester moves; only the label and the default for new browsers change (Phase 1's behaviour).
  • A teacher who can't see the new active semester (unpublished) is not moved.
  • Tabs already open move on their next reload, not live.

Shape: the same single update() also writes activeSemesterSwitchAt: <ISO timestamp>, only when ticked. On load, just before the existing pick at app.js:65: if currentConfig.activeSemesterSwitchAt is set and differs from localStorage activeSemesterSwitchSeen, and the active semester is visible, set globalSemesterKey to it. In every case record activeSemesterSwitchSeen = activeSemesterSwitchAt, so each switch applies once per browser. A browser that has never seen a switch (seen value missing) takes it. That matches what a new browser gets anyway: the default is the active semester.

This is a new field on an existing document (curriculum/appData), not a new collection, so no rules change. Nothing reads it until the first switch, so deploying Phase 2 moves nobody by itself. The timestamp comes from the manager's clock, and it only needs to differ from the last value, not be accurate. The comparison is "not equal to seen", not "newer than", so a skewed clock can't block a switch.

Firebase safety checklist

  • Rules: none needed. curriculum/appData is already manager+ read/write. No new collection. Phase 1's e2e includes the non-manager refusal against the real rules.
  • Partial update: updateAppData (update() of named dotted paths). Never set(). Only activeSemester, optionally semesters.<key>.published and activeSemesterSwitchAt, plus the existing lastUpdated/lastUpdatedBy.
  • No undefined or empty values: every path is a known string or true. The key is validated against currentConfig.semesters before writing.
  • Awaited: the one write is awaited, and on failure the in-memory state is restored exactly (the toggleSemesterPublish pattern, including "field was absent").
  • No bulk op, no delete: no snapshot needed. The previous value is shown in the confirmation. To roll back, make the old semester active again with the same button (or the console line).
  • Refuses on a bad load: inherited from updateAppData (config load failed, season registry unknown or error).
  • Production spot-check after deploy: Christie uses the button once for real (or the console line has already done it), then checks curriculum/appData.activeSemester in the Firebase Console.

Completeness: what if this is interrupted?

  • Mid-code, before deploy: nothing is live. Resume from the branch.
  • The write itself is atomic: one update(), so the active flag and the auto-publish can't half-happen.
  • Phase 1 shipped without Phase 2: still coherent. The button works and moves nobody. (The plan still deploys both together.)
  • After a switch: browsers pick it up on their next load, whenever that is. There's no deadline and nothing to finish.
