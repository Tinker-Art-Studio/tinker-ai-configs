Plan: Classbook — e2e suite runs only against Firebase emulators

Goal: Running the Classbook Playwright suite never signs into, reads from, or writes to the production Firebase project (tinker-hq-apps) — it runs against local Auth + Firestore + Storage emulators seeded with a small, personal-data-free fixture set, and refuses to start in any other configuration.
App: tinker-spring-curriculum (The Classbook) — e2e/, playwright.config.js, js/firebase-config.js, js/firebase-data.js
Branch: claude/funny-nash-6aab81 (worktree)

Research findings (Phase 1 of the planning workflow — read-only)

  • How the app initialises Firebase: compat SDK 10.8.0 from gstatic (index.html:472-475). initFirebaseApp() in js/firebase-config.js is the shared init; requireAuth() (auth-guard.js) calls it first on every load. One second init path exists: getFirebaseStorage() in js/firebase-data.js:964 calls firebase.initializeApp(FIREBASE_CONFIG) directly.
  • How the tests reach Firebase today: e2e/helpers/firestore.js signs in with signInWithEmailAndPassword (TEST_EMAIL/TEST_PASSWORD from .env.test) against the real project through the client SDK; e2e/helpers/login.js does the same in the browser; e2e/global-setup.js saves that production session as Playwright storage state. No connectFirestoreEmulator / FIRESTORE_EMULATOR_HOST anywhere.
  • Spec shape: one spec, e2e/data-safety.spec.js (161 tests, 32 describes). Every test creates its page with browser.newPage() and every test goes through login(page) (directly or via a helper) — login() is therefore a per-test choke point. Tests self-seed TEST-prefixed data and clean up; the only pre-existing data they depend on is the summerCamps_curriculum/TEST_DATA_SAFETY_curriculum camp doc (spec header), the test user's users doc, and the existence of the shared curriculum/lessonData and curriculum/cutProjects docs (helpers use updateDoc, which fails on a missing doc). Five page.route('**/firebasestorage.googleapis.com/**') patterns intercept Storage traffic.
  • Boot requirements for the app under test: loadSummerCampData() throws if summerCamps_curriculum is empty → lessonDataLoadedSuccessfully=false → saves blocked. So the fixture must contain at least one camp. The CA grid renders a placeholder when a semester has no lessons, which satisfies the tests' ca-grid-wrapper readiness check.
  • Emulator facts (verified by trial run): firebase emulators:exec --config /Users/christiehubley/studio-hub/firebase.json starts Firestore + Storage but not Auth ("make sure you have run firebase init" — there is no emulators block in studio-hub's firebase.json). A generated emulator-only firebase.json whose firestore.rules/storage.rules point at the studio-hub files by absolute path starts all three, loads the ONE rules file as-is, and exports FIRESTORE_EMULATOR_HOST, FIREBASE_AUTH_EMULATOR_HOST, FIREBASE_STORAGE_EMULATOR_HOST to the exec'd script. A demo- project ID needs no CLI login and the CLI itself states "attempts to access non-emulated services for this project will fail". Java 25 is installed; ports are free; no ADC credentials file exists on this machine.
  • Rules involved (read only, not changed): users, curriculum, summerCamps_*, backupStatus — the seeded test user mirrors the production e2e account's profile — role: 'staff' with appAccess: ['classbook','curriculum-admin'] (corrected in Phase 4, see Decisions) — so rules behave the same way.
  • Existing tests: the suite itself (161 e2e tests). No unit tests for the helpers. Rules tests live in studio-hub and are unaffected.

Phase 1 — App: emulator mode behind a flag nothing in production sets

What it does

js/firebase-config.js: when window.__USE_EMULATORS__ is present, initFirebaseApp() initialises with a demo-project config and calls firebase.auth().useEmulator(), firebase.firestore().useEmulator(), firebase.storage().useEmulator() before any other Firebase call. js/firebase-data.js's getFirebaseStorage() routes through initFirebaseApp() instead of its own initializeApp, so there is exactly one init path.

Acceptance

  • With no flag, the app behaves byte-for-byte as before (same config object, same calls).
  • With the flag, no request leaves the browser for *.googleapis.com Firebase endpoints.
Given: index.html served by Netlify or a plain local server (no injected flag) When: the app boots Then: initFirebaseApp() uses FIREBASE_CONFIG unchanged and never calls useEmulator() Given: the test server injected window.__USE_EMULATORS__ before js/firebase-config.js When: requireAuth() → initFirebaseApp() runs Then: the app is initialised as demo-tinker-classbook and Auth/Firestore/Storage all point at 127.0.0.1 emulator ports Given: the flag is present but the storage compat SDK is not loaded (e.g. user-admin.html) When: initFirebaseApp() runs Then: Auth and Firestore are connected to the emulator and the missing Storage SDK is skipped without throwing

Reviewer questions (2026-09-21) — answered

Q1 — "Is the integrity the same as before? Does this align with my hardening work and AI configs, or negate it? Was it set up wrong in the first place?"

Integrity: the same for everything this suite exists to prove, stronger in three ways, with two honest trade-offs.

What is identical. The exact app code under test (the real js/app.js, firebase-data.js, auth-guard.js, served as-is); the real Firebase SDKs (the same compat 10.8.0 build from gstatic in the browser, the real firebase client in Node); the real studio-hub rules file, loaded unchanged and genuinely enforced (verified: an unauthenticated read came back 403 citing firestore.rules lines 106–112); the real Storage rules; and real Firestore semantics — the emulator is Google's own Firestore engine, not a mock, so transactions, arrayUnion/arrayRemove, FieldValue.delete(), merge:true, getDocFromServer and onSnapshot listeners behave as in production. The 161 tests' logic is unchanged — the diff is fixture data, one URL-scheme assertion, and two timing helpers (see the Decisions log).

Where it is stronger. (1) Deterministic starting state: every run begins from exactly the fixture set. Production carried debris from crashed runs (the leaked TEST_DATA_SAFETY_* keys are still there), so a test could pass or fail on leftovers. (2) The suite now exercises the rules file × the app together before a rules release. Before, it only ever saw rules that were already live; a regression like May's would now fail this suite on your machine first. (3) No auth quota throttling (the auth/quota-exceeded timeouts that were misread as network flake for weeks) and no ~2M billable reads per run — 3.8 minutes, green, zero attempted production requests across three runs.

Trade-offs, stated plainly. (1) It no longer runs on top of the real dataset's size: a 3,150-doc load takes ~100 ms here vs 1.5–3 s in production. That matters for one class of bug — timing races. It cut both ways: the emulator's speed exposed three real harness races that production's slowness had masked (all fixed in Phase 4), but a race that only appears under a slow load is not reproduced here. (2) The emulator does not enforce composite-index requirements or per-project quotas, so a query that needed an index would pass here and fail live — the Classbook has no such queries today (and the indexes-hazard note already says to avoid multi-field orderBy). (3) It tests the rules file in studio-hub, not the rules currently live; "file → live" is what the release guard and studio-hub's npm test gate cover. None of these touch what this suite is for: proving the save paths don't destroy data and the rules permit exactly what they should.

Alignment: this is the hardening work, not a departure from it.

  • studio-hub/firebase-agent-defense-hardening.md (Resilience Plan Step 3), Credential-handling section, verbatim: "tests must talk to the local emulator, never production." §3.1 calls pointing these tests at the emulator "the top recommendation for the next session that touches Classbook." §5 ranks the production-backed helper as unresolved risk #1 and describes the Aug 12 production sign-in as "a stop-gap, not the full fix — … The full fix (app + tests both pointed at a local emulator) is scoped but not yet built."
  • The Resilience Plan's Step 4 sequencing (your memory notes) lists "do the Classbook emulator switch" as a planned item — deferred only so it would not collide with the Data Safety Plan session that was using the same test files.
  • ~/.claude/CLAUDE.md, the Classbook AGENTS.md, and the development-workflow skill all say emulator tests first. The Classbook AGENTS.md itself carried the "stop-gap … full fix not yet built" note until this change replaced it.
  • Firebase's own guidance is the same: emulators for automated tests, demo- project ids for exactly this. Nothing in your configs marks this as a way not to go.
  • Nothing was negated. The release guard, the "approved to change firebase" phrase, the ONE-rules-file rule and the --only release forms are untouched and remain the only path to production. One interaction is logged for the guard session: the generated e2e/.emulators/firebase.json names the rules files so the emulators can load them; it is only ever passed to emulators:exec/emulators:start, never to a release command.

Was it set up wrong? In stages. The original (pre-Aug) helper minted a production OAuth token from your CLI login and bypassed rules — wrong, and the audit's top finding. The Aug 12 rewrite moved it to a rules-enforced production sign-in — better, and labelled "stop-gap" in three places (the hardening doc, AGENTS.md, and the helper's own header). The emulator setup is the end state those documents scoped. The reads incident on Sep 21 is what made the stop-gap's cost visible.

Q2 — "I thought we were supposed to do it via the production path instead of emulator-only…?"

No — the opposite. The production path was the interim step, never the target: the hardening doc (§5, risk #1), the Classbook AGENTS.md and the helper file itself all called it a stop-gap pending "app + tests both pointed at a local emulator." Every standing rule you have on testing (~/.claude/CLAUDE.md, AGENTS.md, development-workflow, the hardening doc's credential-handling section) says emulator, never production. Deleting the production sign-in path is what makes the guarantee real: with no production config and no env-supplied password anywhere in e2e/, there is nothing for a future change (or a future agent) to fall back to.

What still legitimately touches production — unchanged:

  • The planning workflow's manual spot-check one real document in the Firebase Console after any data-write phase. That is a human verifying real data, not an automated test, and it stays.
  • Local development at :8087 (npx http-server) still runs against production exactly as before — the emulator flag is injected only by the test server, so nothing about your dev workflow changed.
  • Rules releases, via the guarded --only forms, after the phrase.

If you want a deliberately tiny production smoke check some day (e.g. "the live site loads and a signed-in read succeeds"), that should be its own read-only script with its own approval — not folded back into this suite, which writes.
