Plan: Firebase deploy guard — approve a diff, not an act

Repos: ~/studio-hub (the ONE rules file, tests, the guard script) · ~/.claude/settings.json (the cross-session hook) · ~/.claude/CLAUDE.md (the gate's wording) · Drafted: Sep 21 2026 · execution-ready: false · v1, awaiting two-model design review · Under the Firebase Backend Resilience Plan.

Goal: a Firestore rules deploy can only ship a commit Christie named, from a clean tree, after the tests, and every session — in any repo, whether or not it read CLAUDE.md — is held to that mechanically. "What is live?" is answered by git in one command, never by signing into the console.
The incident this closes (Sep 21 2026): the approval gate is a sentence in CLAUDE.md that each Claude session applies to itself, and it gates running the deploy command. But the command ships the whole file on disk, and the file is one shared working tree that every session edits in place. A session with approval for ITS change deployed the file while ANOTHER session's unreviewed rules sat in the same tree. It missed by minutes — the live ruleset was verified byte-for-byte against the earlier commit — but nothing prevented it. Every session followed the rules and the outcome was still wrong: the gate is per-session and per-command when the risk is per-content.

Why this shape

  • Approve a sha, not an act. The phrase becomes "approved to change firebase <sha>". The guard refuses unless HEAD is that sha. Christie is approving a specific diff she can read, and a session cannot deploy anything else, including someone else's edits that happen to be in the tree.
  • Clean tree, or nothing. Uncommitted changes to tracked files mean the deployed bytes would not match any commit. Refused.
  • A moving rules-live tag + an immutable dated tag per deploy. Moved only by the guard after a successful release, pushed to origin. git diff rules-live -- firestore.rules is "what would this deploy change"; the dated tags are the rollback ladder. Today the rollback runbook guesses the known-good commit from git log; it stops guessing.
  • A user-scope Claude Code hook, not a project one. Sessions deploy rules from cwds in other repos (Classbook, Payroll, Training Hub…) with cd ~/studio-hub && firebase deploy …. A hook in ~/.claude/settings.json sees every Bash call in every session; a project hook would only see sessions started inside studio-hub. The hook denies any firebase deploy that is not the guard script, with a message that says what to run instead.
  • The guard is a plain shell script with its own tests. No new dependency. It is exercised against a throwaway git repo with a fake firebase on PATH, so every refusal is a test, not a hope.
  • Not solved here, named honestly: the hook governs Claude sessions only — Christie typing firebase deploy in a terminal is her call. Two sessions editing the shared file can still clobber each other's uncommitted edits; the guard makes that unshippable, not impossible. Branch-per-change is recommended in CLAUDE.md, not enforced. netlify deploy (costs credits; "ask first") has the same shape and is a follow-up.

Design

The guard: studio-hub/scripts/deploy-rules.sh

scripts/deploy-rules.sh --approved <sha> [--target firestore:rules|storage|firestore:indexes] [--dir <firebase project dir>]
scripts/deploy-rules.sh --status                      # what is live vs HEAD, per target; exits 0
scripts/deploy-rules.sh --diff [--target …]           # git diff <live-tag>..HEAD -- <the target's file>

Refuses (non-zero, one plain sentence each) when:
  1. --approved is missing, or is not a prefix of `git rev-parse HEAD` (short shas accepted, ≥ 7 chars)
  2. the tree has modified/staged TRACKED files (`git status --porcelain --untracked-files=no` non-empty)
  3. HEAD is not on origin (`git branch -r --contains HEAD` empty) — the deployed commit must be shared
  4. the target's file does not exist, or .firebaserc has no default project
  5. `npm test` fails (only when package.json has a test script; studio-hub does)
Then, in order: prints the project, the target, the live tag → HEAD diff stat (or "first guarded deploy, no tag yet"),
runs `firebase deploy --only <target>` from --dir, and ONLY on exit 0:
  git tag -f  live/<project>/<target>                       HEAD      # moving
  git tag     deployed/<project>/<target>/<UTC yyyymmddTHHMMZ> HEAD    # immutable
  git push origin --tags --force-with-lease=…   (tags only; never a branch; the moving tag is the only one ever rewritten)
Tag names use slashes so they group in `git tag -l 'live/*'`. Target "firestore:rules" → "firestore-rules" in the name.

Tests: scripts/deploy-rules.test.sh builds a temp bare "origin" + clone, puts a fake firebase on PATH (records its argv, exit code controllable), and asserts each refusal, the happy path's tag moves + push, and that a failed firebase deploy moves no tag. Run by npm run test:guard; added to npm test.

The hook: ~/.claude/hooks/firebase-deploy-guard.sh, wired in ~/.claude/settings.json

{ "hooks": { "PreToolUse": [ { "matcher": "Bash", "hooks": [ { "type": "command",
      "command": "~/.claude/hooks/firebase-deploy-guard.sh", "timeout": 5 } ] } ] } }

The script: reads stdin JSON, extracts .tool_input.command; if it does not match /(^|[;&|(]\s*|\s)firebase\s+deploy\b/
exit 0 silently (every other Bash call is untouched, ~2 ms). If it matches AND the command invokes
scripts/deploy-rules.sh (the guard) → exit 0. Otherwise print the deny JSON with the reason:
  "firebase deploy is gated. Run: cd ~/studio-hub && scripts/deploy-rules.sh --approved <sha Christie named>
   [--target …]. Christie's phrase is 'approved to change firebase <sha>'. See CLAUDE.md → FIREBASE RULES."
Pipe-tested with synthesized stdin per the update-config skill, then proved live with a harmless `firebase deploy --help`.

The words

  • ~/.claude/CLAUDE.md → FIREBASE RULES: the three --only forms are replaced by the guard; the phrase is "approved to change firebase <sha>"; "what's live" is scripts/deploy-rules.sh --status; rules edits go on a branch and land on main before approval (recommended, not enforced).
  • studio-hub/RULES-ROLLBACK.md: step 2 becomes git tag -l 'deployed/tinker-hq-apps/firestore-rules/*'; rollback = git revert (or checkout the previous dated tag's file onto a commit), then the guard with the phrase.
  • Memory: the resilience-plan entry gains this step; the incident is recorded.

Firebase safety checklist

  • No Firestore data or rules change in this plan. The seeded tags point at the commit already verified live.
  • The guard never runs bare firebase deploy; always --only <one target>.
  • Never reads ~/.config/configstore/firebase-tools.json; the CLI's own login is what firebase deploy already uses, unchanged.
  • Tag pushes are tags only, never a branch; the moving tag is the only ref ever force-updated.
  • The hook fails closed: a broken hook blocks deploys, never allows them.

Completeness check

  • After Phase 1: the guard exists and works, but nothing forces its use — the old command still runs. Better than today (the tag answers "what's live"), not yet safe.
  • After Phase 2: safe in every Claude session. CLAUDE.md still describes the old command until Phase 3 — the deny message bridges the gap.
  • After Phase 3: complete.

Open questions for review

  • Should the guard also require the approving sha to be on main specifically, not just on origin?
  • Hook false positives: any Bash command whose TEXT contains firebase deploy is denied (an echo, a grep). Acceptable, or should the regex require it at a command position only?
  • Should --status also fetch the live ruleset's hash from the Rules API to prove the tag is honest? It needs an OAuth token — which is the credential rule's line — so v1 trusts the tag. Alternative: the guard hashes the file it deployed and stores the hash in the dated tag's message, so a later console check has something to compare against.
  • Same guard for netlify deploy now, or as its own follow-up?
