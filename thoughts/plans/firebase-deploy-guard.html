Plan: Firebase deploy guard — approve a diff, not an act

Goal: a Firestore rules deploy can only ship the exact commit Christie named — read from git, never from the shared working tree — after the tests, and every Claude session on this machine, in any repo, is held to that mechanically. Every deploy leaves an immutable receipt that says what shipped; rollback is "pick the previous receipt".
Two incidents this closes (both Sep 21 2026):
  1. The approval gate is a sentence in CLAUDE.md that each session applies to itself, and it gates running the command. The command ships the whole file on disk, and the file is one shared working tree every session edits in place. A session with approval for ITS change deployed the file while ANOTHER session's unreviewed rules sat in the same tree. It missed by minutes (the live ruleset was verified byte-for-byte against the earlier commit). Every session followed the rules and the outcome was still wrong: the gate is per-session and per-command when the risk is per-content.
  2. A deploy-guard hook and all the auto-mode rules for Firebase were installed on Aug 15 in ~/.claude/settings.local.json — believed machine-wide, but that file is the project-local settings of a project rooted at ~, loaded only by sessions launched from the home directory. Proof: this session's cwd is tinker-timeclock, that hook denies any deploy whose cwd is not studio-hub, and the Phase 2 rules deploy ran. Every session launched in Classbook, Payroll, Training Hub… has had no hook and none of those auto-mode rules.

Why this shape

  • Approve a sha, not an act. The phrase becomes "approved to change firebase <full sha>". --status prints the exact sentence to say, so it is copy-paste, not typing. The guard deploys that commit and nothing else.
  • Deploy from git, never from the shared tree. The guard exports the approved commit into a temporary worktree and runs the tests AND firebase deploy from there. What another session does to ~/studio-hub/firestore.rules during those 30 seconds cannot reach production. This closes incident 1 outright; a clean-tree check only narrowed it (design review, both models).
  • The sha must be on origin/main (an ancestor of it, after a fetch). Any pushed branch was too weak — a wip/ branch would pass. "Ancestor of" rather than "equal to" so a rollback to an earlier receipt's commit is itself a guarded deploy.
  • Immutable receipts, no moving tag. Each successful deploy creates one annotated tag deployed/tinker-hq-apps/firestore-rules/<UTC yyyymmddTHHMMSSZ>-<sha7> whose message records the full commit, the target file's sha256 and the timestamp; pushed as one explicit refspec, never --tags, never forced. "Latest receipt" is the newest tag. A moving live/* tag needed force-pushes and could lie (both reviewers); receipts cannot be rewritten. They are receipts of guarded deploys, not proof of production — a deploy from a terminal leaves none, which is the honest limit of git-based truth; the predeploy backstop below is what makes that terminal deploy hard.
  • A CLI-level backstop in firebase.json. firebase-tools runs predeploy hooks for every target (verified in lib/deploy/index.js: lifecycleHooks(target, "predeploy") before prepare; a non-zero exit is predeploys_error and nothing is uploaded). A tiny predeploy script refuses unless TINKER_DEPLOY_SHA is set and the file about to ship is byte-identical to git show $TINKER_DEPLOY_SHA:<file>. Only the guard sets that variable. This catches npx firebase-tools, absolute paths, wrapper scripts, npm scripts, aliases, and Christie's own terminal — everything a text-matching hook cannot. The human escape hatch is setting the variable by hand, on purpose.
  • The Claude hook is an accidental-invocation guard, not a security boundary. A regex over the Bash command string cannot enforce anything against indirection; it exists to stop the ordinary cd ~/studio-hub && firebase deploy … a session reaches for by habit, with a message that names the guard. It lives in ~/.claude/settings.json — true user scope — and is the ONLY hook file (incident 2 is closed by moving, not copying).
  • Not solved here, named honestly: two sessions can still clobber each other's uncommitted edits in the shared file — now unshippable, still annoying; branch-per-change is recommended in CLAUDE.md, not enforced. A hook timeout is fail-open in Claude Code; the hook does no I/O beyond reading stdin so it cannot time out in practice. The guard cannot tell whether a clean commit contains someone else's hunks — it prints the full diff and CLAUDE.md tells the session to paste it verbatim and stop if it contains hunks it did not write; the review is the control. Netlify stays out (different shape: a cost decision, no content invariant; the existing auto-mode line covers it).

Design

The guard: ~/studio-hub/scripts/deploy-rules.sh (bash, set -euo pipefail, cwd-independent)

scripts/deploy-rules.sh --approved <full sha> [--target firestore:rules|storage|firestore:indexes]
scripts/deploy-rules.sh --status [--target …]     # latest receipt vs origin/main; prints the exact phrase to say for HEAD
scripts/deploy-rules.sh --diff   [--target …]     # FULL diff, latest receipt → origin/main, target file only (paste this verbatim when asking)

v1 is pinned: repo /Users/christiehubley/studio-hub, project tinker-hq-apps, the three targets and their files. Nothing else.

Order of operations (every refusal is one plain sentence and a distinct exit code):
  0. Lock: mkdir "$repo/.git/tinker-deploy.lock" — refuse if it exists (another guard, or an emulator run, is in flight). Removed on EXIT.
  1. Reconcile: any local receipt tag missing on origin is pushed now; if that push fails, refuse ("DEPLOYED EARLIER; receipt not
     published; fix the push before another deploy").
  2. --approved must be a full 40-hex sha (lower-cased) that `git rev-parse --verify --quiet "$sha^{commit}"` resolves.
  3. `git fetch origin main` (refuse if it fails — tags could not be pushed either); `git merge-base --is-ancestor "$sha" origin/main`
     — refuse otherwise ("land it on main first").
  4. Dirty shared tree is a WARNING naming the files, not a refusal — the tree is not what ships, and a refusal invites a session to
     commit someone else's edits to get a clean tree (design review).
  5. `git worktree add --detach "$tmp" "$sha"`; `ln -s "$repo/node_modules" "$tmp/node_modules"`; removed on EXIT.
  6. Print: project, target, the receipt this replaces (or "no receipt yet"), and the FULL diff receipt→sha for the target file.
  7. In $tmp: `npm test` — for firestore:rules only (storage/indexes have no suite; --status says so rather than implying).
  8. In $tmp: TINKER_DEPLOY_SHA="$sha" firebase deploy --only "$target" --project tinker-hq-apps --non-interactive
  9. Only on exit 0: sha256 of the deployed file; `git tag -a "deployed/tinker-hq-apps/<target-slug>/<UTC>-<sha7>" "$sha"
     -m "project=tinker-hq-apps target=… commit=<sha> file=<path> sha256=<hash> at=<UTC> by=deploy-rules.sh"`;
     `git push origin "refs/tags/<that tag>"`. Push failure → exit with a DISTINCT code and message
     ("DEPLOY SUCCEEDED; RECEIPT NOT PUBLISHED — run: git push origin refs/tags/…"); step 1 retries it next time.
Never `--tags`, never a branch push, never force.

The backstop: firebase.json predeploy + scripts/predeploy-check.sh

"firestore": { "rules": "firestore.rules", "indexes": "firestore.indexes.json", "predeploy": ["bash scripts/predeploy-check.sh firestore"] },
"storage":   { "rules": "storage.rules",                                         "predeploy": ["bash scripts/predeploy-check.sh storage"] }

predeploy-check.sh <target>: refuse (exit 1, one sentence naming the guard) unless TINKER_DEPLOY_SHA is a full sha AND, for each
file the target deploys, `git -C <repo> show "$TINKER_DEPLOY_SHA:<file>"` is byte-identical to the file in cwd. Runs in ~50 ms.
Human escape hatch: `TINKER_DEPLOY_SHA=<sha> firebase deploy …` by hand, knowingly — and even then only that commit's bytes ship.

The hook: ~/tinker-ai-configs/scripts/firebase-deploy-hook.sh, wired in ~/.claude/settings.json

{ "hooks": { "PreToolUse": [ { "matcher": "Bash", "hooks": [ { "type": "command", "timeout": 5,
      "command": "bash /Users/christiehubley/tinker-ai-configs/scripts/firebase-deploy-hook.sh || exit 2" } ] } ] } }

The script: `cmd=$(/usr/bin/jq -r '.tool_input.command // empty')`; if it does not match
   grep -qE '(^|[^[:alnum:]_.-])(firebase|firebase-tools)([^;&|]*[[:space:]])?deploy([[:space:]]|$)'
exit 0 silently (matches: bare, `cd … && firebase deploy`, `/opt/homebrew/bin/firebase deploy`, `./node_modules/.bin/firebase deploy`,
`npx firebase-tools deploy`, `firebase --project x deploy`, `$(…)`, heredocs, `bash -c '…'`; accepted false positives: echo/grep/comments —
the deny text says "if you only meant to read text, use Read/Grep"). Otherwise print the deny JSON and exit 0:
  "firebase deploy is gated. Run the guard from any cwd: /Users/christiehubley/studio-hub/scripts/deploy-rules.sh --approved <full sha>
   [--target …]. Christie's phrase is 'approved to change firebase <full sha>'; --status prints it. See ~/.claude/CLAUDE.md → FIREBASE RULES."
No exception for "invokes the guard" — the guard's inner deploy is a subprocess the hook never sees, and an exception was a bypass
(`deploy-rules.sh --status; firebase deploy …`). `|| exit 2`: a missing or crashing script BLOCKS EVERY BASH CALL with the bash error on
stderr — loud, fixed in a minute, and the honest price of fail-closed (a hook that exits 1 or 127 is silently ignored by Claude Code).
Timeout stays fail-open by platform design; the script does no I/O beyond stdin.

Firebase safety checklist

  • No Firestore data change. The only production interaction in this plan is a --dry-run that aborts at predeploy.
  • The guard never runs bare firebase deploy; always --only <one target> --project tinker-hq-apps.
  • Never reads ~/.config/configstore/firebase-tools.json; the CLI's own login is unchanged.
  • Tag pushes are one explicit refspec, never a branch, never force, never --tags.
  • Three independent layers: hook (habit), guard (content + receipt), predeploy (bytes). Each is tested alone.
