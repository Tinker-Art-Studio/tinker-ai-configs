Phase 2 — Scheduled pauses start on their own + Sawyer timing alert execution-ready: false

Finding

Processing a pause with a future start date stores scheduledPause, but nothing moves the member to Paused when the day comes, and nothing reminds anyone when to process it in Sawyer.

Christie's decision (Sep 25)

  • Automatic: on the pause start date the member moves to Paused on their own.
  • Sawyer alert: the pause must be processed in Sawyer just after the last billing before the pause starts (so that billing goes through and the next one is skipped). The app raises a banner/View-list alert "Process pause in Sawyer: [Name]" from the day after that billing date until someone marks it done.

Changes

  • Scheduling a future pause records it without requiring the "Process pause in Sawyer" step; that step moves to a scheduledPause.sawyerProcessedAt flag set by a "Mark processed in Sawyer" button on the member card.
  • Alert date = day after the last billing date before the pause start, computed from nextPaymentDate and billing type. Alert stays until marked; escalates if the pause start arrives unmarked.
  • On page load, Active members whose scheduledPause.startDate ≤ today: add to pauseHistory (carrying the Sawyer flag), stage Paused, clear scheduledPause, log "Scheduled pause started". Banner note "1 pause started today". If the end date has also passed, go straight to the existing auto-resume.
  • Pure decision functions in member-status.js with tests; checked against the premature-pause correction and stale-pause cleanup so nobody bounces between stages.
To confirm while building: for 3-month prepaid members, is "the last billing before the pause" their last 3-month charge (possibly weeks before the pause), or do you convert them to monthly first? The app will show the computed alert date on the card so it can be sanity-checked.
BDD: Given a monthly member billed on the 15th schedules a pause Nov 1–30, then on Oct 16 the banner says "Process pause in Sawyer: [Name]"; after "Mark processed" it clears; on Nov 1 they are Paused; on Dec 1 they auto-resume. · Given the pause start arrives and Sawyer was never marked, then they still move to Paused and the alert turns red ("pause started — Sawyer not processed"). · Given the member is Off-Boarding, the scheduled pause is left alone.

Phase 3 — Member Since, onboarding → active, and the real membership rules execution-ready: false

Findings

  • For 3-month prepaid members, when the billing date passes the app sets termStart = next billing date − 1 day — the next term — so terms show in the future (Anne: "Oct 29, 2026 → Jan 28, 2027").
  • "Member Since" shows termStart, so it moves forward each renewal and the real start date is overwritten in Firestore.
  • The "3-Month Commitment Cycle" box and pause eligibility are computed from that moving date, and model a 3-month commitment the studio doesn't actually enforce.
  • Onboarding members already have an orientationDate (date + time) set in the app, but nothing uses it to activate them.

Christie's rules (Sep 25)

  • Member Since = orientation day = first bill date.
  • 3-month prepaid members are treated like monthly ones for pauses and cancellations.
  • With 1 month's notice, a pause or cancellation can be processed regardless of where they are in their term.
  • No refunds: a cancellation takes effect at the end of a billing cycle.
  • Pauses: at most 2 months per year; never retroactive; not before they're eligible (existing 3+ months as a member).
  • Cancelling isn't possible before a member is pause-eligible.

Changes

  • New memberSince field that never moves. Going forward: on the orientation day, onboarding members move to Active automatically and memberSince is set to that date (banner: "N moved to Active today — confirm they attended orientation", with a one-click undo for no-shows).
  • Backfill existing members from the Onboarding Spreadsheet (Christie to share it); members it lacks are listed for Christie to fill by hand. JSON snapshot first; fill only where empty.
  • Fix the 3-month roll-forward so the term shown is the current one; "Member Since" reads memberSince.
  • Replace the "3-Month Commitment Cycle" box with a "Notice & dates" box: next billing date, earliest cancellation (end of the first billing cycle at least 1 month out, and not before pause eligibility), earliest pause start (1 month out), and pause months used in the last 12 months. Pure functions with tests for each rule.
Still open:
  1. "2 months per year": is that any rolling 12 months, or per calendar year? The app today uses cooldowns instead (6 months after a 1-month pause, 12 after a 2-month one); those differ from a rolling window in edge cases.
  2. Does a pause push back the earliest cancel date? You leaned "probably not, since they can't cancel before pause-eligible". Recommendation: no, keep it simple: earliest cancel = later of (pause-eligible date, end of the first billing cycle ≥ 1 month out).
  3. Auto-activation on orientation day: OK to happen automatically with the confirm/undo banner, or should it wait for a click?

Phase 4 — Stop full-record rewrites on page load execution-ready: false

Findings

  • Every page load runs saveAllMembersToFirestore, which rewrites every member doc with .set() (no merge) from whatever this browser has in memory. Every single-member save is also a full .set().
  • Risks: two people with the app open can overwrite each other's edits; a browser with stale or partially-loaded data can write that over good data; one bad record (e.g. an undefined field) makes the whole batch fail.

Changes

  • Load-time checks (auto-resume, off-boarding → cancelled, billing roll, pause start) track which members they actually changed and save only those.
  • Saves send only the changed fields with update() (or set(…, {merge:true}) where a doc may not exist yet); strip undefined/empty strings; await and surface failures instead of only logging.
  • Same treatment for the waitlist batch save after the Google Sheet sync.
Firebase safety: Firestore emulator tests first (two-writer overwrite scenario must fail on old code, pass on new); JSON snapshot of clayHub_members and clayHub_waitlist before shipping; no rules change expected (collections already have rules); spot-check real docs after deploy.
BDD: Given Christie edits Member A's notes while an employee has the app open, when the employee reloads, then Christie's notes survive. · Given one member has a malformed field, then every other member still saves. · Given a save fails, then the person sees an error instead of silent loss.
