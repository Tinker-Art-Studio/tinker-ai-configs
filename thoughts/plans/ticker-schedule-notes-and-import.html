⚠️ The getShiftForDate() precedence trap

js/app.js. The guard is a bare if (future), not if (future && future.recurring). Any in-range futureSchedule short-circuits and returns null without ever consulting base overrides or base recurring.

So writing a futureSchedule with a past validFrom does not layer on top of someone's real schedule — it silently hides it. Sibling helpers (countUpcomingOverrides, getNormalRecurringShift) do check future.recurring first; getShiftForDate is the odd one out.

Two consequences that matter for Phase 2:

  • The in-app CSV importer (Settings) writes only to futureSchedule, with overrides: {} hardcoded on every write. Its conflict check looks for an existing futureSchedule and cannot see that base-field data is the thing actually in force. For anyone whose live schedule lives in base recurring/overrides — which is nearly everyone — running it would hijack precedence and hide their real schedule behind a no-overrides shell.
  • It is also weekly-pattern only by design: the format is name,day,start,end,studio,validFrom,validUntil. No date column, no note column. It cannot express a dated one-off at all. That scope was an explicit decision confirmed with Christie Aug 31 — correct at the time, but it is the gap Phase 2 fills.

Phase 1 — Recurring notes survive an edit (data loss, do first)

The bug

Several people have notes on their recurring weekly shifts — not just dated overrides. Ivy's Thursday carries 14:30 Thursday Huddle · 15:05 1:1 — Maryssa & Ivy; Kaitlyn's and Leah's carry class names and 1:1s; Erica's Friday carries FAN (Friday Art Night).

handleSaveSchedule() rebuilds recurring from the editor grid inputs, and the grid has no note input — it reads only start, end and studio per day. So opening any of those people in the Schedule Builder and clicking Save silently drops their recurring notes. No warning, no diff, and the notes are only visible again if someone notices they're gone.

Given Ivy's Thursday recurring shift has the note "14:30 Thursday Huddle · 15:05 1:1 — Maryssa & Ivy"
When an admin opens her schedule in the Schedule Builder and changes an unrelated day's end time, then saves
Then her Thursday note is still there afterwards

Approach

Add a note field per day to the recurring grid, mirroring the one the per-date override form already has. Preferred over silently preserving the existing note behind the scenes: the notes are real content people rely on, and they should be editable in the same place the hours are, not invisible-but-preserved.

  • Add a note input per weekday row in the schedule editor grid
  • handleSaveSchedule() reads it into recurring[day].note, stripping empty strings (Firestore rejects undefined; the codebase convention is to omit rather than store empty)
  • Populate it when the editor opens, from the existing recurring data
  • Confirm the same path is safe for futureSchedule.recurring, which the editor also writes when a future schedule is active
Worth checking before building: a regression test that loads a schedule with recurring notes, simulates a save with the note input untouched, and asserts the notes survive. This bug is invisible in the UI, so a test is the only thing that will keep it fixed.

Phase 2 — Dated-override import in Settings

The chore this removes

Every term — fall, spring, summer — there are roughly 70–75 dated one-off entries to enter: camp days, SDOC coverage, split days, half-days, break camps, each with a descriptive note. Neither in-app tool can do it (see the trap section above), so each term falls back to a one-off HTML file on the Desktop whose payload Claude has to edit by hand. It works and it has real safety rails, but it is not something Christie can do alone.

Given a term's worth of dated shifts with notes, in a CSV
When Christie imports it from Settings and confirms the dry run
Then those dates appear on the right people's schedules, existing entries are untouched, and no confirmation emails are sent

Design constraints (each one learned the hard way)

  • Write to base overrides, never futureSchedule — see the trap section. This is the single most important constraint.
  • Merge by date key; never replace the map. The Desktop tool replaces overrides wholesale via mergeFields, which is why its payload must carry every entry that should survive — and why the Sep 4 run needed a full snapshot diff to catch that Leah's Sept 8 would have been erased. An in-app version should add and update by key so this class of loss is structurally impossible.
  • Reuse the dry-run → snapshot → write flow. It is proven, Christie is used to it, and it caught a real problem on its first use.
  • Show a diff, not just counts. The Desktop tool's dry-run table shows old vs new counts; that was enough to notice something was wrong (16 → 15) but not to say what. The snapshot had to be downloaded and diffed separately to find it. An in-app version should name the specific dates being added, changed and removed.
  • Suppress confirmation emails on bulk import. Currently moot — the trigger is Extra Shift only as of Sep 4, and term entries don't use that phrase. But if the trigger ever widens again, a bulk importer without its own suppression would blast staff. See ticker-oneoff-shift-reminders.
  • Match on full name, not first name. The existing CSV importer already does this (resolveFutureScheduleTargets) and blocks on zero or multiple matches rather than guessing. Follow it.

Format sketch

A second accepted CSV shape alongside the existing weekly one, distinguished by its header row:

namedatestartendstudionote
Leah Trumble2026-11-1108:3018:30clayhub08:30-12:30 SDOC / Break camp (AM) · 15:00-18:30 regular shift
Kayleigh Wood2026-12-26(blank = day off)
Open question: notes contain commas and middots routinely, so a naive split(',') will not survive this format — unlike the existing weekly CSV, whose parser explicitly documents that it has no quoted fields and so a plain split is safe. This format needs either real quoted-field parsing or a different delimiter. Decide before building.
