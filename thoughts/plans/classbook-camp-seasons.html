Context — why "just make a Summer 2027 semester" doesn't work today

Summer is not a semester in the code; it is one hard-wired key. Research on Sep 20, 2026 (read-only) found:

  • semesterType: 'summer-camp' is assigned in exactly two places — loadConfig()'s auto-migration that creates summer-2026 if missing (firebase-data.js:59-71) and getDefaultConfig() (:99-108). The + New Semester modal cannot create a camp-type semester — createNewSemester() never sets semesterType, so anything Christie creates there is a weekly-classes semester with a roster and a week grid.
  • 11 hard-coded 'summer-2026' references decide behavior: loadLessonData() and the live listener load ALL summer camp data into currentLessonData['summer-2026'] (firebase-data.js:336, :554); renderAdminGrid() routes semKey === 'summer-2026' to renderSummerCA() (app.js:4177); the summer content-count reads currentLessonData['summer-2026'] (app.js:3732); plus the config sites above. Everything else already keys off semesterType === 'summer-camp' (12 sites) — good news, the pattern half-exists.
  • The summer collections have no season on them. summerCamps_curriculum (48 docs: campTopic, teacher, blocks, publishedToClassbook, …) and summerCamps_schedule (229 docs: campTopic, week, timeSlot, teacher, maxCapacity, enrollment, …) carry no year/season field; loadSummerCampData() does .get() on the whole collection with no filter. summerCamps_lessonData docs are keyed teacher|||campTopic|||blockName|||projectTitle — a 2027 camp with the same name and project as a 2026 one would collide on the same document.
  • The Summer Camp App is itself single-season — titled "Summer Camp 2026", js/config.js hard-codes startDate: '2026-05-26', endDate: '2026-08-11', date pickers are bounded to 2026, and it is the writer of record for camps, schedule, materials and project details. Classbook only reads those (plus writes teacher plans to summerCamps_lessonData). So the season has to be born in the Summer Camp App's data, or Classbook has nothing to filter on.
  • saveLessonData() / saveSingleLesson() route to the summer collections by key prefix (semesterKey.startsWith('summer-')), not by semesterType. The backtracking-audit plan named this as residual R5-3 and pointed at its companion's Phase 18 (block ambiguous keys at creation). This plan closes it structurally — once semesters carry an explicit type, routing must follow the type, and the prefix check goes away.
⚠️ What a teacher would see if Christie created "Summer 2027" today with + New Semester: nothing wrong at first — an unpublished weekly-classes semester with 16 weeks and a roster. But it would be the wrong shape entirely (weeks and classes, not camps and blocks), and nothing in the Summer Camp App would feed it. Don't do this as a workaround; it would also need deleting, and deleteSemester()'s lesson-data cleanup is warn-only.

Completeness check — what if this is interrupted?

  • After Phase 1 only: Summer 2027 can exist but shows 2026's data (loaders not yet season-filtered) — acceptable only if Summer 2027 stays unpublished; Phase 1's acceptance therefore includes "a camp semester without a season filter is admin-only until Phase 3". Weekly semesters are unaffected.
  • Mid-Phase 2: some docs stamped, some not — both apps treat unstamped as 2026, so nothing breaks; re-run to finish.
  • After Phase 2, before Phase 3: everything works as today; the field is inert.
  • Mid-Phase 3: the dangerous window — one writer season-scoped, another not. Phase 3 is therefore designed as one deploy (all summer writers together), with the full two-season canary suite green before it, and Summer 2027 still unpublished.
