Plan: Tinker Playbook — Concurrent-Edit Data Loss Fix

Goal: Stop the Tinker Playbook app from silently overwriting other people's changes when two sessions edit the playbook data at different times.
App: tinker-playbook — ~/tinker-playbook/js/firebase-data.js, js/app.js
Incident: Anika (manager) added content to a role's playbook; two days later it was gone. No Firestore rules change and no app deploy occurred in that window, ruling out the two usual causes. Root cause traced to the write pattern below.
Risk: Medium — touches the single write path used by every edit action in the app (11 call sites), but the fix itself is additive (a guard before an existing write), not a schema change.
execution-ready: false — pending review

Root Cause

All playbook content — every role, section, and entry — lives in one Firestore document: playbooks/rolesData. The whole document is loaded into a single in-memory object (_rolesData) once per browser session. Every edit action (add/edit/delete a role, add/edit/delete an entry, add/delete an annual item, edit prompts, the Settings → "push current roles data to Firestore" button) mutates that in-memory object and then calls saveRolesData(_rolesData), which does a full-document .set(data) — the entire document is replaced with whatever is currently in memory.

A realtime onSnapshot listener is supposed to keep every open session's in-memory copy current. But there is no check, anywhere, that a session's copy is actually still current before it writes. If any session's copy goes stale — a tab left open across days, a dropped/errored listener, or simply two people editing around the same time — the next save from that session silently reverts everyone else's changes since that session's last sync. Nothing errors, nothing warns the user, and nothing in Firestore records that it happened.

The Settings → "Push current roles data to Firestore" button (seedDataToFirestore, wired to settings-seed-btn) is the sharpest version of this risk: it's a deliberate, one-click, unconditional full overwrite of live data, gated only by a generic confirm() dialog with no indication of what it will clobber.

This is the most plausible explanation for the incident: some session (Anika's own stale tab, another admin's tab, or the Settings seed button) saved from an outdated in-memory copy after her additions landed, wiping them out with no error message at all.

Phase 1 — Optimistic-concurrency guard on the write path

What it does

Add a version check to the one choke point all saves already go through: saveRolesData() in firebase-data.js. Wrap the write in a Firestore transaction that reads the live document, compares its version to the version the caller last loaded, and only writes if they match. If they don't match, the write is rejected — the caller is told there's a conflict instead of the document being silently clobbered.

Add a _version integer field to the rolesData document, incremented only inside this transaction. (Not reusing lastUpdated for this — client clocks can skew or collide; a server-incremented counter is unambiguous.)

Given: Session A loaded rolesData at version 5 When: Session A saves an edit Then: The transaction reads version 5 from Firestore, matches, writes version 6 AND Session A's local copy is updated to version 6 Given: Session A and Session B both loaded rolesData at version 5 When: Session A saves first (version 5 → 6), then Session B tries to save (still holding version 5 locally) Then: Session B's transaction reads version 6, sees it doesn't match its expected 5 AND Session B's write is rejected — Firestore still holds Session A's version-6 data unchanged AND saveRolesData() resolves with { success: false, reason: 'conflict' } instead of throwing or silently succeeding Given: The device is offline when a save is attempted Then: saveRolesData() resolves with { success: false, reason: 'offline' } (existing local-storage fallback still fires so no data is lost locally) AND the transaction is never attempted against a document that can't be reached
✅ No schema migration. No new collection. No rules change — playbooks/{docId} rule already covers this doc. The full-document .set() stays (it's a legitimate whole-object write, not a partial edit standing in for one) — the fix is gating it on a freshness check, not switching to updateDoc.

Phase 2 — Make every call site handle a conflict instead of ignoring the result

What it does

Today every call site does saveRolesData(_rolesData).then(() => { render...; }) and never checks whether the save actually succeeded. Update all 11 call sites (saveRole, confirmDeleteRole, backfillMissingSections, addInlineTask, deleteInlineTask, setTaskDay, saveEntry, deleteEntry, savePrompts, addAnnualItem, deleteAnnualItem) plus seedDataToFirestore to check the result.

Given: A builder clicks "Save" on an entry and the save comes back { success: false, reason: 'conflict' } When: The failure is handled Then: An alert explains someone else updated this playbook while they were working AND the app reloads the latest rolesData from Firestore (via the existing realtime listener data, already current) AND the modal stays open with their typed content intact so they can re-apply it and save again AND their edit is NOT silently lost — they're told to retry, not left thinking it saved Given: Christie clicks Settings → "Push current roles data to Firestore" When: Another session has written since Christie's copy was loaded Then: The same conflict check fires (seedDataToFirestore routes through the same guarded save) AND Christie sees "Someone else has updated the playbook since you last loaded it — refresh and try again" instead of the button silently overwriting their changes
The confirm() copy on the seed button should also be tightened to state plainly what it does ("This replaces ALL roles data in Firestore with what's currently loaded in this browser tab") — it's a rarely-used escape hatch, not a normal save action, and should read like one.

Phase 3 — Emulator test coverage

What it does

Per this app's AGENTS.md, any data-write change needs a failing-then-green emulator test. Add tests against the Firestore emulator (firebase emulators:start --only firestore from studio-hub):

  • Two sequential writes with the same starting version: second one is rejected, first one's data survives unchanged.
  • A single writer with the correct version: write succeeds, version increments by 1.
  • Existing Playwright suite (e2e/admin.spec.js, e2e/smoke.spec.js) — confirmed neither currently exercises concurrent-session saves; this is a real coverage gap being closed, not a regression risk in existing tests.

Not in scope

  • Splitting rolesData into one Firestore document per role. Would shrink the blast radius further (an edit to Role A could never touch Role B's data) but is a real data migration touching every read/write in the app, for a team small enough that concurrent edits to the same role are rare. The version guard directly fixes the incident; revisit this only if the app grows to a size where same-role concurrent editing becomes common.
  • Applying the same version guard to playbooks/progress_{uid} docs (per-user onboarding progress). Collision there requires the same person editing from two devices at once — low likelihood, low impact (only their own progress). Not worth the extra complexity in this pass.
  • Auto-merging a rejected edit against the freshly-loaded data automatically. Simpler and safer for v1: reject, reload, ask the user to redo the one small action (add a task, edit an entry, etc.) — every edit here is a small discrete action, so retrying is low-friction.

Decisions Log

  • Aug 2: Chose a transaction + version-counter guard over a per-role document schema migration. Rationale: fixes the actual incident (silent overwrite) with much less risk and no data migration; team size doesn't currently justify the bigger change.
  • Aug 2: On conflict, reject and ask the user to retry rather than attempt an automatic merge. Rationale: every write in this app is a small, single-field-ish action — retrying costs the user one click, not a form's worth of re-entry.
  • Aug 2: playbooks added to the automated backup script (~/tinker-backups/backup.js) as a prerequisite, independent of this plan — it was previously the only collection missing from backups, so there was no way to recover the lost content even after the fact.
