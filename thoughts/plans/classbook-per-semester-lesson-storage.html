Plan: Classbook — each class semester in its own document

Goal: Teachers never hit a wall where lesson saves stop working. Every Fall/Spring semester's lessons live in their own Firestore document instead of one shared document that's almost full, with no lesson lost or changed in the move.

Design

  • New store 'semesterDoc': lessons for semester K live in curriculum/lessons_K as { <lessonKey>: lesson, lastUpdated, lastUpdatedBy }, the same lesson shape as today. A semester uses it when appData.semesters[K].lessonStore === 'doc'. lessonStoreFor returns 'semesterDoc' for those, 'weekly' for weekly semesters without the flag, and 'camp' as today.
  • One path helper replaces the hard-coded doc('lessonData') in every weekly site: weeklyLessonRef(K) returns the doc, and weeklyLessonPath(K, lessonKey, field?) returns lessonKey.field for 'semesterDoc' or K.lessonKey.field for legacy. Every site listed above goes through them, with a static ratchet: no doc('lessonData') outside the helper and the legacy migration code.
  • Loading: loadLessonData reads legacy lessonData (for unmigrated semesters) plus each lessons_K for migrated semesters listed in appData. currentLessonData[K] keeps its current shape, so no rendering code changes. The live listener follows the same split: one listener per migrated semester doc, plus the legacy one.
  • New semesters (createNewSemester) are created with lessonStore: 'doc' from Phase 3 on, so the shared document never grows again.
  • Stale tabs can't write to the old location (rules, Phase 2). appData gets migratedSemesters: [K, …]. The lessonData rule refuses any update whose changed top-level keys intersect migratedSemesters, for every role including managers, except a manager's removal of exactly that key in Phase 4. A tab loaded before a migration then gets a loud permission error on save ("reload"), instead of silently writing a lost edit to the stale copy or recreating an orphan. This is enforced on the server, so it closes the stale-tab problem that sank the make-active plan's delete design.
  • Studio Hub alerts also listen to lessons_K for each migrated semester (read from appData.migratedSemesters), so Q&A alerts don't vanish.

How: a manager-only button in Settings, "Move this semester to its own storage", runs:

  1. A forced-server read of lessonData[K], then a JSON snapshot download (classbook-K-lessons-<ISO>.json). The move refuses if either fails.
  2. One transaction that reads lessonData and lessons_K (which must not exist) and appData (K must exist, not yet migrated). It sets lessons_K = the map read inside the transaction, sets appData.semesters.K.lessonStore = 'doc', and adds K to migratedSemesters with arrayUnion. Once this commits, Phase 2's rule fences the old copy.
  3. Verify: a forced-server read of lessons_K must deep-equal the transaction's source map. On mismatch it shows a loud alert, and the manager undoes it with "Move back" (removes the flag and list entry; the old copy is intact because nothing deleted it).

It's run by Christie at a quiet time. She also spot-checks one lesson in the Firebase Console.

Firebase safety checklist

  • Rules: Phase 2 is a shared-rules change. The rules tests come first, all tests must pass, and it deploys only through deploy-rules.sh --approved <sha> after the phrase. New lessons_K docs need no new rule (curriculum/{docId}).
  • Snapshots: JSON downloads before the move (Phase 3) and before the removal (Phase 4). Nightly backups cover the whole curriculum collection, including the new docs.
  • Atomic: the move is one transaction (target created, flag set, list updated). The removal is one manager update that the rules restrict to deleting exactly that key.
  • Verified: deep-equal checks from forced-server reads after the move and before the removal.
  • Reversible: Phase 3 can be undone ("Move back") until Phase 4. After Phase 4, the snapshot plus the nightly backup can restore it.
  • Partial updates: per-field dotted paths as today (buildLessonFieldUpdates), just rooted at lessonKey in the new doc. No whole-lesson set().
  • Spot checks: one real lesson in the Firebase Console after Phase 3 and after Phase 4.

If interrupted

  • Phase 1–2 code deployed, nothing migrated: fully safe, and everything behaves as today.
  • Mid-move: the transaction either committed or didn't, so there's no half state. After commit and before verify, the old copy is intact and "Move back" exists.
  • Between Phases 3 and 4: two copies exist. The app uses the new one, and the rules freeze the old one. No space is freed yet, so the lessonData headroom is unchanged, same as today.
