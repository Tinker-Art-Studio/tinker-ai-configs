Cross-app coordination

Confirmed with Christie: this plan is scoped to Studio Hub only (users/{uid}, Firestore rules, Manage Team UI). It does not touch timeclock_settings/employees.roster[] or any file inside tinker-timeclock/.

Christie is running a parallel session with its own plan — tinker-ticker-archive-employees.html — for Tinker Ticker's roster/schedule-visibility side (kiosk clock-in, Who's Working, Schedule Builder). That plan independently arrived at the same boundary and explains why, which is worth restating here since it's the reason this plan doesn't write to the roster:

  • timeclock_settings/employees is saved as one full array on every write (saveEmployeeRoster() / this repo's own syncTimeclockRoster()/addToTinkerTickerRoster()) — no per-field update exists. Two systems writing to it independently risk clobbering each other's concurrent changes (e.g. a PIN just set in Ticker).
  • The two features are additive, not overlapping: Studio Hub's active:false on users/{uid} revokes app access everywhere (can no longer log into any of the 21 apps, including Ticker itself). Ticker's own Archive flips the roster entry's existing active flag, which controls schedule/kiosk visibility (no longer shown in Who's Working, Schedule Builder, or the kiosk PIN pad) independent of whether they can still authenticate.
  • Neither plan calls into the other's write path. "Fully offboarded" = archived in both places; that's a manual two-click action across two apps for now, not a single trigger. A shared trigger is a plausible fast-follow once both features exist and are stable, not part of this plan.
Non-goal, explicit: no single button that archives someone everywhere at once. Christie will archive in Studio Hub (revoke access) and, separately, in Ticker (hide from schedule/kiosk) if both are needed for a given person.

Goal

Give admins and managers a reversible "Archive" action in Manage Team that immediately revokes a person's access to every Tinker app, hides them from the default team list, and preserves their exact role/appAccess/studios so "Reactivate" restores them with zero reconfiguration — replacing the current permanent, silently-reversible-by-relogin Delete.

Design decisions

Fields on users/{uid}: add active (boolean), archivedAt (ISO string), archivedBy (email of who archived). Missing active is treated as true everywhere (rules use .get('active', true); UI uses user.active !== false) — existing users need no migration write.
Rules gating: add isActiveUser() and require it inside isAdmin(), isManager(), isManagerOrAbove(), hasAppAccess(), and — as its own explicit check, since it doesn't call the other four — belongsToStudio(). This is the single change that cuts off all 21 apps at once. Self-read/self-update stay independent of it (see table above) so the app can still load and show an "archived" state instead of crashing. isKiosk() (line 32-38) is also deliberately left independent — it's a hardcoded PIN-lookup bypass unrelated to any person's role, and kiosk/schedule visibility for an archived person is governed by Tinker Ticker's own separate roster active flag (see Cross-app coordination above), not this one.
Pin active in the self-update rule alongside role/appAccess/studios, so an archived person can never self-reactivate.
Who can archive/reactivate: admin and manager, matching the existing manager-can-edit-appAccess/studios boundary. Not adding new role restrictions beyond what already exists for Manage Team.
Data preserved on archive: role, appAccess, studios are left exactly as-is — only active flips. Access is denied purely by the rules gate, so there's no need to clear the fields, and leaving them intact is what makes Reactivate a single click with no reconfiguration.
UI: the per-card "Delete" button is replaced with "Archive" (active users) / "Reactivate" (archived users). Archived users are hidden from the default Manage Team list behind a "Show archived (N)" toggle next to search, shown dimmed with an "Archived {date}" badge when revealed. CSV export gains a status column.
Rejected: keep a hard-delete option in the UI. The current destructive action is exactly what Christie asked to move away from. True permanent deletion of a users doc remains possible via the Firebase Console for genuine junk records (e.g. a mistyped signup), but this plan doesn't wire a UI button for it.

Second-model review findings (2026-08-28) — both fixed below

1. Admin self-archive had no recovery path. firestore.rules:128 (allow write: if isAdmin();) is unrestricted and, because Firestore ORs sibling allow rules, sits completely outside the self-update rule's fieldUnchanged('active') pin. An admin could write active: false to their own doc through this rule; the instant it commits, isAdmin() requires isActiveUser() and fails for them on every future request — including their own attempt to undo it, since the self-update rule (their only remaining path to their own doc) pins active unchanged. No client-side recovery; only another active admin or a manual Console edit fixes it. This is the identical bug shape to a loophole already found and fixed in this same file for managers (firestore.rules:114-122, regression tests at rules.test.js:448-468) — that fix just didn't need to consider a field like active that didn't exist yet. Fix (added to Phase 1 below): extend the admin-write rule so an admin can do anything to other users' docs (unchanged), but can never touch their own active field — an admin can only be archived/reactivated by a different admin. This forecloses admin self-archiving entirely, which is the deliberate tradeoff: simple, rules-only, and avoids needing an "are you the last active admin" check (which would require a Firestore query inside the rule and isn't attempted).
2. belongsToStudio() needed its own explicit active check. Its non-admin branch (studio in getUserData().studios) doesn't route through isAdmin()/isManager()/etc. at all, so gating those four functions on isActiveUser() would not have touched this one — an archived staff member with a studios array would keep access to every belongsToStudio()-gated collection: rosterManager, clayHub_members/clayHub_waitlist/clayHub_appData, clayInventory. Fix (added to Phase 1 below): belongsToStudio() gets its own explicit isActiveUser() check rather than inheriting one.

Phase 1 — Firestore rules + data model

Acceptance criteria (user outcome)

When a users/{uid} doc has active: false, that person can no longer read or write anything gated by isAdmin/isManager/isManagerOrAbove/hasAppAccess/belongsToStudio in any app — verified by emulator tests, not just Studio Hub's own UI. They can still load Studio Hub far enough to see their own (archived) doc rather than the app erroring. They cannot un-archive themselves.

Given an admin's users/{uid} doc has active: false When that admin's client tries to read a payroll document Then the read is denied (isAdmin() now requires isActiveUser()) Given a staff member has appAccess: ['kpiData'] and active: false When they try to read a kpiData document Then the read is denied, even though appAccess still lists 'kpiData' Given an archived user's own doc When they read or lightly self-update it (e.g. a Ticker login patch) Then the read/update succeeds and active stays false (pinned, unchanged) Given an archived staff member When they attempt to write active: true to their own doc directly Then the write is denied by the self-update rule's fieldUnchanged('active') pin Given a manager (not admin) editing an admin's users/{uid} doc When they try to write active: false (archive) or active: true (reactivate) Then the write is denied — only the target admin themself or another admin can change it Given a manager editing another manager's or a staff member's doc When they try to write active: false or active: true Then the write succeeds — unchanged from their existing appAccess/studios capability Given an admin's own users/{uid} doc (active: true) When that admin tries to write active: false to their own doc via any rule path, including the blanket admin-write rule at firestore.rules:128 Then the write is denied — an admin can only be archived/reactivated by a different admin, never by themselves (closes the self-lockout hole below) Given an archived staff member whose studios array still lists 'clayhub' When they try to read a clayHub_members document (gated by belongsToStudio()) Then the read is denied — belongsToStudio() checks isActiveUser() directly, not just via isAdmin() Given an archived manager (previously isManagerOrAbove()-gated) When they try to read a payroll document Then the read is denied

Work

  • Add isActiveUser() helper to firestore.rules: isAuthenticated() && getUserData().get('active', true) == true
  • Require isActiveUser() inside isAdmin(), isManager(), isManagerOrAbove(), hasAppAccess()
  • belongsToStudio() (found in second-model review — its non-admin branch doesn't route through any of the other four functions, so it needs its own check): rewrite to return isActiveUser() && (isAdmin() || studio in getUserData().studios);
  • Add fieldUnchanged('active') to the self-update rule (line ~108-112)
  • Admin self-archive guard (found in second-model review — same OR'd-sibling-rule bug shape already fixed once in this file for managers): change the admin-write rule (line ~128) from allow write: if isAdmin(); to:
    allow write: if isAdmin() && (request.auth.uid != userId || fieldUnchanged('active'));
    Admins keep unrestricted write on every other user's doc (including delete); only their own active field becomes untouchable by themselves, closing the self-lockout hole with no recovery path.
  • Manager-on-admin guard (resolved in review): extend the manager-update rule (line ~123-125) so a manager can't touch an admin's active field, using the same pattern as the existing role pin:
    allow update: if isManager() && request.auth.uid != userId && request.resource.data.role == resource.data.role && (resource.data.role != 'admin' || fieldUnchanged('active'));
    Managers keep full appAccess/studios editing on admins (that existing gap is explicitly tabled, not touched here) — only active gets the guard.
  • Extend rules.test.js's existing "Users —" describe block with the nine scenarios above, plus one per already-tested collection type (finance, KPI, timeclock) confirming an otherwise-authorized-but-archived user is denied
  • Run npm test — must be green before deploy

  • updateDoc-style partial writes, never set without merge, for archive/reactivate
  • No bulk delete/import in this plan — nothing to snapshot
  • New fields (active, archivedAt, archivedBy) on an existing, already-ruled collection — no new collection, no new rule block needed
  • Deploy command: firebase deploy --only firestore:rules from /Users/christiehubley/studio-hub, only after the standing "approved to change firebase" phrase, green tests, and a commit

Completeness check — what if this is interrupted mid-way

  • Interrupted after Phase 1, before Phase 2: safe. Rules are deployed and tested; no UI references active yet, so no user is archived and behavior for existing users is unchanged (missing active defaults to active everywhere).
  • Interrupted mid-Phase 2: safe as long as each function (archiveUser, renderUserCard, loadTeamUsers, CSV) is committed individually — a partially-shipped UI at worst shows an inconsistent Archive/Delete label, not data loss, since no destructive write path exists once deleteUser is removed.
  • Interrupted mid-Phase 3: safe — archiving individual employees is independent per-person; resume by archiving whoever's left.
