Plan: Archive Employees — Tinker Ticker

Status: NOT execution-ready. Plan only — no implementation code has been written. Waiting on Christie's review + a second-model review before Phase 1 begins.
📝 Revised Aug 28 — Christie is running a parallel session planning a Studio-Hub-wide offboarding flow (revoking appAccess via users/{uid}, which gates all 21 apps). That session found timeclock_settings/employees.roster[] is already written to from Studio Hub's side too (syncTimeclockRoster / addToTinkerTickerRoster). Original design here used two independent flags (roster active + a new schedule-doc archived) — replaced below with a single-flag design keyed only off the roster's existing active field, so this plan's behavior is correct regardless of which system (Ticker's own Archive button, or a future Studio-Hub-driven roster write) ends up flipping it. See the new "Cross-app coordination" open question.
Goal: Give admins a reversible "Archive" action for a roster entry that makes that person disappear from every current-schedule view (Who's Working, Schedule Builder's schedule list, the roster picker, kiosk PIN entry) without deleting any of their data — and an "Unarchive" that brings them back exactly as they were.
App: tinker-timeclock — ~/tinker-timeclock/js/app.js, js/firebase-data.js
Why now: The roster has 37 entries; only 18 are in the live Fall 2026 schedule. The existing "Remove" button is a hard, permanent delete (roster entry + both schedule docs, no undo) — too destructive for routine end-of-term cleanup.
Risk: Low data risk (no field this plan touches is ever deleted — only two new boolean flags are added/toggled). Main risk is UI coverage: several views read schedule data directly and must all respect the new flag, or an archived person could still show up somewhere.
Reversible: Yes, by design — Unarchive clears both flags and restores full visibility with zero data loss.

Core design decision

Archiving writes exactly one flag: active: false on the roster entry in timeclock_settings/employees. No new field is added to timeclock_schedules at all. The 3 places that already check roster active (kiosk PIN, roster settings list, employee picker) are fixed for free, as before.

Filter once, centrally, keyed off the roster — not a second flag. loadSchedulesData() (app.js:2770-2788) already loads employeeRoster alongside allSchedules. It's changed to partition schedule docs by looking up each one's owner in the roster (via the existing employeeRoster.find(e => e.id === sched.uid || e.claimedBy === sched.uid) resolution already used by getSchedName() at app.js:2792) and checking that person's active field — producing allSchedules (roster active — every existing consumer keeps the name and needs zero code changes) and archivedSchedules (roster inactive, used only by Phase 2's "Show Archived" panel).
Considered and rejected — a second archived flag directly on the schedule doc (original draft of this plan): works in isolation, but Studio Hub's own roster-writing code (syncTimeclockRoster / addToTinkerTickerRoster) only ever touches the roster document, not individual schedule docs. If a future Studio-Hub-driven offboarding flow flips active:false on the roster directly, a second, Ticker-only flag it doesn't know about would silently go unset — the person would vanish from the roster list and kiosk but keep showing up in Who's Working. Keying everything off the one field both systems already write eliminates that failure mode entirely, and is also less code.
Considered and rejected — editing all 4 render functions individually: works, but multiplies the chance of missing one, and every future new consumer of schedule data would need to remember the same check again. A single choke point is safer to review and safer long-term.
Considered and rejected — moving/blanking recurring/overrides into a backup field and restoring on unarchive: works, but creates two copies of the same data that can drift, and is meaningfully more code than a boolean flag for the same visible result. A flag is trivially reversible; a data move is not risk-free.

The two features should combine additively (archived-in-Ticker + access-revoked-in-Studio-Hub = fully offboarded) without either calling into the other's write path. Phases

Phase 1 — Data layer: archive/unarchive functions + centralized filter

Acceptance criteria: Two new functions, archiveEmployee(empId, name) and unarchiveEmployee(empId, name), mirroring the existing removeEmployee signature/pattern. Archiving sets active:false on the roster entry only — via the existing saveEmployeeRoster full-array-save convention already used by every other roster mutation in this file (add/remove/claim/set-PIN) — not a new write pattern. No timeclock_schedules document is touched by either function. loadSchedulesData() is changed to look up each schedule doc's owner in the freshly-loaded roster and split into allSchedules (owner's active !== false) and archivedSchedules (owner's active === false).

Given: an employee with an existing timeclock_schedules doc (recurring + overrides + futureSchedule) When: archiveEmployee() is called Then: the roster entry gets active:false AND the schedule doc itself is never written to — every field on it is untouched AND on next loadSchedulesData(), the person is absent from allSchedules and present in archivedSchedules Given: an employee who has a roster entry but NO schedule doc yet (never been scheduled) When: archiveEmployee() is called Then: active:false is set on the roster entry AND the roster-only archive still works (they vanish from roster list / picker / kiosk) with no error Given: an archived employee When: unarchiveEmployee() is called Then: active is set back to true on the roster entry (their schedule doc, if any, was never touched by archiving, so nothing needs restoring on it) AND the person reappears in allSchedules, roster list, picker, and kiosk PIN lookup Given: a person's active flag is flipped to false by some OTHER write path in the future (e.g. a Studio-Hub-driven roster sync), not by this plan's archiveEmployee() function When: loadSchedulesData() next runs Then: they are still correctly excluded from allSchedules and included in archivedSchedules — the filter reads the roster's active field directly, it does not care who set it
⚠️ Firestore: the roster write keeps using the existing saveEmployeeRoster(array) full-array-save pattern already used by add/remove/claim/set-PIN — not a new convention. No new field is ever added to any timeclock_schedules document, so there is nothing there that needs updateDoc-vs-setDoc care for this feature specifically.
Open question for review — no test harness exists in this repo. AGENTS.md requires "a failing emulator test first, then fix, then green" for any data-write change, but tinker-timeclock has no jest/emulator setup at all today (unlike studio-hub). Two options, needs a decision before Phase 1 starts:
  1. Stand up a minimal emulator+jest harness for this repo, mirroring studio-hub's firebase emulators:exec --only firestore jest pattern — real automated coverage, but meaningfully more setup than the feature itself.
  2. Skip automated tests for this phase; instead write a small read-only verification script (same pattern as check-roster-duplicates.html) that Christie runs by hand after Phase 1 to confirm archive/unarchive didn't touch recurring/overrides — faster, but not a repeatable regression test for future changes.

Phase 2 — Roster settings UI: Archive button + "Show Archived" panel

Acceptance criteria: Each row in renderRosterList() gets a new "Archive" button (alongside the existing PIN/Remove buttons — Remove stays, for the rare true-delete case). A new "Show Archived (N)" link/toggle reveals a separate list of archived entries (renderArchivedRosterList()), each with an "Unarchive" button. No existing button's behavior changes.

Given: the admin is on the Schedule Builder tab's Employee Roster section When: they click "Archive" on an employee's row Then: a confirm prompt explains this is reversible (contrast with Remove's "cannot be undone" wording) AND on confirm, that employee disappears from the visible roster list and the "Select employee" picker AND a "Show Archived (1)" indicator appears/increments Given: at least one employee is archived When: the admin clicks "Show Archived" Then: a panel lists each archived employee by name with an "Unarchive" button AND clicking Unarchive removes them from this panel and restores them to the main roster list, the employee picker, and (per Phase 3) Who's Working / Schedule Builder's card list

Phase 3 — Verify Who's Working & Schedule Builder's card list respect the filter

Acceptance criteria: Because of the Phase 1 design (centralizing the filter inside loadSchedulesData()), this phase should require no code changes to renderWhosWorkingDaily/Weekly/Monthly or renderAllSchedulesList — they already consume allSchedules unchanged. This phase is a deliberate verification pass, not new implementation, specifically to catch any consumer of schedule data this plan's research missed.

Given: an employee is archived When: I view Who's Working in Daily, Weekly, and Monthly modes, for today and for a date they'd normally be scheduled Then: they do not appear in any of the three views, on any date Given: an employee is archived When: I open Schedule Builder's schedule-card list Then: their card does not appear Given: an employee is unarchived When: I repeat both checks above Then: they appear again, identically to before archiving, in every view

Not changed

  • timeclock_entries (clock history) — never read, written, or filtered by this feature
  • The existing "Remove" button and deleteScheduleFromList — both stay exactly as they are today, for the cases where a true permanent delete is actually wanted
  • Studio Hub's users collection, appAccess, login/auth — archiving is a Ticker-only concept; it does not touch account access anywhere else
  • Firestore rules — no change needed (see research table above)
