That session found timeclock_settings/employees.roster[] is already written to from Studio Hub's side too (syncTimeclockRoster / addToTinkerTickerRoster). Original design here used two independent flags (roster active + a new schedule-doc archived) — replaced below with a single-flag design keyed only off the roster's existing active field, so this plan's behavior is correct regardless of which system (Ticker's own Archive button, or a future Studio-Hub-driven roster write) ends up flipping it. See the new "Cross-app coordination" open question.
Goal: Give admins a reversible "Archive" action for a roster entry that makes that person disappear from every current-schedule view (Who's Working, Schedule Builder's schedule list, the roster picker, kiosk PIN entry) without deleting any of their data — and an "Unarchive" that brings them back exactly as they were.
App: tinker-timeclock — ~/tinker-timeclock/js/app.js, js/firebase-data.js
Why now: The roster has 37 entries; only 18 are in the live Fall 2026 schedule. The existing "Remove" button is a hard, permanent delete (roster entry + both schedule docs, no undo) — too destructive for routine end-of-term cleanup.
Risk: Low data risk (no field this plan touches is ever deleted — only two new boolean flags are added/toggled). Main risk is UI coverage: several views read schedule data directly and must all respect the new flag, or an archived person could still show up somewhere.
Reversible: Yes, by design — Unarchive clears both flags and restores full visibility with zero data loss.

Archiving writes exactly one flag: active: false on the roster entry in timeclock_settings/employees. No new field is added to timeclock_schedules at all. The 3 places that already check roster active (kiosk PIN, roster settings list, employee picker) are fixed for free, as before.

Filter once, centrally, keyed off the roster — not a second flag. loadSchedulesData() (app.js:2770-2788) already loads employeeRoster alongside allSchedules. It's changed to partition schedule docs by looking up each one's owner in the roster (via the existing employeeRoster.find(e => e.id === sched.uid || e.claimedBy === sched.uid) resolution already used by getSchedName() at app.js:2792) and checking that person's active field — producing allSchedules (roster active — every existing consumer keeps the name and needs zero code changes) and archivedSchedules (roster inactive). Clarified after second-model review caught an inconsistency: Phase 2's "Show Archived" panel in Settings is built directly from employeeRoster (filtered to active === false), not from archivedSchedules — archivedSchedules exists purely as the internal complement needed to test the partition logic (see the pure-function fix below) and isn't rendered as its own list anywhere.
Considered and rejected — a second archived flag directly on the schedule doc (original draft of this plan): works in isolation, but Studio Hub's own roster-writing code (syncTimeclockRoster / addToTinkerTickerRoster) only ever touches the roster document, not individual schedule docs. If a future Studio-Hub-driven offboarding flow flips active:false on the roster directly, a second, Ticker-only flag it doesn't know about would silently go unset — the person would vanish from the roster list and kiosk but keep showing up in Who's Working. Keying everything off the one field both systems already write eliminates that failure mode entirely, and is also less code.
Considered and rejected — editing all 4 render functions individually: works, but multiplies the chance of missing one, and every future new consumer of schedule data would need to remember the same check again. A single choke point is safer to review and safer long-term.
Considered and rejected — moving/blanking recurring/overrides into a backup field and restoring on unarchive: works, but creates two copies of the same data that can drift, and is meaningfully more code than a boolean flag for the same visible result. A flag is trivially reversible; a data move is not risk-free.

Cross-app coordination with Studio Hub's offboarding plan — resolved, now confirmed against the actual registered Studio Hub plan (studio-hub-archive-employees.html, plan__ArypVn99fHf), not just a hypothetical.

The two plans solve genuinely different problems that happen to share the word "archive":

  • Studio Hub's plan adds an active flag to users/{uid} and gates it into the five Firestore rule helpers every one of the 21 apps shares (isAdmin, isManager, isManagerOrAbove, hasAppAccess, belongsToStudio). This controls authentication/authorization — can this person read or write anything, in any app, at all. It is confirmed scoped to users/{uid} and Studio Hub's own rules/UI only — it does not touch timeclock_settings/employees.roster[] or any file in tinker-timeclock/.
  • This plan (Tinker Ticker) controls schedule/kiosk visibility — does this person's shift show up in Who's Working, Schedule Builder, or the kiosk PIN pad — entirely independent of whether they can still technically log in anywhere.

Why they don't call into each other, even though both use the word "active": saveEmployeeRoster() (and Studio Hub's own existing syncTimeclockRoster / addToTinkerTickerRoster) re-save the entire roster array on every write — there is no partial/per-field update path for that document. Two systems writing to it independently, near the same moment, risk one silently clobbering the other's unrelated concurrent change (e.g. a PIN just set in Ticker). Since this plan's single-flag design already makes Ticker's own Archive button fully sufficient for Ticker's views, Studio Hub's plan has no need to touch the Ticker roster at all — and it doesn't, by explicit design.

Net result — this is a deliberate two-click "fully offboarded," not a bug: to fully offboard someone today, Christie archives them in Studio Hub (revokes login everywhere) and, separately, archives them in Ticker (hides them from schedule/kiosk views). Neither plan wires a single button that triggers both. The Studio Hub plan explicitly logs this as a deliberate non-goal for now, with a shared trigger noted as a plausible fast-follow once both features exist and are proven stable — not something either plan should try to build speculatively before that.

Phase 1 — Data layer: archive/unarchive functions + centralized filter

Acceptance criteria: Two new functions, archiveEmployee(empId, name) and unarchiveEmployee(empId, name), mirroring the existing removeEmployee signature/pattern. Archiving sets active:false on the roster entry only — via the existing saveEmployeeRoster full-array-save convention already used by every other roster mutation in this file (add/remove/claim/set-PIN) — not a new write pattern. No timeclock_schedules document is touched by either function. The actual partitioning logic is extracted into a standalone, exported pure function — partitionSchedulesByRosterActive(allSchedules, employeeRoster) → {active, archived} — that loadSchedulesData() calls to populate allSchedules/ archivedSchedules. It defaults any schedule doc with no matching roster entry to active (visible), matching today's behavior for the existing Unknown/Reassign path. renderOrphanedSchedules()'s own roster lookup is fixed to stop treating an archived entry as "no match."

Phase 2 — Roster settings UI: Archive button + "Show Archived" panel

Per Christie's comment: this must not add clutter to the default Settings view — archived entries live behind the toggle, full stop, never inline in the main list.
