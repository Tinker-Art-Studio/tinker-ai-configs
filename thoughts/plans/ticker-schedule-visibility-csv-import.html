Current state (confirmed by reading the code, not assumed)

  • Every schedule doc already has a clean current/future split: recurring/overrides (current) and an optional futureSchedule sub-object with its own validFrom/ validUntil that automatically takes over once its start date arrives. This is resolved by getShiftForDate() (js/app.js:3503-3530) and used everywhere in the app. This plan does not change that mechanism — it only fixes how it's displayed and adds a better way to write to it.
  • Bug found: in renderAllSchedulesList() (js/app.js:3190-3255), the "Days: Mon, Tue…" line correctly resolves for today (swaps to futureSchedule.recurring once active), but the "Overrides: N" badge (js/app.js:3209, 3240) is Object.keys(sched.overrides || {}).length — an unfiltered lifetime count that includes every past date ever written, including old approved/withdrawn time-off churn. It never looks at futureSchedule.overrides either. This is the direct cause of confusion about whether Schedule Builder shows current or stale data.
  • Dangerous leftover found: the existing "Import Spreadsheet Schedules" button (index.html, wired to handleImportSpreadsheetSchedules(), js/app.js:5710-5753) is not a reusable tool — it's one-time migration code from last semester's transition. It writes a hardcoded constant (SPREADSHEET_SCHEDULES, js/app.js:5512+, ~200 lines of last semester's data) straight into the CURRENT recurring/overrides fields via plain saveSchedule() → .set(..., {merge:true}), with a hardcoded validUntil: '2026-05-09' — a date that's already passed. If anyone clicked this button today, it would silently corrupt every current live schedule with stale spring data, using the exact recursive-merge bug already identified and fixed once this session in the Fall 2026 import tool. This plan removes it.
  • The "AI Schedule Builder" free-text parser (handleAiParse, js/app.js:4663+, calling /.netlify/functions/schedule-builder) is a separate, working feature for one-off edits ("Remove Kathy from Thursday March 5"). This plan does not remove it — it stays for small ad hoc tweaks. The new CSV uploader is specifically for bulk, whole-semester future-schedule authoring, which is what free text is bad at.
  • The proven safe-write pattern already exists in this session's fall-2026-import.html (moved to ~/Desktop/tinker-tools-not-deployed/, not part of the app): name resolution by first name against the live roster (ambiguous/no-match blocks the row), a dry-run preview table with per-row status, a downloadable pre-write JSON snapshot required before the write button unlocks, and mergeFields (not merge:true) so the write replaces named top-level fields wholesale instead of recursively merging stale nested data. This plan turns that one-off tool into a permanent, reusable feature in the app itself.

Phase 1 — Fix the Overrides badge

Acceptance criteria

Every schedule card in Schedule Builder shows an overrides count that only reflects today-forward dates on whichever schedule (current or active future) is actually in effect — never a lifetime total of dead dates.

Given a schedule doc has 10 overrides dated in the past and 3 dated today or later, when Schedule Builder renders that card, then the badge reads "Overrides: 3", not "Overrides: 13".
Given a person has an active futureSchedule in effect today, when Schedule Builder renders their card, then the overrides count comes from futureSchedule.overrides (date-filtered), matching what the "Days" line already correctly does — not from the base overrides map.
Given a schedule doc has zero overrides at all, when rendered, then the badge reads "Overrides: 0" — no error, no "undefined."

Firebase safety checklist

  • Read-only display change — no Firestore write anywhere in this phase.
  • No rules change.

Phase 2 — Remove the dangerous stale migration button

Acceptance criteria

The "Import Spreadsheet Schedules" button and its hardcoded SPREADSHEET_SCHEDULES constant are gone. Nobody can accidentally click a button that overwrites current live schedules with last semester's frozen data.

Given Settings is open, when an admin looks at the roster panel, then there is no "Import Spreadsheet Schedules" button.
Given the codebase after this phase, when searched for SPREADSHEET_SCHEDULES or handleImportSpreadsheetSchedules, then nothing is found — dead code fully removed, not just unwired.

Firebase safety checklist

  • Deletion of dead client code only — no data touched, no rules change.

Phase 3 — CSV future-schedule uploader

Acceptance criteria

Christie composes a CSV (with Claude/chat) listing next semester's schedule, uploads it, sees a dry-run preview of exactly what will change per person (including conflicts with any existing active future schedule), downloads a pre-write snapshot, and only then can commit the write — which touches only futureSchedule, never the current live recurring/overrides.

CSV format (proposed, confirm with Christie before building)

One row per person per recurring day: name, day, start, end, studio, validFrom, validUntil. A person can have multiple rows (one per working day). validFrom/validUntil must be identical across all of one person's rows (validated, not silently averaged).

Given a CSV with a name that matches exactly one active roster entry, when parsed, then the row resolves to that person's real uid (claimedBy || id, same as the existing import tool) and shows "ready" in the dry-run table.
Given a CSV name matches zero or more than one active roster entry, when parsed, then that row is flagged no-match/ambiguous and blocked from writing — never guessed.
Given a person already has an active or pending futureSchedule whose date range overlaps the new CSV's range, when the dry-run runs, then that row is flagged as a conflict and requires explicit confirmation before being included in the write — never silently overwritten.
Given the dry-run preview is showing, when Christie has not yet downloaded the pre-write snapshot, then the write button stays disabled.
Given the write executes, when checked against Firestore afterward, then only the futureSchedule field changed on each written doc — the current recurring/overrides fields are byte-for-byte unchanged, verified via mergeFields: ['futureSchedule'], not merge:true.
Given a malformed CSV (missing column, unparseable time, mismatched validFrom across one person's rows), when parsed, then the specific bad row is flagged with a clear error and blocked — the rest of the file's valid rows are unaffected.

Firebase safety checklist

  • Write is mergeFields: ['futureSchedule'] only — never touches current schedule fields.
  • Dry-run required before write; write button gated on snapshot download, mirroring the Fall 2026 tool.
  • No rules change — futureSchedule is already a permitted field within an already-permitted timeclock_schedules write.
  • Name resolution never guesses — no-match/ambiguous always blocks, never silently picks one.

Completeness check

If interrupted after Phase 1 or 2: no partial state — each phase is independently complete and safe to ship alone. If interrupted mid-Phase-3 build: the CSV uploader is new, additive UI; nothing is destructive until a real write is triggered, and the write itself requires the explicit snapshot-then-write UI gate, so there's no way to leave Firestore in a half-written state from an interrupted coding session.
