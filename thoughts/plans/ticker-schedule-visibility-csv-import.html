Phase 1 — Fix the Overrides badge

Acceptance criteria

Every schedule card in Schedule Builder shows an overrides count that only reflects today-forward dates on whichever schedule (current or active future) is actually in effect — never a lifetime total of dead dates.

Given a schedule doc has 10 overrides dated in the past and 3 dated today or later, when Schedule Builder renders that card, then the badge reads "Overrides: 3", not "Overrides: 13".
Given a person has an active futureSchedule in effect today, when Schedule Builder renders their card, then the overrides count comes from futureSchedule.overrides (date-filtered), matching what the "Days" line already correctly does — not from the base overrides map.
Given a schedule doc has zero overrides at all, when rendered, then the badge reads "Overrides: 0" — no error, no "undefined."
Given the same stale-count scenario as above, when the schedule's detail modal is opened via viewScheduleFromList() instead of just the card list, then it shows the same corrected, date-filtered count — the fix applies to both locations, not just the summary card.

Firebase safety checklist

  • Read-only display change — no Firestore write anywhere in this phase.
  • No rules change.
  • Test coverage: this repo's established pure-function test pattern (schedule-helpers.test.js) — extract the date-filtering logic into a testable function rather than inlining it in the render functions, per this repo's own precedent from partitionSchedulesByRosterActive().

Phase 3 — CSV future-schedule uploader

Acceptance criteria

Christie composes a CSV (with Claude/chat) listing next semester's schedule, uploads it, sees a dry-run preview of exactly what will change per person (including conflicts with any existing active future schedule), downloads a pre-write snapshot, and only then can commit the write — which touches only futureSchedule, never the current live recurring/overrides.

CSV format (proposed, confirm with Christie before building)

One row per person per recurring day: name, day, start, end, studio, validFrom, validUntil. A person can have multiple rows (one per working day). validFrom/validUntil must be identical across all of one person's rows (validated, not silently averaged).

Given a CSV with a name that matches exactly one active roster entry, when parsed, then the row resolves to that person's real uid (claimedBy || id, same as the existing import tool) and shows "ready" in the dry-run table.
Given a CSV name matches zero or more than one active roster entry, when parsed, then that row is flagged no-match/ambiguous and blocked from writing — never guessed.
Given a person already has an active or pending futureSchedule whose date range overlaps the new CSV's range, when the dry-run runs, then that row is flagged as a conflict and requires explicit confirmation before being included in the write — never silently overwritten.
Given the dry-run preview is showing, when Christie has not yet downloaded the pre-write snapshot, then the write button stays disabled.
Given the write executes, when checked against Firestore afterward, then only the futureSchedule field changed on each written doc — the current recurring/overrides fields are byte-for-byte unchanged. Confirmed against the real SDK (this repo is 100% Firebase v8 compat syntax, no v9 updateDoc anywhere): the write must be docRef.set({futureSchedule: {...}}, {mergeFields: ['futureSchedule']}) — mergeFields is a .set() option, not valid on .update(). This protects sibling fields (recurring/overrides) but gives zero protection to sub-fields within futureSchedule itself — the write must reconstruct that whole sub-object (recurring, overrides, validFrom, validUntil) each time, following the existing precedent in handleAiSaveAll() (js/app.js:4941-4948), not assume partial-field merging happens automatically inside it.
Given the CSV has two rows for the same person on the same day, when parsed, then this is flagged as an error on that row, not silently resolved by taking the first or last one.
Given a CSV's day column uses a different case or format than the canonical Mon/Tue/Wed/Thu/Fri/Sat/Sun keys this app uses everywhere else, when parsed, then it's normalized to the canonical form or rejected with a clear error — never silently written under a mismatched key that the rest of the app won't recognize.
Given an empty CSV, or a CSV where every row fails to parse, when uploaded, then the dry-run clearly shows zero ready rows and the write button never becomes enabled — no confusing empty-success state.
Given the write is in progress across many people and fails partway through (network interruption, one doc's write rejected), when that happens, then the dry-run table clearly marks which specific rows succeeded vs. failed — writes are per-document, not a single atomic transaction, so a partial failure is a real possible state that must be visible, not hidden.
Given a CSV name resolves to a roster entry that is archived (active: false), when parsed, then it's blocked the same way a no-match is — archived people don't get new future schedules written for them.
Given a malformed CSV (missing column, unparseable time, mismatched validFrom across one person's rows), when parsed, then the specific bad row is flagged with a clear error and blocked — the rest of the file's valid rows are unaffected.

Firebase safety checklist

  • Write is mergeFields: ['futureSchedule'] only — never touches current schedule fields. Uses .set(docRef, data, {mergeFields:[...]}) (v8 syntax, matching this whole codebase) — not updateDoc.
  • Dry-run required before write; write button gated on snapshot download, mirroring the Fall 2026 tool.
  • No rules change — futureSchedule is already a permitted field within an already-permitted timeclock_schedules write.
  • Name resolution never guesses — no-match/ambiguous always blocks, never silently picks one.
  • No CSV parsing library exists in this repo today — hand-rolled parsing carries real risk for quoted fields/embedded commas. Keep the CSV format simple enough (plain fields, no embedded commas) that naive splitting is safe, or bring in a minimal, dependency-free parser rather than writing a fragile one.
  • After a successful write, check whether timeclock_settings/futureSchedule (the separate global summary doc feeding the AI Schedule Builder UI) needs refreshing too, so it doesn't go stale relative to the per-person data this phase actually writes.
  • Test coverage required: an emulator test (this repo's *.emulator.test.js pattern, via firebase-admin against the Firestore emulator, no mocks) proving a CSV write really only touches futureSchedule and leaves recurring/overrides untouched — this is the core safety claim of this phase and deserves a real test, not just code review.
Shared prerequisite, found by second-model review — fix before Phase 3 depends on it. saveSchedule() and deleteSchedule() (js/firebase-data.js:205-230) are not async and don't await their internal .set()/.update() calls — they return true before the write is actually durable, and swallow rejections. This is the same class of bug already found and fixed once this session in addClockEntry() during the Archive Employees feature. Phase 3's CSV writer either needs its own direct, properly-awaited write (bypassing saveSchedule()), or this shared function should be fixed once, the same way addClockEntry() was — recommended, since Plan B's Phases 2-4 rely on the equivalent updateTimeOffRequest() having the same fix.

Completeness check

If interrupted after Phase 1 or 2: no partial state — each phase is independently complete and safe to ship alone. If interrupted mid-Phase-3 build: the CSV uploader is new, additive UI; nothing is destructive until a real write is triggered, and the write itself requires the explicit snapshot-then-write UI gate, so there's no way to leave Firestore in a half-written state from an interrupted coding session.
